계획 — 다중 프로세스 테스트 하니스

상태: 초안 — 소유자 승인 대기

1. 목표

단일 프로세스·태스크 체인 방식의 테스트 스위트를 다중 프로세스 하니스로 교체한다. 러너가 테스트렛(testlet) 하나당 자식 EngineTest 프로세스를 하나씩 생성하고, 타임아웃(기본 16초, 테스트렛별 재정의 가능)을 강제하며, 멈춘 자식을 kill 하고, 결과를 취합한다. 엔진은 프로세스 관리 기능을 OSAL 역량(OSProcess)으로 획득하고, 테스트 하니스는 그 첫 번째 소비자가 된다.

2. 확정된 결정 사항

#결정 항목선택
D1격리 단위테스트렛별 (약 429개의 수명이 짧은 프로세스)
D2생성 방식같은 바이너리를 argv 선택자와 함께 재실행(re-exec)
D3러너 위치EngineTest 내부의 러너 모드 (새 타깃 없음)
D4플랫폼Linux + macOS + Windows, 전부 검증
D5기존 단일 프로세스 모드삭제 — 다중 프로세스 전용
D6타임아웃기본 16초, 테스트렛별 재정의 가능
D7자식 출력파이프 우선: 러너가 배수 (File 모드는 선택 옵션으로 유지)
위험 (D4 관련): 이번 세션에서는 Windows 호스트를 사용할 수 없었다 (저널의 기존 선례). WindowsProcess.cpp는 동일한 계약에 맞춰 작성하고 가능한 범위에서 컴파일 검증을 진행한다. 실제 Windows 실행은 소유자가 수행하는 것으로 마무리된다. 조용히 통과 처리하지 않고 열린 게이트로 기록한다.

4. 작업 항목

4.1 OSProcess (신규 OSAL 역량)

  • Engine/OSAL/OSProcess.h — OSThread 패턴을 따르는 OS 네임스페이스의 자유 함수들. OSProcessTest 컬렉션을 헤더에 선언.
  • Engine/OSAL/OSProcess.cpp — 공통 코드 + OSProcessTest::Prepare.
  • LinuxProcess.cpp (posix_spawn 계열), OSXProcess.cpp, WindowsProcess.cpp (CreateProcess / WaitForSingleObject / TerminateProcess / GetExitCodeProcess).
  • API 표면(정확한 시그니처는 구현 중 확정, 계약은 문서화): 생성(경로, 인자, 스트림별 리디렉션: 상속/파일/파이프), 상태 + 종료 코드를 반환하는 슬라이스 대기, kill, 핸들 닫기(Windows HANDLE 위생 관리).
  • 문서: 함수마다 한 페이지, 테스트 컬렉션의 클래스 페이지, 설계 문서 docs/design/OSProcess_Design.html (플랫폼 매핑, 핸들 수명주기, 좀비/HANDLE 누수 방지, 타임아웃 의미론).
  • API 설계 (파이프 우선, 제안):

타입

타입계약
EProcessStream StdOut / StdErr — 연산이 다루는 자식 스트림 선택.
EStreamMode Inherit / File / Pipe — ProcessSpawnDesc의 스트림별 리디렉션 모드.
ProcessSpawnDesc executablePath, arguments, 스트림별 EStreamMode, File 모드용 파일 경로.
ProcessPipe 파이프 한 개: 비블로킹 Read(buffer, maxBytes) — >0 읽은 바이트, 0 지금은 없음, -1 EOF(자식이 끝을 닫음). CloseReadEnd().
ProcessHandle 네이티브 핸들(pid_t / HANDLE) + stdout/stderr 읽기 끝의 ProcessPipe (Pipe 모드에서만 유효). IsValid(), GetStdoutPipe(), GetStderrPipe().
EProcessWaitResult Exited / TimedOut / Failed.

함수

함수계약
ProcessHandle SpawnProcess(const ProcessSpawnDesc& desc) noexcept desc대로 자식을 생성한다. Pipe 모드에서 자식이 쓰기 끝을 받고 부모의 쓰기 끝 복사본은 spawn 내부에서 닫힌다 — 열어 두면 EOF가 영원히 오지 않는다. File 모드에서는 해당 스트림이 지정 경로로 리디렉션된다. 실패 시 유효하지 않은 핸들.
EProcessWaitResult WaitForProcess(ProcessHandle& handle, uint32_t timeoutMilliSecs, int& exitCode) noexcept 블로킹 대기가 아니라 타임 슬라이스: 최대 timeoutMilliSecs만큼 기다린 뒤 Exited(종료 코드 기록) / TimedOut(자식 생존) / Failed를 답한다. 슬라이스인 이유는 호출자가 대기 사이에 파이프를 배수하기 위해서다.
void KillProcess(ProcessHandle& handle) noexcept 강제 종료 (SIGKILL / TerminateProcess). 뒤에는 회수하는 WaitForProcess(좀비)와 마지막 배수가 따라야 한다.
void CloseProcessHandle(ProcessHandle& handle) noexcept 파이프와 네이티브 핸들을 닫는다 (Windows CloseHandle; POSIX에서 회수는 WaitForProcess의 몫이고 나머지를 여기서 해제).
배수 루프가 설계의 이유다. 파이프의 커널 버퍼(POSIX 약 64KB)는 아무도 읽지 않으면 차고, 자식의 쓰기가 블록되고, 러너는 "파이프가 막혀 멈춘" 자식을 멈춘 것으로 오해해 kill 한다 — 거짓 타임아웃. 그래서 WaitForProcess는 슬라이스다. 러너의 루프: 파이프 배수 → WaitForProcess(50ms) → Exited까지 반복, 데드라인 도달 시 KillProcess → 마지막 배수.

예제 (설명용; 정확한 시그니처는 구현 중 확정)

러너의 전체 주기 — 파이프로 생성, 대기하며 배수, 데드라인 kill, 정리:

OS::ProcessSpawnDesc desc;
desc.executablePath = engineTestPath;
desc.arguments = {"EngineTest", "--testlet", "37"};
desc.stdoutMode = OS::EStreamMode::Pipe;
desc.stderrMode = OS::EStreamMode::Pipe;

OS::ProcessHandle child = OS::SpawnProcess(desc);
if (!child.IsValid())
{
	RecordSpawnFailure(testletIndex);
	return;
}

int exitCode = 0;
const auto deadline = std::chrono::steady_clock::now() + std::chrono::seconds(16);
OS::EProcessWaitResult result = OS::EProcessWaitResult::Failed;

while (true)
{
	AppendToLog(testletIndex, DrainToString(child.GetStdoutPipe()), DrainToString(child.GetStderrPipe()));

	result = OS::WaitForProcess(child, 50, exitCode);
	if (result != OS::EProcessWaitResult::TimedOut)
	{
		break;
	}

	if (std::chrono::steady_clock::now() >= deadline)
	{
		OS::KillProcess(child);                    // SIGKILL / TerminateProcess
		OS::WaitForProcess(child, 1000, exitCode); // 좀비 회수
		AppendToLog(testletIndex, DrainToString(child.GetStdoutPipe()), DrainToString(child.GetStderrPipe()));
		break;
	}
}

OS::CloseProcessHandle(child);

배수 헬퍼 — ProcessPipe::Read의 세 갈래 답변의 사용:

std::string DrainToString(OS::ProcessPipe& pipe)
{
	std::string out;
	char buffer[4096];
	while (true)
	{
		const int bytes = pipe.Read(buffer, sizeof(buffer));
		if (bytes <= 0)
		{
			break; // 0 = 지금은 없음, -1 = EOF
		}
		out.append(buffer, static_cast<std::size_t>(bytes));
	}
	return out;
}

파일 모드 — 같은 생성, 출력만 테스트렛별 로그로 리디렉션:

OS::ProcessSpawnDesc desc;
desc.executablePath = engineTestPath;
desc.arguments = {"EngineTest", "--testlet", "37"};
desc.stdoutMode = OS::EStreamMode::File;
desc.stderrMode = OS::EStreamMode::File;
desc.stdoutFilePath = "build/Applications/EngineTest/Dev/testlet-logs/037.log";
desc.stderrFilePath = "build/Applications/EngineTest/Dev/testlet-logs/037.log";
  • 핸들 타입은 하나, 별도의 id 타입은 없다: POSIX에서 pid_t는 id이자 핸들이고, Windows에서도 생성 시 얻은 HANDLE이 이 API의 모든 호출에 답한다 (숫자 id는 구현 세부로 남고, 진단이 필요해지면 GetProcessId로 얻을 수 있다). 러너는 날 id를 소비할 일이 없으므로 API도 노출하지 않는다.
  • 함께 선언되는 보조 타입: ProcessHandle, ProcessPipe, ProcessSpawnDesc, EProcessStream, EStreamMode, EProcessWaitResult — 위 표의 계약 참조.

8. 부록 — OS별 프로세스 API (참고자료)

OSProcess 구현을 위한 참고 자료. 매핑 표가 실제 작업 계약이고, 플랫폼별 표는 그 뒤에 있는 원자료다.

mode — r 또는 w		stdio FILE*; pclose는 대기 상태.편의 래퍼: pipe + fork + 셸(sh -c) 실행. pid를 돌려주지 않아 kill·타임아웃·stderr 분리가 모두 불가 — 이 하니스가 쓰지 않는 이유. 내부는 posix_spawn이 조립하는 것과 같은 pipe/fork/exec/wait 순서다.

타입과 객체: pid_t (프로세스 id이자 유일한 핸들), sigset_t, posix_spawn_file_actions_t, posix_spawnattr_t, W* 매크로로 해석하는 대기 상태 int, 파이프 fd 쌍.

pid_t 값 범위 — pid_t는 Linux(glibc)와 macOS(__darwin_pid_t) 양쪽 모두 부호 있는 32비트 int이므로 ProcessHandle의 int pid 유니언 멤버가 정확히 대응한다.

값의미
1 ~ pid_max실제 프로세스. Linux: 기본 32768, 64비트에서 최대 4194304 (2²²); macOS: 100000 아래에서 순환.
0실제 프로세스가 아님 — kill/waitpid에서 "호출자의 프로세스 그룹". 무효 센티널; kill(0, …)은 호출자 자신의 그룹을 시그널하므로 IsValid() (pid > 0)가 KillProcess를 게이트해야 함.
-1kill/waitpid에서 "모든 프로세스" — 핸들에 저장하지 않음.
≤ -2kill에서 프로세스 그룹 id — 핸들에 저장하지 않음.

성공한 생성은 0이나 음수 pid를 절대 내놓지 않는다; posix_spawn 실패 시 pid 출력은 미정의(unspecified)이므로 실패 경로는 센티널을 명시적으로 써야 한다.

헤더 — 위 함수들은 아래 여섯 헤더에서 선언된다; macOS SDK에서 직접 검증했고 Linux glibc도 같은 POSIX 헤더를 쓴다.

헤더선언
<unistd.h>fork, execve/execvp, pipe, getpid/getppid, _exit
<signal.h>kill, SIGKILL, sigset_t
<sys/wait.h>waitpid/waitid/wait, WNOHANG, WIFEXITED/WEXITSTATUS, WIFSIGNALED/WTERMSIG
<fcntl.h>fcntl, O_NONBLOCK (<sys/fcntl.h>의 우산 헤더)
<spawn.h>posix_spawn, posix_spawn_file_actions_*, posix_spawnattr_*와 그 타입들
<stdio.h>popen/pclose — 완전성을 위해 기록; 하니스는 사용하지 않음
<sys/types.h>pid_t (<unistd.h>를 통해 전이적으로도 도달)
주의사항
  • fork()와 exec() 사이에서는 async-signal-safe 호출만 합법 — 멀티스레드 부모에서 그 외의 것은 정의되지 않음. 러너가 엔진 없이 생성하고 posix_spawn을 선호하는 이유가 바로 이것.
  • kill된 자식은 waitpid로 회수될 때까지 좀비 — KillProcess 뒤에는 타임아웃 경로를 포함해 항상 회수하는 WaitForProcess가 따라야 함.
  • SIGKILL로 종료된 자식은 종료 코드가 아니라 WIFSIGNALED로 나타남.

예제 — 파이프로 연결된 stdout으로 생성, 배수, 대기, kill (C, POSIX):

이 예제의 컴파일·실행까지 검증된 완결판은 Examples/OSProcessPipeExample/posix_pipe_spawn.c에 있다(독립 실행형, 엔진 무의존; 이 호스트에서 run.sh로 빌드·실행: 정상 종료·데드라인 kill 실행 모두 검증). Windows 쌍둥이는 Examples/OSProcessPipeExample/win32_pipe_spawn.cpp와 run.bat(Windows 호스트에서의 컴파일·실행은 대기 중). 

int fds[2];
pipe(fds);

posix_spawn_file_actions_t actions;
posix_spawn_file_actions_init(&actions);
posix_spawn_file_actions_adddup2(&actions, fds[1], STDOUT_FILENO); // 자식 stdout -> 파이프
posix_spawn_file_actions_addclose(&actions, fds[0]);               // 자식은 읽기 끝 불필요

posix_spawnattr_t attr;
posix_spawnattr_init(&attr);

pid_t pid;
const char* argv[] = {"EngineTest", "--testlet", "37", NULL};
posix_spawn(&pid, "/path/EngineTest", &actions, &attr, (char* const*)argv, environ);
posix_spawn_file_actions_destroy(&actions);
posix_spawnattr_destroy(&attr);

close(fds[1]);                       // 부모의 쓰기 끝을 지금 닫는다, 아니면 EOF가 영원히 안 온다
fcntl(fds[0], F_SETFL, O_NONBLOCK);  // 비블로킹 배수

char buffer[4096];
const ssize_t bytes = read(fds[0], buffer, sizeof(buffer)); // >0 데이터, -1+EAGAIN 없음, 0 EOF

int status = 0;
const pid_t done = waitpid(pid, &status, WNOHANG); // 0 = 아직 실행 중
if (done == pid && WIFEXITED(status))
{
	const int exitCode = WEXITSTATUS(status);
}

kill(pid, SIGKILL);        // 데드라인 도달 시
waitpid(pid, &status, 0);  // 좀비 회수

헤더 — 포함 하나로 전부 해결: <windows.h>가 위 표의 모든 API와 타입을 선언하는 SDK 파티션 헤더들을 끌어온다. 하니스 코드는 <windows.h>만 포함한다.

주의사항
  • STILL_ACTIVE (259)는 자식이 합법적으로 반환할 수 있는 종료 코드이기도 하므로, "종료했는가?"는 종료 코드가 아니라 대기 결과로 판단해야 함.
  • TerminateProcess는 정리 핸들러 없이 프로세스를 죽임; PROCESS_INFORMATION의 hThread도 닫지 않으면 누수됨.
  • 출력 리디렉션에는 세 가지가 모두 필요: 파일 핸들을 상속 가능하게 생성 (bInheritHandle = TRUE 또는 SetHandleInformation), STARTF_USESTDHANDLES 설정, CreateProcessW에 bInheritHandles = TRUE.

예제 — 완전한 리디렉션 배관을 갖춘 파이프 stdout (C++, Win32):

SECURITY_ATTRIBUTES sa{sizeof(SECURITY_ATTRIBUTES), nullptr, TRUE};
HANDLE readEnd = nullptr;
HANDLE writeEnd = nullptr;
CreatePipe(&readEnd, &writeEnd, &sa, 0);
SetHandleInformation(readEnd, HANDLE_FLAG_INHERIT, 0); // 읽기 끝은 부모에 남긴다

STARTUPINFOW si{};
si.cb = sizeof(si);
si.dwFlags = STARTF_USESTDHANDLES;
si.hStdOutput = writeEnd; // 자식 stdout -> 파이프 쓰기 끝
si.hStdError = writeEnd;

PROCESS_INFORMATION pi{};
CreateProcessW(L"...\\EngineTest.exe", commandLine, nullptr, nullptr, TRUE,
	0, nullptr, nullptr, &si, &pi);
CloseHandle(writeEnd); // 부모의 쓰기 끝을 지금 닫는다, 아니면 EOF가 영원히 안 온다

DWORD available = 0;
DWORD bytesRead = 0;
char buffer[4096];
if (PeekNamedPipe(readEnd, nullptr, 0, nullptr, &available, nullptr) && available > 0)
{
	ReadFile(readEnd, buffer, sizeof(buffer), &bytesRead, nullptr); // ERROR_BROKEN_PIPE = EOF
}

const DWORD wait = WaitForSingleObject(pi.hProcess, 50); // WAIT_OBJECT_0 / WAIT_TIMEOUT
if (wait == WAIT_OBJECT_0)
{
	DWORD exitCode = 0;
	GetExitCodeProcess(pi.hProcess, &exitCode);
}

TerminateProcess(pi.hProcess, 1);               // 데드라인 도달 시
WaitForSingleObject(pi.hProcess, 1000);
CloseHandle(pi.hProcess);
CloseHandle(pi.hThread);
CloseHandle(readEnd);

9. 부록 — IPC 기법 (참고자료)

하니스가 정확히 하나의 IPC 기법을 쓰는 이유, 그리고 대안들이 사들였을 것이다. 출처: 기법 분류(Wikipedia, POSIX), 커널 개입 분석(opencsf IPC 모델), 지연 시간 서열(UDS 약 5–10µs, TCP 루프백 약 15–30µs).

9.2 하니스 결정의 근거

  • 메시지 전달 계열(파이프, 소켓, 메시지 큐)은 교환마다 커널이 개입 — 데이터가 커널 메모리를 거쳐 복사된다. 공유 메모리는 매핑 후 시스템 콜이 없다. 하니스는 대량 데이터를 교환하지 않으므로 공유 메모리의 이점은 여기서 무의미하다.
  • 익명 파이프는 관련 프로세스(부모/자식) 사이에서만 쓸 수 있다 — 정확히 러너/자식 위상이다. 명명 파이프는 무관한 프로세스를 위한 것이다.
  • 하니스의 IPC 요구 전체는: 단방향 바이트 스트림(자식 출력), 종료 코드(대기의 답), 강제 종료(kill 시그널). 셋 모두 파이프 + waitpid/GetExitCodeProcess + SIGKILL/TerminateProcess 집합이 답하므로, 양방향 기법(UDS, 소켓), 무복사 기법(공유 메모리), 결합 없는 큐(메시지 큐)는 이식성과 코드 비용을 치르고 얻는 것이 없다.
