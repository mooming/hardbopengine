Signature

void Deallocate(Pointer ptr, SizeType size) noexcept

Function description

Defined in Engine/Memory/StackAllocator.cpp as StackAllocator::Deallocate(Pointer ptr, const SizeType requested) noexcept. Individual deallocation is legal on this allocator — that is the whole difference between it and a monotonic allocator — but it is legal in exactly one shape: the block must be the current top of the stack, and the byte count must round up to what the block was charged. Anything else is reported, not repaired.

SizeType size = requested;
{
	constexpr auto AlignUnit = Config::DefaultAlign;
	const auto multiplier = (size + AlignUnit - 1) / AlignUnit;

The byte count is a parameter rather than a lookup because the stack stores nothing per block: no header, no footer, no record of what Allocate handed out. The size pairing is tolerant within one alignment unit — allocate 20 bytes (charged 32), release with 17 (rounds to 32), and the comparison matches — because the same rounding is applied here that was applied there.

Out-of-order release is a logged, asserted failure that leaks silently in a Release build. On a mismatch the function logs an error naming the pointer it was given and the address it expected, calls Assert(false), and returns with the cursor exactly where it was — so those bytes stay charged and stay unreachable until the destructor drops the whole buffer. In Debug and Dev that assert aborts the process (hbe::Assert in Engine/Core/Debug.h calls std::abort()). In Release the same name resolves to an empty inline function, and the log line behind it is not printed either: MemoryManager::LogError forwards to MemoryManager::Log, whose entire body sits inside #if MEMORY_LOGGING_ENABLED, and Engine/Config/BuildConfig.h defines that as 0. A wrong-order release in a shipped build therefore strands its bytes with no trace at all. See Coverage for the one part of that claim no test demonstrates.
A stale handle to a reused offset can rewind a block that is still in use. Nothing in this class can detect a double release. Allocate a block, release it, allocate again — the next Allocate returns the very same address at the very same offset, because the cursor rewound. Now release the stale handle a second time: IsMine says true, Assert(cursor >= size) holds, and buffer + cursor == stalePtr + size matches, so the cursor rewinds again and the live block is handed back to the allocator while its holder is still using it. There is no block header and no generation counter, so no check exists that could catch this. Derived from the code above; no testlet in Engine/Memory/StackAllocator.cpp performs it, so it is named as a hazard rather than documented as observed behaviour.
A pointer that is not yours is forwarded — with the number you gave, not the rounded one. The first branch sends a foreign pointer to mmgr.Deallocate(parentID, ptr, requested). That is the correct route for a block that came from the parent through Allocate's overflow path, and it is the reason a caller may release every allocation it got from this object the same way regardless of which buffer it landed in. Note the asymmetry: the parent is charged back the requested count, which is the count the parent was originally given — while a block that really lives in this buffer is judged against the rounded count. A pointer that is not yours and was also not the parent's is forwarded anyway, and nothing in the manager's release path detects that (MemoryManager::Deallocate(TId id, void* ptr, size_t nBytes) checks id validity only).
A null pointer is not "not mine" in a harmless way. IsMine() compares against the buffer, so nullptr is below it and is treated as foreign, which lands in MemoryManager::Deallocate(TId id, void* ptr, size_t nBytes) — whose first act is if (unlikely(ptr == nullptr)) { Assert(nBytes == 0); return; }. Releasing null with a non-zero byte count therefore asserts in Debug and Dev; with 0 it is a clean no-op. Contrast PoolAllocator::Deallocate, which discards null silently before any dispatch.
What a rewind does to the rest of the stack. On a match the only effect is cursor -= size. Bytes below the released block keep their addresses and stay valid; the released address becomes immediately reusable by the next Allocate; and nothing clears or poisons the released memory first, so a pointer into a block you have released still reads the old bytes. That last property is what makes the stale-handle hazard above silent even in a checked build until someone writes through the wrong pointer.

Parameters

ParameterTypeRequirement
ptrPointerAn address this allocator returned, or a foreign address that should reach parentID. For a rewind it must be the most recent block not yet released.
sizeSizeTypeThe block's byte count. Rounded up to a multiple of Config::DefaultAlign (16) and then used both for the cursor >= size check and for the top-of-stack comparison, so it must round to the value Allocate charged.

Return value

Nothing. The function is noexcept and has no result: the only signal a caller gets for a release that did not happen is an assertion (checked builds) or a log line this configuration never prints. Whether the bytes actually returned is observable from outside only through GetUsage().

Examples

No engine or application source calls Deallocate on a stack allocator by name; this lambda, handed to MemoryManager::RegisterAllocator, is the call site. Anything releasing under an AllocatorScope over GetID() reaches this function through the manager's proxy dispatch — which is how the testlets in Engine/Memory/StackAllocator.cpp drive a String destructor into a cursor rewind and then assert stack.GetUsage() == 0. Because every one of those testlets allocates and releases in strictly nested order through one container at a time, the mismatch branch this page documents most heavily is never executed by them.
