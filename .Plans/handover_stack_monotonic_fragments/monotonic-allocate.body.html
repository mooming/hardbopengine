[[nodiscard]] TPointer Allocate(size_t size)

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::Allocate(const size_t requested). Round the request, compare it against what the buffer holds, then either advance the cursor or ask the parent. The cursor never moves backwards after this returns, which is the property the class is named for. 

size_t size = requested;
{
	constexpr auto AlignUnit = Config::DefaultAlign;
	const auto multiplier = (size + AlignUnit - 1) / AlignUnit;
	size = multiplier * AlignUnit;
}

const auto freeSize = GetAvailable();
if (unlikely(size > freeSize))
{
	auto& mmgr = MemoryManager::GetInstance();
	mmgr.LogWarning([size, freeSize](auto& ls)
	{ ls << "The requested size " << size << " is exceeding its limit, " << freeSize << '.'; });

	auto ptr = mmgr.Allocate(parentID, requested);

	return ptr;
}

auto ptr = reinterpret_cast<void*>(buffer + cursor);
cursor += size;

A block is size bytes at buffer + cursor, charged at the rounded size, and the cursor is the only bookkeeping: no header, no footer, no per-block record. Under PROFILE_ENABLED the call reports ReportAllocation(id, ptr, requested, size) — requested and charged kept apart, where the stack reports the rounded size in both slots.

Exhaustion does not fail — it silently changes which allocator owns the answer. When the rounded request exceeds GetAvailable(), the call becomes mmgr.Allocate(parentID, requested) and the memory arrives from the parent. Three consequences: the pointer is outside this buffer, so IsMine says no and a later Deallocate of it is forwarded to parentID and genuinely released — the only release this object ever honours; the count the parent was charged is requested, not the rounded size, so that is the number that must come back; and the block is not freed by this object's destructor, so it leaks past the allocator unless someone releases it.
The overflow path differs from the stack's in one call, and that call is the accounting. The stack routes its overflow through MemoryManager::FallbackAllocate(GetID(), parentID, requested), which records a fallback against the child's registration. This path calls MemoryManager::Allocate(parentID, requested) directly, so under PROFILE_ENABLED the same event appears as an ordinary allocation of the parent and is never attributed to this allocator. The warning the stack omits is present here — LogWarning with the rounded size and the free size — and is dead code in this tree: MemoryManager::LogWarning forwards to MemoryManager::Log, whose body is inside #if MEMORY_LOGGING_ENABLED, and Engine/Config/BuildConfig.h defines that as 0. So an overflow here is invisible in both the log and the profile.
The comparison uses the rounded size, and a zero-byte request is degenerate. With 10 bytes left, a request of 10 rounds to 16, 16 is greater than 10, and the request goes to the parent — the last partial Config::DefaultAlign of the buffer is unreachable for anything but a request that already fits it. A request of 0 rounds to 0 and the comparison never favours the parent, so the call returns buffer + cursor without moving the cursor: two zero-sized requests answer with the same address, neither owns anything, and when the buffer happens to be exactly full that answer is buffer + capacity — an address one past the end that IsMine disowns. Derived from the quoted code; no testlet allocates zero bytes.
Alignment is a stride, not a promise. Every charge is a multiple of 16, so consecutive blocks are exactly 16 bytes apart and no block starts misaligned relative to the buffer itself. What the class cannot promise is that the buffer is 16-byte aligned: that is inherited from whichever allocator answered the constructor, whose default path is SystemAllocator's malloc (Engine/Memory/SystemAllocator.h), and nothing checks or forces it. There is no aligned-allocation entry point on this class. See Coverage.
A null answer means the parent failed, and only a checked build says so before the caller does. MemoryManager::Allocate(TId id, size_t nBytes) ends with Assert(ptr != nullptr, "Allocation Failed"): in Debug and Dev that aborts; in Release the assertion is an empty inline function (Engine/Core/Debug.h) and the null travels back to a caller holding a [[nodiscard]] pointer. The same function returns nullptr for a zero-byte request before it reaches that assertion, so a parent-side call carrying a rounded-up non-zero size is the only way this returns null silently.

Parameters

ParameterTypeRequirement
sizesize_tBytes wanted. Rounded up to a multiple of Config::DefaultAlign (16) before anything is compared or charged. The count matters only on the overflow path, where the parent is given the unrounded value — and since no release of a buffer block does anything, keeping the number is useful only for releases of blocks that went to the parent.

Return value

TypeWhat you get
TPointer (void*)Useful bytes, or nullptr if the parent's answer was nullptr. Which allocator owns the block depends on whether the buffer could cover it: inside the buffer nothing can free it but this object's destructor; from the parent, a release through this object or the parent frees it. The attribute is [[nodiscard]] — a discarded pointer cannot be recovered, because the allocator keeps no record of what it handed out.

No engine or application source calls Allocate on a monotonic allocator by name; this lambda, handed to MemoryManager::RegisterAllocator, is the call site. Anything allocating under an AllocatorScope over GetID() reaches the function through the manager's proxy dispatch — which is how the testlets in Engine/Memory/MonotonicAllocator.cpp fill a 1 MiB buffer with an HVector<int> and a String without naming the allocator once. No testlet asks for more bytes than the buffer holds, so the overflow branch above is the least exercised code in this file.
