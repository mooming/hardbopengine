[[nodiscard]] size_t GetUsage() const

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::GetUsage() const. Two lines: an assertion about the cursor, then the cursor itself. 

Assert(cursor < capacity);

return cursor;

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::GetUsage() const

The number is bytes charged against the buffer, so it counts the rounding as well as the request: five allocations of 20 bytes report 160, not 100, because each was charged 32. It is a faithful picture of the buffer's state and an unfaithful picture of what the caller asked for.

On this class the figure can never go down, and that makes it the class's only visible contract. Deallocate ignores every release of a block that lives in the buffer, so nothing lowers cursor between construction and destruction. The class's own testlets in Engine/Memory/MonotonicAllocator.cpp assert exactly this after the allocating scope has closed, with the message "Monotonic Allocator doesn't provide deallocation." It is also the only way a caller can discover that a release it made did nothing: the function returns nothing and logs nothing.
The assertion is strict, so a working allocator eventually trips it. The condition is cursor < capacity, not <=. A buffer that has handed out its last byte has cursor == capacity, and asking it how much it is using then fires Assert — which aborts in Debug and Dev (hbe::Assert, Engine/Core/Debug.h) and does nothing in Release, where the function returns capacity as if nothing had happened. Because releases never reclaim bytes here, a full buffer is a state a busy arena reaches by design rather than by accident — and the same strict form fires immediately on a zero-capacity allocator, where 0 < 0 is false from construction. Derived from the source; no testlet fills a buffer or constructs a zero-capacity allocator, so this is stated as a hazard and named in Coverage.
It counts buffer bytes only, so it under-reports what a caller is holding. Blocks that arrived through Allocate's overflow path belong to parentID and never touched cursor. An allocator can report usage 0 while its caller holds live memory that will outlive it — those blocks are not freed by the destructor either.
Nothing here is the manager's accounting. Under PROFILE_ENABLED the manager keeps its own per-registration figures, fed by ReportAllocation and ReportDeallocation; this function reads cursor and is independent of them. That macro is 0 in Engine/Config/BuildConfig.h, so in this tree this function is the only usage number that exists — and it is the figure the destructor reports to the profile as one lump deallocation on the way out.

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocatorTest::Prepare(), Vector Allocation testlet

The test reads this figure once, after the container's destructor has already run, and requires it to be non-zero — a test that passes only because releases are ignored. The stack's version of the same test demands the opposite, and that pair of assertions is the clearest statement in the repository of the difference between the two classes.
