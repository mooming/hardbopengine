Signature

~StackAllocator()

Function description

Defined in Engine/Memory/StackAllocator.cpp as StackAllocator::~StackAllocator(). Two calls, in this order: the whole buffer goes back to the manager, then the registration is released. 

auto& mmgr = MemoryManager::GetInstance();
mmgr.Deallocate(bufferPtr, capacity);

From Engine/Memory/StackAllocator.cpp, StackAllocator::~StackAllocator()

Then mmgr.DeregisterAllocator(GetID()) — the two-argument overload taking srcLocation is the PROFILE_ENABLED branch, and that macro is 0 in this tree (Engine/Config/BuildConfig.h).

Who is asked for the bytes back is whichever allocator is current at the moment of destruction. Deallocate(bufferPtr, capacity) is the manager's two-argument overload, and it is a one-line redirect: 

void MemoryManager::Deallocate(void* ptr, size_t nBytes)
{
	Deallocate(GetScopedAllocatorID(), ptr, nBytes);
}

From Engine/Memory/MemoryManager.cpp, MemoryManager::Deallocate(void* ptr, size_t nBytes)

So the release is dispatched through the thread's current scope, not through the parentID the constructor recorded. Destroy the allocator under an unrelated scope and that scope's allocator is asked to free bytes it never allocated; the proxy record it goes through carries no owner, base address or range (Engine/Memory/AllocatorProxy.h), so nothing detects the mismatch in a default build. The same object destroyed with no scope open hands the bytes to the system allocator — which is right only if no scope was open at construction either. This is the asymmetry the PoolAllocator destructor in Engine/Memory/PoolAllocator.cpp closes by releasing through its recorded parent; this destructor does not.

The order of two declarations is therefore part of the contract. ScopedAllocator<TAlloc> (Engine/Memory/ScopedAllocator.h) declares the allocator before the scope, so the scope is destroyed first and the buffer is returned to the allocator that originally supplied it. The testlets in Engine/Memory/StackAllocator.cpp declare stack before scope for the same reason. Reversing either pairing — destroying an allocator while its own scope is still open — routes the buffer release into that allocator's own Deallocate, which reports the pointer as mismatched. No testlet covers that ordering.

Everything still allocated dies here, quietly. There is no per-block release and no leak report in this configuration: the buffer is freed in one call, so every pointer this object handed out from the buffer stops being valid the instant the destructor returns, whether or not it was ever released, and GetUsage is meaningless on a destroyed object. Blocks that arrived through the overflow path are the exception in the other direction — they belong to parentID, the destructor does not release them, and they stay allocated until someone releases them, through this object's Deallocate or through the parent directly. In a PROFILE_ENABLED build the manager warns on the way out (MemoryManager::DeregisterAllocator() logs "Memory leak is detected!" when the registration's usage is non-zero, and does not return the id to the pool in that case); that build does not exist in this tree.
The id is recycled, so a saved id outlives its meaning. MemoryManager::DeregisterAllocator() clears the proxy's function pointers and pushes the record back onto the manager's free pool (proxyPool.Push(allocator)), which makes the same number available to the next allocator registered. Keep an id only as long as the object is alive — a GetID value held past this destructor addresses whoever got that slot next.

Parameters

None.

Return value

Nothing. The destructor cannot report a failure, and the two failures it can encounter — a buffer released to the wrong allocator, a registration id that was never valid — are reported by the manager's log lines rather than to the caller.

Examples

StackAllocator stack("Test::StackAllocator::Deallocation", 1024 * 1024);
AllocatorScope scope(stack.GetID());
{
	String a = "0";
}

if (stack.GetUsage() != 0)
{
	ls << "Deallocation Failed. Usage should be zero, but " << stack.GetUsage() << lferr;
}

From Engine/Memory/StackAllocator.cpp, StackAllocatorTest::Prepare(), Deallocation testlet

The declaration order the destructor depends on, visible in the test's own layout: stack outlives scope, so the scope closes — restoring the allocator that was current before it — and only then does the stack destroy and return its buffer. The check beside it is the stack's distinguishing property: where a monotonic allocator would still be reporting non-zero usage here, the stack's cursor is back to zero because the string's release rewound it.
