Testlet

Engine/Test/Testlet.h  ·  hbe::Testlet  ·  class template, final

Class description

One registered test: the name it was registered under, and the lambda that runs it. Both are held inside the object, which is the entire reason the type exists. Registering a test must not allocate, because the suite is the thing that audits allocation, and a registration that quietly took from the global heap would be invisible to every allocator scope it is supposed to be measuring.

Measured, not argued: 151 of the 378 test names in this suite are longer than a small-string buffer holds, so a std::string name member heap-allocated for two in five tests. And std::function — the obvious way to hold the lambda — has a small-object buffer whose size is a library implementation detail; a closure larger than it allocates with nothing recorded anywhere the suite could read. Both cases are compile errors here instead, naming the limit that was exceeded.

Two design alternatives were considered and rejected, and the reasons are worth keeping:

AlternativeWhy it was not used
A borrowed view of the callable (a function_ref shape) It allocates nothing, and it does not work here. Every AddTest call hands over a temporary lambda that dies at the end of that expression, and a view cannot extend a lifetime. It would dangle, or refuse to compile — the same outcome with better manners.
A plain function pointer, as TRunnable does Zero allocation and zero capture, which the engine's own task contract already uses. Rejected on proportion: measured across the tree, 0 of 379 test lambdas are non-capturing (315 use [this]), so it would mean rewriting every test in the engine to reach the same storage property.

Ownership and lifetime. A testlet owns its name bytes and its closure bytes. Copies are deleted — copying an arbitrary closure would need a clone hook that nothing in the suite asks for. Moving one relocates the closure into the new storage and leaves the source with no dispatch table, so a moved-from testlet reports itself and does nothing rather than invoking a closure that no longer lives there.

Thread safety. Registration is main-thread only and happens before the run is posted. During the run each testlet is executed by exactly one thread — the one driving the base stream — and never concurrently with another testlet of the same collection.

Template parameters

ParameterDefaultMeaning
TClosureBytes48 Inline storage reserved for the closure. A parameter rather than a constant inside the type because the ceiling belongs where the captures are known — by whoever holds the testlets — and raising it should be a visible edit at the use site, not an edit to a shared type. The default is measured: 375 of 379 closures in this suite fit in 32 bytes, and the four that do not are all 40 (the importance-sampling tests, whose [&] captures hold pointers to locals, not the static generator they share). 48 is that maximum plus one word.

Class properties

NameTypeMeaning
ClosureBytesstatic constexpr size_t The storage this instantiation reserved for the closure, reported back to the caller that chose it.
MaxNameBytesstatic constexpr size_t Inline storage for the test name: 128. Long enough for the longest name measured in the suite today (105 characters) plus room for one more clause. Enforced by a static_assert in the constructor, so a longer name is a compile error at the registration site rather than a truncated label in a failure report.

Three static_asserts guard the parameters themselves: TClosureBytes > 0, TClosureBytes a whole number of words, and MaxNameBytes > 1.

Class methods

template <size_t TNameBytes, typename TClosure> Testlet(const char (&testName)[TNameBytes], TClosure&& closure)

Registers one test. The name is a char-array parameter rather than a pointer or a view, so only a literal compiles: that gives the buffer something to copy from, gives the per-testlet allocator the null terminator it needs as a property of the type, and refuses a computed name at its call site instead of dangling later. The closure is a template parameter so it arrives with its real type — that is what allows the size check below and keeps any allocation off the path. noexcept is deliberately absent: constructing an arbitrary closure is the case the coding standard points at when it declines to promise exception freedom for something whose body this type cannot see.

Preconditions. testName must be a literal of 2 to MaxNameBytes characters including its terminator; sizeof(closure) must fit TClosureBytes and must not be over-aligned. All are compile-time checks, not runtime ones.

Postconditions. The testlet owns a copy of the name and a constructed closure. Neither can outlive the testlet; both need no external storage.

Testlet(Testlet&& other) noexcept

Relocates. The name bytes are copied, the closure is placement-moved into this object's storage, and the source loses its dispatch table so its destructor has nothing to destroy. Required because the collections hold testlets in a vector that grows during registration. noexcept holds because the closures being relocated were written by this suite and the engine is exception-free.

Testlet(const Testlet&) = delete · operator= both deleted

A copy would need a clone hook for an arbitrary closure type, and nothing in the suite asks to duplicate a test.

~Testlet()

Destroys the closure through the dispatch table when there is one; a moved-from testlet destroys nothing.

void Run(TLogOut& outLog) const noexcept

Invokes the closure. outLog is a write-only parameter by the coding standard's out-prefix convention: a testlet's whole effect is what it writes there, plus whatever its assertions record. A testlet that has been moved from writes an error to std::cerr, asserts, and returns without running.

Thread-safety. Called by the thread driving the base stream, once per testlet, never concurrently with another testlet of the same collection.

Contract note. noexcept here is a promise about the suite, not about this function: a testlet signals failure by logging and asserting, and the engine is exception-free. A testlet that ever threw would terminate rather than unwind the run.

const char* GetName() const noexcept

The registered name, owned by this testlet and null terminated by construction, so a caller may print it freely.

Non-member helper functions

No free functions. One companion type lives in the same header:

TypeMeaning
TestletDispatch A POD of three function pointers — invoke, destroy, relocate — with one constexpr instance generated per closure type. Its address is stable and it needs no vptr, which is what lets a testlet be two words of bookkeeping plus its own storage.

Logging inside this type goes to std::cerr rather than the engine logger, following the rest of the Test module and deliberately so: pulling Log/Logger.h into this header would make every test file in the engine sensitive to the logger's own include order, which is a real fragility in the tree — HSTL/HUnorderedMap.h uses Memory::DefaultAllocator without including its header — found when this change tried it.

Coverage

No unit test exercises Testlet directly, and this page says so rather than implying otherwise. What covers it instead:

  • Every testlet in the engine is a Testlet. A broken one does not fail a test; it removes a test, and TestEnv's registered-versus-executed check makes that removal a run failure rather than a shorter green run.
  • Double execution is refused by name. TestEnv counts runs per testlet, because the suite's own totals cannot see this defect: a schedule that ran one testlet 372 times would still report 372 of 372.
  • The limits are compile-time and were fired on purpose. Setting the closure ceiling to 32 refused exactly four closures at their registration sites; setting MaxNameBytes to 100 refused the 105-character name at its own site. Those are the witnesses for the two decided numbers.
  • Relocation was mutated. Removing the relocate call from the move constructor makes the suite die by signal — detected, but as a crash rather than a named assertion, which is recorded here as the weaker half of this coverage.

Still allocated and disclosed: TestCollection::tests is a std::vector of testlets, so its buffer — roughly 372 × 192 bytes — comes from global operator new at registration. The testlets themselves allocate nothing; the array that holds them is the next thing that should move onto the engine's books.
