ReportDriveTimeout

Engine/Test/TestHelper.cpp free function in hbe::TestHelper declared in the header, defined in the source writes the error line that says a drive-until wait gave up, kept out of the template so a failure line does not drag the logging header into every translation unit that waits

Signature

void ReportDriveTimeout(TaskSystem& taskSystem, const char* waitingFor,
                        const std::chrono::milliseconds patience) noexcept
{
        Logger::Get().AddLog(taskSystem.GetName(), ELogLevel::Error, [waitingFor, patience](auto& logStream)
        {
                logStream << "A thread driving the engine loop gave up waiting for " << waitingFor << " after "
                                  << patience.count() << "ms. The work was still queued, so nothing was going to run it, and a caller that proceeds "
                                  "from here usually blocks on the very thing it waited for. The intake that should have drained it is the "
                                  "first thing to look at.";
        });
}

Declared at Engine/Test/TestHelper.h:15, defined at Engine/Test/TestHelper.cpp:13-26.

Function description

Called from exactly one place: the end of the driving branch of DriveUntil, after the bound expires with the predicate still false. Its only argument that the caller had not already passed is taskSystem, from which it takes GetName as the log line's source — the one reason a function that writes a sentence needs the system at all.

Why it is not inside the template. DriveUntil is a header template, so anything it calls is compiled into every translation unit that drives a wait. Naming Logger there would pull the logging header into all of them for a line that runs once, on failure. Keeping the report in a function defined in Engine/Test/TestHelper.cpp holds the template's includes to what the loop itself needs, which is the same reason a non-template body belongs in a source file at all.
It is declared above the template, and that is not a style choice. The call ReportDriveTimeout(taskSystem, waitingFor, patience) has argument types fixed at the template's definition, so it is a non-dependent call and is looked up in that definition context — a name declared later in the namespace is simply not visible to it. While both were members of TaskSystem the order meant nothing, because a class body is read complete; the first version of the header put the declaration after the template and failed to compile with use of undeclared identifier. Anyone tempted to re-group this header by topic rather than by dependency should expect the build, not a review, to catch it.
The other branch of DriveUntil never calls it. A caller that is not the engine-loop thread takes the sleep-poll path, and that path returns without reporting. So a wait that times out on an application thread is invisible in the log — correct in the sense that the thread could never have driven anything, misleading in the sense that the symptom looks like silence rather than like a misuse of the API.

The wording is the diagnosis, not decoration: "the work was still queued, so nothing was going to run it" points at the intake rather than at the waiter. The line exists because a suite that hangs reports nothing, which is how a missing drain looked for a while: no failing test, only a wall clock.

Parameters

ParameterTypeRequirement
taskSystem TaskSystem& Read only, for GetName, which becomes the log line's source string. It is a reference rather than a literal so the line still names TaskSystem when the report itself no longer lives in that class
waitingFor const char* The label the waiter was given, interpolated as-is. No ownership is taken, so it must still be valid when the log line is formatted — every call site passes a string literal
patience std::chrono::milliseconds The requested bound, printed as count() milliseconds — not a measurement of how long the wait actually took, which can run longer because the loop decrements a counter instead of reading a deadline

Return value

void. The log line is the entire effect: the waiter's own return value is decided by its predicate, not by this function.

The report is the last thing a failed drive does before handing its answer back, so a test that prints its own failure message afterwards has both halves: this line in the log, naming what was waited for and for how long, and the test's own message naming what the missing condition proves. Engine/Core/TaskSystem.cpp's aged-work tests read the boolean into a variable for exactly that second half — "aged-out count moved by N, DriveUntil reported true" — because a ceiling that drops work invisibly is the defect the test is looking for, and the count alone cannot tell an invisible drop from a slow one.
