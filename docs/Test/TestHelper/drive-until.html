DriveUntil

Engine/Test/TestHelper.h free function in hbe::TestHelper header template waits for a predicate by driving the base stream when the caller owns it, and by sleeping when it does not

Signature

template <class Predicate>
bool DriveUntil(TaskSystem& taskSystem, const char* waitingFor, Predicate&& isDone,
                std::chrono::milliseconds patience = std::chrono::milliseconds(30000)) noexcept
{
        TaskStream& baseStream = taskSystem.GetStream(TaskSystem::GetBaseTaskStreamIndex());
        auto remaining = patience;

        if (std::this_thread::get_id() != baseStream.GetThreadID())
        {
                while (!isDone() && remaining > std::chrono::milliseconds::zero())
                {
                        std::this_thread::sleep_for(std::chrono::milliseconds(1));
                        remaining -= std::chrono::milliseconds(1);
                }
                return isDone();
        }

        baseStream.SetNestedPumpAllowed(true);

        struct NestedPumpGuard
        {
                TaskStream& stream;
                ~NestedPumpGuard() { stream.SetNestedPumpAllowed(false); }
        } nestedPumpGuard{baseStream};

        while (!isDone() && remaining > std::chrono::milliseconds::zero())
        {
                taskSystem.Update();
                std::this_thread::sleep_for(std::chrono::milliseconds(1));
                remaining -= std::chrono::milliseconds(1);
        }

        if (!isDone())
        {
                ReportDriveTimeout(taskSystem, waitingFor, patience);
        }

        return isDone();
}

Function description

A function template, because a predicate cannot live anywhere else. Its purpose is the one wait that is legitimate on the thread that drives the engine: work is already queued, the caller needs it done, and on this engine the only way it gets done on this thread is for this thread to run it. Parking a stream thread on a condition variable is the shape the task system exists to avoid, and a testlet that simply blocks on a future is a testlet waiting for itself to be scheduled.

Every caller in this tree is a testlet, and every testlet runs as a task on the base stream, so every caller reaches the driving branch. That is what makes the wait honest rather than merely convenient: the condition becomes true because of the driving this call does, not because of a thread somewhere else that may or may not be scheduled.

The two behaviours

CallerWhat the loop doesOn giving up
The engine-loop thread — the one the base stream recorded at Engine/Core/TaskStream.cpp:305-307 Update plus a 1 ms sleep per iteration, nested pumping allowed for the duration and withdrawn by the guard on every exit path ReportDriveTimeout logs an error naming what was waited for and how long it tried
Any other thread Sleeps 1 ms and re-tests. It cannot drive anything — it does not own the base stream, and a second driver would break the one-driver rule that Update depends on Silent. The reporting call sits inside the driving branch only, so a foreign thread's timeout produces no log line at all
The inner loop calls taskSystem.Update(), not baseStream.Update(). A callback posted to the engine loop lives on the stream the loop drives, and a stream's pump is what runs it. Going straight to the stream would run its lanes but skip what the task system wraps around that — including the budget-window pass that lets a throttled stream take anything at all. This is the reason the helper takes the system rather than the stream.
SetNestedPumpAllowed is a gate, not a flag. The wait can be reached while the base stream is already being pumped — a task running on the base stream that waits for something else is exactly that case, and the six window tests do precisely this — and re-entering a pump is allowed only for a caller that has said so. The guard's destructor clears the permission on every exit path, so a nested drive does not leave the stream permanently re-entrant. The assert that consumes the permission is quoted on the namespace page.

The 1 ms sleep is a yield, not a poll rate: the predicate is usually set by work this very thread is running, so the sleep costs one millisecond per unfinished unit and keeps the loop from spinning the core while it drives.

patience is a wall-clock bound, not a pass count, and remaining is decremented by the sleep rather than measured against a deadline — so a call whose sleeps overshoot runs slightly longer than the number it was given. A bounded number of pump passes was the first shape considered and rejected: the same burn is milliseconds apart between configurations, so a pass budget would be a different test in each build.

Parameters

Predicate template parameter Anything callable as bool(). Bound by forwarding reference, so a lambda that captures by reference is the normal case; nothing forwards it, because it is called, never moved
taskSystem TaskSystem& The system whose base stream is driven and whose Update is called. Non-const: pumping is not a read
waitingFor const char* A literal naming the condition, used only in the timeout report. Held for the length of the call, but it must be a string literal or equivalent, not a temporary — the log line is formatted inside the call
isDone Predicate&& Tested before the first pass and after each one. Must not block: it runs on the thread that is trying to make it true
patience std::chrono::milliseconds Wall-clock bound, defaulting to 30 000 ms. Decremented by the sleep rather than measured against a deadline, so a call that overshoots each sleep drifts slightly longer than named. Every engine task-system test passes 200-600 ms; the window tests take the default, which is why a hung window backend costs them 30 s each

Return value

TypeWhat you get
bool The predicate's final value. false means the bound expired: the work was still queued, nothing was going to run it, and a caller that proceeds from here usually blocks on the very thing it waited for. Every call site in this tree tests the result and writes a failure message that says what the missing condition was
