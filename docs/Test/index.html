Module Index / Test

Test

namespace hbe namespace hbe::Test Engine/Test 3 headers, 3 sources — the framework every engine module's unit tests are written against

Module description

A test is a function taking a log sink; tests group into a TestCollection; collections run inside a TestEnv that counts passes and failures and reports them. Almost every engine header carries its own *Test class inside an #ifdef __UNIT_TEST__ region at the bottom of the file, which is the convention docs/CodingStandards.md fixes.

The whole surface is conditional. UnitTestCollection.h is wrapped in #ifdef __UNIT_TEST__, so RunTests does not exist unless the build defined it. That is the same switch build.sh -test passes as -D__TEST__ -D__UNIT_TEST__, and it is why a build without that flag reports a green EngineTest that compiled no test at all. See docs/RunningTests.md.

TestCollection (Engine/Test/TestCollection.h)

Class description

A named group of tests. A subclass adds its tests in Prepare, the framework runs them, and the same object then reports whether the run succeeded. Nearly every engine header declares one subclass in its own trailing #ifdef __UNIT_TEST__ region.

Template parameters

None — TestCollection is not a template.

Class properties

Three LogFlush guards — lf for the test's own output, lfwarn, lferr — each holding a name, a level, a test index and a pointer into the buffer it collects into. Then the title, the test list, isDone and isSuccess. The guards are the mechanism behind GetWarningMessages and GetErrorMessages: a test's output lands in a buffer chosen by severity instead of a shared console.

MethodContract a caller depends on
PreparePure virtual: the one thing a subclass supplies. It is called by the framework, not by you
AddTestRegister one test by name. The body receives a log sink, which is how a test reports a mismatch without throwing — the engine is exception-free
StartRuns the collection; IsDone is false until then, so reading a result early reads a false failure
GetWarningMessages, GetErrorMessagesWhat the run printed, kept per collection — the text you read after a failure instead of scrolling a console

TestEnv (Engine/Test/TestEnv.h)

Class description

The environment the suite runs in: it owns the collections, starts what they need, executes them, and prints the tally.

Template parameters

None — TestEnv is not a template; AddTestCollection is the variadic method.

Class properties

The registered collections and the pass and failure counts; private, read through GetPassCount and GetFailureCount.

The suite itself executes as a task on the base task stream (TaskSystem). That is a fact with teeth: the base stream is occupied for the whole run, so a test that enqueues work expecting the base stream to pick it up will wait forever. The measurement and the trap are recorded in docs/TaskSystemRedesign.md.

Coverage

GapDetail
How a test signals failure TLogOut is now named — std::stringstream, with TLogBuffer as std::vector<std::string> — but what a test body is expected to write into that stream to register a failure rather than a warning is not documented anywhere yet.
Assertion helpers The Assert family lives in Core and is what test bodies call. Whether the framework should own its own assertion macros is a real question, and the answer belongs in a design document.
Which collections run RunTests registers them; the list is code, not documentation. Engine modules with a trailing test class — Config, Container, Memory, OSAL, Resource, HSTL and others — are the current membership.
