Test

namespace hbe namespace hbe::Test namespace hbe::TestHelper Engine/Test 7 headers, 6 sources — the framework every engine module's unit tests are written against, plus the cells that measure performance

Lifecycle changed on 2026-09-28. The one-call run this page describes is gone. A test is now a Testlet and the unit the harness schedules, so TestCollection::Start became PrepareTests / RunTestAt / Complete, TestEnv::Start became PrepareTestlets / RunTestlet / Finalize, and hbe::Test::RunTests became RegisterSuite and ScheduleSuiteOnBaseStream. The statements below that name the old lifecycle are history, not reference; the replacements are documented: PrepareTests / RunTestAt / Complete on TestCollection and PrepareTestlets / RunTestlet / Finalize on TestEnv.

Module description

A test is a lambda taking a log stream. That lambda and its name together are one Testlet, which owns both inline, and the testlet — not the collection — is the unit the suite schedules. Tests group into a TestCollection subclass that names them one by one; collections are registered by type into a TestEnv, which flattens them into one sequence, runs one test at a time, and counts what actually executed against what was registered. hbe::Test::RegisterSuite and hbe::Test::ScheduleSuiteOnBaseStream are the entry points Applications/EngineTest calls: the first registers before the main thread is entered, the second posts the first testlet to the base stream, and after that each testlet posts the next. Almost every engine header carries its own *Test class inside an #ifdef TEST_ENABLED region at the bottom of the file, which is the convention docs/CodingStandards.md fixes.

The lifecycle is the whole API. A subclass supplies one function — Prepare — and inside it calls AddTest once per case. The framework then clears its state, calls Prepare, runs the cases in registration order each inside its own allocator scope, and decides the verdict from a single fact: whether any error message was recorded. There is no assertion macro and no exception — the engine is exception-free — so a case reports by streaming text and ends the message with a guard object: ls << "Size is 3, not 4." << lferr;. That one idiom is the reason a test body is written the way it is, and it is documented on the TestCollection streaming operator.

Success means "no error message was recorded", which is weaker than "the assertions held". The error text is appended from inside the logger's message callback, and the logger may decline to run a callback at all — logging compiled out, the Log.Level parameter above that severity, or a filter on the collection's category. Decline it, and a failing case records nothing and passes. The same weakness runs the other way: a collection whose Prepare registered nothing also passes.

A second concern shares this module: how fast is it, measured without ever turning a measurement into a test failure. PerfBenchmark is one cell of that — a shape of traffic, every implementation of it, measured alternately in rotated rounds with a fresh queue each round — and EPerfGrade is the colour it prints. A grade is information: no colour reports an error or a warning, and none of them moves the suite's pass count. The one thing a cell can refuse is its own number, and REJECTED exists for that. RingBufferPerfTest registers the three cells that belong in every regression run; the full sweep lives in RingBufferPerfBenchmarkTest and is registered only by Examples/RingBufferBenchmark. The harness section of the design document carries the properties those cells exist to protect, the measured noise floor that decides which claims are gradable, and the time budget every cell prints to prove it is keeping.

Module variables

None. No header in the module declares an object at namespace scope. The only statics are function-local ones that hold the module's whole mutable state: the static TestEnv instance inside TestEnv::GetEnv, and the static TaskID inside RegisterSuite · ScheduleSuiteOnBaseStream that keeps the suite's own task identity across calls.

hbe::Test and hbe::TestHelper are the module's entire free-function surface; everything else is reached through the three types above. One more free function waits — hbe::WaitUntil at Engine/Test/TestCollection.h:32 — and owns no page; see the row for it in Coverage.

The suite runs as a task on the base task stream (TaskSystem), and that is a fact with teeth: the base stream is occupied by the suite for the whole run, so a test that enqueues work expecting the base stream to pick it up waits forever. Engine tests that need a stream pick a worker instead and say so in a comment — the wording is quoted on the RunTests page. The measurement and the trap are also recorded in docs/TaskSystemRedesign.md.

Conditional build

Everything here is test-build API, but not all of it is conditional in the same way, and the difference matters when a build goes quietly green.

WhatSwitched byConsequence
UnitTestCollection.h, entirely #ifdef TEST_ENABLED around the whole file RunTests does not exist unless the macro is defined, so an EngineTest built without it links a different main branch
TestCollection.h, TestEnv.h nothing — both are unguarded and includable in any configuration The types are visible everywhere; what is missing in a normal build is the fixtures. Every *Test subclass sits behind #ifdef TEST_ENABLED in the header it tests, so a suite compiled without the macro registers nothing and has nothing to run
The Test library target itself precompileDefinitions = TEST_ENABLED in Engine/Test/.module.config, and add_compile_definitions(TEST_ENABLED) in Engine/Test/CMakeLists.txt The framework's own sources always see the macro. It is the rest of the tree that needs it from build.sh -test, which reconfigures with -DTEST_ENABLED — and it has to be global, because the test bodies live in the library sources the executable links, not only in TestMain.cpp

This is why EngineTest refuses to report success when it was built without the macro: it prints what is missing, how to get it, and returns 1 — see docs/RunningTests.md and docs/BuildSystem.md. Before that guard existed, a build without -test reported a green run over zero tests.

Coverage

GapDetail
No assertion helpers of any kind The framework has no EXPECT, no ASSERT_EQ, no helper that formats "expected X, got Y". Test bodies hand-write if and stream text by hand, and the Assert family they sometimes reach for lives in Core: Debug and aborts rather than reporting. Whether the framework should own its own assertion macros is a real open question, and the answer belongs in a design document, not here
Per-case results exist only as console output Start prints [PASS] or [FAIL] per case and keeps nothing: no accessor answers how many cases a collection ran, and no accessor names the failing one. Nothing can be reported as a failure either — a case that crashes, leaks, hangs or registers nothing is indistinguishable from one that passed. Details on IsSuccess and TestEnv: Coverage
Per-case memory is scoped but never checked Each case runs inside an AllocatorScope over a local MultiPoolAllocator named after the case, which makes its allocations attributable — and nothing compares what is outstanding when the case ends, so a leak passes. PrintUsage(), the call that would have shown it, has its entire body inside #if PROFILE_ENABLED
The AddTestCollection argument path Its parameter pack is forwarded as std::forward(args)... rather than std::forward<Types>(args)..., which does not preserve an lvalue argument. No call site in the repository passes an argument — all sixty are AddTestCollection<SomeTest>() — so that path is compiled and never exercised. Stated on the method page
What the reporting channel will and will not deliver Which callbacks run, and when the text reaches the console, is Log's contract (Logger) — as is whether a report has actually left the process when main reads the tallies. Restated here only where it can turn a failure into a pass
Which collections run RegisterSuite · ScheduleSuiteOnBaseStream registers sixty of them, drawn from Container, Core, HSTL, Math, Memory, OSAL, Renderer, Resource and String. Config is not among them — no header in Engine/Config/ declares a TestCollection subclass, so that module's behaviour is exercised only as a side effect of the logger's and allocator's own tests. The list is code, not documentation, and a collection that is written but never registered simply does not run

None of them are API and none are documented further; the binary is a build artefact under source control, which its own review note flags

What a testlet may spend

A testlet is a task that owns nothing, and it is also measured for what it spends. Each one is checked for how much global heap it still holds when its body ends, against TestCollection::MaxRetainedGlobalBytes - 64 KiB, taken from the measured distribution rather than picked. The reason the guard has to sit on the global door is the module's own history: the per-testlet allocator scope that was built to watch a test's memory sees none of it, because a std::vector or std::string inside a test reaches the heap through operator new, which no scope redirects. Those entry points are accounted for by MemoryManager, and this module is what turns the accounting into a limit.
