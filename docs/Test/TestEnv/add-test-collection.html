AddTestCollection

member of hbe::TestEnv Engine/Test/TestEnv.h member template construct one collection into the registry — the type is a template argument, not a parameter

Signature

template<typename T, typename... Types>
void AddTestCollection(Types&&... args)
{
        tests.push_back(std::make_unique<T>(std::forward(args)...));
}

Declared and defined in the header; this is the whole body.

Function description

Builds a T in place, forwards args to its constructor, and appends the resulting std::unique_ptr<TestCollection> to the registry. Two things follow from doing the construction here rather than in Start: every registered collection exists before any of them runs, and whatever AllocatorScope is open at the registration call is where that construction allocates — not the per-case scope, which only exists once Start reaches the case loop.

T has to be a concrete TestCollection subclass: it is stored as a pointer to the base, so an abstract T — including TestCollection itself — and anything not derived from it are compile errors. Registration order is execution order, and is also the order of the report's blocks.

There is no duplicate guard. Calling it twice with the same T produces two independent instances, both run, both counted, and both writing the same messages under the same log category — so a suite can report all 61 collections passed over sixty collections' worth of work.

The pack is forwarded without its template arguments, so this template only works when there is nothing to forward. The call is written std::forward(args)..., not std::forward<Types>(args).... std::forward's parameter type is remove_reference_t<T>&, a non-deduced context, so the argument-taking form does not quietly degrade into a move — it does not compile, failing with no matching function for call to 'forward' and couldn't infer template argument. An empty pack expands to no call at all, which is the only reason this header has never broken the build: all sixty engine call sites are AddTestCollection<SomeTest>(), and every collection the suite registers is default-constructible, so there has never been an argument to forward.

What that costs a caller: the variadic signature advertises constructor arguments that cannot be passed. A collection needing one cannot be registered until the header says std::forward<Types>(args).... The failure is loud rather than silent, which is the only good thing about it.

Parameters

ParameterTypeRequirement
T template parameter A concrete, non-abstract subclass of TestCollection with an accessible constructor matching args. It is named between the angle brackets, never passed as a value
Types template parameter Deduced from the arguments; empty in every call the engine makes
(function parameters) Types&&... args Constructor arguments for T, which would be forwarded to std::make_unique<T>. In practice the pack must be empty: a non-empty pack does not compile, so every engine call passes nothing — see the hazard above

Return value

void, and nothing to check: the registration either compiles or does not. There is no handle returned — the registry is private and has no accessor — so after this call the collection is unaddressable except by running the whole environment.

Examples

The engine's whole suite is one such call per collection, in the order the author wanted them reported:

From Engine/Test/UnitTestCollection.cpp

        auto& testEnv = TestEnv::GetEnv();

        testEnv.AddTestCollection<SystemAllocatorTest>();
        testEnv.AddTestCollection<BaseAllocatorTest>();
        testEnv.AddTestCollection<InlinePoolAllocatorTest>();
        // … fifty-six more …
        testEnv.AddTestCollection<RHICapabilitiesTest>();

        testEnv.Start();

Adding a module's tests to the suite is one line here plus the fixture in the module's own header, in its trailing #ifdef __UNIT_TEST__ region — see Prepare for the other half. A collection that is declared and never registered with the environment never runs, and nothing warns you that it exists.

The constructor-argument form is reachable in principle — AddTestCollection<MyTest>(title) — and unused. It is documented as written, not as intended; the hazard box above is the reason it is not offered as the way to do anything.
