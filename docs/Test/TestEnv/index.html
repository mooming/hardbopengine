TestEnv

Engine/Test/TestEnv.h namespace hbe final compiled under __UNIT_TEST__ the registry and runner for collections — and the object the exit status is read from

This is test-build API. TestEnv.h carries no #ifdef of its own, so it is includable anywhere, but it is only useful where the fixtures it runs exist — and every TestCollection subclass in the engine sits behind #ifdef __UNIT_TEST__ in the header it tests. The Test library defines the macro for itself; the rest of the tree gets it from build.sh -test. See how the Test module is built.

Class description

A TestCollection is registered by type into this class, and Start walks the registrations, calls each collection's own Start, sorts the outcomes into a pass count and two name lists, merges the collected message text, and prints the report. That is the whole job: it schedules nothing and owns no thread.

Everything the outside world learns about a run comes out of two numbers, GetPassCount and GetFailureCount, and both are counted per collection, not per test case — the header's own doc comments say "Collections that completed successfully" and "Collections that ran and failed, plus any that never completed". Applications/EngineTest/TestMain.cpp reads them to choose its exit status. The engine currently registers sixty collections holding roughly three hundred and fifty AddTest calls, and the process still reports two small numbers.

Access is through GetEnv, a function-local static, and the engine's suite registers itself into that singleton. But the constructor is public and the class is not a singleton in the enforcing sense — see the box below, because that combination has a consequence for the exit status.

A TestEnv you construct yourself is invisible to the build gate. The constructor is public, so a test can build a private environment, register collections into it and run them. Applications/EngineTest/TestMain.cpp however reads TestEnv::GetEnv().GetFailureCount() — the singleton — so a failure recorded in your own instance never reaches the exit code, and the executable reports success. Only the collections registered into GetEnv's instance are counted by the process.
final, and there is nothing to override anyway. Every member that does the running is private: ExecuteTest and Report. A subclass could not extend the run even if deriving were allowed, which is why customising the suite means writing a TestCollection subclass rather than an environment.

Template parameters

None — TestEnv is not a template. The template in this class is the member AddTestCollection, whose own parameter list carries the collection type.

errorMessages std::vector<std::string> errorMessages; private Every collected error, from failed collections only — a passing collection's error buffer is never read. Printed as one block after the failed-collection list
testedCount unsigned int testedCount; private Collections that completed, whether they passed or failed. Incremented, printed in the report and read by no accessor — see Coverage
passCount unsigned int passCount; private Collections that completed and reported no error; what GetPassCount returns. Initialised by the constructor's noexcept initialiser list and never reset afterwards

Class methods

Two further members are private and documented here instead of on pages of their own, because no caller can reach them:

  • bool ExecuteTest(TestCollection&) — one collection's run. Calls its Start, routes the name into invalidTests if it is not done, else increments testedCount and either passCount or failedTests, then merges that collection's warnings (both branches) and errors (failure only) into the environment's lists. Its bool return — the collection's own verdict — is discarded by the only caller, Start.
  • void Report() — prints the tally under ##### TEST COMPLETED #####: total registered, done, invalid, pass, fail; then the invalid, failed, error and warning blocks in that order at error severity except the warning block; then flushes the logger.

Non-member helper functions

None. TestEnv.h declares the class and nothing else at namespace scope; the module's one free function, hbe::Test::RunTests, lives in another header.

Coverage

GapDetail
Three counters, two accessors testedCount — how many collections actually finished — is incremented and printed but has no getter, and there is no accessor for tests.size() either. From outside, a run of 60 collections of which 59 finished reads exactly like a run of 59. The numbers are on the console and nowhere else
No case-level tally Neither this class nor TestCollection counts individual test cases. "Total Count" in the report is the registered collection count; per-case [PASS] and [FAIL] lines are printed by Start and thrown away
State that outlives a run Start clears invalidTests and failedTests only. passCount, testedCount, warningMessages and errorMessages accumulate across calls, so a second Start reports a cumulative pass count over a per-run failure count. The header's doc comment on GetFailureCount states the clearing rule for the two lists it clears, and says nothing about the counters
Nothing removes or replaces a registration tests is append-only and private. A suite cannot unregister a collection, so there is no supported way to run one collection alone except to build your own TestEnv — which, per the box above, the exit status will not see
Contracts owned by other modules The suite runs as a task, and what the base task stream means for a test that enqueues work is Core: TaskSystem; when the report's lines reach the console and what Flush at the end of Report guarantees is Log; shutting the engine down from inside a task is Engine. None of it is restated here
Which collections are registered Not this class's concern: the list is written by RunTests, and it is code, not documentation

Global allocation totals

GetGlobalAllocationBytes, GetGlobalAllocationCount and GetTestletCountWithGlobalAllocations sum the matching per-collection figures, so the suite reports one triple instead of one per collection. They are the numbers behind the report line # Global heap over testlet bodies = …. Read them together with the whole-process figures the entry point prints from MemoryManager: the gap between the two is what the harness and the engine consume on a run's behalf.
