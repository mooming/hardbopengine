Lifecycle changed on 2026-09-28. The one-call run this page describes is gone. A test is now a Testlet and the unit the harness schedules, so TestCollection::Start became PrepareTests / RunTestAt / Complete, TestEnv::Start became PrepareTestlets / RunTestlet / Finalize, and hbe::Test::RunTests became RegisterSuite and ScheduleSuiteOnBaseStream. The statements below that name the old lifecycle are history, not reference; the replacements are documented: PrepareTests / RunTestAt / Complete on TestCollection and PrepareTestlets / RunTestlet / Finalize on TestEnv.

PrepareTestlets

member of hbe::TestEnv Engine/Test/TestEnv.h replaces Start (2026-09-28) prepares every collection and flattens their testlets into one schedulable sequence

Signature

void PrepareTestlets();

Function description

Calls PrepareTests on every registered collection in registration order, and flattens the result: a running total becomes collectionOffsets - the exclusive end of each collection in the flattened sequence - and one label per testlet of the form CollectionName TC<n>.<name>, which is the string later used as that testlet's task name so the registry shows which case a task belongs to.

This replaced Start(), which prepared and ran in one call. The suite is posted as tasks now, so the count of testlets has to exist before the first one runs - discovered totals cannot be checked against, and the harness's central promise is that every registered testlet executed.

What it leaves behind

Contract

PropertyGuarantee
When After the last AddTestCollection, before anything is posted. A collection added after this call is invisible to the run and will be reported as a registered-versus executed gap, not silently skipped.
Cost attribution Everything preparation allocates - including each label string - lands outside every testlet's measurement window, so it is attributed to the harness. That is visible in the numbers: the suite's totals and the process's totals differ by roughly this work.
Null collections Asserted rather than tolerated: a null entry in the list is a harness bug, not a runtime condition.
