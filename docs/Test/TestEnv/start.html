Start

member of hbe::TestEnv Engine/Test/TestEnv.h void run every registered collection, in registration order, then print the report

Signature

void Start();

Function description

One pass over tests, in this order:

  1. invalidTests and failedTests are cleared. Nothing else is — see the box below.
  2. Each entry is asserted non-null and handed to the private ExecuteTest. That helper calls the collection's own Start, which is where Prepare and every test case actually run; then it routes the outcome into passCount, failedTests or invalidTests, and merges that collection's warnings and errors into the environment's own lists.
  3. Report() prints the tally — total registered, done, invalid, pass, fail — followed by the invalid, failed, error and warning blocks, and finishes by flushing the logger.

It is entirely synchronous and single-threaded from the caller's point of view: Start does not return until the last collection's report line has been printed. The word "Start" therefore describes the test run, not this call — there is nothing to poll and nothing to wait for. Whatever thread calls it is the thread the collections run on, which in the engine is a worker task on the base task stream rather than the main thread.

Only two of the five lists are cleared, so a second run reports two kinds of number at once. passCount and testedCount keep counting up, and warningMessages and errorMessages keep appending. So after a second Start the failure count is from this run and the pass count is from every run, and the merged message blocks repeat everything printed before. The header comment on GetFailureCount documents the clearing rule for the two lists it clears and is silent about the rest; a harness that calls Start twice has to read that asymmetry off the source.
The per-entry null check cannot fire through the public API. Each step asserts its entry non-null with Assert, but the only way an entry gets into tests is AddTestCollection storing the result of std::make_unique, which is never null. It is a guard against corruption, not against a caller — and, being Assert, it is silent in a Release configuration, where a null entry would be dereferenced anyway.

Parameters

None.

Return value

void. The environment keeps its own verdict in the two counters, and the only failure signal the language offers is GetFailureCount afterwards. ExecuteTest's per-collection bool is discarded here — the loop does not look at it, so nothing about an individual collection survives the loop except as a name in a list.

Examples

Exactly one call site in the engine, at the end of the registration list and inside the task the suite runs on:

From Engine/Test/UnitTestCollection.cpp

        testEnv.AddTestCollection<ComponentSystemTest>();
        testEnv.AddTestCollection<TaskStreamAffinityTest>();
        testEnv.AddTestCollection<TaskSystemTest>();
        testEnv.AddTestCollection<RHICapabilitiesTest>();

        testEnv.Start();

        Engine::Get().ShutDown();

The position matters: Start runs what is registered at the moment it is called, so a collection added afterwards is never run by that Start. And the whole suite is enqueued as a task — see RunTests for how, and why the base task stream being occupied for the entire run is a fact with consequences for a test that enqueues work of its own.

Because Start does not return early even for a failing collection, one failing test does not stop the suite: every registered collection runs, and the failures are only visible at the end.
