Lifecycle changed on 2026-09-28. The one-call run this page describes is gone. A test is now a Testlet and the unit the harness schedules, so TestCollection::Start became PrepareTests / RunTestAt / Complete, TestEnv::Start became PrepareTestlets / RunTestlet / Finalize, and hbe::Test::RunTests became RegisterSuite and ScheduleSuiteOnBaseStream. The statements below that name the old lifecycle are history, not reference; the replacements are documented: PrepareTests / RunTestAt / Complete on TestCollection and PrepareTestlets / RunTestlet / Finalize on TestEnv.

GetEnv

member of hbe::TestEnv Engine/Test/TestEnv.h static [[nodiscard]] the one environment whose tallies the executable reads

Signature

[[nodiscard]] static TestEnv& GetEnv();

Function description

Defined in TestEnv.cpp as a function-local static returned by reference: 

TestEnv& TestEnv::GetEnv()
{
        static TestEnv instance;
        return instance;
}

The instance is built on first call, not at load time, and every call after that returns the same object. The reference stays valid for the rest of the process; the object itself is destroyed during static destruction, after main has finished, which is why the registered collections and their message text are still allocated while the exit status is being chosen.

Local statics are initialised once even under concurrent first calls, so this is safe to reach for from any task. That is a property of the idiom, not of this class — once you hold the reference, its private state is unsynchronised, and Start walking sixty collections while a second thread registers one is a data race.

It hands back an empty environment. Nothing registers itself: the registry is filled by whoever calls AddTestCollection, and in the engine that is RunTests, which adds all sixty collections and then calls Start. Calling GetEnv before that is legitimate and returns an environment with a total of zero.
There is exactly one counted environment per process. The class has a public constructor and does not prevent a second TestEnv, but Applications/EngineTest/TestMain.cpp asks this function for its environment. Collections registered anywhere else ran, printed a report and contributed nothing to the exit status: a build gate can therefore go green over a suite that failed inside an uncounted environment.

Parameters

None.

Return value

TypeWhat you get
TestEnv& The process-wide environment — mutable, so the same reference serves AddTestCollection and Start as well as the two const counters. [[nodiscard]], since calling it and dropping the result does nothing at all

Examples

Filling it, from inside the task the suite runs on:

From Engine/Test/UnitTestCollection.cpp

        auto& testEnv = TestEnv::GetEnv();

        testEnv.AddTestCollection<SystemAllocatorTest>();
        testEnv.AddTestCollection<BaseAllocatorTest>();
        // …
        testEnv.Start();

And reading the outcome, after Run() has returned and the suite's task has finished:

From Applications/EngineTest/TestMain.cpp

const hbe::TestEnv& testEnv = hbe::TestEnv::GetEnv();
const unsigned int failures = testEnv.GetFailureCount();

if (failures > 0)
{
        std::cerr << "EngineTest: " << failures << " test collection(s) FAILED" << std::endl;
        return 1;
}

Those two files are the only call sites; no test body asks for the environment it is running inside, because a TestCollection subclass is never told about the environment that owns it.
