Lifecycle changed on 2026-09-28. The one-call run this page describes is gone. A test is now a Testlet and the unit the harness schedules, so TestCollection::Start became PrepareTests / RunTestAt / Complete, TestEnv::Start became PrepareTestlets / RunTestlet / Finalize, and hbe::Test::RunTests became RegisterSuite and ScheduleSuiteOnBaseStream. The statements below that name the old lifecycle are history, not reference; the replacements are documented: PrepareTests / RunTestAt / Complete on TestCollection and PrepareTestlets / RunTestlet / Finalize on TestEnv.

GetFailureCount

member of hbe::TestEnv Engine/Test/TestEnv.h const noexcept inline the number a build gate exits non-zero on — failed collections plus collections that never finished

Signature

/// @brief Collections that ran and failed, plus any that never completed.
/// @details Valid after Start(); Start() clears both lists on entry.
[[nodiscard]] unsigned int GetFailureCount() const noexcept
{
        return static_cast<unsigned int>(failedTests.size() + invalidTests.size());
}

Function description

Computed on demand from the two name lists rather than stored in a counter: collections that ran and reported an error message, plus collections whose Start never completed. Unlike GetPassCount there is nothing to accumulate — Start empties both lists on entry, so what you read after a run describes that run. The header's @details line states exactly that clearing rule.

The unit is again the collection, not the test case: the header says "Collections that ran and failed", and one collection containing ten failures counts as one. It is the number EngineTest prints and the condition it returns 1 on, which makes this the module's only exit-status contract.

The two halves are not equally reachable. invalidTests requires a collection that is not done after Start returned, and the engine is exception-free — a collection that gets that far always sets isDone. So in a run that reaches the summary this number is failedTests.size(), and the "plus any that never completed" half describes a crash that took the process with it.
Zero failures is not evidence that anything was verified. Nothing ran, nothing was registered, and every case's lferr was declined by the logger — all three answer zero here, and this is the number a CI gate trusts. Applications/EngineTest/TestMain.cpp guards the widest of those holes directly, by refusing to report success when the binary was compiled without __TEST__ at all, rather than returning zero over an empty suite — see how the Test module is built. The narrower holes, a collection that registered no cases and a suite filtered quiet, are still visible only in the report's own counts.

Parameters

None.

Return value

TypeWhat you get
unsigned int failedTests.size() + invalidTests.size(), narrowed from size_t by an explicit cast. Zero before the first Start, since both lists start empty and the constructor does not touch them. [[nodiscard]]

Examples

The only consumer, and the only place a test result becomes a process exit status:

From Applications/EngineTest/TestMain.cpp

// The suite runs as a task that shuts the engine down when it finishes, so the tallies
// are only complete once Run() returns. A failing suite has to leave a non-zero exit
// status behind: until now it always returned 0, which made the run impossible to gate on.
const hbe::TestEnv& testEnv = hbe::TestEnv::GetEnv();
const unsigned int failures = testEnv.GetFailureCount();

if (failures > 0)
{
        std::cerr << "EngineTest: " << failures << " test collection(s) FAILED" << std::endl;
        return 1;
}

Both of those lines are why the environment has to be the GetEnv singleton: the caller is main, several frames and one task away from the code that ran the tests, and the only channel between them is this instance's two lists.

To find out which collections those failures were, there is no accessor — the names live in the private failedTests vector and reach the outside world only as the report's = Failed Tests ===== block. See Coverage.
