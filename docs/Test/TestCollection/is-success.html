IsSuccess

member of hbe::TestCollection Engine/Test/TestCollection.h const noexcept did the last run produce no error message — one bool, computed from one vector

Signature

[[nodiscard]] bool IsSuccess() const noexcept;

Function description

Returns isSuccess, which Start assigns exactly once per run, as errorMessages.empty(). There is no per-case tally behind it and no severity threshold in it: one lferr anywhere in the collection makes the whole collection fail, and a hundred make it fail the same amount. Warnings are not in the expression at all.

This is the value TestEnv::ExecuteTest turns into GetPassCount or a failedTests entry, and therefore — through GetFailureCount and Applications/EngineTest/TestMain.cpp — the value a build gate exits non-zero on. It is also what the collection's own report line prints: [SUCCESS] at info severity when true, [FAIL] at error severity when false.

Before the first run and during one it reads false, which is a conservative default: a result read too early is a failure, not a pass.

Three different situations all answer true. Since the answer is "the error buffer is empty", it is also true of a collection that registered no cases at all, of one whose cases were all rejected by AddTest for a null body, and of one whose lferr messages the logger declined to deliver. The framework counts nothing that would distinguish them — it prints a total and a done count, never a case count. A collection that passes without emitting a single line has probably tested nothing; check its Prepare.
Per-case results are printed but not stored. The framework prints # TC<i>.<name> Result [PASS] or [FAIL] per case, then discards that verdict — nothing on the object records which cases failed, only which messages were emitted. Finding the failing case means reading the [TC<index>.<name>] prefix on the entries from GetErrorMessages.

Parameters

None.

Return value

TypeWhat you get
bool True when the last completed run recorded no error message; false before a run, during one, and after a run that recorded at least one. Collection-scoped — a subclass with ten cases and one failure reports false, and the failure is only locatable through the message text

Examples

The framework's use — the branch that decides whether a collection's name goes on the failed list:

From Engine/Test/TestEnv.cpp

        ++testedCount;

        if (testCollection.IsSuccess())
        {
                ++passCount;

                auto& warnMessages = testCollection.GetWarningMessages();
                // …
        }
        else
        {
                ss << testCollection.GetName() << " : [FAIL]";
                failedTests.push_back(ss.str());

                // … fold warnings and errors into the environment's lists …
        }

        return testCollection.IsSuccess();

The same file both branches IsSuccess and returns it, while Start — the caller — discards that return value and keeps its own lists. So the bool a collection reports is re-derived by the environment rather than stored once; nothing in the engine reads the return value of ExecuteTest.

A subclass itself has no reason to ask: it is either inside Prepare, where the answer is not yet assigned, or it is not running at all. The consumers are the environment and, one step further out, whatever built the executable.
