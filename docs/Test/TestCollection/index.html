TestCollection

Engine/Test/TestCollection.h namespace hbe abstract compiled under __UNIT_TEST__ a named group of tests, the run of those tests, and the verdict on it — all in one object

This is test-build API. The Test library target defines __UNIT_TEST__ for itself (Engine/Test/.module.config, add_compile_definitions in Engine/Test/CMakeLists.txt), and every subclass you would actually write lives behind #ifdef __UNIT_TEST__ in the header it tests. The header itself carries no such guard, so including it compiles in a normal build — but there is nothing there for a normal build to do with it. The whole suite is switched on by build.sh -test; see how the Test module is built and docs/RunningTests.md.

Class description

A subclass does exactly three things: pass a title to the constructor, override Prepare, and inside Prepare call AddTest once per case with a name and a lambda. Everything else on the class is the framework's side of that bargain — Start runs the cases, IsSuccess and the two message getters report the outcome.

The lifecycle is fixed and entirely inside Start: it clears its own state, opens a log line, calls Prepare() so the subclass can register the cases, runs them in registration order, sets isSuccess from whether any error message appeared, sets isDone, and prints the collection's verdict. A subclass never drives this; TestEnv::Start calls Start on each registered collection.

There is no assertion macro. A test case reports by writing into the log stream it is handed, and it fails a case by ending that message with lferr — the streaming operator for the error-severity guard. A case passes when no error message arrived while it ran; the check is literally a cursor comparison on the error buffer, so the mechanism is "the error count grew", not "a condition was false". Warnings are collected the same way by lfwarn and never affect the verdict.

The stream argument on its own reports nothing. The TLogOut& a case receives is one std::stringstream shared by every case in the collection, emptied after each one. The only reader it has is the streaming operator — so a case that writes ls << "mismatch"; and stops there produces no console output, no stored message and no failure. Every message ends in lf, lfwarn or lferr.

Template parameters

None — TestCollection is not a template. The variadic machinery in this module is TestEnv::AddTestCollection.

errorMessages std::vector<std::string> errorMessages; protected The buffer lferr points at. This vector is the verdict: isSuccess is exactly errorMessages.empty() after the run

isDone bool isDone; private Set false on entry to Start and true after the last case; read by IsDone
isSuccess bool isSuccess; private Assigned once, from errorMessages.empty(); read by IsSuccess
Copying a collection silently misroutes its messages, and copying is not forbidden. Each guard stores a raw TLogBuffer* initialised to &warningMessages or &errorMessages of the object being constructed, and the copy constructor the compiler generates copies those pointers without rebasing them. A copy's lferr would therefore append to the original's vector, and if the original is gone first, append through a dangling pointer. Nothing in the engine copies a collection — AddTestCollection constructs one in place into a std::unique_ptr — but the class does not delete the copy operations either, so the hazard is reachable by a caller the compiler will not stop.

Non-member helper functions

// declared as a friend inside TestCollection, defined in Test/TestCollection.cpp
std::ostream& operator<<(std::ostream& os, const TestCollection::LogFlush& lf);

This operator is the reporting channel, and it is the reason a test body is ls << "…" << lferr; rather than a call. On each use it drains whatever os holds so far, prefixes it with TC<testIndex>.<testName>, and emits it through Logger::Get(lf.name, lf.level). The logger's own formatted line is then appended to lf.messageBuffer — which for lferr is the collection's error vector, and so the act of printing a failure is the act of failing the case. It returns the same stream it was given, after emptying it, which is what lets one buffer carry several messages in a row.

It is found by argument-dependent lookup: LogFlush lives in hbe, so ls << lferr resolves without a using-declaration anywhere in the test body.

A dropped log line is a passing test. The failure text reaches the buffer from inside the logger callback, and Logger::AddLog can return without running a callback at all — logging disabled, the Log.Level parameter above the message's severity, or a category filter for that collection's name. errorMessages then stays empty, and IsSuccess reports success for a case that failed. The default threshold is Info so error messages pass by default; raising it or filtering a category turns a red suite green without anything else changing.
Message routing is per-collection-name, not per-test. Because all three guards are built from title, one collection is one log category, and the only thing distinguishing cases inside it is the TC<index>.<name> prefix. That prefix is read from mutable state on the guard, so a message emitted from a thread the case started, after the case returned, is attributed to whichever case is current — and can fail a case that did nothing wrong.

Coverage

GapDetail
ExecuteTests and Report Both private, so no page of their own. In short: ExecuteTests loops the cases in order, updating the three guards' testIndex/testName, wrapping each case in a per-case AllocatorScope over a local MultiPoolAllocator named after the case, comparing the error-cursor before and after to print [PASS] or [FAIL], and emptying the shared stream. Report prints the one-line collection verdict. alloc.PrintUsage() sits inside that loop but its whole body is #if PROFILE_ENABLED, so an ordinary build accounts for a case's memory and says nothing about it
Per-case leak detection The per-case allocator scope makes a case's allocations attributable, but no leak is a failure: nothing compares the allocator's outstanding count to zero, and no lferr is emitted for it. A case that leaks passes
What a failure message should say The convention is "observed, expected, why it matters", readable in the AddTest examples. It is a convention of the codebase, not a contract of the type — the framework stores whatever bytes you stream
Contracts owned by other modules Which callbacks the Logger actually runs and how categories and levels filter is Log; which assert each guard uses is Core: Debug; what the per-case AllocatorScope costs and when it can fall back is Memory. None of it is restated here
Subclasses are not documented here Engine headers each declare their own *Test subclass in a trailing #ifdef __UNIT_TEST__ region — ArrayTest in Engine/Container/Array.h is one of roughly sixty. Which ones are registered is RunTests
