MaxRetainedGlobalBytes

static constexpr member of hbe::TestCollection Engine/Test/TestCollection.h std::size_t the ceiling on global heap memory one testlet may still be holding when its body ends

Declaration

static constexpr std::size_t MaxRetainedGlobalBytes = 64 * 1024;

What it guards

Every testlet runs inside its own MultiPoolAllocator under an AllocatorScope, but that fixture cannot see the traffic that actually matters: a std::vector or std::string inside a test body reaches the heap through operator new, and no scope redirects that. The engine accounts for those entry points globally - see Global allocation accounting - and this constant turns that accounting into a per-testlet limit.

Measured across the suite, 320 of 372 testlets reach the global heap from their own bodies in Debug and 282 in Release, and the per-testlet allocator reports usage for none of them. A limit on something that was previously invisible is the entire point of this constant.

Retention, not requests

The quantity compared is retention: bytes requested during the body minus bytes released during it. That choice is the design. A stress loop can request hundreds of megabytes while holding almost none of it; a leak holds every byte without requesting more. A ceiling on bytes requested would refuse the honest test and pass the leak, so it is not a ceiling worth having.

A ceiling on the number of requests was considered and rejected on the same data: p99 is 3.8 million and the maximum 33.5 million, because the allocator performance tests allocate tens of millions of times for a reason. Any request ceiling that passes them today is not a guard.

How a breach behaves

A breach logs an error naming the testlet, its retained byte count and the ceiling, and records an entry in the collection's error buffer - which is the thing the verdict is decided on. A guard that only printed would be a comment with a number in it. Verified by mutating the ceiling down to 1 KiB: eleven testlets refused by name, EngineTest: 7 test collection(s) FAILED, runner exit non-zero.

The refusal says whose ceiling was breached, so a declared budget is never mistaken for the default:

# TC0.Print CallStack retained 1568 bytes of the global heap at the end of its body,
   over the 256 byte ceiling this testlet declared for itself. Free it, or raise the
   ceiling with a reason that survives review #

Raising it for one testlet

AddTest has a form taking the allowance, so an exception is an argument beside the test that needs it rather than an edit to this shared constant that quietly relaxes all 372 testlets at once. A testlet with a declared budget also repeats it on every line it logs, so the exception stays visible in a log excerpt rather than only in the source that registered it. Nothing passes the argument today: the mechanism shipped with zero exceptions granted.

What this ceiling does not cover

LimitDetail
The engine allocator door A testlet allocating through its AllocatorScope draws on MultiPoolAllocator banks, which are not in this figure. Covering it needs a public usage accessor on that class, declined as speculative while the door measures zero traffic across the whole suite.
Retention can read slightly low A release through the unsized operator delete reports the block size the system heap chose, which can exceed the size asked for, so the released total can outrun the requested total a little. The clamp at zero absorbs it, and the direction is the safe one for a ceiling.
No test inside the suite covers the guard Not expressible rather than missing - see the reasoning recorded on the testlet. The substitute is the mutation described above, run in both directions.
