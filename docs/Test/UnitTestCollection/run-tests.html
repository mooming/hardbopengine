RunTests

hbe::Test Engine/Test/UnitTestCollection.h free function only under __UNIT_TEST__ register the engine's suite and enqueue it — and return before any test has run

Signature

#ifdef __UNIT_TEST__
namespace hbe::Test
{
void RunTests();
}
#endif // __UNIT_TEST__

No arguments, no return value, no namespace-scope state. Declared in a header whose entire content is inside the guard, and defined in Engine/Test/UnitTestCollection.cpp inside the same guard again.

Function description

The definition is one lambda plus the four lines that put it on a task stream:

  1. It builds a task body that opens one MultiPoolAllocator named "UnitTest" inside an AllocatorScope, takes the TestEnv::GetEnv singleton, calls AddTestCollection once per collection — sixty of them — calls Start, then calls Engine::Get().ShutDown() and returns 1.
  2. It creates that body as a task named "TestEnv", through a function-local static TaskID that is only filled in when it still IsNull().
  3. It looks the task back up, FatalAsserts that the registry knows it, and generates a ranged sub-task over (0, 1, 0) — one element, one invocation.
  4. It enqueues that sub-task on TaskSystem::GetBaseTaskStreamIndex() and discards the status.

So this function does not run the tests. It arranges for them to be run, on the base task stream, by the task system of an Engine that the caller has already initialised and is about to call Run() on. Every number in this module is therefore read after the engine stops — and the engine stops because the suite's own task shuts it down when the last report line has been printed.

The base task stream is the one stream a test cannot use. The suite is not merely running near it, it is the task occupying it, so work a test enqueues there cannot run until the suite finishes — which the test is blocking. Engine code that has to hand work to the task system from inside a case picks a worker stream instead, and says why: 
        // The whole suite executes inside a task on the base stream - see UnitTestCollection.cpp's TestEnv
        // subtask - so the base stream is occupied until the suite ends and can never run anything a test
        // enqueues to it. The first worker stream is the nearest one that is genuinely idle.
        const auto workerIndex = TaskSystem::GetIOTaskStreamIndex() + 1;

From Engine/Core/TaskSystem.cpp

Two failures are possible before a single test runs, and only one is reported. If the registry cannot find the task back, the function FatalAsserts with "The task registry could not track the suite's own task, so no test can run." and returns — and since FatalAssert is live in every configuration, that path is loud. A refused enqueue is the quiet one: its status is cast to void, so nothing reports it, no report is ever printed, and nothing shuts the engine down. Both the pass count and the failure count stay zero.
A second call does not build a second suite. The static TaskID is remembered, so a repeat call skips creation and re-enqueues the same sub-task into the same TestEnv whose counters are never reset. Registration also happens again inside the task body, so the registry ends up holding duplicates — and the report is a mixture of both passes rather than a fresh measurement. What re-enqueuing an already-completed task means in the scheduler belongs to Core: TaskSystem.

Parameters

None.

Return value

void, and it is not a report of anything. When RunTests returns, at most one enqueue has been attempted; no collection has been constructed, no case has run, and the tallies on the environment are still whatever they were. Everything a caller wants to know is read afterwards, from GetFailureCount, once the engine has finished running the task this call queued.

Examples

The caller, which is also the only caller:

From Applications/EngineTest/TestMain.cpp

#ifdef __UNIT_TEST__
        hbe::Engine hengine;
        hengine.Initialize(argc, argv);
        hbe::Test::RunTests();
        hengine.Run();

        // The suite runs as a task that shuts the engine down when it finishes, so the tallies
        // are only complete once Run() returns.
        const hbe::TestEnv& testEnv = hbe::TestEnv::GetEnv();
        const unsigned int failures = testEnv.GetFailureCount();

        if (failures > 0)
        {
                std::cerr << "EngineTest: " << failures << " test collection(s) FAILED" << std::endl;
                return 1;
        }
#else
        // … every test body in the engine sits behind #ifdef __UNIT_TEST__, so built without the
        // macro there is nothing left to run; this branch prints what is missing and how to get
        // it, then:
        return 1;
#endif // __UNIT_TEST__

The Run() between the call and the read is not a formality: the suite advances only while the engine is pumping its task streams. Remove it and the tallies stay zero forever.

The registration itself, beginning and end of the list:

From Engine/Test/UnitTestCollection.cpp

void RunTests()
{
        auto testFunc = [](void*, std::size_t, std::size_t) -> std::size_t
        {
                MultiPoolAllocator allocator("UnitTest");
                AllocatorScope scope(allocator);

                auto& testEnv = TestEnv::GetEnv();

                testEnv.AddTestCollection<SystemAllocatorTest>();
                // … fifty-eight more …
                testEnv.AddTestCollection<RHICapabilitiesTest>();

                testEnv.Start();

                Engine::Get().ShutDown();

                return 1;
        };

        static TaskID taskID;

        auto& taskSystem = Engine::Get().GetTaskSystem();
        if (taskID.IsNull())
        {
                taskID = taskSystem.CreateTask("TestEnv", testFunc, nullptr);
        }

        auto* testTask = taskSystem.FindTask(taskID);
        FatalAssert(testTask != nullptr, "The task registry could not track the suite's own task, so no test can run.");
        if (testTask == nullptr)
        {
                return;
        }

        const auto rangedTask = testTask->GenerateSubTask(0, 1, 0);

        const auto baseStreamIndex = TaskSystem::GetBaseTaskStreamIndex();
        (void) taskSystem.Enqueue(baseStreamIndex, rangedTask);
}

Adding a module's collection to the suite is one AddTestCollection line in that lambda, plus the fixture in the module's own header. Note the shape of the task body's signature — (void*, size_t, size_t) -> size_t — which is the ranged-task contract from Core: Runnable; the body ignores all three arguments and answers 1 for the one element it covers.
