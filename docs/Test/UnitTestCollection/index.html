Lifecycle changed on 2026-09-28. The one-call run this page describes is gone. A test is now a Testlet and the unit the harness schedules, so TestCollection::Start became PrepareTests / RunTestAt / Complete, TestEnv::Start became PrepareTestlets / RunTestlet / Finalize, and hbe::Test::RunTests became RegisterSuite and ScheduleSuiteOnBaseStream. The statements below that name the old lifecycle are history, not reference; the replacements are documented: PrepareTests / RunTestAt / Complete on TestCollection and PrepareTestlets / RunTestlet / Finalize on TestEnv.

UnitTestCollection

Engine/Test/UnitTestCollection.h namespace hbe::Test not a class entire header inside #ifdef TEST_ENABLED the engine's suite entry point — one free function, and the registration list it owns

Class description

There is no class. The name is the header's, and the header's whole content is a single declaration inside an #ifdef TEST_ENABLED guard: 

#ifdef TEST_ENABLED
namespace hbe
{
namespace Test
{
void Suite entry points();
}
} // namespace hbe
#endif // TEST_ENABLED

hbe::Test::RegisterSuite and ScheduleSuiteOnBaseStream is what Applications/EngineTest/TestMain.cpp calls, and it is the only place in the engine that decides which collections are tested: its definition registers sixty of them into TestEnv::GetEnv, then enqueues the run as a task. Add a module to the suite by editing that definition; nothing discovers tests on its own.

This is the one header in the module that is genuinely conditional. TestCollection.h and TestEnv.h carry no guard and are includable from any build; this one declares nothing unless TEST_ENABLED is defined, so RegisterSuite and ScheduleSuiteOnBaseStream does not exist to link against in a normal build — which is the same switch build.sh -test passes as -DTEST_ENABLED. The consequences for an EngineTest built without it are recorded on the module page.

It is also the only entry in this module in hbe::Test. The framework's two types are in hbe proper; the namespace here exists to hold the engine's own suite, as a per-module suite would live in hbe::RendererTest or anywhere else the author chose.

Template parameters

None — there is no template here, and no class for one to belong to.

Class properties

None. No type, no alias, no data. The only state anywhere near this entry is the function-local static TaskID taskID in its definition, which remembers the suite's task across calls so a second call re-enqueues rather than creating a second task — see the RegisterSuite and ScheduleSuiteOnBaseStream page.

Class methods

The entry has no members. Its one callable is a free function in hbe::Test, and it carries a page because there is a real contract to read before calling it — this function returns before the tests have run.

Suite entry points void RegisterSuite()
void ScheduleSuiteOnBaseStream()		 Registers the suite and enqueues it on the base task stream; returns as soon as the enqueue is issued. The engine is shut down by the suite's own task when the last report is printed

Non-member helper functions

hbe::Test::RegisterSuite and ScheduleSuiteOnBaseStream is itself the non-member function this entry declares — it is shown under Class methods above so the page has a working navigation target rather than an empty table. Nothing else in UnitTestCollection.h is declared.

Coverage

GapDetail
Which collections are in the suite Sixty AddTestCollection calls, listed by type in Engine/Test/UnitTestCollection.cpp. They are enumerated on the RegisterSuite and ScheduleSuiteOnBaseStream page only as a sample — the authoritative list is that source file, and it is the kind of list documentation cannot keep current
What a real suite needs before it can run The caller must have an Engine initialised and must then call Run(): the suite is a task, and the task system has to be running for it to be executed at all. TestMain.cpp does both around this call; the ordering is not enforced or checked here
Engine shutdown as a side effect The suite's task calls Engine::Get().ShutDown() as its last act, which is what ends Run() and lets main read the tallies. It means "run the tests" also means "end this process's engine" — there is no way to run the suite and carry on using the engine afterwards. Attributed to Engine, documented here because it is set up here
A second call The function-local static TaskID means a repeat call reuses and re-enqueues the same task rather than creating another. What that does to the tallies is a TestEnv::Start matter — its counters accumulate, and the page explains why a re-run is not a clean second measurement
Memory the suite allocates outlives its own allocator The task body opens a MultiPoolAllocator named "UnitTest" inside an AllocatorScope, and inside that scope the collections are constructed — while being owned afterwards by a TestEnv static that is destroyed long after the scope closes. Whether anything is then freed through the closed pool is a Memory question (MemoryManager) that this page cannot answer, and it is flagged rather than asserted
Renderer and Vulkan example coverage The suite registers RendererTest (declared in Engine/Renderer/RendererTest.h) and RHICapabilitiesTest. What those assert is Renderer's subject, not this module's
