Module Index / Renderer

Renderer

namespace hbe::Renderer Engine/Renderer 7 headers, 7 sources one API-neutral device descriptor, one Vulkan backend built on it, and the seam a second backend would copy

Module description

The renderer's durable idea is RenderCapabilities: one descriptor whose field names are chosen so Vulkan, Direct3D 12 and Metal can all answer them, filled from a real device rather than assumed, and asserted trivially copyable so it crosses the backend seam by value. Everything else in the module either answers questions about that descriptor or is one backend's use of it. The architecture argument for the whole render-hardware-interface design is docs/RendererDesign.html, and docs/design/LightweightRenderer_Design.html covers the lightweight path; this page and the pages below stay on what the headers declare.

Two of those documents exist twice, in markdown and in HTML, and the pairs are not equivalent - which is why both forms are linked above rather than one. Measured by section headings:

PairSectionsOverlapWhat the unlinked form holds
RendererDesign.md / RendererDesign.html 24 / 17 5 Not a rendering of the same text. The markdown is 47 KB against the HTML's 15 KB, and the heading sets barely intersect: this is a second, larger design document that shares a title, not a second format. The HTML form is the one every module page has been linking.
LightweightRenderer_Design.md / .html 42 / 35 33 Close to the same document. The markdown carries the phase plan (Phase 1 Core data structures, Phase 2 Render graph) and a shorter vision heading; the HTML has two sections the markdown does not. The markdown was modified 2026-09-06, the HTML 2026-09-01 - so the linked form is the older of the two.

Deciding which form is authoritative is the owner's call, not something to settle by editing links, and the first renderer in the tree is a Vulkan backend that would have to change if the answer moved. What is not debatable is the state this page is correcting: before this note both markdown files were referenced by nothing, so a reader following the reference could not discover that a competing 47 KB renderer design exists in the same folder. That matches the site's own rule - a second copy of a standard is a second place to be wrong - and duplication you cannot reach is worse than duplication you can.

The one backend is Vulkan, split across two files for one class: VulkanRenderer.cpp holds the portable pipeline and the frame protocol, and VulkanRenderer.mm creates the macOS surface — a CAMetalLayer adopted by a layer-backed content view, wrapped by vkCreateMetalSurfaceEXT. The same class has a Windows surface path marked compile-unverified in its own comment, and no Linux path at all: CreateSurface returns false there, so Initialize fails on Linux. Backend selection is compile-time and link-time, the way OSAL selects a window implementation.

What the previous guide described that is not in this tree. There is no Engine/Renderer/IRenderer.h, no RendererFactory.h, and no DX12/ or Metal/ backend directory — Engine/Renderer/ contains one subdirectory, Vulkan/. Grepping Engine/ and Applications/ for IRenderer, RendererFactory, APIType, IsMetalSupported, IsDX12Supported and GetPreferredAPI returns nothing at all: no declaration, no definition, no use. The old document's own marginal notes already called the factory sketch aspirational, and the code never grew the interface. Backend identity now travels in the descriptor's deviceName and apiVersionMajor / apiVersionMinor, and the reasoning for removing a runtime API-kind enum is the design document's.

Module variables

No header in this module declares an object at namespace scope. The two constants that exist are class members, and both are ceilings a caller has to respect:

NameTypeWherePurpose
RenderCapabilities::MaxDeviceNameLength static constexpr size_t = 128 RenderCapabilities.h Length of the inline deviceName buffer, so an identity needs no allocation. The Vulkan adapter copies at most 127 characters and always writes the terminator
VulkanRenderer::MAX_FRAMES_IN_FLIGHT static constexpr size_t = 2 (private) Vulkan/VulkanRenderer.h Command buffers, fences and semaphores per frame slot. It is the reason SetMesh cannot free buffers safely mid-loop

Availability is decided twice, and the two decisions disagree. VULKAN_SDK is 1 when __has_include finds vulkan/vulkan.h and 0 otherwise with a #pragma message naming the install script — a tolerant, header-level answer. The build is not tolerant: Engine/Renderer/CMakeLists.txt runs find_path(vulkan/vulkan.h …) and find_library(vulkan …) and both FATAL_ERROR, with the comment "The engine is Vulkan-only, so a missing loader is a hard error, not a silent skip." No header here guards its #include <vulkan/vulkan.h> on the macro. So in this tree the renderer does not compile out when the SDK is missing — configure stops. Installation scripts are linked from the index.

Engine/Renderer/.module.config carries ignoreSubdirectories = DX12 Metal Vulkan: the two absent backends are reserved directory names in the generator's configuration, and the Vulkan/ sources are wired into the target explicitly by customCMake.txt instead of being discovered — which is how a second backend directory would join, without an API-kind enum deciding at run time.

Module functions

Three free functions live at namespace scope in hbe::Renderer. The previous version of this page said "None at namespace scope" while quoting one of them in prose; all three are real, and none has a page of its own in this batch — they are named here and detailed in their headers.

NameHeaderWhat it does, and who calls it
IdentityMatrix Vulkan/VulkanRenderer.h inline void IdentityMatrix(float m[16]) noexcept — zeroes sixteen floats, then sets m[0] = m[5] = m[10] = m[15] = 1.0f. Column-major identity written in place, no return value. The only caller is the renderer's constructor, which uses it on its three matrix slots before any caller sets them
FillRenderCapabilities Vulkan/VulkanCapabilities.h void FillRenderCapabilities(VkPhysicalDevice physicalDevice, RenderCapabilities& outCapabilities) noexcept — resets the descriptor to "unknown", then reads the physical device's properties and features into it and sets isDeviceQueried last. A null handle logs an error and leaves the output untouched. Called by VulkanRenderer::QueryCapabilities inside CreateDevice. This is the seam a second backend copies rather than extends
QueryDefaultDeviceCapabilities Vulkan/VulkanCapabilities.h bool QueryDefaultDeviceCapabilities(RenderCapabilities& outCapabilities) noexcept — creates a throwaway instance, enables VK_KHR_portability_enumeration only if the loader advertises it, takes the first physical device, fills the descriptor and destroys the instance. Returns whether a device answered; failures are warnings, not errors. The sole caller is RHICapabilities::GetCapabilities

Data layouts

Four plain structs define what goes to the GPU. Each has a page; what belongs at module level is the set of promises that span files, because none of it is checked by the compiler.

TypeBytesLayoutBound to
Vertex 28 Vector3<float> position then Vector4<float> color Nothing today — no pipeline in this tree declares this layout
MeshVertex 24 float position[3] at offset 0, float normal[3] at offset 12 The pipeline's vertex input, and MC.vert's aPosition / aNormal
Mesh host only Two std::vector: MeshVertex vertices, uint32_t indices SetMesh, which copies both blocks out and holds no reference
PushConstants 128 float model[16] at 0, float viewProj[16] at 64, column-major One push-constant range (vertex stage, offset 0, 128 bytes) and MC.vert's Push { mat4 model; mat4 viewProj; }
Two vertex formats in one module is a fact, not a mistake. Vertex is the unlit example layout — position and colour; MeshVertex is the lit one — position and normal. A pipeline is created against one stride and one pair of offsets, and this backend creates exactly one pipeline, so the type a mesh is built from has to be the type that pipeline was told about.
Three matrices become two before they reach the shader. The renderer keeps modelMat, viewMat and projMat as separate slots, and Render multiplies viewProj = projMat * viewMat on the CPU once per frame so the guaranteed 128-byte push range can also carry a model matrix. Anything the fragment stage needs cannot ride here at all: the range is vertex-stage only.

Frame and lifetime contracts

Five rules that a caller has to honour regardless of which page they are reading. Each is stated with its reasoning on the method page that owns it.

RuleWhat it costs to ignoreFull contract
isDeviceQueried == false means nobody asked, never "not supported" Reading an unqueried descriptor as a feature list quietly disables capabilities the hardware has — and the previous revision of the type hid this behind guessed defaults of 4096 / 16 / 16 RenderCapabilities
Before a device exists, probe; afterwards, read the cache RHICapabilities::GetCapabilities creates and discards a Vulkan instance every call and describes the first enumerated device; VulkanRenderer::GetCapabilities is a copy of the device actually chosen. Note that the renderer's returns a copy, not a reference RHICapabilities
One EndFrame per BeginFrame, even when nothing drew BeginFrame resets the slot's fence before acquiring; skipping EndFrame leaves that fence unsignalled and the next BeginFrame waits on it forever BeginFrame, EndFrame
Render is recording, and needs this cycle's BeginFrame Its guard is initialized && frameActive, and EndFrame does not clear frameActive — a second Render re-records a command buffer that may still be running Render
The swapchain extent is fixed at Initialize No swapchain recreation exists, so a resized window keeps rendering at the old extent; GetExtent reports that fixed size and is the number to build an aspect ratio from GetExtent

The creation order inside Initialize — instance, surface, device pick, device, swapchain, render pass, depth, framebuffers, command buffers, pipeline, sync objects — is private: the surface must exist before a device is picked, because queue-family presentation support is queried against that surface, and Initialize is the only legal way through it. Geometry is not part of it; vertex and index buffers come from SetMesh.

Coverage

GapDetail
Names the previous guide documented that do not exist IRenderer, RendererFactory::Create and CreateWithFallback, Vulkan / DX12 / Metal renderer classes, APIType, IsMetalSupported, IsDX12Supported, GetPreferredAPI, and the IsVulkanSupported-style "runtime availability" reading those implied. Recorded so the absence is findable; the reasoning for compile-time backend selection is in docs/RendererDesign.html
The capability translation seam has no page Vulkan/VulkanCapabilities.h holds the two free functions under Module functions. Its per-field Vulkan-to-descriptor mapping — which VkPhysicalDeviceFeatures member feeds which bit, and which limits are cast — is documented in that header and in the design document, not restated here. Two of its behaviours do appear on class pages: supportsComputeShader is set true without a query because Vulkan makes compute mandatory, and uniformBufferOffsetAlignment comes from the minimum alignment
VulkanRenderer internals Swapchain recreation, synchronisation objects, descriptor and pipeline construction are implementation and belong in a design document under docs/design/ — there is none for the Vulkan backend yet, which is why the frame and lifetime rules on this page are stated from the source. The private step list is named there too
Thread-safety is asserted nowhere No header in this module states a thread requirement, and no class here holds a mutex or an atomic. What the code supports is narrower: one thread must drive the frame protocol, because currentFrame, imageIndex and frameActive are shared by all three calls, and on macOS Initialize calls AppKit ([nsWindow setContentView:]) which AppKit wants on the main thread. Recorded as a gap, not as a rule — the headers do not say it
ShadersSpv.h Generated SPIR-V held as data, consumed by CreatePipeline. Its content is a build artefact and how it is regenerated — Vulkan/gen_spv_header.py over Shaders/MC.vert and MC.frag — is documented nowhere on this site
Vertex has no user Compiled into the library, never constructed: no pipeline, mesh, test or application names it. Stated on its own page rather than presented as a working format
RendererTest and the fixture pattern Declared under __UNIT_TEST__ in RendererTest.h and registered with the runner documented in Test. Its cases are quoted as call sites on Render, GetCapabilities and Initialize; the fixture itself is not engine API
Contracts that belong to another module What OS::Window means by its width and height, and who owns the native handle, is OSAL; the assert family used by the test cases is Core: Debug; matrix builders are Math. None of it is restated here
