Module Index / Renderer

Renderer

namespace hbe::Renderer Engine/Renderer 7 headers, 6 sources — a Vulkan renderer today, one API-neutral device descriptor, and the seam a second backend would copy

Module description

The renderer's durable idea is RenderCapabilities: one descriptor whose field names are chosen so Vulkan, Direct3D 12 and Metal can all answer them, filled from a real device rather than assumed. The architecture document for the whole render-hardware-interface design is docs/RendererDesign.html, and docs/design/LightweightRenderer_Design.html covers the lightweight path.

What the previous guide described that is not in this tree. There is no Engine/Renderer/IRenderer.h, no RendererFactory.h, and no DX12/ or Metal/ backend directory — the old document's own marginal notes already called the factory sketch aspirational, and the code never grew the interface. The backend is selected by macros at compile time, the way OSAL selects a window implementation, which is exactly why an APIType runtime enum was removed: it had one enumerator, nothing branched on it, and every use was an assertion that could not fail. Backend identity now travels in the descriptor's deviceName and apiVersionMajor / apiVersionMinor.

RenderCapabilities (Engine/Renderer/RenderCapabilities.h)

Class description

One device, described in words every backend can answer. Field names are deliberately neutral, and the header documents the mapping each backend is expected to use. Nothing in here is a default the engine hopes for: values come from the device, and the default-constructed object means nothing was asked.

Template parameters

None — RenderCapabilities is not a template.

Class methods

One constructor, which zero-fills: an all-zero descriptor is an explicitly unqueried one.

Non-member helper functions

None. Translating a real device into this descriptor is backend work — see Coverage for where the Vulkan translation lives.

isDeviceQueried == false means nobody asked, never "not supported". Treating an unqueried descriptor as a feature list is how code quietly disables a capability the hardware has, or — worse — how a test that never probed passes. Check this flag before reading any supports… bit.

Class methods

RHICapabilities (Engine/Renderer/RHICapabilities.h)

Class description

Answers the capability questions that arrive before a renderer does — the installer and the test suite being the two that must ask without a window.

Template parameters

None — RHICapabilities is not a template.

Class properties

None. There is no instance and no cache: every answer is a fresh probe.

Class methods

[[nodiscard]] static bool IsVulkanSupported() noexcept;

/// Probe the first available device, creating and discarding a Vulkan instance.
/// @return a descriptor whose isDeviceQueried is false when nothing could be probed
[[nodiscard]] static RenderCapabilities GetCapabilities() noexcept;
This call is not cheap, and the return value says so rather than hiding it. GetCapabilities creates a throwaway Vulkan instance, reads the first physical device through the same adapter the renderer uses, and tears the instance down. Once a renderer owns a device, call VulkanRenderer::GetCapabilities instead: it is cached, and it describes the device that was actually chosen, which may not be the first one enumerated. A false isDeviceQueried in the result means the probe failed, and that is the case a caller must branch on.

Non-member helper functions

None. The older guide also listed IsMetalSupported, IsDX12Supported and a GetPreferredAPI returning an APIType; none of those exist, and neither does the enum they were built around.

VulkanRenderer (Engine/Renderer/Vulkan/VulkanRenderer.h)

Class description

The Vulkan backend, and today the only renderer built. It owns instance, surface, device, swapchain and command buffers, and takes the OS window through the portable OS::Window facade — reaching the native handle only where Vulkan requires it.

Template parameters

None — VulkanRenderer is not a template.

Class properties

The Vulkan objects it creates — instance, surface, device, queues, swapchain, command buffers and descriptors — all private, plus the cached RenderCapabilities filled by QueryCapabilities.

Class methods

[[nodiscard]] bool Initialize(OS::Window* window) noexcept;
void Shutdown() noexcept;

void BeginFrame() noexcept;
void Render(float deltaTime) noexcept;
void EndFrame() noexcept;

[[nodiscard]] const RenderCapabilities& GetCapabilities() const noexcept;
[[nodiscard]] VkExtent2D GetExtent() const noexcept;

void SetMesh(const Mesh& mesh) noexcept;

void SetView(const float* m) noexcept;
void SetProj(const float* m) noexcept;
MethodContract a caller depends on
InitializeReturns false rather than throwing — the engine is exception-free, so every Vulkan creation step is a bool the caller has to honour. It takes the application's window and nothing else
BeginFrame, Render, EndFrameThe frame contract, in that order. Render takes the frame delta in seconds, matching SystemStatistics::GetDeltaTime
GetCapabilitiesCached, and it describes the device this renderer picked — the answer to prefer once a device exists
SetModel, SetView, SetProjMatrices as 16 float; see PushConstants for where they land, and Matrix4x4 for producing them
SetMeshInstalls geometry and rebuilds its vertex buffers — a per-mesh change, not a per-frame one
GetExtentThe swapchain's actual extent, which can differ from the window's requested size

The creation steps — CreateInstance, CreateSurface, PickDevice, CreateDevice, QueryCapabilities, CreateVertexBuffers — are private: the order is the backend's business, and Initialize is the only legal way through it.

None — all four are plain structs.

Class properties

Listed above. Both vertex types are public data with constructors that take components in order: Vertex(x, y, z, r, g, b, a) and MeshVertex(x, y, z, nx, ny, nz).

Class methods

Constructors only, including = default so an array of them can be built without initialising every field twice.

Non-member helper functions

IdentityMatrix, which fills a matrix argument in place.

Two vertex formats in one module is a fact, not a mistake: Vertex is the unlit example layout, MeshVertex the lit one. A pipeline is created against one of them, so the type you build a mesh from has to be the type the pipeline was told about.

Coverage

GapDetail
Names the previous guide documented that do not exist IRenderer, RendererFactory::Create and CreateWithFallback, Vulkan/DX12/Metal renderer classes, APIType, IsMetalSupported, IsDX12Supported, GetPreferredAPI. Recorded here so the absence is findable; the reasoning for removing the runtime API-kind enum is in docs/RendererDesign.html.
The capability translation seam Vulkan/VulkanCapabilities.h turns a physical device into a RenderCapabilities, and it is the shape a second backend would copy rather than extend. Its per-field mapping is documented in that header and in the design document, not here.
VulkanRenderer internals Swapchain recreation, synchronisation objects and descriptor layout are implementation, and belong in a design document under docs/design/ — there is none for the Vulkan backend yet.
ShadersSpv.h Generated SPIR-V held as data. Its content is a build artefact; how it is regenerated is not documented anywhere on this site.
