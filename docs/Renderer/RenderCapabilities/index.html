RenderCapabilities

Engine/Renderer/RenderCapabilities.h namespace hbe::Renderer trivially copyable one graphics device described in words every backend can answer — identity, twenty-one one-bit flags, eighteen limits

Class description

A plain aggregate of numbers: which device answered, what it can do, how far each thing may go. Field names are chosen to be expressible by Vulkan, Direct3D 12 and Metal alike, so a backend adapter only translates names and never reshapes the struct; the mapping the Vulkan adapter uses is written out per field in the header and quoted on the module page. Nothing in the type is a default the engine hopes for — a real value arrives only from a query, and the constructor zeroes everything so an unqueried descriptor cannot be mistaken for a queried one.

The file closes with static_assert(std::is_trivially_copyable_v<RenderCapabilities>), because the descriptor is passed and returned by value across the backend seam. Adding a member with a non-trivial constructor, a reference or an owning pointer turns that assertion into a compile error at the definition, not a silent change of calling convention later.

isDeviceQueried == false means nobody asked, never "not supported". Every limit of a fresh descriptor is 0 and every bit is false, so reading a limit before checking this flag gives you a device that supports nothing and draws to a 0×0 texture. The previous revision of this type shipped 4096 / 16 / 16 and supportsTessellation = false as defaults; real hardware contradicted all four numbers and a caller had no way to tell the guess from a measurement. Check the flag first — that is the only contract in this header a caller must not skip.
A runtime-only description: never copy these bytes anywhere. The feature flags are twenty-one bool : 1 bit-fields in one contiguous run, and the header states two consequences. You cannot take the address of one — &caps.supportsComputeShader does not compile — and bit order within a storage unit is implementation-defined, so the struct must never be serialised, memcpyd between processes, or uploaded to a shader. Read and write the fields by name.

Template parameters

None — RenderCapabilities is not a template.

Class properties

There is no private: section: every name below is public data, read directly by callers in this module and its tests. The badges say which kind of declaration each row is.

MaxDeviceNameLength static constexpr size_t MaxDeviceNameLength = 128; member constant Size of the inline deviceName buffer, so an identity needs no allocation. apiVersionMinor uint8_t apiVersionMinor; public data Minor version alongside it. There is no patch field: the descriptor deliberately has no room for a driver-build number, which belongs to driverVersion

Feature support — twenty-one bits, one storage run

Each is bool : 1. They are one run so they share storage units instead of burning a byte apiece; see the note above about what that also forbids.

NameDeclarationWhat it means
isDeviceQueried bool isDeviceQueried : 1; public bit field Not a feature. True only when an adapter completed a real query — the Vulkan adapter writes it last, after every other field. An adapter must set it on success only
supportsComputeShader bool supportsComputeShader : 1; public bit field Programmable compute stage. Vulkan makes compute mandatory in core 1.0, so there is no feature bit to read and the Vulkan adapter sets this to true by definition — on this backend it is not evidence of anything
supportsTessellation bool supportsTessellation : 1; public bit field Hull and domain equivalent — Vulkan tessellationShader
supportsGeometryShader bool supportsGeometryShader : 1; public bit field Geometry stage. Always present on Direct3D 12, and Metal has no such stage at all, so this bit is where the three backends genuinely disagree
supportsMultiDrawIndirect bool supportsMultiDrawIndirect : 1; public bit field One indirect call drawing several ranges, bounded by maxDrawIndirectCount
supports32BitIndices bool supports32BitIndices : 1; public bit field Index buffers of uint32_t — Vulkan fullDrawIndexUint32. The renderer's own index path uses them unconditionally
supportsCubeTextureArrays bool supportsCubeTextureArrays : 1; public bit field Cube maps as array layers — Vulkan imageCubeArray
supportsIndependentBlend bool supportsIndependentBlend : 1; public bit field Different blend state per colour attachment
supportsDualSourceBlend bool supportsDualSourceBlend : 1; public bit field Two source colours per blend

supportsWireframeFill bool supportsWireframeFill : 1; public bit field Non-solid fill. A debug-drawing convenience modern APIs tend to omit

Class methods

Exactly one: the default constructor. There is no destructor, no assignment operator and no accessor — the class is data plus a rule for what "no data" looks like, which is the point of keeping it trivially copyable.

MethodSignatureWhat a caller depends on
constructors RenderCapabilities() Zero-fills all forty-six data members and sets isDeviceQueried to false, so an all-zero descriptor is an explicitly unqueried one rather than a device that supports nothing

Non-member helper functions

None. RenderCapabilities.h declares no free function — translating a real device into this descriptor is backend work, and the Vulkan translators sit in Engine/Renderer/Vulkan/VulkanCapabilities.h as FillRenderCapabilities and QueryDefaultDeviceCapabilities. They are listed under module functions and explained per field in that header and in docs/RendererDesign.html.

Coverage

GapDetail
The per-backend field mapping The header carries a Vulkan / Direct3D 12 / Metal mapping comment for every field, and the Direct3D 12 and Metal columns are targets, not facts: no such backend exists in this tree. Quoting them as engine behaviour would repeat the mistake that deleted the previous guide, so this page states only what the Vulkan adapter actually does
Exact Vulkan source of each value Which VkPhysicalDeviceFeatures member or VkPhysicalDeviceLimits field feeds each row is VulkanCapabilities.cpp's business, and it is deliberately not restated field by field here; the two cases a caller can be surprised by — supportsComputeShader being set without a query, and uniformBufferOffsetAlignment coming from the minimum alignment — are noted in their rows above
Who fills this descriptor Two producers: VulkanRenderer caches one filled from the device it picked, and RHICapabilities returns a throwaway one. Their costs differ; documented on those pages, not here
Which fields a backend may leave at zero The header says Metal exposes no driverVersion; with only a Vulkan backend built, no engine code depends on that yet. Treat a zero limit as "ask this backend" rather than "unsupported", which is the same rule isDeviceQueried encodes for the whole struct
