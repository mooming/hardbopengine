RenderCapabilities

member of hbe::Renderer::RenderCapabilities Engine/Renderer/RenderCapabilities.h 1 overload build an "unknown" descriptor: nothing queried, nothing supported, no limits

Signature

RenderCapabilities();

Function description

Initializes every one of the forty-six data members to zero — deviceName to an empty string, deviceType to DeviceType::Unknown, every flag to false, every limit to 0, isDeviceQueried to false. It takes no argument because there is no sensible partial state: the type's only two states are "nobody asked" and "a backend answered", and this constructor can only produce the first.

The explicit member-initializer list in RenderCapabilities.cpp carries the warning that a new field must be added to it too. That is not ceremony — a field left out of the list would keep an indeterminate value while the descriptor still self-reported as unqueried, which is the exact bug this constructor exists to prevent.

Zeroing is the fix for a bug this type actually shipped. The previous revision defaulted to maxTextureDimension2D = 4096, maxVertexAttributes = 16, maxUniformBufferBindings = 16 and supportsTessellation = false. Real hardware the code was tested on answered 16384, 31 and 155 with tessellation supported, so a caller could not tell a measurement from a guess, and a wrong guess in the safe direction still silently disabled a feature the GPU had. Every zero you see here is a deliberate "unknown", so read isDeviceQueried before reading any of them.

Parameters

None.

Return value

There is no return value to inspect: the constructor is the report. An object it built describes no device, and the only way to learn whether a later object describes one is isDeviceQueried. Because the type is trivially copyable — asserted at the bottom of the header — a descriptor is also cheap to hand back by value, which is how both RHICapabilities::GetCapabilities and VulkanRenderer::GetCapabilities return it.

Examples

The pattern both producers use: construct an unknown descriptor first, then let a backend fill it, so a failure halfway through the query leaves "unknown" rather than a half-written device.

From Engine/Renderer/RHICapabilities.cpp

// Real values, read from the driver - see VulkanCapabilities for the translation. The
// descriptor self-reports as unqueried when no device answers, so callers can tell the
// difference between "this machine has nothing" and "nobody asked".
RenderCapabilities capabilities;
QueryDefaultDeviceCapabilities(capabilities);

return capabilities;

The same reset-then-fill is what makes the adapter idempotent: it starts from a fresh unknown descriptor before touching the driver, so a call on a null VkPhysicalDevice leaves the caller's object explicitly unqueried instead of stale.

From Engine/Renderer/Vulkan/VulkanCapabilities.cpp

// Start from "unknown" so a failed query can never leave stale or invented values behind.
outCapabilities = RenderCapabilities();

if (physicalDevice == VK_NULL_HANDLE)
{
        log.OutError("Error: cannot query capabilities from a null physical device; leaving capabilities unqueried");
        return;
}

What a fresh descriptor must never do is assert a limit. The unit test for this constructor asserts exactly that, and is the only executable statement of the contract.

From Engine/Renderer/RendererTest.cpp

AddTest("RenderCapabilities starts explicitly unknown", [](auto& ls)
{
        const Renderer::RenderCapabilities caps;

        ls << "isDeviceQueried=" << caps.isDeviceQueried << " maxTextureDimension2D=" << caps.maxTextureDimension2D;

        Assert(!caps.isDeviceQueried, "A fresh descriptor must not claim to describe a device");
        Assert(caps.maxTextureDimension2D == 0, "Unqueried limit must be zero, not a guessed default");
        Assert(caps.deviceName[0] == '\0', "Unqueried device name must be empty");
        Assert(caps.deviceType == Renderer::DeviceType::Unknown, "Unqueried device type must be Unknown");
});
