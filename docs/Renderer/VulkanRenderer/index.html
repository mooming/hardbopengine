VulkanRenderer

Engine/Renderer/Vulkan/VulkanRenderer.h namespace hbe::Renderer no base class non-copyable the Vulkan backend: instance, surface, device, swapchain, pipeline and two frames in flight, reached by constructing it directly

Class description

A concrete class with no interface behind it. There is no IRenderer to hold it through and no factory to ask for it — the example constructs it on the stack and calls it by name, which is the only pattern in this tree: "Vulkan-only: construct the concrete renderer directly (no factory, no inheritance)" says the comment in Applications/VulkanExample/Main.cpp. The header's own wording is "Concrete Vulkan renderer (no inheritance)". Backend choice is a compile-time and link-time decision, the way OSAL picks a window implementation, and the argument for it lives in docs/RendererDesign.html.

It owns every Vulkan object the frame needs — instance, surface, logical device, one queue, swapchain with its images and views, a depth image, one render pass, one framebuffer per image, a command pool with one command buffer per frame in flight, a pipeline layout with a single push-constant range, one graphics pipeline, two shader modules, the mesh's vertex and index buffers, and the semaphores and fences that pace two frames. All of that is private, and the destructor calls Shutdown, so an object going out of scope tears the whole set down in dependency order.

Two files implement one class: VulkanRenderer.cpp holds the portable pipeline and the frame loop, and VulkanRenderer.mm holds the macOS surface — a CAMetalLayer adopted by a layer-backed content view, wrapped by vkCreateMetalSurfaceEXT. On Windows the surface comes from the window handle inside VulkanRenderer.cpp; on Linux CreateSurface has no implementation and returns false, so Initialize fails there.

Copy is deleted, and move is simply absent. The header declares VulkanRenderer(const VulkanRenderer&) = delete and the matching assignment as deleted; it declares no move operation either, and since it declares a destructor the compiler would not synthesise one. The object therefore lives in exactly one place — a member of your class, a static, a stack local — and neither the Vulkan handles nor the OS::Window* it borrows can be relocated by a container. See the constructors.
This header drags Vulkan into everything that includes it. VulkanRenderer.h does #include <vulkan/vulkan.h> with no guard, its private section is made of Vulkan types, and GetExtent returns VkExtent2D by value. Any translation unit that wants to render is therefore compiling against the SDK headers, which is why this module cannot compile out when the SDK is absent — see module variables. Code that only needs a window size can read OS::Window::GetWidth instead of including this header — the two numbers are not the same thing, as GetExtent explains.

Template parameters

None — VulkanRenderer is not a template.

Class methods

Thirteen documented names. The lifecycle pair is Initialize / Shutdown; the frame trio must run in the order its name spells; the three setters are plain copies that can run any time.

Frame contract

The three frame calls are one protocol with a shared flag between them, and each one behaves differently when that flag says "no frame". This is the order the example uses and the only order the code supports:

CallRequiresProduces for the next call
BeginFrame initialized A fence reset for this slot, an acquired imageIndex, and frameActive set only if that index has a framebuffer
Render initialized and frameActive A recorded, ended command buffer for currentFrame. Records nothing when either is false
EndFrame initialized — it runs even when there is no frame, to release the fence A submit and a present, or an empty submit; then currentFrame advances
Render without BeginFrame is a no-op the first time and a double submit the second. frameActive starts false, so a Render before any BeginFrame records nothing — the module's own test renderer.Render(0.016f); on a renderer that was never initialized relies on exactly that. But EndFrame never clears frameActive: it stays true after a successful frame. Calling Render twice before the next BeginFrame therefore re-records the same command buffer, and the second EndFrame submits a command buffer whose previous submission may still be running, with no fence waited in between. Keep the calls one-for-one.
A resize has no effect on what is rendered. extent is written once inside CreateSwapchain, which Initialize calls exactly once, and the depth image, framebuffers, render area and viewport are all built from it. When the window changes size the layer's drawable changes with it, but the swapchain image stays the same, and the only signal the code takes from that is VK_ERROR_OUT_OF_DATE_KHR or VK_SUBOPTIMAL_KHR on acquire — out-of-date ends the frame (draws nothing), suboptimal is ignored and keeps drawing at the old extent. Recreating the swapchain is called out in BeginFrame's comment as "the real fix (tracked as a follow-up)" and does not exist, so aspect ratio comes from GetExtent taken once, at startup.

Coverage

GapDetail
The private creation sequence Thirteen private steps — CreateInstance, CreateSurface, CreateMetalSurface, PickDevice, CreateDevice, QueryCapabilities, CreateSwapchain, CreateRenderPass, CreateDepthResource, CreateFramebuffers, CreateCommandBuffers, CreatePipeline, CreateSyncObjects — plus CreateBuffer, RecordFrame, ReleaseVertexBuffers and Destroy. Their per-field Vulkan detail is implementation and belongs in a design document; there is none for this backend yet, which is why the frame and lifetime contracts above are stated from the code rather than from a document
Swapchain recreation Not a documentation omission: no such code exists. The class cannot recover from VK_ERROR_OUT_OF_DATE_KHR, and there is no public way to ask for one — no Resize, no RecreateSwapchain. See the hazard under GetExtent
Thread-safety is asserted nowhere The header documents no thread requirement and the class holds no mutex, atomic or thread-local; every guard is a plain bool. What the code does establish is that one thread must drive the whole protocol, because currentFrame, imageIndex and frameActive are shared by all three frame calls. On macOS Initialize additionally calls AppKit ([nsWindow setContentView:]) through the borrowed window, and AppKit's own rule is that this happens on the main thread — a rule this class neither checks nor states. Recorded here because the header is silent, not because the code supports a claim
The mesh buffer lifetime rule is not stated in the header SetMesh's comment says "Upload (or replace) the mesh to render" and nothing about in-flight work, yet the first thing its implementation does is free the old buffers with no vkDeviceWaitIdle. The page for it states what the code does and what that costs
One vertex format, baked in The pipeline's vertex input is sizeof(MeshVertex) with positions and normals at offsetof, so Vertex — position and colour — can only be rendered by a different pipeline this class does not build
RendererTest Engine/Renderer/RendererTest.h declares the fixture under __TEST__ and RendererTest.cpp exercises null-window initialization, unqueried capabilities and a Render with no frame — quoted as a call site on Initialize and Render. It is a fixture, not API: the runner is the Test module's subject
Shader content The push block the pipeline matches is declared in Engine/Renderer/Vulkan/Shaders/MC.vert as Push { mat4 model; mat4 viewProj; } and shipped as generated data in Vulkan/ShadersSpv.h; how that header is regenerated is documented nowhere on this site. PushConstants carries the mirror-image rule
