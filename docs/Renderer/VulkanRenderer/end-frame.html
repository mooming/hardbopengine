EndFrame

member of hbe::Renderer::VulkanRenderer Engine/Renderer/Vulkan/VulkanRenderer.h noexcept submit, present, and advance the frame slot — and release the fence even on a frame that drew nothing

Signature

void EndFrame() noexcept;

Function description

After the initialized guard it splits on frameActive, and both branches end with work on the queue:

WhenWhat runs
frameActive vkQueueSubmit of the frame's command buffer, waiting semaphoresImageAvailable[currentFrame] at COLOR_ATTACHMENT_OUTPUT and signalling semaphoresRenderFinished[currentFrame], with fences[currentFrame] as the completion fence. Then vkQueuePresentKHR waiting that render-finished semaphore on imageIndex.
no frame An empty vkQueueSubmit whose only content is the fence. It draws nothing and exists purely to put the fence back to signalled, so the next BeginFrame can wait on it without hanging.

Finally currentFrame = (currentFrame + 1) % MAX_FRAMES_IN_FLIGHT. This is the only place the slot advances, and the reason the two frames in flight rotate at all: the CPU may run ahead by one frame, and no further, because the next BeginFrame waits on the fence that this call armed.

Two results are tolerated rather than reported. VK_SUBOPTIMAL_KHR from the present is treated as success, which is the code acknowledging a surface that no longer matches the window and continuing anyway. The first present that succeeds logs one line — extent, swapchain image count and index count — as proof the pipeline reached the screen, latched by firstFramePresented.

Every BeginFrame must be answered by exactly one EndFrame, including the frames that render nothing. BeginFrame resets this slot's fence before it tries to acquire an image, so if the acquire fails and you skip this call, the fence is left unsignalled, the slot never advances, and the next BeginFrame waits on it with an infinite timeout. A skipped frame is a normal event — a resize makes it normal — and this function's empty-submit branch is what makes skipping it survivable. Do not treat "nothing was drawn" as a reason to omit the call.
A failed submit does not advance the slot, and releases the fence by hand. If vkQueueSubmit fails, the code logs it, issues a zero-command-buffer submit carrying the same fence so the wait cannot hang, and returns before incrementing currentFrame. The frame is lost — it is never presented — but the cycle stays consistent, and the next BeginFrame reuses the slot. Present failures, by contrast, are logged and the slot advances normally, because the work already ran.

Parameters

None.

Return value

void. A frame that failed to submit and a frame that presented are the same to the caller; both errors go to the always-on error logger with their VkResult. There is no "was this frame presented" query, and frameActive stays true either way — which is the flag Render trusts, so a caller that loops Render / EndFrame without a fresh BeginFrame is submitting the same command buffer twice.

Examples

From Applications/VulkanExample/Main.cpp

        renderer.BeginFrame();
        renderer.Render(deltaTime);
        renderer.EndFrame();

        std::this_thread::sleep_for(std::chrono::milliseconds(16));

Nothing between the three calls is conditional, which is the correct shape: the loop does not try to detect a lost frame, and does not need to, because the empty submit inside this function keeps the fence honest.
