~VulkanRenderer

member of hbe::Renderer::VulkanRenderer Engine/Renderer/Vulkan/VulkanRenderer.h defined in VulkanRenderer.cpp destroys the renderer by calling Shutdown — which is a no-op unless initialization fully succeeded

Signature

~VulkanRenderer();

Function description

Its whole body is Shutdown(), so the destructor inherits that function's rule: destroy nothing unless initialized is true, and otherwise return. Letting a renderer go out of scope is therefore always safe — including the case the test exercises, a renderer that was constructed and never successfully initialized.

When it does run, teardown follows dependency order rather than creation order reversed at random: wait the device idle, then both semaphore arrays and the fences, then the mesh's vertex and index buffers, then the command pool — which frees its command buffers with it — then the pipeline, pipeline layout and both shader modules, then the framebuffers, then the depth view before the depth image and its memory, then the swapchain image views before the swapchain, then the logical device, and finally the surface before the instance. Every handle is nulled afterwards, so a second destruction finds nothing to act on.

A failed Initialize leaks what it managed to create, and the destructor cannot help. Initialize returns false at the first failing step without calling Destroy, and initialized — the flag Shutdown and this destructor gate on — is set only after the last step succeeds. So if instance creation, surface creation, device picking, device creation or anything after them fails, the objects already built stay alive with no owner: nothing in the public interface frees them, and destroying the renderer returns at the first line. The example exits the process on that path, which is the only recovery available today.
Teardown clears handles, not answers. Destroy resets frameActive, currentFrame and imageIndex, but it leaves capabilities, extent, window and the three matrices exactly as they were. After the destructor or an explicit Shutdown, GetCapabilities still reports isDeviceQueried == true with the name of a device that no longer exists, and GetExtent still reports the old size. Both are safe to call — they touch no Vulkan object — but neither describes live hardware any more.

Parameters

None.

Return value

None, and nothing to check: Shutdown returns void and the Vulkan destroy entry points it calls report no result. The header does not write noexcept here, but destructors are implicitly noexcept and every function this one reaches is declared noexcept, so the difference is cosmetic.

Examples

The test round trip is the clearest statement of what the destructor guarantees: a null-window Initialize is rejected, a Render with no frame does nothing, capabilities stay unqueried, Shutdown is called explicitly, and then the destructor runs on the same object without anything being double-freed.

From Engine/Renderer/RendererTest.cpp

AddTest("VulkanRenderer Round Trip", [](auto& log)
{
        VulkanRenderer renderer;
        OS::Window* window = nullptr;

        // Initialize rejects a null window on purpose - the surface is built from the window,
        // and queue family support is queried against that surface.
        Assert(!renderer.Initialize(window), "Initialize must reject a null window");
        renderer.Render(0.016f);
        Assert(!renderer.GetCapabilities().isDeviceQueried, "A rejected Initialize must leave capabilities unqueried");
        renderer.Shutdown();

        log << "null-window round trip is a safe no-op";
});

The application reaches the same function the ordinary way, after closing down the loop — and note that it closes the window only after the renderer has shut down, which is the correct order for a borrowed OS::Window:
