BeginFrame

member of hbe::Renderer::VulkanRenderer Engine/Renderer/Vulkan/VulkanRenderer.h noexcept wait this slot's fence, reset it, and acquire the next swapchain image — the call that decides whether this frame will draw at all

Signature

void BeginFrame() noexcept;

Function description

Five things happen, in this order, once the initialized guard passes:

vkWaitForFences(device, fences[currentFrame], UINT64_MAX)   // block until this slot's previous work is done
vkResetFences(device, fences[currentFrame])                  // now this slot may be recorded again
frameActive = false;                                          // nothing is a frame until the acquire succeeds
vkAcquireNextImageKHR(..., UINT64_MAX, imageAvailable[currentFrame], imageIndex)
frameActive = imageIndex < framebuffers.size()               // the acquired image must have a framebuffer

The fence wait is the CPU-side pacing of the whole loop: with MAX_FRAMES_IN_FLIGHT = 2, waiting on the current slot's fence guarantees that the work submitted for this slot two frames ago has finished, which is what makes re-recording its command buffer legal. The fences are created already-signalled so the very first frame does not wait on work that was never submitted.

If the acquire returns anything other than VK_SUCCESS or VK_SUBOPTIMAL_KHR — in practice VK_ERROR_OUT_OF_DATE_KHR — the function returns there, leaving frameActive false. This round draws nothing: Render will refuse to record and EndFrame will present nothing. Suboptimal is treated as usable, so a window that changed size keeps drawing at the old extent.

The fence is reset before the acquire, so EndFrame is owed even on a frame that drew nothing. This is the load-bearing rule of the protocol. If you call BeginFrame and then skip EndFrame because nothing was drawn, the fence you just reset is never signalled again, currentFrame never advances, and the next BeginFrame waits on that same unsignalled fence with an infinite timeout — a hang with no diagnostic. EndFrame exists to cover exactly this: when there is no frame it issues an empty submit whose only job is to release the fence.
A lost swapchain is reported and survived, never repaired. There is no swapchain recreation anywhere in the class; the in-code comment calls it "the real fix (tracked as a follow-up)". So once the surface goes out of date — resized away, minimized, monitor moved — every subsequent frame takes the early return and presents nothing, forever. Shutdown followed by Initialize would build a fresh swapchain at the current size, but nothing in this module detects the condition for you, and there is no public query that reports it.
Both waits are unbounded, and nothing tells the caller which one is blocking. The fence wait and the image acquire each pass UINT64_MAX, so a GPU that never finishes, or an acquire that never returns on a hidden surface, stops the calling thread rather than skipping a frame. There is no timeout branch, and no way to ask afterwards whether this BeginFrame actually got an image — frameActive is private. The only observable is that Render then records nothing.

Parameters

None.

Return value

void, and deliberately no status: a skipped frame is not an error the caller can act on, since the only available action — recreate the swapchain — does not exist. Treat the return as "the frame protocol advanced", not as "an image was acquired".

Examples

The example calls all three in the order that names them, once per loop iteration, with nothing conditional in between:

From Applications/VulkanExample/Main.cpp

        SetRotationY(model, angle);
        renderer.SetModel(model);

        renderer.BeginFrame();
        renderer.Render(deltaTime);
        renderer.EndFrame();

        std::this_thread::sleep_for(std::chrono::milliseconds(16));

The frame-rate cap here is a sleep_for, not the renderer: presentation mode is mailbox-or-FIFO and the fence wait is what actually bounds how far ahead the CPU runs.
