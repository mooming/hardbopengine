VulkanRenderer

member of hbe::Renderer::VulkanRenderer Engine/Renderer/Vulkan/VulkanRenderer.h 2 overloads — one usable, one deleted a renderer that holds no Vulkan object until Initialize runs, and can never be copied or moved

Signatures

Both declarations sit together in the header; the second exists to remove copying:

VulkanRenderer() noexcept;
VulkanRenderer(const VulkanRenderer&) = delete;

// Also declared deleted in the same block, and equally unusable:
VulkanRenderer& operator=(const VulkanRenderer&) = delete;

Function description

The default constructor is pure state: every handle becomes VK_NULL_HANDLE, the counts and indices become zero, initialized and frameActive become false, and each of the three matrices is filled with identity by IdentityMatrix. Nothing is created — no instance, no window query, no driver call — so this constructor cannot fail and is safe on a machine with no Vulkan install at all. That is what lets the module's test construct a renderer and ask it what it can do: see GetCapabilities.

Being constructed but not initialized is a real, reachable state with its own behaviour. The getters answer from their fields — GetCapabilities returns the zero-filled unknown descriptor, GetExtent returns {0, 0} — while BeginFrame, Render, EndFrame, Shutdown and SetMesh return at their first line. The three setters do not check, so SetModel and friends work before Initialize and their values survive into the first frame.

Identity matrices are a default that will surprise a caller who never sets projection. A renderer straight out of this constructor pushes an identity model, identity view and identity projection, so anything SetMesh installed is drawn in raw object coordinates: the example's unit quad covers a quarter of the screen, with no perspective and no Vulkan depth-range mapping. SetProj and SetView are not optional polish — the example builds a right-handed perspective mapped into Vulkan's [0, 1] depth with a Y flip, and only then calls them once.

Parameters

ParameterTypeRequirement
The usable constructor takes none.
(deleted copy) const VulkanRenderer& Exists only to be removed. A call is a compile error, and there is no overload that would accept it

Return value

Constructors return nothing, and this one has no failure to report either: readiness is Initialize's bool, and until that returns true the object describes a renderer that owns nothing.

Copy is deleted; move was never available. The header deletes the copy constructor and the copy assignment operator, and it declares a destructor — under the language rules a user-declared destructor means the move constructor and move assignment operator are not implicitly declared at all. So std::move(renderer) does not compile either. A renderer therefore lives at a fixed address for its whole life: not in a std::vector you might resize, not returned from a factory, not behind a std::unique_ptr you intend to move between owners. With two frames in flight and raw VkDevice-scoped handles inside, that restriction is the cheap way to make a real hazard impossible.

Examples

The only production call site, which also shows the intended lifetime shape — a stack object next to its window:

From Applications/VulkanExample/Main.cpp

// Vulkan-only: construct the concrete renderer directly (no factory, no inheritance).
VulkanRenderer renderer;
if (!renderer.Initialize(window.get()))
{
        // The logger is asynchronous: flush so its diagnostics survive this exit.
        Logger::Get().Flush();
        std::cerr << "Error: Failed to initialize Vulkan renderer" << std::endl;
        return 1;
}

The test constructs one with no window and no initialization at all, which the constructor explicitly supports: VulkanRenderer renderer; followed by const RenderCapabilities caps = renderer.GetCapabilities();, asserting that an uninitialized renderer must not claim queried capabilities. That quote and its consequences are on the capabilities page.
