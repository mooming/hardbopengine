GetExtent

member of hbe::Renderer::VulkanRenderer Engine/Renderer/Vulkan/VulkanRenderer.h const noexcept [[nodiscard]] the swapchain size chosen once at Initialize — the aspect ratio to build, and the number that will not follow a resize

Signature

[[nodiscard]] VkExtent2D GetExtent() const noexcept;

Function description

A field read of extent, which is written exactly once — inside CreateSwapchain, the fifth step of Initialize. Two rules decide it there. If the surface sizes itself from the window (caps.currentExtent.width == 0xFFFFFFFF) the window's GetWidth / GetHeight are used, clamped into the surface's minimum and maximum image extent. If the surface reports a real currentExtent, that wins outright. The macOS unit explains why the second branch is the important one: the CAMetalLayer is sized by AppKit to the view's bounds, so the layer's drawable size — and therefore the swapchain extent — follows the window's content rect, and the code reads the authoritative number from the driver instead of assuming the requested size.

That is the reason this getter exists at all. The size a caller asked a window for is not the size it ends up with: title bar, content layout and scale all intervene. The example states it as a comment where it uses the value: "The drawable follows the window content rect, so the aspect ratio comes from the renderer rather than the 800x600 we asked the window for."

Everything the frame draws into is derived from this one number: the depth image, every framebuffer, the render area and the dynamic viewport and scissor set during Render.

After a window resize this returns the pre-resize extent, and the rendered image keeps the pre-resize size. extent is never rewritten, because rewriting it means recreating the swapchain, the depth image and the framebuffers, and no such code exists in this class — BeginFrame's comment calls swapchain recreation "the real fix (tracked as a follow-up)". The only signals taken from a resize are acquire results: VK_ERROR_OUT_OF_DATE_KHR ends the frame without drawing, VK_SUBOPTIMAL_KHR is ignored and drawing continues at the old extent. OS::Window::GetWidth is no help as a cross-check either — it reports the size OSAL was last told, which no live user resize changes. The only in-API recovery is Shutdown followed by Initialize, which rebuilds at the current size.
Call it before Initialize and you get {0, 0} — which turns into a NaN, not a crash. The field is value-initialised by the constructor and there is no guard in this function, so an early call returns zeroes. Dividing width by height for an aspect ratio then yields 0.0f / 0.0f, which propagates silently through SetProj and produces an empty screen far from the mistake. Call it after Initialize returned true. The converse trap is Shutdown: the field is not cleared, so it keeps reporting the extent of a swapchain that no longer exists.

Parameters

None.

Return value

TypeWhat you get
VkExtent2D Swapchain width and height in pixels — a Vulkan struct, which is why anything calling this function is compiling against the SDK headers through this header. {0, 0} before Initialize, the startup extent after it, and the same stale extent after Shutdown. [[nodiscard]]; the call is a field read, so it is cheap enough to keep in a hot path even though the value never changes

Examples

From Applications/VulkanExample/Main.cpp

// The drawable follows the window content rect, so the aspect ratio comes from the
// renderer rather than the 800x600 we asked the window for.
const VkExtent2D extent = renderer.GetExtent();

float view[16];
float proj[16];
float model[16];
SetPerspective(proj, DegreeToRadian(60.0f), static_cast<float>(extent.width) / static_cast<float>(extent.height),
               0.1f, 100.0f);

One call, stored, used to build a projection that is then set once. Given that the value cannot change over the renderer's lifetime, caching it is not a premature optimisation here — it is the only behaviour that matches the renderer itself.
