DeviceType

Engine/Renderer/RenderCapabilities.h namespace hbe::Renderer enum class : uint8_t the class of device that answered, in the API's own terms

Class description

Five names for what kind of thing is behind the driver. It is the classification the API itself gives — Vulkan's VkPhysicalDeviceType — translated name for name, not a ranking the engine invented. One enumerator is special: Unknown is both the value of an unqueried descriptor and the value the Vulkan adapter gives a device the driver classifies as "other". 

enum class DeviceType : uint8_t
{
        Unknown = 0,
        DiscreteGpu,
        IntegratedGpu,
        VirtualGpu,
        CpuSoftware
};

Template parameters

None — DeviceType is not a template.

Class properties

NameDeclarationWhat it means
Unknown Unknown = 0 enumerator The value of a fresh descriptor, and also the value the Vulkan adapter writes for VK_PHYSICAL_DEVICE_TYPE_OTHER and for anything it does not recognise — so this enumerator is reached by real devices too, and only isDeviceQueried says which case you are in
DiscreteGpu DiscreteGpu (1) enumerator Separate GPU with its own memory. The answer a workstation gives, and the reason picking "the first device" is not the same as picking the fast one
IntegratedGpu IntegratedGpu (2) enumerator GPU sharing system memory with the CPU
VirtualGpu VirtualGpu (3) enumerator Paravirtual or remote adapter. Capability answers from one are the driver's, not the physical hardware's
CpuSoftware CpuSoftware (4) enumerator Software rasteriser — Vulkan VK_PHYSICAL_DEVICE_TYPE_CPU, which is what a driver-less CI machine exposes when it exposes anything at all

Non-member helper functions

None declared. There is no ToString and no stream operator for this enum anywhere in the module, so logging one prints the underlying integer; the engine's test cases report deviceType != DeviceType::Unknown rather than a name.

Ignoring deviceType is how a capability check passes on a CI machine and fails on real hardware. VirtualGpu and CpuSoftware are the answers a headless runner gives, and both will happily report the features their API mandates — Vulkan makes compute mandatory in core, so supportsComputeShader is true even for a software device. Branch on the type when a feature is about performance rather than correctness.

Coverage

GapDetail
No device-selection policy Nothing in this module picks a device because of its type. VulkanRenderer takes the first device offering a graphics queue that can present to the surface, so a system with an integrated and a discrete GPU gets whichever the driver enumerates first. Recorded on the renderer page as well
The Vulkan mapping table VulkanCapabilities.cpp translates five VkPhysicalDeviceType values; two of them (OTHER and the unmatched default) collapse onto Unknown, which is the one ambiguity this enum carries
No Metal or Direct3D 12 translation exists The header's mapping comment names MTLGPUFamily / isLowPower and DXGI_GPU_DESCRIPTOR as what a future adapter would read, but no such backend is in this tree
