PushConstants

Engine/Renderer/Vulkan/VulkanRenderer.h namespace hbe::Renderer 128 bytes the two matrices pushed inline with the draw — model and a CPU-combined viewProj, and not three matrices

Class description

One hundred twenty-eight bytes of raw floats: two float[16] side by side, column-major by the GL/Vulkan convention. The header states its one rule — it "must mirror the GLSL push block exactly" — and the shader agrees: layout(push_constant) uniform Push { mat4 model; mat4 viewProj; } uMat; in Engine/Renderer/Vulkan/Shaders/MC.vert. The renderer's pipeline layout declares one push-constant range: vertex stage only, offset 0, size sizeof(PushConstants).

The struct holds two matrices, not three, and the reason is arithmetic rather than taste. Vulkan guarantees a device supports at least 128 bytes of push constants — maxPushConstantBytes reports the real figure — so a block carrying model, view and projection separately would be 192 bytes and would not be portable at all. Combining viewProj = projMat * viewMat once per frame on the CPU is what leaves room for a model matrix inside the guaranteed 128, and the header says so: "viewProj is combined on the CPU once per frame, which is what leaves room for a model matrix."

Two independent declarations must keep agreeing with a third file. The struct here, the push-constant range built in CreatePipeline, and the Push block compiled into Vulkan/ShadersSpv.h have to describe the same bytes in the same order. Add a field — the header names the light direction as the thing "that moves to a uniform buffer later", which is precisely the change that would push this block past 128 — and the failure is a graphics-pipeline or layout creation error surfacing as a false from Initialize, or, if the GLSL block shrank instead, wrong transforms silently read from the wrong offsets. The API cannot catch this; the size check happens in the driver.
Vertex stage only. The range is declared with VK_SHADER_STAGE_VERTEX_BIT, so only the vertex shader may read these bytes; the fragment stage receives interpolated outputs (vNormal) and nothing else. Per-frame data the fragment stage needs cannot be added to this struct even if it fitted — it needs a buffer and a descriptor set, which this pipeline has none of.

Template parameters

Class properties

NameDeclarationWhat it means
model float model[16]; public data Offset 0, 64 bytes. A verbatim copy of the last value passed to SetModel, with no processing at all
viewProj float viewProj[16]; public data Offset 64, 64 bytes. projMat * viewMat, multiplied on the CPU during recording — the product of SetProj and SetView. There is no field for the view or the projection alone; neither reaches the shader separately

Class methods

None declared, and none needed: it is filled by memcpy and multiplication into a stack local, then handed to vkCmdPushConstants by address. Being an aggregate, PushConstants push{}; zero-fills it.

Non-member helper functions

IdentityMatrix, declared in the same header at namespace scope, fills a float[16] in place — the natural way to build the model half when no transform is wanted. The matrix multiply that produces viewProj is not public: MultiplyColumnMajor lives in an anonymous namespace inside VulkanRenderer.cpp, so a caller combining its own matrices has to use Matrix4x4 or write the loop.

Coverage

GapDetail
No size or layout assertion Unlike RenderCapabilities, which carries a static_assert in its header, this struct states its 128-byte contract in a comment only. A field inserted before viewProj would move it to offset 64+ while the compiled shader still read it at 64
No time, light or material data There is no slot for any of it and no descriptor set to hold it. The header flags the light direction as something to move to a uniform buffer "later"; until that exists, anything animated beyond the model matrix has to ride inside model
The device limit is never checked maxPushConstantBytes is queried and reported, but nothing compares it against sizeof(PushConstants); the driver decides whether vkCreatePipelineLayout accepts the range. In practice every Vulkan 1.0 device allows 128, which is why this gap has not bitten yet — see Initialize
Only one pipeline consumes it The struct is bound to one push-constant range in one pipeline layout. A second pipeline with a different block is a different struct, not a different field set in this one
