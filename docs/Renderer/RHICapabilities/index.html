RHICapabilities

Engine/Renderer/RHICapabilities.h namespace hbe::Renderer final static members only the two render-hardware-interface questions that arrive before a renderer exists

Class description

Two static functions, no state. They answer the questions an installer, a test runner or a startup log asks when nothing has been created yet: is this build able to talk to Vulkan at all, and roughly what can this machine do. The header's own instruction is that the renderer is the authority once it owns a device — VulkanRenderer::GetCapabilities reports the device that was actually picked and costs a copy — so this class is for the before-Initialize window and nothing else.

The two members are not equally expensive, and the difference is the first thing a caller needs to know: IsVulkanSupported reads a build-time flag and touches no driver, while GetCapabilities creates a throwaway Vulkan instance, reads one physical device through it and destroys the instance.

An availability question is not a capability answer, and vice versa. IsVulkanSupported() returns whether this binary was compiled against a reachable Vulkan SDK; it stays true on a machine with no loader, no installable client driver and no GPU. GetCapabilities() returns a descriptor whose isDeviceQueried is false when nothing could be probed — that flag, not the bool, is the signal that a device exists. A caller that checks only the bool will decide the machine can render and then be surprised by a descriptor of zeroes.

Template parameters

None — RHICapabilities is not a template.

Class properties

None. The class declares no data member, no nested type and no constructor — nothing is stored between calls, and nothing can be configured. Since no constructor is declared or deleted, the implicit ones still exist: RHICapabilities probe; compiles, and constructing one buys an empty object.

NameDeclarationWhat it means
None — there is no alias, no constant and no field in this class.

Class methods

Both members are static, noexcept and [[nodiscard]]: the engine is built without exceptions, so the only failure channel is the value you get back, and discarding it is a compile error.

MethodSignatureWhat a caller depends on
IsVulkanSupported static bool IsVulkanSupported() noexcept Compiles to a read of the VULKAN_SDK flag — no driver, no loader, no enumeration. True means this build can compile and link a Vulkan path

Non-member helper functions

None in RHICapabilities.h. The work these two delegate to sits in Engine/Renderer/Vulkan/VulkanCapabilities.h as the free functions QueryDefaultDeviceCapabilities and FillRenderCapabilities, listed under module functions.

The deleted guide also documented IsMetalSupported, IsDX12Supported and a GetPreferredAPI returning an APIType enumerator. None of the four exist anywhere in this tree — grep Engine/ for those names and there is no declaration, no definition and no use. Backends are chosen by macros at compile time, the way OSAL picks a window implementation, so there is no runtime API-kind value to prefer. That reasoning is docs/RendererDesign.html's, not repeated here.
