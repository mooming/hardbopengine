VulkanCapabilities

Engine/Renderer/Vulkan/VulkanCapabilities.h namespace hbe::Renderer the Vulkan spelling of the neutral capability descriptor: one translator per device, one probe without one

Class description

A utility header, not a class: its entire surface is two free functions at hbe::Renderer scope, and both answer the same question in two situations — what can this machine's Vulkan device do?, translated into the API-neutral RenderCapabilities descriptor. FillRenderCapabilities is the translator a renderer calls once it holds a physical device; QueryDefaultDeviceCapabilities is the pre-device probe for the question asked before any renderer exists — RHICapabilities::GetCapabilities's whole job.

This header is the seam the module's backend story turns on: backends are chosen by macros at compile time, the way OSAL does it — one neutral descriptor, one adapter per backend directory, and a macro decides which adapter compiles. A Direct3D 12 or Metal backend therefore adds its own translator writing the same descriptor rather than extending this one or introducing a runtime API-kind enum. What makes that work is that the descriptor's field names were chosen to be expressible by all three APIs, so an adapter translates names and never reshapes the struct.

Two behaviours of the translator are decisions, not readings. supportsComputeShader is set true without a query, because compute is mandatory in core Vulkan 1.0 and there is no feature bit to read; and uniformBufferOffsetAlignment takes the minimum alignment, because a caller needs the value to respect, not the driver's preference. Every other field is copied or cast from VkPhysicalDeviceProperties and VkPhysicalDeviceFeatures read straight off the device.

Template parameters

None — the header declares two free functions, and neither is a template.

Class properties

None — the header declares no types, no aliases, no constants and no data members of its own. The descriptor it fills is owned by RenderCapabilities.

Class methods

None — the two functions are free functions, and their contracts are tabled under Non-member helpers below and summarised in the module page's Module functions table.

FillRenderCapabilities void FillRenderCapabilities(VkPhysicalDevice physicalDevice, RenderCapabilities& outCapabilities) noexcept Resets the descriptor to all-unknown first, so a failed query can never leave stale or invented values; reads identity, features and limits from the device; sets isDeviceQueried last. QueryDefaultDeviceCapabilities bool QueryDefaultDeviceCapabilities(RenderCapabilities& outCapabilities) noexcept The no-owner probe: creates a throwaway instance, takes the first enumerated physical device, fills the descriptor, and destroys the instance on every path. Returns whether a device answered — failures are logged as warnings and leave the descriptor explicitly unqueried

The reset-then-fill order is the whole safety argument of the first function, so it is worth reading in the source:

The probe differs from the renderer's own instance creation in one deliberate way: it enables VK_KHR_portability_enumeration only if the loader advertises it, because a conforming driver is not required to offer the extension and enabling a missing one fails instance creation outright — where VulkanRenderer::CreateInstance asks unconditionally, entitled by its macOS portability assumption: 

	const bool enablePortabilityEnumeration = HasInstanceExtension(VK_KHR_PORTABILITY_ENUMERATION_EXTENSION_NAME);
	const char* enabledExtensions[] = {VK_KHR_PORTABILITY_ENUMERATION_EXTENSION_NAME};

	VkInstanceCreateInfo instanceInfo{};
	instanceInfo.sType = VK_STRUCTURE_TYPE_INSTANCE_CREATE_INFO;
	instanceInfo.pApplicationInfo = &appInfo;
	if (enablePortabilityEnumeration)
	{
		instanceInfo.flags |= VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR;
		instanceInfo.enabledExtensionCount = 1;
		instanceInfo.ppEnabledExtensionNames = enabledExtensions;
	}
