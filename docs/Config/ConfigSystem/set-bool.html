SetBool

member of hbe::ConfigSystem Engine/Config/ConfigSystem.h one overload write an existing bool-or-byte parameter by name — it creates nothing and reports nothing

Signature

void SetBool(const StaticString& key, bool value);

Function description

Interns key, looks it up in byteParams, and calls the stored setter. It is a write path only: no entry is created, no default is stored, and the parameter that owns the name is the thing that changes — the registry holds no value of its own.

Two lookups are folded in here because bool and uint8_t share one map. A name registered by a uint8_t parameter is therefore writable through this function, and the bool argument converts to 0 or 1 on the way in, so SetByte("X", 3) followed by SetBool("X", true) leaves that byte at 1. If that is not what you meant, use SetByte and keep the width explicit.

Parameters

ParameterTypeRequirement
key const StaticString& The registered name. A string literal works — StaticString converts from const char* and the conversion is what interns it. The lookup is confined to the byte map, so a parameter of that name registered as int, size_t or float is not found rather than converted. A defaulted StaticString is not an empty name: it is the interned string "None", so an accidental one here looks up that key and misses like any other unknown name
value bool The new value. No range to check, no failure it can cause — but see the thread rule below

Return value

void. A key that is absent — and a key whose identity is null, which the lookup tests separately with IsNull() — is answered by one log line under EngineSettings, and then nothing happens. There is no status to branch on, so a caller that cares verifies with GetBool — remembering that its not-found answer is false, the same as an honest false value.

Writing a non-atomic parameter from the wrong thread aborts in Debug and Dev. The setter the registry stored calls ConfigParam::Set, and that function asserts the calling thread equals the thread the parameter was constructed on unless the parameter is atomic. So a name-based write from a console or debug overlay to a ConfigParam<T, false> owned by another subsystem stops the process — under __DEBUG__, which Debug and Dev have and Release does not (BuildConfig). Every parameter the engine registers today is the atomic form, so this trap only bites parameters you add.

Examples

Illustrative — the only occurrences of this call family in the tree sit commented out inside Engine::ShutDown in Engine/Engine/Engine.cpp; nothing calls them in a live build.

auto& settings = hbe::ConfigSystem::Get();

settings.SetBool("Physics.UseSleeping", false);   // needs a bool parameter registered under that name

// The names that really exist in a default build, with their maps:
//   Log.Level, Log.Engine, Log.Engine.Print, Log.TaskSystem                  -> byte map
//   Task.RegistryInitialRecords, Task.RegistryGrowByRecords, Task.RegistryMaxRecords -> size map
//   TaskStreamDurationThreshold                                           -> float map
// so SetBool finds nothing among them and logs "is not found". Use SetByte / SetSize / SetFloat for those.
// (Log.Memory joins the byte map only when MEMORY_LOGGING_ENABLED is 1, so it is not in the list above)

The comment block above is the practical contract: no bool and no int parameter is registered anywhere under Engine/ or Applications/, so both of those write paths exist for parameters an application has to add first. The names are from Engine/Log/Logger.cpp, Engine/Engine/Engine.cpp, Engine/Memory/MemoryManager.cpp, Engine/Core/TaskSystem.cpp and Engine/Core/TaskStream.cpp.
