Parse

member of hbe::ConfigFile Engine/Config/ConfigFile.h private not callable by a caller the file format, defined here — first = splits, both sides trim, empty members drop

Signature

void Parse(const char* fileName);

Declared in Engine/Config/ConfigFile.h, defined in Engine/Config/ConfigFile.cpp as ConfigFile::Parse()

Function description

This is not an operation a caller performs; it is what a constructor does, and therefore the definition of the file format every ConfigFile reader depends on. Documenting a private member is justified by exactly that: the rules below are the contract of the whole class, and no public name states them.

The sequence, as implemented:

  1. Open a std::ifstream on the path. If it does not open: print [ConfigFile] Not Found: and the path to std::cout, and return — isValid stays false and keymap stays as it was.
  2. Otherwise print [ConfigFile] Open and the path, also to std::cout.
  3. Read lines until the stream reports end of file. For each line: an empty line is skipped; a line with no = is skipped; otherwise the part before the first = is the key and everything after it is the value.
  4. Trim both halves with StringUtil::Trim.
  5. If either the key or the value is empty, skip the pair. Otherwise assign it into the map, overwriting an earlier entry under the same key.
  6. Set isValid = true.

What that leaves unsaid, and what it therefore means for a file you write:

Line in the fileResultWhy
vsync = true"vsync" → "true"Both sides are trimmed, so spaces around the separator are free
path = C:\tools=bin"path" → "C:\tools=bin"Only the first = splits; the rest of the line is value
window = 1280x720 # borderless"window" → "1280x720 # borderless"No comment syntax exists; a trailing comment becomes part of the value
# a headingskippedNo = on the line — skipped by the separator rule, not by comment support
emptyValue =dropped entirelyAn empty value member fails the guard, so the key does not exist afterwards rather than holding ""
= onlyValuedropped entirelyAn empty key member fails the same guard
the same key twicethe last one winsAssignment into the map. Contrast ConfigSystem::Register, where the first registration wins and the second is refused
A setting that must be able to hold an empty value cannot be expressed. The empty-member guard drops key = before it reaches the map, so a file that clears a setting produces "no such key" at GetValue — indistinguishable from never mentioning it. There is no quoting, escaping or sentinel documented in the code that changes this, so a caller that needs empty-means-empty must reserve a literal such as <none> and interpret it itself.
Two behaviours that look like bugs and are not, and one that is only harmless by accident. The while (!ifs.eof()) test runs before the read, so the final iteration performs a failed getline; a failed extraction clears its string, which is then caught by the empty-line skip. The loop is harmless because that guard exists — remove the empty-line check and the last line would be parsed twice. And the whole map lives in the engine's default allocator via HUnorderedMap, so a config file's memory is engine-tracked rather than system-heap, which is the point of the HSTL types here.

Parameters

ParameterTypeRequirement
fileName const char* A complete file path — the single-argument constructor passes its whole path straight through, and the two-argument constructor passes the path it joined. The header's parameter name is misleading here: the definition in ConfigFile.cpp calls the same parameter filePath, which is what it holds (noted as a defect)

Return value

void. Success is reported through the object, not through the return: isValid says whether the file opened, and the size of keymap says whether anything parsed. The stream is a local, so the file is closed on return and no handle outlives the call.

Examples

Illustrative — Parse is private and cannot be called; the file below is what its rules accept, and the read that follows is how a caller consumes it. Nothing in the repository constructs a ConfigFile.

# config/engine.cfg — a heading line (skipped: no '=' on it)
max_particles = 20000
vsync         = false
render.scale = 1.35 prefer_wide
path = assets/models
= ignored, empty key
blankvalue =
max_particles = 40000

Four pairs survive that file: render.scale keeps the trailing word because nothing after the value is stripped, the two malformed lines are dropped by the empty-member guard, and the repeated max_particles is overwritten rather than refused. 

const hbe::ConfigFile settings("config/engine.cfg");

settings.IsValid();                              // true — the file opened
settings.keymap.size();                         // 4: max_particles, vsync, render.scale, path
settings.GetValue("max_particles")->c_str();     // "40000" — last assignment won
settings.GetValue("blankvalue").has_value();     // false — the empty-value guard dropped it
