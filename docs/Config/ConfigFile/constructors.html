ConfigFile (constructors)

member of hbe::ConfigFile Engine/Config/ConfigFile.h 2 overloads a path in, a parsed map out — loading is not a step you take, it is the construction

Signatures

One page for the name, because the two forms state one contract and differ only in how the path is assembled:

/// treat `path` as the complete file path
explicit ConfigFile(const char* path);

/// join `path` + separator + `fileName`, then parse that
ConfigFile(const char* path, const char* fileName);

Function description

Both set isValid to false in their initialiser list and then call Parse, which opens the file, parses it and — only on a successful open — sets the flag to true. So an object of this type is either fully loaded or marked invalid; there is no half-constructed state, no Load() to forget, and no failure to check before use beyond reading IsValid().

The two-argument form builds an HString from path, appends "/" unless the last character is already '/' or '\\', appends fileName, and hands the result to the same Parse. Note what that does not do: it never inspects whether path names a file rather than a directory, and it never resolves .., ~ or an absolute fileName — concatenation is all it is.

The single-argument form is explicit, so no const char* converts into a configuration file implicitly; the two-argument form has no single-argument equivalent to be explicit about and is not marked.

A missing file is not an error, an exception, or even a log line — it is a printed sentence and an invalid object. Parse reports [ConfigFile] Not Found: <path> on std::cout and returns, leaving IsValid() false and keymap empty. Nothing throws, no log level sees it, and a build with logging compiled out still prints it. A caller that must distinguish "no file yet, use defaults" from "file corrupt" has to print its own message: this class tells the two apart only by IsValid() versus keymap.empty(), and both are true-shaped for a corrupt-but-readable file.
Construction does file I/O, so it has the cost and the failure modes of file I/O. That is fine for a start-up load and wrong on a frame path; it also means a ConfigFile in a container that reallocates re-opens the file for every element it builds, since there is no copy-from-loaded form — copy and move are the compiler's, and copying one copies the whole map rather than aliasing a load.

Parameters

ParameterTypeRequirement
path const char* In the one-argument form, the whole file path. In the two-argument form, the directory part; a trailing '/' is optional and a trailing '\\' is accepted as well, which is the only cross-platform handling here
fileName const char* The file name appended to path. Not checked for a separator of its own, so "/sub/x.cfg" is accepted and becomes part of the joined path

Return value

Constructors have no return value, and the success or failure of the load is not one: check IsValid() on the object. A constructor cannot fail — a missing file produces a fully constructed, invalid object rather than no object.

Examples

Illustrative — no call site for this exists in the repository; nothing in Engine/ or Applications/ constructs a ConfigFile.

// Whole path in one string.
const hbe::ConfigFile engineSettings("config/engine.cfg");

// Directory and name kept separate, joined the same way:
const hbe::ConfigFile sameFile("config", "engine.cfg");
const hbe::ConfigFile alsoSame("config/", "engine.cfg");

if (!engineSettings.IsValid())
{
        // the file could not be opened; fall back to built-in defaults explicitly
}

// "IsValid" is not "has settings" — check the map you actually need:
if (engineSettings.IsValid() && engineSettings.keymap.empty())
{
        // readable file, nothing in it parsed
}

keymap is public, so the emptiness test above is legal without any accessor — see Class properties for what that costs in invariants.
