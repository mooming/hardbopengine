GetValue

member of hbe::ConfigFile Engine/Config/ConfigFile.h 2 overloads const noexcept one lookup, two answers: an optional that can say "absent", or a string that never can

Signatures

Both are a single hash lookup in keymap; the difference is entirely what absence becomes:

/// absence as data: an empty optional when the key is not there
TValue GetValue(const TString& key) const noexcept;

/// absence as the default you supplied
TString GetValue(const TString& key, const TString& defaultValue) const noexcept;

Function description

Both find key in the map and return a copy of what was stored — the string exactly as Parse left it: trimmed at both ends, split on the first =, and otherwise untouched. There is no conversion of any kind: "true", "1" and "0.16" come back as three strings, and parsing them into a bool, an int or a float is the caller's job.

Case matters. The key is an HString hashed as a string, so "MaxParticles" and "maxparticles" are two different lookups, one of which is a miss.

Parameters

ParameterTypeRequirement
key const TString& The name as it appears left of the = in the file. A string literal binds through std::string-style conversion, which allocates a temporary — worth hoisting out of a loop
defaultValue const TString& (second overload only) Returned when the key is absent. It is not written into the map, so a later lookup of the same key still misses and ForEach still will not see it

Return value

TypeWhat you get
TValue = std::optional<TString> The stored string, or an empty optional. This is the only member of the class that reports absence as a value rather than hiding it, so it is the right choice wherever "not set" must differ from "set to the empty-ish thing"
TString The stored string, or defaultValue. Indistinguishable from a file that literally sets the key to that same text — and, unlike ConfigSystem::GetInt, there is no odd sentinel like -1 pretending to be an answer
Both overloads are noexcept and both allocate. The value is returned by copy, and an HString copy goes through DefaultAllocator — so an allocation failure inside this call cannot be reported to you: it terminates the process instead of throwing. That is a deliberate engine stance, not an oversight, but it does mean the overload pair is unsuitable for the one situation where a caller wants to keep going after a failure, and the empty-optional form buys you no safety there.
The map is public; GetValue is not the only door. A direct keymap.find(key) answers the same question with one fewer copy of the string (Class properties). Read this function as the convenience form and the map as the one that tells you whether a key exists without copying its value out first.

Examples

Illustrative — no call site for this exists in the repository; the class is never instantiated in Engine/ or Applications/.

const hbe::ConfigFile settings("config/engine.cfg");   // max_particles = 20000
                                                        // vsync = false

// Absence matters: only apply an override when the file actually carries one.
if (const auto particles = settings.GetValue("max_particles"); particles.has_value())
{
        const auto count = std::stoi(particles->c_str());
        // … and std::stoi throws on junk the file happily contains, e.g. "20k" …
}

// Absence does not matter: take the default and move on.
const auto present = settings.GetValue("vsync", "true");   // "false" — the file's value wins
const auto layout = settings.GetValue("ui.layout", "default");   // "default" — the key is absent

Note what the last two lines have in common with the first: no member of this class converts "false" to false. A file-driven setting needs a comparison or a parse written by the subsystem that reads it, and that is precisely the glue ConfigParam does not provide either — the two halves of this module are not joined (class description).
