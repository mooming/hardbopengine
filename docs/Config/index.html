Config

namespace hbe namespace hbe::Config Engine/Config 5 headers, 4 sources — compile-time defines, compile-time sizes, and a key-value parameter database you can change while the process runs

Module description

Config answers the same question at three different times. Compile time: BuildConfig.h decides what is built at all — platform, logging, memory verification, profiling, coordinate handedness, Vulkan availability. Load time: EngineConfig.h holds the constexpr sizes and caps that other modules size their buffers from. Runtime: ConfigSystem stores named parameters an application or a debug menu can change while the process runs, and ConfigParam<T> is the handle a subsystem holds to one of them.

The three do not meet in the way the split suggests. Config::EngineLogLevel is computed from a BuildConfig.h define and becomes the default of a runtime parameter, which is the only wire between compile-time and runtime in this module. There is no wire from files to either: ConfigFile is a separate, unrelated facility that ConfigSystem never consults and that nothing in the engine instantiates.

Where a value in this module meets a value from another module, the other module owns the meaning: log level numbers are ELogLevel, allocation alignment is consumed by Memory, the assert family that __DEBUG__ gates lives in Core, and the interning that makes a parameter key cheap is String.

Build configuration

How the engine is configured and generated lives in docs/BuildSystem.md — including the rule that generated CMakeLists.txt files are never edited by hand. How to build one target quickly lives in docs/HelperScript.md. The flags are repeated here because they are the part a reader of the API page reaches for: 

./build.sh <target> [-dev] [-debug] [-release] [-clean] [-test]

# build VulkanExample in all three configurations, cleaning first
./build.sh Applications/VulkanExample -dev -debug -release -clean

Dev is the default configuration. -test reconfigures with -D__TEST__ -D__UNIT_TEST__ so the unit-test sources compile at all; without it EngineTest builds green while testing nothing. build.sh only builds — it never runs a test binary. To run the suite, see docs/RunningTests.md.

The one build flag that changes this module's own behaviour is __DEBUG__. The top-level CMakeLists.txt puts -D__DEBUG__ on the Debug flag line and defines Dev as Debug plus -O1, so Debug and Dev have it and Release does not. That is what turns Assert into a real check and what enables the thread-affinity assertion inside ConfigParam::Get. FatalAssert is outside that gate and is live in all three configurations — see BuildConfig, whose header comment on this point is stale and contradicts CMakeLists.txt.

Coverage

GapDetail
Nothing in this module reads a file ConfigFile and ConfigSystem are not connected, and no code under Engine/ or Applications/ instantiates ConfigFile at all. A parameter's initial value comes from its constructor and from no disk file — the page for that class states the evidence
Five of the fifteen constants have no reader StaticStringBufferSize, LogMemoryBlockSize, LogNumMemoryBlocks, MaxConcurrentTasks and — with PROFILE_ENABLED at its default 0 — DebugTimeOutMultiplier are declared and unread in a default build. Their purposes beyond the header's comment grouping are not asserted anywhere in this reference
MAX_NUM_TASK_STREAMS enforces nothing Defined as 64 in BuildConfig.h, read by no file in the tree, so this reference records the header comment and not a limit. See BuildConfig: Class properties
GetMaxSystemMemoryTarget is a declaration only No definition in EngineConfig.cpp, no call site, so what it would return is unknown and undocumented — see the function's page
No bool and no int parameter exists yet A default build registers eight parameters: four uint8_t, three size_t, one float — nine and five uint8_t once MEMORY_LOGGING_ENABLED adds Log.Memory. So GetBool and GetInt and their writers are documented against parameters an application has to add, and their pages say so rather than implying live keys
Thread-safety and lifetime rules that span two classes A parameter must outlive the registry that holds references to it, and registration is unsynchronised. Those are stated on ConfigSystem's destructor and Register, not repeated here
Related defect, outside this page The configuration table in README.md still prints __MEMORY_VERIFICATION__, __MEMORY_LOGGING__, __FORCE_USE_SYSTEM_MALLOC__, __MEMORY_DANGLING_POINTER_CHECK__ and __RIGHT_HANDED__. No such define exists in BuildConfig.h; the live names are on the BuildConfig page
