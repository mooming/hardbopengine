Set

member of hbe::ConfigParam Engine/Config/ConfigParam.h noexcept change the stored value — nothing is notified, validated, saved, or re-applied

Signature

void Set(const T& inValue) noexcept;

Function description

Stores inValue into value: an atomic store when IsAtomic is true, a plain assignment otherwise. No validation of any kind — a log level of 9, a negative size, a threshold of 0.0f are all accepted and stored exactly as given, because the class knows a type and not a meaning.

Before the store, the same debug assertion as Get: under __DEBUG__, a non-atomic parameter asserts that the calling thread is the one recorded at construction. This is the path a name-based write goes through — ConfigSystem::SetByte and its siblings call exactly this function via the setter closure Register installed — so writing a parameter from a console thread is subject to the same rule as writing it directly.

After the store, nothing happens. No callback, no dirty flag, no event: the class holds a value and has no knowledge of who consumed it.

A write only reaches a consumer that reads again. The engine shows both outcomes. The task stream re-reads its threshold every iteration (deltaTime > thresholdDuration.Get()), so a write lands on the next frame; the task registry, by contrast, receives its sizes as arguments at Initialize and never consults the parameters again, so writing Task.RegistryMaxRecords at runtime changes only what a future initialisation would use. Before you expose a setting in a debug menu, find the read — if there is no repeated read, the setting is start-up-only no matter how this function behaves.
Nothing persists. A value written here is gone when the process ends; no file, no registry, no environment is updated, and no code reads configuration off disk into these objects (ConfigFile is a separate, unused facility). If a change has to survive a restart, that is a feature to build, not one to expect.

Parameters

ParameterTypeRequirement
inValue const T& The new value, in the parameter's own type — this is why SetByte cannot write a float parameter and why a level must arrive as uint8_t rather than as ELogLevel. Taken by const reference and copied into the storage; for an atomic parameter the reference is read once by the store

Return value

void, and there is no way to ask afterwards whether the write took effect. Confirm with Get if it matters — that read is a copy, so it reports what is stored rather than what you asked for.

Examples

Illustrative — no call site for this exists in the repository; the engine's parameters are only ever written through ConfigSystem, and no live code does that either.

static hbe::TAtomicConfigParam<uint8_t> verbose("Debug.VerbosePhysics",
                                               "1 = log every contact pair. Costs the frame rate",
                                               0);

verbose.Set(1);

if (verbose.Get() != 0)
{
        // safe: the same thread wrote it, and an atomic parameter may be written from anywhere anyway
}

The equivalent through the registry, which is the same store seen by name:

hbe::ConfigSystem::Get().SetByte("Debug.VerbosePhysics", 1);

SetByte documents what happens when the name is wrong; the difference between the two forms is only the lookup, since both end in this function.
