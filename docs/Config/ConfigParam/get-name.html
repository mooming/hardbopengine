GetName

member of hbe::ConfigParam Engine/Config/ConfigParam.h const, not noexcept the key this parameter is reachable by — and the first thing to vanish when descriptions are compiled out

Signature

[[nodiscard]] StaticString GetName() const;

Function description

Returns the interned name given to the constructor. With ENGINE_PARAM_DESC_ENABLED — the default, 1 in BuildConfig.h — the body is return name;, a copy of a StaticString, which is the copy of one pointer: an interned identity, not a character buffer.

With that macro at 0 the name member is not declared, and the body becomes return StaticString(); — a default-constructed one, which the string table defines as the interned string "None" rather than an empty or null identity (Engine/String/StaticString.cpp). The function still compiles and still returns, and the consequence is not cosmetic: Register calls this to pick its key, so within one map every parameter ends up on the same None key and all but the first are refused as duplicates.

It is const but not noexcept, because the returning type is constructed by value; the enabled branch does nothing that can throw, but the signature does not promise it.

Parameters

None.

Return value

TypeWhat you get
StaticString The key, e.g. "Log.Level" — or the interned string "None" when ENGINE_PARAM_DESC_ENABLED is 0, because that is what a default-constructed StaticString holds. IsNull() does not report that case — the "None" entry is a real interned identity, so its pointer is not null — which means the only reliable test for "this parameter has no name" is comparing the text against "None"

Examples

The engine's only caller is the registry itself, taking the key it will store the entry under. The snippet below is Register's first line, which every registration in a running build passes through. 

auto name = param.GetName().GetID();

if (unlikely(intParams.find(name) != intParams.end()))
{
        // duplicate: FatalError line, nothing installed
}

From Engine/Config/ConfigSystem.cpp, condensed from the Register overload for int parameters

Illustrative — using the name from outside the registry, e.g. a debug UI that builds its own labels.

// Owned by this subsystem:
static hbe::TAtomicConfigParam<float> fadeSeconds("Audio.FadeSeconds", "Cross-fade length in seconds", 0.25f);

// The label and the value come from the same object, so they cannot disagree:
label.SetText(fadeSeconds.GetName());
slider.SetValue(fadeSeconds.Get());

Note that this example is non-atomic on purpose to make the point about locality: a name you can read is a name you can hand to GetFloat by key.
