Function description

The thirteen scalar overloads are one line each in BufferInputStream.cpp: a call to the scalar Get with the argument and a type-appropriate default ('\0' for char, 0 for the integers, 0.0 for the floats), then return *this;. So the read either fills the argument from the block or fills it with that constant and raises the count; there is no third outcome and no way for the argument to be left uninitialised.

Strings are the asymmetric ones. operator>>(StaticString&) reads the size_t length prefix that operator<< wrote. A zero length assigns a function-local interned empty string and returns. Otherwise it reserves in a local HInlineString<256> and reads the characters one at a time through the scalar Get, then asserts the collected size equals the declared length and assigns str = StaticString(tmpStr.c_str()) — a fresh interning, not a recovered handle. Interning identity does not survive a round trip through a buffer, only the characters do.

Reading a string one character at a time is a consequence of alignment rather than of laziness: each character is an aligned 1-byte read at the running cursor, so the reader stays on the same offset arithmetic as the writer for every element it consumes.

The array and container templates forward to the two bulk Get forms, so the prefix semantics, the container clearing and the static_assert on element type are described there.

The container overload cannot be selected by >>. Its T appears only in the default argument of class TContainer = TVector<T>, so it is not deducible from the operand and stream >> someVector; fails to bind. Reachable only as stream.operator>><T>(container), which no engine code does — the loaders read a count and then loop over scalars instead. The C-array overload immediately above has no such problem, since T and N both deduce from T(&array)[N].
operator>>(const HString&) reads nothing. Its body is return *this; — no Get call, no cursor movement, no error count. It is a declared, defined, chainable no-op. It cannot fill its argument in any case, because the parameter is const, so the overload as written has no reachable effect: an image containing a string passed to this overload leaves the string untouched and the cursor unmoved, and everything after it in the chain desynchronises against the image. The StaticString overload immediately above is the one that works, and the writer has no matching HString write either — it converts every string type with c_str() and writes bytes.
A stored length above 256 characters leaves the inline buffer behind. The local collection buffer is HInlineString<256> with reserve(length) called on it, so a longer stored string depends on that class growing off its inline storage, and the value handed to StaticString comes from c_str() afterwards. The Assert(tmpStr.size() == length) that follows checks the count, not the capacity behaviour. Long strings are therefore exercised by a different path than short ones, and the engine's own test collection does not cover the long case.
Every overload returns *this, including the ones that read nothing. Chains always run to completion. That is what makes a single HasError() at the end of a chain the load-bearing check — no intermediate return value can tell you a field was missing.

Examples

A chain that matches the writer in operator<<, and the single check that makes the result trustworthy:

BufferInputStream is(buffer);
uint32_t version = 0;
size_t count = 0;
StaticString name;
is >> version >> count >> name;
returnIfB(is.HasError());
while (!is.IsDone()) {
	PoolConfig config;
	is >> config.a >> config.b;
}

Shape used by the deserialisation paths in Engine/Memory/

The loop condition is IsDone rather than a count, and it relies on alignment and the cursor. A truncated final record is caught by IsValidIndex, which compares the end offset of the proposed read against GetSize() — behaviour pinned by the "Tail Shorter Than One Element" and "Bulk Read Past The End" testlets, both of which fail against the guard as it stood before this cycle.
