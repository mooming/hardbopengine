IsValidIndex

member of hbe::BufferInputStream Engine/Resource/BufferInputStream.h private const noexcept the bounds test every read relies on, testing the end of the read

Signature

[[nodiscard]] bool IsValidIndex(size_t index) const noexcept
{
	return index <= buffer.GetSize();
}

Quoted from Engine/Resource/BufferInputStream.h. The comparison is against index, the offset the proposed read would end at.

Function description

One comparison, and it is the only bounds decision any read makes. Three call sites in Get use it identically:

const size_t startIndex = ((cursor + tSize - 1) / tSize) * tSize;
const size_t newIndex = startIndex + tSize;      // or startIndex + tSize * length

if (unlikely(!IsValidIndex(newIndex)))
{
	++errorCount;
	value = defaultValue;
	return;
}

From Engine/Resource/BufferInputStream.h, the scalar form; the two bulk forms test the same way

Why <= rather than <: a read whose end offset equals the buffer size consumed the last byte exactly and is legitimate. Rejecting it would refuse the final element of every image whose length is an exact multiple of the element size.

This function previously compared cursor instead of index — it is quoted verbatim on the previous revision of this page — and the parameter was never read. That answered "have we already run out" where three call sites needed "does this fit", so a read starting inside a block and ending outside it was honoured: the scalar forms read up to one element past the tail, and the bulk forms read length elements where length came from the image. It was corrected during the Resource documentation cycle, which is how the defect was found — nothing else in the tree exercises it.

Three testlets in BufferInputStreamTest now pin the behaviour, and each of them fails against the previous comparison:

TestletSetupWhat it asserts
"Tail Shorter Than One Element"a 6-byte buffer, two int reads The 4-byte read at offset 0 is honoured; the one ending at byte 8 is refused, and the count is exactly 1
"Bulk Read Past The End"a 64-byte buffer whose prefix declares 20 elements Refused, and every element of the destination array still holds its sentinel — the read did not touch it
"Refused Read Keeps The Container"a 4-byte buffer, too small for the size_t prefix alone Refused, and the caller's container keeps its previous contents — see Get

Parameters

ParameterTypeContract
indexsize_t The offset one past the last byte the read would touch, already alignment-rounded by the caller. Compared against the buffer size

Return value

TypeWhat you get
bool true when the read fits inside the block, including the case where it ends exactly at the end. Says nothing about the current cursor position, and nothing about whether the buffer holds bytes at all — see the note below

Notes

A buffer that claims a size and owns no bytes still passes this test. GenerateDummyBuffer produces exactly that — size == max, pointer null — as a measuring device for the writer. A reader pointed at such a buffer passes every bounds test and then dereferences a null base, because the guard reasons about sizes only. The test for that condition is GetData() == nullptr, and it belongs to the caller.
The output stream owns the same helper and still compares cursor. Nothing calls it there — Put carries its own newIndex > size test — so it is dead code rather than a second defect, but the two helpers no longer have identical bodies: BufferOutputStream: IsValidIndex.
