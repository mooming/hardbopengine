IsValidIndex

member of hbe::BufferInputStream Engine/Resource/BufferInputStream.h private const noexcept argument ignored the bounds test every read relies on, testing the wrong offset

Signature

[[nodiscard]] bool IsValidIndex(size_t index) const noexcept
{
	return cursor < buffer.GetSize();
}

Quoted verbatim from Engine/Resource/BufferInputStream.h. The parameter index does not appear in the body.

Function description

Three call sites, all inside Get, all of the same shape:

const size_t startIndex = ((cursor + tSize - 1) / tSize) * tSize;
const size_t newIndex = startIndex + tSize;      // or startIndex + tSize * length

if (unlikely(!IsValidIndex(newIndex)))
{
	++errorCount;
	value = defaultValue;
	return;
}

From Engine/Resource/BufferInputStream.h, the scalar form; the two bulk forms are the same test

The argument is the offset the read would end at, and the body never looks at it. What is actually tested is whether the current cursor lies inside the block. So the answer to "does this read fit" is derived from a different question — "have we already run out" — and any read whose start is inside while its end is outside passes the test and proceeds.

For the scalar form the overhang is bounded: the read is sizeof(T) bytes from an offset at most one alignment unit past the old cursor, so a short tail of the block can be read past by less than the element size. The bulk forms are not bounded that way. There, newIndex is startIndex + tSize * length and length came from the image itself, so a truncated or corrupt length makes the copy run past the end of the block by an amount the caller supplied, and Get then copies that many elements into the caller supplied container or array.

The correct comparison is the one the writer uses on its own path:newIndex > size, evaluated against GetSize(), as documented on Put. That is also what the writer's identical helper would have to become to be usable — it is never called there, which is the only reason the writer does not share this behaviour.

Consequence, stated plainly. A read is refused only when the cursor has already left the block. A read that starts inside the block and ends outside it is not refused: the scalar forms read up to one element past the tail, and the bulk forms read length elements, where length is data from the image. The guard is the engine's only bounds check on this path, so a malformed buffer is not detected here. Nothing in Engine/Resource/ validates a length prefix against the remaining size before copying.
This page documents behaviour, it does not approve of it. The engine's comment ban means every such finding lives here rather than in the source, which is also the place a reader of the header would look for it. The fix is a two-character change in the body — compare index rather than cursor — and would turn three call sites from"are we still inside" into "does this fit".

Notes

It is marked [[nodiscard]], so the compiler enforces that the result is used; no diagnostic exists for the weaker problem that the result answers a different question. A unit test for it would need a buffer whose tail is shorter than one element — a case the existing BufferInputStreamTest collection does not cover.
