BufferUtil

Engine/Resource/BufferUtil.h namespace hbe::BufferUtil free functions, one template using namespace BufferTypes; the six ways a Buffer comes into existence

What every function here does

Buffer stores a size, a pointer and the closure that frees them; it allocates nothing itself. Every function in this namespace is therefore the same shape: build a TGenerateBuffer lambda that knows how to obtain bytes, hand it to a Buffer constructor, and — where the bytes need freeing — follow with SetReleaser. The header runs using namespace BufferTypes; inside the namespace, which is why these signatures say TBufferData and TSize unqualified.

Two of them matter as a pair more than as functions. A buffer whose pointer is null and whose size is a lie — GenerateDummyBuffer() — is what lets BufferOutputStream run over a serialisation and count the bytes without writing any; and GetWriteOnlyFileBuffer(path, size) takes exactly that count to create and map a file of the right length. MemoryManager::SaveMultiPoolConfigs uses them in that order: probe, take the writer's cursor, create, write for real.

Failure is reported twice and neither is a return code: a message is logged through a Logger obtained as a function-local static, and the returned buffer comes back empty — size zero, pointer null. So the caller's test is GetData() == nullptr, and the engine's own callers use returnIfB against exactly that.

Functions

GenerateDummyBuffer

[[nodiscard]] Buffer GenerateDummyBuffer(size_t size = std::numeric_limits<size_t>::max()) noexcept;

The generator captures size and writes outSize = size; outData = nullptr;. Nothing else: no releaser is installed, because there is nothing to release. The result is a buffer that claims a size and owns no bytes, which is the measuring device described above — Put sees a null base, advances its cursor when the write would fit the claimed size, and refuses when it would not.

The default size is size_t max, and that is load-bearing. With it, a probe of any plausible image always "fits" and the writer's cursor ends as the true image size. Passing a smaller size turns the same call into an upper-bound test: writes past it raise the writer's error count instead of advancing the cursor.

GenerateFileBuffer

[[nodiscard]] Buffer GenerateFileBuffer(StaticString path, OS::FileOpenMode openMode,
                                                OS::ProtectionMode protection, size_t size = 0);

The one real implementation; the four Get…FileBuffer functions below are argument presets for it. Its generator runs the whole sequence, and any step that fails returns with the buffer left empty after logging:

StepCallOn failure
OpenOpen(fh, path, openMode) in OSAL OutError "Failed to open", buffer stays empty
Resize, only when size != 0Truncate(fh, fileSize) OutWarning "Failed to resize", buffer stays empty
Reject nothing-to-mapthe resulting file size OutWarning "Nothing to map. File size is zero"
MapMapMemory(fh, fileSize, protection, 0) OutError "Failed to map", buffer stays empty

Only after a mapping exists does the function take the file handle's raw data out of the local FileHandle, invalidate the local so it stops owning, and install a releaser capturing the raw handle. That releaser, run by ~Buffer: re-arms a FileHandle from the captured data, asserts the size is non-zero, calls MapSync with the sync mode set, then UnmapMemory, then Close. Writes through the mapping are therefore flushed before the mapping is dropped and the descriptor closed, in that order, and the buffer needs no further ceremony from its owner.

The early return skips the releaser installation, and that is intended — but it means an empty buffer is indistinguishable from a deliberate no-releaser buffer. On every failure path the function returns Buffer(generator) with no releaser installed and GetData() null. The engine's own file-mapping path also builds a buffer in that state deliberately for one statement before installing the releaser, so the gap recorded on Buffer about a mapped block with no releaser is reachable here too if the process exits between those two statements.
if (fileSize <= 0) on a file size. The size is unsigned, so this is a test for zero. An empty file is refused with a warning rather than mapped, which is what keeps a zero-length mapping from reaching Buffer at all.

GetFileBuffer

[[nodiscard]] Buffer GetFileBuffer(StaticString path);

GenerateFileBuffer(path, read-write, readable + writable) with no size, so an existing file is mapped for reading and writing at its current length and resized by nobody. This is the load path: the image is read through BufferInputStream, and the writable mapping is what makes the same buffer usable for in-place editing.

GetReadOnlyFileBuffer

[[nodiscard]] Buffer GetReadOnlyFileBuffer(StaticString path);

GenerateFileBuffer(path, read-write, readable). The name promises read-only, and the mapping keeps that promise — the protection is readable only — but the file itself is opened read-write.

The name describes the mapping, not the open mode. openMode.SetReadWrite() is what this function passes; only protection is restricted. So the process holds a writable descriptor on a file it has asked to see read-only, and the read-only guarantee is the mapping's protection fault rather than an OS-level denial. Writing through the pointer is undefined behaviour, not a graceful error; nothing in the engine writes through a read-only mapping today, so the distinction has not been tested.

GetWriteOnlyFileBuffer

[[nodiscard]] Buffer GetWriteOnlyFileBuffer(StaticString path, size_t size);

Opens read-write, then either SetTruncate() when Exist(path) is true or SetCreate() when it is not, with writable-only protection and the given size — which GenerateFileBuffer turns into a Truncate. The result is a file of exactly size bytes, mapped for writing, and released with a sync when the buffer dies.

The size is a parameter rather than a discovery, and that is the pairing that makes the probing trick work: measure the image with GenerateDummyBuffer() and GetCursor(), then create a file that size. Too small a size and the writer's later writes are refused — counted, not fatal.

Existing content is destroyed without a trace, and the mapping cannot be read. A file that exists is truncated; protection is writable only, so reading the mapped bytes back is not permitted by the mapping. A caller that needs to inspect what it wrote must release the buffer and open the file again through GetFileBuffer or GetReadOnlyFileBuffer.

GetMemoryBuffer

template <typename T>
[[nodiscard]] Buffer GetMemoryBuffer(TSize numElements, const T& defaultValue);

Defined in the header, and the only function here that allocates rather than maps. The generator takes MemoryManager::GetInstance() by reference, computes numElements * sizeof(T), and stores a block from mmgr.NewArray<T>(numElements, defaultValue). The releaser divides the size back by sizeof(T), asserts the division was exact, and calls mmgr.DeleteArray<T>(ptr, numElements).

The Assert on exact division is what makes the closure pair safe: the TReleaseBuffer signature carries a byte size and a pointer and nothing else, so a releaser that needs an element count has to recover it, and this is the check that the recovery was lossless. MemoryManager is the allocator on both sides, so a memory buffer returns its bytes to whichever pool served them.

defaultValue is a value-initialisation, not a memset. It is handed to NewArray<T>, so T's own construction runs per element. For a trivially copyable T that is the same cost as a fill; for anything with a constructor it is a loop of constructor calls, and the caller is naming a value of T rather than a byte pattern.
