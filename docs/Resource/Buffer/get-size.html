GetSize

member of hbe::Buffer Engine/Resource/Buffer.h const noexcept [[nodiscard]] the byte count of the block — not an element count, and not a capacity

Signature

[[nodiscard]] auto GetSize() const noexcept;

Declared with a deduced return type, over the member TSize size;, so the type it names is TSize — size_t — returned by value.

Function description

A field read: return size;, inline in the header. No computation, no allocation, safe on a buffer holding nothing and on one that was moved out of.

It is a byte count, so element arithmetic is explicit and lives in TranslateSizeAs<T>(). It is also the only bound any of this module's readers has: the cursor arithmetic in the buffer streams compares against this value and nowhere else.

Parameters

None.

Return value

TypeWhat you get
TSize (size_t) Bytes available at GetData(). 0 for a default-constructed, failed or moved-from buffer. Unsigned, so a subtraction against a cursor that is ahead of the end wraps rather than going negative. [[nodiscard]], so discarding the call is a compile error

Examples

It is the bound every reader in this module tests. From Engine/Resource/BufferInputStream.h, where the whole "have we finished" question is one comparison against it: 

[[nodiscard]] bool IsDone() const noexcept { return cursor >= buffer.GetSize(); }
[[nodiscard]] bool IsValidIndex(size_t index) const noexcept { return cursor < buffer.GetSize(); }

From Engine/Resource/BufferInputStream.h

A buffer used the other way — as an output to measure against — is how a size is discovered before anything is allocated for it. MemoryManager::SaveMultiPoolConfigs serialises into a buffer whose GetData() is null and takes the resulting byte count from the writer's cursor, then opens a file of that size.

GetSize() > 0 is not a validity test. A buffer's pointer and size are written by whatever generator built it, and nothing cross-checks them: BufferUtil::GenerateDummyBuffer produces size = std::numeric_limits<size_t>::max() with data == nullptr, deliberately, so a writer can be run over it to count bytes. Ask GetData() for null if you need to know whether there are bytes to touch.
It is a size, never a capacity. TResizeBuffer exists as a type for a policy that proposes a larger capacity, but no code uses it and Buffer stores no spare room, so writing past GetSize() is not "using capacity" — it is a bounds violation that the streams record as an error count and that raw writes commit silently.
