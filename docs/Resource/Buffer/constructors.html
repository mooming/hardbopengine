Buffer

member of hbe::Buffer Engine/Resource/Buffer.h 4 overloads choose who frees the bytes — the two-argument form names somebody, the others name nobody

Signatures

Buffer();
Buffer(Buffer&& rhs) noexcept;
explicit Buffer(const TGenerateBuffer& genFunc);
Buffer(const TGenerateBuffer& genFunc, const TReleaseBuffer& releaseFunc);

Nothing else is declared, and the absences are load-bearing. There is no copy constructor: declaring the move constructor removes it. There is no assignment operator in either direction: the declared destructor removes the move assignment operator and the declared move constructor leaves the copy assignment operator deleted. A buffer is created empty, created from a generator, or moved into a new object — never assigned.

Function description

The two generator forms initialise size to 0 and data to nullptr, then call genFunc(size, data) on that fresh pair. The generator returns void and reports through its arguments, so the arguments arriving pre-cleared are what make failure detectable: a generator that opens nothing and writes nothing leaves an empty buffer whose GetData() is null, and that is how every caller in the engine tests for a buffer that was never built. Nothing is deferred — the block exists, or does not, by the time the constructor returns.

The one-argument form stops there, so the block it produces has no releaser and will not be freed by this object. That is the documented use of it: a caller that keeps ownership elsewhere hands over a view. The two-argument form assigns the releaser afterwards, which is also the order BufferUtil::GenerateFileBuffer uses when it cannot know whether a releaser is needed until it sees whether the mapping succeeded.

The move constructor copies size and data, moves the releaser, then writes 0, nullptr and an empty function back into the source. A moved-from buffer is therefore not "valid but unspecified" — it is exactly the default-constructed state, and destroying it is a no-op rather than a double free.

Parameters

ParameterTypeRequirement
genFunc const TGenerateBuffer& Callable as void(TSize&, TBufferData&), and not empty — an empty std::function called here throws std::bad_function_call out of a constructor that is not noexcept. It is called exactly once, here, and is never stored: the closure and its captures may die as soon as this returns
releaseFunc const TReleaseBuffer& Callable as void(TSize, TBufferData). Copied into the buffer's own std::function, which is what gets called at destruction — so anything it captures by reference must outlive the buffer, not just this constructor
rhs Buffer&& The buffer to empty into this one. Left a default-constructed buffer; no requirement beyond being alive, since it is written rather than read

The default constructor takes nothing.

Return value

Constructors have no return value, and these report nothing: not whether the generator succeeded, and not whether a releaser was installed. Both are read back from the object — GetData() for the first, and the silence or noise of the destructor for the second.

Examples

Allocating and freeing belong to one pair of closures, which is exactly what the two-argument form is for. This one is real — a memory-backed buffer of T, from Engine/Resource/BufferUtil.h: 

auto& mmgr = MemoryManager::GetInstance();
auto generator = [&mmgr, numElements, defaultValue](TSize& outSize, TBufferData& outData)
{
        outSize = numElements * sizeof(T);
        auto ptr = mmgr.NewArray<T>(numElements, defaultValue);
        outData = reinterpret_cast<TBufferData>(ptr);
};

auto releaser = [&mmgr](TSize size, TBufferData data)
{
        const TSize numElements = size / sizeof(T);
        Assert((numElements * sizeof(T)) == size);

        auto ptr = reinterpret_cast<T*>(data);
        mmgr.DeleteArray<T>(ptr, numElements);
};

return Buffer(generator, releaser);

From Engine/Resource/BufferUtil.h, in BufferUtil::GetMemoryBuffer

The same releaser needs an argument the buffer already carries — the byte count — which is why DeleteArray can be called correctly without the closure remembering anything but the allocator. The releaser also checks the division round-trips, because a size that is not a whole number of T would otherwise free the wrong extent.

The one-argument form, in real use, is a buffer that is never meant to own anything — a size probe, from Engine/Resource/BufferUtil.cpp: 

auto generator = [size](TSize& outSize, TBufferData& outData)
{
        outSize = size;
        outData = nullptr;
};

return Buffer(generator);

From Engine/Resource/BufferUtil.cpp, in BufferUtil::GenerateDummyBuffer

A byte count and a null pointer: GetSize() answers a huge number while GetData() answers null, which is the combination a writer treats as "count the bytes, write nothing". MemoryManager::SaveMultiPoolConfigs exploits precisely that to measure a serialisation before allocating a file for it.

A generator that allocated, combined with no releaser, is a leak the program only mentions once. The destructor logs a warning naming the class and the pointer and returns without freeing. Nothing asserts, no error is returned, and in a Release build the pointer fields are not even cleared, so the buffer looks intact after it is gone. Use the two-argument form for anything that really allocated, or install the releaser with SetReleaser — but note that the window between the constructor and that call is exactly the window an exception can escape through.
The one-argument generator form is explicit; the two-argument form is not. So Buffer b = someGenerator; is rejected while a two-argument conversion sequence is permitted. The asymmetry is visible in the header and has no behavioural consequence for a call that names the type, which is what every call site in the repository does.
