Module Index / Resource / Buffer / destructor

~Buffer

member of hbe::Buffer Engine/Resource/Buffer.h Engine/Resource/Buffer.cpp runs the releaser this buffer was built with, or says out loud that it has none

Signature

~Buffer();

Declared without noexcept, and implicitly noexcept all the same — every member is a size_t, a pointer and a std::function, none of whose destructors may throw. See the hazard below for what that costs when the releaser throws.

Function description

The body in Buffer.cpp has three exits, in this order:

  1. returnIf(data == nullptr) — a buffer holding no block exits immediately, releaser or not. This is the exit a default-constructed buffer, a generator that failed, and every moved-from buffer all take, which is what makes a move safe to destroy.
  2. Data with no releaser: a warning is logged through Logger under the name GetClassName(), carrying the function name __func__ resolves to at that point — ~Buffer — and the address being abandoned, and then the destructor returns. Nothing is freed.
  3. Data with a releaser: releaser(size, data) runs, and the buffer's job is done. Whatever that call does — return an array to a MemoryManager pool, MapSync and unmap a file view and close the handle — is the closure's contract, not this class's.

After either of the last two paths, a __DEBUG__ build additionally stores 0 into size and nullptr into data. Reading a destroyed buffer's accessors therefore looks clean in Debug and returns the old, dead values in every other configuration — a difference that only ever matters when something was already reading a destroyed object.

Parameters

None.

Return value

void. Whether the release succeeded is not reportable from a destructor, and the releaser's own signature returns void — so a closure that fails to unmap or to close is silent unless it logs or asserts itself.

Examples

Releasing is a scope event, and the engine's own test for this class is written that way on purpose: the buffer is built inside a block so that the releaser runs while the test can still observe it. From Engine/Resource/Buffer.cpp: 

{
        Buffer buffer(gen, rel);

        if (buffer.GetSize() != BufferSize)
        {
                ls << "Invalid buffer size = " << buffer.GetSize() << lferr;
        }

        if (buffer.GetData() == nullptr)
        {
                ls << "Invalid buffer data = " << (void*) buffer.GetData() << lferr;
        }
}       // ~Buffer runs here and calls rel(BufferSize, data)

From Engine/Resource/Buffer.cpp, in the BufferTest "Generation & Release" case

The rel closure passed here checks the byte count and the pointer it received and reports a mismatch, which is the only way a caller can verify a release at all: the arguments the destructor hands over are the whole story.

A throwing releaser ends the process. The call sits in an implicitly noexcept destructor, so an exception escaping it reaches std::terminate rather than propagating to the scope that ended. A release closure that can fail — a MapSync or a close that may error — has to handle it inside the closure, as the engine's own file releaser does, instead of letting it out.
The warning for a data-holding buffer with no releaser is the only diagnostic this class has. It names the class and the abandoned address and does not stop anything, so in a long run it is easy to lose. If a buffer you constructed that way is not meant to own its block, make that explicit by keeping the block alive somewhere obvious; if it is meant to, this warning is the leak notification — see the constructors.
