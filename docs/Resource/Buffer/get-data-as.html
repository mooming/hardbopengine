GetDataAs

member of hbe::Buffer Engine/Resource/Buffer.h 2 overloads template<typename T> the same address, cast to the element type you assert the block holds

Signatures

Both are defined in the header as return reinterpret_cast<T*>(data);:

template<typename T>
T* GetDataAs();

template<typename T>
const T* GetDataAs() const;

Function description

Hands the stored uint8_t* to reinterpret_cast and returns the result. No null check, no size check, no alignment check, no record of what T was used. Subsequent arithmetic on the result is in units of sizeof(T), so element i is GetDataAs<T>()[i] — and the bound on i is the element count you have to derive yourself from GetSize(), which is what TranslateSizeAs<T>() exists for.

The pair is selected by the const-ness of the buffer, and the const overload imposes const T* through its return type. A const Buffer& therefore cannot be talked into a mutable typed view, even though the cast written inside it names T*.

Parameters

ParameterTypeRequirement
T template parameter, typename The element type the block is asserted to contain. Nothing verifies the assertion — not the byte count, not the alignment, not whether a generator of that type ever built the buffer. A wrong T is silent misinterpretation of bytes, not a compile error
(function parameters) — None. Neither overload takes an argument and neither takes an index

Return value

TypeWhat you get
T* / const T* GetData() reinterpreted, so the same address and the same lifetime: good until the buffer is destroyed or moved out of. May be nullptr. Neither overload is [[nodiscard]], so a call whose result is thrown away compiles without a warning

Examples

Illustrative — no call site for this exists in the repository. Grepping Engine/ and Applications/ finds no use of either overload; the code that consumes buffers goes through the streams instead, and the code that produces them casts by hand with reinterpret_cast. The types below are real: BufferUtil::GetMemoryBuffer is the factory that makes such a buffer, in Engine/Resource/BufferUtil.h.

auto buffer = BufferUtil::GetMemoryBuffer<int>(count, -1);

auto* values = buffer.GetDataAs<int>();        // int*, same address as GetData()
const auto elementCount = buffer.TranslateSizeAs<int>();

for (size_t i = 0; i < elementCount; ++i)
{
        values[i] = 0;                  // no bounds check on i; elementCount is the only bound
}
Neither overload is [[nodiscard]], and this module does not check the cast it performs. Two consequences. A statement-sized call such as buffer.GetDataAs<int>(); compiles and does nothing, with no diagnostic to point at it. And a T whose alignment the block does not satisfy is undefined behaviour reached through the one cast a compiler cannot reason about — the alignment of the block is whatever the producer delivered, whether a MemoryManager array or an OS file mapping, and nothing here records it.
Prefer the streams for structured data. BufferInputStream and BufferOutputStream read and write primitives with cursor arithmetic, an error count and padding handling, rather than trusting the caller's T. They are separate classes in their own headers and have no page in this batch — see Coverage.
