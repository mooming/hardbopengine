Buffer

Engine/Resource/Buffer.h namespace hbe final move-only a byte block plus the closure that knows how to release this particular block

Class description

Three fields: a byte count, an address, and a TReleaseBuffer naming the code that frees them. Ownership is expressed as a callback rather than as an allocator type or a templated owning pointer, which is what lets one buffer class stand for memory from a MemoryManager array, for a file mapping made by the OS layer, and for no memory at all — all three of those exist today, produced by the factories in BufferUtil. The buffer does not care where the bytes came from; it holds the instruction for letting them go, and the destructor runs it.

This is the engine's serialisation currency as well as its blob type: a buffer is handed to something that writes into it or read from something that reads out of it, by reference, without transferring ownership. MultiPoolConfigCache::Serialize(Buffer&) and MultiPoolConfigCache::Deserialize(const Buffer&) in Engine/Memory/ are the two live users, and MemoryManager calls them when it saves and loads the pool configuration cache.

Move-constructible, and not assignable in any form. The header declares a move constructor and a destructor; under the language rules that combination removes the move assignment operator and leaves the copy assignment operator deleted, so a = std::move(b); does not compile while Buffer b = std::move(a); does. A buffer therefore cannot be reused by assignment-over — one object, one block, from construction to destruction — and a container of buffers can insert and grow but cannot reorder elements by assignment. See the constructors for what is declared.
A buffer with data and no releaser leaks, and only warns. That state is reachable through the single-argument constructor, which installs no releaser, and through SetReleaser not having been called yet. At destruction the block is left alone and a warning is logged; the process is not stopped and nothing is freed. The engine's own file-mapping factory deliberately constructs in exactly this state and installs the releaser one statement later, so an exit between those two statements is the leak.

Template parameters

None — Buffer is not a template, deliberately. It is a byte block, so a typed view of it is taken per call at the point of use: GetDataAs<T>() and TranslateSizeAs<T>() are members templated on the element type, not the class. One buffer type therefore moves through the API unchanged no matter what somebody intends to read out of it, and the type promise is made and consumed at the call site with nothing recording it.

Non-member helper functions

None in Buffer.h. The functions that build buffers live in the sibling namespace hbe::BufferUtil (Engine/Resource/BufferUtil.h): GenerateDummyBuffer, GenerateFileBuffer, GetFileBuffer, GetReadOnlyFileBuffer, GetWriteOnlyFileBuffer and the GetMemoryBuffer<T> template, documented on BufferUtil — they are the real call sites for these constructors and for SetReleaser, and each section there quotes the closure pair it builds.

Coverage

GapDetail
Nothing about a buffer is lazy The word "buffer" invites an assumption of deferred work, so it is worth stating plainly: every constructor that takes a TGenerateBuffer calls it before the constructor returns, and no generator is stored for later. A buffer is therefore fully resolved at the end of its own construction, and the only thing that can still be pending is the releaser — see SetReleaser
BufferInputStream and BufferOutputStream Both exist, in their own headers Engine/Resource/BufferInputStream.h and Engine/Resource/BufferOutputStream.h — not inside Buffer.h, which is what the previous version of the module page asserted. They are public classes with a wide operator>> / operator<< surface over primitives, strings and containers, and they borrow rather than own: the input stream holds const Buffer&, the output stream holds Buffer& and pins itself to the thread that constructed it. Both are documented now — BufferInputStream and BufferOutputStream — and the image they agree on is described once, on the writer's format section
Alignment and provenance of data Nothing here allocates, so alignment is whatever the producer delivered — a MemoryManager array for GetMemoryBuffer, an OS mapping for GenerateFileBuffer. Reading a type whose alignment exceeds that through GetDataAs is therefore not checked anywhere in this module
What GetClassName returns exactly It is derived from __PRETTY_FUNCTION__ by StringUtil::ToCompactClassName, so the spelling is that helper's business — String: StringUtil
