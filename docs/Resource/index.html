Module Index / Resource

Resource

namespace hbe Engine/Resource 7 headers, 6 sources binary buffers and the manager that is meant to load and keep them

Module description

Two ideas and one skeleton. A Buffer is a byte count, an address and the callback that releases them, so ownership of a blob does not depend on who allocated it: memory from a MemoryManager array, a file view mapped by the OS layer, and no memory at all are all held by the same type, and each one knows how to let go. That idea is complete and in use — the pool configuration cache is written and read through buffers by MemoryManager.

A ResourceManager is the second idea: buffers keyed to paths, loaded synchronously or asynchronously, kept in one table with a reference count so a path is loaded once. The class is declared with exactly that machinery and almost none of it is implemented — RequestLoad and Load have no definition at all, PostUpdate has an empty body and no caller, and the reference count is never read. A Resource is the handle a caller would hold back, and it is empty: no path, no id, no accessor, so nothing can be asked of it.

The third piece is BufferTypes, the namespace holding the size type and the three callback shapes a buffer is built from, so a generator and a releaser written anywhere are the same type everywhere.

Module variables

None. No Resource header declares an object at namespace scope; the only statics in the module are function-local ones — the cached class name inside Buffer::GetClassName and a logger inside BufferUtil::GenerateFileBuffer.

Module functions

Not reached through an object, and not none either: the nested namespace hbe::BufferUtil in Engine/Resource/BufferUtil.h declares six free functions, all of them returning a Buffer by value, and all of them live code — MemoryManager calls three of them when it loads and saves the pool configuration cache.

NameHeaderWhat it produces
GenerateDummyBuffer BufferUtil.h A byte count and a null pointer — a buffer for measuring an output before allocating one. Its default size argument is std::numeric_limits<size_t>::max()
GenerateFileBuffer BufferUtil.h A file mapped into memory with the open mode and protection asked for; the only call to SetReleaser in the engine
GetFileBuffer BufferUtil.h The same mapping, read/write
GetReadOnlyFileBuffer BufferUtil.h The same mapping with read-only protection. The open mode it passes on is read/write, so the name describes the view, not the handle
GetWriteOnlyFileBuffer BufferUtil.h The same mapping, writable only, created or truncated to a requested size
GetMemoryBuffer BufferUtil.h A T[] array from MemoryManager, filled with a default value — the one template of the six, and the pair of closures quoted on the buffer constructors

Each is documented in its own section of BufferUtil, including the pairing that makes a size probe possible before a file is created.

Coverage

GapDetail
Resource has no accessor No path, no id, no buffer, no loaded flag — stated plainly on its own class page. Whether the handle should expose the path, the id or the bytes is a design decision, not a documentation omission
The streams' bounds guard does not test the end of a read Both classes declare an identical private IsValidIndex(size_t index) whose body compares cursor against the buffer size and never reads its argument. The output stream never calls it — its real guard is the newIndex > size test inside Put. The input stream calls it three times, so a read that starts inside a block and ends outside it is not refused: BufferInputStream: IsValidIndex
operator>>(const HString&) reads nothing Defined as return *this;, with a const parameter it could not fill. An image deserialised through it leaves the string untouched and desynchronises the rest of the chain: operator>>
Read-only names the mapping, not the descriptor GetReadOnlyFileBuffer opens the file read-write and restricts only the protection, so the guarantee is a protection fault rather than an OS-level denial. Nothing in the engine writes through a read-only mapping, so the difference is untested
Asynchronous loading, caching and retirement Not merely private mechanics: the two loaders (RequestLoad, Load) are declared with no definition anywhere, so a call does not link; PostUpdate has an empty body and is never called; and ResourceItem::referenceCount is initialised and never read, so nothing shares a buffer or retires an item. There is no behaviour here to document, only a declared shape — which is why the previous version of this page's claims about queueing, blocking and reference counting are gone
Engine integration is not wired Engine owns a manager and exposes GetResourceManager(), but EInitLevel has no resource level, SetResourceManagerReady() is never called, and nothing pumps the manager. See the manager constructors
Declarations with no users BufferTypes::TResizeBuffer and BufferTypes::TIndex are used by no code, and the nested ResourceManager::LoadingRequest is never instantiated — the pending list stores ResourceItem* instead. Recorded on BufferTypes and ResourceManager
Test-only code __UNIT_TEST__ declares BufferTest, BufferInputStreamTest and BufferOutputStreamTest in the module's headers, all three registered with the runner documented in Test. Their cases are quoted as call sites where a real call site was needed — notably the buffer destructor
Contracts that belong to another module What GetFileBuffer maps and how it fails is OS behaviour (OSAL: file); which pool GetMemoryBuffer draws from and how long it holds it is Memory; what a released-but-still-open mapping means for a file is platform-specific. None of it is restated here
