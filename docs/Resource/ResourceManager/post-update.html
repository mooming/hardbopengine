PostUpdate

member of hbe::ResourceManager Engine/Resource/ResourceManager.h noexcept body: { } the per-frame pump the asynchronous design is written around — currently an empty function nobody calls

Signature

void PostUpdate(Engine& engine) noexcept;

Function description

The definition in ResourceManager.cpp is {}. It returns without looking at its argument, without touching loadingRequests or resources, and without logging. So the honest contract today is: cheap, side-effect-free, idempotent, and useless.

Its shape says what it is for. Taking the Engine by reference is how this class reaches the TaskSystem — Engine exposes GetTaskSystem() — and the private RequestTasks(TaskSystem&) next to it is the half that would dispatch work. Read together, the pair describes a pump that collects finished asynchronous loads and dispatches new ones. Neither half does anything yet.

Nothing calls this. Grepping Engine/ and Applications/ finds the declaration, the empty definition, and no call site: Engine has no update hook of its own that would reach it, and no application calls it. A design in which "the load completes on a later PostUpdate" therefore has no mechanism in this build, and adding your own call is a decision about frame order, not a documentation question — the engine has no defined frame phases to slot it into.

Parameters

ParameterTypeRequirement
engine Engine& A live engine, non-null — the only source of the task system this pump would need. Unused by the current definition, so passing one costs nothing and proves nothing; the type still has to be complete at the call site, which means including Engine/Engine/Engine.h

Return value

void. Nothing about progress, completion or failure: a pump with a status to report would need a return type or an out-parameter, and this one has neither. noexcept.

Examples

Illustrative — no call site for this exists in the repository.

auto& engine = hbe::Engine::Get();

while (running)
{
        // ... application frame ...
        engine.GetResourceManager().PostUpdate(engine);
}

The two calls this snippet makes are both real — Engine::Get, GetResourceManager() and this function are declared and defined, so the loop compiles and links. It returns having advanced nothing, because RequestLoad never enqueued anything to advance.

Calling it twice per frame is currently harmless, and will not stay that way. The warning against pumping the queue yourself, which the previous version of the module page carried, was aimed at a future in which the engine also pumps it; there is no engine call to collide with. Keep this function's invocation in exactly one place when the pump gets a body, since a queue advanced twice retires or dispatches twice.
