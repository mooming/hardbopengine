ResourceManager

Engine/Resource/ResourceManager.h namespace hbe final declared: path-keyed loads, reference counting, async advance implemented: construction, destruction the intended owner of every loaded Buffer — a skeleton today

Class description

The header's summary says what it is for: "Manages resource loading and lifetime with reference counting." The declarations agree — a table of loaded ResourceItems, a list of in-flight requests, a synchronous Load and an asynchronous RequestLoad, and a PostUpdate taking the Engine so it can reach the rest of the frame. The Resource handle a load returns is the caller's half of the arrangement.

What is written so far is the shape and the ownership, not the behaviour. ResourceManager.cpp defines the constructor and destructor as = default and defines PostUpdate and the private RequestTasks with empty bodies; RequestLoad and Load are declared and have no definition anywhere in the repository. So a manager can be constructed, can be destroyed, and does nothing in between.

Calling RequestLoad or Load does not link. Both are declarations only; grepping every .h and .cpp under Engine/ and Applications/ finds the header line and nothing else. A caller therefore compiles and fails at link time, and no code in the engine attempts it. Nothing reads resources, loadingRequests or ResourceItem::referenceCount, so the reference count is initialised to zero by ResourceItem's constructor and never touched again: no load can share a buffer, and no item can be retired.
One instance exists, and nothing drives it. Engine/Engine/Engine.h holds ResourceManager resourceManager; as a member and hands it out from GetResourceManager(), so the lifetime claim is true. But PostUpdate is called by nobody — not by Engine, not by any application — EInitLevel offers no level that starts the resource manager, and SetResourceManagerReady() is never invoked, which makes IsResourceManagerReady() answer false for the whole process. "The engine advances it each frame" is a description of a plan, not of this build.

Template parameters

None — ResourceManager is not a template. It declares one member alias template, TVector, which is what its two containers are built from; there is no resource-type or allocator parameter to specialise on.

Class properties

NameDeclarationWhat it means
TVector template<typename T>
using TVector = hbe::HVector<T>;		 member type The storage for both containers below. HVector<T> is std::vector over DefaultAllocator<T>, so the tables allocate through the engine's allocator scope rather than the global one — HSTL: HVector and Memory: allocators
ResourceItem class ResourceItem final with uint32_t id;, uint32_t referenceCount;, StaticString path;, Buffer buffer; private nested class One loaded thing: a numeric id, the count that is meant to decide when it dies, the path it came from and the Buffer holding its bytes. The default constructor sets id and referenceCount to 0 and leaves the path null and the buffer empty. path is a StaticString, so it is an interned string and two items loaded from one path carry the same pointer — the mechanism a lookup would compare on
LoadingRequest class LoadingRequest final with uint32_t resourceID;, StaticString path; private nested class A request waiting to be serviced: which id was asked for, at which path. Declared and then not used — the pending list below stores ResourceItem* instead, so nothing in the class has this type
resources TVector<ResourceItem> resources; private The loaded set, held by value: the manager owns the items, and therefore owns the buffers inside them. Never read or written by any code that exists
loadingRequests TVector<ResourceItem*> loadingRequests; private Requests in flight, stored as raw pointers into resources. hazard by construction Those pointers address elements of a vector that grows, so the first reallocation invalidates every entry in this list. Any implementation that fills both containers has to reserve, store indices, or move the items somewhere stable — a defect an implementer will meet immediately, and worth naming now because the declaration is the only place the constraint is visible

Class methods

MethodSignatureWhat a caller depends on
constructors ResourceManager() noexcept One default constructor, = default: both containers come back empty. No path table, allocator or task system is supplied, because there is nothing yet for them to be used for
destructor ~ResourceManager() noexcept = default, and it is the one behaviour here that genuinely works: destroying the manager destroys every ResourceItem, which destroys each Buffer, which runs that buffer's releaser
PostUpdate void PostUpdate(Engine& engine) noexcept Declared to be the per-frame pump; defined with an empty body, and called by nobody in the repository
RequestLoad Resource RequestLoad(StaticString path) [[nodiscard]], takes a path, returns a handle. The intended asynchronous path, judging by the name and the private request machinery — no definition, so no behaviour to depend on and no link
Load Resource Load(StaticString path) [[nodiscard]], same argument and result. The intended synchronous counterpart; likewise declared only

The remaining member, void RequestTasks(TaskSystem& taskSys) noexcept, is private and its definition is an empty body. It is named here because it is the only declaration in the class that mentions TaskSystem, which is what an asynchronous load would have to go through; it is not documented as API. See Coverage.

Non-member helper functions

None. ResourceManager.h forward-declares class Engine; and class TaskSystem; so the two signatures above do not have to include those headers, and declares nothing else at namespace scope.

Coverage

GapDetail
Loading, caching, deduplication and retirement Every one of these is implied by the members and none is written. There is consequently no documented answer to "what happens when two callers ask for one path", "what does a load do when the file is missing", or "when exactly does a buffer get freed" — those are questions about code that does not exist yet, and guessing them from the summary would be exactly the kind of drift this site exists to prevent
Reference counting One field, ResourceItem::referenceCount, initialised to 0 and never modified. The previous module page asserted that two loads of one path share a buffer and that an item is released when the count reaches zero; no declaration or definition supports that, so the assertion is gone from the module page and recorded here as unimplemented
RequestTasks Private, empty body. Not documented as API; noted under Class methods as the hook a real RequestLoad would use
How an item is keyed and looked up ResourceItem::path and id both exist and no code reads either. Whether the id is a hash of the path, an index into resources, or a slot counter is undetermined by the header — String: StaticStringID is what an interned-path key would most plausibly use, but nothing here names it
Thread-safety The header states none, and there is no mutex in the class. An asynchronous loader that touches resources from a worker thread would need one, but saying more than that would be describing a design that has not been written
Engine integration Ownership and the accessor are real; starting, pumping and readiness are not wired. The Engine page documents what the engine actually initialises each frame, and this module is not part of it
