Load

member of hbe::ResourceManager Engine/Resource/ResourceManager.h [[nodiscard]] declared, not defined the synchronous counterpart of RequestLoad, in name only

Signature

[[nodiscard]] Resource Load(StaticString path);

Function description

Same argument, same result, same state as its counterpart: a declaration in ResourceManager.h and no definition in ResourceManager.cpp or anywhere else in the repository. Calling it compiles and does not link.

The pairing of the names is the entire documentation of the difference between them — Load does the work and returns something finished, RequestLoad starts work and returns a promise. Nothing else in the header distinguishes them: no comment on either, no different parameter, no completion callback, no status type.

If it were implemented, the shape forced by the rest of this module would be: intern or hash path, look it up in resources, build a Buffer on a miss, return a Resource. The last step is the weak one — the handle has no members, so a caller that receives it has the buffer's address in nothing it can read. Any real use of this function needs the handle class to grow an accessor first.

Parameters

ParameterTypeRequirement
path StaticString (by value) The resource to load. Interned string, cheap to pass, implicitly convertible from a const char*. Whether a missing or unreadable path is an assert, a log line or an empty handle is unanswered — there is no implementation to read the answer from

Return value

TypeWhat you get
Resource A handle, [[nodiscard]]. It exposes nothing: no path, no id, no buffer, no loaded flag. "Blocks until the buffer is resident" was the previous module page's description of this return value; the resident buffer is not reachable from the handle, and never was

Examples

No example is given. No call site exists in Engine/ or Applications/, and a snippet calling a function with no definition would be a snippet that does not link. The synchronous, blocking, "give me the bytes now" need this name describes is met in this build by BufferUtil::GetFileBuffer and friends, which return a real Buffer — named on the module page, and documented on BufferUtil.

"The right call at startup, the wrong one inside a frame" is advice about a function that does not exist. It was on the previous module page and it is not supported by any header, so it is not repeated here. Once a blocking load exists, the cost it hides is a file open plus a mapping made on the calling thread — the same work BufferUtil::GenerateFileBuffer performs synchronously today, and which MemoryManager already does at start-up.
