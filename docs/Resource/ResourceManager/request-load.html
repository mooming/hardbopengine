RequestLoad

member of hbe::ResourceManager Engine/Resource/ResourceManager.h [[nodiscard]] declared, not defined the asynchronous half of resource loading: ask for a path now, take the handle, keep going

Signature

[[nodiscard]] Resource RequestLoad(StaticString path);

Function description

Declared in the header and defined nowhere: ResourceManager.cpp contains the constructor, the destructor, an empty PostUpdate and an empty RequestTasks, and grepping the whole repository for RequestLoad returns this one line. A call compiles — the declaration is visible — and fails at link time.

What the name and the surrounding declarations commit to is a request rather than an acquisition: it hands back a handle immediately, and the class owns the machinery a request would need — loadingRequests holds entries waiting to be serviced, the private RequestTasks(TaskSystem&) is where work would be posted to the TaskSystem, and PostUpdate is the pump that would notice completion. The contrast with Load is the only statement of synchronicity anywhere, and it is a naming one.

The old module page described this as queueing a load and finishing it on later PostUpdate calls. That behaviour does not exist. No queue is ever appended to, nothing dispatches a task, and the pump is empty. What is worse than absent is unobservable: since Resource has no members and no accessors, a returned handle cannot report "not loaded yet" either. A caller writing against this API today has no way to learn when bytes arrived, and no code to test that against.

Parameters

ParameterTypeRequirement
path StaticString (by value) The thing to load. Passed by value, and it is one interned pointer, so copying it into the request is cheap and the string outlives the call by construction. A const char* literal converts implicitly, since StaticString has a non-explicit constructor from one. What counts as a valid path, and what happens for one that does not resolve, is undetermined: no implementation exists, so there is no documented error behaviour to promise

Return value

TypeWhat you get
Resource The handle for the request, marked [[nodiscard]] so dropping it is a compile error. It is an empty class: no id, no path, no buffer, no way to ask whether anything arrived. Even with a definition in place, this return value carries no information today

Examples

No example is given, deliberately. There is no call site anywhere in Engine/ or Applications/, and a snippet that called this function would name a symbol the linker cannot find — see the class Coverage for what is missing and Load for the same situation on the synchronous side.

For a buffer you can actually read right now, the working path in this build is BufferUtil, not this class. BufferUtil::GetFileBuffer, GetReadOnlyFileBuffer and their relatives return a Buffer directly, with a releaser attached, and are used by MemoryManager. Each is documented on BufferUtil.
