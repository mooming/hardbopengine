member of hbe::BufferOutputStream Engine/Resource/BufferOutputStream.h explicit noexcept copy and move deleted one stream per buffer, pinned to the thread that opens it

Signature

BufferOutputStream(const BufferOutputStream&) = delete;
BufferOutputStream(BufferOutputStream&&) = delete;

explicit BufferOutputStream(Buffer& buffer) noexcept;
~BufferOutputStream() = default;

The deletions are declared before the constructor that exists, so the disabled forms are the first thing a reader of the header meets.

Function description

The constructor stores the buffer reference and starts the stream at the beginning of it: cursor(0), errorCount(0), and threadID(std::this_thread::get_id()). It reads nothing and writes nothing, so a freshly opened stream has not touched the block; the first byte is written by the first operator<<.

The thread captured there is not informational. Every Put begins by asserting the current thread equals it, so opening a stream is also the act of declaring which thread owns it — see thread pinning below.

Copying and moving are deleted for one reason: the cursor is the stream's entire state, and two streams holding one cursor would write over each other at the same offsets. A second stream over the same buffer is legal — construct one — but it starts at 0 and knows nothing about the first. The deletion stops the one case that looks like ownership transfer and is not: handing a stream on as a value.

Both string-family overloads and the container overloads are on operator<<; the buffer's own lifetime is a Buffer question, not a stream question.

Thread pinning is an assertion, and Release builds compile assertions away. Assert is a function in Core/Debug.h with an empty Release form, so the cross-thread check that makes this contract real in Debug and Dev is not present in Release. What remains is the ordering discipline of whoever constructed the stream; nothing detects the violation there.
The stream does not verify that the buffer outlives it. The member is Buffer& buffer;, and the buffer is never asked whether it still holds the bytes the stream last wrote. The usual shape in this engine is one buffer, one stream, both local to the same scope — MemoryManager::SaveMultiPoolConfigs does exactly that — and a stream kept past its buffer is undefined rather than detected.
