BufferOutputStream

Engine/Resource/BufferOutputStream.h namespace hbe final not copyable, not movable thread-pinned at construction a cursor, an error tally, and the only write path into a borrowed Buffer

Class description

Four members do everything: a Buffer& the stream writes into and does not own, a byte cursor, an error count, and the thread id captured by the constructor. Serialising is the act of pushing values through operator<<; each one lands in the block before the call returns, so there is no buffer of its own, no flush, and nothing to do at destruction.

The engine has no exception mechanism, so a stream that cannot write does not report it in any way a caller can miss by accident: the write is refused, the cursor stays put, and HasError reads the tally afterwards. noexcept on every overload is therefore accurate rather than decorative — this class has no failure path that could unwind.

Its purpose is pair-work. The bytes it produces are read back by BufferInputStream, which applies the same alignment rounding and the same length prefixes. The two classes are the same design mirrored: the input stream holds const Buffer&, the output stream holds Buffer&; both count refusals rather than reporting them; the output stream additionally pins itself to a thread, because it is the one that mutates.

A third use is measurable rather than productive: build the stream on a buffer whose pointer is null and every write becomes a reservation, so the cursor afterwards is the size the image needs. That is how MemoryManager::SaveMultiPoolConfigs learns the size of the file it is about to write. See Put for the exact conditions.

One stream, one thread — asserted in Debug and Dev, unenforced in Release. Both Put templates open with Assert(std::this_thread::get_id() == threadID), and Assert is an ordinary function in Core/Debug.h whose Release form discards its argument. The capture happens once, in the constructor, so which thread owns a stream is decided by where it was constructed.

The image format

Writing is not a byte copy, and a reader that assumes one will not agree with this writer. Three rules define what lands in the block, all of them in Put:

RuleWhat it doesWhy it is there
Per-value alignment The cursor is rounded up to a multiple of sizeof(T) before each write The value is stored through reinterpret_cast<T*>, so it has to sit on its own alignment for the store to be valid on every platform the engine builds for
Padding is zero-filled The skipped bytes are written as 0 rather than left alone Two runs of the same write sequence give byte-identical output, so a saved file is comparable and whatever was in the block before does not reach disk
Strings and arrays are length-prefixed A size_t count precedes the elements. Strings write no terminator; arrays count elements, not bytes The reader needs a length to size a container, and the engine's strings are not NUL-terminated in memory either — String stores an interned view

Nothing in the image identifies itself: no magic, no version, no endianness marker, and no type tags. A format that needs those writes them itself before opening a stream, the way MultiPoolConfigCache::Serialize writes MultiPoolConfigCache::Version as its first value — a convention between two functions, not a feature of this class.

Template parameters

None on the class — BufferOutputStream is not a template, and a stream does not need to know what type it is writing because the type arrives per call. The templates are on the members: the two Put<T> forms that carry every byte into the block, the operator<< overload taking T(&array)[N], and the one taking HInlineString<N>. sizeof(T) is taken inside Put as constexpr size_t tSize, with static_assert(tSize > 0), so the alignment arithmetic is resolved at compile time and a zero-size element type is a compile error rather than a divide-by-zero.

Non-member helper functions

None in BufferOutputStream.h. The buffers this class writes into come from the sibling namespace hbe::BufferUtil, documented on its own page — GenerateDummyBuffer is the one that makes probing mode possible, and GetFileBuffer and GenerateFileBuffer are the ones that produce a writable block in the first place.

Coverage

GapDetail
Bounds work is done twice, and the helper that looks like it does it is unreachable IsValidIndex is declared, defined and never called, and its body compares cursor against the buffer size while ignoring its argument. The guard that actually runs is the newIndex > size test inside Put. The sibling class calls its identical helper three times — BufferInputStream: IsValidIndex
A refused array write can leave its length prefix behind The array form of Put commits the size_t prefix before testing whether the payload fits, so refusal can leave a count with no elements after it. Nothing rolls it back, and there is no rewind to correct it
Nothing in the image identifies the image No magic number, version field or endianness marker is written. Callers that need one write it themselves — MultiPoolConfigCache::Serialize in Engine/Memory/ writes its own Version first
Width of long double and size_t across platforms long double is a distinct overload and its sizeof is platform-dependent, as is whether size_t is a distinct type at all — hence the #ifndef PLATFORM_LINUX around that one overload in the header. An image written on one platform and read on another is not guaranteed the same shape
No test collection for the output stream Unlike BufferInputStream, this header declares no test class under __UNIT_TEST__. Its behaviour is exercised indirectly, as the writer half of Engine/Test/ cases and of the pool-config save path in MemoryManager
The buffer must outlive the stream, and nothing checks it Discussed on the constructors. The reference member is the only link to the block, and no weak-handle or generation check backs it
