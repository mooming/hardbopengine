StaticStringTable

Engine/String/StaticStringTable.h namespace hbe final the global intern table — one address per distinct text, forever

Class description

The global intern table behind StaticString: one process-wide singleton that owns every byte of interned text from first registration to process exit. Register maps text to a stable address — the first caller's bytes, reused by everyone afterwards — and Get maps an id back to the characters. Equality of StaticString values is pointer equality on what this table mints, so the table's core promise is one address per distinct text, forever.

Lookup is hashed, not global: GetTableID hashes the text with StringUtil::CalculateHash and takes it modulo NumTables (Config::StaticStringNumHashBuckets), and the linear search runs only inside that one bucket. Storage is a bump allocator over malloc'd banks — see the private members below — so text bytes never move and an id handed out by Register stays valid until the table is destroyed.

The table never shrinks. Memory is released only when the singleton is destroyed at process exit; there is no unregister. After that destructor runs, the bytes behind every StaticStringID ever handed out are freed — a StaticString in static storage that outlives the table would read freed memory. Ordinary engine lifetime (wrappers created after engine initialisation, destroyed before it ends) never reaches that point.

Template parameters

None — the class is not a template. Its nested Allocator is, and it is documented in the properties table below.

Non-member helpers

None declared in the header. The Bank struct and the banks/bankIndex/ memLock globals in Engine/String/StaticStringTable.cpp's anonymous namespace are the storage mechanism — implementation, not API, and documented through Allocate and the destructor.

Coverage

This page documents every member the header declares, including the private ones — the storage contract is the point of the class. Two omissions are named rather than glossed: the nested Allocator's member functions are covered by one row above rather than pages of their own (they are one-line forwards), and the exact growth schedule of the banks is stated at the level the code fixes it — 1 MiB default, oversized requests get their own bank — without a performance analysis the code does not carry.
