HVector

Engine/HSTL/HVector.h namespace hbe 2 aliases, 0 functions std::vector with the allocator replaced — a pure rename apart from where the bytes come from

Class description

There is no class here. HVector.h declares two aliases and includes <vector> plus the two engine allocators; it defines no type of its own and adds no member, helper or free function. Every behaviour of HVector is std::vector's — growth policy, reallocation, iterator invalidation, the copy and move rules — because the header reimplements none of it.

So HVector<int> is std::vector<int, hbe::DefaultAllocator<int>>. The one question this page exists to answer is which pool those bytes come from, and the answer is not in this header: DefaultAllocator<T>'s default constructor stores MemoryManager::GetCurrentAllocatorID(), and a container default-constructs its allocator when the container is constructed. The pool is therefore chosen at the vector's construction site and never revisited — a later push_back or reserve allocates from the pool that was current when the vector came into being, not from the one current at the call. When that id is MemoryManager::SystemAllocatorID, DefaultAllocator::allocate calls malloc directly and the allocation is not accounted at all.

The header declares no members, so every use of it is a name written somewhere else. Twenty-six files outside Engine/HSTL/ name HVector; the three declarations below are three of them, chosen because each is a different shape of use — a templated member typedef, a plain one, and a vector held by an allocator itself — plus the one inline-pool vector that sizes itself against the pool. 

// Engine/Core/TaskStream.h
template <typename T>
using TVector = hbe::HVector<T>;
using TRangedTasks = TVector<RangedTask>;

From Engine/Core/TaskStream.h

// Engine/Core/ComponentSystem.h
using TCompoList = hbe::HVector<TComponent>;

From Engine/Core/ComponentSystem.h

// Engine/Memory/ThreadSafeMultiPoolAllocator.h, a member of the allocator itself
hbe::HVector<PoolAllocator> banks;

From Engine/Memory/ThreadSafeMultiPoolAllocator.h

The engine already has a dynamic array, and it is a deliberately different animal. Array allocates exactly the element count with no capacity, deletes its copy operations, indexes with int, and names its allocator as a template argument you can see at the use site. HVector has the standard's geometric growth, is copyable whenever the element is, sizes with size_t, and hides its allocator inside the alias. The choice the engine makes in practice is by layer, not by taste: ComponentSystem, TaskStream and ResourceManager all use HVector behind a member typedef.

Template parameters

AliasTemplate parametersContainer it binds
HVector template<typename T> — T only, nothing defaulted std::vector<T, hbe::DefaultAllocator<T>>
HInlineVector template<typename T, size_t PoolSize = 16> std::vector<T, hbe::InlinePoolAllocator<T, PoolSize, 2>>

Neither alias forwards an allocator, an element-count type or an comparator: the allocator is fixed by the alias, which is the entire point and also the limitation — there is no way to ask HVector for a different pool. Naming a pool means Array<T, TAllocator> or a new alias.

Class properties

Both lines as Engine/HSTL/HVector.h spells them. An alias owns no members, so each row is the alias and the cell states the difference from std::vector<T>.

Named by 26 files outside Engine/HSTL/, 21 of which include the header directly; among them TaskStream, ComponentSystem, ResourceManager, BufferInputStream, ThreadSafeMultiPoolAllocator and OS::ListFilesInDirectory
HInlineVector<T, PoolSize> template<typename T, size_t PoolSize = 16>
using HInlineVector = std::vector<T, hbe::InlinePoolAllocator<T, PoolSize, 2>>;		 alias template The element type and interface are unchanged; what changes is that the first allocation can be satisfied from bytes stored inside the vector object. The pool lives in the allocator, the vector holds the allocator, and InlinePoolAllocator's own arithmetic is ActualBlockSize = max(PoolSize, sizeof(void*)), ActualNumBlocks = max(2, 1) = 2, BlockSizeInBytes = sizeof(T) * ActualBlockSize — so PoolSize is a count of T per block, two blocks, and the vector object carries 2 * PoolSize * sizeof(T) bytes inline

The only engine use of the inline form sizes itself against that block: 

// Engine/Memory/MultiPoolAllocator.cpp
constexpr size_t InlineBufferSize = 128;
Assert(initialConfigurations.size() <= InlineBufferSize);

HInlineVector<PoolConfig, InlineBufferSize> vlist;
vlist.reserve(InlineBufferSize);

From Engine/Memory/MultiPoolAllocator.cpp

Read against the arithmetic above, reserve(128) asks allocate(128), which asks for 128 * sizeof(PoolConfig) bytes against a block of max(128, 8) * sizeof(PoolConfig) — exactly one block, so the buffer is the vector's own storage and no pool or allocator is consulted. The Assert two lines earlier is that ceiling enforced in code rather than left to the alias. The same pair appears in ThreadSafeMultiPoolAllocator.cpp.

The name PoolSize and the parameter it feeds disagree about units. InlinePoolAllocator's second parameter is named BlockSize and its header comment calls it "The desired size of the object allocated in bytes", but the class computes BlockSizeInBytes = sizeof(T) * ActualBlockSize. For char the two readings coincide; for any other element type the number in the alias is elements, not bytes, so HInlineVector<PoolConfig, 128> reserves 128 configs — hundreds of times the figure a reader who trusts the comment would infer. Both spellings are in the headers; the multiplication is the one the code executes. See Memory for the allocator and docs/AllocatorGuide.md for the pool design.
An inline-pool vector must not be copied. InlinePoolAllocator declares InlinePoolAllocator(const InlinePoolAllocator&) : InlinePoolAllocator() { Assert(false); }: a copy builds a fresh pool and fires the assertion, which is live in Debug and Dev and silent in Release. The standard makes get_allocator() return the allocator by value, and a vector is free to copy its allocator elsewhere; storing an HInlineVector in another container copies elements. The full hazard, including the string side of it, is on the HString page.

Class methods

None, and none is possible: an alias has no members. Every std::vector member is present with the standard's contract — push_back, emplace_back, reserve, size, operator[], the iterators — and none of them is engine-specific, so none has a page here. This page has no method pages by design, not by omission. The engine's own container surface, where the contracts are engine-defined, is documented under Container.

Non-member helper functions

None. HVector.h declares nothing at namespace scope beyond the two aliases — no std::hash specialisation (contrast HString, which does declare one), no test fixture under __TEST__ (contrast HUnorderedMap), and no source file: the module's CMakeLists.txt lists HVector.h as a header of the HSTL target with no HVector.cpp beside it.
