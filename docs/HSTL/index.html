HSTL

namespace hbe Engine/HSTL 3 headers, 2 sources 6 aliases, 1 hash specialisation standard containers rebound to engine allocators — and the sources ship no code at all

Module description

HardBop STL is six using-declarations across three headers. Each one names a standard container specialisation with an engine allocator substituted, and none of them declares a class, a member or a function in namespace hbe. There is no wrapper and no reimplementation, so a member you already know is the member you get, with the standard's contract attached.

The one thing the layer actually decides is which allocator a container holds, and that answer is subtler than "the engine's". DefaultAllocator<T>'s default constructor stores MemoryManager::GetCurrentAllocatorID(), and a container default-constructs its allocator when the container is constructed. So the pool an HVector, HString or HUnorderedMap draws from is fixed at its own construction site by whichever allocator scope happens to be open there, and never revisited by a later insertion. When that id is MemoryManager::SystemAllocatorID, DefaultAllocator::allocate calls malloc directly and bypasses MemoryManager — so "engine allocator" does not by itself mean the allocation is accounted.

There is one piece of second behaviour to learn, and it is not in a container. HString.h specialises std::hash<hbe::HString> with djb2 over c_str(). It is not a rename of anything: it replaces the hash the standard library would otherwise have refused to supply, it stops at the first null while operator== compares the whole string, and it widens char in a way whose result depends on that type's ABI-defined signedness. The HString page carries the code and the consequences.

Where the engine's own Container module covers the same need, prefer it for engine internals: Array names its allocator at the use site and allocates exactly the element count, while these aliases hide the allocator and keep the standard's growth policy. Use the standard shapes where a standard container is wanted — at OS and serialisation boundaries, and behind a member typedef inside a class, which is how the engine itself uses them.

The module's two .cpp files are worth stating plainly, because they change what a build of libHSTL contains. HString.cpp is a copyright line and #include "HString.h" and nothing else; HUnorderedMap.cpp is an include plus the body of a __TEST__-guarded fixture. Outside the test build the target compiles no code — which is exactly what an alias layer should do, and is the reason HVector.h has no source file beside it.

Module variables

None. An alias declares no entity, so nothing in this module has storage, linkage or a lifetime, and there is no object to read. The inline pool sizes are template arguments, not variables, and are listed with each alias on its page. The single value the module reads from elsewhere is Config::MaxPathLength — 512, a static constexpr int in Engine/Config/EngineConfig.h — which HInlinePathString uses as its block size.

Module functions

None: no header declares a function at namespace scope in hbe. This is not quite "nothing callable" — HString.h declares std::hash<hbe::HString>::operator(), a noexcept call operator reached by every HUnorderedMap keyed on HString. It is documented where it is declared, on the HString page, rather than claimed as an engine function.

The standard library's own guarantees Growth factors, rehash and iterator invalidation, small-string behaviour and complexity bounds belong to std::vector, std::basic_string and std::unordered_map and are not reproduced. Where a page needed a library fact it cited the standard; where the answer is implementation-defined — a growth factor, which internal types a container rebinds an allocator to — the page says so instead of guessing
Test-only code HUnorderedMap.h declares the fixture HUnorderedMapTest under __TEST__ and HUnorderedMap.cpp defines it; that is the module's only fixture, and its operator[] expectations are recorded on HUnorderedMap. HString.h and HVector.h declare none. Fixtures and registration are Test's subject
Alias names do not carry the T prefix the standard requires docs/CodingStandards.md spells type aliases and template type parameters TIndex-style. None of the six aliases here does — HString, HInlineString, HInlinePathString, HVector, HInlineVector, HUnorderedMap — and neither do the template parameters spelled T and PoolSize. The H prefix is this module's own convention: every name is the standard container it renames. Renaming reaches 123 occurrences in 38 files outside Engine/HSTL/, spanning ten engine modules, so it is an owner decision recorded here rather than a defect a standards pass may settle silently. The names are documented as the headers spell them
What the aliases permit that the engine's memory rules discourage The standard asks callers to avoid dynamic allocation and to know where a container's bytes come from. An alias cannot honour either request on a caller's behalf: HVector and HUnorderedMap grow geometrically as their element count grows, DefaultAllocator stamps the allocator id current at construction, and neither the growth nor the pool is visible at the use site. There is no wrapper here to put a ceiling in — that is what an alias is. Each shape's consequence is stated once where it bites, on HString and HVector; the container that names its allocator and allocates the exact element count is Array. Bounded or pool-named variants would be new aliases, which is a module decision, not a documentation one
