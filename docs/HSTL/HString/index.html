HString

Engine/HSTL/HString.h namespace hbe 3 aliases 1 std::hash specialization std::basic_string on an engine allocator — a different type from std::string, not an alias for it

Class description

There is no class here. HString.h declares three type aliases and one std::hash specialization; every string operation is the standard library's, unchanged. What the header actually changes is the allocator, and that single change is the whole reason the alias exists: an HString takes its storage from the engine's memory system instead of from the global operator new.

The consequence a caller meets first is that HString is not std::string. It is std::basic_string<char, std::char_traits<char>, hbe::DefaultAllocator<char>>, a distinct type: no conversion exists between the two in either direction, and the codebase crosses between them only through const char* — a const char* constructs an HString, and c_str() hands one back.

The allocator is where the memory comes from, and it is decided once, at construction. DefaultAllocator<char>'s default constructor stores MemoryManager::GetCurrentAllocatorID() in the allocator object, so an HString records whichever allocator scope was open at the moment it was built — not the one that is open when it next reallocates. Two HStrings built in different scopes draw from different pools and are not allocator-equal, because DefaultAllocator::operator== compares those stored ids. The same header that supplies it warns about exactly this: "It should be careful to use this when the current allocator is stack allocators."

A string that outlives the scope it was built in keeps a stale allocator id. Nothing re-stamps DefaultAllocator::allocatorID after construction, so the deallocation at destruction is routed to whatever allocator now holds that id — reused id, wrong pool. HString is therefore safe as a permanent member and unsafe as a long-lived copy of something built inside a temporary scope. That is the allocator's contract, not this alias's; it is recorded on Memory.

One branch of that contract is worth knowing before you measure anything. DefaultAllocator::allocate short-circuits to malloc when the stored id equals MemoryManager::SystemAllocatorID, bypassing MemoryManager entirely. Built outside any explicit scope, an HString is therefore system-heap memory that the engine's statistics never see; the accounting only happens when a non-system allocator is current at construction.

The name says what it is for; nothing in the repository uses it — see Coverage
Copying an inline-pool string asserts, in every configuration where Assert is compiled. InlinePoolAllocator declares its copy constructor as InlinePoolAllocator(const InlinePoolAllocator&) : InlinePoolAllocator() { Assert(false); } — it builds a fresh pool rather than copying, then fires the assertion. Assert is active in Debug and Dev, silent in Release, where the copy quietly produces an independent second pool. The standard specifies that get_allocator() returns the allocator by value, so that call alone is enough to reach it, and a container is free to copy its allocator elsewhere too. In other words: use HInlineString and HInlineVector in place, by reference, and do not put them in a container that copies elements. See Memory for the allocator itself.

Class methods

None, and none is possible: an alias has no members of its own. Every std::basic_string member — size, c_str, append, reserve, the iterators — is available with the standard's contract, which is the point of the layer. A name that standard-library code already defines has no page here, so this page has no method pages by design rather than by omission.

Non-member helper functions

One, and it is the only thing in the module that changes behaviour rather than storage. HString.h specialises std::hash for hbe::HString, in namespace std, and marks the specialisation final: 

template<>
struct hash<hbe::HString> final
{
        [[nodiscard]] std::size_t operator()(const hbe::HString& obj) const noexcept
        {
                auto text = obj.c_str();
                constexpr size_t Djb2Seed = 5381;
                size_t hashCode = Djb2Seed;

                while (*text != '\0')
                {
                        size_t ch = *text;
                        ++text;
                        hashCode = ((hashCode << 5) + hashCode) + ch;
                }

                return hashCode;
        }
};

This is djb2: the seed 5381, named Djb2Seed in the header so the value carries a role, then hashCode * 33 + ch per character. It is the hash ConfigFile keys run on — its TMap is HUnorderedMap<TString, TString> and HUnorderedMap's THash defaults to std::hash<TKey>, which resolves to this specialisation. Three properties of it follow from the code above:

What the code doesWhat follows for a caller
Walks c_str() to the first '\0' Characters after an embedded null do not affect the hash, while operator== compares the whole string — so "a\0b" and "a\0c" hash identically and compare unequal. A legal collision, not a bug in the hash, but it is the string's length that is being ignored, not a pathological input
Widens with size_t ch = *text;, where text is a const char* Where char is signed, a byte at or above 0x80 sign-extends to a huge size_t; where it is unsigned, the same byte widens to 0..255. char signedness is set by the ABI, not by this header, so two platforms can give different hashes for one non-ASCII string. The values are stable within a platform, which is all any in-process hash map needs
Takes the string by const reference and returns std::size_t, marked noexcept Nothing surprising: it is usable as an unordered-container key and cannot throw out of a rehash

There is no matching specialisation for HInlineString or HInlinePathString — each is a different std::basic_string specialisation, so std::hash is not defined for them and one cannot be used as an unordered-container key without passing a hash of your own as THash.
