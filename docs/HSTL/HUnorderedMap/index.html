HUnorderedMap

Engine/HSTL/HUnorderedMap.h namespace hbe 1 alias, 0 functions std::unordered_map on the default allocator — one alias, four template parameters, no inline-pool variant

Class description

There is no class here. HUnorderedMap.h declares exactly one alias, and it is a pure rename of a std::unordered_map specialisation: no wrapper, no member, no free function, no behaviour added. Everything about lookup, rehashing, node and iterator stability, and operator[]'s default-insertion is the standard library's, because the header implements none of it.

What the alias pins down is the allocator, and it pins it to the map's value type rather than to either of the types you pass in: hbe::DefaultAllocator<std::pair<const TKey, T>>. DefaultAllocator's default constructor stores MemoryManager::GetCurrentAllocatorID(), so a map's nodes come from whichever allocator scope was open when the map was constructed — the same rule HVector carries, with the same consequence that the choice is made once and a later insertion does not revisit it, and the same malloc fast path when the system allocator is current.

Unlike its two siblings, this header exposes its remaining template parameters instead of hard-coding one shape: THash and TPred are yours, defaulted to the standard pair. That is the difference that decides whether a key type works at all — the default is std::hash<TKey>, and a key whose hash the standard does not define cannot be used until you pass one. Both live uses in the engine are specialisations supplied elsewhere: 

// Engine/Config/ConfigFile.h
using TString = HString;
using TMap = HUnorderedMap<TString, TString>;

From Engine/Config/ConfigFile.h

// Engine/Log/Logger.h
using TLogFilter = std::function<bool(ELogLevel)>;
using TFilters = hbe::HUnorderedMap<StaticString, TLogFilter>;

From Engine/Log/Logger.h

ConfigFile::TMap hashes on the module's own std::hash<hbe::HString> (documented on the HString page); Logger::TFilters hashes on std::hash<hbe::StaticString>, specialised in Engine/String/StaticString.h and belonging to String. One alias, two key types, two hash functions, neither of them named at the use site.

Class properties

The alias as Engine/HSTL/HUnorderedMap.h spells it, on one line as the header does. An alias owns no members, so the row is the alias and the cell states the difference from std::unordered_map.

NameDeclarationWhat it means
HUnorderedMap template<class TKey, class T, class THash = std::hash<TKey>, class TPred = std::equal_to<TKey>>
using HUnorderedMap = std::unordered_map<TKey, T, THash, TPred, hbe::DefaultAllocator<std::pair<const TKey, T>>>;		 alias template A pure rename of that specialisation. The allocator argument is the map's value type, std::pair<const TKey, T>, not TKey and not T — the pair is what a node holds, and it is the type whose size the allocator multiplies by the count. DefaultAllocator also declares a nested rebind, which is what lets the container obtain the same allocator for storage that is not a value; a map allocates bucket arrays as well as nodes, so the allocator you see named here is not the only instantiation the map ends up using. See Memory: allocators
There is no inline-pool member of this family. HUnorderedMap.h includes only Memory/DefaultAllocator.h, while HString.h and HVector.h each include InlinePoolAllocator.h too and publish a second alias from it. So there is no HInlineUnorderedMap: the naming pattern is not a promise. A map whose memory must come from a specific pool is a HashMap or a new alias, not a variant of this one.
Iteration order is the hash's order, and the hash is the module's own. Code that walks a ConfigFile's pairs sees them in bucket order: neither file order nor alphabetical. That is not a defect in the map: it follows from std::unordered_map plus HUnorderedMap<HString, HString> plus this module's std::hash<HString>. A caller that needs an order has to sort after reading, and any output that a test compares line by line has to do the same.

Class methods

None, and none is possible: an alias has no members. Every std::unordered_map member is present with the standard's contract — find, insert_or_assign, operator[], emplace, reserve, the bucket interface, the iterators — and none of them is engine-specific, so none has a page here. This page has no method pages by design, not by omission. The engine's own hash table, whose contracts are engine-defined, is under Container.
