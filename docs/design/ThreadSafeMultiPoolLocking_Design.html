Thread-safe multi-pool locking design

Five candidate replacements for the single mutex in ThreadSafeMultiPoolAllocator, decided by the one question every design has to answer first
Scope. This document owns the design reasoning behind the locking model of Engine/Memory/ThreadSafeMultiPoolAllocator.h: what the lock is bought with, how a deallocation locates its bank, and which primitive is strong enough to retire the mutex. The defects found while reviewing that class are recorded in JOURNAL.md under 2026-10-05, and the allocation and ownership contracts belong to the Memory module page. Nothing here is implemented. The measurement that settles the choice has now run: the gate section holds Dev-build figures from the four testlets, and every other performance claim is still labelled predicted.

What the current design pays for

One std::mutex guards the whole bank array. Two costs follow from that single decision, and only one of them is the mutex:

The comparison against std::malloc is the uncomfortable one. The platform allocator already keeps per-thread caches, so a design whose fast path touches a single shared word cannot overtake it even uncontended, which is the reason this document looks at ownership rather than at cheaper locks.

The deciding question: how a free finds its bank

Allocate can pick a bank from the requested size. Deallocate(void* ptr, size_t size) has to recover that choice, and today it recovers it by asking every bank whether the pointer is its own. Every option below is really an answer to this question, so it is settled first.

WayCostWhat it has to assumeVerdict
Scan every bank with IsMine, as todayO(banks) per freenothingMust go. It is the second of the two costs above
Recompute the size class from sizeO(1)that the caller passes the same size it allocated withUnsafe today. JOURNAL.md records operator delete(void*, align_val_t) passing its alignment where Deallocate expects a size, and the suite contains calls of the form Deallocate(ptr, 0). Trusting the argument inherits both
Eight-byte header per block holding class and ownerO(1), plus eight bytes taken from every blocknothingRejected: GetBlockSize() stops meaning usable payload, which is a promise to callers
Address-indexed chunk map: each bank is split into chunks holding a power-of-two block count, a chunk header sits at a masked address, and a published sorted range table maps an address to a bankone masked load and a binary search over banksnothingChosen. Class and owner both come from the address, and a reader takes no lock

There is a second, quieter problem behind the scan. The bank chosen today depends on which banks still hold free blocks, because an exhausted bank is skipped rather than grown. That is why the mapping from size to bank is not a function, and why the free path cannot recompute it. Replacing several banks per size with one bank per size grown in chunks makes the mapping a function again, and the scan loses its reason to exist even where the address table is present only as a fallback.

Five designs compared

A compare-and-swap proves only that a word still reads as expected, so a loop built on it retries under contention and inherits the ABA hazard. A fetch_add makes no such assumption, which is why it is wait-free and immune. That distinction, not the presence or absence of a mutex, is what separates the options.

Two honest readings of that table. First, calling B and D lock-free does not make them fast when shared, because both funnel frees onto one cache line: the current workload is overwhelmingly allocate then free on the same thread, so both would move work from a mutex onto a contended word. Second, only C makes the common path touch no atomic at all, which is the only condition under which this class can beat the platform allocator rather than match it. E is viable only after growth leaves the critical section, because a spin lock held across a one megabyte parent allocation is worse than the mutex it replaced.

Recommended target design

Option C, built on the address-indexed chunk map from the deciding question. Blocks belong to chunks, chunks belong to a size class and to the thread that claimed them, and a block's owner is read from the chunk header rather than stored per block. 

Allocate(n)
  class  = f(n)                              pure function of size, no bank state read
  shard  = classSlots[class][streamIndex]    thread local, padded to a cache line
  if shard.freeHead is not empty             NO ATOMIC: private last-in-first-out pop
       take that block
  else if shard.inbound has a block          cross-thread returns, drained by the owner alone
       take that block
  else ClaimChunk(bank[class])               rare: mutex or compare-and-swap, this is growth

Deallocate(ptr, n)
  chunk  = address of ptr AND NOT (chunkBytes - 1)     chunkBytes is a power of two
  class  = chunk header class
  owner  = chunk header owner
  if owner is this stream                  NO ATOMIC: push onto that owner's private list
  else push onto owner.inbound             one compare-and-swap, the cold path
MechanismWhy it is safe here
Tagged head: a uint64_t holding a 32-bit block index and a 32-bit push counterAn index returning to a previous position cannot return with a previous version, so the ABA pattern cannot be constructed. The whole tag fits one word, so no 128-bit compare-and-swap is needed and no new platform guarantee is asked for
Chunk header located by masking the block addressNo per-block metadata, so GetBlockSize() keeps meaning usable bytes
Chunks hold a power-of-two block countMaking the owner and class reachable by one mask rather than a search. numberOfBlocks per bank stays a 32-bit index, so the bank plan needs an assertion that it fits
Chunks are about 64 KiB of target volume, clamped to a power-of-two block count, minimum eight blocksOtherwise a 4 KiB class leases 256 KiB per thread per class. This is the only way the design can lose, and it is bounded by a rule rather than by hope
Banks grow in chunks and never shrink while the allocator livesBanks are released only by the destructor, which is what removes any need for epoch or hazard-pointer reclamation. Individual blocks are recycled, so the shared head still needs the tag
Foreign returns land on the owner's inbound list and the owner drains itKeeps the cost of a cross-thread deallocation at one compare-and-swap and keeps the private list single-threaded. It is the same shape PoolAllocator already uses when it forwards a foreign pointer to its parent

The measurement that chooses between them

Specified in .Plans/PLAN_lockfree-contention-benchmark.md and implemented as four testlets in the class's own test collection. Figures below are one representative Dev-build run of EngineTest; the workload is 20,000 operations per thread over the eight fixed block sizes, timed as one allocate plus one free per operation, measured as direct calls on the allocator object so the MemoryManager proxy dispatch is excluded from every figure.

Three caveats on these figures, stated rather than buried. First, the M2 private-pool pass was pre-sized to 5,000 blocks per size class precisely so that no bank grows inside its timed region, while the shared column grows banks during its measurement. Part of the 67.5 times therefore measures the absence of growth rather than the presence of sharding, and M4 shows growth is expensive, so the honest reading is that sharding and pre-sizing together buy 67.5 times and the split between them is not yet known. Second, the benchmark was repeated in Release, and several figures moved by more than a quarter between runs:

The ratios move because their denominators are 1 to 3 nanoseconds, while the shared column and the latency tail stay put. What survives repetition is the shape: efficiency collapses under sharing, and a private pool is far faster than a shared one. What does not survive is any individual ratio, so no number in this document is a target to hit. Absolute nanoseconds are not comparable across configurations either, since the Dev build measured 24.6 ns uncontended where Release measured 41.8 and then 30.3, so only ratios taken inside one configuration carry meaning. Third, the workload is 20,000 operations per thread on one machine. That is enough to show a collapse and enough to show headroom; it is not enough to rank two options against each other by a factor of two.

Taken together the four measurements settle the choice in the comparison on the reproduced shape rather than on any magnitude. M1 says the mutex is the cost and not the pool logic, and the shared column is the stable measurement that carries that claim. M2 says thread sharding has headroom that is large in every run of both configurations, so option C earns its implementation risk while option B, which only moves work from a mutex onto a contended word, does not. M3 says a cross-thread free costs about the same as a same-thread one, so the return mechanism C depends on is affordable. M4 says bank growth has to leave the critical section whatever is chosen, which is a prerequisite rather than a design option, and it is the most reproducible of the four.

What this document does not own

The class has no reference page. docs/Memory/index.html is the only page the module has, so no per-method contract page exists for ThreadSafeMultiPoolAllocator. The behaviour of Allocate, Deallocate and PrintUsage as a caller must obey it is a contract that page will own; this document describes only the locking design behind them.

No defect list, no implemented design. Defects and the repeated-run spread live in JOURNAL.md, the contention figures are in the gate section and are reproducible through the class's own test collection, and the tree still contains the mutex described in the first section.

Alignment policy, allocator selection between engine allocator types, and the manager's registration and statistics contract are not described here. See docs/AllocatorGuide.md and Memory manager internals.
