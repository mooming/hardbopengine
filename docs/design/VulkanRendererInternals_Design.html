Vulkan renderer internals design

The VulkanRenderer reference pages own what a caller depends on; this document owns the implementation decisions behind them — the ordering constraints the initialisation sequence encodes, the Vulkan quirks the code works around, and the failure-path protocol that keeps the frame cycle intact. Every claim here was read from Engine/Renderer/Vulkan/VulkanRenderer.cpp or Engine/Renderer/Vulkan/VulkanCapabilities.cpp; where a reference page already owns a claim, this document links there instead of restating it.

The surface exists before the device is picked

CreateSurface runs before PickDevice because queue-family support is queried against the surface itself: vkGetPhysicalDeviceSurfaceSupportKHR needs the VkSurfaceKHR, so a device that cannot present to this window cannot be picked before the window's surface exists. The pick additionally requires a graphics queue that can present — which is also why the pre-device probe in VulkanCapabilities cannot do the pick: it has no surface at all.

No optional features are requested

CreateDevice requests no VkPhysicalDeviceFeatures at all: asking for one the driver does not support fails vkCreateDevice outright, and the simple mesh pipeline needs none. VK_KHR_swapchain is the one device extension enabled per device — without it the loader leaves the swapchain entry points null and vkCreateSwapchainKHR fails at use.

Where real capability data first exists

The physical device is valid from CreateDevice onwards, which makes that the first point where real capability data exists; QueryCapabilities fills the cached descriptor once there, so GetCapabilities is a copy, not a query.

Format, present mode and extent

Three choices in CreateSwapchain: the surface format matches the CAMetalLayer's BGRA8Unorm when it is offered, because that is what the macOS surface is configured as; FIFO is the only present mode Vulkan guarantees to exist, with MAILBOX preferred when the driver offers it; and currentExtent arrives as 0xFFFFFFFF when the surface sizes itself from the window, in which case the window's content rect decides — the fact GetExtent exists to report.

Both render-pass descriptions must be contiguous

CreateRenderPass builds its attachment descriptions in one array because pAttachments is indexed by reference from the subpass description, not bound per element — the colour and depth attachments must stay contiguous in the order the subpass indexes them.

The fence release protocol on the failure paths

Three rules keep the frame cycle intact when a frame does not complete:

  • Fences start signaled — frame 0 must not block on work that was never submitted.
  • When the swapchain is lost, EndFrame still releases the fence it just reset; otherwise the next BeginFrame waits on a fence nobody will signal. Recreating the swapchain in place is the real fix and is tracked as a follow-up.
  • When the submit itself fails, or nothing was drawn this frame, the fence is released through an empty submit so the per-frame cycle still turns.

Vertex memory is host visible, on purpose, for now

CreateVertexBuffers maps host-visible memory directly because the mesh is written once from the CPU and never modified per frame. A device-local copy with a staging transfer is the right long-term shape and is tracked as a follow-up.

The teardown order

Destroy releases image views before the images and device memory they alias — a VkImageView is a handle into the image, so reversing the order destroys a live view of a dead image. The command pool frees its command buffers when destroyed, so they have no separate release.

The pre-device probe does not pick the device

QueryDefaultDeviceCapabilities takes the first enumerated device because its question is about the machine, before any renderer exists. Actual device selection stays with PickDevice, which additionally requires a graphics queue that can present to the real surface — something the probe has none of.

Why the non-Apple surface stub must stay excluded on macOS

The CreateMetalSurface stub in VulkanRenderer.cpp is guarded out on macOS because the real implementation lives in VulkanRenderer.mm. If both translation units defined the symbol, the linker would satisfy it from VulkanRenderer.cpp.o and never pull VulkanRenderer.mm.o out of the static archive — the Metal surface would silently never run.
