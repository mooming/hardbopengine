Unit-test selection

How __UNIT_TEST__ reaches the tree, what a test body may vary per configuration, and the three places a test was once wrong without failing
Scope. This document owns the invariants behind the test bodies inside Engine/ and the way their defining macro reaches them. The harness itself — TestCollection, Testlet, TestEnv — is on the Test module page, and what Assert does when it is live is on the Core page.

The suite is compiled per module, not per executable

Each module's own sources carry its test bodies behind #ifdef __UNIT_TEST__ — Engine/Core/TaskSystem.cpp, Engine/Memory/DefaultAllocator.cpp, Engine/Container/LinkedList.cpp and the rest — while Engine/Test/UnitTestCollection.cpp registers the resulting classes. The definition therefore has to be tree-wide. The proof is the link: a build in which only Applications/EngineTest/TestMain.cpp saw the macro produced libTest.a with undefined hbe::BufferTest, hbe::StringTest and hbe::VectorTest constructors and vtables while libCore.a contained no TaskSystemTest at all.

So the macro arrives as a per-configuration definition of the whole tree, named in precompileDefinitionsDebug and precompileDefinitionsDev in .project.config, and EngineTest in Debug or Dev runs the suite whether or not the build was configured with build.sh -test. Applications/EngineTest/TestMain.cpp keeps its #else branch — a Release build prints that it verified nothing and exits non-zero, because an exit status that means "passed" while nothing ran is worse than a failure. See Build macros for why a target-scoped definition cannot do this job.

What a test varies with the configuration, and what it must not

LinkedListTest::Prepare() uses one element count in every configuration. It used to double that count when the build was not a Release build, which meant the suite a developer ran covered an eighth of the elements the Release CI run covered — the same test name, a different test. That was the only place in the suite where the build configuration changed what was exercised rather than how loudly a failure reported, and it is the reason ComponentSystemTest's workload split is the exception worth keeping: a smaller iteration count in a build where every step is checked is a runtime decision, while a different data set is a different test.

The rule. A test body may run less of the same test in a checked build. It may not run a different test. When a size must vary, the variation belongs in the suite's own configuration, not in a build-configuration macro.

An assertion in a test body is live in two configurations, not three

Engine/Renderer/RendererTest.cpp asserts that VulkanRenderer::Initialize rejects a null window — the surface is built from the window and queue family support is queried against that surface, so a null window cannot produce a renderer. The assertion once said the opposite and survived, because the configuration in which it was wrong was the one in which Assert compiles to nothing: a Release build reported the testlet as passed no matter what the code did.

The consequence for anyone editing a test body is that a passing Release run is not evidence about an assertion at all. Assert is compiled in under #if !RELEASE_BUILD, so the proof of an assertion inside a test is a Debug or Dev run of EngineTest; what a Release run proves is only that the code compiles and does not crash. See Assertion design for the parity rule that keeps both branches declaring the same overloads.

Field-by-field comparison where memcmp would compare padding

Where a test compares a descriptor that is a bit-field struct holding a fixed array, it compares field by field rather than with memcmp. A bit-field struct carries padding the compiler chooses, so an object-wise comparison can report a difference between two values the API considers equal — a false failure whose cause is not in the code under test.

Unknown must be reported as unknown

A renderer that has no device yet reports its capabilities as unknown. An uninitialised renderer used to answer 4096/16/16 — plausible numbers that looked as though the hardware had been asked — and a caller could not distinguish "the device said so" from "nobody asked". The test asserts the unknown answer, and an implementation that returns a comfortable default instead is wrong even when every other field is right.

What this document does not own

The registration order of the suite is not recorded here. Engine/Test/UnitTestCollection.cpp lists the collections, and TestEnv::PrepareTestlets fixes the order they run in; this page documents why the bodies are compiled where they are, not which ones exist.

No page yet owns LinkedList or VulkanRenderer in full. docs/Container/LinkedList/ is missing method pages that docs_coverage.py reports, and the Vulkan wiring lives in Renderer. Neither gap is paid by this document.
