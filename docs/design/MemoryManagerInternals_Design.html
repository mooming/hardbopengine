Memory manager internals

The three error paths of MemoryManager that answer instead of failing, and what PROFILE_ENABLED decides about the answer
Scope. This document owns the invariants behind Engine/Memory/MemoryManager.cpp's error and diagnostic paths. Allocation and deallocation contracts, ownership, and the proxy interface belong to the Memory module page and to AllocatorProxy; PROFILE_ENABLED itself is a Core build flag, documented where the profiling counters live.

What an allocator name is worth

MemoryManager::GetAllocatorName answers in three different ways, and only one of them is a name:

ConditionAnswerMeaning
id fails IsValid"Null"The id was never registered, or is the invalid id
PROFILE_ENABLED onallocators[id].stats.nameThe name registration was given
PROFILE_ENABLED off"Unknown"Names are not stored at all in this configuration

A caller printing allocator identity therefore learns nothing about the allocator in a build without profiling, and "Unknown" is not a name that some allocator happens to have. "Null" and "Unknown" are two different facts and must not be collapsed into one "no name" case by a caller.

What registration records

RegisterAllocator takes the allocator pointer, a name, whether it is inline, its capacity, and the allocate and deallocate function pointers. A null name becomes "None" rather than an error, so the registration never fails on the name alone. Under PROFILE_ENABLED the name, the inline flag and the capacity are stored in the allocator's statistics and the registration takes statsLock; without it the recording lambda does not capture them at all, so the same call records only the three things needed to route allocations. The return value is the assigned id, and a registration whose id came back invalid is caught by the Assert on the way out — which is live in Debug and Dev only, so a Release build records the failure in the Info log line and returns the id it was given.

An invalid id answers with a dummy proxy

GetAllocatorProxy is the path every allocation crosses, and it does not fail: an id that fails IsValid logs an Error and returns a default-constructed AllocatorProxy held as a function-local static, re-constructed on each call. The intent is that a bad id cannot index allocators out of bounds; the consequence a caller must know is that the returned proxy is real and usable-looking, so the allocation that follows it does not fail where the mistake was made. A bad id therefore surfaces as a log line plus work that goes somewhere other than the allocator named, not as a crash at the call.

Two properties of that dummy are not decided anywhere. The static object is shared by every thread that asks with a bad id, and it is placement-reconstructed while another thread may be inside a call that received it, so the dummy is not a thread-safe object. And because a default-constructed proxy routes nowhere, an allocation through it neither returns an error nor reaches the system allocator — it is dropped. Recorded here rather than answered, because the fix is a policy choice: fail loudly, or route the dummy to the system allocator so the work at least happens.

Where a checked build stops instead of continuing

Three diagnostics stop the process in a non-Release build and only log in a Release build: an allocator used from a thread other than the one that owns it, an allocator destroyed while its statistics still report usage > 0, and a null-length or otherwise invalid request. Both halves are compiled together — the Log call runs in every configuration and the debugBreak() that follows it is guarded by #if !RELEASE_BUILD — so the report is never the thing that was switched off. The same guard covers the verbose dump of the multi-pool configuration table and the ordering check over each block-size run in Engine/Memory/MultiPoolConfigCache.cpp, which is a fatal error in a checked build and silence in a Release one.

Allocation can also be forced to the system allocator independently of the configuration, by FORCE_USE_SYSTEM_MALLOC: when it is true, both allocate and deallocate paths replace the requested id with SystemAllocatorID before validating it, so a profiled build can be run against the system allocator without changing a single call site.

What this document does not own

The class has no reference page. docs_coverage.py reports that Engine/Memory/MemoryManager.h has no docs/Memory/MemoryManager/index.html, so no per-method contract page exists. The three behaviours above are contracts of GetAllocatorName, RegisterAllocator and GetAllocatorProxy and are shelved here until that page is authored; when it is, they move to the method pages and this document keeps only the invariants.

Allocator selection policy, alignment rules and the pool geometry are not described here. Only the error and diagnostic paths of the manager are.
