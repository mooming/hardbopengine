Memory manager internals

The manager's error policy — answer instead of failing — and the build flags that decide what a report is worth
Scope. This document owns the invariants behind Engine/Memory/MemoryManager.cpp's error and diagnostic paths — the patterns that hold across several methods at once. The per-method contracts, including the three behaviours that used to be written here, live on the method pages of MemoryManager. Allocation and deallocation contracts, ownership and the proxy interface belong to the Memory module page; PROFILE_ENABLED itself is a Core build flag, documented where the profiling counters live.

One error policy, nine different answers

Across every entry point that receives a TAllocatorID, the manager's policy is identical in shape and startling in detail: validate, then answer instead of failing. Nothing in the class throws, returns an error code or refuses a call outright because an id is out of range — each substitutes something, and what it substitutes is decided per method. IsValid carries the table of those outcomes. The invariant this document exists to state is the one no single method page can: a bad id is almost never fatal, and its only trace is a log line, which in a build of this repository (MEMORY_LOGGING_ENABLED = 0) means the trace is nowhere.

Two of those answers are design rather than accident, and both are reasons a defect reproduces as wrong data rather than as a crash:

  • On the dispatch path an invalid id is rewritten to SystemAllocatorID and the request proceeds, so a mis-scoped allocation succeeds from the wrong place instead of failing at the right one (Allocate, Deallocate).
  • On the inspection path an invalid id answers with a stand-in that is type-indistinguishable from a real answer — "Null" from GetAllocatorName, a zeroed record from GetAllocatorStat, a default proxy from GetAllocatorProxy.

Where a checked build stops instead of continuing

Three diagnostics stop the process in a non-Release build and only log in a Release build: an allocator used from a thread other than the one that owns it, an allocator destroyed while its statistics still report usage > 0, and a null-length or otherwise invalid request. Both halves are compiled together — the Log call runs in every configuration and the debugBreak() that follows it is guarded by #if !RELEASE_BUILD — so the report is never the thing that was switched off. The same guard covers the verbose dump of the multi-pool configuration table and the ordering check over each block-size run in Engine/Memory/MultiPoolConfigCache.cpp, which is a fatal error in a checked build and silence in a Release one.

Allocation can also be forced to the system allocator independently of the configuration, by FORCE_USE_SYSTEM_MALLOC: when it is true, both allocate and deallocate paths replace the requested id with SystemAllocatorID before validating it, so a profiled build can be run against the system allocator without changing a single call site.

What this document does not own

The per-method contracts do not live here. Engine/Memory/MemoryManager.h now carries its address — docs/Memory/MemoryManager/index.html — and every declared name has a page, so anything that is a contract of one method belongs there. This document keeps only what spans methods: the error policy above, the checked-build-versus-Release pattern below, and the generalisation each retired section was an instance of. Where a page and this document seem to disagree, the page is the one that read the function.

Two findings are recorded on pages, not here, so they are not lost by the move. A profiled build adds Config::MemCapacity to the engine-wide total twice — once unconditionally in RegisterSystemAllocator and again inside the PROFILE_ENABLED block — and ReportDeallocation logs a usage underflow and then performs the subtraction anyway, wrapping an unsigned figure. Both are stated with their consequences on those pages.

Two questions still have no answer anywhere. What a caller holding a live block must do when its allocator is deregistered, and what a registration attempted after shutdown is meant to achieve (the free-slot pool contains slot 0 by then, and slot 0 is the one proxy whose id was never written). Neither is answered by any source, comment or test; they are named as omissions in the class Coverage table, and this document does not guess at them either.

Allocator selection policy, alignment rules and the pool geometry are not described here. Only the error and diagnostic paths of the manager are.
