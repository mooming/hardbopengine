Build macros

Every configuration names itself with one macro set to 1, written on its own compiler-flag line, so a definition cannot arrive by inheritance
Scope. This document owns where DEBUG_BUILD, DEV_BUILD and RELEASE_BUILD come from and what a source file may conclude from seeing one of them. What Assert and FatalAssert do is on the Debug section of the Core page and in Assertion design; what the generator does with a BuildConfig header is that class's own reference.

One macro per configuration, set to 1

MakeBuild's template writes exactly one of the three onto each configuration's compiler-flag line, in every generated CMakeLists.txt. A configuration therefore carries its own name, and the three are mutually exclusive and exhaustive: exactly one is defined in any translation unit.

ConfigurationMacroFlag line it is written ontoFlags on that line
DebugDEBUG_BUILD=1CMAKE_CXX_FLAGS_DEBUG-g -O0
DevDEV_BUILD=1CMAKE_CXX_FLAGS_DEV-g -O1
ReleaseRELEASE_BUILD=1CMAKE_CXX_FLAGS_RELEASE-O3

Why each flag line reads only its own variable

The Dev line used to read ${CMAKE_CXX_FLAGS_DEBUG} and append -O1. That is CMake's variable semantics — a variable is whatever the enclosing scope last set — and not a rule about configurations. Its cost was that every definition written for Debug silently became a Dev definition too, and there was no input file that could say otherwise: a project could not define a macro for Debug alone.

Each of the three lines now reads only the variable it assigns, so the flag sets are independent. Dev still gets -g -O1 and Debug still gets -g -O0: reading the Debug line produced -g -O0 followed by -O1, and the later -O wins, so spelling the result out changes no effective flag. Only the definitions stopped travelling between configurations.

What the source writes

A file that wants a configuration asks for it: #if DEV_BUILD. A file that wants "not the shipping build" writes #if !RELEASE_BUILD, which is the pair Debug and Dev — the engine's assertion guard, thread-identity tracking, and every diagnostic that a shipping build must not pay for. Both forms are correct and they are not the same question; the second is written wherever a Dev build must behave like a Debug build, and the first wherever it must not.

An undefined macro evaluates to 0 in a #if, so #if !RELEASE_BUILD holds in Debug and Dev without either defining RELEASE_BUILD as false. That is also why the trio is defined to 1 rather than merely present: a reader of #if DEV_BUILD sees a value test, not a name membership test, and cannot accidentally write the inverted question with #ifdef.

Definitions a project adds per configuration

A definition that is not about the configuration itself — the engine's __TEST__, which gates the test bodies each module carries — comes from precompileDefinitionsDebug, precompileDefinitionsDev or precompileDefinitionsRelease in .project.config. The generator appends them as -D tokens to the matching flag line, so they reach every module while belonging to one configuration. The two lists are independent by the rule above, so a definition wanted in Debug and Dev is written twice, which is the point: the pair is stated rather than assumed.

Writing such a definition into one module's customCMake.txt does not work. Those lines are appended after add_subdirectory, so a directory-level definition there reaches no child, and a target_compile_definitions there reaches only that module's own sources — which for __TEST__ means the test executable compiles its half of the suite and then fails to link against libraries that compiled the other half out. The same trap is why build.sh -test passes the defines on the configure command line rather than through a target, and why it remains the only route that puts them into Release.

How a define is proved rather than read

A preprocessor definition is per-translation-unit state, so the proof is counted in the generated ninja files rather than read off a CMakeLists.txt, which says what was intended rather than what was applied: 

grep -c 'DRELEASE_BUILD' build/CMakeFiles/impl-Release.ninja   # every translation unit
grep -c 'DDEV_BUILD'     build/CMakeFiles/impl-Dev.ninja
grep -c 'D__TEST__'      build/CMakeFiles/impl-Release.ninja   # 4: Engine/Test's own sources only

From docs/BuildSystem.md, which repeats the commands as the build-system gate

The macro this replaced

A single macro, __DEBUG__, used to be written onto the Debug flag line only, and Dev received it because its flags were read from Debug's. Three things follow from that history and are worth keeping, because each is a claim a page elsewhere still makes in the old vocabulary:

  • Every site that says #if !RELEASE_BUILD is the same set of configurations the old macro covered, so the rename carried no behaviour change — the proof was a build and test run of all three configurations.
  • It was written by hand into a generated CMakeLists.txt before the generator emitted it, and a hand-edit is erased by the next generation pass, silently. That is why both the build macros and the per-configuration definitions are generator inputs and nothing else.
  • The name invited the wrong reading. "Debug" described a configuration that also happened to be the one Dev inherited, so a reader could not tell a Debug-only effect from a not-Release one. ComponentSystem's test body is the case that mattered: it used the guard to pick a smaller workload, which is a configuration question wearing a diagnostic name.

A second macro followed the first out. __UNIT_TEST__ and __TEST__ were defined together in every configuration that defined either, and no source ever asked __TEST__ a question: all 127 guards read __UNIT_TEST__. So the pair was never two questions, only two names for one question, and the dead half let a page claim something was compiled when it was not — docs/RunningTests.md and README.md both said -D__TEST__ built the test bodies while it in fact built nothing. __UNIT_TEST__ is now removed and __TEST__ carries the meaning alone. The change is a rename of the live macro onto the dead one's name, proven by the flag count moving from __UNIT_TEST__ to __TEST__ without either configuration's number changing: 455 tokens in Debug and Dev, 4 in Release, before and after.

What this document does not own

The generator's own documentation is in the tool. Tools/MakeBuild/README.md lists the .project.config keys and the flags each configuration line carries. Nothing here restates that table, and a change to the template belongs there first.

No page yet owns MemoryManager, StringUtil or LinkedList as classes. docs/Memory/ and docs/String/ hold a module index only, and docs/Container/LinkedList/ is incomplete, which docs_coverage.py reports as a blocker for those headers. That debt predates this document and is not paid by it.
