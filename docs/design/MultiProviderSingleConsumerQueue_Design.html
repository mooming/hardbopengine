Multi-provider single-consumer queue design

How Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.h keeps a queue lock-free on the push side and lock-free-by-affinity on the pop side
Scope. This document owns the algorithm, its invariants, its memory ordering and its cost. What a caller may depend on — the meaning of a null return, who may call what, what happens on destruction — lives on the reference pages: the class page and its Push, Pop and IsEmpty.

Scope

The requirement this class serves is the one written into docs/TaskSystemRedesign.md §9: an enqueue that is lock-free where a single consumer is provable by construction, and no multi-consumer lock-free enqueue at all until profiling asks for one behind a seam. Many threads want to hand work to one thread that owns draining it. That topology — many providers, one consumer — is the whole design space this document covers; a second consumer is a different algorithm with a memory-reclamation scheme attached to it, and the guardrail says that scheme is not free enough to buy speculatively.

The second requirement is the one that decided the representation: the engine's MultiPoolAllocator is not thread-safe, and ThreadSafeMultiPoolAllocator reaches for a mutex. A queue that allocated a node per enqueue would therefore put a lock in the exact path built to avoid one. Nodes belong to the caller, which is what the View in the name advertises and what AtomicStackView already does for the same reason.

The two fields, and who may touch them

FieldWritten byRead byGuarded by
std::atomic<T*> newest Any producer (compare-exchange-weak), the consumer (exchange to null) Producers, the consumer The atomic itself; this is the only shared mutable word in the class
T* oldest The consumer alone The consumer alone Nothing, deliberately — it is thread-private state, and the single-consumer rule is its guard
T::next of a node in the producer stack That node's own producer, once, before publishing The consumer, after its acquire exchange The release/acquire pair on the publish
T::next of a node in the private list The consumer alone, during the reversal and again when it detaches a node to hand out The consumer alone Thread affinity

Every row assigns one writer to one field. That is the design: the queue is lock-free because the shared surface is a single pointer and everything else is private to whichever thread holds it.

Four invariants

#InvariantWhat it buys
1 A producer writes only the link field inside the node it is pushing, and writes it before the compare-and-swap that publishes that node No push ever reaches into a node another thread has already published, so a node the consumer has handed away can not be written by a stranger — the property that makes caller-owned storage sound
2 A node's link field is written at most once while the node sits in the producer stack The reversal can read a link and rely on it not changing underneath it, even though producers are still running
3 oldest and the chain it heads are reachable only from the one consumer thread The reversal and the detach are ordinary pointer code — no atomics, no compare-and-swap, no ABA window on the pop side at all
4 A node leaves the producer stack exactly once, and after that the container never reads it again Nothing to reclaim, nothing to defer, no hazard pointers, and no requirement that a node outlive its own pop beyond the pop itself

Invariant 1 is the one the class would lose if anyone "optimised" the publish into two steps. Exchange the head first and then link by writing the previous head's field, and a producer is writing into a node the consumer may already have returned to its owner. That is not a theoretical worry: injecting exactly that late write into this class makes ThreadSanitizer report a race on the node's link field, and drops one testlet's delivery count from 32 nodes to 1.

Where the missing lock went

The classical two-stack queue (Michael and Scott's AMQ queue) protects each of its two stacks with a lock. Here the producer half is a Treiber stack, so it needs no lock and is lock-free; the consumer half needs mutual exclusion only against other consumers, and there is exactly one consumer, so thread affinity supplies what a lock otherwise would. The reversal therefore runs as seven lines of plain pointer assignment.

The cost of that substitution is a contract instead of a mechanism. oldest is not atomic precisely because the rule is believed, and a second consumer calling Pop would race on it and hand the same node to both threads. Adding the second consumer means adding an atomic to the pop side, which in turn means a compare-and-swap loop, which in turn means the pop side can no longer hand a node away without attaching a reclamation scheme — the whole class of cost the design exists to avoid. That is why the guardrail in docs/TaskSystemRedesign.md treats a single consumer as something to be provable by construction: the type does not enforce it, and no test can catch every interleaving of a rule that is stated rather than implemented.

Memory order, one row per operation

SiteOperationOrderWhy that one
Push newest.load relaxed The value is used only as the expected operand of the compare-and-swap that follows; the synchronisation is carried by that store, not by this read
Push compare_exchange_weak success release Publishes the link field this thread just wrote, plus everything the caller wrote into the node before pushing it
Push compare_exchange_weak failure relaxed A failed attempt publishes nothing; its only effect is refreshing the expected value for the retry
ReverseNewest newest.exchange acquire Synchronises with each release publish whose link it is about to walk; without it the nodes are visible while their contents are not
IsEmpty newest.load relaxed An emptiness answer is about a moment, and no data becomes visible by reading the pointer harder

The pairing that matters is release-publish against acquire-claim. It is the same pairing AtomicStackView uses, and it is the only reason a node's payload is readable after it comes out of this queue.

Cost model

OperationShared-memory workFreedomNotes
Push One relaxed load plus one or more compare-and-swap attempts on one word Lock-free, not wait-free Retries are contention against other producers only. The retry loop is the same one AtomicStackView runs
Pop, private list non-empty None — no atomic is touched Wait-free Two pointer reads, one pointer write
Pop, refill needed One exchange, then one pass over the reclaimed batch Wait-free for the claim; the pass is proportional to the batch Amortised one pass per node per lifetime, concentrated on the call that claims the batch
IsEmpty One relaxed load and one plain read Wait-free Must read both halves; reading one is the classic wrong answer, recorded on its page

The shape of the trade against a bounded slot-array queue is worth stating plainly: a linked queue dirties a caller node's cache line per enqueue and chases a pointer per pop, which a fixed array of sequence-numbered slots does not. What the array costs in exchange is a capacity ceiling, a full condition the caller must handle, and — for the multi-consumer variants — a compare-and-swap on the pop side. For a stream that drains itself every frame, the ceiling and the full path are the more expensive of the two. No measurement of either exists in this tree yet; see Open items.

The shape that was rejected, and why

The intrusive multi-producer single-consumer queue that publishes in two steps — exchange to take the head, then write the previous head's link — was the first candidate and is the shape most engine readers will already know. Deriving it against the ownership rule turned up two consequences it cannot shed:

ConsequenceWhy it follows from the two-step publish
The queue must own a sentinel node The consumer's frontier has to be read through tail->next before the queue can tell whether an item exists, so the frontier must be memory the queue itself owns — and a view that allocates nothing cannot conjure one, so the caller would have to hand a seed node to the constructor
The newest node is unreachable until a later node arrives A node may be handed back only once its single link write is known to have landed, and the only evidence of that is a non-null link; the node at the head has no such evidence yet, so a drain stops one item short until someone else pushes

Both are properties of that algorithm rather than of this implementation, and both were found by deriving the steps before writing them — which is the reason the record is here rather than in a commit message. The chosen shape pays for its simplicity somewhere else, and that somewhere else is named on the class page's Coverage: no benchmark, and no measured call site.

What is proved, and how

The testlet set in Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.cpp is five tests, and each concurrency claim was checked by re-injecting the defect it is supposed to catch and reading the failure. A test that has never failed is not evidence.

ClaimTestletNegative control and what it did
First-in first-out per producer, one total order across producers, nothing lost or duplicated Four Producers and One Consumer Lose Nothing (4 × 1,000 nodes) Late write to a published node: reported 1 delivered of 4,000 before the deadline
A returned node is never touched by the container again A Popped Node Belongs to Its Owner and to No One Else (150 rounds × 32 nodes, producers hammering throughout) Same injection: ThreadSanitizer reported a race on the node's link field and the round stranded after one node
IsEmpty sees both halves IsEmpty Covers the Stolen Batch as Well as the Producer Stack Single-field emptiness test restored: testlet failed with its own explanation as the report
Destroying a non-empty queue releases nothing and damages nothing Destroying a Queue That Still Holds Nodes Releases Nothing None available: the test asserts the absence of an action, and an implementation that did free caller nodes would fail it as a crash rather than as a report
No data race in the algorithm as written Both stress shapes, built -fsanitize=thread against the real header Zero reports at 4,000 delivered nodes and 4,800 handoffs

One control earned a change to the tests rather than to the code. The first draft of the sole-ownership drain loop ran while (returned < nodeCount) with no deadline, and the injected defect made it spin forever: a lost node produced a hung test instead of a failed one, which is the failure mode WaitUntil exists to prevent. The loop is now bounded by a deadline and reports the round it stranded on.

Open items

ItemState
False sharing between newest and oldest Unmeasured. Both words sit in one 16-byte object; producers hammer the first on every push while the consumer reads the second on every pop, which is the textbook shape. Padding them apart is plausible and was not done, because the engine has no padding convention to follow beyond one ad-hoc reservedToCacheLine field in Engine/Core/TaskRegistry.h, and adding one without a number would be decoration. The measurement that decides it is a push-rate comparison with and without the gap
Throughput against AtomicStackView and against a mutex-guarded queue Not run. PerformanceAnalysis.md is where such a figure would go, and no claim in this document is stated as a measurement that was not taken
Adoption on a task stream Deliberately out of scope. Placing this queue in the enqueue path is a change to the task system with its own profiling question attached, per the guardrail it would satisfy
