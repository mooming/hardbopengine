Assertion design

The __DEBUG__ guard is a compile-time switch with two branches that must be kept identical — and the build break that taught the rule
Scope. This document owns the invariants that Engine/Core/Debug.h must preserve across its configurations. What Assert and FatalAssert promise a caller — when each is active, what they print, that they abort — is on the Debug reference section, and the project rule that a message must precede any assertion is in docs/CodingStandards.md.

Both branches of the guard must agree

The __DEBUG__ and #else branches of Debug.h must declare exactly the same overloads, with the same exception specification. That is a structural requirement, not a style preference: the call sites are written once and compiled against whichever branch the configuration selects, so a difference between the branches is invisible until the other configuration is built.

The rule exists because it was broken. The release branch used to demand a const char* as the second argument, so a message assembled from any other type compiled under __DEBUG__, ran for days, and then broke the Release build. A mismatch of noexcept alone is enough to do the same damage by a different route: it flips std::is_nothrow_* traits between configurations, so code that is well-formed in one build is rejected in another without a single line of it changing. Both branches therefore say noexcept.

The failure mode is timing, not compilation. The bug above survived because the configuration that was wrong was the one nobody was running. Any change to one branch of this guard is a change to both, and the proof is a build of every configuration — which is why the engine's standards gate builds Dev, Debug and Release rather than the one being edited.

What a Release build evaluates

In a Release build the arguments of Assert are unnamed and unused on purpose: the call inlines away, and with it goes every subexpression that produced the arguments. An argument with a side effect is therefore evaluated in Debug and dropped in Release — the same trap as any assert, and the reason docs/CodingStandards.md puts the message on its own statement.

TDebugVariable is the support for that split: template <typename T> using TDebugVariable = const T; names a binding whose only reader is a Debug build, so the variable that feeds a Debug-only assertion does not raise an unused-variable warning in Release. It is an alias, not a wrapper — it adds no storage and no lifetime rule.

Includes that only one branch uses, unconditionally

<cstdio>, <cstdlib> and <source_location> are used only by the __DEBUG__ branch, and they are included unconditionally. That is a deliberate concession to the project's include layout: every include belongs in one block at the top of the file, and a guarded #include cannot satisfy that rule. The cost is three standard headers pulled into a configuration that ignores them, which is a compile-time cost paid to keep one readable include preamble — the standard the layout rule protects is a readability rule, and the alternative was a preamble split across a preprocessor conditional.

An asymmetry recorded, not explained

Assert is noexcept in both branches; FatalAssert is noexcept in neither. The parity rule above is about the two branches of one name, so it does not forbid this, and the code is consistent about it. What does not exist anywhere is a statement of why — whether FatalAssert's absence is intentional (its arguments are printed through the same PrintArgs path, which can allocate) or simply never examined. Recorded here as an open question so that a reader who finds it does not have to guess which it is, and so that the parity rule is not silently generalised to cover it.
