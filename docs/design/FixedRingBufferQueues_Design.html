Fixed-size ring buffers: two lock-free queues and their mutex baselines

Engine/Container/AtomicFixedRingMPMC.h Engine/Container/AtomicFixedRingMPSC.h Engine/Container/FixedRingMPMC.h Engine/Container/FixedRingMPSC.h How a static ring of Capacity slots gets a lock-free hot path, and what it cost against a mutex

Scope. This document owns the protocol, the invariants, the memory ordering, the measurement method and the numbers behind four containers and one experimental arm. What a caller may depend on — who may call what, the meaning of each return value, what destruction does — lives on the reference pages: AtomicFixedRingMPMC, AtomicFixedRingMPSC, FixedRingMPMC, FixedRingMPSC. The design record for the shape decision, including the designs that were refuted before these were written, is .Plans/PLAN_fixed_ring_queue.md.

Why a fixed ring, and what it removes

A fixed array is not merely a smaller implementation. Because a slot address never changes and no slot is ever freed, the entire class of problems that made the block-chained queue hard — declaring a hazard, deferring a block, proving no producer is standing inside a block before freeing it — cannot be stated here. What takes their place is one question, is the element at the frontier ready yet, and this document is mostly about answering it without lying in either direction.

The three lock-free shapes, and what they are called

ContainerClaimName in the literature

benchmark app only		 one fetch_add on writeIndex, never retried; a full ring becomes producer latency the fetch-and-add claim of a multi-producer sequencer, as in LMAX Disruptor’s MultiProducerSequencer

Removing the consumer’s CAS is not a cleverer algorithm; it is the direct consequence of one fact — a single consumer owns its frontier outright, so its index needs no arbitration. That makes the consumer one acquire load of the slot’s readyIndex plus one plain increment, which is the floor: no MPSC consumer can be cheaper, because one atomic read of the frontier is the minimum on which a correct answer depends.

The fetch_add arm is deliberately not engine surface. It cannot answer Full: by the time it knows the ring is full it has already taken the index, and what a burned index does to a bounded ring is measured, not theoretical. An engine container that cannot refuse work honestly is a worse API than one that refuses. It lives in Applications/RingBufferBenchmark to answer one question with numbers, and the answer is below.

The ready index carries an absolute index

Each slot owns one std::atomic<size_t> named readyIndex, and it holds the absolute index of the element it refers to, not a lap counter: 

free for lap L      ⇒  readyIndex == L
published for lap L  ⇒  readyIndex == L + 1
released by consumer ⇒  readyIndex := L + Capacity   (which is "free for lap L + Capacity")

Because readyIndex holds an absolute index, a false match would need 264 items pushed — at one item a nanosecond, several thousand years of a saturated queue — and the failure mode is a queue that answers Full forever, not one that corrupts. The plan proposed catching that with one FatalAssert; implementation found no assert that could catch it, because a wrapped index is indistinguishable from a full one without extra state, and an assert that cannot fire is decoration. The claim is therefore recorded as an argument, and the width of the index is what makes it.

Why the word is readyIndex and not occupied, dataStored or dataReadiness

The name was chosen against the value, not against the idea. The stored number is an absolute element index, and in the free state it is the index of an element that does not exist yet — the one the slot will accept next. Three candidates were examined and refused on that reading:

CandidateHow the free state readsVerdict
occupied[i] == w "occupied equals the index of a future element" refused — a name that reads as a boolean, compared against an index; and in the released state (w + Capacity) it asserts occupancy for data that is gone
dataStored[i] == w + 1 correct for exactly one of the three states refused — the same boolean grammar, and "stored" cannot describe a slot whose value names a future element
dataReadiness[i] == w + 1 "the readiness is w + 1" defensible, refused on precision — the name does not say the unit, and the unit is the whole trick
readyIndex[i] == w + 1 adopted "the index this slot is ready for, or the index it is ready with" adopted — the name states the kind (index) and the property (readiness), which is what a reader needs to parse the comparison at the use site

The boolean vocabulary did not go unused; it moved to the predicates, where it is grammatically correct. IsDataReady, MarkDataReady and ReleaseSlot are what the hot path reads, so the raw comparison survives in exactly one place per direction: the producer’s loop, which must tell full apart from stale frontier and therefore needs the loaded value itself rather than a yes-or-no answer about it.

Why the full and empty test precedes the claim

Both directions of both queues test readyIndex before committing an index, and a successful claim therefore already implies the payload it is about to write or read is safe. This is the one rule the shape cannot relax, and it was earned by measuring the alternative. The plan’s §4c built the fetch_add-claims-with-a-flag design literally and ran it:

ObservationValueDiagnosis
2 producers + 2 consumers, 200,000 pushes706,741 pops reported successslots nobody published were delivered
Values never pushed, detected0stale values from the previous lap look valid — the corruption is silent
Pops that gave up waiting593 in 0.2 sburned indices are lost items
Failed push CASes33,354each burned an index while enqueuing nothing

The mechanism is short. fetch_add cannot be undone, so a claim that finds the slot busy and returns Full leaves the index consumed while nothing was stored. writeIndex - readIndex then grows with no data behind it, each readyIndex stops matching any future index, and slots die one at a time. Consumer over-claim is worse still: skipping an index loses whatever is later published at it. Hence the rule — and hence the fetch_add arm waiting rather than refusing, which is the only way it stays correct.

One consequence deserves emphasis for readers of the MPMC queue: because readiness is decided before the dequeue CAS commits, its consumer never waits on a gap. A claimed-but-unpublished slot is answered Empty, and no thread can hold a claimed index while spinning for someone else’s payload write.

Why Blocked is not answerable here

The shipped block-chained queue answers EPopResult::Blocked when a slot has been claimed but not yet published, and that third answer is one of its better features. The fixed rings cannot offer it, and the reason is structural rather than unfinished: its readyIndex holds two states, free and published, so a producer that has won a claim and not yet stored the ready index is invisible. The consumer sees Empty, which is a true statement about what it may take, not a false one.

Buying the third answer would cost a second atomic store on the publish path of every push, to make visible a commitment the consumer cannot act on anyway — it may neither skip it nor take it. The two containers therefore differ in what they can report, and a caller that needs to distinguish nothing yet from something coming needs the block-chained queue, not this one.

A testlet pins the property rather than leaving it to this paragraph: An Unpublished Claim Is Invisible, Never an Element parks a producer inside its own copy constructor — a value type whose copy waits — which is the only way to occupy the claim-then-publish window from a test, then asserts that Pop answers Empty and that the element arrives afterwards rather than being lost.

Who may touch what

Construction and destruction are single-threaded in all four, and destruction requires that no producer is still inside Push: the destructor walks [readIndex, writeIndex) and destroys the slots whose readyIndex says published, so an element under construction at that instant would be destroyed half-written or leaked. The precondition is the same one the shipped queue carries.

Memory order, one row per site

SiteOperationOrderWhy
writeIndex, readIndexCAS successrelaxedallocates an index only; every payload edge crosses the ready index
writeIndex, readIndexCAS failurerelaxedlearns a fresher index and nothing else
slot readyIndexstore index + 1releasemust not become visible before the payload write
slot readyIndexloadacquirethe only gate through which a payload is read
slot readyIndexstore index + Capacityreleasethe payload read must precede the slot’s reuse
payloadconstruct, move, destroyplainthe claim gives that thread sole ownership of the slot
fetch_add armclaimrelaxedsame argument; the RMW’s atomicity is the claim

A stale position read cannot cause a double claim, because the claim is the atomic RMW: a CAS whose expected value has moved fails atomically whatever its memory order, and a fetch_add hands out distinct values by construction. That is why the position words are the relaxed half of the design and readyIndex is the ordered half.

The stronger alternative — acq_rel on the claim — is nearly free on x86, where lock cmpxchg is already a full barrier, and costs a dmb ish on this machine’s ARM cores. It was not taken, because the proofs below pass without it. Were one to fail, the escalation belongs in this row with the proof that forced it, which is how the shipped queue records its own seq_cst.

How the testlets decide exactly-once, and why they cannot decide it from order alone

Each of the four collections verifies delivery with a per-id mark rather than with a sequence: every id is claimed once in a bitmap, so a duplicate is a slot found already marked and a loss is a slot never marked, and neither verdict depends on which consumer happened to win a given item. That independence is what lets one harness judge both the single-consumer MPSC queue and the many-consumer MPMC queue without a second implementation. The id doubles as the value, and it is the producer’s own index into [0, total), so a wrong value is refused by its bounds before it can index the bitmap — corruption cannot turn into an out-of-range write that merely crashes.

Checking that per-producer order survived is subtler than it looks, and the naive version is wrong. Each consumer tracks the next id it expects from each producer, and when it takes an item it must advance that producer ‘s expectation. Two consumers can legally own two items of the same producer at once, and the later one reaches the check first while the earlier one is still mid-move; a bare compare-and-swap would call that ordinary interleaving a violation. The testlet therefore waits for the predecessor to finish before advancing. That is the whole reason the check can refuse duplicate and lost and nothing else — a check that rejected the legal interleaving would have been reporting failures in correct runs.

The third control is the one worth reading twice. A loosened free-slot test does not corrupt an element in the way a reader expects: it lets a producer overwrite the slot holding an item the consumer has not yet reached, after which the consumer can never satisfy its frontier test and the queue stops. The exact readyIndex == pos comparison is what makes a fullness answer harmless, and it is load-bearing in a way that a passing functional test alone would never have shown.

Two harness defects found while running the controls

Both are the same failure the repository has recorded before — a harness is code, and a wrong harness reports a wrong verdict with full confidence.

  • Classifying a control by grepping its output for a failure word reads a hang as not detected. A watchdog kill is a detection: the mutant stranded the consumer, which is the worst failure a queue can have.
  • With stdout block-buffered into a pipe, a run killed by the watchdog printed nothing at all, so the run looked like it had never started. Unbuffered stdout turns a hang into a readable last line.

A third defect was in this module’s own testlets, and it is worth stating because WaitUntil is shared harness surface: hbe::WaitUntil polls a predicate and then return isReady(), calling it once more after the loop. A predicate that merely reports a flag is unaffected, but a predicate that withdraws — one that calls Pop — consumes on the first call and reports false on the last, and the testlet then reports a lost element that was in fact delivered. The testlet now uses a bounded poll. WaitUntil’s own page does not warn against consuming predicates; that is an open item below.

The spin cap, measured twice, refuting two different claims

Every retry loop in these containers yields after MaxSpinAttempts failed attempts, so a bounded busy-wait replaces an unbounded one. The default, 8, was chosen before anything was measured. The sweep now measures the default against yielding immediately, at capacity 64, in the two regimes that could disagree — saturated, where a producer is usually blocked on a full ring, and sparse, where a consumer is usually blocked on an empty one. Best-of-five rounds, Release, ns/item:

MPSC saturated16116.393.7yield, 1.24×
MPSC sparse, 2 µs gap16548.11427.3spin, 2.60×

An earlier version of this document read the saturated cells alone and concluded that yielding is best — 1.5× at four producers and 4.2× at sixteen against a spin cap of 64. That conclusion was right about the mechanism and wrong about its scope. Under saturation the thread that can unblock a waiter is another thread of the same cell, so a waiter that spins holds a core the other thread needs, and with more runnable threads than cores a spin is a tax on every retry. In the sparse regime the waiter is waiting for work that is not on this machine yet: nobody can be unblocked, and a yield only pays the scheduler to put the thread back. Spinning wins there by 2.6×.

What the two readings agree on is the mechanism: the right cap is a function of what the waiter is waiting for, not a constant. 8 is defensible as a compromise — it captures most of the sparse win while bounding the saturated loss to roughly the noise floor — and it stays a template argument precisely so a call site that knows which regime it is in can choose. The measurement does not vindicate a larger number: spin 64 was the worst cell ever measured here, at 447.7 ns/item, so an unbounded busy-wait would be worse than either arm above.

What the numbers say

  • MPSC: the lock-free ring wins every cell, saturated and sparse. 3.6× at one producer, 2.7× at two, and still 1.45× at four, where its own curve dips. The uncontended mutex costs roughly 90–100 ns per item on this machine and is paid whether or not anyone contends.
  • MPMC: the lock-free ring wins every cell too, which is the correction in this table. The margin is thin in the middle — 1.23× at two producers, 1.25× at four, 1.22× at eight — and wider at the ends, 1.86× at one and 1.66× at sixteen. An earlier measurement of the same classes said the opposite at one, two and four producers; see why the two measurements disagree. The consequence for the guide is that no MPMC cell carries a claim: the numbers are printed, and nothing is graded.
  • The fetch_add arm still answers the question it was built for. With no CAS at all it beats the tagged ring by 1.5× at four producers and 1.6× at eight, then loses by 2.5× at sixteen, where producers genuinely must wait for the ring and the arm converts a refusal it could have reported into latency it absorbs. “The CAS is the cost” is true only while the ring is not actually full — and an arm that cannot answer Full is not an engine API, which is why it stays a benchmark-local class.
  • Sparse separates the designs better than saturated does. With an arrival gap the mutex arms sit 2.0–3.6× behind, because the gap hands the queue to one thread at a time and the only cost left in the mutex arm is the lock itself.

The tables in this document came from two drivers, run on the same 12-CPU machine, over the same four container classes, and they do not agree:

Both drivers used the same shape (capacity 64, two consumers, a busy-polling consumer, invariant checks inside the timed region) and rotated their arms each round, so the difference is not in what was measured. Two conditions differ, and both push in the direction observed:

  • The engine is running. A testlet runs inside hbe::Engine, whose task system keeps worker threads alive on 12 cores. A mutex held across a preemption stalls every other thread of the cell, which is exactly the failure mode the mutex baseline pays for; a lock-free ring has nothing to be preempted inside. The standalone driver measured on an otherwise idle machine.
  • Run length. The standalone driver moved 20,000 items per producer at every producer count — 20,000 items total at one producer. Thread creation, first-touch page faults and the wake-up of the start gate are a fixed cost, so the short cells carried a larger share of them, and a cell that takes 2 ms is not measuring the same thing as a cell that takes 25 ms. The registered cells hold the item total constant instead.

Neither driver is wrong; they answer different questions. A queue in this engine is used while the engine runs, so the registered cells are the answer that matters for the guide, and they are the numbers the grades compare against. What is not settled is whether the mutex baseline would win on an idle machine at low producer counts with long runs — the standalone driver says yes, and nothing here refutes it, because the current sweep cannot be run that way from inside a testlet. Open items carries the experiment that would close it.

The harness, and the properties it exists to protect

The benchmark is a set of registered performance testlets, not a separate program with its own arithmetic. RingBufferPerfTest registers three cells into every EngineTest run, so a regression run sees the direction of the two designs at the cost of about 0.7 s; RingBufferPerfBenchmarkTest registers the full sweep — twenty-two cells, about 16 s — and only Examples/RingBufferBenchmark registers that collection. The two binaries differ in nothing but which collection they register, so a number in the sweep and a number in the regression run cannot be computed differently, which is the failure this shape was chosen to prevent.

Five properties are requirements rather than style, and each was bought with a wrong number somewhere in this repository’s history:

  • A real inner loop. A cell that performs one operation reports 0.01 ns and looks fast.
  • A fresh queue per round. A queue shared across rounds carries its fuse into the next measurement.
  • A timed region that covers the consumers. Timing only the producers lets a starved consumer report 19.6 ns.
  • No static state in a cell. A static cursor is reused by the next cell, and the two cells then share a result.
  • A cell that finishes. Every wait in a cell has a deadline, so a broken container cannot hang a suite.

The schedule is a rotation: every round walks every arm exactly once and the starting offset moves each round, so drift with time, thermals or schedule position cannot spend itself on one arm and spare another. Invariant checking happens inside every measured round, so a measurement that was wrong shows up as a violation count on the same row as the number it would have produced. Instrumentation belongs to the harness, not to the container: a per-operation fetch_add inside a queue would change what is being measured.

Anatomy of a cell

A cell’s measure function owns everything. In order: it builds a fresh queue, a bitmap of producers × items marks and three counters; it creates the producer and consumer threads, all of which park on one release-stored start flag; it records the clock; it releases the flag; it joins every thread; it stops the clock. The bitmap is checked after the join, so the loss check costs nothing inside the timed region.

Each producer stamps its own index and a per-item check value, and retries a refused Push. Each consumer verifies the check value, the producer index, and that it has not seen this item before, then advances the shared count — unconditionally, including for a corrupt item. That last detail is a bug this document owns: an early-continue on the corruption path skipped the increment, the consumer’s exit condition never became true, and the suite hung on the first performance cell for as long as anyone let it run. An exit condition must not depend on the correctness of the thing being counted.

Every spin loop in a cell carries a deadline, checked once every 4,096 refusals rather than every attempt, so it is free inside the measured region. On expiry the thread leaves, marks the cell abandoned, and the missing marks turn the cell into a REJECTED row. This exists because a performance cell is registered in the same suite as correctness tests: a cell that can hang takes the whole suite down with it, which is a worse failure than a wrong number. The deadline is what turned “the run is stuck” into a row that says which cell and why.

The floor: what the same code measures twice

A cell may declare a control arm: the same measure function and the same shape a second time, so a third queue instance of the same design runs in the same rotation. The spread between its fastest and slowest round is the machine’s own noise, and it is what a grade is allowed to trust. Measured on this 12-CPU machine (8 performance, 4 efficiency cores), Release build:

Two conclusions, and the second is the one that changed the harness. Saturated cells on a machine whose cores are all busy are noisy at the 10–30% level, so a claim of 1.2× cannot be graded there however clean the code is. And Dev is not a quieter Release but a different machine: its spreads ran up to 66% on the very cells that measured 4% in Release, which is why claims are graded only in an optimised build and a Dev run prints its numbers with the words claim numbers only.

How a grade is chosen, and why none of them fails a build

GradeOf is the single place a colour is picked, and the rule is five ordered tests: violations give REJECTED; a ratio below the margin gives RED; a ratio that fits inside the noise floor gives NOISE; a middle round that also clears the margin gives GREEN; a claim that cleared only on the fastest round gives AMBER.

None of them calls the framework’s error or warning path, and none changes whether the suite passed. A failing test suite whose failure is a ratio is a suite whose owner learns to ignore the ratio: the colour has to be worth reading, and it is worth reading only when it is not also a complaint. The one thing a cell can refuse is its own number — REJECTED exists because a ratio measured on a queue that lost an item is not a slow design but a measurement of nothing, and quoting it is the error, not the design.

The uncertainty term is deliberately the control’s spread rather than the winner’s own, when a control exists. The winner’s slowest round is usually its cold round — first threads, first pages — and letting one arm’s cold start veto its own claim turned a 3.85× win into NOISE in a measurement run while writing this. Both numbers are printed, so a reader can disagree with the choice.

The MPSC margin is 2.00× up to two producers and 1.20× beyond, because that is where the mutex baseline stops paying for itself: at one and two producers an uncontended lock dominates, and at four the lock-free ring dips to 1.45× before recovering. MPMC carries no claim at all. The guide it was built to check — that a mutex beats a CAS ring at two producers and two consumers — is what the standalone driver measured, and the registered cells measure the opposite at every producer count; the disagreement is documented rather than resolved in favour of the newer number. Until that experiment runs, an MPMC cell prints its numbers and grades nothing.

Time budget, because these cells run in a regression suite

No testlet in this repository may exceed five seconds, and the performance cells are held to three. The report prints the wall time of every cell, for the same reason a compiler prints the size of a struct: a budget that cannot be read is not a budget. Measured in Release, the three compact cells cost 0.21 s, 0.24 s and 0.30 s; the twenty-two sweep cells run from 0.20 s to 2.37 s, the slowest being sixteen producers with an arrival gap. Total suite cost of the compact cells is about 0.75 s, against a whole-suite runtime of roughly ten seconds.

The item count, not the round count, is what was reduced to meet this. Round counts below five make the middle-round statistic meaningless, whereas 200,000 items per cell is far past the point where a per-item figure stabilises — and holding the item total rather than the per-producer count constant is what makes sixteen producers cost the same as one.

Two member-layout waivers, both stated

The layout rule puts a class’s nested types in the first block and its constants in the second, and two types in this work cannot obey that because a type is sized by a constant it is supposed to precede. Each marks its declaration line // hb-standards:ignore, keeps the constant directly above it, and is counted by layout.py as MEMBER-WAIVED rather than passing silently:

The two mutex baselines are one program

FixedRingMPSC and FixedRingMPMC carry the same state — one mutex, one head, one count, one payload array — and the same method bodies. That is not duplication that survived review; under a mutex the number of consumers is not a variable of the program, so there is no difference to implement, and any apparent difference would be noise. The two names exist because the cells need two arms to make that visible, and their agreement in the tables above is itself a control: the same program measured twice in one rotation, whose rows should match and do.

A deliberate limit, stated rather than hidden: these baselines answer Empty and Full immediately, like the lock-free arms, so the comparison is like-for-like. A condition_variable baseline would sleep instead of returning, trading CPU for wake latency, and on the sparse cells it would be the better program — the sparse mutex rows above are paying for a busy-poll the design never asked for. That variant is not measured here; see open items.
