Task system internals

The invariants the running code holds, and how the unit tests are built to see them
Scope. This document owns two questions: what Engine/Core/TaskStream.cpp, TaskProvider.cpp, TaskRegistry.cpp, StreamDrainPolicy.cpp, CPUBudget.cpp and ResultPacket.cpp guarantee while the engine runs, and why the testlets in those files are written the way they are. It does not teach the API — that is TaskSystem and its sibling class pages — and it does not re-argue the design decisions, which docs/TaskSystemRedesign.md records. Usage is docs/TaskSystemGuide.md.

Who drives a stream

A stream is served by whoever calls Update on it. The base stream is a ride-on-thread stream driven by the thread running the engine. The IO stream is also ride-on-thread, and it is driven by the logger's own thread: the logger has to work before the task system exists and after it is gone, and giving it a thread of its own would make the logger's writing depend on a stream the logger is also responsible for feeding. That circularity is the whole reason the IO stream has no thread of its own.

A driven stream shares its driver thread with whatever else that thread does, so the thread index and the allocator are entered and left around each pass rather than assumed for the lifetime of the thread. A pass that assumed the association would hold an index for a thread that is doing something else between passes.

Posted callables are served before the queues: they are the main thread's own work, and the frame budget is spent on them before the stream's queues are asked for anything. They run with the queue's lock released, which is what lets a posted callable post again — a requirement of any work that schedules more of itself.

Lane selection, and the borrowing rule

Which list serves a lane is fixed by the lane; an out-of-range index means the lane is None. The drain policy chooses a lane from what the lanes hold and what the allowance still permits.

When both lane shares are spent while the stream total is still inside budget, the policy borrows: the work exists, the stream can still pay for it, and refusing here would idle the stream over a bookkeeping detail. The preference order is the heavier lane first, then FIFO, so the choice is never arbitrary — an arbitrary tie-break is the kind of thing that reads as starvation in a profile and cannot be reproduced.

A lane holding work with no lane chosen is the decline itself. ChooseLane returns a lane whenever work exists and the allowance is unlimited, so no other combination produces that state. The stream counts it per pass, which makes the counter a rate and not a queue depth.

The allowance, and who may be asked

A refill is served whenever there is any, without consulting the drain policy. The rate and the budget gate the stream's own loop; gating the refill as well would let a caller's refill stall on an exhausted allowance, which would make the thing that restores the budget depend on the budget.

The provider invariant. A provider is asked only while this stream's allowance permits taking work. Asking while spent is the failure the gate exists to prevent: a spent stream would otherwise keep manufacturing work it has no right to run. Reading the budget a second time at that point is legal for exactly one reason — this is the owning thread, the only thread ever allowed to read that unsynchronised field.

The allowance is the owning thread's field to write, so a request made from elsewhere is applied on the owning thread rather than landing in the middle of another thread's store. When both lanes offered nothing, the stream asks whoever is attached to them; the lane that is empty is the one that asks, and a spent allowance means no asking at all.

Order, release, and re-adding

A task that finished elsewhere is released from its lane and put back on that same lane, so the sweep and the re-add are per lane and no task changes lane on the way. Rotating a lane drops finished tasks in place and preserves arrival order for the rest, which is the same O(n)-per-loop price BoundedPriorityQueue::Remove already pays — the stream does not buy a cheaper structure by taking a subtler bug.

Closing, abandoning, and shutdown

A stream that has been asked to close stops taking work. What it still holds is dealt with by the close path that asked, which reports anything it cannot run rather than leaving the driver to pump a stream that has said it is done. Work that can never run is abandoned, and an abandoned task's notice fires so its owner learns rather than waiting.

Ageing work out

Age is judged after the task lookup, not before: a task that no longer exists has no owner to explain a refusal to, and the released path already owns that case. Both lanes pass this point, which is why one insertion covers the FIFO lane and the priority lane with one rule.

Two boundaries are pinned rather than described. A stream that never opted in ages nothing out, however old the work is — without that guard the feature would be "off by default" in name only, and every existing stream would start dropping tasks whose age happens to exceed a zero ceiling. And work exactly as old as the ceiling is still admissible while one nanosecond more is not: pinning only the far side would let the comparison become >= unnoticed, and a ceiling one nanosecond stricter than documented is a starvation change nobody approved. The stamp in that testlet is a real instant rather than zero, because a zero stamp makes the delta mean nothing — which is the arithmetic this test originally got wrong in its own favour.

Work with no stamp cannot be dated. Hand-built tasks and anything constructed before the registry loaded it land here, and the safe answer for a stream is to run it, not to guess it is stale.

Record layout and sizing, and what the numbers are for

A registry record is priced at 256 bytes, which is four cache lines. The successor is a full TaskID, and that pushed the record past three cache lines, so it is padded to four rather than left straddling. The task inside it stayed at 176 bytes — the join's generated counter went into padding it already had. A record that straddles lines is a per-task cost paid by every lookup, so the padding is decided at compile time and asserted, not measured later.

The growth arithmetic is asserted with literal figures: 8 records grown by 4 is 12. A doubling policy would give 16, and rounding to a power of two would give 16 as well, so 12 is the only figure that separates the arithmetic the design promises from the alternatives that would otherwise pass. The same reason governs the rest of the literals in these testlets: a comparison against the constant that produced the value cannot fail, so it tests nothing.

Free-list accounting is checked by counting admissions. A record released twice is held by another task by the time it is counted, so a 4-record table owes exactly three more admissions; a double release that pushed the same record onto the free list twice shows up as a fifth admission — one record the table never owned.

How the tests observe these mechanisms

Several behaviours cannot be reached by asking the production objects politely, so the testlets carry probes. Their shape is not incidental:

  • A provider that records what it was handed, so the interface contract can be observed rather than assumed.
  • Probes detach before they die. The probes attach to stream indices this engine really does have, so they register — and a provider destroyed while registered is exactly the dangling pointer the detach-before-destruction assert exists to catch. A test double that cleans up after itself keeps that rule strict for everyone else.
  • A probe that hands out a bounded number of real work items, so a drain can be observed doing what a drain is for. It deliberately owns nothing the stream has to know about: each item is a task created in the system the provider was built with, released only once the test has seen it run.
  • A probe that releases a task inside Produce, so the item names a record that is already gone by the time the stream can see it. The release happens under the stream's queue lock, which is where the ordering is arranged rather than raced.
  • A probe that stays inside Produce until the test lets it go. The only way to test "a detach waits for a drain in flight" is to have a drain actually in flight, and a Produce that returns immediately never is.
  • A spinner bounded by CPU time, not iterations, so the same test means the same thing on a slow core, under a debugger, and in Release, where an iteration count is meaningless.

Stale-identity handling is tested against a record that is still live in a different generation — the case TaskID exists for. A released-ID version of the same testlet stayed green with the guard removed, because Create clears the field when it reissues a record; the write refusal is only observable against a record somebody is still using.
