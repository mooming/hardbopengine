ResultPacket

Engine/Core/ResultPacket.h final namespace hbe one task's result: an 8-byte header over a 120-byte payload, embedded in the task and therefore in the registry record

Class description

class alignas(std::uint64_t) ResultPacket final at Engine/Core/ResultPacket.h: 8 bytes of header over 120 bytes of payload, embedded by value in Task and therefore in every record of the task registry. This is the whole of what the engine knows about results. A task writes one packet; a task with more to say than one packet holds puts a handle to memory it owns into the payload and owns that memory itself. There is no per-stream result buffer, no capacity to admit against, and no delivery window measured in frames. 

static_assert(SizeBytes == 128, "A result packet must be the 128 bytes the design fixed");
static_assert(HeaderBytes > DestinationByteIndex, "The header must be wide enough to hold both decided fields");

From Engine/Core/ResultPacket.h, hbe::ResultPacket

Two more assertions sit at file scope after the namespace closes: sizeof(hbe::ResultPacket) == hbe::ResultPacket::SizeBytes (the compiler adds no padding) and alignof(hbe::ResultPacket) == sizeof(std::uint64_t) (the payload is reachable in aligned words wherever the packet lands). The width is not academic: because the packet is embedded, its 128 bytes are added to a task, and a task is a registry record's largest field — TaskRegistry::RecordSizeBytes is 256, and the default table is 4096 records, so the packet is half the price of tracking a task at all.

The header is not padding either. Its first two bytes are the only things a reader needs before interpreting the payload — what the result is, and who asked for it — and both are written by the producer, which is why routing never needed the header to grow past eight bytes. Everything from byte 2 on is spare and deliberately nameless: the two meaningful fields are byte-indexed by KindByteIndex and DestinationByteIndex rather than declared as three named fields with a gap between them.

Kind 0 means "no result", and that is a state rather than a value. A record is reused without being zeroed, so the cleared state is what a packet comes back in (Clear) and what a reader stops at (HasResult). Kind is zero because a packet that was never written to is a packet of zeroes. Values from FirstApplicationKind (64) up belong to the application; below it is the engine's range, so the engine cannot allocate an application's kind by accident. The split is a boundary, not a table: nothing dispatches on it.
One writer, one late reader — and no synchronisation. The type is not thread-safe and does not negotiate: one task writes its packet while it runs, and the reader arrives after that task finished. A task writing while another thread reads the same packet is a bug in whoever declared the result. There is a second writer the design accepts: TaskSystem::DispatchSuccessor() assigns one packet to another when it delivers an outcome (Engine/Core/TaskSystem.cpp) — so the claim, made in this header and in Task::GetResult, that nothing in the engine copies a packet is not true of the shipping path.
Nothing checks that a result was ever written before it is delivered. TaskSystem::DispatchSuccessor() routes on the destination byte alone; it never calls HasResult. A producer that set a destination and wrote nothing still delivers: the successor is dispatched with a packet whose kind is KindNoResult and whose payload is whatever a Clear left in it. A successor that cares about the difference reads the kind itself.
