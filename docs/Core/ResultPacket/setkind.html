SetKind

member of hbe::ResultPacket Engine/Core/ResultPacket.h declare the result and its kind at once; the write a producer makes last

Signature

void SetKind(std::uint8_t newKind) noexcept

Function description

Defined in the header Engine/Core/ResultPacket.h as ResultPacket::SetKind(); the body is header[KindByteIndex] = newKind;. It does two things at once because they are the same thing: it says what the result is, and, by not being KindNoResult, it says there is one.

Call it last, after the payload is written — the header says so, and the reason is a reader in the middle. A reader that arrives between the two writes sees a kind claiming a payload that has not been filled yet (Engine/Core/ResultPacket.h). Since nothing in this type is atomic, a producer that sets the kind first publishes a result whose bytes are still Clear's zeroes. Filling the payload first means a reader that sees a kind at all sees a complete one.
The value is unchecked, both ways. No range is enforced, so an application may write a kind below FirstApplicationKind and collide with the engine's half of the byte, and writing KindNoResult is silently accepted — which erases the packet as far as HasResult is concerned while leaving every payload byte in place. That inversion is a documented feature (it is how a producer says "no result" without clearing), but it is not what a caller passing 0 by accident looks like from the outside.

Parameters

ParameterTypeRequirement
newKindstd::uint8_tThe result's type as producer and reader agreed; 0 declares "no result", and any value 64 or above is application-owned

Return value

void. Nothing reports the previous kind, and nothing refuses to overwrite it.

Examples

From Engine/Core/TaskSystem.cpp, WriteOutcome() (unit-test region)

ResultPacket& packet = task->GetResult();
packet.SetKind(kind);
packet.SetDestinationStreamIndex(fixture.destination);
packet.GetPayload()[0] = outcomeByte;

Note the order in this helper: the kind is set before the payload byte is written, which is the order the header warns against. It is harmless there because nothing reads the packet concurrently — the fixture's successor is only dispatched after the producing item finishes — but a producer with any reader in flight should write the payload first and declare the kind last.
