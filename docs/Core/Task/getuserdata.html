GetUserData

member of hbe::Task Engine/Core/Task.h the context pointer handed to the runnable, unchanged and unowned

Signature

[[nodiscard]] void* GetUserData() const noexcept

Function description

Defined in the header Engine/Core/Task.h as Task::GetUserData(); the body is return userData;. It returns the pointer that was handed to TaskSystem::CreateTask and stored by LoadIntoRecord, unchanged: the engine never reads through it, never copies it and never clears it.

One reader in the engine — WorkItem::Run reads it immediately before calling the task's runnable, so every item of a task passes the same pointer to the same function. It is a task-wide context, not a per-item one: an item's position in the work is carried by its start/end/current range instead (Engine/Core/WorkItem.h).

Its lifetime is the creator's obligation, not the engine's. The pointer stays in the record until the next task reuses it. A task that outlives what the pointer points at is not detected: the runnable is handed a dangling address and the join still counts the item as finished. A task whose context lives on the stack of a function that returns before the work runs fails this way, and nothing in the task system can see it.
This is not the abandonment context. abandonedUserData is a separate pointer for a separate party — the requestor who asked to be told when work was dropped, which is frequently not the owner of the runnable's context (TaskSystem::SetAbandonedNotice).

Parameters

None.

Return value

TypeWhat you get
void*The context pointer as stored — nullptr for a task created with none, or built by the default constructor

Examples

From Engine/Core/WorkItem.cpp, WorkItem::Run()

auto userData = task.GetUserData();
auto delta = runnable(userData, current, end);
current += delta;

Read once per item, on the thread that is about to run the work, which is the only thread the runnable may assume anything about. A runnable that needs per-item state must derive it from current and end.
