LoadIntoRecord

member of hbe::Task Engine/Core/Task.h private: fill a recycled record, reloading every field including the previous tenant's notice

Signature

void LoadIntoRecord(TaskID newID, StaticString taskName, TRunnable newFunc, void* newUserData) noexcept

Function description

Private; defined in Engine/Core/Task.cpp as Task::LoadIntoRecord(), and its one caller is TaskRegistry::Create() (Engine/Core/TaskRegistry.cpp). It fills this task where it sits, because Task cannot be assigned: the std::atomic join counter deletes the implicit copy and move assignment (proved on the destructor page), so the registry has no assignment to lean on when it recycles a record.

name = taskName;
numSubTasks = 0;
numGeneratedSubTasks = 0;
result.Clear();
numFinishedSubTasks.store(0, std::memory_order::relaxed);
func = newFunc;

abandonedUserData = nullptr;
offerTime = std::chrono::duration_cast<std::chrono::nanoseconds>(time::ElapsedSinceEngineEpoch());

From Engine/Core/Task.cpp, Task::LoadIntoRecord()

Every field is reloaded, including the three the caller was not given. That is not tidiness: the record this task lives in belonged to another task until a moment ago, and a notice left behind by that previous tenant would fire the old requestor's callback with its stale context pointer for work this task never asked about. The in-class initialisers on those fields run once, when the record is first constructed (TaskRegistry::AllocateBank() placement-news a whole bank), so a reused record depends entirely on this call to be clean.

The age clock starts here, not on the work item. offerTime is stamped once, at record issue, and each WorkItem copies it in its constructor. A task that splits late, or whose runnable returns part of its range and is re-queued, therefore stays exactly as old as it was — which is the point: stamping the item instead would let a task postpone a stream's max age by not finishing in one call. See StreamDrainPolicy::IsOverAge in Engine/Core/StreamDrainPolicy.h for the reader.
The join and the result both start empty. numSubTasks and numFinishedSubTasks go to 0, so HasDone is false and no successor can be dispatched on a task that has not declared anything. result.Clear() puts the packet back to KindNoResult, so a reused record cannot report its previous occupant's answer.
The identity is published before the record is marked in use. The caller stores the new generation, calls this, and only then marks the record live (TaskRegistry::Create()), so a lookup that sees the record as in use sees a task whose GetID already matches the ID being issued. Passing an ID that does not name this record would break that invariant for every item built from it — this call is the only place the two are joined, and nothing checks that they agree.

Examples

From Engine/Core/TaskRegistry.cpp, TaskRegistry::Create()

const TaskID::TGeneration generation = record.generation.load(std::memory_order::relaxed) + 1;
record.generation.store(generation, std::memory_order::relaxed);
record.successor = {};
record.task.LoadIntoRecord(TaskID{recordIndex, generation}, taskName, func, userData);
record.inUse.store(true, std::memory_order::release);

Three things happen around this call, and their order is the design: the generation advances first, so an ID issued for the previous occupant stops resolving; the successor is cleared, so a recycled record does not inherit routing (TaskRegistryTest in Engine/Core/TaskRegistry.cpp pins that); and the record is published as in use last, with release ordering, so no thread can find a record before the task inside it says who it is.
