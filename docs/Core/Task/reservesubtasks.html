ReserveSubTasks

member of hbe::Task Engine/Core/Task.h declare the join before the first item is queued; a late count makes the task report itself finished early

Signature

void ReserveSubTasks(TNumSubTasks count) noexcept

Function description

Defined in the header Engine/Core/Task.h as Task::ReserveSubTasks(); the body is numSubTasks = count; and nothing else. It declares how many work items this task will be split into, and that figure is the join: ReportFinishedSubTask closes the join when the finished count reaches it, and HasDone asks the same comparison.

The order is the contract. The count has to be the truth before the first item can be seen by a worker, because the winner of a join is decided by equality against numSubTasks — so declaring three items after one has already finished makes the task report itself complete on a task that still has two items queued. A caller waiting on the real completion never learns it. Both engine call sites reserve before they generate anything: TaskSystem::EnqueueTask() reserves one immediately before its single GenerateSubTask, and TaskSystem::EnqueueTask()'s splitting sibling TaskSystem::RunSplit() reserves the clamped count before the loop that hands out ranges (Engine/Core/TaskSystem.cpp).

One plain byte, written and read unsynchronised. numSubTasks is not atomic. Reserving while the task's items are already running races with the reads inside ReportFinishedSubTask and HasDone, and nothing here detects it — the header's rule ("call it once, on a task the registry has just issued, before the first item is queued") is the whole guarantee. Note that DispatchSuccessor reads this field to decide whether a successor can be dispatched at all, so a successor that reserved nothing is refused with a log line rather than run.
Reserving is not the same as promising a waiter. A fire-and-forget job still reserves the number of items it queues — the count is what makes the join close correctly for whatever else reads it. What is optional is somebody reading the result, not the count. The count cannot exceed MaxNumSubTasks (255) because the parameter is a TNumSubTasks; the one splitter in the engine clamps its request to 255 rather than refusing it.

Parameters

ParameterTypeRequirement
countTNumSubTasks (uint8_t)How many items will report in. Overwrites any previous value; 0 means the join can never close and a successor naming this task is refused

Return value

void. No clamp, no refusal, and no report of a previous reservation.

Examples

From Engine/Core/TaskSystem.cpp, TaskSystem::EnqueueTask()

task.ReserveSubTasks(1);
Enqueue(streamIndex, task.GenerateSubTask(0, 1, priority), lane);

The declare-then-generate order is visible in the two lines: the join exists before the item can reach a lane. In TaskSystem::RunSplit() the same shape appears once for the whole split — task->ReserveSubTasks(static_cast<Task::TNumSubTasks>(numSubJobs)); — followed by the loop that generates exactly that many items.
