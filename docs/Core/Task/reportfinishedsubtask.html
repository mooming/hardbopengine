ReportFinishedSubTask

member of hbe::Task Engine/Core/Task.h true to exactly one caller, the one that closed the join — and that caller owes the successor a dispatch

return finishedBefore + 1 == numSubTasks;

From Engine/Core/Task.h, Task::ReportFinishedSubTask()

Three things are decided by those two lines. The increment is sequential consistency, which is what orders everything the finished task wrote — including its result packet — before the completion another thread is about to observe. The comparison is an equality, not a threshold, so a caller past the last item is told it did not win. And the return value is a claim of ownership: exactly one caller of this function gets true for a given join, and that thread is the one that completed the task.

The winner owes a dispatch. Nothing else delivers an outcome. TaskStream::TryExecuteWorkItem() (Engine/Core/TaskStream.cpp) runs the item through WorkItem::Run, and only on true calls TaskSystem::DispatchSuccessor — which copies the result packet onto the successor and queues the successor's item. A caller that swallows the true ends the chain silently: no symptom until something downstream waits for a task that will never run.
A join closes only if every reserved item reports. Fewer reports than NumSubTasks means the equality never matches, and no caller ever learns the task is finished — the failure mode of a task whose items were dropped, aged out or never queued. Both are counted rather than assumed here: dropped work is reported by the stream that dropped it (TaskStream::ReportAgedOutWorkItem(), TaskStream::FireAbandonedNotice()), and the count of items a stream abandoned is readable there.
Both numbers are 8 bits. numFinishedSubTasks is an atomic uint8_t, so the counter wraps modulo 256 while the comparison is computed in int. The equality therefore fires once under any sane reservation, and fires a second time if the finished count wraps all the way back to the reserved figure — which needs 256 further reports on a single task, i.e. an item generator that ignored its reservation entirely. The guard that was meant to catch that is documented as inert on GenerateSubTask.

The report happens once per item, and only after that item consumed its whole range — a runnable that returns part of its range is re-queued and does not count as a finished item. In Engine/Core/TaskRegistry.cpp (TaskRegistryTest) the same call is driven by hand to pin the rule down: three reserved items produce false, false, true, and a fourth report produces false.
