SetRunnable

member of hbe::Task Engine/Core/Task.h replace the task's function pointer; nothing in the repository calls it

Signature

void SetRunnable(TRunnable runnable) noexcept

Function description

Defined in the header Engine/Core/Task.h as Task::SetRunnable(); the body is func = runnable; and nothing else. It replaces the function pointer that GetRunnable reports, with no check on the previous value and no report of what it overwrote.

Nothing in this repository calls it. A grep of Engine/ and Applications/ finds the declaration in Engine/Core/Task.h and no call site: every task that runs received its runnable through LoadIntoRecord — issued by TaskRegistry::Create() — or through the named constructor, and both happen before a record is published as in use.

Changing a runnable under a running task is undefined in the plainest sense. func is an ordinary data pointer and GetRunnable reads it without synchronisation, so a write concurrent with an item about to start races with that read. Which item calls the old function and which calls the new one is then a matter of timing, and — because the join counts items rather than work — a task can end up counting a finished item whose work belonged to a different function entirely.
Swapping the work does not reset the join. The counter, the reserved count, the age clock and the result packet all stay exactly as they were. Replacing a task's behaviour mid-life needs a new task — created through TaskSystem::CreateTask, with its own reservation — not this call.

Parameters

ParameterTypeRequirement
runnableTRunnableA function with external linkage, or nullptr — which every subsequent item of this task will answer with an error line and a closed range

Return value

void. Whether a runnable was already set is neither reported nor preserved.

Examples

Illustrative — no call site for this exists in the repository.

Task* task = taskSystem.FindTask(id);
if (task != nullptr)
{
    task->SetRunnable(&ReplacementRunnable);
}

The shape above is what the interface permits and what nothing in the tree does. The safe window for it is between a record being issued and its first item being queued; after the first item is visible to a stream there is no window at all, because the read in WorkItem::Run has no lock to wait for.
