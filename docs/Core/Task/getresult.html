GetResult

member of hbe::Task Engine/Core/Task.h this task's own 128-byte packet, cleared when the record was issued

Signature

[[nodiscard]] ResultPacket& GetResult() noexcept

[[nodiscard]] const ResultPacket& GetResult() const noexcept

Function description

Both overloads are defined in the header Engine/Core/Task.h as Task::GetResult(); each body is return result;. The packet is an embedded member — 128 bytes living inside the task, and therefore inside the registry record — not a buffer a stream owns. There is no per-stream result arena, no capacity to admit against, and nothing to free: the result lives exactly as long as the task is tracked.

It starts empty. LoadIntoRecord calls ResultPacket::Clear() when the registry issues the record (Engine/Core/Task.cpp), so a recycled record cannot report its previous occupant's answer, and ResultPacket::KindNoResult is the state a reader stops at.

Two writers, both engine-side. The task's own runnable writes it through the task it was given, and TaskSystem::RunSplit() stamps the packet's destination byte when the split names a successor (Engine/Core/TaskSystem.cpp).

A packet is copied by the delivery path. The header's note says nothing in the engine copies this packet; the source disagrees. TaskSystem::DispatchSuccessor() assigns the finished task's packet onto its successor before queueing the successor's item, so the successor inherits the producer's kind byte and the producer's destination byte along with the payload. 
successor->GetResult() = packet;

streams[destination].EnqueueFifo(successor->GenerateSubTask(0, 1));

From Engine/Core/TaskSystem.cpp, TaskSystem::DispatchSuccessor()

Anything bigger than 120 bytes of payload is the task's problem. The engine's knowledge of results stops at this packet: a task with more output than the payload holds keeps that output in memory it owns and puts a handle to it in the payload. The engine neither allocates, nor copies out, nor frees that memory — see ResultPacket::PayloadBytes in Engine/Core/ResultPacket.h.
A mutable reference to this is a write the reader cannot see coming. The packet is not synchronised: one task writes it while it runs, and the reader arrives after the join closed. Writing it while another thread reads the same packet is a bug in whoever declared the result, and nothing here detects it.
