Task

Engine/Core/Task.h final namespace hbe the unit of work the registry tracks: a runnable, a declared join, a finished-item counter, and one embedded result packet

Class description

class Task final at Engine/Core/Task.h: the unit of work the task system tracks, and the thing a caller holds an identity for. It is not a queue item — WorkItem is — and it is not a thread. A task is a name, a TRunnable, one user pointer, a declared join (how many items will report in), the counter of those reports, an age clock, an optional abandonment notice, and one embedded result packet.

A live task lives inside a TaskRegistry::Record (Engine/Core/TaskRegistry.h), never on a caller's stack. The registry issues the record, calls LoadIntoRecord to fill it, and hands back the identity; every engine path that wants a task goes through TaskSystem::CreateTask and TaskSystem::FindTask. The two public constructors still exist, but they build a task with a null identity, and a work item built from a null-identity task names a record no stream can resolve — the constructor pair has no call site outside the unit tests (Engine/Core/TaskRegistry.cpp, TaskRegistryTest; the helper TrackedTask in Engine/Core/TaskSystem.cpp is what the task-system tests use, and it asks the registry).

The join is the class's whole reason for existing. ReserveSubTasks declares how many items the task will be split into; ReportFinishedSubTask counts each finished item and returns true to exactly the one that closed the join; and the thread that got true is the one that dispatches the successor (TaskStream::TryExecuteWorkItem() in Engine/Core/TaskStream.cpp calls WorkItem::Run and, on true, TaskSystem::DispatchSuccessor). 

if (workItem->Run(*task))
{
    taskSys.DispatchSuccessor(task->GetID());
}

From Engine/Core/TaskStream.cpp, TaskStream::TryExecuteWorkItem()

The join counter is 8 bits, so 255 items is the ceiling. MaxNumSubTasks is the width of numFinishedSubTasks, not a policy limit, and the one splitter in the engine clamps to it rather than refusing: TaskSystem::RunSplit() in Engine/Core/TaskSystem.cpp caps the requested sub-job count at Task::MaxNumSubTasks. A request for a thousand slices becomes 255 slices, each covering more of the range — the split still covers every item, it just runs in fewer, larger pieces.
Reserving is not optional, and doing it late is a hang. The join is decided by counting finished items against the reserved figure, so a task that queues two items and reserves one reports itself finished when the first item closes — and a caller waiting on the second never wakes. TaskSystem::EnqueueTask() reserves immediately before generating its one item (Engine/Core/TaskSystem.cpp), and TaskSystem::RunSplit() reserves before the loop that generates any item; both orders are load-bearing. What is optional is the reporting, not the count: a fire-and-forget job still reserves the number of items it queues and simply has nobody reading the join.
The counter cannot tell a finished task from one that never ran. HasDone is numSubTasks > 0 && finished >= numSubTasks, so a task whose executor vanished reads as not-done forever. That is why it is private: the six friends are the whole surface it is reachable through, and a customer that needs an honest answer asks what work is still queued instead.
