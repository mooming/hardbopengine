HasDone

member of hbe::Task Engine/Core/Task.h private: cannot tell a finished task from one that never ran, which is why it is not a customer API

Signature

[[nodiscard]] bool HasDone() const noexcept

Function description

Defined in the header Engine/Core/Task.h as Task::HasDone(); the body is return numSubTasks > 0 && NumFinishedSubTasks() >= numSubTasks;. Private — reachable only through the six friend declarations (TaskRegistry, WorkItem, TaskSystem, TaskProvider and the two test collections), and its callers in this repository are all inside the unit tests of Engine/Core/TaskSystem.cpp and Engine/Core/TaskRegistry.cpp.

It is ReportFinishedSubTask's comparison re-evaluated at an arbitrary moment: the same two counters, with >= instead of == and with a guard that a task which reserved nothing is never "done".

A finished task and a never-dispatched one read identically here. Both report not-done: an unreserved task by the numSubTasks > 0 test, and a task whose items were dropped, aged out or never queued because its counter never reached the reservation. A caller that waits on this therefore has no way to notice that the executor it depends on is gone, and no deadline it could honestly apply. That is why it is not a customer API: a customer asks what it can actually answer — whether work is still queued. Logger::StopTask() (Engine/Log/Logger.cpp) is the pattern: it polls TaskStream::CountPendingItems() against a deadline and reports a timeout rather than waiting on a counter that cannot explain itself.
Two reads, no snapshot. The relaxed load of numFinishedSubTasks and the plain read of numSubTasks are separate, and the counter can pass the reservation (an item generated beyond it is still counted), so >= rather than == is what makes an over-produced task still report done. The ordering guarantee that makes a completed task's results visible lives in ReportFinishedSubTask, not here: reading true off this function from another thread is not the same promise as being the call that returned true.
Within a test, wait with the harness, not with this. The tests that use it wrap it in WaitUntil (Engine/Core/TaskSystem.cpp), which carries a deadline and reports a stall as a failure instead of hanging.

Parameters

None.

Return value

TypeWhat you get
booltrue when something was reserved and at least that many items have reported in. false means "not done", never "will never run"

Examples

From Engine/Core/TaskRegistry.cpp, TaskRegistryTest

task.ReserveSubTasks(3);

const bool first = task.ReportFinishedSubTask();
const bool second = task.ReportFinishedSubTask();

if (first || second || task.HasDone())
{
    ls << "A join of three closed after two items, so whatever waits on it is woken early and reads"
       << " results that were never written." << lferr;
}

The test uses this as a witness for a claim the winner-only return cannot make: that the join had genuinely not closed yet. Note also that the task here was built by hand, so the counters work while the identity is null — this function needs no registry, which is exactly why it cannot tell whether any executor exists.
