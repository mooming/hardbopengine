GenerateSubTask

member of hbe::Task Engine/Core/Task.h private: build one item for a range and count nothing — the join was declared, not discovered here

Signature

WorkItem GenerateSubTask(TIndex start, TIndex end, uint8_t priority = 0) noexcept

Function description

Private; defined in Engine/Core/Task.cpp as Task::GenerateSubTask(). It builds one WorkItem covering [start, end) and stamps it from this task — identity, abandonment notice pair and age clock — which is the only way an item ever gets a valid identity (WorkItem::WorkItem() is private, and Task is one of its three friends). 

Assert(numGeneratedSubTasks < numSubTasks, …);

return {*this, start, end, priority};

From Engine/Core/Task.cpp, Task::GenerateSubTask()

The elided arguments are the assert's message, which names the very failure it is meant to catch: handing out a work item beyond the number the task reserved, so the task reports itself finished before that item runs.

Generating an item counts nothing. The join was declared by ReserveSubTasks, and it is the number of items that report in which closes it, so an item is only correct if the reservation already covers it. The item is a value: it is returned by value, copied into the queue on every push, and copied again when a stream re-adds it after a partial run.

The reservation check cannot fire on over-production — the counter it tests is never incremented. numGeneratedSubTasks appears five times in the engine: declared in Engine/Core/Task.h, initialised to 0 in both Task constructors, reset to 0 in LoadIntoRecord, and read here. Nothing ever adds to it. The comparison therefore reduces to 0 < numSubTasks: it catches generating an item for a task that reserved nothing, and it stays silent for every case its message describes — the second item of a task that reserved one, the fourth of a task that reserved three. The field's own description in the header ("how many work items have been handed out for this task, which is never more than numSubTasks") states a bookkeeping that does not exist. Recorded in this page's Coverage as a defect rather than glossed: the consequence is that over-production is undetected in every build, and it is exactly the mistake that makes a task report itself finished before its last item runs.
Even the check that does exist is Debug-only. Assert is an ordinary function with two definitions (Engine/Core/Debug.h): under __DEBUG__ it flushes logs, prints and std::abort()s; otherwise its body is empty. CMakeLists.txt defines __DEBUG__ for the Debug configuration and inherits it into Dev, so Release performs no check here at all — an over-produced item in Release is queued as though nothing happened.
Empty ranges are allowed. Nothing rejects start == end: the item's current starts at start, HasFinished() is then already true, and the first run of that item reports a finished subtask without the runnable doing anything meaningful — Engine/Core/TaskSystem.cpp has a test that drives exactly this (taskSys.Enqueue(task.GenerateSubTask(0, 0))).

The protected helper a producer-side TaskProvider uses, and the smallest legal shape: declare one item, build one item. The engine's own splitter does the same once for the whole job — TaskSystem::RunSplit() reserves the clamped count and then generates exactly that many items, dividing numItems into contiguous ranges — and TaskSystem::DispatchSuccessor() generates the single item that delivers an outcome to a successor.
