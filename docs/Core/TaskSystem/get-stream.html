GetStream

member of hbe::TaskSystem Engine/Core/TaskSystem.h the stream at index — and an index outside the array returns the base stream instead of failing, which is the most consequential line in this class

Signature

TaskStream& GetStream(int index) noexcept

Function description

Defined in Engine/Core/TaskSystem.cpp as TaskSystem::GetStream(). Almost every internal path reaches a stream through it: Update (:174), JoinAndClear, RequestOtherStreamsClose, DispatchToMainThread, and the wait in TestHelper::DriveUntil — a free function that takes the system by reference precisely because it needs a stream out of it. There is no const overload, so the reference it yields lets a caller enqueue, close, wake and reconfigure the stream it names.

An out-of-range index silently means the base stream. The guard's fallback is streams[0], not an assert and not a null: work addressed to a stream that does not exist is queued on stream 0 and runs there, on the engine-loop thread, inside the base frame budget. Nothing logs it. The symptoms are all behavioural — a task that takes far longer than it should, a base stream that appears to be doing someone else's work, and a budget window charged for CPU the real owner was supposed to spend. This is why HasStream exists, and why ParallelFor validates its whole stream list before splitting rather than letting a bad index take this path.
The one case that does stop is the empty array. Before Initialize and after JoinAndClear there is no element 0, so the fallback itself indexes invalidly and Array::operator[] aborts on its bounds assert. That is the only reason the claim "a bad index aborts" ever appeared to be true: it is true for the empty array and false for every other out-of-range value.

Parameters

ParameterTypeRequirement
index int A stream index between 0 and streams.Size() - 1. Anything else yields stream 0, so the precondition is real and unchecked — verify with HasStream

Return value

TypeWhat you get
TaskStream& A live, mutable reference to the stream — or to the base stream, on the fallback path. The referenced object is destroyed by JoinAndClear, so a reference held across a teardown is the next hazard
