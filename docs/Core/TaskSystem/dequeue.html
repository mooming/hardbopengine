Dequeue

member of hbe::TaskSystem Engine/Core/TaskSystem.h the taking side of the general queue: one mutex, the top item by priority, and an affinity test that decides whether this thread may have it

Signature

	void Dequeue(std::optional<WorkItem>& outTask) noexcept;

Function description

Defined at Engine/Core/TaskSystem.cpp:277. It holds the same taskQueueMutex that Enqueue takes, so the general queue is one lock for every producer and every taker. The item is the highest-priority one waiting — 0 is the least urgent — and it is copied out; the queue's copy is popped only after the caller's std::optional has been assigned.

The stated rule is that a stream which fails to take the top item because of its task-stream affinity records that fact, so that one item a thread cannot use does not block the whole general queue for everybody. The mechanism is WorkItem::affinity, a mutable TaskStreamAffinity (Engine/Core/WorkItem.h:49) — 64 bits, one per stream index.

In the engine as it stands, only the non-stream case actually fires. The affinity is touched at exactly two places outside its own unit tests — Engine/Core/TaskSystem.cpp:297 and :299, both inside this function — and nothing calls Unset. A fresh TaskStreamAffinity starts with every in-range bit reading back true, so for any real stream index Get succeeds, the guard is skipped, and the item is taken on first contact. The path that would record a refusal is reached only when Get has already returned false, and the only way to make it return false is an index at or above the mask's width. That is exactly what NonStreamIndex is: widened to unsigned int it is 4294967295, Get is out of range and answers false, Set is out of range and does nothing, and the function returns without popping. So a thread that is not a stream never takes from the general queue and is never recorded as having looked — which is the documented intent. What does not happen is the other half of the design: a stream that cannot use an item does not hand it on to a different stream, because no code marks it.
The mask is 64 bits wide; the stream count is not bounded to it. TaskStreamAffinity is TaskStreamAffinityBase<64> (Engine/Core/TaskStreamAffinity.h:103), while the number of streams comes from GetNumHardwareThreads with no upper clamp. On a machine with more than 64 hardware threads, every stream from index 64 up is out of range for the mask — Get answers false — so those streams can never take from the general queue. Nothing logs it; they simply stop being served by it.

Parameters

ParameterTypeRequirement
outTask std::optional<WorkItem>& Written on every path: set to the taken item, or reset when the queue is empty. Note that the path which declines to take because of affinity leaves it untouched — a caller that reuses the optional without resetting it will read the previous item again

Return value

void; the result is in outTask. There are three distinct outcomes — taken, empty, and declined for affinity — and the caller can only distinguish the first from the second, because the third leaves the optional as it found it.

Examples

Illustrative — no call site for this exists outside Engine/Core/TaskSystem.cpp; a stream's drain policy is what decides when to ask.

std::optional<WorkItem> item;
item.reset();
taskSys.Dequeue(item);
if (item.has_value())
{
        // run it, and report the item back to the stream that took it
}

The reset() before the call is not decoration — it is what makes the third outcome indistinguishable from the second, which is the honest reading of this signature.
