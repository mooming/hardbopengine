Dequeue

member of hbe::TaskSystem Engine/Core/TaskSystem.h the taking side of the general queue: one mutex, the top item by priority, and an affinity test that decides whether this thread may have it

Signature

void Dequeue(std::optional<WorkItem>& outTask) noexcept

Function description

Defined in Engine/Core/TaskSystem.cpp as TaskSystem::Dequeue(). It holds the same taskQueueMutex that Enqueue takes, so the general queue is one lock for every producer and every taker. The item is the highest-priority one waiting — 0 is the least urgent — and it is copied out; the queue's copy is popped only after the caller's std::optional has been assigned. 

const unsigned int streamIndex = GetCurrentStreamIndex();

auto& affinity = workItem.affinity;
if (!affinity.Get(streamIndex))
{
        affinity.Set(streamIndex);
        return;
}

From Engine/Core/TaskSystem.cpp, TaskSystem::Dequeue()

TaskStreamAffinity stores its mask inverted: a zero bit means permitted and a one bit means excluded, so a default-constructed mask permits every in-range index, Unset(i) excludes stream i, and Set(i) permits it again. The names describe the permitted set, not the bits — which is the one thing a reader must get right before the rest of this makes sense (Engine/Core/TaskStreamAffinity.h, TaskStreamAffinityBase::Get).

WorkItem's private constructor excludes the two engine streams from every item it builds, so the guard is not dormant in the engine as it stands: 

affinity.Unset(TaskSystem::GetBaseTaskStreamIndex());
affinity.Unset(TaskSystem::GetIOTaskStreamIndex());

From Engine/Core/WorkItem.cpp, WorkItem::WorkItem()

Who is askingWhat happensWhy it happens
Stream 0 (Base) or 1 (IO) Refused on the first look at a fresh head item, served on the next Those two bits are unset at construction. The guard then records the refusal by Set-ing the refusing stream — permitting itself — and returns without popping, so the same item and stream cannot refuse each other twice
A thread with no stream Never served, and never becomes eligible NonStreamIndex widened to unsigned int is out of range, where Get answers false and Set does nothing
A stream at index 64 or above Never served, and nothing logs it The mask is TaskStreamAffinityBase<64> while GetNumHardwareThreads has no upper clamp

A refusal therefore costs one attempt and bounds head-of-line blocking at a single pass — the item stays at the head untouched, and the refusing stream may take it the next time round. What the guard does not do is hand the item on: Set widens the mask for the stream that just refused and for nobody else, so the intent that a stream which cannot use an item should let another stream have it has no mechanism behind it. The general queue is reached only after a stream's own lanes come up empty and its budget allows work (Engine/Core/TaskStream.cpp, TaskStream::Update).

Parameters

ParameterTypeRequirement
outTask std::optional<WorkItem>& Written on every path: set to the taken item, or reset when the queue is empty. Note that the path which declines to take because of affinity leaves it untouched — a caller that reuses the optional without resetting it will read the previous item again

Return value

void; the result is in outTask. There are three distinct outcomes — taken, empty, and declined for affinity — and the caller can only distinguish the first from the second, because the third leaves the optional as it found it.

Examples

Illustrative — no call site for this exists outside Engine/Core/TaskSystem.cpp; a stream's drain policy is what decides when to ask.

std::optional<WorkItem> item;
item.reset();
taskSys.Dequeue(item);
if (item.has_value())
{
        // run it, and report the item back to the stream that took it
}

The reset() before the call is not decoration — it is what makes the third outcome indistinguishable from the second, which is the honest reading of this signature.
