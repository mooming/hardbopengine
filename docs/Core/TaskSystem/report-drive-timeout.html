ReportDriveTimeout

writes the error line that says a drive-until wait gave up — kept out of the template so the report does not drag the engine header into every translation unit that waits

Signature

void TaskSystem::ReportDriveTimeout(const char* waitingFor, const std::chrono::milliseconds patience) noexcept
{
        Logger::Get().AddLog(GetName(), ELogLevel::Error, [waitingFor, patience](auto& logStream)
        {
                logStream << "A thread driving the engine loop gave up waiting for " << waitingFor << " after "
                                  << patience.count() << "ms. The work was still queued, so nothing was going to run it, and a caller that proceeds from "
                                  "here usually blocks on the very thing it waited for. The intake that should have drained it is the "
                                  "first thing to look at.";
        });
}

Function description

Defined at Engine/Core/TaskSystem.cpp:171, and called from exactly one place: the end of the driving branch of DriveUntil, after the bound expires with the predicate still false.

Why it is not inside the template. DriveUntil is a header template, so anything it calls is compiled into every translation unit that drives a wait. Naming Logger there would pull the logging header into all of them for a line that runs once, on failure. Moving the report into a function defined in TaskSystem.cpp keeps the template's includes to what the loop itself needs.
The other branch of DriveUntil never calls it. A caller that is not the engine-loop thread takes the sleep-poll path, and that path returns without reporting. So a wait that times out on an application thread is invisible in the log — correct in the sense that the thread could never have driven anything, misleading in the sense that the symptom looks like silence rather than like a misuse of the API.

The wording is the diagnosis, not decoration: "the work was still queued, so nothing was going to run it" points at the intake rather than at the waiter, and the source comment for the call site says why the line exists at all — a suite that hangs reports nothing, which is how a missing drain looked for a while: no failing test, only a wall clock.

Parameters

ParameterTypeRequirement
waitingFor const char* The label the waiter was given, interpolated as-is. No ownership is taken, so it must still be valid when the log line is formatted — every call site passes a string literal
patience std::chrono::milliseconds The requested bound, printed as count() milliseconds — not a measurement of how long the wait actually took, which can run longer because the loop decrements a counter instead of reading a deadline

Return value

void. The log line is the entire effect.
