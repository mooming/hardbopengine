RunSplit

member of hbe::TaskSystem Engine/Core/TaskSystem.h the private half of ParallelFor: clamps the counts, records the routing, then hands out contiguous ranges round-robin — the only place the range arithmetic lives

Signature

	TaskID RunSplit(StaticString taskName, TRunnable func, void* userData, TIndex numItems, TIndex numSubJobs,
					TIndex successorStream) noexcept;

Function description

Declared in the public block of Engine/Core/TaskSystem.h but documented as engine-internal: it is the body both ParallelFor forms call once they have validated their own stream arguments, and it is where the two forms stop differing. Defined in Engine/Core/TaskSystem.cpp as TaskSystem::RunSplit().

#StepDetail
1 Refuse a zero or negative count numItems <= 0 or numSubJobs <= 0 → logged, null identity. The counts are signed, and a negative one turns into an enormous range the moment it reaches an index
2 Refuse a successor with nowhere to run Non-null successor and successorStream that is not a stream → logged, null identity
3 Clamp, twice, silently numSubJobs down to numItems, then to Task::MaxNumSubTasks (255) because the join counter is 8 bits. Fewer units of work, same coverage
4 Create and look up the record CreateTask then FindTask; a null record is logged as "The registry is at its capacity" and nothing is queued
5 Record the routing before anything can finish SetSuccessor, then the packet's destination byte from successorStream. Both before the first item exists
6 Declare the join ReserveSubTasks(numSubJobs) — the count must be true before the first item can be seen by a worker, or a task reports itself done after one item of three and a caller waiting on it never wakes up
7 Hand out ranges round-robin See the arithmetic below

The range arithmetic

const TIndex itemsLeft = numItems - itemStart;
const TIndex jobsLeft  = numSubJobs - subJob;
const TIndex itemEnd   = itemStart + (itemsLeft + jobsLeft - 1) / jobsLeft;

auto& destination = streams[streamIndices[destinationSlot]];
const auto item = task->GenerateSubTask(itemStart, itemEnd, priority);
if (priority > 0) { destination.EnqueuePriority(item); }
else              { destination.EnqueueFifo(item); }

itemStart = itemEnd;
destinationSlot = (destinationSlot + 1) % numStreamIndices;

Ceiling division, so any remainder lands on the earlier ranges: three items in two sub-jobs is 2 + 1, not 1 + 2. Ranges are contiguous and non-empty because step 3 guaranteed numSubJobs <= numItems. Stream selection is a simple cycle over the caller's list, so a split over two streams alternates item by item rather than giving each stream a block.

One queue lock per item, and nothing else. Each EnqueueFifo / EnqueuePriority takes that stream's lock for the length of a push. The function never waits for work to finish, which is what makes it callable from inside a running task's own runnable — the shape a split that finishes one stage and forks the next one needs.
MaxStreamsPerSplit is 64 so that the count form needs no allocation. ParallelFor's count form fills TIndex chosen[MaxStreamsPerSplit] on the caller's stack; the constant exists to make that array's size a compile-time fact, not because a split has ever wanted 64 streams. A job spread over more streams than that is not a shape the engine has, and the clamp keeps the choice reproducible instead of allocating.

Parameters

The same eleven as ParallelFor, already validated by whichever form reached here — except that streamIndices is now required to be a real, non-empty caller-owned array, because the cycle above indexes it.

Return value

TypeWhat you get
TaskID The created task's identity, or a null identity on any of the refusals above. Every refusal logs, because a split that silently did not happen looks exactly like a split still waiting

Examples

Illustrative — RunSplit is engine-internal; call sites go through ParallelFor, whose examples section shows the real splits.

// six items, four sub-jobs, one stream:
//   ranges handed out: [0,2) [2,4) [4,5) [5,6)
//   all four land on the same stream because the cycle has length one

The arithmetic is the whole reason this function is separate: the count form and the explicit form disagree about which streams to use, and must agree perfectly about how a range is cut.
