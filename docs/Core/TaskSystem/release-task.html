ReleaseTask

member of hbe::TaskSystem Engine/Core/TaskSystem.h stops tracking a task and returns its record to the registry — the caller's half of every CreateTask, and the one thing that makes an identity stale on purpose

Signature

	void ReleaseTask(TaskID id) noexcept;

Function description

A forward to TaskRegistry::Release at Engine/Core/TaskSystem.cpp. The record's memory is not freed — the registry keeps its banks for the life of the table — but the generation advances, so every TaskID naming that slot from before now resolves to nullptr through FindTask. That is the whole stale-identity defence in this engine, and it only works if records are actually released.

Ownership of an identity is the caller's, and the engine does not take it back. Nothing releases a task whose join has closed: the engine has no reason to hold a record a caller still owns, and a task whose identity was never kept is a record that stays live until the registry is torn down. ParallelFor states the same rule for splits.

A release nobody noticed is reported, not tolerated. Releasing an identity that is not live — null, never issued, or already released — changes nothing and is logged. A double release that went unnoticed would hand one record to two tasks, which is the kind of corruption that shows up much later as an unrelated task misbehaving.
Releasing a task while something is waiting on it abandons an outcome. If a successor was recorded with SetSuccessor and the successor is released before its producer finishes, DispatchSuccessor finds it untracked, logs that "a successor released while its producer ran abandoned the outcome it asked for", and dispatches nothing. Releasing the *producer* is worse: the chain has no source to read a successor from at all. Neither is detected at the moment it happens — only at delivery, if anything was ever going to be delivered.

Parameters

ParameterTypeRequirement
id TaskID An identity the caller owns and is finished with — the result of CreateTask or ParallelFor. Once released, every pointer obtained from FindTask for it is reading a record that may be reissued at any moment

Return value

void. Success is silent; the failure case is a log line.

Examples

Illustrative — no engine code outside the task-system unit tests releases an identity; the tests do it through a scope guard rather than at a call site a page can quote.

const TaskID id = taskSys.CreateTask("Stage", &Run, data);
if (auto* task = taskSys.FindTask(id); task != nullptr)
{
        taskSys.EnqueueTask(worker, *task);
        ...
}
taskSys.ReleaseTask(id);   // the packet is no longer wanted; the record goes back

The rule the snippet is really showing: release last, after the last pointer derived from the identity is dropped, and release once — the second time is the case the registry logs.
