GetSuccessor

reads the successor recorded for a task, or a null identity when nobody is waiting on its join

Signature

TaskID GetSuccessor(TaskID task) noexcept
{
        return taskRegistry.GetSuccessor(task);
}

Function description

A forward to TaskRegistry::GetSuccessor, defined at Engine/Core/TaskSystem.cpp:327. It reads one field of the producer's record and returns it. A null identity means no successor was recorded — which is the normal case, and the fire-and-forget case, and the case where routing was never attempted because ParallelFor refused the call before getting as far as SetSuccessor.

It answers "who is recorded", nothing more. It cannot say whether that successor is still tracked (FindTask answers that), whether it reserved a subtask, or whether the producer's packet names a destination stream — all three of which DispatchSuccessor must have, and each of which it checks separately and reports separately.

It also tells you when routing was left undone. After a split has been created with a successor, a null from here means the record did not take — usually because the identity passed to SetSuccessor was not tracked. Reading it back after building a chain is the cheapest check in this part of the API, and it is the one that catches a chain assembled from the wrong end.

Parameters

ParameterTypeRequirement
task TaskID The producer whose routing is being asked about. An untracked or null identity returns a null identity — the registry has no record to read and does not report which of the two it was

Return value

TypeWhat you get
TaskID The recorded successor, or a null TaskID. The value is a copy of an identity, so it stays readable after the producer is released — and a successor that has since been released resolves to nullptr through FindTask

Examples

Illustrative — the engine reads the successor inside DispatchSuccessor rather than exposing a call site for this forward.

const TaskID next = taskSys.GetSuccessor(producer);
if (!next.IsNull() && taskSys.FindTask(next) == nullptr)
{
        // recorded, but no longer tracked: delivery will be refused and logged
}

The two tests together are what a chain needs before it can be trusted: recorded, and still there. Delivery checks the same two, and its refusal message names the pair — see the five refusals on DispatchSuccessor.
