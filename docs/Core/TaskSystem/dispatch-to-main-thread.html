DispatchToMainThread

member of hbe::TaskSystem Engine/Core/TaskSystem.h posts a callable to the thread that drives Engine::Run — the base stream's own posted queue, drained at the top of every pass, which is why there is no "process main thread tasks" call to go with it

Signature

void DispatchToMainThread(TMainThreadTask task, void* userData, uint8_t priority = 128) noexcept

Function description

One forward, at Engine/Core/TaskSystem.cpp, to the base stream's DispatchPostedTasks, which enqueues into that stream's postedTasks. TMainThreadTask is void (*)(void* userData) — a plain callable plus one pointer, not a TRunnable and not a work item: nothing reserves a join, and nothing reports completion.

"Main thread" is the engine-loop thread, and there is exactly one queue for it. There used to be a MainThreadTaskQueue facility beside the task system alongside a base-stream queue, and a call named ProcessMainThreadTasks to drain one of them; two queues for one thread was the reason a wait on "the main thread" could be satisfied by a queue the pump never read. The facility was absorbed — the base stream owns postedTasks, and the drain happens at the top of every pass (Engine/Core/TaskStream.cpp), so a thread driving the stream reaches posted work without knowing it exists. That is why the header carries a posting call and no draining call: the draining is part of Update.

Priority defaults to 128, and the number is not arbitrary. 0 is the least urgent and 255 the most; the default used to be 0 under the old "0 = highest" convention, so inverting the direction without moving the default would have sent every existing caller to the bottom of the queue instead of the top. 128 is MainThreadTaskQueue's own default, which keeps a caller that never thinks about priority where it always was.

Posted work runs only while something is pumping the base stream. Nothing waits for a driver, and no thread is created for this: if the run loop is not calling Update, the callable sits in the queue indefinitely. Two consequences that have both been paid for. First, a caller that needs the work done must be on the thread that can drive it, which is what TestHelper::DriveUntil exists for. Second, posted callables still in the queue at shutdown are the one kind of abandoned work JoinAndClear can only report as present rather than count — the queue says whether it holds any, and inventing a number would be a guess printed as a measurement.

Parameters

ParameterTypeRequirement
task TMainThreadTask void (*)(void* userData). A captureless lambda converts to it; a lambda that captures state passes that state through userData and takes it mutable at the call site, as the window backend does
userData void* Handed to the callable untouched. It must outlive the drain, which is unbounded until something pumps — so state on a stack needs a wait, not just a post
priority uint8_t 0 least urgent, 255 most, default 128. Ordering inside the posted queue; it is not a lane and not a task-system priority — see Enqueue for the distinction

Return value

void. The post cannot fail, and it cannot report when the callable runs — the only witness is whatever the callable writes.
