ParallelFor

member of hbe::TaskSystem Engine/Core/TaskSystem.h splits a heavy job into sub-jobs across streams and returns immediately — two forms, one because it names the streams and one because it only knows how many it wants, and neither of them waits

									 TIndex successorStream = NonStreamIndex) noexcept;

	[[nodiscard]] TaskID ParallelFor(StaticString taskName, TRunnable func, void* userData, TIndex numItems,
									 TIndex numSubJobs, TIndex numStreams, uint8_t priority = 0, TaskID successor = {},
									 TIndex successorStream = NonStreamIndex) noexcept;

Function description

Both forms end in the same private work (RunSplit) and neither ever blocks. The engine creates the task, declares the join with ReserveSubTasks, queues one work item per contiguous non-empty range round-robin over the chosen streams, and returns. The last item to report in closes the join, and the join dispatches the successor the caller named — so a caller that wants to combine results supplies a task to do the combining, not a thread to park. The shape this retires is a busy-wait, which occupies a stream thread for the whole duration, and a stream thread is the scarcest thing the engine has.

What each form refuses

ConditionExplicit formCount form
numItems <= 0 or numSubJobs <= 0 Refused, logged. These counts are signed, and a negative one becomes an enormous range the moment it is used as an index — so a refusal, not an empty split
Stream list is nullptr or empty Refused, logged: "Naming the streams is the point of this form" n/a
A named index is not a stream Refuses the whole call, logged — silently dropping part of the list would produce a split that runs somewhere else while looking configured n/a
numStreams <= 0 n/a Refused, logged
No worker stream exists Runs on whatever streams were named, including base or IO Refused, logged: "a split is never placed on either of its own accord". Defensive as configured — ENGINE_MIN_HARDWARE_THREADS is 4, so a machine that reaches this line has at least two workers
A successor is named and successorStream is not a stream Refused, logged. A split has no producer to write the routing into its packet, so this argument is where that byte comes from
Registry has no free record Refused, logged ("The registry is at its capacity")

What gets clamped, silently

numSubJobs is clamped down to numItems, because an empty range is a work item that reports in for nothing, and further down to Task::MaxNumSubTasks — 255 — because the join counter is 8 bits. Neither clamp is a refusal: the split still covers every item, with fewer units of work. The unit tests assert both, at Engine/Core/TaskSystem.cpp (three items, ten requested sub-jobs) and :2826 (more requested than 255).

Per-item output belongs to the caller, and it has to go in indexed slots. One task holds one 128-byte result packet, so the sub-jobs of one split cannot each own a packet. Memory that userData names is where results go, and they must be written at slots addressed by index rather than accumulated: items reach different streams and finish in an order nobody controls, so a shared accumulator is a data race that usually passes — which is worse than one that fails. The combine happens in the successor's runnable, and must be order-independent or ordered by that index. Deriving a slot from the range start, which every runnable receives, is how a runnable knows which slot is its own.
One split, one priority band. priority == 0 sends every item down each destination stream's FIFO lane; anything above sends them all down that stream's priority lane. A split cannot carry per-item bands, because the items are this call's, not the caller's.

The count form chooses from the worker range only — never the base stream, never the IO stream — starting at GetIOTaskStreamIndex() + 1 and taking up to min(numStreams, numWorkers, MaxStreamsPerSplit) contiguous streams, which makes the choice reproducible for a given engine configuration. Asking for more streams than exist clamps rather than refusing; a caller that needs specific streams should name them, which is what the other form is for. The reproducibility has a consequence worth knowing: two splits of the same size ask for the same streams, because "reproducible" and "starts from the first worker" are the same rule.

The caller owns what comes back. Release the identity with ReleaseTask when the packet is no longer wanted: nothing else will, and a split whose identity was never kept is a record that stays live until the registry is torn down.

Return value

TypeWhat you get
TaskID The identity of the created task, or a null TaskID if the call was refused. On a refusal nothing was created and nothing was queued; each one is logged with the task name. The identity is the caller's to release
