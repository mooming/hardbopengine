DriveUntil

waits for a predicate by driving the base stream — if the caller is the thread that owns it. From any other thread the same call is a sleep-poll that cannot make the condition come true

Signature

template <class Predicate>
bool DriveUntil(const char* waitingFor, Predicate&& isDone,
                std::chrono::milliseconds patience = std::chrono::milliseconds(30000)) noexcept
{
        TaskStream& baseStream = GetStream(GetBaseTaskStreamIndex());
        auto remaining = patience;

        if (std::this_thread::get_id() != baseStream.GetThreadID())
        {
                while (!isDone() && remaining > std::chrono::milliseconds::zero())
                {
                        std::this_thread::sleep_for(std::chrono::milliseconds(1));
                        remaining -= std::chrono::milliseconds(1);
                }
                return isDone();
        }

        baseStream.SetNestedPumpAllowed(true);

        struct NestedPumpGuard
        {
                TaskStream& stream;
                ~NestedPumpGuard() { stream.SetNestedPumpAllowed(false); }
        } nestedPumpGuard{baseStream};

        while (!isDone() && remaining > std::chrono::milliseconds::zero())
        {
                Update();   // not baseStream.Update — see below
                std::this_thread::sleep_for(std::chrono::milliseconds(1));
                remaining -= std::chrono::milliseconds(1);
        }

        if (!isDone())
        {
                ReportDriveTimeout(waitingFor, patience);
        }

        return isDone();
}

Function description

A member template defined in the header, because a predicate cannot live anywhere else. Its purpose is the one wait that is legitimate on the thread that drives the engine: work is already queued, the caller needs it done, and on this engine the only way it gets done on this thread is for this thread to run it. Parking a stream thread on a condition variable is the shape the task system exists to avoid.

The two behaviours

CallerWhat the loop doesOn giving up
The engine-loop thread — the one the base stream recorded at Engine/Core/TaskStream.cpp:305-307 Update plus a 1 ms sleep per iteration, nested pumping allowed for the duration ReportDriveTimeout logs an error naming what was waited for and how long it tried
Any other thread Sleeps 1 ms and re-tests. It cannot drive anything — it does not own the base stream, and a second driver would break the one-driver rule that Update depends on Silent. The reporting call is inside the driving branch only; a foreign thread's timeout produces no log line at all
The inner loop calls Update(), not baseStream.Update(). Left as a comment in the source and worth keeping: a callback posted to the engine loop lives on the stream the loop drives, and a stream's pump is what runs it. Going straight to the stream would run its lanes but skip what the task system wraps around that — including the budget-window pass that lets a throttled stream take anything at all.
SetNestedPumpAllowed is a gate, not a flag. This call can be reached while the base stream is already being pumped — a task running on the base stream that waits for something else is exactly that case — and re-entering a pump is allowed only for a caller that has said so. The guard's destructor clears it on every exit path, so a nested drive does not leave the stream permanently re-entrant.

The 1 ms sleep is a yield, not a poll rate: the predicate is usually set by work this very thread is running, so the sleep costs one millisecond per unfinished unit and keeps the loop from spinning the core while it drives.

Parameters

ParameterTypeRequirement
Predicate template parameter Anything callable as bool(). Bound by forwarding reference, so a lambda that captures by reference is the normal case
waitingFor const char* A literal naming the condition, used in the timeout report. It is stored only for the length of the call, but it must be a string literal or equivalent, not a temporary
isDone Predicate&& Tested before the first pass and after each one. Must not block: it runs on the thread that is trying to make it true
patience std::chrono::milliseconds Wall-clock bound, defaulting to 30 000 ms. Decremented by the sleep rather than measured against a deadline, so a call that overshoots each sleep drifts slightly longer than named
(function parameters) — Three, all above; the template parameter is not a call argument

Return value

TypeWhat you get
bool The predicate's final value. false means the bound expired: the work was still queued, nothing was going to run it, and a caller that proceeds from here usually blocks on the very thing it waited for

Examples

const bool isReady = taskSystem.DriveUntil("window creation", [&windowFuture]()
{ return windowFuture.wait_for(std::chrono::seconds::zero()) == std::future_status::ready; });

if (!isReady)
{
        ls << "The engine loop never ran the posted window creation, so there is no window to examine." << lferr;
        return;
}

Engine/OSAL/Window.cpp:123-130, and the same shape again at :235. This is the window backend's unit-test region — the file's test code begins at its #ifdef __UNIT_TEST__ on line 25, so it is built only in a test configuration. What it demonstrates is the whole point of the function: the work is posted with DispatchToMainThread, and the waiting thread is the one that drives the base stream, so the predicate can only become true because of the driving this call does. The result is checked, and the failure message says what it means — no window exists to look at.
