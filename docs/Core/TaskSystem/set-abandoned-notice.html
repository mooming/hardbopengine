SetAbandonedNotice

member of hbe::TaskSystem Engine/Core/TaskSystem.h opts a task in to being told when its work is discarded without running — stored on the record, copied into each item, and fired on whichever thread dropped it

Signature

void SetAbandonedNotice(TaskID task, FAbandonedNotice handler, void* userData = nullptr) noexcept

Function description

Two field writes on the task record, guarded by FindTask. The handler type is void (*)(TaskID abandonedTask, void* userData) noexcept (Engine/Core/WorkItem.h). A task nobody asked about notifies nobody: the record's default is nullptr, and the engine checks that pointer before every call.

The notice is set on the task and each work item copies it at generation (Engine/Core/WorkItem.cpp), so one call covers every item the task later produces — a ParallelFor split needs one notice for its dozen sub-jobs, not one per item.

What gets reported

Every drop path inside TaskStream fires it, and there are three:

DropWhereAlso reported by the engine
The task was released between the queueing and the take Engine/Core/TaskStream.cpp ReportReleasedTask
The item aged out — the drain policy judged it too old to be worth starting Engine/Core/TaskStream.cpp ReportAgedOutWorkItem, with the age
The stream closed with work still held AbandonHeldWork, Engine/Core/TaskStream.cpp The shutdown report in JoinAndClear, for base-stream work
Set it before the task is offered, and accept the window. Once work is queued the engine may drop an item before this call lands, which loses the notice rather than racing it. There is deliberately no lock to close that window: a mutex on the offer path to protect an opt-in courtesy is the trade this engine has already refused twice. The call is therefore a request to be told about the future, not a guarantee about items that already exist.
The handler runs on the thread that dropped the work, which may be a worker mid-shift. Not a dedicated reporting thread, and not necessarily the thread that queued it. Do not block in it. And do not look the task record up from inside it — the first drop case above is "the record is gone", so a handler that calls FindTask is asking for the thing that just failed. Act on abandonedTask and userData, or hand both to something else.

Parameters

ParameterTypeRequirement
task TaskID A tracked task. An untracked identity is skipped in silence — the if has no else, and a miss here means no notice will ever fire
handler FAbandonedNotice nullptr clears the notice, which is also the default. Must be noexcept: it is called from drop paths that are themselves noexcept
userData void* Handed to the handler untouched and never cleared by the engine. Its lifetime is the requestor's to guarantee, and it must outlive every drop this task's work can suffer — which, for a queued item, is unbounded until it runs or is dropped

Return value

void. It does not report whether the task was tracked, so a call made against a stale identity is indistinguishable from one that took.

Examples

Illustrative — no engine code calls this; the task-system unit tests exercise it with a probe handler and a sentinel user-data pointer, asserting both arrive intact (Engine/Core/TaskSystem.cpp).

void OnDropped(TaskID dropped, void* userData) noexcept
{
        auto* pending = static_cast<std::atomic<int>*>(userData);
        pending->fetch_sub(1, std::memory_order_relaxed);   // never block, never re-look-up the task
}

taskSys.CreateTask("Upload", &RunUpload, &job);
taskSys.SetAbandonedNotice(id, &OnDropped, &outstandingCount);   // before the task is offered

The handler takes the identity and the pointer and does nothing but arithmetic — which is the shape the two hazards above add up to. The engine's own silence test is worth knowing: an item whose notice is nullptr must produce no call at all, so "the notice never fired" is not by itself proof that nothing was dropped.
