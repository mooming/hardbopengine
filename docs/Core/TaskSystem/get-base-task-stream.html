GetBaseTaskStream

the stream at index 0 as a typed reference — the same object GetStream hands out, without the fallback that hides a bad index

Signature

auto& GetBaseTaskStream() noexcept
{
        return streams[GetBaseTaskStreamIndex()];
}

auto& GetBaseTaskStream() const noexcept
{
        return streams[GetBaseTaskStreamIndex()];
}

Function description

Two inline overloads, identical in shape to GetIOTaskStream with a different constant. The deduced return type is TaskStream& or const TaskStream& depending on which overload the call resolves through.

It differs from GetStream in one way that matters: there is no bounds path. The index is a constant, so an out-of-range value is impossible — but an empty array still reaches Array::operator[]'s bounds assert and aborts. Before Initialize and after JoinAndClear, this is the accessor that stops rather than lying.

Nothing in the engine calls it. The base stream is reached internally through GetStream(GetBaseTaskStreamIndex()), which is the same object by a longer road — Update, JoinAndClear and DispatchToMainThread all do that. So this accessor exists for callers outside the class, and its absence from the engine's own code is the reason the two spellings coexist.

Parameters

None.

Return value

TypeWhat you get
TaskStream& / const TaskStream& Stream 0 — the one that rides the engine loop, drains posted callables at the top of every pass, and is the last executor to close. It is not the caller's thread unless the caller is the engine loop: see IsBaseThread

Examples

Illustrative — no call site for this exists in Engine/, Applications/ or Examples/.

auto& base = taskSys.GetBaseTaskStream();
if (base.HasPostedTasks())
{
        // someone posted to the main thread and nothing has drained it yet
}

Which is the useful thing to ask here rather than through GetStream: with a constant index there is no fallback path to mistake for success.
