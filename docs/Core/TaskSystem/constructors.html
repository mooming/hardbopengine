TaskSystem

records the constructing thread as the one that will drive Engine::Run, reads the hardware thread count, and starts nothing

Signature

TaskSystem() noexcept
    : isRunning(false)
    , name("TaskSystem")
    , numHardwareThreads(GetNumHardwareThreads())
    , engineLoopThreadID(std::this_thread::get_id())
{
        FatalAssert(numHardwareThreads > 0, "It should have at least one hardware thread.");
}

Function description

A process has exactly one of these, and it is a direct member of Engine at Engine/Engine/Engine.h:48 — not heap-allocated, not registered anywhere. Constructing an Engine therefore constructs the task system, on whatever thread the application constructed the engine on.

The one decision this constructor makes for the rest of the process is engineLoopThreadID. It captures std::this_thread::get_id() at construction, and two later operations test against it: BuildStreams asserts it before creating any stream, and JoinAndClear pumps the base stream only when the caller is that thread. So constructing on a thread that never runs the engine loop is not a style violation — it is a shutdown that will not pump, and a build that asserts.

Construction stops when the thread count is not computable. GetNumHardwareThreads returns std::thread::hardware_concurrency() unchanged, and that call is permitted to report 0 when the count is unrepresentable or simply not determined. The FatalAssert at Engine/Core/TaskSystem.cpp:76 turns a 0 into a halt at construction rather than a task system that owns no streams and pumps nothing, which is the cheaper failure: the alternative is an engine that starts and never runs a task.

Nothing runs here. streams is an empty Array<TaskStream>, isRunning is false, and no thread exists. The engine's run loop reads isRunning immediately, so a task system between construction and Initialize is one the loop would exit at once.

Parameters

None.

Return value

A constructed but inactive task system: no streams, isRunning false, nothing scheduled. It becomes usable only after Initialize has built the streams.

The declaration is the whole call site, at Engine/Engine/Engine.h:48. Because it is a member and not a pointer, the task system is constructed during Engine's own construction and destroyed during its destruction, which is why the destructor is a real teardown path and not a formality — see destructor. Its position in the block also fixes the order: the logger is constructed before the task system and destroyed after it, which is what lets JoinAndClear still write an error line about abandoned work.
