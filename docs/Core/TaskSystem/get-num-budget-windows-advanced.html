GetNumBudgetWindowsAdvanced

member of hbe::TaskSystem Engine/Core/TaskSystem.h how many budget windows have closed since the task system was built — the number that makes RunBudgetWindowPass provable rather than plausible

Signature

	[[nodiscard]] std::size_t GetNumBudgetWindowsAdvanced() const noexcept;

Function description

A relaxed load of the counter RunBudgetWindowPass increments once per base frame period. It exists because a stream that reopens on schedule looks exactly like a stream that was never throttled: the observable behaviour of "budget working" and "budget absent" is the same, so the pass needed a number of its own to be checkable at all.

Which makes it the assertion a test or a diagnostic writes down: if the figure is not climbing at roughly the base frame rate, the base stream is not being driven, and every stream's CPU allowance is stale — no stream takes from its own lanes on a spent allowance. If it is climbing while tasks do not run, the fault is downstream of the window.

Relaxed, and meant to be. The counter is a witness, not a gate: nothing branches on it inside the engine. A read concurrent with an advance returns whichever increment completed last, with no ordering against anything else — enough to prove liveness, not enough to build a decision on.

Parameters

None.

Return value

TypeWhat you get
std::size_t Windows closed since construction. It counts advances, not elapsed time, so a process suspended for a minute advances nothing for that minute

Examples

Illustrative — the engine never reads its own counter; a diagnostic or a test is the intended reader.

const auto before = taskSys.GetNumBudgetWindowsAdvanced();
taskSys.Update();   // the base stream's pass asks for the window pass
const bool alive = taskSys.GetNumBudgetWindowsAdvanced() > before;

The comparison over one Update is deliberately weak, because a period may not have elapsed. Over a few hundred milliseconds the figure should advance a handful of times; over a second at 60 Hz base rate, tens.
