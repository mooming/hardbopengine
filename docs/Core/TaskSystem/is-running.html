IsRunning

member of hbe::TaskSystem Engine/Core/TaskSystem.h hands out the std::atomic<bool> itself rather than a copy of it — which is why the run loop can poll it without a call of its own

Signature

	[[nodiscard]] bool IsRunning() const noexcept;

Function description

Declared at Engine/Core/TaskSystem.h:109 and defined at Engine/Core/TaskSystem.cpp:568. The return type is bool, not the atomic: the body is one load() with std::memory_order_acquire, so a caller cannot store through it and cannot read a stale copy. Before the body moved out of the class the method returned const std::atomic<bool>&, and only because auto& deduced it; a definition outside the class needs a written type, and the written type chosen is the answer rather than the member.

Two places write the flag and nothing else does: Initialize sets it through BuildStreams, and RequestShutDown clears it. Every other reader goes through this accessor, and the only engine-side reader is Engine::Run.

The read is an acquire load, so it is a synchronization point. The run loop's condition while (taskSystem.IsRunning()) re-reads the flag on every test with acquire ordering — it is not a cached value and it is not a relaxed read. That is what lets a task on any stream end the process by clearing the flag: the loop sees it on its next condition test, with no notification involved. The other half of that is that nothing here debounces the read; a loop that polls it in a tight spin is hammering an atomic across cores.

Parameters

None.

Return value

const std::atomic<bool>& The flag itself, not a snapshot. load(), implicit conversion to bool, and comparison are all available; store() is not — the flag is changed by RequestShutDown, never by a reader
