Enqueue

member of hbe::TaskSystem Engine/Core/TaskSystem.h three overloads, two destinations: name no stream and the item waits in the shared general queue, name one and it goes onto that stream's FIFO or priority lane

Function description

The general-queue form

void TaskSystem::Enqueue(const WorkItem& task) noexcept
{
        std::scoped_lock<std::mutex> lock(taskQueueMutex);
        taskQueue.Push(task);
}

One mutex (taskQueueMutex) guarding one BoundedPriorityQueue<WorkItem>, at Engine/Core/TaskSystem.cpp:271. "Low priority" describes when it is consulted, not how the item is treated: a stream drains its own lanes first and reaches into the general queue afterwards, and Dequeue is the taking side of that. Bounded refers to the priority range — 256 buckets — not to the number of items: Push checks nothing and the queue grows.

The indexed forms

void TaskSystem::Enqueue(const TIndex streamIndex, const WorkItem& task) noexcept
{
        Enqueue(streamIndex, task, StreamDrainPolicy::ELane::Fifo);
}

void TaskSystem::Enqueue(const TIndex streamIndex, const WorkItem& task,
                                                           const StreamDrainPolicy::ELane lane) noexcept
{
        if (!streams.IsValidIndex(streamIndex))
        {
                Assert(false, "Invalid stream index %d", streamIndex);
                return;
        }

        switch (lane)
        {
                case StreamDrainPolicy::ELane::Fifo:     streams[streamIndex].EnqueueFifo(task);     break;
                case StreamDrainPolicy::ELane::Priority: streams[streamIndex].EnqueuePriority(task); break;
                case StreamDrainPolicy::ELane::None:     Assert(false, "...ELane::None...");        break;
        }
}

The two-argument form is a forward to the three-argument one with ELane::Fifo (Engine/Core/TaskSystem.cpp:350), so there is one behaviour with two spellings. Neither form can refuse a task for capacity: a stream used to refuse a task that declared more results than it could fit, and that question stopped existing when a result moved into the task's own record, which is allocated when the task is created.

Lane and priority are two different things and this API keeps them apart. The lane is which queue serves the work; WorkItem::priority is the ordering inside the priority queue. Before the lane overload existed, the lane was decided by which internal function a caller happened to reach, and the engine's public surface could only reach the FIFO lane — so the priority lane, its share of the drain rate, and its half of the shutdown drain were unreachable from the public API. That is recorded as decision 5 in the task-system redesign notes.
An out-of-range index discards the item, and in Dev and Release it does so in silence. The guard calls Assert(false, …) and then returns. Assert is defined twice, and the definition outside __DEBUG__ is empty (Engine/Core/Debug.h:72-79) — only FatalAssert survives in every configuration (Engine/Core/Debug.h:85). So the abort is a Debug-build behaviour, while the return is unconditional: outside Debug the work item is gone, with no log line and no error, and the task whose item it was never runs. ELane::None behaves the same way for the same reason. Use HasStream before indexing a stream you did not create yourself.

Parameters

ParameterTypeRequirement
streamIndex TIndex (int) A stream between 0 and streams.Size() - 1. Only in the two indexed forms
task const WorkItem& A work item, copied into the queue. Build it from a tracked task with Task::GenerateSubTask, or let EnqueueTask do that — a hand-built item carries a task identity a stream must be able to resolve, or the item is dropped at run time
lane StreamDrainPolicy::ELane Fifo for arrival order, Priority for highest priority first with the oldest winning a tie. None names no queue and is a caller error — see the hazard above. Only in the three-argument form

Return value

void in all three forms. None of them reports whether the item was accepted, which is precisely the hazard above.
