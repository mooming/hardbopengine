GetCurrentThreadName

the other door onto the same thread_local name, and the one the engine actually prints

Signature

static StaticString GetCurrentThreadName() noexcept
{
        return ThreadName;
}

Function description

Byte for byte the body of GetCurrentStreamName (Engine/Core/TaskSystem.cpp:50 against :45): both return thread_local StaticString ThreadName, which only SetThreadName writes. The two functions cannot report different values on the same thread, in any state, at any time.

The name's meaning depends on who set it, and the engine sets it three ways. A stream's own thread is labelled with the stream's name ("Worker3", "Base", "IO") by TaskStream::RunLoop; the engine-loop thread is labelled "EngineLoop" by BuildStreams; and the logger's driver thread labels itself "LogDriver" (Engine/Log/Logger.cpp:205) while driving the IO stream. A thread nobody named returns a default-constructed StaticString — an application thread, most of the time.

The name is not the OS's. No code in the engine calls a platform thread-naming API, so nothing outside this process can see the value — see the hazard on SetThreadName. It is a log line that was moved into a thread_local so it could be asked for.

Parameters

None.

Return value

TypeWhat you get
StaticString The last name stored on this thread, or a default-constructed StaticString if none was. Not a copy of the bytes

Examples

From Engine/Core/TaskSystem.cpp

ls << "... this thread reports stream index " << TaskSystem::GetCurrentStreamIndex() << " named \""
   << TaskSystem::GetCurrentThreadName().c_str() << "\" and IsBaseThread = " << TaskSystem::IsBaseThread()

A stream-identity failure report in the task-system unit tests, at Engine/Core/TaskSystem.cpp:2103-2105. All three facts are printed together because they are three views of the same thread_local state, and a wrong one of them is the diagnosis: an index that disagrees with the name means a claim that was never restored.
