BuildStreams

member of hbe::TaskSystem Engine/Core/TaskSystem.h creates every stream, names this thread, starts the ones that own threads, and hands the IO stream to the logger — private, called once, and the reason Initialize must be called on the right thread

Signature

	void BuildStreams();

Function description

Defined in Engine/Core/TaskSystem.cpp as TaskSystem::BuildStreams(), and it is the body of what Initialize appears to do.

#StepConsequence
1 Assert(std::this_thread::get_id() == engineLoopThreadID) The thread check is Debug-only — see the hazard below
2 FatalAssert(numHardwareThreads >= ENGINE_MIN_HARDWARE_THREADS) The minimum is 4 (Engine/Config/BuildConfig.h), so the smallest machine the engine will start on has two worker streams — indices 2 and 3
3 SetThreadName(EngineLoopThreadName) This thread's engine-internal name becomes "EngineLoop", distinct from the base stream, which is stream 0 on a thread of its own in no engine — it rides this one
4 streams.Swap(Array<TaskStream>(numHardwareThreads)) The array is sized once, for the life of the object. Any previous contents go into the temporary and are destroyed — which is why a second call is fatal rather than merely wrong
5 Emplace "Base" at 0, "IO" at 1, then "Worker1" … up to numHardwareThreads Names a log line and a debugger see; built with an InlineStringBuilder<64> so the loop allocates nothing per stream
6 isRunning = true, then stream.Start(*this) for every stream Streams that own threads spawn them; the base stream records this thread as its driver and never reaches RunLoop, and the IO stream records nothing until its first driven pass
7 Logger::Get().SetIODriver(&GetIOTaskStream()) The last statement, so the logger's thread cannot be handed a stream that is not yet constructed — and the reason Initialize implies the logger is started after the task system
The thread check does not exist outside Debug builds. Step 1 calls Assert, and Assert is defined twice — the definition selected when !RELEASE_BUILD is undefined has an empty body (Engine/Core/Debug.h). Only FatalAssert aborts in every configuration, and step 2 is a FatalAssert about core counts, not about threads. So in Dev and Release a task system can be built on a thread that will never drive it, and the failure appears later as a run loop that never drains the base stream and a shutdown that joins without pumping. Construction is what binds the identity; keeping the two on one thread is a caller obligation the code cannot enforce.
A second call terminates the process. Step 4 moves the old buffer into the temporary, and destroying a TaskStream whose std::thread is joinable calls terminate() — the stream's own destructor is = default and does not join. Nothing tests whether streams already exist.

Parameters

None. It reads numHardwareThreads from construction and the registry has already been sized by Initialize before this runs.

Return value

void. Success is a populated streams array, running threads, and the logger wired to stream 1.

Examples

Illustrative — private and called from one place: the tail of Initialize. What the result looks like, on an eight-core machine:

index 0  "Base"     driven by the engine-loop thread   (threadID recorded here, at step 6)
index 1  "IO"       driven by the logger's thread      (threadID recorded at its first pass)
index 2  "Worker1"  owns a thread, runs RunLoop
index 3  "Worker2"  owns a thread, runs RunLoop
   …     …
index 7  "Worker6"  owns a thread, runs RunLoop

Two engine streams and six workers, which is why the worker range starts at GetIOTaskStreamIndex() + 1 rather than at 2, and why the CPU-budget window pass is the base stream's job: it is the only stream whose thread is guaranteed to be running the engine.
