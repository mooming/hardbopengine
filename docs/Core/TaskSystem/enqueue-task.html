EnqueueTask

member of hbe::TaskSystem Engine/Core/TaskSystem.h the customer's entry point for single-shot work: declares the task's join, builds the one item that fills it, and queues it — in that order, which is the only order that works

Signature

	void EnqueueTask(TIndex streamIndex, Task& task, uint8_t priority = 0,
					 StreamDrainPolicy::ELane lane = StreamDrainPolicy::ELane::Fifo) noexcept;

Function description

Defined at Engine/Core/TaskSystem.cpp:341. A task declares its own join and the engine builds the item that fills it, which is the only order in which those two facts can be stated without the caller knowing anything about items. A customer that builds an item itself has reached inside the engine for a handle it should not hold — and this is the call it wants instead.

The task is offered as a single whole-range item: the runnable receives startIndex == 0 and endIndex == 1, whatever the task's own notion of size might be. Splitting is ParallelFor's job.

Call it once per task, and only on a task that declared no join. This declares a join of exactly one item, so a task that already declared one has that declaration overwritten — the earlier count is lost, and a caller waiting on the old number is waiting for reports that will never arrive. A second call on the same task also queues a second item against a join that expects one, so the join closes on whichever item reports first and the second item runs as work nobody is counting.
The reserve comes first for a reason. The join's count must be true before the first item can be seen by a worker: reserving afterwards lets a task report itself done when the one item queued has finished, which is correct here by construction — and is the trap the ordering avoids in general, since GenerateSubTask hands out an item a worker can take the instant it exists.

Lane and priority keep the distinction Enqueue documents: lane chooses the queue, priority orders within the priority lane, and the lane parameter is added last and defaulted so that EnqueueTask(i, t, 1) binds to the priority rather than to the lane. Because the underlying enqueue is the indexed form, its rules apply unchanged — including the one where an out-of-range streamIndex drops the item silently outside Debug builds.

If a successor was recorded for the task, this can complete a chain. The item closes the join, the stream that ran it calls DispatchSuccessor, and delivery proceeds or refuses under those rules — including the requirement that the packet name a destination stream. Single-shot work usually has no successor, so this only bites when a task was routed with SetSuccessor and then offered by hand.

Parameters

ParameterTypeRequirement
streamIndex TIndex (int) Which stream takes the work. An index outside the streams is a programming error, and outside Debug builds it is a silently dropped task — see HasStream
task Task& A record the registry issued, taken from FindTask. It must not already declare a join. The reference must stay valid while the item is queued, which it does as long as the record is not released early
priority uint8_t Ordering inside the priority queue, 0 least urgent; default 0. Not a lane
lane StreamDrainPolicy::ELane Which queue serves the work, Fifo by default. None is a caller error and is asserted — which outside Debug means the item is dropped

Return value

void. The identity is not returned because it was never taken: the caller already holds the task. Whether the item was accepted follows the same silence as Enqueue.
