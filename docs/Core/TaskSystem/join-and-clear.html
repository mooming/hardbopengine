JoinAndClear

asks, pumps, flushes, closes, joins and clears — the whole teardown of the task system, bounded at 2000 ms and deliberately louder when it runs out of time than when it does not

Signature

void JoinAndClear() noexcept;

Function description

Defined at Engine/Core/TaskSystem.cpp:200. The order is the contract; each step is here because the next one breaks without it.

#StepWhy it is in this position
1 Records whether the caller is the constructing thread, and whether streams exist at all Both decide which of the steps below are possible; HasStream is what keeps an already-cleared task system out of the index assert
2 RequestOtherStreamsClose, if there are streams Not asking would make the wait below one that never ends. Teardown can be reached without the ordered shutdown, since the destructor is a caller
3 baseStream.SetDrivenByShutdownPump(), then pump the base stream for up to 2000 ms while any of three conditions hold Recorded before the first pass rather than after: the whole point is that work run by this pump cannot claim the engine loop ran. The three conditions are the other streams not closed, posted tasks on the base stream, and queued items on it
4 If work remains, an Error log naming the count Never dropped quietly. A queued item left here is a promise made to a customer who will not be answered. Posted callables are reported as present rather than counted, because the queue only says whether it holds any — inventing a number would be a guess printed as a measurement
5 Logger::Get().Flush() Log lines are written by a task running on a stream, so the flush that ends the run has to happen while that stream is still running its own work. Joining first leaves the flush waiting on an executor that has already exited — a timeout and a fatal assert rather than a shutdown
6 SetIODriver(nullptr), then CloseDrivenStream() on the IO stream and then the base stream The driver thread outlives the task system, so each stream must be taken back from its driver before the streams are freed. After this the logger writes its queue directly, which keeps it working to the last line of the process
7 RequestClose() on the IO stream, then on the base stream The reporting the shutdown exists to produce is finished, so the two executors that carried it close last, in that order
8 Join every joinable thread, then Assert(stream.IsClosed()) for each stream, then streams.Clear() Nothing is destroyed that was not closed first. A stream left unclosed here means either a new stream kind nobody asked to close, or a thread still running while its queues are being freed — both cheaper as a named assert than as a crash in a later run
Only the constructing thread pumps; every other thread merely waits. Step 3 is conditioned on std::this_thread::get_id() == engineLoopThreadID. A call from any other thread asks the streams to close, joins them, and never drains the base stream — so work still posted there is abandoned with no log line about it, because the pump that would have reported it never ran. This is not a thread-safe "wait for shutdown" from an application thread; it is the shutdown, and it belongs on the thread that owns the run.
The bound is 2000 ms, and it is a measured choice. A bound that resumable work can outrun is not a bound, and this loop asks for work rather than for an end. Without it the shutdown waits on posted work that may never be drained — found by sampling, after every test had finished and nothing else could run — so the honest outcome is a named loss rather than a process that never exits.

It is safe to call twice. After the first pass the array is empty, so the second call skips steps 2 through 7, joins nothing, asserts over nothing, and clears nothing — which is exactly what ~TaskSystem relies on.

Parameters

None.

Return value

void. Whether it succeeded is visible only as what it logged: silence, or an error naming the work it had to leave behind.
