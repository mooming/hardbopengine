SetThreadName

member of hbe::TaskSystem Engine/Core/TaskSystem.h stores a name in a thread_local of the calling thread — it does not name the thread for the operating system, a debugger or top

Signature

	static void SetThreadName(StaticString name) noexcept;

Function description

One assignment to thread_local StaticString ThreadName, declared in the anonymous namespace at Engine/Core/TaskSystem.cpp:23. It affects the calling thread only, and only for the lifetime of that thread's thread_local storage.

This is not the operating system's thread name. No translation unit in the engine calls pthread_setname_np, SetThreadDescription or prctl(PR_SET_NAME) — a grep of Engine/ for all three returns nothing. So the name is invisible to lldb, top -H and any profiler that reads the OS's own thread labels; it appears only where engine code prints it, which is what GetCurrentThreadName and the log lines that use it do. Anything that names a thread for the platform has to do it separately.

Three places set it. BuildStreams labels the engine-loop thread with EngineLoopThreadName ("EngineLoop"), TaskStream::RunLoop labels each stream thread with its own stream's name at Engine/Core/TaskStream.cpp:706, and the logger's driver thread labels itself "LogDriver" at Engine/Log/Logger.cpp:205. That last one is the interesting case: the IO stream has no thread of its own — the logger's thread drives it — so that thread carries a name that is not a stream name, and GetCurrentStreamName will report LogDriver from it.

Parameters

ParameterTypeRequirement
name StaticString A name to remember for the calling thread. StaticString is a pointer and a length, so the bytes it points at must outlive the assignment — every call site in the engine passes a string literal or a stream name held by the stream itself

Return value

void. Nothing reports failure, and the name of the calling thread's previous owner is simply lost.

The first thing a stream's own thread does, before it logs its arrival, is label itself with the stream's name (Engine/Core/TaskStream.cpp:706). Everything a worker logs from then on can be attributed without passing a name through the call chain — and a task that outlives the pass that ran it will report whichever thread it happens to be running on, which is why the pairing with SetStreamIndex matters more than the name does.
