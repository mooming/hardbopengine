TaskSystem

the scheduler: a fixed set of streams, one shared general queue, a task registry that issues identities with generations, and a shutdown that has to finish the reporting before it closes the executors carrying it

Class description

class TaskSystem final at Engine/Core/TaskSystem.h:17. A process has one, as a direct member of Engine (Engine/Engine/Engine.h:48) — constructed with the engine, destroyed with it, reachable everywhere through Engine::GetTaskSystem().

Work is described twice, and both descriptions matter. A task is a record in the registry: a name, a TRunnable, a user pointer, a join counter, and a 128-byte result packet. A work item is one unit of that task's work — a range of it, an identity, an affinity and a priority. Items are what queues run; tasks are what callers hold.

PieceWhat it isWhere the contract lives
Streams One TaskStream per hardware thread: "Base" (0) riding the engine loop, "IO" (1) driven by the logger's thread, then "Worker1" … each owning a thread BuildStreams, Update, IsBaseThread
General queue One mutex, one BoundedPriorityQueue<WorkItem>, drained only after a stream's own lanes Enqueue, Dequeue
Registry Record table with generations; never grown by the create path CreateTask, FindTask, GetRegistry
Chains One successor per task, routed by the destination byte of the producer's packet; delivery is one packet copy and one push, run by the thread that closed the join SetSuccessor, DispatchSuccessor
Budgets CPU-time allowances per stream, reopened once per base frame period by request RunBudgetWindowPass, GetNumBudgetWindowsAdvanced

The lifecycle has exactly four moments, and the ordering is the design: construct on the thread that will run the engine; Initialize to size the registry and build every stream; Update in a loop while IsRunning — which is what Engine::Run does at Engine/Engine/Engine.cpp:139-143; then JoinAndClear, which is also what the destructor calls. The design rationale, including the R-numbered decisions several pages cite, is in docs/TaskSystemRedesign.md.

Two of the streams are executors without threads. The base stream is driven by Update and the IO stream by the logger, so their identity is borrowed for the length of a pass: the thread-local stream index and the allocator scope are entered and restored around each pass rather than owned for a thread's life. Almost every surprising rule in this class follows from that — IsIOThread being true only mid-pass, TestHelper::DriveUntil behaving differently on the two threads, and the shutdown order that keeps both open until the last log line is written.
Nothing in this class refuses a bad stream index in a shipped build. The indexed Enqueue and EnqueueTask assert and then drop the item; GetStream hands back the base stream instead of failing; and the thread check in BuildStreams is an Assert, which has an empty definition outside __DEBUG__ (Engine/Core/Debug.h:72-79). Only FatalAssert and the logging paths survive. So the checks that exist are for Debug builds, and the behaviour that ships is the fallback — which makes HasStream the caller's job rather than the engine's.

Template parameters

None. TaskSystem is final and takes no template parameters. It declares no template member either: the one it had — the wait now documented as TestHelper::DriveUntil — left the class on 2026-10-02.

Non-member helper functions
