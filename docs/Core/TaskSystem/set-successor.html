SetSuccessor

records which task to dispatch when this task's join closes — half of a chain, the other half being the destination byte, which this call does not set

Signature

void SetSuccessor(TaskID task, TaskID successor) noexcept
{
        taskRegistry.SetSuccessor(task, successor);
}

Function description

An inline forward to TaskRegistry::SetSuccessor at Engine/Core/TaskSystem.h. One task records one successor; when the producer's join closes, the thread that closed the join calls DispatchSuccessor, which reads this record. Chains need no engine machinery: the successor's own work item closes its join the same way and dispatches in turn, so A can wake B and B wake C without the engine knowing pipelines exist.

Record it before the first work item is queued, never after. A join that closes before the routing exists delivers to nobody, and with enough streams running that is a race rather than a bug report. RunSplit is written this way on purpose: it records the successor and fills the destination byte before it queues a single item. A caller that enqueues first and routes second has a chain that works in a debug build and stops in a fast one.
This names the successor; it does not say where it runs. Delivery is routed by the destination byte of the producer's result packet (ResultPacket::GetDestinationStreamIndex), not by anything set here. A split supplies that byte from ParallelFor's successorStream argument, because a split has no producing task to write it. An ordinary task must set the byte on its own packet, or DispatchSuccessor refuses the delivery and logs that the successor "was never dispatched" — the pair that caused it named in the message.

Parameters

ParameterTypeRequirement
task TaskID The producer — the task whose join closing should trigger the dispatch. Must be tracked; an untracked identity has nowhere to record anything
successor TaskID The task to dispatch. Must already exist and must have reserved at least one subtask, because delivery queues exactly one item covering the successor's whole range. Passing a null identity is how fire-and-forget is expressed: the join closes and nothing is dispatched

Return value

void. It does not report whether either identity is tracked — the registry has no answer to give at this moment, and the failure surfaces at delivery time in DispatchSuccessor.

Examples

From Engine/Core/TaskSystem.cpp

if (!successor.IsNull())
{
        SetSuccessor(taskID, successor);
        task->GetResult().SetDestinationStreamIndex(static_cast<std::uint8_t>(successorStream));
}

task->ReserveSubTasks(static_cast<Task::TNumSubTasks>(numSubJobs));

Inside RunSplit, before any item is queued. The two statements belong together — the pair is "who" and "where" — and ReserveSubTasks comes after them for the same reason: nothing may be able to finish before the routing exists.
