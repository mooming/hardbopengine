GetRegistry

member of hbe::TaskSystem Engine/Core/TaskSystem.h the task system's TaskRegistry, by reference — the door to capacity and growth, which the rest of this class deliberately does not expose

Signature

	[[nodiscard]] TaskRegistry& GetRegistry() noexcept;

Function description

A getter for the registry member, defined at Engine/Core/TaskSystem.cpp:573. CreateTask, FindTask, ReleaseTask, SetSuccessor and GetSuccessor are all forwards into this same object; the getter exists for what those forwards do not cover — capacity, count, and growth.

Growth is the reason to ask for it, and growth has a thread rule. CreateTask never grows the table: it hands back a null identity when the table is full. The registry's own Grow adds one bank of records and is legal only while no lookup is in flight, because a bank swap moves the storage every record pointer refers to. So the shape the engine expects is: read GetCount() and GetCapacity() to see where you are, call Grow() at a point where no task is being resolved — between frames, on the owner — and treat a refusal from CreateTask as a sizing problem to fix there. The initial and maximum sizes come from the configuration parameters Initialize reads.

A count read while other threads are creating or releasing is the last one that completed, not a snapshot a decision may be built on. It is there to be looked at, not to be raced against.

Parameters

None.

Return value

TypeWhat you get
TaskRegistry& The live registry, not a copy and not a const view. It is valid for the life of the task system: the registry is a member, cleared only when the task system is — and teardown does not release records one by one, it destroys the table

Examples

Illustrative — no engine code outside the task-system unit tests takes the registry; the engine reaches it only through the forwards above.

auto& registry = taskSys.GetRegistry();
while (registry.GetCount() == registry.GetCapacity() && registry.Grow())
{
        // between frames, with nothing in flight — see the rule above
}

The loop is deliberately at the point where a caller has decided memory may be taken. Doing it somewhere else is how a record pointer taken before the growth becomes the interesting kind of bug: still valid memory, no longer the record it named.
