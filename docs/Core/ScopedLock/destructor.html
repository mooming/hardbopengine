~ScopedLock

member of hbe::ScopedLock Engine/Core/ScopedLock.h unlocks first, then reports a hold that outstayed its timeout in a profiled build

Signature

~ScopedLock();

Function description

lockable.unlock() is the first statement of the body and is unconditional: the lock returns whether or not PROFILE_ENABLED built the timing members in. Everything after it exists only in the profiled shape.

After the unlock the profiled body measures duration = time::ToFloat(time::TStopWatch::now() - startTime) and, when timeOutSec > 0.0f && duration > timeOutSec — a branch hinted unlikely, because a guard that outstays its threshold is the exception the mechanism hunts for — emits a warning through the Log module: Logger::Get(name) with name the compact class name of this instantiation (StringUtil::ToCompactClassName(__PRETTY_FUNCTION__), e.g. ScopedLock<std::mutex>), and a message carrying the recorded call site as file(line:column) function_name, the measured duration and the threshold. The warning fires at most once per guard, at scope exit; a threshold of <= 0 never fires.

The measured span is acquisition wait plus hold time, not the wait. startTime was sampled by the constructor's member-initialization list — before lock() ran — and the stop is taken after unlock() returned. A log line therefore cannot tell you whether the mutex was contended or the critical section was long; it tells you the scope was slow. Attribute the cause by reading the recorded call site, not the number alone.

In the profiling-disabled shape — PROFILE_ENABLED 0, every configuration shipped today — the destructor body is exactly the unlock, and the class collapses to the same job as std::lock_guard.

The guard must be destroyed by the thread that constructed it. unlock() runs on whatever thread leaves the scope, and owner-tracking lockables such as std::mutex treat an unlock from a non-owner as undefined behavior. The class cannot enforce this — it stores no thread id — and cannot be rescued by moving either, because it is neither copyable nor movable: the scope that locks is the scope that unlocks, by construction.

Parameters

None.

Return value

A destructor has no return value. It is implicitly noexcept; in the profiled shape it performs a clock read, a logger lookup and a formatted write on the slow path, and the engine builds exception-free, so nothing on that path may throw.

Examples

Illustrative — no call site for this exists in the repository; see the constructors page for the state of usage.

std::mutex counterLock;
long long committedCount = 0;

void Commit(int count)
{
        hbe::ScopedLock guard(counterLock, 0.05f);   // locks here
        committedCount += count;
}                                        // unlocks here, and in a profiled build warns
                                         // if the scope outstayed 0.05 s (0.1 s if !RELEASE_BUILD)

The warning the closing brace can produce names the construction point — the srcLoc the constructor recorded — with the measured span and the threshold, under the log category ScopedLock<std::mutex>. A scope that routinely trips it is either waiting on a contended mutex or doing real work under lock; the message shows where, never which.
