ScopedLock

Engine/Core/ScopedLock.h a RAII lock guard that holds a CLockable lock for a scope, and measures the hold against a timeout when profiling is built in

Class description

ScopedLock is an RAII-style lock wrapper: it acquires a lock on construction and releases it on destruction, so a critical section is a lexical scope. There is no unlock member and no handle to misuse — the guard exists while the lock is held, and the lock is released exactly once, at the closing brace.

The class stores one thing that matters: a reference to the caller's lockable. It does not own it, so the lockable must outlive the guard. The copy constructor is deleted and no move constructor is generated, which is not a limitation but the mechanism: the thread that locks must be the thread that unlocks for owner-tracking lockables, and a guard that can neither be copied nor moved cannot leave the scope that locks it. ScopedLock is final; a guard is not a base class.

The type exists in two build shapes. When PROFILE_ENABLED is 1 the guard additionally records the clock at entry, a timeout threshold and the call site, and the destructor warns through the Log module when the scope outstayed the threshold. When it is 0 — the value Engine/Config/BuildConfig.h defines today, which no build configuration in this repository overrides — the timing members do not exist, and the extra constructors that would fill them accept their arguments and discard them, so one call-site spelling works in both shapes. See the constructors and the destructor for what each shape does.

The class template is constrained by the CLockable concept declared in the same header. Engine/Core/ScopedLock.cpp explicitly instantiates hbe::ScopedLock<std::mutex>, which is the only instantiation the repository uses; any other lockable instantiates at its point of use. There is no call site of the guard anywhere in Engine/ or Applications/ — see Coverage.

The guard is a scope discipline, not a checking layer. It ignores whatever lock() returns, does not detect recursion, does not assert thread identity, and cannot tell you that the same mutex is already held two frames up. Everything the lockable refuses — self-deadlock on a non-recursive mutex, unlocking from the wrong thread — remains exactly as refused with the guard as without it.

Template parameters

ScopedLock is constrained by a concept declared at namespace scope in the same header: 

template <typename T>
concept CLockable = requires(T t) {
        t.lock();
        t.unlock();
};
ParameterKindWhat it must satisfy
TLockable CLockable (constrained) Anything with a nullary lock() and a nullary unlock(). The concept asks for the expressions only: return values are not examined, and a type with try_lock but no plain lock does not qualify. std::mutex is the type the engine instantiates; recursive mutexes and engine-internal lockables qualify on the same two expressions, and the semantics of holding them belong to the lockable, not to the guard.

The concept is not a class and owns no folder of its own; this section is its reference.

Non-member helpers

None. ScopedLock.h declares no free functions; its namespace-scope names are the class template and the CLockable concept that constrains it.
