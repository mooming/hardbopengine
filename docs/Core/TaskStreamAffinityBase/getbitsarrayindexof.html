From Engine/Core/TaskStreamAffinity.h, TaskStreamAffinityBase::GetBitsArrayIndexOf()

Which word of bitBuffer holds a bit, and the reason the three private constants have to agree with each other. The caller pairs this index with the shift it computes itself — bitIndex - (index * BitsPerUnit) — in all three of Unset, Set and Get, so the divisor belongs to both halves: divide by bits per word here and by bytes per word there, and two streams land on the same bit.

Both halves of this arithmetic once divided by the same wrong figure, and the type still worked. The word count was derived from BitArrayUnitBytes — bytes per word where the division needed bits per word — which made the buffer eight times as long as it needed while leaving each 64-bit word holding only 8 usable bits, because this helper divided by the same figure. Both halves agreed with each other, so the encoding was correct and merely fat: a queued work item paid 64 bytes for a 64-stream mask. No behavioural test can tell the two encodings apart, which is precisely why the defect survived; the fix is pinned by a test in this module's collection (A mask reserves one word per 64 bits and not one per 8, Engine/Core/TaskStreamAffinity.cpp) that checks sizeof for the 64-bit alias and for a 517-bit instantiation.
No range check here, and none is needed. Every caller has already rejected an index at or above GetNumBits() before asking this question, so the division cannot land outside bitBuffer. Move this helper somewhere a caller can reach it without that guard and the guarantee goes with it.
