SystemStatistics

Engine/Core/SystemStatistics.h One instance of counters, timings and a shutdown report: two live figures, six structurally zero, one uninitialized.

Class description

class SystemStatistics final at Engine/Core/SystemStatistics.h: one struct of counters, four time fields, and a shutdown report. Six std::atomic<uint64_t> counters raised by the allocator and the log paths, four size_t allocation figures guarded by a mutex and compiled out, four time fields written by a function nothing calls, and one instance that lives inside Engine for the length of a run (Engine/Engine/Engine.h). It stores nothing else and owns no subsystem.

Of the eleven lines Print writes, two report real counts, six are structurally zero, and one prints an uninitialized field. The engine increments only IncEngineLogCount and IncFallbackAllocCount. IncFrameCount and IncSlowFrameCount have no call site at all, and the log-line pair and the whole allocation bookkeeping are incremented only inside #if PROFILE_ENABLED regions — a flag defined as 0 unconditionally in Engine/Config/BuildConfig.h, with no #ifndef guard, so a build cannot set it from the command line. And because UpdateCurrentTime is never called, the Running Time line prints timeSinceStart, a double the constructor never initialized (Engine/Core/SystemStatistics.cpp). The breakdown, line by line, is on Print.
The profiling half is not merely unused — it does not compile. Report, ReportSysMemAlloc and ReportSysMemDealloc are declared noexcept in the header and defined without it in the source, and a definition that omits the exception specification of its declaration is a compile error (confirmed with a minimal translation unit). So the first person to set PROFILE_ENABLED to 1 finds these three pages describing code that will not build, and the shutdown's allocation lines stay at zero until that is fixed (Engine/Core/SystemStatistics.h, Engine/Core/SystemStatistics.cpp).
Three locking disciplines in one small class, and a report that observes only the first. The atomic counters are fetch_add/load with std::memory_order_relaxed: cheap, and carrying no ordering promise about anything else. The allocation figures are plain size_t written under sysMemReportLock — but read by Print without it. The four time fields are plain and written by one non-atomic sequence (UpdateCurrentTime). At class scope, before any member, a static_assert(std::atomic<uint64_t>::is_always_lock_free) refuses to compile the class on a platform where those counters would be mutex-backed (Engine/Core/SystemStatistics.h).

Template parameters

None. The class is final, is not a template, has one instance per engine, and is constructed by Engine as a direct member — there is no variant of it to parameterize.

Non-member helper functions

None. Engine/Core/SystemStatistics.cpp holds the out-of-line definitions — seven of them, three inside #if PROFILE_ENABLED — and a using of StringUtil inside one function, and nothing else; the time helpers the definitions call — time::ToFloat, time::ToDouble, time::TStopWatch — belong to Engine/Core/Time.h and to the time utilities, not to this class (Engine/Core/Time.h).

No claim is made about other standard libraries, because none was tested
A lock order for sysMemReportLock Nothing in the sources states one, and today the lock has one writer and no reader. The race that would exist in a profiling build is recorded on Print, and stating a lock hierarchy that no code declares would be an invention
Which thread is allowed to increment what The atomics are used from the allocator paths and Engine::Log, on whichever threads those run, and every increment in the class is relaxed, which is exactly the guarantee a statistics counter needs.
