ReportSysMemAlloc

member of hbe::SystemStatistics Engine/Core/SystemStatistics.h Under PROFILE_ENABLED only: count one system allocation and track the running and peak totals.

Signature

void ReportSysMemAlloc(size_t usage) noexcept

Function description

Declared in Engine/Core/SystemStatistics.h under #if PROFILE_ENABLED, defined in Engine/Core/SystemStatistics.cpp under the same condition, compiled out in every configuration because Engine/Config/BuildConfig.h defines PROFILE_ENABLED as 0 unconditionally. This page is written from the source text; nothing here was observed running, and the build breakage recorded below is the reason nobody has.

Records one system-allocation event: under sysMemReportLock it increments allocCount, adds usage to totalUsage, keeps maxUsage at the high-water mark, and reads the new total back out of the lock before warning if the total has passed Config::MemCapacity. 

size_t localTotalUsage = 0;

{
    std::lock_guard lock(sysMemReportLock);
    ++allocCount;
    totalUsage += usage;
    maxUsage = std::max(maxUsage, totalUsage);
    localTotalUsage = totalUsage;
}

if (unlikely(localTotalUsage > Config::MemCapacity))
{
    ...
    log.OutWarning([localTotalUsage](auto& ls)
    { ls << "System Memory Usage " << localTotalUsage << " exceeds its limit " << Config::MemCapacity; });
}

From Engine/Core/SystemStatistics.cpp, SystemStatistics::ReportSysMemAlloc() (under PROFILE_ENABLED; elided: the logger lookup)

The copy out of the lock, and the warning outside it, are the whole design of this function. Logging while holding the statistics mutex would let a memory report block other memory reports; taking a snapshot of the total and warning afterwards avoids that at the cost of a warning that may describe a total already overtaken. The counter updates themselves are never lost — they are inside the lock (Engine/Core/SystemStatistics.cpp).
Nothing in a shipping build calls it, so the two figures it owns are permanently zero in the report. The single caller is MemoryManager::ReportAllocation, and it too is inside a #if PROFILE_ENABLED region, reached only for the system allocator's own traffic (Engine/Memory/MemoryManager.cpp). Print therefore writes "Allocation Count = 0 (Alloc), 0 (Dealloc)" and "System Memory Usage = 0 (0 MB) / 0 (0 MB)" in every build the engine produces, and reads those four fields without the lock this function insists on (Engine/Core/SystemStatistics.cpp).

Parameters

NameTypeMeaning
usagesize_tBytes handed out by this allocation, as the memory manager measured them — added to the running total, not maxed against it

Return value

void. The only observable output is a warning through the logger, and only for the first moment the configured capacity is exceeded; there is no count of how many allocations were over the line.

Examples

}

From Engine/Memory/MemoryManager.cpp, MemoryManager::ReportAllocation() (under PROFILE_ENABLED)

Only the system allocator's traffic is reported — pool allocations are the pools' own business (IncFallbackAllocCount counts the moment a pool falls back to the system, and is compiled in). The pairing on the other side is ReportSysMemDealloc.
