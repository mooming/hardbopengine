DetachFrom

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp Stop feeding one stream, on every lane it held, and wait for a drain already in flight.

From Engine/Core/TaskProvider.cpp (the elided loop copies each later slot down one)

One call removes the stream from every lane it was attached to — the mask decides which, so a provider attached to both lanes is unregistered from both. The lane unregistration is the part that matters for safety: it enters the stream, and that is where the stream's queue lock is taken.

It waits for a drain already in flight, which is the reason the call exists at all. "Takes the stream's lock per lane, so a Produce still running has handed over (or refused) its item before this returns, and no item can arrive afterwards" (Engine/Core/TaskProvider.h). Without that wait, a detach would either drop an item a provider had already produced or leave a pointer in a list a worker is walking — and R37's destructor assert is exactly the check this call keeps satisfied.
It is silent about a stream it does not find. Falling off the end of the search loop returns without a log (Engine/Core/TaskProvider.cpp) — unlike AttachTo, which reports every refusal. That is defensible for a teardown path that over-unregisters, but it means "detached" and "was never attached" are indistinguishable here; ask IsAttachedTo before and after if the difference matters to the report.
Positions are not stable across a detach. The array is shift-compacted, so every attachment recorded after this stream moves down one. A caller holding an index from GetAttachedStream across a detach is reading a different stream's entry — which is why the accessor's contract is a walk, not a handle.
What it does not do: stop anything. No Stop, no cancellation, no notice to a successor. Work this provider already handed to the stream stays on its lane and runs; work it has not handed over simply stops being asked for, because the stream's list no longer names this provider. A provider detached and then re-attached is the same object with a clean slate, and RegisterOnStream counts the new registration separately.
