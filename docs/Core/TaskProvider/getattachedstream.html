GetAttachedStream

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp The attached stream at a position in attachment order; out of range asserts and returns 0.

From Engine/Core/TaskProvider.cpp

Assert and then refuse, rather than either alone: the assert is the loud signal in a Debug build that a caller's arithmetic is wrong, and the return keeps the same mistake from reading past the array in a build where the assert is compiled away (CMakeLists.txt defines __DEBUG__ for Debug only). The header states the contract as one line: "Out-of-range asserts and returns 0" (Engine/Core/TaskProvider.h).

Zero is both a valid stream index and the out-of-range answer, so the sentinel is ambiguous. TaskSystem::BaseStreamIndex is 0 (Engine/Core/TaskSystem.h), so a walk that stops on a zero return can stop early at the base stream, and a caller that treats a zero as "out of range" cannot tell it from the base stream. Drive the loop from GetAttachedCount and index within that bound — the accessor's bound check is a guard against a bug, not a loop terminator.
Positions are not stable, because DetachFrom shift-compacts the array. Detaching a stream that sat before this one moves every later entry down a slot, so an index held across a detach names a different stream — and returns it without complaint, since it is still in range (Engine/Core/TaskProvider.cpp). A walk must be completed, or the list re-read, before it is acted upon.
What an entry means depends on the registration, not on this number. An index here is a stream this provider asked to feed; whether that stream ever accepted the provider is RegisterOnStream's answer, reported as a warning when the engine has no such stream. Pair this with GetAttachedLanes to see which lanes of that stream were named.

Examples

Illustrative — no call site outside the class uses this accessor; the provider tests read the count rather than walk the list.

for (TStreamIndex index = 0; index < provider.GetAttachedCount(); ++index)
{
    ls << "feeds stream " << provider.GetAttachedStream(index)
       << " on lanes " << unsigned(provider.GetAttachedLanes(provider.GetAttachedStream(index)));
}

Bound by the count, resolved per entry, and paired with the lane mask — the shape the three reporting accessors are designed to be used in. Doing it while a drain may be detaching is the one arrangement to avoid, for the reason above.
