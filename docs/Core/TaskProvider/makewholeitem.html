From Engine/Core/TaskProvider.cpp

Two engine calls in the only order that is legal: declare the join, then hand back the item that fills it. A provider whose Produce wants to run a task outright has nothing else to work out — the item's index range is [0, 1), its reserved count is 1, and its priority is the argument.

The reason it exists is that an item is built by the engine, not by a customer. "the index range, the priority and the reserved count have to agree with the task they belong to, and only the engine can keep them agreeing. This is that facility, kept where a provider can reach it and away from everyone else: the base class is a friend of Task, and derived providers inherit the helper instead of each being made a friend of a type they have no business knowing" (Engine/Core/TaskProvider.h). That is also why it is static — it needs nothing from the provider that calls it beyond the inheritance that grants it.
The precondition "must not already declare a join" is a caller's duty, and a violation is not this function's to catch. Reserving twice on a task that already declared one is Task::ReserveSubTasks's contract to report, and the item this returns is GenerateSubTask(0, 1, priority) — a range that silently overlaps any join already on the task. A provider that reuses a task across drains must build its own items with its own ranges and call this only for the first (Engine/Core/TaskProvider.h).
It names the task by value-copying its TaskID into the item, which is the whole point of the item being a value. The stream re-checks that id against the registry when it dequeues, so "an item naming a task that was released in between is dropped by the stream with the usual warning, so a provider cannot smuggle dead work past the liveness check" (Engine/Core/TaskProvider.h). The test probe exploits exactly that: it releases the task inside Produce, after this call, and asserts the stream drops the item.
One item, one task, always. A task that wants to be sliced across drains — the streaming form, where a single item is re-enqueued with its current cursor advanced — cannot be built here, because the range is hard-wired to [0, 1). Providers that stream build the item themselves with Task::GenerateSubTask; this helper is the whole-task shortcut, and the name is the claim.

Parameters

Create, look up, wrap, hand over — the full body of a provider that produces whole tasks, including the lookup that can fail and the nullopt that answers it. Note the item is taken by value and the task pointer is not kept: the item carries the id, which is the only reference the stream will honour (Engine/Core/TaskProvider.cpp).
