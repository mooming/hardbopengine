AttachTo

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp Start being drained by one lane of one stream; duplicates are per (stream, lane).

Signature

void AttachTo(TStreamIndex stream, StreamDrainPolicy::ELane lane) noexcept

Function description

Defined in Engine/Core/TaskProvider.cpp as TaskProvider::AttachTo(): start being drained by one lane of one stream. Three outcomes — the stream was already attached and gains a lane bit, the stream is new and takes a slot, or the call is refused and reports itself. 

for (TStreamIndex index = 0; index < attachedCount; ++index)
{
    if (attached[static_cast<size_t>(index)] != stream)
    {
        continue;
    }

    const bool alreadyOnLane = (lanes[static_cast<size_t>(index)] & laneBit) != 0;
    lanes[static_cast<size_t>(index)] |= laneBit;

    if (!alreadyOnLane)
    {
        RegisterOnStream(stream, lane);
    }

    return;
}

From Engine/Core/TaskProvider.cpp

Duplicates are per (stream, lane), and one stream never occupies two slots. Re-attaching the same lane changes nothing, "because a stream that listed a provider twice on one lane would call Produce twice per drain and double its output rate silently". Attaching the other lane is a different thing and is allowed: it says this provider may be drawn on by either lane, "which is the same doubled-call hazard taken with intent, so it has to be the caller's decision and never a default" (Engine/Core/TaskProvider.h). The mask that records the pair is what GetAttachedLanes reports.
ELane::None is refused with an error rather than accepted. "An attachment with no lane would sit in the slot and never be drained", so the call logs and returns having changed nothing (Engine/Core/TaskProvider.h). The reason the report matters is the symptom: a lost attachment is a stream that quietly never gets work, which is otherwise indistinguishable from a provider with nothing to do.
When a registration fails, the recorded attachment stays. The slot is written and counted, then RegisterOnStream decides whether the stream really exists and really has room; a missing stream is a warning and a full lane list is an error, and neither rolls the slot back (Engine/Core/TaskProvider.cpp). The consequence is that GetAttachedCount and IsAttachedTo can report an attachment that will never be asked about — which is exactly what the R38 rule needs them to be able to say, since the drain reads the stream's list and not this one.
The capacity ceiling asserts, reports, and drops. Past MaxAttachedStreams the call Asserts with the provider name, the limit and the fact that the attachment was dropped, logs the same in an error line naming the lane bit, and returns (Engine/Core/TaskProvider.cpp). The limit is 64 for a reason the header prices: feeding every worker stream is an ordinary thing providers do, and R35's two lanes per worker double the attachments. Note the assert is Debug-only (!RELEASE_BUILD in CMakeLists.txt), so a shipping overflow is the log line and nothing else.
This object's own arrays have no lock, so attachment is a lifecycle event on one thread. What makes attaching and detaching safe against a drain is that RegisterOnStream and UnregisterFromStream enter the stream — whose queue lock guards its provider list — not that anything here is synchronised. Two threads calling this on one provider race attached, lanes and attachedCount, and no check detects it (Engine/Core/TaskProvider.cpp).

Parameters

ParameterTypeRequirement
streamTStreamIndex (int)The stream to feed. An index the engine does not have is recorded and warned about, and nothing will ever ask this provider
laneStreamDrainPolicy::ELaneWhich lane, because "which lane attaches decides the policy the stream applies to what this provider hands it" (R35). None attaches nothing

Return value

void. No return distinguishes "attached now" from "already attached" from "recorded but never registered" — read GetAttachedLanes for the first two, and the log for the third.

Examples

From Engine/Core/TaskProvider.cpp, TaskProviderTest

fifoProvider.AttachTo(worker, StreamDrainPolicy::ELane::Fifo);
priorityProvider.AttachTo(worker, StreamDrainPolicy::ELane::Priority);

Both lanes of one worker fed by two different providers — the arrangement the lane split exists for, since each lane applies its own drain policy to what it is handed. One provider attached to both lanes of the same stream is also legal and takes one slot with both bits set, at the cost of being asked on either lane's schedule (Engine/Core/TaskProvider.h).
