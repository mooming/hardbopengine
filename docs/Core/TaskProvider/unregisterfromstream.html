UnregisterFromStream

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp Private: remove this provider from one lane under that stream's lock, which waits out a drain in flight.

Signature

void UnregisterFromStream(TStreamIndex stream, StreamDrainPolicy::ELane lane) noexcept

Function description

Declared private in Engine/Core/TaskProvider.h, defined in Engine/Core/TaskProvider.cpp as TaskProvider::UnregisterFromStream(); five lines, and the reason a detach can be called while a worker is draining. 

if (!taskSystem.HasStream(stream))
{
    return;
}

if (taskSystem.GetStream(stream).DetachProvider(*this, lane))
{
    --registeredCount;

From Engine/Core/TaskProvider.cpp

The wait is inside TaskStream::DetachProvider, not here. That call takes the stream's queue lock before it removes the pointer (Engine/Core/TaskStream.cpp), which is what makes the header's promise true: "Takes the stream's lock per lane, so a Produce still running has handed over (or refused) its item before this returns, and no item can arrive afterwards" (Engine/Core/TaskProvider.h). This function contributes the lane-by-lane decomposition and the count, nothing more.
The count moves only when the stream confirms it held this provider. A false from DetachProvider leaves registeredCount alone, so a detach of a lane that never registered — an attachment naming a stream the engine lacks, or a lane list that refused the provider — cannot drive the count negative (Engine/Core/TaskProvider.cpp). That guard is what keeps the destructor's R37 assert meaningful in builds where it exists, and keeps a mismatched detach from hiding a real registration elsewhere.
A stream the engine does not have is skipped without a word, unlike RegisterOnStream, which warns about the same condition. The asymmetry is defensible — the registration already said out loud that nothing was registered, and a teardown path that over-detaches should not log twice — but it does mean a silent no-op and a successful removal are indistinguishable from the outside (Engine/Core/TaskProvider.cpp).
It removes one lane's entry, and the caller decides how many lanes to ask about. DetachFrom reads the recorded mask and calls this once per bit set, so a provider on both lanes ends up unregistered twice and decremented twice. Nothing here consults the mask itself, so a caller that drove this directly could leave the other lane holding the pointer — which is precisely why the function is private (Engine/Core/TaskProvider.h).

The one public route to it: read the mask, ask for each bit. The pairing of that mask with this function's per-lane removal is what guarantees the recorded attachment and the stream's list empty out together — and therefore that registeredCount is back at zero before a provider is allowed to die (Engine/Core/TaskProvider.cpp).
