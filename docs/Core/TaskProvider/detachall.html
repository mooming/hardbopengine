DetachAll

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp Detach from every stream this provider is attached to, which is what makes destruction legal.

Signature

void DetachAll() noexcept

Function description

Defined in Engine/Core/TaskProvider.cpp as TaskProvider::DetachAll(); the body walks the slot list from the back and reuses the single-stream path. 

for (TStreamIndex index = attachedCount - 1; index >= 0; --index)
{
    DetachFrom(attached[static_cast<size_t>(index)]);
}

From Engine/Core/TaskProvider.cpp

Nothing here duplicates DetachFrom's work, which is the point: the per-lane unregistration, the wait for a drain in flight and the compaction are the same code, so a provider cannot be half-detached by one path and fully detached by the other. Walking backwards is what makes the compaction safe — every entry still to be visited sits below the one being removed, so nothing shifts out from under the loop.

This is the call that makes destruction legal. The destructor asserts that the provider is registered on no live stream (R37), and the probes satisfy it by calling this from their own destructors: "a provider that is destroyed while registered is exactly the dangling pointer the assert exists to catch" (Engine/Core/TaskProvider.cpp). Because the assert is compiled away outside the Debug configuration (CMakeLists.txt defines __DEBUG__ for Debug only), a shipping owner has this call and the discipline, not the check.
Each stream's lock is taken in turn, so a provider feeding many streams waits many times. DetachFrom enters a stream to unregister a lane, and a provider attached to a dozen workers — an ordinary figure, since MaxAttachedStreams is sized for every stream on a machine — serialises a dozen short critical sections, each waiting for whatever that stream's current Produce is doing. Detaching is a teardown path, and it is not cheap enough to belong in a frame.
The loop's bound is the array itself, so a stream recorded twice would be visited twice — and cannot be. AttachTo keeps one slot per stream, merging lane bits rather than adding an entry, so every value in attached is distinct and one pass is enough (Engine/Core/TaskProvider.cpp). That invariant is what lets this loop be three lines.
After this call the provider is inert but intact. Its slot list is empty, registeredCount is back to zero, and its stop flag is untouched — a stopped provider that is detached and re-attached is still stopped. Re-attaching after a detach is legal and registers afresh.

Parameters

None. There is no "detach from streams that exist" variant: everything recorded is visited, including an index the engine never had, which is removed from the list and never needs a lock.

Return value

void. Nothing reports how many streams were released; a caller that needs the number reads GetAttachedCount on both sides.

Examples

From Engine/Core/TaskProvider.cpp, TaskProviderTest

deadProvider.DetachAll();

Called while the provider is still alive and the stream may still be draining it, which is the ordering that matters: the call returns only once each lane's lock has been taken, so the object can then go out of scope without a worker holding its address. The test afterwards asserts on what it observed rather than on what the detach reported, because this function reports nothing (Engine/Core/TaskProvider.cpp).
