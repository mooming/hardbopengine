~TaskProvider

member of hbe::TaskProvider Engine/Core/TaskProvider.cpp Assert that no live stream still holds this provider's pointer, which R37 makes a destruction requirement.

Signature

virtual ~TaskProvider()

Function description

Defined in Engine/Core/TaskProvider.cpp as TaskProvider::~TaskProvider(); the body is a single assert. 

Assert(registeredCount == 0, "TaskProvider ", name, " was destroyed while it still fed ", registeredCount,
       " live stream(s). A stream holds this object's pointer, so destroy it only after DetachFrom or DetachAll.");

From Engine/Core/TaskProvider.cpp

Virtual, because a provider is owned and destroyed through a base pointer by whoever built it — an app's provider, a subsystem's provider — and the class has a pure virtual entry already. Its whole work is the check: a stream's lane list holds this object's address, so a provider destroyed while still registered leaves a dead pointer in a list a worker thread iterates every drain.

The rule counts registrations, not recorded attachments, and the difference is deliberate. "An attachment naming a stream the engine does not have puts nothing anywhere, so it cannot dangle and must not be fatal" (Engine/Core/TaskProvider.h). RegisterOnStream increments the count only when the real stream accepted the provider, so a probe attached to an index nothing owns dies clean — which is how the unit probes are written.
In a Dev or Release build the assert is not there. Assert compiles to nothing unless __DEBUG__ is defined, and the build defines it only for the Debug configuration (CMakeLists.txt, Engine/CMakeLists.txt). Outside Debug this destructor is empty, and the failure it describes — a lane list naming a destroyed provider — surfaces later as a call through that pointer from TaskStream::DrainProvidersLocked, on whichever worker drains next, with nothing left to name the provider that was lost.
A destructor assert cannot see a drain in progress, which is why detaching takes a lock and this does not. "A destructor assert alone cannot see a drain in progress, which is why DetachFrom and DetachAll take the target stream's lock rather than clearing flags here" (Engine/Core/TaskProvider.h). The correct teardown is therefore DetachAll — which waits — and then destruction, not destruction with a hope that the count is zero.
Nothing else is released here. No DetachAll call, no Stop, no log. A provider that dies quietly stops being a producer only in the sense that it can no longer answer Produce; the streams attached to it keep whatever they were handed, and the ones registered on it keep a pointer they will keep using.

Parameters

None.

Return value

Nothing. It is not noexcept — a destructor of a type whose derived classes may hold resources makes no stronger promise than the standard already imposes.

Examples

From Engine/Core/TaskProvider.cpp, TaskProviderTest

DrainObservation deadRuns;
DrainingProvider deadProvider("DeadItemProbe", taskSystem, deadRuns);
deadProvider.releaseImmediately = true;
deadProvider.AttachTo(worker, StreamDrainPolicy::ELane::Fifo);

const bool askedForDead = WaitFor([&]() { return deadProvider.GetAsks() >= 4; }, 500);

deadProvider.DetachAll();

The shape every owner must copy: attach, let the stream ask, then DetachAll while the provider is still alive, so the destructor is reached with registeredCount back at zero. The tests then assert the bookkeeping rather than trusting the assert — the assert that would catch a violation exists only in the Debug configuration, and where a probe deliberately names a stream the engine does not have, the count stays zero and the destructor stays silent, which is the R37 distinction working as intended (Engine/Core/TaskProvider.h).
