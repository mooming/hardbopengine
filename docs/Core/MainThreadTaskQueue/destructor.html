~MainThreadTaskQueue

member of hbe::MainThreadTaskQueue Engine/Core/MainThreadTaskQueue.h Discards whatever is still queued; it neither runs nor reports those callables.

Signature

~MainThreadTaskQueue() = default

Function description

Declared in Engine/Core/MainThreadTaskQueue.h as ~MainThreadTaskQueue() = default; and therefore has no definition in Engine/Core/MainThreadTaskQueue.cpp. Its work is member destruction: the mutex, the atomic flag, and the container — which releases whatever its populated buckets hold.

Anything still queued is discarded, not run, and the destruction says nothing. A TaskItem is a function pointer and a context pointer; destroying one does not call it. So a queue that dies with work in it drops that work silently, and the caller that posted it is never told. The engine treats this as an error condition worth logging at the level above the class: the shutdown path pumps the base stream for up to 2000 ms and, if work remains, logs "Shutdown abandoned work on the base stream after 2000ms: N queued item(s) and at least one posted callable. Whatever was promised through them will not happen." (Engine/Core/TaskSystem.cpp).
It does not stop the queue. The flag read by IsRunning is left as it was, so destroying a queue does not make Enqueue unsafe — that is simply impossible to express here, and nothing claims otherwise. What is required of the caller is the ordinary one: no Enqueue may be in flight, and none may arrive afterwards, because a queue cannot outlive the threads that hold its function pointers' context.
A task running under ProcessTasks on another thread is not awaited. The destructor takes no lock and checks no counter, because the class keeps none: ProcessTasks pops an item and invokes it with the lock already released, so nothing observable exists between the pop and the call. A drainer that is still inside a posted callable while the queue is destroyed is a use-after-free of the mutex, and preventing it is the drainer's obligation — which is why the engine's only drainer is the stream's own pass, on the stream's own thread.

Parameters

None.

Return value

Nothing. No count of discarded callables, no log, no assert — which is precisely why the shutdown path counts them before the destruction happens.

Examples

From Engine/Core/TaskSystem.cpp, the engine-loop shutdown path

const bool hasAbandonedPostedWork = baseStream.HasPostedTasks();
const auto abandonedItemCount = baseStream.CountPendingItems();

if (hasAbandonedPostedWork || abandonedItemCount > 0)
{
    Logger::Get().AddLog(GetName(), ELogLevel::Error,
                         [hasAbandonedPostedWork, abandonedItemCount](auto& logStream)
    {
        logStream << "Shutdown abandoned work on the base stream after 2000ms: " << abandonedItemCount
                  << " queued item(s)";

        if (hasAbandonedPostedWork)
        {
            logStream << " and at least one posted callable";
        }

        logStream << ". Whatever was promised through them will not happen.";
    });
}

The compensation for a silent destructor: the only owner of a queue in the engine measures what it is about to discard and reports it as an error, with the sentence that makes the consequence plain — whatever was promised through those callables will not happen.
