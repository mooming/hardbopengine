From Engine/Core/MainThreadTaskQueue.cpp

Pop under the lock, call outside it, repeat until a pop returns nothing. The scope around the lock is the whole design: the mutex is not held across a call, so a posted callable may post more work without deadlock — the failure the class exists to avoid (Engine/Core/MainThreadTaskQueue.h).

A producer that keeps posting can keep this loop alive indefinitely, and nothing bounds it. The header states it as intended behaviour — "Returns once the queue is observed empty; producers that keep enqueueing can extend the loop, which is the behaviour callers already rely on" — but the consequence for a frame budget is real: a self-reposting callable makes this an unbounded loop inside the stream's pass. RequestStop will not break it, because the loop never reads that flag.
The return counts callables actually invoked, not items taken. An item with a null taskFunc is popped, discarded, and not counted — so the count is what ran, and an enqueue of a null function is a silent drop with no trace anywhere.
Intended for the main thread, and in practice run by whichever stream owns the queue. Each TaskStream holds one and drains it at the top of its pass, before its lanes are asked for anything: "Posted callables first: they are the engine loop's own work, and the frame budget is spent on them before the stream's queues are asked for anything" (Engine/Core/TaskStream.cpp). Priority order is honoured within one pass; a callable posted by a callable in this pass runs in the same pass if the loop is still going.
It ignores a close or shutdown request. The stream's pass drains posted work before it consults closeRequested, so work posted after a close was asked for still runs, and the shutdown pump keeps pumping the base stream while HasPendingTasks reports anything left. Stopping the drain of posted work is not this function's job — which is why the stop flag is wired to nothing here.
