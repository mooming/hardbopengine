From Engine/Core/MainThreadTaskQueue.cpp

Build the item, take the lock, hand it to the container. The item is filed by its priority byte into that priority's bucket and joins it at the back, so two callables sharing a priority run in arrival order; ProcessTasks always takes from the highest populated priority first.

What a caller must hold ontoWhy
userData must outlive the call, not the statementThe queue stores the pointer and nothing else — no ownership, no copy, no lifetime token. A posted callable runs later, on another thread
There is no failure to checkPush performs no capacity test, so an enqueue cannot be refused, cannot drop, and cannot report — see the bounded-name gap below
255 is urgent, 0 is least, 128 is the defaultThe direction was inverted on 2026-09-18 along with the container; a small number now means low urgency (Engine/Core/MainThreadTaskQueue.h)
"Bounded" and MaxQueueSize do not bound the number of queued callables. MaxQueueSize = 1024 is the container's third template parameter, whose documented role is BucketSizeHint — the capacity a bucket is created with on first use. So the first item ever pushed at a given priority reserves a deque of 1024 slots, and at 24 bytes per TaskItem that is 24,576 bytes from the engine allocator, per priority level, per queue (Engine/Container/Deque.h, Engine/Container/BoundedPriorityQueue.h). Levels are released when they drain, so the peak is what is simultaneously populated. Enqueue's cost is therefore not proportional to how full the queue is but to how many distinct priorities have been touched since the last drain.
Callable from any thread, and the engine relies on that pairing. "Window callbacks reach it through TaskSystem::DispatchToMainThread on a task-stream thread while the process main thread is draining the same queue" (Engine/Core/MainThreadTaskQueue.h). The lock makes that legal; it does not make the ordering predictable — a callable enqueued during a drain is simply picked up by the same loop if it is still running.
The priority byte on a queued item is a filing label, not a live value. The container files an item by the byte and never re-sorts it, and on the way out it overwrites the byte with the level it actually served from. Changing a queued callable's priority means removing it and pushing it again; nothing here offers that, so for this queue the byte is write-once at enqueue (Engine/Container/BoundedPriorityQueue.h).

The stream's forwarder, reached from TaskSystem::DispatchToMainThread(), which routes to the base stream. The engine's heaviest user is Engine/OSAL/Window.cpp, which packs a struct of this, a log stream and a std::promise reference into a local, passes its address, and then drives the engine until the future is ready — the pattern that keeps userData alive across the thread boundary.
