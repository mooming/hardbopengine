From Engine/Core/MainThreadTaskQueue.cpp

A locked read of the container's emptiness — the reason the mutex is declared mutable, as its own header note says: "Guards queue alone. Mutable because HasPendingTasks takes it while reporting const." (Engine/Core/MainThreadTaskQueue.h). Without the lock this would race the container's plain size counter, which is the ThreadSanitizer finding the class carries a note about.

The answer is a moment, not a state. The lock is released the instant the read is done, so a true only says the queue was non-empty at that point: another thread may drain it before the caller acts, and a producer may fill a queue that answered false. A caller that acts on the answer must tolerate both, which is why the engine's use is a loop condition rather than a decision.
Its one shipping use is a shutdown report, which is exactly the use a stale answer cannot harm. The engine-loop shutdown pumps the base stream until its posted queue and its lanes are empty or 2000 ms have passed, then asks this question one last time to decide whether to log an error — "and at least one posted callable ... Whatever was promised through them will not happen." (Engine/Core/TaskSystem.cpp). Asking after the pumping stops removes the race that would otherwise matter: nobody is draining any more.

Examples

From Engine/Core/TaskSystem.cpp, the engine-loop shutdown path

while (std::chrono::steady_clock::now() < pumpDeadline &&
       (!AreUserStreamsClosed() || baseStream.HasPostedTasks() || baseStream.CountPendingItems() > 0))
{
    baseStream.Update();
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
}

Reached through TaskStream::HasPostedTasks(), which forwards this call unchanged (Engine/Core/TaskStream.cpp). The deadline is what makes the loop terminate despite the race: a queue that never drains cannot keep the engine alive forever, and the report afterwards is the honest admission of what was left.
