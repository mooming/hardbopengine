ForStream

member of hbe::TaskProduceContext Engine/Core/TaskProvider.cpp Builds the context for one drain of one stream, taking the clock once.

Signature

[[nodiscard]] static TaskProduceContext ForStream(TStreamIndex streamIndex) noexcept

Function description

Defined in Engine/Core/TaskProvider.cpp as TaskProduceContext::ForStream(); the body is one aggregate return. 

return TaskProduceContext{streamIndex, std::chrono::steady_clock::now()};

From Engine/Core/TaskProvider.cpp

It names the stream and takes the clock once, and the whole design of the context is in that pairing: "The clock reading is taken here rather than at each call site so that a single drain - and every provider inside it - shares one instant" (Engine/Core/TaskProvider.h). The clock it reads is steady_clock, which is what time::TEngineTimePoint is, so the instant lands in the same time base as the engine epoch (Engine/Core/Time.h) without this call having to reach the engine at all.

Called once per drain, not once per provider. TaskStream::DrainProvidersLocked() builds one context and hands it to every provider on the lane, so all of them see the same instant even if the drain itself runs long (Engine/Core/TaskStream.cpp). That is what lets a provider's decision be reproducible: a scheduling effect and a clock effect are distinguishable only if the clock did not move between the two providers.
The instant is the drain's, not the caller's — and not what time::ElapsedSinceEngineEpoch would return now. The header advises "Call time::ElapsedSinceEngineEpoch to turn it into a duration", which is true of the time base but not of the value: that function takes a fresh reading, so for a context built earlier in the same pass it reports a later instant. The arithmetic that preserves the drain's own instant is context.now - time::GetEngineEpoch(). A provider that stamps work with the fresh reading instead will report items as slightly younger than the drain that made them.
Nothing checks that streamIndex names a stream that exists. A context is a value, and a provider may be attached to an index the engine does not own — the provider machinery deliberately allows that, and the R38 bookkeeping path exists for exactly that case (Engine/Core/TaskProvider.h). The tests rely on it, building a context for stream 3 in a process with other stream counts (Engine/Core/TaskProvider.cpp).
A stored context goes stale immediately, and nothing warns about it. The context is a snapshot of one drain; keeping it for a later call means both fields are wrong — the stream may not be asking, and the instant has passed. Providers are meant to read it and drop it, which is why the type has no members beyond the two fields it was built with.

Examples

const TaskProduceContext context = TaskProduceContext::ForStream(streamIndex);

for (TIndex index = 0; index < list.count; ++index)
{
    if (auto produced = list.items[static_cast<size_t>(index)]->Produce(context); produced.has_value())
    {
        return produced;
    }
}

The only shipping call site, inside the drain itself. Note what the loop does with the answer: the first provider that produces ends the drain, and the providers are asked in attachment order — see TaskProvider::Produce for what that ordering costs a provider later in the list.
