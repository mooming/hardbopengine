Init

member of hbe::Component Engine/Core/Component.h Pure virtual: one-time setup, called with the state BORN.

Signature

virtual void Init() = 0

Function description

Pure virtual; declared and unimplemented in the interface block of Engine/Core/Component.h. There is no default behavior — a component that needs no setup overrides it with an empty body. It is the entry into the lifecycle: called once, by ComponentSystem::ProcessInit, on the pass after the component was created.

The state you are allowed to observe here is BORN, and nothing else. The system sets BORN at creation, then calls Init, then sets ALIVE, then calls OnEnable — three statements in that order, with no reordering (Engine/Core/ComponentSystem.h). A subclass that checks its own state during setup asserts exactly that: 
void Init() override
{
    if (GetState() != ComponentState::BORN)
    {
        ls << "State failure, state = " << GetState() << ", but expected " << ComponentState::BORN << lferr;

        testResult = false;
    }

    isInit = true;
}

From Engine/Core/ComponentSystem.cpp, ComponentSystemTest

Because ALIVE is set after this returns, a component that asks IsEnabled during its own setup is told false. Setup code must not use enable state to decide what to do; it has not been enabled yet.

Called on whatever thread called ComponentSystem::Update, once, with no re-entry protection. There is no isInit flag in this class, and the system clears its init list after the loop (Engine/Core/ComponentSystem.h), so a second call can only come from a component being placed in a second system — which copies or moves it and gives both copies the same state field. Setup work must therefore be safe to have done once, by one thread, and must not have left anything registered that assumes this address (Update).

Parameters

None.

Return value

void. There is no failure channel: a component that cannot initialise itself has no way to say so. Setting a state here is possible through SetState, but ProcessInit overwrites it with ALIVE immediately afterwards, so a component that fails during setup cannot prevent itself from being enabled.

Examples

The call site, and the fact that the whole init list is consumed in one pass: 

for (auto& compo : initList)
{
    compo.Init();
    compo.SetState(ComponentState::ALIVE);
    compo.OnEnable();
    updateList.push_back(std::move(compo));
}

initList.clear();

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessInit()

A component waiting in the init list is initialised and updated in the same pass — it never has to wait for one of its own: Update on the system calls ProcessInit before ProcessUpdate, and ProcessInit moves every component it has just initialised onto the update list (Engine/Core/ComponentSystem.h). A component is therefore created, initialised, enabled and updated without ever waiting for a pass of its own.
