Destroy

member of hbe::Component Engine/Core/Component.h Mark the component DEAD; the disable, release and destruction follow in the system's transition pass.

Signature

void Destroy() noexcept

Function description

Defined in the header Engine/Core/Component.h. Its body is SetState(State::DEAD) and nothing else: it raises no callbacks, frees nothing, and does not end the current update. The death it requests is carried out later, by the system, in the order OnDisable then Release then the destructor (Engine/Core/ComponentSystem.h).

Asking to die inside your own update is the intended exit, and the death is same-pass. ProcessUpdate asks IsEnabled the instant Update returns; DEAD is not ALIVE, so the component goes to the transition list, is processed in the same pass by the DEAD case, and is destroyed when that function clears its list (Engine/Core/ComponentSystem.h). The repository's subclass retires itself exactly this way: 
++updateCount;

if (updateCount > updateNum)
{
    Destroy();
}

From Engine/Core/ComponentSystem.cpp, ComponentSystemTest

Everything after this call in the same function still runs, on an object already marked dead. There is no early exit and no guard: the rest of the update body executes, and the object it belongs to is moved out of the caller's reach the moment the update loop continues (Engine/Core/ComponentSystem.h). Code after a Destroy must not touch the component, and a component cannot be resurrected afterwards by any legitimate means — the state set here survives the move, and the switch's DEAD case does not place the component on any list. Writing ALIVE from here through SetState does reach the switch's ALIVE case, which re-enables it, but that is the system's re-enable path, not a cancel of a death already processed.

Parameters

None.

Return value

void. No acknowledgment, and no way to find out from here when the release will happen — it depends on when the system next runs its transition pass, which is the same pass if the call came from inside Update.

Examples

case ComponentState::DEAD:
    compo.SetState(ComponentState::SLEEP);
    compo.OnDisable();
    compo.SetState(ComponentState::DEAD);
    compo.Release();
    break;

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessTransition()

What the flag buys: the disable runs under SLEEP, the release under DEAD, and the component is not pushed onto any list, so the transitionList.clear() that closes the function destroys it (~Component). A component destroyed by any other route — a system torn down around sleeping members, for instance — never sees these two callbacks at all (Release).
