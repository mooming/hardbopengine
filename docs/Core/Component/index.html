Component

Engine/Core/Component.h The lifecycle interface a component inherits: five callbacks, a state and a name, driven by ComponentSystem.

Class description

class Component at Engine/Core/Component.h: the lifecycle interface every engine component inherits — Init, Update, Release, OnEnable, OnDisable — plus two fields, a state and a name, and the four accessors that expose them. It holds no resources and knows of no system: it is the half of a component that a component writes, and the other half — the pump that decides when each callback runs — is ComponentSystem.

The state field is the only coordination between the two halves, and each callback is defined by the state it is allowed to see. The system writes the state and then calls the callback that documents it, so the state a component observes at the top of a callback is the system's statement of what is happening to it:
CallbackState it must findSet by
InitBORNComponentSystem::Create, at creation
OnEnableALIVEProcessInit after Init, or the ALIVE case of ProcessTransition
UpdateALIVEas above — this is the only state in which an update happens
OnDisableSLEEPthe SLEEP case, or set to SLEEP by the DEAD case before the callback
ReleaseDEADthe DEAD case, after OnDisable

The states themselves belong to ComponentState; this class only aliases it privately as State, which is why the signatures above read State (Engine/Core/Component.h).

A component object does not stay where it was put, and this class is the reason it cannot. The system stores components by value and moves every one of them between lists on every pass (Engine/Core/ComponentSystem.h), so a pointer or reference to a component is stale the moment a pass ends (Update). That requirement reaches into this class's own special members: because the destructor here is user-declared, the implicit move constructor and move assignment are not generated, and the implicit copy constructor is deleted because String can only be copied from a non-const reference (hbe::String, Engine/String/String.h). A compiler probe of the real headers confirms all four: Component is not copy-constructible, not move-constructible, copy-assignable, and not move-assignable. Every subclass the system is to store must therefore declare its own move constructor and move the base through it — the one contract of this class that a subclass can violate silently until it fails to compile (the constructor page).
Nothing in the engine uses this class, and the only subclass is a unit-test type. The sole derivation in the repository is struct Test : public Component, defined inside the #ifdef TEST_ENABLED region of Engine/Core/ComponentSystem.cpp, and the sole ComponentSystem instantiation is that test's No subsystem in Engine/ outside these two headers, and nothing in Applications/, declares a component or owns a system. Engine/Core/Component.cpp includes the header, names the namespace, and defines nothing — the entire class lives inline in the header. What follows is therefore documented from the interface, from the system that drives it, and from the behavior the test asserts, which is the only executable statement of the lifecycle in the tree.

Template parameters

None. Component is not a template and is not final: it exists to be subclassed, and its five pure virtuals make it abstract — a component is always the derived type. The system that stores it is the template (ComponentSystem<TComponent>), not the base.

Which list a component is on, and what moves it That is ComponentSystem's state, not this class's — the init, update, sleep and transition lists are the system's members and the three Process* functions are the only code that moves a component. This page says what each callback is allowed to observe, which is the part a component author can rely on; the pump's own contract belongs to its module page
A thread-safety guarantee for state and name The sources show a single-threaded pattern — one thread calls the system's Update, and every read and write in the engine is on that thread — but nothing in Engine/Core/Component.h or Engine/Core/ComponentSystem.h states it as a rule, and neither field is an atomic. The pages here say what the fields are and who writes them, and stop short of a promise the headers do not make
Use of a component outside a ComponentSystem There is no such use to document: no code constructs a component that no system owns, and this class provides no way to drive the lifecycle by hand — Init and Release are callable, but nothing here decides the order, checks it, or moves the object. Whether a hand-driven component is a supported arrangement is a question for the module's owner, not something this page can invent
