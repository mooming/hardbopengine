SetEnable

member of hbe::Component Engine/Core/Component.h Select ALIVE or SLEEP; the callbacks and the list moves follow from the state, not from this call.

Signature

void SetEnable(bool isEnabled) noexcept

Function description

Defined in the header Engine/Core/Component.h. One line: SetState(isEnabled ? State::ALIVE : State::SLEEP). Turning a component off selects SLEEP, turning it on selects ALIVE, and neither calls OnEnable or OnDisable — those follow from the state, at the end of the pass (Engine/Core/ComponentSystem.h).

Turning a running component off takes effect at the end of its own update, and the disable callback runs in the same pass. ProcessUpdate asks IsEnabled right after Update returns, so a component that calls SetEnable(false) inside its update is moved to the transition list immediately and gets its OnDisable there, before the pass ends. It is not updated again in that pass, and it is not updated at all afterwards (Engine/Core/ComponentSystem.h).
Turning a sleeping component back on does not wake it up. Nothing ever looks at the sleep list again. The call writes ALIVE, and the answer to IsEnabled changes — but the component is sitting in the system's sleepList, and no code in Engine/Core/ComponentSystem.h reads that list: ProcessInit consumes the init list, ProcessUpdate walks the update list, ProcessTransition walks the transition list and clears it, and the sleep list is only ever pushed to, in the SLEEP case, and tested for emptiness by the system's conversion to bool. So this call succeeds, reports success by every question the component can ask, and the component never runs again; when the system is destroyed the component is destroyed with no OnDisable and no Release. Only a component still in the update list can be re-enabled — by setting ALIVE during its own update, which routes it to the switch's ALIVE case and back onto the update list (Engine/Core/ComponentSystem.h).

Parameters

NameTypeMeaning
isEnabledbooltrue selects ALIVE, false selects SLEEP. It is not a query of the previous state, and it cannot be used to toggle

Return value

void. Nothing reports whether the callbacks will run — they are the system's decision, made from the state this writes, and the sleep-list limitation above is invisible to the caller.

Examples

Where a false answer ends up: one callback, then the list nothing reads. A component that needs to pause and resume should keep itself in the update list and gate its own Update body on its own flag, rather than using this call to park itself.
