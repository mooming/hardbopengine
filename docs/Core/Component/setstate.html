SetState

member of hbe::Component Engine/Core/Component.h Raw write of the state field: no callback, no validation, no list movement.

Signature

void SetState(State inState) noexcept

Function description

Defined in the header Engine/Core/Component.h. Assigns the state field and nothing else: no callback, no list movement, no validation of the value. It is the raw write behind every state change in the engine, and its body is literally Component::state = inState;.

Move semantics, not validation, are the reason this is public. The system uses it for the death sequence — SLEEP, then OnDisable, then DEAD, then Release — and for the birth sequence, BORN at creation and ALIVE after Init (Engine/Core/ComponentSystem.h). A subclass uses it to change its own fate from inside Update. What it never does is notify: the enable and disable callbacks are the system's job, and they are driven by the state this writes, read at the end of the pass.
An invalid value is not rejected, and outside Debug it is not even reported. The parameter is an unscoped write to an enum class field: any ComponentState is accepted, including NONE and BORN, neither of which the transition switch handles. A component that sets one of those during its update is routed to the switch by the IsEnabled check — since neither is ALIVE — and lands in the default case, whose one statement is Assert(false, "Unexpected component state %d on processing transition.\n", compo.GetState()). That assert compiles away unless !RELEASE_BUILD is defined, which only the Debug configuration is (Engine/Core/ComponentSystem.h, Engine/Core/Debug.h); in Dev and Release the fall-through is silent and the component is destroyed by the following transitionList.clear() with neither OnDisable nor Release.

Parameters

NameTypeMeaning
inStateState (a ComponentState)The new state, stored as given. The name is spelled inState to distinguish it from the member it shadows in the body

Return value

void. No acceptance is reported — a caller who wants to know what happened must read the state back with GetState, which will agree, because nothing here can refuse.

Examples

compo.Init();
compo.SetState(ComponentState::ALIVE);
compo.OnEnable();
updateList.push_back(std::move(compo));

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessInit()

The ordering rule this enables: the state is always set before the callback that documents it, so a callback that checks GetState is checking the system's intent rather than a leftover. Prefer SetEnable and Destroy, which name the intent, and reserve this for the birth and death sequences the system itself owns.
