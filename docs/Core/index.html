Core

namespace hbe Engine/Core 26 headers, 17 sources — types, constants, the task system, the component system, time, assertions and statistics

Module description

Core is the foundation the rest of the engine is built on. It fixes the scalar vocabulary (TByte, TIndex, TReal and their aliases), the compile-time constants, the task system that every parallel subsystem submits through, and the component system that owns component lifetimes. It also holds the utilities that every module reaches for: assertions, the clock, scoped timers and locks, command-line parsing, and the statistics counters the engine prints.

The task system is the backbone of parallel execution, built on Task, WorkItem, TaskStream and TaskSystem. How it is designed — stream accounting, budget windows, provider drain — is in docs/TaskSystemGuide.md and docs/TaskSystemRedesign.md, not on this page: this page says what you call, those say why it works that way. What the running code guarantees and how the testlets are built to see it is Task system internals; the clock everything measures against is Engine clock design.

Runnable (Engine/Core/Runnable.h)

The function signature a Task executes, and the unit a stream dispatches work in.

using TRunnable = std::size_t(*)(void* userData,
                                 std::size_t startIndex,
                                 std::size_t endIndex);

Function description

Receives the task's user data and the index range it was asked to process, and returns the number of items it handled.

Parameters

ParameterTypeMeaning
userDatavoid*Opaque pointer supplied when the task was built; the engine never reads it
startIndexstd::size_tFirst index of the range, inclusive
endIndexstd::size_tOne past the last index, exclusive

Return value

Count of items processed in the range.

Example

static TIndex ClearFloats(void* userData, TIndex startIndex, TIndex endIndex) noexcept
{
    auto values = static_cast<float*>(userData);

    for (TIndex i = startIndex; i < endIndex; ++i)
        values[i] = 0.0f;

    return endIndex - startIndex;
}

class Task final
{
    Task() noexcept;
    Task(StaticString taskName, TRunnable func, void* userData) noexcept;

    void Start(TIndex numberOfSubTasks, TIndex startIndex,
               TIndex endIndex, uint8_t priority = 0) noexcept;

    void Wait(uint32_t intervalMilliSecs = 10) const noexcept;

    [[nodiscard]] bool HasDone() const noexcept;
    void ReportFinishedSubTask() noexcept;

    [[nodiscard]] TRunnable GetRunnable() const noexcept;
    [[nodiscard]] void* GetUserData() const noexcept;

    [[nodiscard]] WorkItem GenerateSubTask(TIndex start, TIndex end,
                                             uint8_t priority = 0) noexcept;
};
MethodPurpose
StartBegin work split into numberOfSubTasks sub-tasks over [startIndex, endIndex)
HasDoneTrue when the task is complete. Private and engine-internal: the counter cannot distinguish a task that finished from one that was never dispatched, so it is not a sound basis for a caller's deadline. Ask the queue instead - TaskStream::CountPendingItems.
ReportFinishedSubTaskOne sub-task announcing it is finished
GetRunnable, GetUserDataRead back what the Task was built with
GenerateSubTaskBuild one WorkItem covering part of this task's range. Private and engine-internal: a queue item is built by the engine. A customer-authored TaskProvider gets the same ability by inheriting the protected TaskProvider::MakeWholeItem, and code that simply wants a task to run calls TaskSystem::EnqueueTask.

Non-member helper functions

None.

Read this before waiting. HasDone requires the sub-task count to have been declared by Start: a Task whose count was never declared is how a suite hangs without printing anything. Task::Wait and Task::BusyWait have been removed for that reason: an unbounded wait on a counter that cannot tell finished from never-dispatched is an unnameable hang. Customers ask the queue (CountPendingItems); unit tests use hbe::WaitUntil, which carries a deadline and reports a stall as a failure. The measured facts behind that are recorded innting docs/TaskSystemRedesign.md.

TaskProvider (Engine/Core/TaskProvider.h)

Class description

The pull interface a stream uses to manufacture work for itself. A stream that owns a provider asks it for an item when it would otherwise sit idle, instead of every producer having to know which stream wants work. Derive from it, implement the work generation, register the derived object with a stream; the engine owns when it is asked, and it asks only while the stream's allowance permits taking work - a spent stream does not get to manufacture work it has no right to run, which is asserted in Debug and Dev and counted in every build by GetProviderAskWhileSpentCount.

Template parameters

None.

Class properties

None that a derived class sets. Whether a provider is asked at all is the owning stream's configuration, not the provider's.

Class methods

MethodPurpose
GenerateTasks (implemented by the derived class)Produce the next item, or report that there is nothing to produce. Runs on the owning stream's thread with its queue lock held: it must not block, must not allocate freely, and must not touch another stream's queues.
MakeWholeItem (protected static)Build a queue item covering a whole task - the sanctioned way for a derived provider to hand work to the engine. Task::GenerateSubTask is private; the provider base is the friend and derived classes inherit this instead, so the door stays closed to everyone else.

Non-member helper functions

None. Code that is not a provider and wants a task to run uses TaskSystem::EnqueueTask rather than building an item.

The general queue is not the stream you expect. Enqueue(task) puts work where whichever stream asks first claims it, so a test that assumes a specific stream ran a task can be wrong twice over. The base stream is occupied for the whole run of the EngineTest suite, which is the same trap recorded in docs/TaskSystemRedesign.md. Target a stream with Enqueue(streamIndex, task) when the stream matters.
