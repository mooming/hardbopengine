ReportReleasedTask

member of hbe::TaskStream Engine/Core/TaskStream.h Private: report a queued item dropped because its task had been released.

Function description

Declared private in Engine/Core/TaskStream.h, defined in Engine/Core/TaskStream.cpp as TaskStream::ReportReleasedTask(). Say that a queued work item was dropped because its task had been released. 

auto log = Logger::Get(name);
log.OutWarning([name = name, index = item.taskID.index, generation = item.taskID.generation](auto& ls)
{
    ls << name.c_str() << " dropped a work item, record " << index << " generation " << generation
       << ", because that task had already been released. Nothing was run.";
});

From Engine/Core/TaskStream.cpp

This is rule R7 made audible, and the header says why audible. "This is R7's rule in action - a reference to a task that no longer exists is recognised and dropped rather than followed - and it is warned rather than left silent because work that vanishes is the single hardest thing to diagnose in this subsystem. A caller that releases a task while its subtasks are still queued will see one line per dropped subtask." (Engine/Core/TaskStream.h) One line per sub-task is the shape to expect in a log: a split task released mid-flight produces as many warnings as it had items still queued.
It logs, and unlike the age report it feeds no counter. The age path increments agedOutWorkCount beside its warning; this path does not increment anything, so released-task drops are visible in the log and nowhere else — GetAgedOutWorkCount stays where it was and GetAbandonedWorkNoticeCount counts only drops at close (Engine/Core/TaskStream.cpp). A test that wants to prove a released task's work was dropped must scrape the log or observe the notice, because no counter moves.
The notice is fired by the caller, not here. Update calls this and then FireAbandonedNotice on the next statement, so the report and the notification stay two calls that the drop site must remember both of. The lookup that decided the drop is the stream's: the item named a TaskID, FindTask returned null, and the item was thrown away before any budget was charged (Engine/Core/TaskStream.cpp).
The parameter is named task in the declaration and item in the definition. The header's spelling — const WorkItem& task — is the interface; the source names the same argument item in both the signature and the captured lambda (Engine/Core/TaskStream.h, Engine/Core/TaskStream.cpp). Harmless here, and worth knowing when grepping for the call's arguments; the type is a work item either way, and the line reports a record by id rather than a task by name.
