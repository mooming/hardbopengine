From Engine/Core/TaskStream.cpp

Three lines, and they are the whole public door into a stream's FIFO lane: take the queue lock, append the item, wake whoever waits on the stream. The item is copied into the lane and the caller keeps its own value — nothing here keeps a reference to the caller's memory.

The header calls the operation unfailable, and records what used to make it failable. "Cannot fail. A task is queued or it is not, and the only reason a stream ever refused one was a declared result count it could not fit - a question that stopped existing when the result moved into the task's own record." (Engine/Core/TaskStream.h) fifoQueue is a Deque<WorkItem>, so the lane has no item ceiling to refuse against (Engine/Core/TaskStream.h).
Liveness is checked at the dequeue, not here. An item names a task by TaskID, and a task released between enqueue and dequeue is caught when the stream takes the item out and looks the id up — reported by ReportReleasedTask as one warning per dropped sub-task. A caller may therefore enqueue an item whose task is already gone and see nothing at the call site; the diagnosis appears on the stream's name (Engine/Core/TaskStream.cpp).
The lock is the same one a provider call is made under, and R40 is the trap that follows. TaskStream::DrainProvidersLocked runs Produce with queueLock held, and the mutex is not recursive, so a provider that calls this on the stream draining it deadlocks itself (Engine/Core/TaskProvider.h). Enqueueing into another stream from a provider is permitted but discouraged; the task registry's lock is the one a provider is told to feel free to take.
One notify per enqueue, with no predicate and no batch form. A caller that pushes a hundred items notifies a hundred times; a waiting thread wakes, sees one item available, and takes it — the extra wakes are cheap but not free (Engine/Core/TaskStream.cpp). There is no range form here, unlike the priority lane's internal re-adding, which uses PushRange during compaction (Engine/Core/TaskStream.cpp).

Parameters

ParameterTypeRequirement
taskconst WorkItem& Copied onto the lane; index range, priority and task id travel with it. A priority byte on a FIFO item affects the drain only if the item is later re-added to the priority lane

Return value

void, because there is no refusal to report. The lane grows as needed, so the only cost of a producer that outruns the stream is memory and queue age — and age is what the stream's max-age rule eventually drops (StreamDrainPolicy::SetMaxAge).

Examples

The engine's own producer: a finished task's result is written into its successor's record and the successor's whole item goes onto that stream's FIFO lane, in that order, so the item cannot be taken before the result it waits for exists (Engine/Core/TaskSystem.cpp). Note the enqueue takes an item built inline from the task — the caller never holds a pointer into the lane.
