Start

member of hbe::TaskStream Engine/Core/TaskStream.h Record the task system, then bind the stream to a driver thread or give it a thread of its own.

Signature

void Start(TaskSystem& taskSys) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::Start(). Records the task system this stream will work for, then either binds the stream to the calling thread or gives it a thread of its own: 

taskSystem = &taskSys;

if (streamIndex == TaskSystem::BaseStreamIndex)
{
    threadID = std::this_thread::get_id();
    return;
}

if (streamIndex == TaskSystem::IOStreamIndex)
{
    return;
}

auto func = [this]() { RunLoop(); };

thread = std::thread(func);
OS::SetThreadPriority(thread, 0);

From Engine/Core/TaskStream.cpp (the elided lines are comments)

Three shapes of stream, and the branch is which one it is. The base stream is a ride-on-thread stream driven by the thread that runs the engine, so its threadID is the caller's. The IO stream is a ride-on-thread stream driven by the logger's own thread — "the logger has to work before the task system exists and after it is gone, and a thread of its own would make the logger's writing depend on a stream the logger is also responsible for feeding" — and its threadID is left unset, to be bound by the first Update pass that asks. Every other stream gets a std::thread running RunLoop at priority 0.

The task system is recorded, not looked up, and Update depends on it being there. "This resolves nothing global. A driven stream must outlive the engine object that hosts the task system, so the pass reads the task system recorded at registration and never the live engine." (Engine/Core/TaskStream.h) The consequence is a lifetime obligation on the caller: Update dereferences taskSystem with no null check and no re-resolution, so a stream that outlives its system is a dangling dereference waiting for the next pass.
Calling this twice on a worker stream terminates the process. The last two lines assign to thread, and assigning to a joinable std::thread calls std::terminate — there is no guard against a second call and no flag recording that the stream started (Engine/Core/TaskStream.cpp). TaskSystem calls it once per stream while initialising (Engine/Core/TaskSystem.cpp), which is the only thing keeping the contract; nothing in the class checks the caller.
An undriven stream cannot be policed, because the field the policing reads is set here. ConfigureBudget and ConfigureRate only assert about the calling thread if (threadID != TThreadID{}). For the IO stream that field is default until its first pass runs, and for any stream it is default before Start — so a mid-run misconfiguration of a stream that has not been bound yet is not detected at all (Engine/Core/TaskStream.cpp). The check is also Debug-only: an Assert is compiled away unless __DEBUG__ is defined, which the build sets for Debug alone (Core/Debug.h, CMakeLists.txt).
Priority 0 is the platform default, stated explicitly. OS::SetThreadPriority(thread, 0) (OSAL/OSThread.h) is a call with a value, not an absence: it is what records that worker streams are deliberately not elevated, so a later change has one place to make. It is issued on the constructing thread immediately after the thread is created, which can race the new thread's first instructions — the first pass may run before the priority is applied.

Examples

From Engine/Core/TaskSystem.cpp, TaskSystem::BuildStreams()

stream.Start(*this);

Called once per stream from the loop that brings the system up, which is the single call site in the engine. The same function constructs every stream and then starts all of them, so nothing configures an allowance or a lane weight in between: the streams that ship begin with an unlimited budget and a 1:1 lane ratio (Engine/Core/TaskSystem.cpp). That is the ordering ConfigureBudget asks for — "Configure before the streams start, or from the stream's own thread" — reached by nobody having configured anything at all yet.
