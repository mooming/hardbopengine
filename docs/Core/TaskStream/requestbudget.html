RequestBudget

member of hbe::TaskStream Engine/Core/TaskStream.h Ask this stream to change its CPU allowance, from any thread, applied on its next pass.

Signature

void RequestBudget(std::chrono::duration<double> allowance) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::RequestBudget(); the body is one call. 

budget.RequestAllowance(allowance);

From Engine/Core/TaskStream.cpp

The thread-safe form of ConfigureBudget: store one pending allowance atomically and let the stream apply it to itself. Callable from any thread, at any time.

The stream applies it, and the pass that applies it also re-rates the lanes. Update opens with: 
if (auto applied = budget.ApplyRequestedAllowance(); applied.has_value())
{
    drainPolicy.ConfigureAllowance(*applied);
}

From Engine/Core/TaskStream.cpp, TaskStream::Update()

"The drain policy's allowance follows the same apply, because a lane ratio computed against the old allowance would spread work against a figure the stream no longer has." (Engine/Core/TaskStream.h) That is the difference from the direct form, which writes both books in the caller's thread and needs the thread check this call does not.

The change is not instantaneous, and the newest request wins over any unapplied one. "The change is not instantaneous - it lands on the stream's next pass, and the most recent request wins over any earlier unapplied one." (Engine/Core/TaskStream.h) There is one pending slot, not a queue: two requests before the next pass leave the second in force and the first never applied. A driver that never runs Update never applies anything, so a closed or idle stream keeps its old allowance indefinitely (RequestClose).
An idle stream still applies the request, because the apply happens before any work decision. The pending allowance is consumed at the top of the pass whether or not the pass finds work, so a parked worker applies a request on the pass after it wakes — which is at most one WaitForWork interval of ten milliseconds for a worker, and one host cycle for a driven stream (Engine/Core/TaskStream.cpp).
Requesting zero does not restart measurement in the way a caller expects. Zero means unlimited, and an unlimited stream stops measuring its tasks entirely — the measurement is gated on a non-zero allowance (ConfigureBudget, GetAccumulatedCPUTime). A caller that requested zero to "let this stream run freely for a while" has also switched off the numbers it may still be reading, and the lane book stops being charged.

Parameters

allowancestd::chrono::duration<double>The allowance to take effect on the stream's next pass; 0 means unlimited. Same unit as ConfigureBudget — a slice of time::GetBaseFramePeriod

void. Nothing reports whether an earlier request was overwritten, and no read-back of the pending value is exposed on this class.
