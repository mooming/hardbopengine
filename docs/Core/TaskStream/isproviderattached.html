IsProviderAttached

member of hbe::TaskStream Engine/Core/TaskStream.h Whether a provider is registered on one lane of this stream, read from the list the drain uses.

Signature

[[nodiscard]] bool IsProviderAttached(const TaskProvider& provider, StreamDrainPolicy::ELane lane) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::IsProviderAttached(). Whether one provider sits on one lane's registration list right now. 

const size_t slot = ProviderSlot(lane);
if (slot >= laneProviders.size())
{
    return false;

std::scoped_lock<std::mutex> lock(queueLock);
const auto& list = laneProviders[slot];

From Engine/Core/TaskStream.cpp (the elided lines scan the list for the provider's address)

It is the same question TaskProvider::IsAttachedTo answers, about the list that matters. The provider's own accessor reads its unsynchronised slot list; this one reads the stream's list — "the stream's list, not the provider's, is what the drain reads" (R38, Engine/Core/TaskStream.h) — so the two disagree in exactly the two cases that matter: a provider whose registration the stream refused, and a provider in the middle of being detached. When they differ, this is the answer that predicts whether DrainProvidersLocked will ask.
The method is not const, because the answer takes the lock. It locks queueLock, which is a non-mutable member, so the declaration cannot be const even though nothing is modified (Engine/Core/TaskStream.h). The consequence for a caller holding a const TaskStream& is that the question cannot be asked without const_cast, while its neighbours CountPendingItems and HasPostedTasks are const — and CountPendingItems reads two container sizes with no lock at all, so the two reads are not equally safe.
A lane of ELane::None answers false without taking the lock. ProviderSlot maps it to an index past the end of the two-element array, so the bounds test rejects it first (Engine/Core/TaskStream.cpp) — the same four opening lines that AttachProvider and DetachProvider use.
The answer is a snapshot, and the lock does not extend it. The lock is released when this returns, so a true is a statement about one instant: an DetachProvider from another thread can empty the slot immediately after, and a provider may be destroyed afterwards with this stream's list holding its address until that detach completes (Engine/Core/TaskStream.cpp). It is a diagnostic, not a reservation.

The accessor's real use is exactly the question it can answer that a provider cannot: after a DetachAll, is the stream still holding the address? The test asks the stream, not the provider, because the provider's slot list is bookkeeping about what its owner asked for and this list is what the drain reads (R38, Engine/Core/TaskStream.h).
