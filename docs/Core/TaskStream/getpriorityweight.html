GetPriorityWeight

member of hbe::TaskStream Engine/Core/TaskStream.h The priority lane's configured share of the stream's allowance.

Signature

[[nodiscard]] uint32_t GetPriorityWeight() const noexcept

Function description

Declared in the header Engine/Core/TaskStream.h, defined in Engine/Core/TaskStream.cpp, returning drainPolicy.GetPriorityWeight(). The priority lane's configured share of the stream's allowance. The header's own note is a pointer to its sibling: "The configured priority lane weight. See GetFifoWeight."

The two weights are a pair, and only their ratio matters. What the lanes get is a split of the stream's CPU allowance, so 3-and-1 and 300-and-100 choose lanes identically (StreamDrainPolicy::ChooseLane). Read both or neither — a caller that reads one and configures the pair has invented the other half (GetFifoWeight).
A weight of zero is stored as zero and served as one, exactly as on the FIFO side (ConfigureRate); and with no allowance configured, the ratio has no book to divide, because the drain charges the lanes only when it is measuring CPU (Update, GetAccumulatedCPUTime).

Parameters

None.

Return value

TypeWhat you get
uint32_tThe stored priority weight. The pair with GetFifoWeight is the ratio; the pair is the constructed default unless a test re-rated it, since every ConfigureRate call site sits in a unit-test region

Examples

Illustrative — no code reads a weight outside these two accessors; they exist so a caller that re-rates a shared stream can restore it.

const auto fifo = stream.GetFifoWeight();
const auto priority = stream.GetPriorityWeight();

stream.ConfigureRate(1, 4);

RunPriorityBoundCollection();

stream.ConfigureRate(fifo, priority);

Saving both before re-rating is what makes the restore exact; a caller that restores 1, 1 instead has rewritten a stream it does not own (Engine/Core/TaskStream.h).
