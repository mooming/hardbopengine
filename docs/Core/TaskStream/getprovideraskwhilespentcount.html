GetProviderAskWhileSpentCount

member of hbe::TaskStream Engine/Core/TaskStream.h Times a provider was asked against a spent allowance; the invariant that must stay zero.

Signature

[[nodiscard]] unsigned GetProviderAskWhileSpentCount() const noexcept

Function description

Declared and defined in the header Engine/Core/TaskStream.h; there is no counterpart in Engine/Core/TaskStream.cpp. Times a provider was asked for work while this stream's allowance was already spent.

It must stay zero, and it is the only counter in this class of which that is true. "The invariant, made countable so it holds in a Release build too, where the assert on the provider gate is compiled out. It must stay zero: a spent stream that still manufactures work will run work it has no right to." (Engine/Core/TaskStream.h) It counts the failure of rule R39 — a stream that has spent its CPU must not manufacture more of it — and it is a bug detector, not a throttle reading. A non-zero value means the drain's budget gate stopped being consulted, and the work it let through is already in a lane by the time this number is read.
It is the release-build half of the assert beside it. The pass checks the same condition twice, once to abort in Debug and once to count in every configuration: 
Assert(budget.CanTakeWork(), "Stream ", name,
       " was asked for provider work while its allowance was spent. The drain gate is what keeps a "
       "spent stream "
       "from manufacturing work, so a provider ask here means that gate stopped consulting the "
       "budget.");

if (!budget.CanTakeWork())
{
    providerAsksWhileSpent.fetch_add(1, std::memory_order_relaxed);
}

From Engine/Core/TaskStream.cpp, TaskStream::Update()

Assert is compiled away unless !RELEASE_BUILD is defined — the Debug configuration only (Core/Debug.h, CMakeLists.txt) — so in Dev and Release this counter is the only witness. Reading it as zero in a Debug run proves nothing about a Release build; the counter is the portable check, which is why it exists at all.

Nothing resets it, and nothing else increments it. The single fetch_add above is the only writer, and no reset path touches it — not RequestWindowAdvance, not the drain, not the close. So a non-zero reading is permanent for the life of the object and cannot be attributed to a window without a second read (Engine/Core/TaskStream.cpp). A test that wants to prove the gate holds must read the counter, not merely assert it is zero at the end of a run in which some other test already broke the gate.
