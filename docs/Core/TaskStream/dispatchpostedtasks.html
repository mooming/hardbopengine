DispatchPostedTasks

member of hbe::TaskStream Engine/Core/TaskStream.h Post a callable to be run by the thread driving this stream, from any thread.

Signature

void DispatchPostedTasks(MainThreadTaskQueue::TTaskFunc taskFunc, void* userData, uint8_t priority = 128) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::DispatchPostedTasks(); the body is one call, postedTasks.Enqueue(taskFunc, userData, priority) (MainThreadTaskQueue::Enqueue). Post a callable to be run by the thread driving this stream, from any thread.

The default priority is 128, which is the middle of the byte and what a plain engine-loop post uses. "0 is the least urgent, 255 the most. The default is 128, matching a plain engine-loop post." (Engine/Core/TaskStream.h) The container behind this has one bucket per value a uint8_t holds — BoundedPriorityQueue<TaskItem, 256, MaxQueueSize> — so the whole byte is addressable and 128 is the neutral choice, not a low one (Engine/Core/MainThreadTaskQueue.h).
It cannot refuse the work, but not for the reason the header gives. The header states: "Cannot refuse the work. The queue is bounded; a post past the bound is a programming error and reports itself." The first sentence is what the code does; the rest does not hold. MaxQueueSize is the container's third template argument — the bucket size hint, not a capacity — and Enqueue locks and pushes, returning void with no check and no log line (Engine/Core/MainThreadTaskQueue.h, Engine/Core/MainThreadTaskQueue.cpp). A poster past any figure is accepted silently and the queue grows; nothing reports it. The observable consequence is memory and latency, never a refusal.
Where the callable runs is decided by which stream it was posted to, not by the word "main". The queue lives on the stream (postedTasks), and Update drains it at the top of every pass — before the close check, and with the queue's lock released so "a posted callable may post again" (Engine/Core/TaskStream.cpp, Update). The engine posts to the base stream, so "main thread" work is base-stream work (Engine/Core/TaskSystem.cpp).
Null checks are the poster's duty and nothing here enforces them. The header marks taskFunc "Must not be null" and userData "May be null", and the drain is where the difference would surface: ProcessTasks tests the function pointer before calling it and simply does not count an item whose function is null (Engine/Core/MainThreadTaskQueue.cpp). So a null function is dropped without a word rather than crashing — and the count ProcessTasks returns will not match the number of posts.

Parameters

ParameterTypeRequirement
taskFuncMainThreadTaskQueue::TTaskFuncInvoked as taskFunc(userData) on the thread driving this stream. Must not be null; a null function is skipped silently
userDatavoid*Passed through untouched; may be null. Its lifetime must outlast the run, which this call cannot arrange
priorityuint8_t, default 1280 least urgent, 255 most; ties run oldest first

Return value

void. There is nothing to check: the call cannot fail, and there is no token, id or cancellation handle for what it queued.

Examples

From Engine/Core/TaskSystem.cpp, TaskSystem::DispatchToMainThread()

GetStream(GetBaseTaskStreamIndex()).DispatchPostedTasks(taskFunc, userData, priority);

The engine-wide post is one line: it names the base stream and forwards the three arguments unchanged, which is what makes the base stream's driver the main thread's executor (Engine/Core/TaskSystem.cpp).
