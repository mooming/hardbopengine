ProcessPostedTasks

member of hbe::TaskStream Engine/Core/TaskStream.h Run every callable posted to this stream and report how many ran.

Signature

size_t ProcessPostedTasks() noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::ProcessPostedTasks(); the body is one call, postedTasks.ProcessTasks() (MainThreadTaskQueue::ProcessTasks). Run every callable posted to this stream that is runnable now, and say how many ran.

The pump is normally run for you, and this is the form for a driver that is not running a pass. Update calls postedTasks.ProcessTasks() itself as the first thing every pass does — before the close check, so a stream asked to close still runs what was posted to it. This public wrapper exists for a driver that must reach posted work without taking a task from the stream's lanes, and the header's reason for the arrangement is a bug that was paid for: the queue "lives on the stream that the engine loop drives, rather than beside the stream, because that is what makes the stream's own pump the only place work is taken: a wait that drives the stream then cannot fail to reach posted work, which was a real deadlock and not a hypothetical one" (Engine/Core/TaskStream.h).
It runs to exhaustion, in priority order, and a callable that posts more work extends the same call. The queue's drain loop pops until the queue is empty and invokes each callable with the queue's lock released (Engine/Core/MainThreadTaskQueue.cpp), so re-posting from inside a callable is legal and the new item is reached in the same loop. That makes this call unbounded in duration: a stream whose posted work re-posts itself — the IO stream's log drain is the known case — never returns control until it stops re-posting (DrainForShutdown).
The count is the number of callables actually invoked. The drain counts an item only when its function pointer is non-null, so a null-function item is consumed without being counted (Engine/Core/MainThreadTaskQueue.cpp, DispatchPostedTasks). Callables run in the caller's stack — this returns after the last one finishes, and a callable that blocks blocks the pump.
Only the stream's driver should call it. The queue's own lock makes the pop safe from any thread, but the callables were posted on the assumption of running on this stream's driver — the contract the whole queue exists to provide (Engine/Core/TaskStream.h). Calling this from a foreign thread executes that work on the wrong thread with nothing to detect it, and it will fight Update for the items.

Parameters

None.

Return value

TypeWhat you get
size_tCallables invoked by this call; 0 when the queue was empty. Items whose function pointer was null are consumed and not counted

Examples
