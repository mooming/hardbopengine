GetLaneWorkRefusalCount

member of hbe::TaskStream Engine/Core/TaskStream.h Times this stream found lane work and was given no lane by the drain policy.

Function description

Declared in the header Engine/Core/TaskStream.h, defined in Engine/Core/TaskStream.cpp. Times a pass found work waiting in a lane and chose no lane, which is the lane throttle itself — the StreamDrainPolicy allowance, not the CPU budget.

One increment per pass, so the number is a rate, not a queue depth. The condition that raises it is stated where it is counted: "A lane holding work with no lane chosen is the decline itself: ChooseLane returns a lane whenever work exists and the allowance is unlimited, so nothing else produces this combination. What a non-zero value means, and what it does not. A non-zero reading means this stream had work it deliberately did not take — held by the lane ratio's time book, waiting for the window that RequestWindowAdvance reopens. It is not a fault: it is the throttle doing the job it was configured for. It becomes a diagnosis when it is non-zero on a stream that was never configured, because the lane book is only charged when a CPU allowance is set, so on an unlimited stream this counter has nothing that can raise it (ConfigureBudget, GetAccumulatedCPUTime). Nothing resets it: it is a life total, so a non-zero value can also be history — read it twice, or compare two runs of the same program, to see whether the throttle is firing now.
It sees a different gate from GetGeneralQueueRefusalCount, and only the pair explains a stalled stream. "The engine throttles from two books, and a watch that reads only one cannot see work held by the other." (Engine/Core/TaskStream.h) A stream refusing the general queue shows here as zero and there as non-zero; a stream ratio-limited on its own lanes is the reverse. A third counter, GetProviderAskWhileSpentCount, is not a throttle reading at all: it is an invariant that must never move.
