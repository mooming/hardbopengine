From Engine/Core/TaskStream.cpp

How many work items this stream holds in its two lanes. It is the measurement a caller uses to ask "is this task's work still queued?", because a task's own done-flag cannot tell a completed task from one that was never dispatched (Task::HasDone).

The read is unsynchronised, and every other reader of those containers takes the lock. EnqueueFifo, EnqueuePriority, Dequeue and Update all hold queueLock around the lanes; this const method reads both container sizes with no lock at all (Engine/Core/TaskStream.cpp). Both containers are growable, so a concurrent enqueue can be moving their bookkeeping while this adds the two numbers. The answer is approximate by construction, and nothing warns when it is wrong.
Three kinds of held work are missing from the number, all of them deliberate. Items parked in readdingFifo and readdingPriority — taken by the last pass, not yet re-added — are not counted, so an item in flight is invisible here and is also invisible to AbandonHeldWork. Posted callables are a separate queue, read by HasPostedTasks. And work a provider still intends to produce does not exist yet, by definition (Engine/Core/TaskStream.cpp).
Zero pending does not mean nothing is coming. A stream whose producers are attached reports zero between drains while the producer has plenty to hand (DrainProvidersLocked). The count is a queue depth, not a statement about the work a task declared — a caller using it as a completion test must also know that no provider can still name the task, which is a question this number cannot answer (Task::HasDone).
