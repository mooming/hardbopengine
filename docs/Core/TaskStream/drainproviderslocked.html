From Engine/Core/TaskStream.cpp

One pass over one lane's provider list: build the context, ask in registration order, hand back the first item anyone produces. It is the whole mechanism by which work enters a stream from outside it, and it is nine effective lines.

The user call happens under the queue lock, and the header draws the rule from that. "The queue lock is held across the provider call, so this helper never runs user code unlocked and never re-enters the queue. A provider must therefore not touch this stream from inside Produce." (Engine/Core/TaskStream.h) That single sentence is R40, and it is why DetachProvider needs no in-flight counter: a detach arriving mid-Produce blocks on the same lock and therefore cannot erase a provider that is mid-call.
One context per pass, so every producer asked in a drain sees the same instant. TaskProduceContext::ForStream(streamIndex) is built once and passed by reference to each Produce — so a provider that compares its own age against context.now cannot be contradicted by a peer asked a microsecond later (Engine/Core/TaskStream.cpp, TaskProduceContext).
First success wins, in registration order, with no rotation. "Providers are asked in registration order and the first that hands something back wins; a provider with nothing returns nullopt and the lane stops being drained this pass rather than spinning." (Engine/Core/TaskStream.h) The consequence for a caller: a permanently productive provider registered early starves the entries behind it, because a producer later in the list is never reached while an earlier one succeeds. Nothing here rotates the cursor, so fairness across providers on one lane is the attaching order's problem.
It is reached only from an empty lane, and only while the budget allows (R39). The caller asks only when the lane has no items, is not draining for shutdown, and budget.CanTakeWork() holds — with a second Assert at the ask, "a spent stream would otherwise keep manufacturing work it has no right to run" (Engine/Core/TaskStream.cpp). A stream that cannot take work does not ask, so a provider cannot starve itself by being eager; and a provider is never asked twice per pass on the same lane, because the ask is inside one branch that ends the branch.
Nothing is charged for asking, and the counter that would have shown the waste is separate. A produced item is charged to the budget only when the task runs; the ask itself is unmeasured. The stream does keep providerAsksWhileSpent — incremented if an ask ever happened against a spent allowance, which R39 forbids and the assert is there to make unreachable (Engine/Core/TaskStream.h). A non-zero reading of that counter is a bug in the gate, not a policy.
