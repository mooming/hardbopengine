The count is per refusal and the log is per stream, because a throttled stream would otherwise log every pass. "A throttled stream has to be visible somewhere or it looks like an idle one, and the count alone is invisible to anyone not reading a debugger." (Engine/Core/TaskStream.h) The increment decides the logging: the fetch returns the previous value, so only the transition from zero prints. Every later refusal is silent and counted, which means the log line is a claim about the first refusal only — the allowance it names was the allowance at that moment, and a stream whose allowance was later changed by RequestBudget has a line that no longer describes it.
The count cannot be un-seen, and the warning cannot be re-shown. Nothing resets generalQueueRefusals, so in a long-running process or a test suite the log line is printed once — ever (Engine/Core/TaskStream.cpp). A verification that wants to see the message needs a fresh stream, and a verification that wants to see the throttling needs GetGeneralQueueRefusalCount, which is the half a test can assert on.
It is the counter's write-side companion and is called from exactly one place: the fallback branch of Update, taken when the lanes offered nothing and the budget refused the general queue (Engine/Core/TaskStream.cpp). It does not refuse anything — the refusal is budget.CanTakeWork() answering false — and it neither drops nor requeues a task: the tasks it names stay in the general queue for another stream or the next window (RequestWindowAdvance).

Parameters

None. Everything it reports — the name, the allowance — it reads from the stream.

Return value

void. It reports rather than decides, so there is nothing for a caller to act on; the caller has already declined the work by not calling TaskSystem::Dequeue.
