SetNestedPumpAllowed

member of hbe::TaskStream Engine/Core/TaskStream.h Open or close the window in which this stream may be pumped from inside its own pass.

Signature

void SetNestedPumpAllowed(bool allowed) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::SetNestedPumpAllowed(); the body stores the flag. 

nestedPumpAllowed = allowed;

From Engine/Core/TaskStream.cpp

Open or close the one window in which a pass of this stream may be entered from inside a pass of the same stream. The permission exists for a wait point — a task that blocks and must keep the engine moving by pumping the stream that is running it — and the header states both halves of its discipline: "Only a designated wait point may allow re-entry, and it withdraws the permission on the way out." (Engine/Core/TaskStream.h)

Nothing in the repository calls this, so the permission is currently never granted. Searching Engine/ and Applications/ finds the definition and no call site. The consequence falls out of the check it feeds, which sits at the top of Update: 
Assert(!isPumping || nestedPumpAllowed, "Stream ", name,
       " was pumped while it was already pumping; only a designated wait point may nest a pump.");

With nestedPumpAllowed permanently false, any nested pass fires that assert in a Debug build (Engine/Core/TaskStream.cpp). Outside Debug the assert is compiled away — !RELEASE_BUILD is defined for the Debug configuration only (Core/Debug.h, CMakeLists.txt) — so a nested pump is silently allowed, and what it breaks is not the assert but the assumptions around it: isPumping is cleared by the inner pass's guard on the way out (Update's PumpGuard), so the outer pass continues with the flag cleared and no pass can detect a second nesting.

The flag is a plain bool on a class that otherwise guards its state with a mutex and its close flags with atomics. That is only sound if the writer is the thread that reads it — the driver — which is what "a designated wait point" means. A call from another thread is an unsynchronised write to a field the driver reads every pass, and nothing detects it (Engine/Core/TaskStream.h).
Nothing withdraws the permission automatically. There is no scope guard and no counter: leaving a wait point must call this with false by hand, and a wait point that forgets leaves the stream permanently nestable (Engine/Core/TaskStream.h). The shape the header describes — grant, wait, withdraw — is enforced by nobody but the caller.

Parameters

ParameterTypeRequirement
allowedbooltrue to open the window, false to close it. There is no query form, so a caller that wants to restore a previous state must have saved it

Return value

void. Nothing reports whether a pump is in progress, and nothing reports whether the grant changed anything.

Examples

Illustrative — no call site for this exists in the repository, so the shape below is the contract's shape rather than an existing wait point.

stream.SetNestedPumpAllowed(true);

RunWaitThatMayPump();

stream.SetNestedPumpAllowed(false);

The withdrawal is the load-bearing line: without it, the grant outlives the wait point and every later pass of that stream may nest (Engine/Core/TaskStream.h). Doing this from inside a task of the stream being pumped is the only case the permission was written for.
