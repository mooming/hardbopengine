TaskStream

Engine/Core/TaskStream.h Two lanes of work, one CPU budget and one drain policy, run by a thread of its own or driven by someone else's.

Class description

class TaskStream final at Engine/Core/TaskStream.h: two lanes of work — a FIFO lane and a priority lane — plus the lock, condition variable, CPU budget, drain policy, provider lists and posted-callable queue that make those lanes runnable by a thread. It is where work is taken and run, and Update is the one function that decides what happens on any given pass.

Three clocks run on one stream, and they are kept in three different books. StreamDrainPolicy decides which lane to serve next from per-lane time shares and a staleness ceiling; CPUBudget decides whether the stream may acquire more work at all; and the general queue is a third source, consulted only when both lanes came up empty. The engine reads both throttles separately: "the engine throttles from two books, and a watch that reads only one cannot see work held by the other" (Engine/Core/TaskStream.h, GetLaneWorkRefusalCount, GetGeneralQueueRefusalCount).
A stream is threaded or driven, and both shapes run the same pass. A worker stream owns a std::thread running RunLoop; the base stream is driven by the thread running the engine, and the IO stream by the logger's driver thread — hence taskSystem is "recorded rather than looked up: Update may run on a thread that outlives the engine, so it cannot resolve the task system through the live engine the way a thread-owned loop can" (Engine/Core/TaskStream.h, Start). The distinction decides who closes a stream (RunLoop against CloseDrivenStream) and who is entitled to write the budget (RequestWindowAdvance).
Posted work lives on the stream, and the reason is a deadlock that happened. postedTasks is a MainThreadTaskQueue, not a peer of the stream: "It lives on the stream that the engine loop drives, rather than beside the stream, because that is what makes the stream's own pump the only place work is taken: a wait that drives the stream then cannot fail to reach posted work, which was a real deadlock and not a hypothetical one" (Engine/Core/TaskStream.h). DispatchPostedTasks is the posting end, and Update is the draining end — the stream's own pass calls ProcessTasks on it directly.
Two readings the name invites, and neither is right. A stream is not necessarily a thread — two of them ride other threads (Start) — and it is not one priority queue but a FIFO lane and a priority lane with a policy between them. Nothing in Engine/Core/TaskStream.h says either fact: the header carries no prose at all, only the address of this page, which is why the two readings used to be argued from the header's stale @brief line. That line is gone, and this note is where the correction lives.

Template parameters

None. TaskStream is final and not a template; everything variable about a stream is configuration — lane weights, staleness ceiling, CPU allowance — rather than type.

Non-member helper functions

One file-local helper, in an anonymous namespace in Engine/Core/TaskStream.cpp: constexpr size_t ProviderSlot(StreamDrainPolicy::ELane lane) maps FIFO to 0, Priority to 1 and ELane::None to 2 — "an out-of-range index when the lane is None" — so AttachProvider, DetachProvider and IsProviderAttached each reject a no-lane request with the same bounds test against a two-element array. It is not reachable from outside the translation unit and has no page.
