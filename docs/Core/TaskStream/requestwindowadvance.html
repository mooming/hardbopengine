RequestWindowAdvance

member of hbe::TaskStream Engine/Core/TaskStream.h Signal that the budget window closed, so this stream reopens its allowance on its own thread.

Signature

void RequestWindowAdvance() noexcept

Function description

Declared and defined in the header Engine/Core/TaskStream.h; there is no counterpart in Engine/Core/TaskStream.cpp. Mark that the budget window has closed, so this stream reopens its allowance on its next pass round the loop. It is a signal: it writes one atomic and no budget field.

Why the signal exists at all — a reset on the wrong thread costs either a lost charge or the thread's whole life. "A budget charges the CPU time of the thread that owns it, so a reset executed on another thread lands on the pairing between that thread's BeginTask and EndTask, and the cost of breaking the pairing is either a lost charge or the thread's whole life billed to the budget, which reads as a stream that refuses work forever." (Engine/Core/TaskStream.h) The consumer therefore does the reset itself, on its own thread: 
if (windowAdvanceRequested.exchange(false, std::memory_order_relaxed))
{
    budget.Reset();
    drainPolicy.EndRound();
}

From Engine/Core/TaskStream.cpp, TaskStream::Update()

The exchange both reads and clears the flag in one step, and it clears the lane book in the same branch — the two allowances always reopen together, because the lane ratio is a split of the same figure (ConfigureBudget).

A reopen that cannot interrupt a task in flight is the honest shape, and the header says so. "It means a window boundary falls between tasks, which is the overshoot rule MayTakeNewWork already states." (Engine/Core/TaskStream.h) A long task therefore spends into the next window: the overshoot is bounded by the longest task, not by the allowance (MayTakeNewWork).
The base stream's pass is the only caller, and it signals every stream at once. 
for (auto& stream : streams)
{
    stream.RequestWindowAdvance();
}

From Engine/Core/TaskSystem.cpp, TaskSystem::RunBudgetWindowPass()

That pass is driven from inside the base stream's own Update, once per configured period (Engine/Core/TaskSystem.cpp). Windows are therefore engine-wide: every stream reopens on the pass after a period boundary, and a stream that is not driven reopens when it is finally driven — a parked worker keeps a spent allowance until it wakes (WaitForWork).

The ordering is relaxed, and that is a claim about what the flag carries. A relaxed store pairs with the consumer's relaxed exchange, and nothing needs to travel with the flag: the allowance a window reopens with was written by the stream itself, either at configuration or by RequestBudget's apply on the same thread. The flag publishes no data, so a caller must not use it to publish any (Engine/Core/TaskStream.h).

Parameters

None. Every stream is signalled the same way, and there is no form that skips one.

Return value

void. The flag is not exposed, so a caller cannot tell whether a stream has consumed the signal yet; the observable consequence is GetAccumulatedCPUTime dropping to zero.

Examples

From Engine/Core/TaskStream.h, TaskStream::RequestWindowAdvance()

windowAdvanceRequested.store(true, std::memory_order_relaxed);

One store, one consumer, one flag per stream — the whole mechanism. It is also the reason the header's field comment says the flag is "set by the base stream's pass, cleared by this stream's own thread", which is the rule that keeps every write to the budget on the thread whose CPU it charges (Engine/Core/TaskStream.h).
