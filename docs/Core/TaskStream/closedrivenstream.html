From Engine/Core/TaskStream.cpp (the elided block is the abandonment warning)

The close path for a stream that rides someone else's thread. It asks, marks itself closed, gives away the work it still holds, and reports — the four things RunLoop would have done on a thread this stream does not have.

The exchange is both the mark and the re-entry guard. A second caller sees the first one's true and returns without abandoning anything twice, so closing twice is safe in the order that matters: only the first call reports (AbandonHeldWork, Engine/Core/TaskStream.cpp). The header's precondition sits on the other side of that: it must be called "after the driver has been withdrawn and can no longer be inside a pass", because nothing here stops a driver that is still running a pass (Engine/Core/TaskStream.h).
It exists because a driven stream can never close itself, and a stream that never closes is a deadlock waiting to be written. "A ride-on stream never enters RunLoop, so nothing there would drain it, report it, or mark it closed - and a stream whose closed state is never set is a stream that any correct future waiter would wait on forever. Whoever drove it closes it, after the driver has been withdrawn and can no longer be inside a pass." (Engine/Core/TaskStream.h) The engine has exactly two such streams — base and IO — and closes both (Engine/Core/TaskSystem.cpp). 
Logger::Get().SetLoggerStream(nullptr);
GetIOTaskStream().CloseDrivenStream();
baseStream.CloseDrivenStream();

From Engine/Core/TaskSystem.cpp, TaskSystem::JoinAndClear()

The IO driver is withdrawn first, which is the precondition in action: the logger's thread is the IO stream's driver, and clearing it is what makes the following close legal (Engine/Core/TaskSystem.cpp).

Nothing is drained here, and the difference from a worker's exit is deliberate. A worker's loop calls DrainForShutdown before marking itself closed; this call goes straight from the ask to AbandonHeldWork. That is the same reasoning that gives the base and IO streams a zero-length shutdown window — for them, "run until the queues are empty" is not what closing means, and the logger is flushed explicitly instead (DrainForShutdown, Engine/Core/TaskStream.h). Work that this drops was work the shutdown had already stopped pumping.
The report counts driven passes, not loops. The number printed is drivenPassCount, incremented at the top of every Update on whichever thread drove it (GetDrivenPassCount) — which is the only pass accounting a ride-on stream has.

Parameters

None.

Return value

void. Whether this call was the one that closed the stream is visible only in the log, since the exchange's earlier value is discarded.
