Update

member of hbe::TaskStream Engine/Core/TaskStream.h Drive exactly one non-blocking pass of this stream on the calling thread.

Signature

bool Update() noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::Update(). One pass of this stream, driven by the calling thread: it drains posted callables, sweeps finished work off both lanes, chooses a lane by policy, takes at most one item, asks the providers of an empty lane, falls back to the general queue, runs what it got, and re-queues a resumable item for the next pass. It never blocks. The thread-owned loop calls it in a tight sequence and calls WaitForWork only when it returns false.

Posted callables run before the close check, so a stream asked to close still runs what was posted to it. "Posted callables first: they are the engine loop's own work, and the frame budget is spent on them before the stream's queues are asked for anything. They run with the queue's lock released, so a posted callable may post again." (Engine/Core/TaskStream.cpp) The consequence is that closing a stream never loses posted work, and that a posted callable can always re-post itself — which is exactly why the IO stream's shutdown drain has no deadline (DrainForShutdown).

The return value means "the pass was worth doing", and a dropped item counts. Both failure paths — a task already released, and an item older than the stream's max age — return true after firing the item's notice: 

auto* task = taskSys.FindTask(workItem->taskID);
if (task == nullptr)
{
    ReportReleasedTask(*workItem);
    FireAbandonedNotice(*workItem);
    restore();
    return true;
}

false therefore means "nothing was taken and nothing was dropped", which is the only signal a driver has that WaitForWork is worth calling. A driver that reads true as "work ran" will spin on a stream whose lanes are full of dead items until the age ceiling clears them.

The queue lock is held across the provider probe, and the sweep is O(n) per pass on both lanes. The whole of step 6 to step 8 runs inside one std::unique_lock, and the FIFO sweep rotates every entry to drop finished ones: 

const size_t fifoCount = fifoQueue.Size();
for (size_t i = 0; i < fifoCount; ++i)
{
    auto entry = fifoQueue.Front();
    fifoQueue.PopFront();

    if (!entry.HasFinished())
    {
        fifoQueue.PushBack(entry);
    }
}

"Rotating the lane drops finished tasks in place and preserves arrival order for the rest, which is the same O(n)-per-loop price BoundedPriorityQueue::Remove already pays." (Engine/Core/TaskStream.cpp) A deep lane therefore costs every pass, not only the pass that empties it, and a provider asked inside that same lock must never touch this stream (DrainProvidersLocked, R40).

Two different counters see two different throttles, and a pass can raise both. A lane refusal needs work waiting and no lane chosen — "the decline itself: ChooseLane returns a lane whenever work exists and the allowance is unlimited, so nothing else produces this combination" — and is counted once per pass, "so it is a rate and not a queue depth". A general-queue refusal needs an empty pair of lanes and a spent allowance. GetLaneWorkRefusalCount and GetGeneralQueueRefusalCount are read together for that reason: "the engine throttles from two books, and a watch that reads only one cannot see work held by the other" (Engine/Core/TaskStream.h).

The CPU charge is conditional, and so is the lane charge that follows it. 

const bool chargingBudget = budget.GetAllowance().count() > 0.0;
const auto chargedBefore = chargingBudget ? budget.GetAccumulated() : std::chrono::nanoseconds::zero();
if (chargingBudget)
{
    budget.BeginTask();
}

With no allowance set, nothing is measured, so GetAccumulatedCPUTime stays zero and StreamDrainPolicy's lane book is never charged either — a lane ratio computed against a budget that is never spent is meaningless, which is why the lane charge sits inside the same if as EndTask. The measurement itself is time::ScopedTime around WorkItem::Run, and the elapsed time it records is what the slow-task warning compares against the TaskStreamDurationThreshold configuration parameter (Config/ConfigParam.h, default 0.16 s).

Age is judged after the lookup on purpose, and the order is the contract. "Age is judged after the task lookup, not before: a task that no longer exists has no owner to explain a refusal to, and the released path already owns that case. Both lanes pass this point, which is why one insertion covers the FIFO lane and the priority lane with one rule." (Engine/Core/TaskStream.cpp) The instant is the engine epoch, so an age in a log line is comparable with the lane time book in the same log (ReportAgedOutWorkItem).
One driver at a time, and that driver becomes the owner thread for the duration of the pass. IsBaseThread, IsIOThread, the owner-thread budget asserts and the thread-local stream index all answer about the thread inside Update, not about the thread that constructed the stream (Engine/Core/TaskStream.h). There is no lock making concurrent passes safe: the isPumping check is an Assert, and an Assert compiles to nothing unless __DEBUG__ is defined, which the build sets for the Debug configuration only (Core/Debug.h, CMakeLists.txt). Two threads driving one stream concurrently is unsynchronised in a Dev or Release build, and the flag that would have caught it is not there.
The pass resolves nothing global. "A driven stream must outlive the engine object that hosts the task system, so the pass reads the task system recorded at registration and never the live engine" (Engine/Core/TaskStream.h) — hence TaskSystem& taskSys = *taskSystem; taken from the pointer Start recorded. A stream whose system has been destroyed dereferences that pointer with nothing to detect it.
The private Dequeue helper is not part of this pass. Update pops both lanes itself inside one lock and consults the policy; the private Dequeue(std::optional<WorkItem>&) pops the priority lane first, ignores the policy entirely, and has no caller in Engine/ or Applications/ — including TaskSystemTest, which is its friend (Engine/Core/TaskStream.cpp). Its comment describes a caller that does not exist: "gating here would let a caller's refill stall on an exhausted allowance." It is recorded here rather than documented as an interface because no interface calls it; the page is dequeue.html.

Parameters

None.

Return value

TypeWhat you get
booltrue when the pass took an item, ran one, or dropped one; false when it was asked to close or found nothing to take. It does not distinguish "ran a task" from "dropped a dead item", and it is not a count of work

Examples

From Engine/Core/TaskStream.cpp, TaskStream::RunLoop()

while (likely(!closeRequested.load(std::memory_order_acquire)))
{
    if (!Update())
    {
        WaitForWork(std::chrono::milliseconds(10));
    }
}

The only loop in the engine that calls this, and the reason the return value is shaped as it is: a pass that got nothing buys a ten-millisecond wait, and a pass that got something is worth running again immediately. A driven stream — the base stream and the IO stream — calls Update from its host thread instead, on that host's own cadence (Start, WaitForWork).
