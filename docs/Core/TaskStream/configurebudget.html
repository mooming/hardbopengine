ConfigureBudget

member of hbe::TaskStream Engine/Core/TaskStream.h Set this stream's CPU allowance for one window; zero means unlimited and switches measurement off.

Signature

void ConfigureBudget(std::chrono::duration<double> allowance) noexcept

Function description

Defined in Engine/Core/TaskStream.cpp as TaskStream::ConfigureBudget(). Set this stream's CPU allowance for one window, expressed as a duration; zero means unlimited, and unlimited is the state every stream is constructed in.

From Engine/Core/TaskStream.cpp

The unit is a duration, and the yardstick is the base stream's frame period. "The yardstick it is measured against is time::GetBaseFramePeriod, engine-wide, so a caller states how much CPU this stream may spend per frame period of the base stream and leaves the arithmetic alone." (Engine/Core/TaskStream.h) An allowance of half a frame period means half a frame period of measured CPU, not half a wall-clock interval.
An unlimited stream does not measure its tasks at all, and that is the reason GetAccumulatedCPUTime reads zero. "A measurement that cannot change a decision is a syscall billed to every task for nothing, and an unlimited budget cannot change a decision. Consequently GetAccumulatedCPUTime stays zero until an allowance is set - that is the absence of accounting, not a task that cost nothing." (Engine/Core/TaskStream.h) The pass implements exactly that with one boolean: 
const bool chargingBudget = budget.GetAllowance().count() > 0.0;

From Engine/Core/TaskStream.cpp, TaskStream::Update()

The same boolean gates budget.BeginTask(), budget.EndTask() and the lane charges ChargeFifo/ChargePriority, so setting an allowance is what turns on both the budget and the lane-ratio machinery that reads it (Update, GetAccumulatedCPUTime, ConfigureRate).

Both books are written here, and both are unsynchronised. budget.Configure and drainPolicy.ConfigureAllowance are plain writes read by the stream on its own thread every pass, which is why the check exists and why the header offers RequestBudget as the cross-thread form: "from elsewhere it is a data race, not a late write" (Engine/Core/TaskStream.h). The check is an Assert, compiled away unless !RELEASE_BUILD is defined — Debug only (Core/Debug.h, CMakeLists.txt) — and it is skipped while threadID is still default, which is the IO stream until its first pass (Start).
The window this allowance bounds is reopened by the base stream, not by this call. A configuration sets the size of the allowance; RequestWindowAdvance is what closes the window and lets the stream reopen it on its next pass, and only the owning thread performs the reopen because the budget charges the CPU time of the thread that owns it (CPUBudget::Reset).

void. Nothing reports the previous allowance; there is no getter for it on this class, and GetAccumulatedCPUTime reports what has been spent rather than what is permitted.

From Applications/EngineTest/TestMain.cpp

The one call site outside a unit-test region: a test application gives the base stream a one-millisecond allowance per window, and does it after Initialize and before Run — the ordering this function asks for, because the stream is not yet bound to a driver (Start). Every other stream in that run is left unlimited, which means it is left unmeasured (GetAccumulatedCPUTime). A change after the stream is bound belongs through RequestBudget, which the stream applies to itself.
