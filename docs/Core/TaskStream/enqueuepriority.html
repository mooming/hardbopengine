From Engine/Core/TaskStream.cpp

Structurally identical to EnqueueFifo — same lock, same notify — and the entire difference is which container receives the item. The header's one-line contract states the ordering the container owes: "Queue a task on the priority lane, which runs the highest priority number first and the oldest first within a tie" (Engine/Core/TaskStream.h). So a large priority byte is urgent here, and equal bytes are served in arrival order.

"Bounded" in the container's name bounds the priority levels, not the number of items. The lane is a BoundedPriorityQueue<WorkItem> with the defaults MaxPriority = 256 and BucketSizeHint = 0: 256 buckets, one per value a uint8_t priority can hold, each a Deque<WorkItem> created the first time that level is used and released when it runs dry (Engine/Container/BoundedPriorityQueue.h). Push returns nothing and never refuses, which is why the header can call this enqueue unfailable.
Constructing the lane allocates nothing, but the first item at a priority pays for a bucket. "Constructing a queue therefore allocates nothing no matter how many priority levels it declares, which is what makes MaxPriority=256 and a roomy BucketSizeHint affordable at the same time" (Engine/Container/BoundedPriorityQueue.h). A stream that sees one priority level does not pay for the other 255 — and a stream that sprays items across 200 levels holds 200 live buckets until each empties.
The priority byte is load-bearing on this lane and nearly free on the other. The drain picks a lane by policy and then pops the head of that lane, so on the FIFO lane the byte only matters if an item is later re-filed to the priority lane during compaction (Engine/Core/TaskStream.cpp). A producer that cares about ordering must choose the lane as well as the byte: EnqueueFifo will not reorder what it is given.
Same lock, same R40 prohibition. Calling this from inside Produce on the stream draining the provider deadlocks on the non-recursive queueLock (EnqueueFifo carries the full statement).

void. No capacity is checked because there is no item capacity to check; a producer that outruns this lane ages its oldest items until the max-age rule drops them (StreamDrainPolicy::SetMaxAge).

Examples

const auto item = task->GenerateSubTask(itemStart, itemEnd, priority);

The engine's split path chooses the lane by the priority byte it was given: nonzero goes to the priority lane, zero goes to FIFO (Engine/Core/TaskSystem.cpp). That is the whole routing rule a caller can rely on — a byte of 0 means arrival order, and any other byte means "ahead of the queue, behind anything more urgent".

From Engine/Core/TaskStream.cpp, TaskStream::Update()

priorityQueue.Remove([](const WorkItem& task) { return task.HasFinished(); });
priorityQueue.PushRange(readdingPriority);

The lane's own maintenance, run inside the drain pass: items whose range finished elsewhere are struck off the lane. It shows what the container actually requires of its element type — a priority byte and HasFinished (Engine/Container/BoundedPriorityQueue.h) — and it is the sweep that keeps a lane whose items were completed by another stream from being drained again (Engine/Core/TaskStream.cpp).
