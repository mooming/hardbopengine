ProcessTransition

member of hbe::ComponentSystem Engine/Core/ComponentSystem.h Private: run the re-enable, sleep or death path each component chose during its update.

Signature

void ProcessTransition()

Function description

Private, defined in the header Engine/Core/ComponentSystem.h; the third and last phase of Update. It walks the transition list — everything ProcessUpdate found no longer enabled — and asks each component's GetState, because "not enabled" covers three different intentions. The answer decides which callbacks run and which list, if any, the component lands on. Then the transition list is cleared, and with it the dead are destroyed. 

switch (compo.GetState())
{
    case ComponentState::ALIVE:
        compo.OnEnable();
        updateList.push_back(std::move(compo));
        break;

    case ComponentState::SLEEP:
        compo.OnDisable();
        sleepList.push_back(std::move(compo));
        break;

    case ComponentState::DEAD:
        compo.SetState(ComponentState::SLEEP);
        compo.OnDisable();
        compo.SetState(ComponentState::DEAD);
        compo.Release();
        break;

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessTransition()

The death case writes SLEEP before disabling and restores DEAD before releasing, and that two-step is the reason a component can have one disable callback instead of two. Both exits reach this function, and a component's OnDisable is specified to see SLEEP in both (the lifecycle table). Without the temporary write, the death path would call the disable with the state already DEAD, and a component that wanted to behave identically on both exits would have to test for two states. The repository's subclass asserts the contract on every one of the four callbacks (Engine/Core/ComponentSystem.cpp).
The ALIVE case is the re-enable path, and it is the only way back to running. A component reaches it by having been found not enabled at the end of its update and having since become ALIVE again — in practice, a component that changed its own state more than once inside Update. It gets OnEnable and a place on the update list, so it is ticked again next pass (Engine/Core/ComponentSystem.h). A component already parked in the sleep list can never reach this case: nothing in the class reads that list, which is the trap stated on SetEnable and on the conversion to bool.
The default case is a Debug-only assert, and the component is destroyed either way. The switch handles ALIVE, SLEEP and DEAD; any other value — NONE or BORN, both reachable by a component calling SetState with them during its update, or any value outside the enum — falls to: 
default:
    Assert(false,
           "Unexpected component state %d on processing "
           "transition.\n",
           compo.GetState());
    break;

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessTransition()

Assert compiles to nothing unless __DEBUG__ is defined, and only the Debug configuration defines it (Engine/Core/Debug.h). In Dev and Release the fall-through is silent: the component is neither enabled, disabled nor released, and the transitionList.clear() that ends the function destroys it without any callback (Release). The repository's component is written so this cannot pass unnoticed — its destructor fails the test if it was destroyed without having seen all four callbacks (Engine/Core/ComponentSystem.cpp) — but nothing outside a Debug build reports which state caused it.

Parameters

None. It reads the state each component carries, and does not take the elapsed time — a transition is not a tick.

Return value

void. Nothing reports how many components were re-enabled, parked or destroyed, and there is no accessor for the sleep list's size, so a system full of sleeping components is indistinguishable from an empty one except through the conversion to bool, which claims it is non-empty.

Examples

The path a retired component takes, end to end, in one call to Update — the repository's components all leave this way: 

++updateCount;

if (updateCount > updateNum)
{
    Destroy();
}

From Engine/Core/ComponentSystem.cpp, ComponentSystemTest

Destroy writes DEAD; ProcessUpdate notices and moves the component to the transition list; this function runs the disable under SLEEP, the release under DEAD, and the final clear destroys the object. Its destructor then confirms all four callbacks happened, which is the only assertion in the tree that the whole lifecycle ran (Engine/Core/ComponentSystem.cpp).
