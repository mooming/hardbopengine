operator bool

member of hbe::ComponentSystem Engine/Core/ComponentSystem.h Whether the system still holds a component, counted from three of its four lists.

Signature

[[nodiscard]] explicit operator bool() const noexcept

Function description

Defined in the header Engine/Core/ComponentSystem.h. Answers "does this system still hold a component?", and its body enumerates three of the four lists the class owns: !initList.empty() || !updateList.empty() || !sleepList.empty(). It is explicit, so it fires only in a boolean context — an if, a while, a ! — and not in an arithmetic or stream one.

It is the pump's termination test, and the test loop is written on top of it. 
while (testSystem)
{
    testSystem.Update(0.033f);

    if (!testResult)
        return;
}

From Engine/Core/ComponentSystem.cpp, ComponentSystemTest

The loop runs until the system holds nothing, which is the intended shape: drive the system, do not count frames. It works for that test because every component there eventually calls Destroy, and a destroyed component is dropped by ProcessTransition instead of being parked anywhere (Engine/Core/ComponentSystem.h).

A system whose only members are sleeping answers true forever, so that loop above never ends. sleepList is counted here and read by nothing else: ProcessInit consumes the init list, ProcessUpdate walks the update list, and ProcessTransition consumes the transition list and moves anything that went to sleep into the sleep list, which no code ever drains (Engine/Core/ComponentSystem.h). A component parked there keeps the system non-empty, and Update on a system with an empty init and update list does nothing at all. The combination is a livelock for a caller that pumps on this operator: the loop spins, Update returns immediately every time, and the condition never becomes false. A component that parks itself with SetEnable(false) therefore cannot be retired afterwards, and neither can the system be driven to empty (SetEnable states the same trap from the component's side).
The transition list is deliberately not counted, and that is what makes the test correct. ProcessUpdate moves anything that stopped being enabled into transitionList, and ProcessTransition empties it in the same call, so the list is always empty when a call to Update returns (Engine/Core/ComponentSystem.h). Leaving it out of the answer avoids a system reading "alive" only in the middle of a pass. The consequence in the other direction is that a system holding nothing but components that fell into the switch's default case reads false while those objects still exist — which, since that case's only handling is a Debug-only assert, is a corner nobody in the tree reaches.

Parameters

None.

Return value

TypeWhat it tells the caller
booltrue if the init, update or sleep list holds anything. It is not a statement that work is possible — a system containing only sleeping components returns true and can do nothing

The only use in the repository, and the only shape of driver this class has ever had. If a component can sleep, a driver written like this needs its own bound — a frame count or a deadline — because this operator cannot tell "still working" from "stuck asleep".
