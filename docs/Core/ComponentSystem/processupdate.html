ProcessUpdate

member of hbe::ComponentSystem Engine/Core/ComponentSystem.h Private: tick every enabled component and sort them by what their state says afterwards.

Signature

void ProcessUpdate(const float deltaTime)

Function description

Private, defined in the header Engine/Core/ComponentSystem.h; the second phase of Update, and the only place a running component's Update is called. It walks the update list, ticks each component, and sorts them by what their state says afterwards: still enabled goes to a scratch list, no longer enabled goes to the transition list. Then the two lists are swapped and the scratch list cleared. 

for (auto& compo : updateList)
{
    compo.Update(deltaTime);

    if (!compo.IsEnabled())
    {
        transitionList.push_back(std::move(compo));
    }
    else
    {
        swapUpdateList.push_back(std::move(compo));
    }
}

std::swap(updateList, swapUpdateList);
swapUpdateList.clear();

From Engine/Core/ComponentSystem.h, ComponentSystem::ProcessUpdate()

The IsEnabled test right after the tick is what makes a component's own decision take effect in the same pass. A component that calls Destroy or SetEnable(false) inside its update is moved to the transition list the instant its update returns, and ProcessTransition — the very next phase of the same call — runs its disable and release (Engine/Core/ComponentSystem.h). No component continues to be ticked after it has asked to stop, because the walk moves it out of the list it is being walked from.
Every component is moved on every pass, and the shells left behind are destroyed at the end of this function. The swap puts the old update list into swapUpdateList, and the clear() that follows destroys the moved-from objects it now holds (Engine/Core/ComponentSystem.h). Two consequences for a component author: an address changes every pass, so a self-reference or an external pointer is worthless once a pass ends; and a destructor runs on a moved-from object every pass, so a subclass destructor that does anything but release must first detect that it is a shell. That is why the repository's component marks itself invalid in its move constructor — the statement rhs.isValid = false; in that constructor is what tells the destructor below that the object never saw a callback because it was only ever moved (Engine/Core/ComponentSystem.cpp): 
~Test() override
{
    if (!isValid)
        return;
}

From Engine/Core/ComponentSystem.cpp, ComponentSystemTest

Without that flag the test would report a spurious failure for every component that merely moved, since a shell is destroyed having never seen a callback (~Component). A second reason not to trust an address: the lists are HVectors — a std::vector on the engine's allocator (Engine/HSTL/HVector.h) — so the push_backs reallocate as they grow.

swapUpdateList must be empty on entry, and only this function's own clear keeps it that way. The scratch list is a member rather than a local so its capacity is kept between passes — the point of the swap dance is to avoid rebuilding the update list every frame. That holds only while the invariant does, and nothing else in the class touches swapUpdateList (Engine/Core/ComponentSystem.h): these lines are its whole usage.

Parameters

NameTypeMeaning
deltaTimeconst floatHanded unchanged to every component's Update, in list order, with no skipping, no per-component timing and no time measurement of any kind

Return value

void. Nothing is reported about the pass. The outcome of the sort is visible only as the contents of the update, transition and sleep lists afterwards, and the class exposes none of them — there is no count, no emptiness test for an individual list, and no way for a caller to see that a component moved at all.

Examples

The repository measures this function directly: thousands of components are created, then the system is pumped to empty and the total loop time reported (Engine/Core/ComponentSystem.cpp). Its components do nothing but count ticks and retire after a fixed number of them, so the figure is the cost of the bookkeeping itself — one tick, one state test and one move per component per pass.
