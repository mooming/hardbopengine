ComponentSystem

Engine/Core/ComponentSystem.h A value-owning pump that drives components of one type through the Component lifecycle, in three phases per call.

Class description

template <typename TComponent> class ComponentSystem at Engine/Core/ComponentSystem.h: a value-owning pump that drives components of one concrete type through the Component lifecycle. It holds five lists and one name, and its public surface is three functions — Update, GetName and the conversion to bool — plus Create, which has no page of its own (Coverage).

The lists are the state machine, and a component's position among them is the only thing the system remembers about it. The transition function is a switch on the state, and the cases differ only in which list they push onto:
ListWritten byRead by
initListCreate, which also sets BORNProcessInit, which consumes the whole list and clears it
updateListProcessInit and the ALIVE case of ProcessTransitionProcessUpdate, every pass
swapUpdateListProcessUpdate only, then swapped with the update list and clearednothing — it is scratch capacity kept between passes
sleepListthe SLEEP case of ProcessTransitionnothing, except the emptiness test in the conversion to bool
transitionListProcessUpdate, for anything that stopped being enabledProcessTransition, which consumes and clears it

Because every list is emptied by the phase that reads it, the state at the end of a pass is: init empty, update holding the live components, sleep holding the parked ones, transition empty, swap empty (Engine/Core/ComponentSystem.h).

The sleep list is a dead end, and the two halves of the class combine into a livelock because of it. Nothing moves a component out of sleepList: ProcessInit, ProcessUpdate and ProcessTransition each walk a different list, and the sleep list is only ever pushed to. So SetEnable(false) is permanent — the component never sees another callback, and Release is never called for it — while the conversion to bool counts that same list, so the driver the class invites, while (system) { system.Update(dt); }, keeps calling Update on a system where all three phases do nothing. The one driver in the repository avoids this only because none of its components ever sleeps: each counts updates and then calls Destroy (Engine/Core/ComponentSystem.cpp).
Every component is moved at least once per pass, and the moved-from shell is destroyed in the same function. ProcessUpdate moves every entry into the scratch list, swaps the lists, and clears the scratch — so a subclass destructor runs on a shell every pass, and an address is worthless once a pass ends (Engine/Core/ComponentSystem.h). The lists are HVectors — a std::vector on the engine's allocator (Engine/HSTL/HVector.h) — so growth moves them again. A component that wants to act on being destroyed rather than moved must detect it itself; the repository's component carries an isValid flag set to false by its move constructor for exactly that reason (Engine/Core/ComponentSystem.cpp).
Nothing in the engine uses this class, and the only instantiation is a unit test. The sole ComponentSystem object in the tree is ComponentSystem<Test> inside the #ifdef __TEST__ region of Engine/Core/ComponentSystem.cpp, where Test is a local struct deriving from Component and asserting the state it sees at each of the five callbacks. No subsystem in Engine/ outside these two headers, and nothing in Applications/, owns a component system — so everything stated here comes from the header's own code plus the behavior that test pins down.

Template parameters

ParameterRequirement the code imposes
typename TComponent A concrete component type, stored by value — not a pointer and not the Component base, which is abstract and cannot be held in a vector. Four things the class does to it narrow the requirement: Create constructs it from whatever arguments the caller passes; the three Process* functions call the five lifecycle methods on it; the phases move it, so it must be move-constructible — which a subclass must declare itself, because the base's user-declared destructor suppresses its implicit move operations (Component::Component); and the swap-and-clear in ProcessUpdate destroys a moved-from object every pass, so its destructor must tolerate being a shell

Non-member helper functions

None. Engine/Core/ComponentSystem.cpp defines no helper and no out-of-line member — since the class is a template, everything about it must live in the header. What the source file does contain, inside #ifdef __TEST__, is ComponentSystemTest::Prepare, the suite entry that builds the only component system in the engine and measures it; the class is declared in the same header, also under #ifdef __TEST__, and belongs to the test module rather than to this one.

The pattern the sources show is single-threaded — one caller enters Update and all five lists are touched inside it — but no header states that as a rule, and a promise here would be an invention.
