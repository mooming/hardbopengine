IsReferenceType

Engine/Core/CommonUtil.h the engine's only hand-written type trait: it answers is this an lvalue reference with a tag type and says how many bytes storing such a type needs

Class description

IsReferenceType is a class template with two members and no functions. Its primary template reports False_t and sizes storage for the object itself; the partial specialisation for T& reports True_t and sizes storage for a pointer to the object. The two members exist together on purpose: Result selects the branch that writes the storage, and TypeSize is how much storage that branch needs. Reporting one without the other would let a caller dispatch correctly and then allocate the wrong number of bytes.

The single consumer is Optional. It sizes its inline storage with this trait — Byte value[IsReferenceType<TType>::TypeSize], aligned by alignas(std::max(IsReferenceType<TType>::TypeSize, Config::DefaultAlign)) at Engine/Memory/Optional.h — and it dispatches every lifetime operation by writing Result(), letting overload resolution choose between storing a referent in place and storing its address. Optional<int&>, Optional<Class&> and Optional<Integer&> are instantiated by the unit tests in Engine/Memory/Optional.cpp, :60 and :80.

TypeSize is the extent of the storage, not a size you may copy with. For an lvalue reference the trait reports sizeof(T*), while sizeof(TType) for the same TType is the size of the referent. Measured on this machine: with TType = int&, TypeSize is 8 and sizeof(TType) is 4. Optional's reference branch sizes its memcpy by sizeof(TType) (Engine/Memory/Optional.h for the copy, :223 for the move) while the storage holds a pointer — so the two sizes disagree for every referent that is not pointer-sized. Reported as a finding against Memory; stated here because a caller that copies storage sized by this trait is the same mistake, and this page is where the number is defined.

Template parameters

T typename The type being questioned, exactly as written. The trait does not strip const, references or anything else before asking the question: const int& is a reference and selects the specialisation, and int&& is not a T& and selects the primary template. Both of those were checked with a compiler, not inferred — see Coverage

Class methods

None, and none is needed. A trait is read through its members at compile time; a function would imply a runtime question that this one never asks. Note also that Result() at a call site is not calling anything on this trait — it is value-initialising one of the empty tags, whose contract is that such a temporary carries nothing.

Non-member helpers

None. Engine/Core/CommonUtil.h declares GetAs, SetAs, CopyAs, ToAddress and CountOf alongside this trait; they are unrelated to it and belong to Module functions.

Coverage

GapDetail
What was compiled to establish the branch rules Seven static_asserts over int, int&, const int& and int&&, checking Result against the two tag types and TypeSize against sizeof(T), sizeof(T*) and sizeof(T&&), compiled clean with c++ -std=c++2b -IEngine -fsyntax-only. Every resolution stated on this page is one of those assertions; nothing here is inferred from the spelling of the specialisation
Function-pointer, array and member-pointer types Not probed. They take the primary template, which is certainly what the header does with them, but their sizeof semantics differ from a scalar's and no consumer in this tree feeds such a type to the trait, so no claim about them is made
Storage layout, alignment and aliasing The trait only reports a number. Whether Byte value[] may be read as TType&, and whether Config::DefaultAlign is sufficient for a type with a larger requirement, are contracts of Memory
