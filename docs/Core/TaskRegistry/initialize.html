Initialize

member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp Takes the initial banks now; call once, before any task is created.

Signature

void Initialize(StaticString registryName, std::size_t initialCapacityRecords, std::size_t growByRecords) noexcept

Function description

Defined in Engine/Core/TaskRegistry.cpp as TaskRegistry::Initialize(). It stores the name, the grow-by (with a zero replaced by DefaultGrowByRecords), a reset ceiling, a reset free list, and the allocator currently in scope; then it allocates initialCapacityRecords / recordsPerBank banks, stopping at the first refusal, and logs what the table ended up holding. 

recordsPerBank = growByRecords > 0 ? growByRecords : DefaultGrowByRecords;
maxCapacityRecords = DefaultMaxCapacityRecords;
freeRecordHead = TaskID::NullIndex;
bankAllocatorID = MemoryManager::GetCurrentAllocatorID();

From Engine/Core/TaskRegistry.cpp

The ceiling is reset to "no ceiling", whatever SetMaxCapacity had been told. SetMaxCapacity is therefore only meaningful after this call. The order the task system uses — Initialize, then any ceiling — is the only order that survives.
A partial bank is asserted in a debug build and accepted silently in every build. The header says initialCapacityRecords "is rounded down to a whole number of banks of growByRecords, and GetCapacity reports what the table really holds", and the loop's initialCapacityRecords / recordsPerBank does exactly that. But the line above it Asserts that the division is exact — "which is not a whole number of banks of N so it holds fewer than that" (Engine/Core/TaskRegistry.cpp). A configuration that asks for 10000 records with a grow-by of 4096 is a bug in a debug build and a quiet 8192-record table in a shipping one. Reading GetCapacity after this call is the only check that works in both.
Call it once, before any task is created. "Calling it again while records are in use leaks the banks it already had, which is why the task system calls it from its own Initialize and nowhere else" (Engine/Core/TaskRegistry.h). The code explains why the header is understating it: bankCount and usedRecords are not reset, while freeRecordHead is, so a second call abandons the previous free chain — the old records stay pointed at by banks[] and are still freed by the destructor, but with a recordsPerBank that may no longer match how they were built.
Allocation failure is not fatal and not silent. A bank that the allocator refuses ends the loop, leaving the table at whatever it managed to take, and the log line reports the capacity actually achieved — "is initialized with N task records" (Engine/Core/TaskRegistry.cpp). A caller that treats this call as a promise should compare GetCapacity with what it asked for.
