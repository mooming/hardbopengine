Structurally it is Find with the record instead of the task, and the same three questions — is the identity real, does a bank hold that index, is this record the generation that index was issued with. Two of its callers hold registryLock (Release) or do not (SetSuccessor, GetSuccessor), and that difference is what a caller inherits from here.

Every load here is relaxed, including the two that Find takes with acquire. Create publishes a filled record by releasing inUse, and the pairing that completes it is Find's acquire load. A relaxed reader is entitled to a value but not to the writes that preceded the release, so through this path record.inUse can read true while the task fields the same Create stored are not yet visible. Release is protected by the lock that covers every write; the two successor calls have no such cover (Engine/Core/TaskRegistry.cpp). The published path is the one to imitate.
Returning the record rather than the task is the reason this exists separately. Release needs the free-list link and the flag, SetSuccessor needs the successor field, and neither belongs in a public type. The consequence is that a caller holding this pointer holds a record that may be re-issued — which is why the mutating calls that use it do so immediately rather than storing it.
A foreign registry's identity can pass this test. An identity is an index and a generation with nothing naming its issuer, so an ID from another registry that happens to match a live record here is accepted — a case the Release log explicitly anticipates ("an ID from a registry that did not issue it", Engine/Core/TaskRegistry.cpp). Isolation between registries is the caller's discipline, not this check's job.

The caller's pattern in full: resolve, report the miss with the identity that missed, and change nothing on that path. The success path then writes a plain field with no lock — see SetSuccessor for what that costs.
