GetMaxCapacity

member of hbe::TaskRegistry Engine/Core/TaskRegistry.h The ceiling in records; zero means no ceiling.

Signature

[[nodiscard]] std::size_t GetMaxCapacity() const noexcept

Function description

Declared and defined in the header Engine/Core/TaskRegistry.h; there is no counterpart in Engine/Core/TaskRegistry.cpp. One read of the ceiling Grow tests, zero meaning no ceiling.

The inert value is the default, and a cap is something a caller opts into knowingly. The header puts it beside the stream's result ceiling so one rule covers both growables (Engine/Core/TaskRegistry.h). The engine runs with no ceiling, and its sizing test asserts exactly that: "R21's inert default is no ceiling" (Engine/Core/TaskRegistry.cpp).
It bounds growth; it does not describe the table. A registry capped at 100000 records with 4096 allocated reports a capacity of 4096 and a ceiling of 100000 — the two figures answer different questions, and the only one that constrains what can be issued today is GetCapacity. Conversely the ceiling does not protect against a Create refusal: a table whose records are all live refuses work long before it reaches either limit.
A ceiling below the current capacity does not shrink anything. Nothing here frees a bank; the number only makes the next Grow refuse, with the log from ReportRefusedGrowth naming the ceiling and the bank limit. Lowering a ceiling is a statement about the future, and the table's present memory is unaffected.

Parameters

None.

Return value

TypeWhat you get
std::size_tThe ceiling in records, or 0 for none. Read the zero as unlimited: the refusal logs spell that convention out in the message so an operator does not read "ceiling is 0" as "no room"

The pair this belongs to is SetMaxCapacity / this read, and the ordering rule that goes with it: Initialize resets the ceiling to zero, so a cap that is set first is silently discarded.
