member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp Tracks a task under the lock and never grows; a full table returns a null ID.

From Engine/Core/TaskRegistry.cpp

The order of the last four statements is the publication protocol, and it is the whole reason Find can be lock-free. The generation is bumped first, the task is filled in place, and only then is inUse released true — so a reader that acquires inUse and sees it set is guaranteed to see the task fields this thread wrote before it. Releasing Release then Create the same record yields a different generation, which is what makes a stale TaskID detectable rather than merely dangerous.

A new identity always carries a fresh generation, and the successor is cleared on the way in. A recycled record cannot inherit either its predecessor's identity or its chain: record.successor = {} is stored before publication, so a join that closed on the previous occupant cannot dispatch the new one.
It never grows the table, and the refusal is the caller's problem to solve elsewhere. "Call Grow where memory may be taken - between frames, on the owner - and treat a refusal here as a sizing problem to fix there" (Engine/Core/TaskRegistry.h). The reason is a latency argument: the thread that runs out of records is not the thread that should pay for a megabyte bank in the middle of whatever it is doing. The refusal path is ReportNoRoom, an error log naming the task, the capacity and the ceiling.
The return value must be checked, and the engine's own callers check it. A null TaskID means the task was not tracked and will not run — and a task that never runs looks exactly like a task still waiting. TaskSystem's split path logs "ParallelFor could not get a record for task ..., so the split was not queued. The registry is at its capacity." when this returns null (Engine/Core/TaskSystem.cpp).
func and userData are stored, not inspected. Nothing validates the runnable, and nothing owns the context pointer: the task that eventually runs receives the same pointer it was given, on whichever stream takes it. The registry guarantees only that the record is live and its identity is current while the task is tracked.
