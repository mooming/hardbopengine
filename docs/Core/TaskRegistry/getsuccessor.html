GetSuccessor

member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp The recorded successor, or a null ID when nobody is waiting.

Signature

[[nodiscard]] TaskID GetSuccessor(TaskID task) noexcept

Function description

Defined in Engine/Core/TaskRegistry.cpp as TaskRegistry::GetSuccessor(); the body is a conditional over the same record lookup the mutating calls use. 

const Record* record = FindLiveRecord(task);

return record == nullptr ? TaskID{} : record->successor;

From Engine/Core/TaskRegistry.cpp

One call answers both questions a dispatcher asks: is this task still the one I recorded, and is anybody waiting on its join. A null ID covers "never recorded", "recorded as null", and "the record is gone or re-issued" — the last case being the one the generation exists to catch, since a recycled record's cleared successor would otherwise dispatch the new occupant's waiter.

The read is unguarded and the field is not atomic. FindLiveRecord takes no lock and reads its flags relaxed, and what this returns is a copy of a plain 16-byte TaskID that SetSuccessor may be writing on another thread at the same moment. A torn read of two 8-byte halves is possible in principle; what matters in practice is that a value read here is not ordered against Create's clearing of the same field. The pages for those two calls carry the details.
Its one shipping reader is the join-close path, on a worker thread. TaskSystem::DispatchSuccessor() calls Find on the completing task, then this, then reads the result packet's destination byte — so the whole dispatch decision is made from lock-free reads (Engine/Core/TaskSystem.cpp). That is the performance intent: closing a join must not queue behind task creation.

Examples

From Engine/Core/TaskSystem.cpp, TaskSystem::DispatchSuccessor()

const TaskID successorID = taskRegistry.GetSuccessor(finishedTask);
if (successorID.IsNull())
{
    return;
}

The common answer is null: most tasks end their join with nobody waiting, and the early return is what keeps the join path free of logging. The interesting failure is the opposite one — a successor recorded with no destination byte in the result packet — which is reported by the next few lines of that function rather than here.
