GetCapacity

member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp Records the table holds without growing - banks times bank size.

Signature

[[nodiscard]] std::size_t GetCapacity() const noexcept

Function description

Defined in Engine/Core/TaskRegistry.cpp as TaskRegistry::GetCapacity(); the body is one line. 

return bankCount.load(std::memory_order::relaxed) * recordsPerBank;

From Engine/Core/TaskRegistry.cpp

Capacity is derived rather than stored, which is why it can never disagree with the banks that actually exist: it is the published bank count times the figure that names every bank's size. Multiply by RecordSizeBytes and it is also the registry's memory footprint, which is how the registry's own test prints the price of the table.

It reports what the table holds, which is not what was asked for. Initialize rounds a request down to whole banks, an allocation failure stops the loop early, and a Grow refusal changes nothing — this is the reading that reflects all three (Engine/Core/TaskRegistry.h: "GetCapacity reports what the table really holds").
It is not a count of what is in use, and it is not a limit. Live tasks are counted by GetCount, and the ceiling that stops growth is GetMaxCapacity — a table can sit far below its ceiling and still refuse work if every record it holds is busy, which is exactly the message ReportNoRoom prints.
Both factors can change after records exist, and this reading moves with them. recordsPerBank is written by Initialize and bankCount by AllocateBank; neither is read under a lock here. In the intended lifecycle both happen before any task is created, so the number is stable exactly when it matters — as the basis of an index computation in Find.

The sizing contract as the tests hold it: the figures are written out rather than read back from the constants that produced them, because "a comparison against the constant that produced the value cannot fail" (Engine/Core/TaskRegistry.cpp). The capacity check is what pins the R22 decision, and a registry that came out at 8192 because someone rounded a request down would be caught here rather than in a lookup that fails.
