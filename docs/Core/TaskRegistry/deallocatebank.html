DeallocateBank

member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp Destroys a bank's records and returns its bytes to the same allocator.

Signature

void DeallocateBank(TBank bank) noexcept

Function description

Defined in Engine/Core/TaskRegistry.cpp as TaskRegistry::DeallocateBank(). Private, and with one caller: the destructor, once per bank it finds published. There is no shrink path, so nothing returns a bank to the allocator while the registry is in service. 

if (bank == nullptr)
{
    return;
}

for (std::size_t record = 0; record < recordsPerBank; ++record)
{
    bank[record].~Record();
}

MemoryManager::GetInstance().Deallocate(bankAllocatorID, bank, recordsPerBank * sizeof(Record));

From Engine/Core/TaskRegistry.cpp

Two halves that must stay paired: every record's lifetime is ended explicitly, because the storage came from MemoryManager::GetInstance().Allocate and not from a constructing operator, and then the bytes go back to the same allocator they came from — bankAllocatorID, not whatever is ambient now. That symmetry is why AllocateBank captured an allocator identity at Initialize instead of allocating from the current one.

The null test exists for a partially-initialised table, and it is the only safety this function has. Initialize stops its loop at the first failed bank, and the destructor walks bankCount entries — but a registry that was constructed and never initialised holds 1024 null pointers, and a stray nullptr in a walked range would otherwise reach the loop below it. What the guard does not check is whether the records in the bank were ever constructed, or how many.
Bank size is taken from today's recordsPerBank, not from what the bank was built with. Both the destructor loop and the byte count are computed from the field, which Initialize is free to overwrite. A second Initialize with a different grow-by therefore makes this function destroy the wrong number of objects and hand the allocator a size it did not give out — the concrete cost behind the header's "call this once" rule (Engine/Core/TaskRegistry.h). See ~TaskRegistry for the same hazard from the other side.
No tracked task is consulted on the way out. This function does not look at inUse, so a bank whose records are live is torn down anyway. Correctness depends entirely on the caller: the destructor runs when nothing can be creating or finding tasks any more, and the task system's close path is what makes that true before the registry is taken apart (Engine/Core/TaskSystem.cpp).

Parameters

ParameterTypeRequirement
bankTBank (Record*)A bank this registry allocated and has not yet freed; nullptr is accepted and ignored

Return value

void. No count of records destroyed, no report from the allocator, and no indication that the bank's size disagreed with GetGrowBy.

Examples

From Engine/Core/TaskRegistry.cpp, TaskRegistry::~TaskRegistry()

const std::size_t allocatedBanks = bankCount.load(std::memory_order::relaxed);
for (std::size_t bank = 0; bank < allocatedBanks; ++bank)
{
    DeallocateBank(banks[bank]);
}

Walking the published count rather than the table's full 1024 entries is what keeps this correct for a registry that grew one bank and then died — and the relaxed load is adequate because a registry being destroyed has no other thread publishing anything.
