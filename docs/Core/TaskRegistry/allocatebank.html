AllocateBank

member of hbe::TaskRegistry Engine/Core/TaskRegistry.cpp Takes one bank, constructs its records, and links them into the free chain.

Signature

TBank AllocateBank() noexcept

Function description

Defined in Engine/Core/TaskRegistry.cpp as TaskRegistry::AllocateBank(). Private, and called from exactly two places: Initialize's loop and Grow — which is how the class guarantees that every bank is taken either before any task exists or between frames on the owner.

Its body is a sequence with no step that can be reordered:

StepWhat it doesWhy the order matters
1Refuse if bankIndex >= MaxBanksThe bank table is a fixed array of 1024 pointers; past it the request is reported by ReportRefusedGrowth rather than writing outside the table
2Refuse if the ceiling would be crossedChecked before allocating, so a capped registry never takes memory it will have to give back; the ceiling is read without a lock, which is why SetMaxCapacity is a build-time call
3Allocate recordsPerBank * sizeof(Record) from bankAllocatorIDExact-sized, one bank at a time, from the allocator captured at Initialize — a pool bank would round a table of this size up by more than the table itself
4Placement-construct every recordnew (&records[record]) Record(): a record's task holds an atomic counter, so records are constructed in place and never moved
5Publish: banks[bankIndex] = records; then bankCount.store(bankIndex + 1, release)The release store is what makes the lock-free Find correct: a reader that acquires a count covering this bank is guaranteed to see its constructed records
6Thread the bank's records into the free chain and move freeRecordHead to the bank's first recordThe chain is walked backwards so records issue in ascending index order, and the new bank is handed out before the older free records that were already chained
Failure is reported and changes nothing at all. Every refusal path returns nullptr without touching banks, bankCount or freeRecordHead, and the two failure reports say different things: a ceiling or bank-limit refusal from ReportRefusedGrowth, and an allocator refusal naming the byte count — "The table keeps the capacity it has." (Engine/Core/TaskRegistry.cpp). This is what lets Grow answer false honestly and Initialize stop a loop and keep what it got.
One bank is 1 MiB at the engine's defaults, and it is a single allocation. That figure, not the record count, is what a caller is really asking for; and the publication step means the megabyte is invisible to a Find until it is fully built. The cost of the alternative — a pool bank sized by a round-number rule — is recorded in the class note as costing more than the table itself.
It never frees anything, so a bank is only ever reclaimed by the destructor. There is no shrink path on this class, and Initialize called twice neither frees nor reuses the earlier banks properly — the header states the leak plainly (Engine/Core/TaskRegistry.h). Growth is monotonic for the life of the registry.

Parameters

None. Bank size comes from recordsPerBank and the allocator from bankAllocatorID, both set by Initialize.

Return value

TypeWhat you get
TBank (Record*)The bank's first record, already published and already in the free chain; nullptr on any refusal, with a log line already emitted

Examples

From Engine/Core/TaskRegistry.cpp, TaskRegistry::Grow()

std::scoped_lock<std::mutex> lock(registryLock);
return AllocateBank() != nullptr;

The only caller that looks at the pointer, and it looks only at whether it is null. The lock is what makes steps 5 and 6 safe against a concurrent Create or Release mutating the same free chain (Engine/Core/TaskRegistry.cpp).
