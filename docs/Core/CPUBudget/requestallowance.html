The cross-thread route to an allowance: one atomic store, no lock, no queue, callable from whatever thread a config reload or a frame-boundary decision happens on. The owner applies it to itself on its next pass with ApplyRequestedAllowance, which is the same hand-off the accounting window uses — the pass signals, the stream acts on itself.

One slot, latest wins, and that is a rule about what an allowance is. "The allowance is a state, not an event, and a stream that asked for 5ms and then for 1ms before its next pass should end up at 1ms, not bill itself for both" (Engine/Core/CPUBudget.h). The test A requested allowance is applied once by the owner and the latest request wins pins both halves, including that an unapplied request is not observable afterwards (Engine/Core/CPUBudget.cpp). A caller that needs to observe every change must poll GetAllowance rather than count requests.
A request of exactly -1 nanosecond is indistinguishable from "no request pending" and is silently dropped. The pending slot's empty marker is PendingAllowanceNone, which is -1, and the duration is stored by casting to nanoseconds — so RequestAllowance of a duration that casts to -1 stores the marker itself, and ApplyRequestedAllowance will report nothing pending. No caller states a negative allowance, so nothing in the repository reaches it; it is the cost of an in-band sentinel, recorded so that a future caller that derives a duration from arithmetic does not stumble on it unknowingly.
The change is not instantaneous, and sub-nanosecond fractions do not survive the trip. A request made now lands on the stream's next pass — including the drain policy's share, which is reconfigured from the applied figure by the same code. Anything finer than a nanosecond is truncated by the cast above, so a request written as std::chrono::duration<double>(0.0000000001) arrives as zero, i.e. unlimited.
