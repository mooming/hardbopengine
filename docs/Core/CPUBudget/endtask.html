EndTask

member of hbe::CPUBudget Engine/Core/CPUBudget.cpp Adds the measured span; an unpaired call charges nothing rather than poisoning the budget.

From Engine/Core/CPUBudget.cpp, CPUBudget::EndTask()

The guard is the entry's substance. Measuring from a start that was never taken would charge the thread's entire life to the budget and leave a stream refusing work forever, so the pairing error loses the charge instead of poisoning the budget — "the same fail-open choice as a failed platform call in OS::GetThreadCPUTime" (Engine/Core/CPUBudget.h). The test Unmatched EndTask charges nothing pairs a call, reads the accumulation, calls again, and requires no change (Engine/Core/CPUBudget.cpp).

The charge itself is one relaxed atomic add. Relaxed is sufficient because nothing derives an ordering from it: the only writer is the owner, and a reader on another thread is satisfied with "as of the last task that thread finished" (Engine/Core/TaskStream.h).

A span is not clamped at zero, so a failed reading taken here subtracts from the accumulation. The platform clock returns zero on failure (Engine/OSAL/OSXThread.cpp, Engine/OSAL/LinuxThread.cpp, Engine/OSAL/WindowsThread.cpp), and 0 - taskStart is negative, which drives accumulatedNanos down and makes the budget more permissive than it earned. The failure the header's fail-open claim covers is a missing BeginTask; a failure of the clock is handled by neither guard. Details on BeginTask.
Nothing here re-reads the allowance or re-decides anything. The charge only becomes a refusal the next time the stream asks CanTakeWork, which is why a lane overshoots its budget by the length of the task that overshot it: the gate sits in front of acquiring, never in front of finishing (Engine/Core/TaskStream.h).

Parameters

None.

Return value

void. An unmatched call is indistinguishable from a matched one from the outside — it charges nothing and says nothing.

if (chargingBudget)
{
    budget.EndTask();

    const auto spent = budget.GetAccumulated() - chargedBefore;
    if (lane == StreamDrainPolicy::ELane::Priority)
    {
        drainPolicy.ChargePriority(spent);
    }
    else
    {

    }

The difference against chargedBefore is how one task's CPU time is attributed to a lane: the budget holds the running total, and the drain policy receives only this task's share of it. Both brackets are guarded by the same chargingBudget flag, so the pair is never split — an unmatched BeginTask would leave the span open, and the next EndTask would charge one interval spanning both tasks.
