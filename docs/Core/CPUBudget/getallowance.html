GetAllowance

member of hbe::CPUBudget Engine/Core/CPUBudget.cpp The configured allowance; zero means unlimited. Reads an unsynchronised field.

Signature

[[nodiscard]] std::chrono::duration<double> GetAllowance() const noexcept

Function description

Defined in Engine/Core/CPUBudget.cpp as CPUBudget::GetAllowance(); the body is return allowance;. The configured figure, unrounded and un-normalised, zero meaning unlimited.

It is the read of a field that has no synchronisation, which is legitimate for exactly one reader — the owning stream thread — and the reason both Configure and RequestAllowance exist as a pair rather than one call.

It answers "what did the stream ask for", not "what does the budget enforce". A pending request is invisible here until ApplyRequestedAllowance runs, so a caller on another thread reading this after a TaskStream::RequestBudget sees the old allowance — correctly, not stale.

Parameters

None.

Return value

TypeWhat you get
std::chrono::duration<double>The allowance as configured. Zero — the default — means unlimited; a negative can only have arrived through Configure, which does not clamp, and behaves as unlimited

Examples

From Engine/Core/TaskStream.cpp, TaskStream::Update()

const bool chargingBudget = budget.GetAllowance().count() > 0.0;
const auto chargedBefore = chargingBudget ? budget.GetAccumulated() : std::chrono::nanoseconds::zero();
if (chargingBudget)
{
    budget.BeginTask();
}

The two shipping uses are both on the owning thread, and this one is the gate on measurement itself: an unlimited stream skips the pair of syscalls entirely, which is why its accumulation stays at zero.

From Engine/Core/TaskStream.cpp, TaskStream::ReportGeneralQueueRefusal()

auto log = Logger::Get(name);
log.OutWarning([name = name, allowance = budget.GetAllowance()](auto& ls)
{
    ls << name.c_str() << " has spent its allowance of "
       << std::chrono::duration_cast<std::chrono::microseconds>(allowance).count()
       << " us and is leaving tasks in the general queue until the budget window advances again.";
});

The other use is a warning's text, captured once when the warning is built rather than read inside the log callback: a reader seeing this line learns the stream is not slow, it is out of allowance, and for how long it will leave tasks in the general queue.
