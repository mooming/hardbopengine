CanTakeWork

member of hbe::CPUBudget Engine/Core/CPUBudget.cpp Whether the allowance still permits acquiring another task; always true when unlimited.

From Engine/Core/CPUBudget.cpp, CPUBudget::CanTakeWork()

The first branch is the common one: an unlimited budget — which is every budget in a shipping build, since nothing configures an allowance — answers true without consulting the counter at all. When an allowance is set, the comparison is against the whole accumulated figure, so the answer flips the moment spending reaches it and does not flip back until a Reset.

This is a gate on acquiring work, never on running work already held. The rule is stated on TaskStream::MayTakeNewWork(): the gate belongs in front of draining a provider and in front of taking from the general queue, and refusing to finish work in flight "would turn a budget into a way to strand results, which is the failure this whole design is careful not to have" (Engine/Core/TaskStream.h). A task already running overshoots by its own length.
It reads an unsynchronised field, so "readable from any thread" is a claim this class does not make. Configure documents that only the owning stream thread may write allowance "because CanTakeWork reads it once per pass on that thread" (Engine/Core/CPUBudget.h), and the counter it reads is atomic while the allowance is not. Yet TaskStream::MayTakeNewWork(), which is this call forwarded unchanged, is marked @threadsafe Readable from any thread and is called from a test thread in Engine/Core/TaskSystem.cpp. The two statements cannot both hold for a budgeted stream; the reading this class supports is that the answer is advisory from any thread and only the owner may act on it.
It is consulted twice per pass on purpose, and the second reading is defended in a comment. TaskStream::Update() asks before asking a provider for work, then asserts the answer again at the provider ask, with the reasoning that "this is the owning thread, the only thread ever allowed to read that unsynchronised field" (Engine/Core/TaskStream.cpp). Asking a provider while spent is the failure the assert exists to catch: a spent stream that keeps manufacturing work it has no right to run.

The gate in front of the general queue — the one place the engine refuses work on budget grounds, and the place where a spent stream says so out loud instead of going quiet. The provider probe a little earlier applies the same rule with an Assert attached, and both are inside the queue lock on the owning thread.
