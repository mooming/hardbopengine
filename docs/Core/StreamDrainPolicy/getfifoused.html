GetFifoUsed

member of hbe::StreamDrainPolicy Engine/Core/StreamDrainPolicy.cpp CPU time the FIFO lane has spent this round; reporting only.

Signature

[[nodiscard]] std::chrono::nanoseconds GetFifoUsed() const noexcept

Function description

Defined in Engine/Core/StreamDrainPolicy.cpp as StreamDrainPolicy::GetFifoUsed(); the body is return fifoUsed;. CPU time charged to the FIFO lane in the current round — nothing else, and nothing since the last EndRound.

It is one of the reporting accessors the header exposes deliberately as const reads rather than folding into the decision: "reads of counters for reporting are exposed as separate const accessors and are only meaningful from the owning thread" (Engine/Core/StreamDrainPolicy.h).

Nothing in the repository reads it. A grep of Engine/ and Applications/ finds the declaration and the definition and no call site — not even in this class's own tests, which assert behaviour (ChooseLane, IsRoundExhausted) rather than the counters behind them. The number exists to be looked at, so the honest expectation is a diagnostic or a test that has not been written yet.

Parameters

None.

Return value

TypeWhat you get
std::chrono::nanosecondsCPU time charged to the FIFO lane this round by ChargeFifo. Zero for an unbudgeted stream, which charges nothing, and zero immediately after EndRound

Examples

Illustrative — no call site for this exists in the repository.

ls << "lane use fifo=" << drainPolicy.GetFifoUsed().count() << "ns priority="
   << drainPolicy.GetPriorityUsed().count() << "ns of "
   << std::chrono::duration_cast<std::chrono::nanoseconds>(drainPolicy.GetFifoShare()
      + drainPolicy.GetPriorityShare()).count() << "ns";

The reading this accessor was built for, and the rule that makes it valid: call it on the stream's own thread, because the field it returns is written by that thread with no synchronisation, and a report built from another thread's view of it is a race that happens to print something.
