ConfigureRate

From Engine/Core/StreamDrainPolicy.cpp, StreamDrainPolicy::ConfigureRate()

Two things happen: the weights are recorded with every zero replaced by one, and both rotation credits are reset to the new weights. The weights are used two ways — as the numerator of each lane's CPU share when an allowance is configured, and as the replenishment amount for credit in the unlimited case — so a re-rate takes effect in whichever mode the stream is in, immediately.

A zero weight is not "never serve this lane". Each zero becomes 1 independently, so ConfigureRate(0, 4) is a 1:4 rate and ConfigureRate(0, 0) is 1:1 — the fallback the test Zero weights fall back to an even split requires (Engine/Core/StreamDrainPolicy.cpp). The reason is stated in the header: a lane that can never be served should not exist, and silently configuring one would strand the tasks already queued on it. There is no supported way to disable a lane through this call.
Only the ratio is observable. Shares are normalised over the sum of the weights, so 3:1 and 300:100 behave identically — while GetFifoWeight and GetPriorityWeight still report the numbers you passed, which is what lets a caller that re-rated a shared stream restore what it found.

The stream's wrapper is where the thread rule lives, because the policy itself has none: it is plain fields written by whoever calls, and the owning stream reads them every pass. Note what the search for callers finds: no shipping code in Engine/ or Applications/ configures a rate at all, so every stream runs the default 1:1 — the only callers are tests in the #ifdef TEST_ENABLED region of Engine/Core/TaskSystem.cpp, which read both weights, set a rate, and put the originals back.
