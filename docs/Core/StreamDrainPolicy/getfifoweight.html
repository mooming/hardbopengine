GetFifoWeight

member of hbe::StreamDrainPolicy Engine/Core/StreamDrainPolicy.cpp The configured FIFO weight, not the normalised share.

Signature

[[nodiscard]] uint32_t GetFifoWeight() const noexcept

Function description

Defined in Engine/Core/StreamDrainPolicy.cpp as StreamDrainPolicy::GetFifoWeight(); the body is return fifoWeight;. The FIFO side of the rate exactly as ConfigureRate stored it — which means a zero that was passed in comes back as one, and nothing records that the substitution happened.

It exists so a borrowed stream can be handed back: the header names "the read half of a change-then-restore" as the reason (Engine/Core/StreamDrainPolicy.h), and a share (GetFifoShare) cannot be fed back into ConfigureRate, so the weight is the only restorable form of a rate.

Both weights are summed before the division, in uint32_t. The share is allowance * (fifoWeight / double(fifoWeight + priorityWeight)), and the addition happens in the wider type only after it — so a pair whose sum overflows 32 bits (for instance 0xFFFFFFFF and 1) wraps and produces a share that bears no relation to the intended ratio. No configuration in the repository comes near this; a caller that derives weights from measured load should still keep their sum inside 31 bits.
No shipping code configures a rate, so every stream runs the default 1:1. The only callers of TaskStream::ConfigureRate() in Engine/ and Applications/ sit in the #ifdef __UNIT_TEST__ region of Engine/Core/TaskSystem.cpp, which reads both weights, sets a test rate, and restores them. This accessor therefore has exactly one kind of user today: a test that borrows the base stream.

Parameters

None.

Return value

TypeWhat you get
uint32_tThe configured FIFO weight, minimum 1, default 1. Pair it with GetPriorityWeight to describe a rate — one number alone means nothing

Examples

From Engine/Core/TaskSystem.cpp, TaskSystemTest (unit-test region)

const uint32_t fifoWeightFound = baseStream.GetFifoWeight();
const uint32_t priorityWeightFound = baseStream.GetPriorityWeight();

baseStream.ConfigureRate(8, 1);

// ... drive the stream and observe which lane it serves ...

baseStream.ConfigureRate(fifoWeightFound, priorityWeightFound);

The change-then-restore the accessor is built for, and the reason both halves must be read: restoring only the lane a test experimented with would leave the other side of the ratio at whatever the test happened to leave, which is a different rate than the one found.
