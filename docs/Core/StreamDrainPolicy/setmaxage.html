SetMaxAge

member of hbe::StreamDrainPolicy Engine/Core/StreamDrainPolicy.cpp The oldest work this stream will still run; zero is unlimited.

Signature

void SetMaxAge(std::chrono::nanoseconds maxAge) noexcept

Function description

Defined in Engine/Core/StreamDrainPolicy.cpp as StreamDrainPolicy::SetMaxAge(); the body is StreamDrainPolicy::maxAge = maxAge;. One store, no validation — a negative ceiling is stored as given, and IsOverAge's first guard (maxAge.count() <= 0) then makes it mean unlimited rather than "everything is too old".

The ceiling is per stream, not global, and it is a ceiling on admission: the check runs on the worker thread that is about to execute one specific offer (Engine/Core/TaskStream.cpp), so a work item's age is judged against offerTime — when it entered this stream — rather than against its type's global age limit.

Zero is unlimited, and it is also the default. The header states that a stream with no ceiling behaves as it did before the feature existed (Engine/Core/StreamDrainPolicy.h), and the member's initialiser is std::chrono::nanoseconds maxAge{{}}. The test A stream with no max age ages nothing out, and work it cannot date is never judged calls this the guard that "decides whether the feature is off by default or merely unreadable" (Engine/Core/StreamDrainPolicy.cpp) — without it, every existing stream would start dropping tasks whose age happened to exceed a zero ceiling.
A ceiling that is shorter than one task's run time strands work. An item is judged when it is taken, so anything still running when the ceiling passes is not recalled — but its successor, or the same item re-queued unfinished, will be judged again on its next attempt. A ceiling set below the stream's typical task duration turns staleness into a permanent refusal, and the only trace is the stream's age-drop counter.

A stream forwards this without a thread assert — unlike TaskStream::ConfigureRate(), which Asserts that the caller is the owning thread. The ceiling is read on a worker thread during TryExecuteWorkItem, so a cross-thread write is a plain data race that the class does not detect; the discipline is the caller's.
