Module Index / OSAL

OSAL

namespace OS Engine/OSAL 18 headers, 35 sources — the operating-system boundary: application, window, files, threads, memory, backtrace

Module description

The OS abstraction layer is where platform difference is allowed to exist. The public interface of a class here is identical on every operating system; what differs is the implementation unit behind it, chosen at build time by PLATFORM_LINUX / PLATFORM_OSX / PLATFORM_WINDOWS. The OS namespace, not hbe, marks this as the boundary.

This is also the module the older guide described least accurately — it documented OS::IApplication and OS::IWindow interfaces that no longer exist. Everything below is read from the headers, and the platform table names the actual per-platform units.

Application (Engine/OSAL/Application.h)

Class description

The platform-independent application facade: it creates the OS application object and pumps its events. On macOS that is the NSApplication the window server requires, on Windows an HINSTANCE, on Linux whatever the display server needs — and none of that reaches a caller.

Template parameters

None — Application is not a template.

Class properties

m_platformHandle, an opaque per-platform handle, private. Note the member name: it carries the m_ prefix that docs/CodingStandards.md tells engine code not to use, which is a local inconsistency in this module rather than a rule change.

Class methods

class Application
{
public:
    Application() noexcept;
    ~Application();

    void Initialize();
    void PollEvents();
};

[[nodiscard]] std::unique_ptr<Application> CreateApplication() noexcept;

The Engine creates and owns the application when EInitLevel::Application is requested, and hands out the pointer through GetApplication() — a real application checks it for null before using it, as the example shows.

Non-member helper functions

CreateApplication() returns a std::unique_ptr, so the caller owns it; it is [[nodiscard]], so ignoring the result does not compile quietly.

Window (Engine/OSAL/Window.h)

Class description

A window on whichever toolkit the platform chose, created with a size and title, polled for events, and closed explicitly.

Template parameters

None — Window is not a template.

Class properties

Size and flags are the same everywhere; the native handle is what the #if defined(PLATFORM_*) block selects:

GetNativeHandle is the deliberate leak: it is what the renderer passes to the graphics API to attach a surface to. Every other method is portable; anything using the handle is not, which is why the renderer is where that call happens.

SourceLocation (Engine/OSAL/SourceLocation.h)

Class description

Where a call came from, captured by default arguments so the caller writes nothing. It is the OSAL's contribution to the assertion family.

Template parameters

None — SourceLocation is not a template.

Class properties

File name, function name, line number and column offset, each filled from the corresponding caller macro.

Class methods

class SourceLocation final
{
    static constexpr SourceLocation current(
        const char* fileName      = CallerFile(),
        const char* functionName  = CallerFunc(),
        uint_least32_t lineNumber = CallerLine(),
        uint_least32_t column     = CallerColumn()) noexcept;

    // accessors: file_name(), function_name(), line(), column()
};

The defaults are what make it usable: SourceLocation::current() written at a call site reports that call site, and a parameter of this type with a default can be left out of a signature entirely.

Non-member helper functions

The caller macros supply every default argument.

Intrinsic macros (Engine/OSAL/Intrinsic.h)

Class description

Compiler-facing primitives. They are macros because the operations are not callable: branch prediction hints and a breakpoint are instructions, and caller information only exists at the expansion site.

MacroPurpose
likely(x)Tell the compiler the condition is usually true — the error path goes the other way
unlikely(x)The reverse, and the one worth putting on a failure branch in a hot loop
debugBreak()Halt for the debugger
CallerFile(), CallerFunc(), CallerLine(), CallerColumn()Expansion-site identity; the four defaults of SourceLocation::current

The names are lower-case, unlike the SCREAMING_SNAKE_CASE that docs/CodingStandards.md asks macros for — these are used as function-call shapes and read as such.

Platform-specific units

Same interface, different implementation file, selected by #if defined(PLATFORM_*). This is the pattern the Renderer copies for its backends.

PlatformWindowApplicationFile handleDebugMemoryThread
macOSOSXWindow.h / .mmOSXApplication.h / .mmOSXFileHandle.cppOSXDebug.cppOSXMemory.cppOSXThread.cpp
LinuxLinuxWindow.h / .cppLinuxApplication.h / .cppLinuxFileHandle.cppLinuxDebug.cppLinuxMemory.cppLinuxThread.cpp
WindowsWin32Window.h / .cppWin32Application.h / .cppWin32Window.cppWindowsDebug.cppWindowsMemory.cppWindowsThread.cpp
One implementation unit per platform, per concern. Because both the generic and the per-platform units define some of the same functions, the build must compile exactly one of them for a given platform — the risk recorded in the repository's own review notes as an ODR hazard. If you add a platform unit, check how the source list selects it before the linker or the reader of the code finds out.
