FileHandle

Engine/OSAL/OSFileHandle.h namespace OS final the movable, non-copyable owner of a platform file descriptor — invalid by default, closes on destruction

Class description

OS::FileHandle is the handle the file-input surface travels in: one public anonymous union holding the platform's handle as raw storage, movable but not copyable, invalid by default, and closing its file when it dies. On POSIX the storage is a descriptor — the int fd view — and OS::Open's implementations write the descriptor straight into it (Engine/OSAL/LinuxInputOutput.cpp assigns outHandle.fd).

The handle owns the descriptor. The destructor closes: a valid handle's destructor calls OS::Close on itself, so a caller who opens a file and lets the handle go out of scope has still closed it. Ownership transfer is the move constructor, which steals the storage and invalidates the source; the copy constructor is deleted, so there is no second owner by accident. Engine/Resource/BufferUtil.cpp leans on both: it moves the raw storage out of a live handle, then lets the buffer's releaser rebuild a handle from the raw bytes to close the file after the mapping is released.

Implemented on Linux and macOS only. The definitions live in Engine/OSAL/LinuxFileHandle.cpp and Engine/OSAL/OSXFileHandle.cpp, each behind its PLATFORM_* guard. There is no WindowsFileHandle.cpp, and Engine/OSAL/WindowsInputOutput.cpp, the only Windows file of the IO surface, is a copyright notice with no code — a Windows build that constructs or passes a FileHandle does not link.
The two platform units reach the descriptor differently, and only one of them is honest about the union. LinuxFileHandle.cpp reads and writes the fd member directly, as OS::Open does; OSXFileHandle.cpp goes through GetHandle / SetHandle helpers in an anonymous namespace that reinterpret_cast the void* data view to int&. Both spellings alias the same four bytes, so the semantics are identical — but the OSX route is the one that would survive the union's pointer view widening, and the Linux route would not.

Non-member helpers

None. Everything that operates on a handle is a free function of OSInputOutput — Open, Close, Read, Write, Truncate, MapMemory — which is why the class itself carries no I/O method.
