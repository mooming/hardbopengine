GenerateBank

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private Append one bank out of parentID, re-sort the list, and defer the log line to the caller's frame.

Signature

void GenerateBank(size_t blockSize, size_t numberOfBlocks)

Function description

Private, defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, and called from NewBankAllocate alone — which is itself reached only from inside Allocate's locked region. Everything here happens with lock held by the calling thread.

Four effects, and the scope on the first line governs all of them. The bank's own buffer is one allocation out of parentID; the bank registers itself with MemoryManager; the vector may reallocate, taking its new storage from the same scope; and the list is re-sorted so the next request's scan still walks block sizes ascending. The bank's registration name is <name>_<blockSize>_<numberOfBlocks>, the same shape GenerateBanksByCache builds, and it is what appears in the allocation log lines. The inner AllocatorScope repeats the outer one — the second is redundant, and both name parentID.

It does not log. It records (blockSize, numberOfBlocks) into the BankGenerationLog guard that Allocate owns for the duration of the call, and that guard's destructor emits the message after the mutex is released — the fix for a Verbose line that used to be written inside the locked region, recorded in JOURNAL.md, 2026-10-05. Because the guard nests through a thread-local pointer the way AllocatorScope nests the ambient allocator, a parent allocator that grows a bank while a child is growing one records the event under whichever frame is outermost.

Re-sorting the bank list moves live pools, and that is only safe by luck. std::sort rearranges PoolAllocator objects, and their move assignment is this->~PoolAllocator() followed by a placement new of the moved-from object (Engine/Memory/PoolAllocator.cpp). A move into a slot whose bank still owns its buffer would therefore release that buffer while callers hold blocks inside it. Measured against the standard library's sort, that never happens: every move-assign lands on a slot an earlier destructive move has just emptied, and the measured release count for an out-of-order insert was zero. The review of 2026-10-05 records the result as safe by luck, not by contract, and with it a second latent consequence — a moved bank's registration record keeps dispatch functions but not a refreshed allocator pointer, so a dispatch by that bank's own id could address a different bank. Nothing in this file passes a bank id anywhere, and banks is private, which is what keeps the finding latent today.
The asserts here are the only validation a bank gets. blockSize > 0 and numberOfBlocks > 0 are Assert, live in Debug and Dev and compiled away in Release (Engine/Core/Debug.h). The bank constructor then floors and aligns the size it is given and asserts that a block can hold its free-list link (Engine/Memory/PoolAllocator.cpp), but nothing checks a bank against a limit: the instance has no maximum size, and the review's unbounded-growth finding applies to this function directly.
Under PROFILE_ENABLED it also books the new capacity, outside the manager's statistics lock. The tail of the function adds blockSize * numberOfBlocks to this instance's registration record through mmgr.GetAllocatorProxy(GetID()) with no call to AcquireStatsLock() (Engine/Memory/MemoryManager.h). This tree defines PROFILE_ENABLED as 0 and does not compile with it set, so that increment has never run here (Engine/Config/BuildConfig.h, JOURNAL.md).
