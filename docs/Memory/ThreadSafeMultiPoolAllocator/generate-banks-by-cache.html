GenerateBanksByCache

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private Build the banks a previous run saved under this name, so an allocator given only a name still boots with a bank list.

Signature

bool GenerateBanksByCache(const class MemoryManager& mmgr)

Function description

Private, defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, and called by exactly one of the two constructors — the one that takes a name alone. The brace-list constructor never consults the cache: a caller who names banks explicitly gets those banks and nothing else. This is how an allocator built with only a name acquires a bank list at all, and the return value is discarded at the call site.

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::GenerateBanksByCache()

auto nameID = name.GetID();
auto& cacheItem = mmgr.LookUpMultiPoolConfig(nameID);
if (cacheItem.uniqueName != nameID)
{
        return false;
}

auto& configs = cacheItem.configs;
for (auto& config : configs)
{
        InlineStringBuilder<1024> str;
        str << name << '_' << config.blockSize << '_' << config.numberOfBlocks;

        banks.emplace_back(str.c_str(), config.blockSize, config.numberOfBlocks);
}

return true;

The miss test is the comparison at the top, because MemoryManager::LookUpMultiPoolConfig answers with a default-constructed configuration rather than a failure (Engine/Memory/MemoryManager.cpp); the id it carries is not the one asked for. A miss builds nothing and the instance starts empty, growing on demand through NewBankAllocate. A hit builds one bank per entry, named <name>_<blockSize>_<numberOfBlocks> — the same naming GenerateBank uses — taking each bank's buffer from whichever scope is open, which at this moment in the constructor is by definition the value that gets stored as parentID.

The function takes no lock, and no other thread can observe the object yet: the pointer is not published to MemoryManager until the constructor's last statement (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp).

Where the entries come from. The cache is read by MemoryManager's own constructor via LoadMultiPoolConfigs and written by PreEngineShutdown — the save half under PROFILE_ENABLED, which this tree defines as 0 (Engine/Memory/MemoryManager.cpp, Engine/Config/BuildConfig.h) — so on a machine that has never run a profiling build there is no file, and every name misses. The entries themselves are what ReportConfiguration reported about a previous run, normalised on the way out: one ascending entry per block size, counts summed, zero totals dropped (Engine/Memory/PoolConfigUtil.cpp).
Nothing sorts the result, and nothing checks a value. The banks are emplaced in stored order and this function never calls std::sort — unlike GenerateBank, which sorts after every insertion. The ascending-by-block-size order that GetBankIndex's "not more than double the request" rule leans on is therefore inherited from the file, and the file is only normalised by the writer. On load, the ordering of a pool's entries is checked and a violation reported, but no values are validated (Engine/Memory/MultiPoolConfigCache.cpp), and the first sort this instance performs happens inside the first bank it generates for itself.

Examples

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::ThreadSafeMultiPoolAllocator()

auto& mmgr = MemoryManager::GetInstance();
GenerateBanksByCache(mmgr);

size_t capacity = 0;
for (auto& bank : banks)
{
        capacity += bank.GetCapacity();
}

The whole of the call site: whatever the cache supplied is summed into the capacity the instance registers with, so a cached allocator reports its full backing from the first moment, while a name miss registers with capacity zero and grows from there.
