GetName

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h The construction-time name, by value — also the log category, the bank-name prefix and the configuration cache key.

Signature

[[nodiscard]] auto GetName() const

Function description

Declared and defined in Engine/Memory/ThreadSafeMultiPoolAllocator.h: the body is return name;, so the deduced return type is the member's type, StaticString — a copy of the interned string handle, not a reference into the object.

name is written by the constructor's member initialiser list and assigned by nothing else: no method in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp stores to it. The value is therefore fixed for the object's life, which is why this accessor reads it without taking lock and is safe to call from any thread at any point except before construction and after destruction.

The name is load-bearing in three places besides this accessor. It is the log category — every diagnostic this allocator writes goes out under Logger::Get(name) (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp). It is the prefix of every bank's registration name, built as <name>_<blockSize>_<numberOfBlocks> by GenerateBank. And its StaticStringID is the key the configuration cache is looked up and stored under, which GenerateBanksByCache reads back at construction — so two instances given one name are one cache entry, and a name shared between unrelated allocators makes their saved configurations interchangeable.

The one instance the engine shares between threads is named for its owner, not for itself. Logger builds its allocator as inputAlloc("LoggerInputPool") (Engine/Log/Logger.cpp), so every line this class writes about the logger's pool is filed under LoggerInputPool, not under Logger.

const auto logName = allocator->GetName();
auto log = Logger::Get(logName);
log.Out(ELogLevel::Verbose, [this, logName](auto& ls)
{ ls << "The bank[" << logName << '_' << blockSize << '_' << numberOfBlocks << "] has been generated. "; });

The deferred bank-generation message: it reads the name of the allocator that grew a bank after that allocator's mutex has been released, so the log line can allocate without re-locking it. The same value is what a caller sees from a log filter or from the usage report under PrintUsage.
