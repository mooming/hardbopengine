ThreadSafeMultiPoolAllocator

Engine/Memory/ThreadSafeMultiPoolAllocator.h namespace hbe final Several block-size classes of pool allocator behind one non-recursive mutex: safe to share between threads, never callable from inside itself.

Class description

class ThreadSafeMultiPoolAllocator final at Engine/Memory/ThreadSafeMultiPoolAllocator.h holds banks: one PoolAllocator per block-size class, kept in ascending block-size order, plus one std::mutex that guards every operation on that list. It is the synchronised twin of MultiPoolAllocator — same idea, same bank list, one added lock — and it registers itself with MemoryManager as a single allocator whose proxy dispatch calls back into Allocate and Deallocate.

A request is answered by GetBankIndex, which scans the banks for the first one whose block size fits, whose block size is not more than double the request, and which still has a free block. If no bank qualifies, Allocate calls NewBankAllocate, which adds a bank sized from bankSize — so the bank set grows under load and never shrinks except in the destructor.

A bank's backing buffer is one allocation of blockSize * numberOfBlocks obtained from parentID, the allocator recorded by MemoryManager::GetCurrentAllocatorID() while the object was under construction, and the destructor opens AllocatorScope(parentID) as its first statement so the release goes back the same way regardless of who destroys the object.

Thread-safe, and not reentrant. lock is a plain std::mutex, so a second acquisition by the thread that already holds it never returns. Nothing inside this class re-enters it today — every diagnostic sits outside the locked regions: Deallocate records a foreignPointer flag under the lock and logs after the scope closes, and GenerateBank records the new bank into a guard owned by Allocate's frame instead of logging, so the message is emitted once the mutex is released (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp). That buys one specific freedom: a Logger call made while this allocator is the ambient scope cannot re-lock this mutex. It does not make the class callable from inside itself — Allocate and Deallocate must never be reached from a callback that runs inside one of this instance's own calls.
One instance is live in the engine, and the logger owns it. Logger declares a ThreadSafeMultiPoolAllocator inputAlloc member (Engine/Log/Logger.h), constructs it as inputAlloc("LoggerInputPool") and opens AllocatorScope inputAllocScope(inputAlloc) around the log input buffer (Engine/Log/Logger.cpp). The class's own diagnostics go through Logger::Get(name), which is why the deferred-log rule above is a correctness requirement here and not a style preference. Everything else in Engine/ reaches this class only through the test suite.
The lock is the measured cost, and its replacement is an open decision. The engine's benchmark of this class found the shared instance scaling badly (one thread to eight threads loses most of the theoretical throughput, and a private pool per thread beats the shared instance by a wide margin) while cross-thread block returns cost almost nothing — see Thread-safe multi-pool locking, which carries the candidate designs and their caveats. Nothing about that decision changes the contract below: one non-recursive mutex, held across bank selection, block take, block return and bank creation.

The deferred-log guard is file-scope implementation, not API. BankGenerationLog and the thread-local activeBankGenerationLog pointer are declared in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp: the guard nests through that pointer the way AllocatorScope nests the ambient allocator id, so a parent allocator generating a bank inside a child's bank generation logs under its own category. It is implementation — no header exposes it — and its locking protocol belongs to the locking design document.

ThreadSafeMultiPoolAllocatorTest The header declares this test collection under #ifdef __TEST__ with one override, Prepare(), defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp and registered by Engine/Test/UnitTestCollection.cpp. Test-only code is documented on the page that owns the header rather than as a page of its own, so the testlets themselves — the contention benchmark and the bank ownership cases — are the Test module's subject, not this reference's
Reentrancy beyond the guard that exists today What these pages prove is the absence of a re-entry inside the locked regions as the source is written. What nothing proves, and nothing states, is what happens if the parent allocator reached from GenerateBank ends up calling back into this instance: the engine declares no lock-ordering rule and keeps no owner-thread record, so a cycle through a parent chain is neither prevented nor detected. Treat "never reach this instance's Allocate from inside one of its own calls" as a caller duty
Lock ordering against MemoryManager The nesting that does exist is one-directional in the paths these pages name: this mutex is held while a bank is constructed and registered, and RegisterAllocator takes MemoryManager's own statistics mutex when PROFILE_ENABLED is set (Engine/Memory/MemoryManager.cpp). Whether the reverse order exists anywhere in the engine is not documented and was not enumerated — a named omission, not a proven safety
Destruction against concurrent callers The destructor takes the lock but does not refuse, wait for, or detect a thread that is inside Allocate. Nothing in the class records who is using it, so the "no caller remains" precondition is unenforced and unverifiable from these pages
Review findings still open Four defects were fixed on 2026-10-05 and are described where they belong (ReportConfiguration, the destructor, Deallocate, PrintUsage). The rest of that review stands as behaviour, and these pages describe it as the contract it is rather than as intended design: no alignment parameter, so an over-aligned type is silently under-aligned; out of memory asserts instead of returning null; unbounded bank growth against MaxNumAllocators with a registration failure caught by no assert; an unvalidated initializer list that can hand a zero block count to PoolAllocator; a bank list whose moves leave a registration record naming a stale allocator. The record is JOURNAL.md, 2026-10-05, and the module page is the allocator catalogue
Every PROFILE_ENABLED path PrintUsage and ReportConfiguration compile away: Engine/Config/BuildConfig.h defines PROFILE_ENABLED as 0, and a tree with it set to 1 does not currently build, so no profiling-only line on these pages has been executed. The prose describes the source as written
