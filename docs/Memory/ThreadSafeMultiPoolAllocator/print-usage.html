Three things follow from those lines, and all three are what a caller of a reporting function needs. The scope opened on the first statement is MemoryManager::SystemAllocatorID — so the std::map nodes, the HVector growth and the StringBuilder at the end allocate from the system allocator and never from this instance. That is what makes it legal to call PrintUsage while this allocator is the ambient scope, including from a thread already deep in this instance's own bookkeeping. The map is filled inside the locked region but under that system scope, so it cannot re-enter this mutex. And every allocation-capable log call sits outside the locked region: one header line before it, one line per bank and the summary after it.

What it reports, under the category this instance is named: one [blockSize] Memory = usage / capacity, Max Usage = maxUsage line per bank, where the peak is GetUsedBlocksMax() * GetBlockSize(), and one final Opt. Args: <name> { {blockSize, peakBlocks}, ... } line holding the per-block-size peaks summed across banks — the exact {blockSize, numberOfBlocks} brace shape the second constructor takes. Banks whose peak is zero are left out of that sum.

Today the guard means the report, and the test that guards it, cannot run. The suite case Print Usage Under Its Own Allocator Scope exists precisely to prove the scope redirect above — and it cannot fail in any configuration this tree builds, because the body it exercises is compiled out and a tree with PROFILE_ENABLED set to 1 does not currently compile (JOURNAL.md, 2026-10-05). Everything on this page describes the source as written, not a measured run.
It reports; it does not save. The configuration the next boot reads is written by ReportConfiguration, which this function does not call. The Opt. Args line and that function's report are two renderings of the same summed peak, produced independently.
