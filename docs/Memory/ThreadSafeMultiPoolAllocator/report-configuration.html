ReportConfiguration

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private PROFILE_ENABLED only Feed the summed per-block-size peak into the configuration cache, asserting the reported total equals it.

Signature

#if PROFILE_ENABLED
	void ReportConfiguration()

Function description

Both halves exist only in a profiling build: the declaration sits between #if PROFILE_ENABLED and #endif in Engine/Memory/ThreadSafeMultiPoolAllocator.h — which is why the Signature block above carries those guard lines as printed — and so does the definition in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp. It cannot be compiled outside PROFILE_ENABLED even in principle: the peak it reports, PoolAllocator::GetUsedBlocksMax(), is itself a PROFILE_ENABLED member (Engine/Memory/PoolAllocator.h).

It is private and has one caller: the destructor, which runs it while the banks are still there and outside the lock, so this function is free to take the lock itself. What it produces is the configuration the next boot will boot from.

The shape of that lambda is the fix, not an accident. The accumulate must be the else branch of the not-found test: configs.reserve(banks.size()) above it means a reallocation never moves the elements, so an entry introduced by emplace_back is constructed at the very address the earlier found iterator referred to, and an unconditional add afterwards counts that bank's peak twice. The measured failure, recorded in JOURNAL.md, 2026-10-05: a true peak of 15 blocks was cached as 25, and every block size a run introduced was over-sized by one bank's peak. The assert is the guard the fix left behind, and it is live in Debug and Dev only — Assert is compiled away in Release (Engine/Core/Debug.h).

After the assert, the vector goes to MemoryManager::ReportMultiPoolConfigutation — spelled that way in MemoryManager — keyed on this instance's name as a StaticStringID. That is the entry GenerateBanksByCache looks up on the next construction. The file itself is written by MemoryManager::PreEngineShutdown (Engine/Memory/MemoryManager.cpp), also under PROFILE_ENABLED, and the writer normalises what it stores: one entry per block size, peaks summed and sorted ascending, a block size whose total is zero dropped (Engine/Memory/PoolConfigUtil.cpp, PoolConfigUtil::Normalize).

What it reports, and what that number means. One PoolConfig per distinct block size, counting GetUsedBlocksMax() — the peak block count of each bank, summed across banks of the same size — including banks that never went above zero. It is a peak, not a live count, and it is per block size rather than per bank, so a configuration that boots from it reproduces the high-water mark, not the shape of the bank list that produced it.
Nothing here has run. A tree with PROFILE_ENABLED set to 1 does not compile today — the breakage is in unrelated files, and every PROFILE_ENABLED path in the Memory module is therefore unverified (JOURNAL.md, 2026-10-05). The figures above come from a standalone model of this exact lambda, not from this binary.

Parameters

None.

Return value

void. The report is handed to MemoryManager; nothing comes back to the caller.
