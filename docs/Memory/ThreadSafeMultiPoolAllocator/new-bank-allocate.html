NewBankAllocate

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private The growth path: add one bank, then take a block from it — entered from Allocate with the mutex already held.

Signature

#endif

Function description

Private, defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, and reached from exactly one place: the two return NewBankAllocate(requested); statements in Allocate, which sit inside that function's std::lock_guard scope. It therefore runs with lock already held by the same thread, and must never be called from anywhere else — the mutex is not recursive, so a caller outside that region would have to release the lock and re-decide the bank to do it safely.

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::NewBankAllocate()

auto& engine = Engine::Get();
auto& statistics = engine.GetStatistics();
statistics.IncFallbackAllocCount();

auto blockSize = CalculateBlockSize(size);
auto numBlocks = CalculateNumberOfBlocks(bankSize, blockSize);

GenerateBank(blockSize, numBlocks);
auto index = GetBankIndex(size);
if (unlikely(index >= banks.size()))
{
        FatalAssert(false);

        return nullptr;
}

So one growth event is: one bank, sized by CalculateBlockSize and CalculateNumberOfBlocks, built by GenerateBank out of parentID, then one block taken from it. The re-scan of GetBankIndex afterwards is the reason the new bank has to be findable by size alone — it is, because a fresh bank is entirely free and its block size is at least the request.

Growth for a size class that already exists but is exhausted produces a second bank of that same block size: GetBankIndex skips banks with no free block, so an empty {64} bank sends a 64-byte request here, and the new bank lands on the same block size. It is a full bank, though — block sizes are chosen from the request while block counts are chosen from bankSize, so a second {64} bank under the default one-megabyte unit holds 16,384 blocks rather than the sixteen the caller asked to replace. The re-sort in GenerateBank orders equal sizes by most free blocks first, so the freshest bank of a class is the one served next.

The failure path ends the process, in every configuration. FatalAssert(false) is not a Debug construct — Engine/Core/Debug.h defines it outside the release guard, and it flushes the logs, breaks and calls std::abort(). The return nullptr; beneath it is unreachable in any build that reaches it. This is the review finding of 2026-10-05 recorded as an open robustness item: an allocator that cannot grow gives a caller no branch to take (JOURNAL.md).
Growth is visible as fallback allocations, and it reaches the engine. The first three statements ask Engine::Get() for the SystemStatistics object and increment its fallback counter (Engine/Core/SystemStatistics.h) — so a burst of bank creation is readable as a rise in fallback allocations, and a Memory module object calls into Engine/ while holding this class's mutex. It is a counter, not a log call — fallbackAllocCount.fetch_add(1, std::memory_order_relaxed) — which is what keeps it out of the reentrancy problem described on Deallocate.

Examples

Illustrative — this function is private and has no call site other than Allocate, which shows the call on its own page.

What a caller causes rather than calls: an allocator built as ThreadSafeMultiPoolAllocator shared("Growth", {{16, 16}}) — the shape the suite builds everywhere (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp) — serves sixteen 16-byte blocks from its one bank, and the seventeenth request takes this path: one more bank of the same block size, 16,384 blocks of memory taken from parentID, under the mutex the request already held.
