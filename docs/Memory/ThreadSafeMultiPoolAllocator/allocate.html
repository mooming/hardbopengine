Allocate

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h One block from a bank that fits, grown on the spot if none does; nullptr only for a zero-size request.

Signature

void* Allocate(size_t size)

Function description

Defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp. A zero-size request returns nullptr immediately, without taking the lock. Everything else acquires lock — one non-recursive std::mutex — and stays inside it for the whole decision:

Two facts sit in those lines. The two return NewBankAllocate(requested); statements are inside the std::lock_guard scope, so the growth path runs with the mutex held; and BankGenerationLog is constructed before the lock is taken, which is what lets the bank-creation message be emitted after the lock is released instead of inside it — see GenerateBank.

The bank is chosen by GetBankIndex, whose answer depends on which banks still hold a free block — so the bank a request lands in is not a function of its size alone, and two identical requests need not land in the same bank. Both "no bank fits" and "the fitting bank is empty" leave the locked region the same way: through NewBankAllocate, which builds a bank while this call still holds the mutex.

What comes back is one block of the bank that served it: at least size bytes, at least minBlock, and aligned to Config::DefaultAlign — 16 (Engine/Config/EngineConfig.h) because PoolAllocator rounds every block size up to that alignment (Engine/Memory/PoolAllocator.cpp). Under PROFILE_ENABLED the call reports the block to MemoryManager after the lock is released; in this tree that macro is 0 (Engine/Config/BuildConfig.h), so the whole call is the locked region plus the return.

Alignment is not a parameter, and out of memory is not a return value. There is no overload taking an alignment, so a type whose alignof exceeds 16 is served a block that is merely 16-aligned — silently under-aligned, and the review of 2026-10-05 records it as an open interface gap rather than intended design. On the failure side, the only nullptr this function returns is the zero-size one: a bank that cannot be created ends in FatalAssert(false) inside NewBankAllocate, and PoolAllocator's constructor never tests the pointer it takes for its bank buffer (Engine/Memory/PoolAllocator.cpp). A caller cannot branch on exhaustion here.
Growth happens inside this critical section, and it is what the lock costs. The bank-creation path allocates the bank's buffer from parentID, appends to banks — which may reallocate the vector — and re-sorts the list, all under the mutex. The measurement recorded in the locking design document put a single allocation's worst-one-percent latency at 27,916 ns and its worst call at 189,542 ns at eight threads while another thread grew a bank, against a typical 42 ns. Bank creation also counts itself through Engine::Get().GetStatistics().IncFallbackAllocCount(), so a growth spike is visible in the statistics as fallback allocations.
The pool's own fallback cannot be reached from here. PoolAllocator::Allocate hands a request larger than its block size to MemoryManager::FallbackAllocate (Engine/Memory/PoolAllocator.cpp), but every bank this function asks is one whose block size is at least size — GetBankIndex skips smaller banks and CalculateBlockSize rounds a new one up — so that branch is not a path this class can put a block on.

Return value

TypeWhat you get
