~ThreadSafeMultiPoolAllocator

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h Releases every bank through the allocator recorded at construction, under the lock, then gives the registration id back.

Signature

~ThreadSafeMultiPoolAllocator()

Function description

Defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp. It states where the release goes before it does anything else:

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::~ThreadSafeMultiPoolAllocator()

AllocatorScope scope(parentID);

auto& mmgr = MemoryManager::GetInstance();

Every bank's backing buffer was obtained from parentID and is returned to it, so the ambient scope at the destruction site is irrelevant: an instance may be destroyed under any scope, including its own. That redirect is also redundant by the time it matters — PoolAllocator's own destructor releases through the parent it recorded (Engine/Memory/PoolAllocator.cpp) — but it is what makes the guarantee not depend on that.

Then, under one std::lock_guard on lock, it clears the bank list. Each bank's destructor releases its buffer through its recorded parent and deregisters its own registration id; the MEMORY_VERIFICATION_ENABLED block above the clear, which would stamp every bank's thread id with the current thread, is compiled out (Engine/Config/BuildConfig.h defines it as 0). The lock is released before the final mmgr.DeregisterAllocator(GetID()), and the id is never reset: GetID keeps answering with the id that was just returned to the engine.

It does not stop, wait for, or notice a thread still inside the class. The precondition is that no caller remains; nothing enforces it. Taking the lock proves only that no other thread is in a critical section at that instant — a thread can be about to enter Allocate, and after the final deregistration the bank list is being destroyed under it. Nothing in the class records who is using it, so this is a caller duty and a named omission rather than a check that exists.
Two ways this teardown can outlive its own guarantees. First, the vector's own storage: banks is a member, so it is destroyed after the destructor body ends and therefore after scope is gone — its release obeys whatever scope the destruction site holds, not parentID. Second, the id: DeregisterAllocator pushes the registration slot back onto the pool RegisterAllocator pops from (Engine/Memory/MemoryManager.cpp), so the number GetID still reports can be handed to a later allocator.
The locked region reaches a logging function, and one build switch is what keeps it silent. banks.clear() runs ~PoolAllocator, which calls MemoryManager::Deallocate and MemoryManager::DeregisterAllocator — and the latter calls Log(ELogLevel::Info, ...) on every success (Engine/Memory/MemoryManager.cpp). That reaches the logger only through MemoryManager::Log, which emits and allocates nothing unless MEMORY_LOGGING_ENABLED is set, and Engine/Config/BuildConfig.h defines it as 0. Under that switch the bank teardown would allocate from whatever pool a logger call allocates from — and for the one instance the engine owns, that pool is this very object (Engine/Log/Logger.h), which is the self-deadlock the fixed diagnostics describe under Deallocate.
Blocks that were never returned are not mentioned. The leak report on a deregistration lives behind PROFILE_ENABLED, which this tree defines as 0 and cannot currently compile, and nothing in this destructor inspects the banks' free-block counts. Dropping blocks and destroying the allocator is silent today.

Parameters

None.

Return value

A destructor has no return value. Its observable effect is that the bank buffers are gone, the registration id is available again, and no allocation may be made through this object afterwards.

Examples

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp

ThreadSafeMultiPoolAllocator parent("TC4 Pool Parent", {{1024, 16}});
ThreadSafeMultiPoolAllocator unrelated("TC4 Pool Unrelated", {{1024, 16}});
bool allocated = false;
{
        AllocatorScope parentScope(parent);
        std::optional<PoolAllocator> pool;
        pool.emplace("TC4 Pool Owner", 64, 8);
        allocated = pool->Allocate(32) != nullptr;
        {
                AllocatorScope unrelatedScope(unrelated);
                pool.reset();
        }
}

Both instances are destroyed at the closing brace of the testlet body — one of them while a scope is open on the other, which is the case the AllocatorScope(parentID) line exists to make irrelevant. The suite names this case Pool Buffer Returns To Its Recorded Parent.

The production instance is destroyed as a member: Logger declares ThreadSafeMultiPoolAllocator inputAlloc (Engine/Log/Logger.h), so its teardown runs when the logger is torn down, under whatever scope that happens under.
