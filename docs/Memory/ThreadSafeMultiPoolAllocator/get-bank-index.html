GetBankIndex

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private 2 overloads Which bank serves a size, and which bank owns an address — both scan every bank, and both answer one-past-the-end for none.

Signature

[[nodiscard]] size_t GetBankIndex(size_t nBytes) const

[[nodiscard]] size_t GetBankIndex(void* ptr) const

Function description

Two private helpers, both defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, both reading banks with no synchronisation of their own — every caller (Allocate, Deallocate, NewBankAllocate) holds lock across the call. Both scan every bank, and both answer banks.size() for "none of them" — an index one past the end, which is exactly why their callers test index >= banks.size().

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::GetBankIndex(size_t) const

nBytes = std::max(minBlock, nBytes);
const auto doubleSize = nBytes * 2;

const auto len = banks.size();
for (size_t i = 0; i < len; ++i)
{
        auto& bank = banks[i];
        if (nBytes > bank.GetBlockSize())
        {
                continue;
        }

        if (bank.GetAvailableBlocks() <= 0)
        {
                continue;
        }

        if (bank.GetBlockSize() > doubleSize)
        {
                return len;
        }

        return i;
}

The size form answers "which bank should serve a request of nBytes", and three rules decide it: the request is floored at minBlock; a bank is skipped if its block is smaller or if it has no free block; and a bank whose block is more than double the request is refused outright — a 16-byte request will not take a 64-byte block, and the answer is "build a bank" rather than "keep looking".

The answer depends on what is free right now, not on size alone. A bank with no free block is skipped, so the same request size can land in a different bank on two consecutive calls, and a bank that is full silently shifts load to the next size class or to a brand-new bank. Nothing records which bank served a pointer, which is why the pointer form below has to scan. The review of 2026-10-05 named this as the thing any locking redesign must remove first — "make size to bank a pure function" (JOURNAL.md) — and it is also why a free path must scan by address.
The double-size refusal stops the scan instead of continuing it. return len on a bank that is too big assumes the list is ascending in block size, so a suitable smaller bank sitting behind a large one would never be examined. GenerateBank sorts after every insertion and the brace-list constructor sorts before its first one, so the assumption holds — but the banks this instance is born with come from GenerateBanksByCache in stored order, unsorted by this class, so a configuration file that is not ascending can make the refusal wrong on the first request.

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::GetBankIndex(void*) const

size_t index = 0;

for (auto& bank : banks)
{
        if (bank.IsMine(ptr))
        {
                return index;
        }

        ++index;
}

The pointer form asks each bank in turn IsMine(ptr), which is a range test on the bank's buffer — buffer <= ptr and the offset below blockSize * numberOfBlocks (Engine/Memory/PoolAllocator.cpp). Two consequences follow from the test as written: an address anywhere inside a bank counts as owned, including the middle of a live block, and a bank that is empty still owns its buffer, so a freed bank's address range is only unreachable once the banks are destroyed.

Bank order changes when a bank is added, and the banks move destructively. Every GenerateBank re-sorts the list, and PoolAllocator's move assignment is this->~PoolAllocator() followed by a placement new (Engine/Memory/PoolAllocator.cpp) — a bank moved into a slot that still owns a buffer would release a live bank. Measured against the standard library's sort, that never happens, because a move-assign always targets the slot a previous destructive move has just emptied; the review recorded the result as "safe by luck, not by contract" (JOURNAL.md, 2026-10-05). The indices these two functions return are positions in that shifting list, so they are valid for one locked operation only, never to be cached.
