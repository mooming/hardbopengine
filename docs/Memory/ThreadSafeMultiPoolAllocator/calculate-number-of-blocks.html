CalculateNumberOfBlocks

member of hbe::ThreadSafeMultiPoolAllocator Engine/Memory/ThreadSafeMultiPoolAllocator.h private static Blocks per new bank: bankSize divided by blockSize, floored at sixteen, or at one for a block above a megabyte.

Signature

static size_t CalculateNumberOfBlocks(size_t bankSize, size_t blockSize)

Function description

Private and static, defined in Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, called from NewBankAllocate alone. Both inputs are arguments and no member is read, so the function touches neither bankSize nor minBlock despite sharing their names — the parameter shadows nothing, and the caller passes the members in.

From Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::CalculateNumberOfBlocks()

size_t numberOfBlocks = (bankSize + blockSize - 1) / blockSize;

constexpr size_t megaBytes = 1024 * 1024;
if (blockSize < megaBytes)
{
        numberOfBlocks = std::max(MinNumberOfBlocks, numberOfBlocks);
}
else
{
        numberOfBlocks = std::max(static_cast<size_t>(1), numberOfBlocks);
}

The bank is sized to hold bankSize worth of blocks, with a floor: sixteen blocks for any class smaller than a megabyte, one block for anything bigger. The floor is the engine's statement that a bank worth creating at all should hold a useful number of small blocks, and the one-block branch is what stops a block larger than a megabyte from producing an empty bank.

bankSize is an aim, not a ceiling. The table's last two rows are the consequence a caller can observe: the sixteen-block floor can multiply the backing memory above the unit, and any block class at or above the unit yields a one-block bank whose backing is the block size itself. A request larger than one megabyte therefore reserves a whole bank of that size the first time it appears (CalculateBlockSize sets the class, this function sets the count) — which is the growth cost described on Allocate, paid inside the mutex.
Unbounded growth is the design, not a bug to be handled. Each call adds one bank's worth to the instance and nothing ever takes it back before the destructor. The engine's ceiling is elsewhere: banks register individually, and MaxNumAllocators caps registrations at 256 (Engine/Memory/AllocatorID.h), so an allocator driven through enough size classes and repeats eventually exhausts the engine's registration table rather than this class. The review of 2026-10-05 records that as an open robustness item (JOURNAL.md).
