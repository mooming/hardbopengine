Serialize

member of hbe::MultiPoolConfigCache Engine/Memory/MultiPoolConfigCache.h write every record to a buffer - and normalise the cache on the way, because writing rewrites what is written

Signature

size_t Serialize(Buffer& outBuffer)

Function description

Writes the whole cache into outBuffer through a BufferOutputStream, in this exact order: the class-name tag from GetClassName, the version number from GetVersion, the number of allocator records, then per record the allocator's name as text, the number of pool configurations, and per configuration the block size and the block count — two size_t values each, with no padding, no per-record length and no checksum.

Before it writes anything it calls Normalize, so the bytes that leave are the sorted, de-duplicated, emptied-records-removed view of data — and data itself is left in that shape afterwards. This is why the cache count written is smaller than the number of reports the run made: one allocator that reported five times leaves one record whose per-size counts are the largest seen (MergeMax).

Two failure points, both logged through Logger under a name derived from __PRETTY_FUNCTION__ and both answered the same way: after the header (tag, version, count) and after each record's configurations, bos.HasError() is tested and the function returns 0. On success it returns bos.GetCursor() — the number of bytes written.

The one caller writes the file twice. MemoryManager::SaveMultiPoolConfigs first serialises into a dummy buffer purely to learn the size, then opens the real file with that size and serialises again — so Normalize runs twice and the second pass sees a list it already compacted. If the second call returns anything other than the measured size the caller logs a failure and leaves the file as it is; that log line reads "Failed to deserialize the file", which is the load path's wording, so a write failure is reported with a read message.

A zero return is indistinguishable from an empty cache. An empty data after normalisation still writes a header and returns a non-zero cursor, so in practice 0 means a stream error — but nothing in the signature says so, and the caller compares the return against the size it measured rather than against an error sentinel. The buffer is sized from the first pass, so a second pass that produced more bytes than the first would be reported as a failure rather than truncating the file.

Parameters

Return value

Examples

The per-bank payload is two integers and nothing else:

bos << config.blockSize;
bos << config.numberOfBlocks;

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Serialize

Those two size_t values are the whole of what survives a restart: an allocator's bank is rebuilt from them by MultiPoolAllocator::GenerateBanksByCache, which names each bank <allocator>_<blockSize>_<numberOfBlocks>. Their source is ReportConfiguration, which reads them off the live banks as the block size and the peak block usage. The reader that pairs with this block is Deserialize.
