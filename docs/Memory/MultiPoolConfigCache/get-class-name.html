GetClassName

member of hbe::MultiPoolConfigCache Engine/Memory/MultiPoolConfigCache.h static the file's type tag, derived from the compiler's own name for this member and cached once

Signature

static StaticString GetClassName()

Function description

A static member of MultiPoolConfigCache, defined in Engine/Memory/MultiPoolConfigCache.cpp. It builds the class's name from __PRETTY_FUNCTION__ through StringUtil::ToCompactClassName, stores it in a function-local static StaticString, and returns a copy of that. The first call pays for the formatting and the string interning; every later call returns the same interned string.

It exists to be a file format's magic value. Both users are in this class:

  • Serialize writes the string as the first field of the buffer, before the version number and before the record count
  • Deserialize reads the first field and compares it, refusing the whole file with an Error that prints both the read name and the expected one

It is a compiler-generated string, so it is not stable under renaming. Nothing in the source fixes its value: it is whatever ToCompactClassName makes of this member's __PRETTY_FUNCTION__. Renaming the class, moving it to another namespace, or changing the compaction helper changes the tag, and a tag change invalidates every existing .multiPoolConfig.dat file — they fail the name check and are ignored rather than upgraded. That is the intended behaviour of a type tag; it is worth knowing because the only symptom is a log line and a run that provisions itself the slow way.

Nothing checks the name for emptiness, and the comparison is case-sensitive string equality. The tag carries no length prefix or checksum beyond what BufferOutputStream does for a const char*, so a file whose tag is corrupted into another plausible name is rejected only because it will not equal this string. The MemoryManager log helpers use the sibling helper StringUtil::ToCompactMethodName for the same purpose on function names, which is why the error lines a load produces name functions rather than the file.

Examples

On the write side the tag is the first thing into the buffer:

bos << classNameStr;

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Serialize

className there is the result of this call, and classNameStr its c_str(). On the read side the comparison is className != GetClassName(), which is why the tag must round-trip exactly — see Deserialize for what a mismatch costs.
