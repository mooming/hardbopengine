Deserialize

member of hbe::MultiPoolConfigCache Engine/Memory/MultiPoolConfigCache.h read a cache file back, refusing the whole thing on a tag or version mismatch and appending whatever a truncation leaves

Signature

bool Deserialize(const Buffer& buffer)

Function description

Reads a buffer written by Serialize back into data, through a BufferInputStream, field for field and in the same order: class-name tag, version, allocator-record count, then per record a name, a configuration count and that many pairs of block size and block count. Each record becomes one MultiPoolAllocatorConfig, constructed in place from the name interned through GetID() and the configurations moved in.

The gates it puts in front of the data, in the order they run:

  1. Tag. The first string must equal GetClassName. A mismatch logs both names and returns false having read nothing else.
  2. Version. The TVersion that follows must equal the private version constant, which is 0 (GetVersion). A mismatch logs the number that was read and returns false.
  3. Header stream state. After the record count is read, bis.HasError() is tested; a failure logs "Input stream failure." and returns false. Only then is space reserved.
  4. Per record. The same stream test closes each record's loop, so a file truncated in the middle stops there — with everything already read left appended to data.

A failed load is a partial load, and a second load is an append. The function never clears data: it reserves and emplace_backs. So the "Input stream failure" path above leaves the records it had already read sitting in the cache, and calling the function twice on one instance yields the union of both files with duplicate allocator names — which Normalize would merge, but nothing between this call and the lookup at LookUpMultiPoolConfig ever does. In practice the manager loads once, from its constructor (LoadMultiPoolConfigs), which is the only thing keeping this invisible.

The ordering check cannot reject anything, and only exists in a development build. After a successful read, an #if !RELEASE_BUILD block walks each record's configurations and, for every adjacent pair where a < b is false, emits a fatal-level log line naming the allocator and both block sizes — the message reads "configs should be well-orddered". It does not stop, does not clear, and does not change the return value: the function still answers true, and the out-of-order list goes straight into the banks that GenerateBanksByCache builds without sorting them. A shipped build runs no check at all. See PoolConfig for what an unsorted bank list then costs.

Parameters

ParameterTypeRequirement
bufferconst Buffer&A read-only buffer holding a whole cache file, obtained by the caller from BufferUtil::GetReadOnlyFileBuffer(path). Its contents are untrusted: the tag, the version, both counts and every size pair is read before it is believed

Return value

TypeWhat you get
booltrue when the tag, the version and every record streamed correctly — not a statement that the data is ordered, complete or usable. false on a tag mismatch, a version mismatch or a stream error, in which case whatever was read before the failure has still been appended.

Examples

One record's worth of reading, and the way its name becomes an id in this process:

data.emplace_back(key.GetID(), std::move(configs));

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Deserialize

The allocator's name crossed the file as text and is interned here, so a record from last month's build matches this run's GetName().GetID() as long as the spelling is the same — and a renamed allocator matches nothing, leaving its old record unused rather than misapplied. The pair of integers read just above this line comes from Serialize; the caller that ignores a false return is LoadMultiPoolConfigs, which logs the failure and carries on with an empty cache.
