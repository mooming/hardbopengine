MultiPoolConfigCache

Engine/Memory/MultiPoolConfigCache.h final namespace hbe bank configurations that survive a restart: what gets written to .multiPoolConfig.dat, when it is read back, and what a bad file does

Class description

class MultiPoolConfigCache final at Engine/Memory/MultiPoolConfigCache.h: a vector of MultiPoolAllocatorConfig records plus the two functions that turn it into bytes and back. Its whole purpose is to carry a multi-pool allocator's observed bank sizes across a process boundary, so the next run provisions the pools that were actually used instead of growing them one fallback at a time.

Two instances exist, both direct members of MemoryManager (Engine/Memory/MemoryManager.h), and the manager owns them for the process's life. Which one is which is the key to reading the rest of this page:

PieceWhat it isWhere the contract lives
multiPoolConfigCache The record read from disk: what the previous run needed. The only one anyone looks up at start-up LoadMultiPoolConfigs, LookUpMultiPoolConfig
multiPoolConfigLog The record of this run: one entry per report, appended while the engine is running. Only exists under PROFILE_ENABLED ReportMultiPoolConfiguration, SaveMultiPoolConfigs
The two orderings Records by allocator name, pool entries inside a record by block size Normalize, PoolConfigUtil::Normalize
The file .multiPoolConfig.dat — the MULTIPOOL_ALLOC_LOG path in Engine/Config/BuildConfig.h, resolved by GetMultiPoolConfigCacheFilePath Serialize, Deserialize

What is written, and when it is read

The file holds nothing but pool sizes: per allocator, its name as text and then, per bank, a block size and a block count (Serialize). No allocator type, no capacity, no parent, no thread, no timestamp. It is written once, from MemoryManager::PreEngineShutdown, and only under PROFILE_ENABLED; it is read once, from MemoryManager's own constructor, before the engine reports memory ready (LoadMultiPoolConfigs) — reading is not behind PROFILE_ENABLED, so a build that never writes a file still tries to read one. Between those two moments nobody opens the file: an edit by hand is read at the next start-up and nothing else.

What a stale or corrupt cache file does

Every failure is a log line and a load that gives up; none of them stops the engine.

ConditionWhat the code does
No file at the path LoadMultiPoolConfigs logs at Significant ("Failed to find") and returns. The cache stays empty and every allocator sizes itself by demand
File present but unreadable The read-only file buffer comes back with null data, logged at Error, and the load returns before Deserialize is called
Wrong class-name tag Deserialize reads the tag first and compares it to GetClassName: an Error naming both, then false — nothing is discarded first, so whatever was already in data stays
Version mismatch The uint32_t after the tag must equal the private version, which is 0 (GetVersion). Any other value logs the read number, returns false, and the file is ignored
Truncated or unreadable stream Checked once after the header and once per allocator record; either logs "Input stream failure." and returns false — but records already read have been appended to data, so a failed load leaves a partial cache, not an empty one
Pool sizes out of order inside a record Outside RELEASE_BUILD only: each adjacent pair that fails a < b logs a fatal error line naming the allocator and both sizes, and the function still returns true having loaded the record as read
A name in the file that no allocator uses this run Nothing. It sits in the vector, never matched by LookUpMultiPoolConfig. Renamed allocators accumulate here

The class-name tag is derived from the compiler, not typed by a person. GetClassName builds its string from __PRETTY_FUNCTION__ through StringUtil::ToCompactClassName and caches it in a function-local static, and that string is the first thing written and the first thing compared on read. Renaming the class, or moving it into another namespace, changes the tag — and every cache file on every developer's machine then fails the name check and is silently ignored. The same trick is used for the log category (ToCompactMethodName(__PRETTY_FUNCTION__)) in both serialisation functions.

Loading does not clear, and serialising does not leave the data alone. Deserialize appends to whatever data already holds — it reserves and emplaces, so calling it twice on one instance gives the union, in file order, with duplicates. And Serialize is not a read-only operation: it calls the private Normalize first, which sorts, collapses duplicate allocator names and empties the pool lists of records that were merged away. The instance the save path uses, multiPoolConfigLog, is therefore rewritten by the act of saving it — and SaveMultiPoolConfigs deliberately serialises twice, once into a dummy buffer to measure the size, so the normalisation runs twice before the file is written.

Coverage

Not documented hereWhy
What a corrupt record-count field does when it is enormous Deserialize does check the stream after reading the allocator-record count and before reserving for it, but it reads each record's configuration count and calls configs.reserve(configSize) with no error check in between. The failure mode of a huge reserve — an allocation throw, or the process ending with it — is decided outside this file by whatever allocator the vector's operator new reaches, and no page in this module states what that does. Recorded as unknown rather than guessed
Whether the file's byte layout is stable across platforms or builds What Serialize writes is whatever BufferOutputStream writes for a const char*, a uint32_t and a size_t; alignment, padding and width are that class's business and no page in Memory documents it. The version constant exists precisely because the answer is not "always"
Thread-safety of the two instances and of GetData's reference Reports arrive from whichever allocator finishes a run, appended through the non-const GetData, while the loaded cache is read by every allocator initialising itself. Neither instance carries a lock and no page states an ordering rule, so the safety of a reference taken while another thread appends is genuinely undocumented
Why reading the cache is unconditional while writing it is PROFILE_ENABLED-only The asymmetry is visible in Engine/Memory/MemoryManager.cpp: the constructor calls LoadMultiPoolConfigs directly, while SaveMultiPoolConfigs and ReportMultiPoolConfiguration are inside #if PROFILE_ENABLED. Nothing states whether that is intended or incidental
