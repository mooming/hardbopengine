Normalize

member of hbe::MultiPoolConfigCache Engine/Memory/MultiPoolConfigCache.h private sort the records by name, collapse one allocator's several reports, and drop the ones with nothing left in them

Signature

void Normalize()

Function description

A private member of MultiPoolConfigCache, defined in Engine/Memory/MultiPoolConfigCache.cpp, called from exactly one place: Serialize, before it writes anything. It is the step that turns "a list of records this run appended" into "one provisioning plan per allocator", in five passes:

  1. std::sort(data.begin(), data.end()) — by allocator name, using MultiPoolAllocatorConfig::operator<, so every record sharing a name lands next to every other.
  2. PoolConfigUtil::Normalize on each record's configuration list, so each list is ascending by block size with one entry per size (PoolConfig::operator< — the other ordering in the same object).
  3. A count of distinct names, skipping any record whose configuration list is empty.
  4. A rebuild: data is swapped into a temporary, space is reserved for the counted names, and the records are replayed in order — each new name flushes the configurations accumulated so far as a fresh record, and each record merges into the accumulator with PoolConfigUtil::MergeMax.
  5. std::sort(data.begin(), data.end()) again, because flushing appends at the end and the order built during pass 4 is only as good as the accumulator's own.

The result is the invariant the rest of the system depends on: one record per allocator name, the vector in name order, and each record's configurations in block-size order. That is what lets MemoryManager::LookUpMultiPoolConfig binary-search, and it is the reason the file Deserialize reads back is already sorted — nothing else ever sorts the records.

It is destructive to its own input, in three ways. The records that get merged away are left behind with empty configuration lists, because MergeMax clears the list it merges from; the vector is swapped out and rebuilt, so every reference, pointer and iterator into the old data dies when this returns; and the counts of equal sizes across duplicate records are not summed but maxed, so two reports of the same allocator collapse to the larger figure. A record whose configuration list is empty is dropped entirely — never counted, never replayed.

Calling it changes what a "serialize" means. Because Serialize normalises first, writing the cache out rewrites the object in memory, and SaveMultiPoolConfigs calls Serialize twice — once into a dummy buffer to measure the size, once into the file. The second run finds nothing left to merge, which is why the double call is harmless here; it is also why the shutdown dump that walks multiPoolConfigLog.GetData() afterwards reports the merged plan rather than the five or six reports the run really made.

Parameters

None. It operates on data, the instance's own record list.

Return value

None, and nothing is reported: records disappear and counts change with no log line and no return value. The only observable effect is the state of data, readable afterwards through GetData.

Examples

The two calls that do the per-record and per-name work:

PoolConfigUtil::Normalize(item.configs);

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Normalize

PoolConfigUtil::MergeMax(tempConfigs, item.configs);

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Normalize

The first runs over every record before any grouping happens; the second is inside the replay loop and is what consumes each duplicate record's list. Together they mean the file that finally leaves the engine describes the largest bank set any single report of that allocator produced, size by size — see MergeMax for why the merge is a maximum rather than a sum, and ReportConfiguration for where the numbers originate.
