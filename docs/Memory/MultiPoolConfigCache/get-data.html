GetData

member of hbe::MultiPoolConfigCache Engine/Memory/MultiPoolConfigCache.h nodiscard 2 overloads the record list itself, by reference - the only way a run appends to a cache while it is in flight

Signature

[[nodiscard]] auto& GetData()

[[nodiscard]] auto& GetData() const

Function description

Two accessors defined in the class body of Engine/Memory/MultiPoolConfigCache.h, each a single return data;. Both declare their return type as auto&, so the non-const form deduces TMultiPoolConfigs& and the const form deduces const TMultiPoolConfigs& — the const-ness comes from the deduction, not from the declaration.

This is not a read-only window. It is the only way the record list is written while a run is in flight: the non-const reference hands the caller the vector itself, and reporting code appends straight into it.

OverloadWho uses itWhat they do with it
non-const MemoryManager::ReportMultiPoolConfiguration data.emplace_back(uniqueName, std::move(poolConfigs)) — one record appended per report, with no de-duplication, no size limit and no lock at this point
const and non-const The verbose start-up and shutdown dumps in Engine/Memory/MemoryManager.cpp Walk every record and log each configuration as index : name (blockSize, numberOfBlocks), inside #if !RELEASE_BUILD and behind a log-level test
const MemoryManager::LookUpMultiPoolConfig That member function is const, so its access to the cache is const and the const overload is the one it gets: a read-only view it binary-searches by name and hands a reference out of

The reference is a borrow, not a lease. data is a std::vector and the reporting path grows it, so a reference or pointer taken from an element — or a MultiPoolAllocatorConfig reached through this accessor — is invalid the moment the vector reallocates. The same holds for Normalize, which swaps the whole vector out and rebuilds it, and for Deserialize, which reserves and appends. The manager gets away with it because the two instances are separated — the loaded cache is grown once at load time and read afterwards, while reports go to the other instance — and no page in the module states that as a rule.

No validation of any kind sits behind it. Nothing sorts, de-duplicates, bounds or inspects what arrives through this accessor; the ordering and collapsing rules live in Normalize, which is private and runs only when Serialize asks for it. A caller that appends through the non-const form has produced an unsorted list, and the only consumer that cares is the binary search in LookUpMultiPoolConfig — which reads the other instance.

Parameters

None.

Return value

TypeWhat you get
TMultiPoolConfigs& (non-const overload) / const TMultiPoolConfigs& (const overload)The cache's record list itself — modifiable through the non-const form, and valid only until the vector next grows or Normalize runs. Never null; an empty list is the answer for a cache that loaded nothing.

Examples

The one mutating caller appends directly:

data.emplace_back(uniqueName, std::move(poolConfigs));

From Engine/Memory/MemoryManager.cpp, MemoryManager::ReportMultiPoolConfiguration

data there is the reference this accessor returned for multiPoolConfigLog.GetData(). The allocator's report is ReportConfiguration, and the list it hands over is still in bank order rather than size order — normalisation is what fixes that, and it happens at Serialize time, not here.
