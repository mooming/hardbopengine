ScopedAllocator

Engine/Memory/ScopedAllocator.h final class template namespace hbe Owns an allocator by value and an AllocatorScope opened over it: one declaration routes a thread's allocations to a temporary allocator, and the member order guarantees the teardown that the module's history says hand-written pairs get wrong

Class description

template <typename TAlloc> class ScopedAllocator final at Engine/Memory/ScopedAllocator.h is the composition of the two pieces this module already has: it owns an allocator object by value, and it owns an AllocatorScope opened over that object. One declaration — ScopedAllocator<StackAllocator> scope("NestedStack0", 1024); — constructs the allocator with the forwarded arguments, registers it however its own constructor registers things, and routes the thread's default allocations to it until the declaration's scope ends. It is the type for the common case "this subtree of code allocates from this temporary allocator and nothing else"; the engine's uses of it are the nested-allocation testlets in Engine/Memory/StackAllocator.cpp, which stack five of them to prove exactly the nesting behaviour described below.

The two members are declared in the only order that works — TAlloc allocator; before AllocatorScope scope; — and both halves of this class's contract follow from that. Construction initialises them in that order: the allocator first, so it is a complete object whose GetID() the scope's template constructor can ask; the scope second, so the id it saves is the outer one and the id it installs is the live allocator's. Destruction runs in reverse — C++ member order — so the scope's destructor restores the outer id before the allocator's destructor releases its buffer and deregisters its slot. There is no instant in which the thread is pointed at a dead id, which is precisely the failure the AllocatorScope pages document as this module's recurring hazard.

The composition protects the id, not the pointer. The destructor order guarantees that no allocation call made after teardown routes through the dead allocator. It says nothing about pointers the subtree handed out: memory allocated from this object and released after the object died is released by whatever scope is current then — the id-free Delete(ptr) path reads the thread's current value, not the pointer's history (the free helpers). Objects that outlive a ScopedAllocator must be destroyed inside it, or released through the id-free paths never at all.
Copying and moving are deleted, and moving would break the registration the constructor just made. Allocators in this module register the object's address with the manager — MonotonicAllocator, for one, passes this to RegisterAllocator (Engine/Memory/MonotonicAllocator.cpp; the pattern repeats across the linear allocators). A move would leave the registration pointing at the source object's address while the buffer's ownership sits in the destination — so the header deletes copy and move, constructor and assignment alike (the class table), and a ScopedAllocator is a fixed point in the stack, nothing more.
