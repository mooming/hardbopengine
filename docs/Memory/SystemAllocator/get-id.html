GetID

member of hbe::SystemAllocator Engine/Memory/SystemAllocator.h MemoryManager::SystemAllocatorID - zero - known at compile time and read from no state: the only allocator identity that cannot go stale

Signature

#endif

	[[nodiscard]] constexpr auto GetID() const

Function description

Defined in the class body of Engine/Memory/SystemAllocator.h: return MemoryManager::SystemAllocatorID;. The return type deduces to TAllocatorID, and the value is constexpr-known — MemoryManager::SystemAllocatorID is a static constexpr zero — so the call folds at compile time and reads no state; it is valid on an unconstructed object's type, let alone a const one. This is why an instantiation can identify itself to the manager without the manager existing yet: RegisterSystemAllocator asserts exactly this agreement, Assert(systemAllocator.GetID() == SystemAllocatorID) (Engine/Memory/MemoryManager.cpp), binding the type's self-report to slot 0's number.

The same value is what every report this allocator files carries: the profiling calls in both private helpers pass GetID() as the record key, so slot 0's statistics are the system heap's traffic (AllocStats). The id is not issued, borrowed or reused — unlike every other allocator's, it cannot go stale, because it is a constant rather than a registration.

Parameters

None.

Return value

TAllocatorID: MemoryManager::SystemAllocatorID, which is 0, always.

Examples

	auto allocFunc = [](void*, size_t nBytes) -> void* { return systemAllocator.allocate(nBytes); };

From Engine/Memory/MemoryManager.cpp, MemoryManager::RegisterSystemAllocator()

The wrapper installed beside this call's guarantee: slot 0's allocate function discards the handle argument — it needs none, because the instance is the file-scope static — and forwards bytes straight to the object whose identity GetID states without looking.
