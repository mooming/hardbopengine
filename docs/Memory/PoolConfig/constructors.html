PoolConfig

member of hbe::PoolConfig Engine/Memory/PoolConfig.h either all zeros or exactly what was handed over - neither form floors, aligns or rejects anything

Signature

PoolConfig() noexcept
		: blockSize(0)
		, numberOfBlocks(0)

PoolConfig(size_t blockSize, size_t nBlocks) noexcept
		: blockSize(blockSize)
		, numberOfBlocks(nBlocks)

Function description

Two constructors defined in the class body of Engine/Memory/PoolConfig.h, both initialising the pair through a member initializer list. The default form leaves a configuration that means "no pool": blockSize and numberOfBlocks are both 0. The two-argument form stores what it is given — blockSize(blockSize), numberOfBlocks(nBlocks) — with no floor, no alignment, no ceiling and no check, so PoolConfig(0, 500) is a value the type will hold.

The parameters shadow the members, which is why the initializer list reads blockSize(blockSize). The second parameter is named nBlocks rather than numberOfBlocks, so a caller reading the header sees a different word in the declaration than the field name the value lands in.

Both are used the same way everywhere: configs.emplace_back(key, value) in MultiPoolAllocator::ReportConfiguration() builds one from a bank's live block size and peak usage, and MultiPoolConfigCache::Deserialize() builds one per record read out of the cache file with whatever two integers the file held. Neither caller validates the pair; validation, if any happens, is left to PoolConfigUtil::Normalize afterwards.

The type has no invariants, so "valid" is not a state a PoolConfig can be in. A default-constructed one is indistinguishable from a deliberately written PoolConfig(0, 0), and both are dropped by Normalize for the same reason — a zero count. That is the whole of the safety net at this layer.

Parameters

ParameterTypeRequirement
blockSizesize_tBytes per block. Accepted as given, including 0; nothing here applies the floor and alignment a real pool would
nBlockssize_tBlocks to provision. Accepted as given, including 0; unsigned, so a negative intent arrives as a very large positive number

The default constructor takes nothing.

Return value

Neither constructor returns a value or reports failure. Construction always succeeds; the pair it produced is judged later, by whoever sorts the list.

Examples

The reporting path builds these straight from live banks, which is how a peak observed in one run becomes a provisioning request for the next: 

configs.emplace_back(key, value);

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::ReportConfiguration() const

key is that bank's real block size and value its peak block usage, so the configuration records what the allocator actually needed rather than what it was asked for. It reaches the next boot through ReportMultiPoolConfiguration and MultiPoolConfigCache::Serialize.
