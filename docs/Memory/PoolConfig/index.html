PoolConfig

Engine/Memory/PoolConfig.h final namespace hbe a pool as a caller states it: a block size and a block count, plus the one comparator that orders every configuration list in the module

Class description

class PoolConfig final at Engine/Memory/PoolConfig.h: two size_t fields and a comparator. It is the request form of a pool — "give me numberOfBlocks blocks of blockSize bytes" — with no allocator, no buffer and no state behind it. A caller builds a list of them, and that list is what PoolConfigUtil normalises, what MultiPoolConfigCache writes to disk, and what MultiPoolAllocator::GenerateBanksByCache replays into real banks at the next boot.

The class exists so a list of pools has one ordering rule. Every algorithm in the module that touches a list of these calls std::sort(configs.begin(), configs.end()) first (PoolConfigUtil::Normalize(), PoolConfigUtil::MergeMax() and MultiPoolConfigCache::Normalize() in Engine/Memory/PoolConfigUtil.cpp and Engine/Memory/MultiPoolConfigCache.cpp), and that sort is decided entirely by operator<. Nothing else in the engine compares two pool configurations any other way.

The ordering rule

The rule is ascending by blockSize, and by nothing else. Two entries with the same block size compare equivalent no matter how far apart their counts are, because the comparator reads only blockSize. That is what makes a list of pool configurations a set of sizes in disguise: PoolConfigUtil::Normalize sorts, then folds every run of equal sizes into one entry whose count is the run's sum, and asserts the result holds exactly as many entries as there were distinct sizes.

An out-of-order list costs different things depending on who receives it:

ReceiverWhat an out-of-order list does
Normalize, MergeMax Nothing: both sort first, so the list self-heals. MergeMax sorts its destination again at the end for the same reason
MultiPoolConfigCache::Deserialize It does not sort. Outside RELEASE_BUILD it walks each adjacent pair and logs a fatal error — "configs should be well-orddered" — for every pair that fails a < b, then still returns true with the data loaded exactly as read
GenerateBanksByCache Banks are created in the order the file lists them, and unlike GenerateBank this path never sorts the bank vector afterwards, so an unsorted cache file leaves an unsorted bank list in a shipping build where no check runs at all
MultiPoolAllocator::GetBankIndex(size_t) Where the cost lands. That scan takes the first bank whose block size covers the request and gives up as soon as it meets a bank more than twice the request size — a rule that only means anything on an ascending list. A bank that is too large, met early, ends the search and pushes the request into the fallback path: a fresh bank every time and a fallback counted against the engine's statistics

numberOfBlocks is size_t, so a negative count cannot be represented. The one place that asks for it writes config.numberOfBlocks <= 0 (PoolConfigUtil::Normalize()), which on an unsigned type is a zero test and nothing more. A caller that computes a count and underflows it gets a value near SIZE_MAX, every check in the module accepts it, and the entry survives into the cache file. The cost is paid at boot: a bank is blockSize * numberOfBlocks requested from the parent allocator, and GenerateBank guards only for Assert(blockSize > 0) and Assert(numberOfBlocks > 0) — assertions, which Engine/Core/Debug.h defines away in a Release build.

A count of zero means "do not provision this size", and it is dropped rather than honoured. PoolConfigUtil::Normalize() skips zero-count entries while it counts distinct sizes and refuses to emit a run whose summed count is zero, so a size that appears only with a zero count disappears from the list. A zero block size behaves the same way but for a subtler reason: the fold seeds its running comparison with blockSize = 0, so a leading zero-size entry is never recognised as a new run and its count is discarded with it. In both cases the trailing Assert(configs.size() == numUniqueBlocks) still holds, so the loss is silent by design — it is a compaction rule, not an error.
