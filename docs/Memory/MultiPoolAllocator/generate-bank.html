GenerateBank

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Private: borrow a buffer from the parent, insert a bank, and re-sort the ladder that other threads must never see.

Signature

void GenerateBank(size_t blockSize, size_t numberOfBlocks)

Function description

Private. Builds one bank, adds it to the ladder, and puts the ladder back in order. It is the only member that calls std::sort, and the only one that can move existing banks while doing so.

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::GenerateBank()

The bank's backing buffer is one request to the parent allocator, made inside that scope (PoolAllocator::PoolAllocator() calls mmgr.Allocate(totalSize)), and the bank registers itself with the manager under the composite name name_blockSize_numberOfBlocks. After the block, a Verbose log line names the bank, and a profiling build adds blockSize * numberOfBlocks to this allocator's registered capacity.

What one bank costsWhere it is paid
One buffer of blockSize × numberOfBlocks from parentIDPoolAllocator::PoolAllocator(), through MemoryManager::Allocate
One registration slot out of the 255 the process sharesMemoryManager::RegisterAllocator, and Engine/Memory/AllocatorID.h for the ceiling
A full re-sort of the ladderstd::sort over every bank, on every growth
One engine-level fallback countBy the caller, in NewBankAllocate
Sorting moves banks, and a moved bank's registration is not refreshed. PoolAllocator's move constructor re-points the manager's proxy for the bank's id at the new allocate and deallocate functions (and refreshes the profiling capacity) but never re-points allocProxy.allocator (Engine/Memory/PoolAllocator.cpp). Dispatch is allocProxy.allocate(allocProxy.allocator, nBytes) (Engine/Memory/MemoryManager.cpp, MemoryManager::Allocate()), and those function pointers begin by casting their first argument back to a PoolAllocator*. After any bank is moved — by the emplace_back growing the vector, or by the sort — the proxy still names the address the bank used to occupy. This class is unaffected today because it reaches banks as banks[index] and never through their ids; the failure arrives the moment anything scopes to a bank id. The same three lines were recorded against the thread-safe twin as finding 5 of the 2026-10-05 review, and no fix has landed.
The sort also depends on how the standard library chooses to move. PoolAllocator::operator=(PoolAllocator&&) is destructive: it runs the destructor on the destination — which returns that destination's buffer to its parent and deregisters it — and then placement-news the moved bank into the same storage (Engine/Memory/PoolAllocator.cpp). Whether a sort ever destroys a live bank therefore depends on which element the algorithm moves into which slot. The 2026-10-05 review measured it against libc++ and recorded zero releases for an out-of-order insert, and its own conclusion is the sentence to keep: "safe by luck, not by contract". The measurement was made on the twin; the two lines it rests on, the emplace_back and the std::sort above, are the same here.
Both asserts that guard this member are Debug and Dev only. Assert(blockSize > 0) and Assert(numberOfBlocks > 0) compile to nothing in a Release build (Core: Debug). A zero count is otherwise unreachable from the only caller — CalculateNumberOfBlocks returns at least one — except where blockSize × numberOfBlocks wraps to zero, which is exactly the case PoolAllocator::PoolAllocator() answers with an early return that leaves the bank's free-list head uninitialised and the bank holding no blocks. Such a bank is then skipped by GetBankIndex forever, and the next request for its size ends in the FatalAssert of NewBankAllocate.
The scope is opened twice, and the second opening changes nothing. parentID is installed at the top of the function and again inside the block that wraps the emplace_back and the sort — the same id, nested (Engine/Memory/MultiPoolAllocator.cpp). The outer scope is the one that matters: it covers the name formatting, the insertion and the profiling bookkeeping. What the inner one is for is not stated anywhere in the sources or in a design document, and it is listed on the class page with the other things two authors appear to have edited separately.
Order is maintained here and nowhere else. Every insertion re-sorts the whole ladder by PoolAllocator::operator<, which orders by block size and breaks a tie by putting the bank with more free blocks first (Engine/Memory/PoolAllocator.cpp). That is what keeps GetBankIndex's early exit a best fit; the cache path relies on the file already being ordered instead.

Parameters

ParameterTypeRequirement
blockSize size_t Bytes per block. Must be non-zero — asserted in a checked build. The pool rounds it up to sizeof(size_t) and to a multiple of Config::DefaultAlign before reserving, so the bank's real block size can exceed what is passed here
numberOfBlocks size_t Blocks in the bank. Must be non-zero — asserted in a checked build. The product of the two parameters is the buffer borrowed from the parent, and it is the capacity a profiling build adds to the allocator's total

Return value

void. The new bank is reachable as banks[index] afterwards — the caller re-runs GetBankIndex rather than being handed the bank, because the sort may have moved it. Failure is not reported: an assert stops a checked build and a Release build continues with whatever the pool managed to reserve.

The single call site. The two constructors build their initial banks with their own loops instead, and those loops open no scope over the parent — which is correct at that moment, because parentID is by definition the ambient allocator while the constructor is running. GenerateBank is different: it runs long afterwards, on whatever thread is allocating, inside whatever scope that caller happens to be standing in, so the explicit AllocatorScope is what keeps a bank's backing buffer out of an unrelated pool. The ordering of the ladder is enforced here too, and nowhere else — the initializer_list constructor sorts once before it inserts, and GenerateBanksByCache sorts nothing.
