Function description

Private, and the only member that adds a bank. Allocate calls it when no existing bank will serve a request, and it converts that request into geometry: a block size, a block count, a new pool bank, and one block taken from it. 

{
	auto& engine = Engine::Get();
	auto& statistics = engine.GetStatistics();
	statistics.IncFallbackAllocCount();

	auto blockSize = CalculateBlockSize(size);
	auto numBlocks = CalculateNumberOfBlocks(bankSize, blockSize);
	GenerateBank(blockSize, numBlocks);

	auto index = GetBankIndex(size);
	if (unlikely(index >= banks.size()))
	{
		FatalAssert(false, "MultiPoolAllocator: bank generated for ", size, " bytes cannot be used: index ", index,
				  " of ", banks.size(), ", proposed block ", blockSize, " by ", numBlocks, ", allocation unit ",
				  bankSize);

		return nullptr;
	}

	auto& bank = banks[index];
	auto ptr = bank.Allocate(size);

#if PROFILE_ENABLED
	{
		auto& mmgr = MemoryManager::GetInstance();
		mmgr.ReportAllocation(GetID(), ptr, size, bank.GetBlockSize());
	}
#endif // PROFILE_ENABLED

	return ptr;
}

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::NewBankAllocate()

The two geometry decisions belong to CalculateBlockSize and CalculateNumberOfBlocks; the creation and its cost belong to GenerateBank. What this member owns is the sequence, and the fact that it is a growth path rather than an allocation path: one call borrows a bank's whole backing buffer from the parent allocator.

Every call is counted as a fallback allocation, at engine level. IncFallbackAllocCount is a SystemStatistics counter on the live Engine object (Engine/Core/SystemStatistics.h), and it is a different quantity from AllocStats::fallbackCount, which counts the manager's own FallbackAllocate calls and is read by PrintUsage (Engine/Memory/MemoryManager.cpp, MemoryManager::ReportFallback()). Bank generation moves the first figure and not the second, so a pool that grew twenty times can report zero fallbacks while the engine reports twenty.
Growth needs a live engine. The first statement is Engine::Get(), which asserts on a null instance in every non-Release build and dereferences it regardless (Engine/Engine/Engine.cpp). An allocator constructed before the engine exists can still serve requests from banks it was given at construction; the moment one of them is exhausted, or the ladder cannot answer a size, this member runs and the missing engine becomes the failure. TaskStream builds its allocator during stream construction and only reaches this path on a pass that allocates (Engine/Core/TaskStream.cpp).
The assert at the end is a witness, not a recovery, and it aborts in every configuration. FatalAssert lives outside the RELEASE_BUILD guard and calls std::abort() (Engine/Core/Debug.h), so the return nullptr after it is dead code and the caller never learns that a request failed. Reaching it means the bank that was just generated still did not satisfy GetBankIndex for the same size — which every earlier guard makes hard to reach: CalculateBlockSize returns a block size never below the request, CalculateNumberOfBlocks returns at least one block, and GenerateBank asserts both. A build that lands here has already broken one of those invariants — a zero minBlock, or a bank whose backing allocation left it with no blocks at all.
The pointer comes back through the ladder, not out of the new bank directly. After growth, this member re-runs GetBankIndex and takes banks[index], so the bank that serves the request is whatever the sorted ladder now considers best — normally the bank that was just created, and provably a bank whose block size is at least the request. The bank underneath (PoolAllocator::Allocate) has its own route to the parent allocator for a request larger than its block size, and neither path into this member can reach it.

Examples

Private, with one caller: Allocate, from both of its refusal branches. No source outside the class can call it, and the unit tests observe it only through the engine's fallback counter — the Multiple Allocations & Fallback testlet in Engine/Memory/MultiPoolAllocator.cpp expects two growth events across eleven requests against a {64 … 4096} ladder, and that assertion is compiled out with PROFILE_ENABLED.
