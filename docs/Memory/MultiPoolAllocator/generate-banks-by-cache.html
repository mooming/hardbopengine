GenerateBanksByCache

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Private: build the bank ladder the previous profiling run filed under this name.

Signature

bool GenerateBanksByCache(MemoryManager& mmgr)

Function description

Private. Asks the manager whether the previous profiling run recorded a bank ladder under this allocator's name, and if so builds that ladder before the object finishes constructing. It is the only reason two runs of the same program do not both spend their first hundred allocations building banks. 

	auto nameID = name.GetID();
	auto& cacheItem = mmgr.LookUpMultiPoolConfig(nameID);
	if (cacheItem.uniqueName != nameID)
	{
		return false;
	}

	auto& configs = cacheItem.configs;
	for (auto& config : configs)
	{
		InlineStringBuilder<1024> str;
		str << name << '_' << config.blockSize << '_' << config.numberOfBlocks;

		banks.emplace_back(str.c_str(), config.blockSize, config.numberOfBlocks);
	}

	return true;

A miss is answered by MemoryManager::LookUpMultiPoolConfig returning a default-constructed record whose name compares unequal, so the test on the returned name is the whole lookup result — there is no null and no error path (Engine/Memory/MemoryManager.cpp).

Question a caller asksWhat the sources say
Who calls this? The name-only constructor, once, before registration. The initializer_list constructor never consults the cache, so a hand-configured ladder is never silently replaced by a cached one
Who reads the result? Nobody. The constructor calls it as a statement and discards the boolean (Engine/Memory/MultiPoolAllocator.cpp) — the difference between "started empty" and "started from the cache" is visible only in the bank count and in the log line the lookup itself writes
Where does the cache come from? MemoryManager::MemoryManager() calls LoadMultiPoolConfigs(), which reads the file named by GetMultiPoolConfigCacheFilePath(); that file is written by SaveMultiPoolConfigs() in PreEngineShutdown() under PROFILE_ENABLED (Engine/Memory/MemoryManager.cpp). With the profiling switch off — the shipped configuration — no run writes the file, so a fresh cache holds nothing and every name-only allocator starts with zero banks
What geometry arrives? The previous run's high-water mark per block size, merged across every instance that shared this name: ReportConfiguration reports peaks and MultiPoolConfigCache::Normalize folds same-name entries by maximum at save time (Engine/Memory/MultiPoolConfigCache.cpp).
The cached order is trusted, never re-established. The banks are appended in the order the cache holds them and this member sorts nothing — unlike the initializer_list constructor, which sorts before building, and GenerateBank, which sorts after every insertion. MemoryManager::LookUpMultiPoolConfig binary-searches the table by name, and MultiPoolConfigCache::Deserialize only checks that each entry's configurations ascend by block size, logging a fatal error when one does not (Engine/Memory/MultiPoolConfigCache.cpp, non-Release builds). That order is what makes GetBankIndex a best fit at all: it stops at the first bank large enough, which is only the smallest one if the vector ascends.
The rest of the configuration is this run's, not the cached one. Only block sizes and counts come from the cache. bankSize and minBlock still come from this object's constructor arguments, so a cached ladder and a generated bank can disagree about the size-class ladder in the same instance — the cached entries keep their own sizes, and anything later is rounded to minBlock.
The parameter asks for more than the body uses. LookUpMultiPoolConfig is a const member (Engine/Memory/MemoryManager.h), so this signature's non-const MemoryManager& is not needed by anything it calls; the twin declares the same helper as taking a const reference (Engine/Memory/ThreadSafeMultiPoolAllocator.h). The difference is a narrowing of who may call the helper, not a difference in behaviour, and it is listed on the class page with the other divergences between the two classes.
