~MultiPoolAllocator

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Return every bank to the allocator that lent its memory, then give up the registration.

Signature

~MultiPoolAllocator()

Function description

Opens the recorded parent as the ambient allocator, hands out what a profiling build wants to know, destroys every bank, then deregisters this allocator. The first statement is the one that decides who pays. 

	AllocatorScope scope(parentID);

	auto& mmgr = MemoryManager::GetInstance();
…
	banks.clear();

	mmgr.DeregisterAllocator(GetID());

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::~MultiPoolAllocator()

banks.clear() runs PoolAllocator::~PoolAllocator() on each bank, and that destructor releases its backing buffer with mmgr.Deallocate(parentID, buffer, totalSize) — the parent the bank recorded when it was built, not whatever scope is open now (Engine/Memory/PoolAllocator.cpp). Both halves were changed together on 2026-10-05: the journal entry at 18:31 records the defect and its fix, and the consequence for a caller is unchanged either way — an allocator may be destroyed under any scope, including one of its own.

Between the scope and the clear, two conditional blocks run, and both are switched off in the configuration the repository ships (Engine/Config/BuildConfig.h defines PROFILE_ENABLED and MEMORY_VERIFICATION_ENABLED to 0):

GuardWhat the destructor does thereWhy
PROFILE_ENABLED Calls ReportConfiguration before any bank dies The block ladder has to be read while it still exists; the figure is what the next run boots from
MEMORY_VERIFICATION_ENABLED Writes the current thread id into every bank's allocator proxy before clearing the vector See the box below — this is the one place the class can erase evidence rather than produce it
The bank proxies are re-stamped to the destroying thread before they are checked. MemoryManager::DeregisterAllocator is the only place in the manager that compares a thread id at all, and it compares the deregistering thread against the one recorded on the proxy (Engine/Memory/MemoryManager.cpp). ~MultiPoolAllocator overwrites each bank's recorded id with std::this_thread::get_id() immediately before destroying it (Engine/Memory/MultiPoolAllocator.cpp), so a bank registered on one thread and destroyed on another cannot produce that mismatch report. Whether the write exists to legitimise a thread hand-over or to keep the check quiet is not stated anywhere in the sources or in a design document, and is named as an open question on the class page.
Blocks still checked out are not detected here; they are destroyed with the bank. The class has no per-block bookkeeping of its own — a live block is simply a byte range inside a bank's buffer — so a block that was never returned is released along with the whole buffer back to the parent. The only witness is MemoryManager::DeregisterAllocator reporting usage > 0 under PROFILE_ENABLED, which in a non-Release build calls debugBreak() and returns early, before its own statistics reset and before the proxy goes back to the pool (Engine/Memory/MemoryManager.cpp, and where a checked build stops instead of continuing). A profiling build that leaks one block out of a pool therefore also retires that pool's registration slot for the rest of the run.
The scope line above has no observable effect today, and that is a measured result, not an assumption. The 2026-10-05 journal entry at 18:31 states it directly for both multi-pools: once PoolAllocator::~PoolAllocator() releases through its own recorded parent, "the banks vector's own storage is freed after locals are destroyed, so no scope reaches it", which makes the line unfalsifiable by test. It stays in the source, and this page records what it is worth rather than what it was meant to be worth.
Destruction is a single-thread act, like everything else the class does. It walks banks, mutates a vector the manager owns and rewrites proxies — none of it under any lock, because MultiPoolAllocator declares none. The thread that created the instance, or a thread that can prove nothing else is inside it, is the only legal caller.

Parameters

None.

Return value

void. Destruction cannot refuse. It can leave a registration slot retired and a leak unreported (Release builds, where Assert and debugBreak are compiled out — Core: Debug), but it will not fail to return.

The destructor runs at the closing brace of a testlet body's block, while the scope over itself is still open and after the usage report has been written. It is the ordinary shape: an allocator declared before its scope, destroyed after everything that used it.
