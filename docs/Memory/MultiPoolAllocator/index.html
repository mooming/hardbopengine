MultiPoolAllocator

Engine/Memory/MultiPoolAllocator.h final Banks of fixed-size blocks, one per size class, grown on demand - and no synchronisation at all, so one thread owns the instance.

Class description

class MultiPoolAllocator final at Engine/Memory/MultiPoolAllocator.h: a set of fixed-block pools called banks, one per size class, kept in ascending block-size order and grown on demand. A request is answered by the smallest bank that can hold it, is not full, and would not waste more than double the request; anything else builds a new bank. Blocks come back by address, because Deallocate asks each bank whether it owns the pointer.

One thread owns an instance, for its whole life, and that is a contract rather than an absence. The class declares no mutex, no atomic and no lock — banks is a plain hbe::HVector<PoolAllocator>, every bank's free list is plain data, and Allocate, Deallocate, GenerateBank and PrintUsage all read and write that state with nothing between them and the caller. Construction, every allocation, every release and the destructor belong to a single thread, and no other thread may touch the instance while they run. Nothing checks it: the manager's one thread comparison is made at deregistration, and the class overwrites the value it compares for its banks on the way there. The allocator built for sharing is the other entry in the allocator catalogue — same strategy, one mutex, and a locking protocol of its own to be careful about.
The ladder only ever grows. A bank is created by NewBankAllocate and lives until the allocator is destroyed: no member releases an exhausted or unused bank, and the memory a bank holds is blockSize × numberOfBlocks borrowed from the parent allocator. A size class that once ran dry is a bank forever, so the shape of a long-lived instance is a record of every size it was ever asked for.
The name is the allocator's identity outside this object. The next run boots from the last one's report by name, and ReportConfiguration files its ladder under the same key — so two instances that share a name share a ladder, and their reports merge into one entry (MultiPoolConfigCache::Normalize in Engine/Memory/MultiPoolConfigCache.cpp).

Non-member helper functions

None. The only helpers in Engine/Memory/MultiPoolAllocator.cpp are function-local lambdas — the allocFunc and deallocFunc trampolines both constructors hand to MemoryManager::RegisterAllocator, and InsertItem inside ReportConfiguration — none of them reachable outside the function that defines it. The allocFunc pair is worth one sentence: both cast the manager's untyped first argument back to a MultiPoolAllocator* and call this class's own members, which is why moving a bank leaves a stale pointer in the manager rather than a broken call here.

Why the destructor re-stamps each bank proxy's thread id Open question. ~MultiPoolAllocator writes the destroying thread's id into every bank's proxy under MEMORY_VERIFICATION_ENABLED immediately before destroying them, and that id is the value MemoryManager::DeregisterAllocator compares against. Whether the write legitimises a hand-over (as Logger::StartTask does for the logger's own pool) or silences the check, the source does not say and the twin does the same thing
Why GenerateBank opens the parent scope twice Open question. The outer and inner AllocatorScope both install parentID, so the inner one has no effect a reader can identify (Engine/Memory/MultiPoolAllocator.cpp)
Copy and move The header declares neither for this class, and this page makes no claim about what compiles: proving that needs a compiler, and authoring the reference does not run one. What can be stated from the sources is the consequence — the object owns banks, whose element type owns a registration and a buffer, so any copy would put two objects in charge of the same bank ids
