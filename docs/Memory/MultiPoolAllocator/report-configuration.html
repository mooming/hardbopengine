ReportConfiguration

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Publish the peak bank ladder for the next run to boot from, behind an assertion on its own total.

Signature

#if PROFILE_ENABLED
	void ReportConfiguration() const

Function description

Publishes this allocator's bank ladder — one entry per block size, each holding the largest number of blocks the banks of that size ever held simultaneously — to the manager, which is what a later run boots from. It exists only when PROFILE_ENABLED is on, and the counters it reads exist only then too (Engine/Memory/MultiPoolAllocator.h, PoolAllocator::GetUsedBlocksMax()). 

	MemoryManager::TPoolConfigs configs;
	configs.reserve(banks.size());

	auto InsertItem = [&configs](const PoolAllocator& alloc)
	{
		auto key = alloc.GetBlockSize();
		auto value = alloc.GetUsedBlocksMax();

		auto pred = [key](const PoolConfig& item) { return item.blockSize == key; };

		auto found = std::find_if(configs.begin(), configs.end(), pred);
		if (found == configs.end())
		{
			configs.emplace_back(key, value);
		}
		else
		{
			found->numberOfBlocks += value;
		}
	};

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::ReportConfiguration()

The else branch is the whole point of the aggregation. Before 2026-10-05 the accumulation ran after the not-found test rather than inside it, and because configs.reserve(banks.size()) guarantees the emplace_back does not reallocate, that new element was constructed at the address found already held — so the value was added twice for every size class the report introduced. The journal entry at 18:31 records the fix, and this function gained its assertion the same day: 

	size_t peakBlocks = 0;
	size_t reportedBlocks = 0;

	for (auto& bank : banks)
	{
		InsertItem(bank);
		peakBlocks += bank.GetUsedBlocksMax();
	}

	for (const auto& config : configs)
	{
		reportedBlocks += config.numberOfBlocks;
	}

	Assert(reportedBlocks == peakBlocks, "ReportConfiguration: the reported block count ", reportedBlocks,
		   " does not match the summed bank peak ", peakBlocks);

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::ReportConfiguration()

The invariant, and which side is wrong when it breaks. Summing the grouped configurations must reproduce the sum of the individual banks: Σ over configs of numberOfBlocks == Σ over banks of GetUsedBlocksMax(). Two banks of one block size merge into one entry, nothing else may change the total. peakBlocks is read straight out of each bank one at a time, so when the assert fires the grouped figure is the defective one: trust peakBlocks and treat the report as wrong. The assert sits before mmgr.ReportMultiPoolConfigutation(uniqueName.GetID(), std::move(configs)), so in a build where Assert is live — every non-Release build, per Core: Debug — the process stops without publishing anything, and the cache keeps the last correct ladder. A configuration in which the assert is compiled out would publish the wrong figure, and that configuration is also one the tree cannot currently build at all, which the same journal entry records as an open task.
What a wrong figure costs is the next run, not this one. The published entries land in MemoryManager::multiPoolConfigLog, which PreEngineShutdown serialises to the cache file; the next boot loads it and GenerateBanksByCache builds this allocator's banks from it (Engine/Memory/MemoryManager.cpp). An entry that counted every size class twice makes the next run boot with a bank twice the size it needed, forever, because each over-sized run reports its own over-sized peak. The doubled figures the journal prints — 18 against a true 9, 25 against 15, 80 against 40 — were measured on a standalone model built from the two variants of the lambda above, not on the engine binary, which the profiling switch cannot currently compile. They are reproduced here as the order of the defect, not as engine measurements.
The peak is a lifetime high-water mark and is never reset. PoolAllocator::AllocateBlock() raises maxUsedBlocks on every allocation and nothing lowers it (Engine/Memory/PoolAllocator.cpp), so what this member reports is the worst moment the instance ever reached, and an allocator that ran for an hour reports its hour's maximum.
Cost is quadratic in the number of banks, not in bytes. Each bank runs a std::find_if over the configurations collected so far, so a ladder of n banks costs on the order of n² comparisons at destruction. It runs once, in the destructor, and the same day's benchmark work is what measures the allocation path instead.
const here, not there. This member is const; ThreadSafeMultiPoolAllocator::ReportConfiguration is not, and neither is that class's PrintUsage (Engine/Memory/MultiPoolAllocator.h against Engine/Memory/ThreadSafeMultiPoolAllocator.h). Both bodies read state and hand it to the manager, so the qualifier is not telling a caller anything about behaviour — it is drift between two classes that were edited separately, and it is named as an open question on the class page.

Parameters

None.

Return value

void. The configuration goes to MemoryManager::ReportMultiPoolConfigutation keyed on the allocator's name id, and there is no read-back: a caller cannot ask the manager what this instance reported, only what the next instance boots from.

Examples

From Engine/Log/Logger.cpp, Logger::ReportMemoryConfiguration()

	allocator.ReportConfiguration();

The logger owns a MultiPoolAllocator member and offers this one-line accessor so a profiling shutdown can ask for its ladder without waiting for the logger itself to die. The other caller is ~MultiPoolAllocator, which calls it under PROFILE_ENABLED before any bank is destroyed.
