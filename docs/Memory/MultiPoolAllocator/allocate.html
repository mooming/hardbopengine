Allocate

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Take a block from the smallest bank that will hold the request, or grow the ladder and then take one.

Signature

void* Allocate(size_t size)

Function description

Asks the bank ladder for a block, and grows the ladder when nothing in it will do. It is the only public member that can change the structure of the allocator, and the only route to NewBankAllocate.

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::Allocate()

GetBankIndex walks the banks from the smallest block size up and returns the first one that is large enough, not full, and no more than double the request rounded up to minBlock. Two different refusals both end at the same place: no bank fits, or the bank that fits is exhausted. Both grow the ladder, so a size class that runs dry gets a second bank rather than a wait.

A profiling build reports the served block through MemoryManager::ReportAllocation with the bank's block size, not the requested size (Engine/Memory/MultiPoolAllocator.cpp) — the difference between the two is the allocator's internal waste, and it is the figure PrintUsage prints per bank.

There is no allocation, only a block. This signature cannot express an alignment, and the block it hands back is 16-byte aligned and nothing more: the pool rounds a bank's block size up to Config::DefaultAlign (Engine/Config/EngineConfig.h, Engine/Memory/PoolAllocator.cpp), and a type whose alignof exceeds 16 is therefore silently under-aligned. The 2026-10-05 review recorded this as finding 9 and no code since has closed it, so treat it as a known gap in the interface rather than as a guarantee: over-aligned types do not belong in a pool of this shape.
Exhaustion stops the process; it does not return null. The only null this function returns for a non-zero request is unreachable: the growth path ends in FatalAssert(false) before it can return one, and FatalAssert is defined outside the RELEASE_BUILD guard, so it aborts in every configuration (Engine/Core/Debug.h). Before that, a bank's own backing request goes through MemoryManager::Allocate, whose Assert(ptr != nullptr, "Allocation Failed") fires first in a Debug or Dev build (Engine/Memory/MemoryManager.cpp). A caller cannot ask this allocator to fail politely, and cannot fall back to another source on its advice.
A request for zero returns null and allocates nothing — but that guard is rarely what stops it. size <= 0 on a size_t tests one value, zero, and behaves identically to the size == 0 spelling the thread-safe twin now uses; the journal entry at 2026-10-05 18:31 records the two spellings and leaves this one alone. A request that arrives through MemoryManager::Allocate is already answered with null before this function is reached (Engine/Memory/MemoryManager.cpp), so the guard only matters to a caller holding the object directly.
Nothing here is synchronised, and the two occupancy reads above are the reason it cannot be added later by accident. GetBankIndex consults GetAvailableBlocks() while choosing, so the bank that answers a size depends on who has taken what. One thread owns an instance for its whole life; the variant built for sharing is named in the allocator catalogue.

Parameters

ParameterTypeRequirement
size size_t Bytes wanted. Zero returns null. Anything from 1 to minBlock is treated as a request for minBlock, and anything above the largest bank's block size creates that bank. The value is not stored with the block: the matching Deallocate must be given it again

Return value

TypeWhat you get
void* A block inside one of this allocator's banks, at least size bytes and up to the bank's block size, or null for a request of zero. The block size that served the request is not returned and cannot be recovered from the pointer by any public member; only a profiling build records it, per bank, in MemoryManager's statistics

Examples

No engine source calls MultiPoolAllocator::Allocate by name. The real route is the function pointer the constructor installed: MemoryManager::Allocate calls allocProxy.allocate(allocProxy.allocator, nBytes), and that lambda is the one the constructor built out of this member (Engine/Memory/MemoryManager.cpp, Engine/Memory/MultiPoolAllocator.cpp). Engine code therefore allocates from an instance by standing in it.
