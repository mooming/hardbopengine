Deallocate

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Find the bank that owns the pointer and hand the block back; the size is a check, not a selector.

Signature

void Deallocate(void* ptr, size_t size)

Function description

Finds which bank owns the pointer, hands the block back, and refuses anything it does not own. The bank is chosen by address, never by size, and that single fact is the contract of this member. 

	auto index = GetBankIndex(ptr);
	if (index >= banks.size())
	{
…
		return;
	}

	auto& bank = banks[index];
	Assert(size <= bank.GetBlockSize());

	bank.Deallocate(ptr, size);

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::Deallocate()

GetBankIndex(void*) asks each bank IsMine(ptr) in turn — a range test against that bank's buffer — so releasing costs one linear scan over the banks no matter which one owns the block.

A foreign pointer is reported and dropped, not forwarded. When no bank owns the address, the member logs OutFatalError naming the pointer followed by every bank's start - end range and then returns without releasing anything (Engine/Memory/MultiPoolAllocator.cpp). The block leaks. This is not what the bank underneath does: PoolAllocator::Deallocate forwards a pointer it does not own to its parent allocator (Engine/Memory/PoolAllocator.cpp). The multi-pool has no parent to forward to on a block's behalf, so the release simply does not happen and no error code comes back — a mismatched allocator pair shows up as a log line in a growing leak, not as a failure at the call.
size is a checked hint here, not a selector — and the check is Debug-only. Because the bank is found by address, a wrong size cannot send a block to the wrong size class, which is the damage the module page's general warning about mismatched sizes describes for pools selected by size. What Assert(size <= bank.GetBlockSize()) protects is the profiling record, and Assert compiles to nothing in a Release build (Engine/Core/Debug.h); PoolAllocator::Deallocate then ignores the argument except for its own profiling assert. A wrong size is therefore invisible in Release, and the block still returns to the list it belongs on.
A double release is not detected at the second release. Nothing in this member or in PoolAllocator::Deallocate asks whether the block already sits on the free list; the block is re-linked and numberOfFreeBlocks is incremented regardless (Engine/Memory/PoolAllocator.cpp). The only witness there is Assert(numberOfFreeBlocks <= numberOfBlocks), which can fire only after the count has passed the bank's total, so the first double free in a bank is silent and the second may not be caught either. Two live owners of one block is the result, and it is undetectable from this class's public surface.
Releasing null is legal once. Deallocate(nullptr, size) asserts size == 0 and returns, so Deallocate(nullptr, 64) stops a Debug or Dev build and does nothing in Release (Engine/Memory/MultiPoolAllocator.cpp, Engine/Core/Debug.h). The same pairing exists in MemoryManager::Deallocate, which answers null before reaching any allocator (Engine/Memory/MemoryManager.cpp).

Parameters

ParameterTypeRequirement
ptr void* A pointer this instance obtained from Allocate and has not released yet. Null is accepted. Anything else — including a block belonging to another allocator of the same shape — is logged and dropped
size size_t The size originally requested, and no more than the block size of the bank that owns the pointer. It does not choose the bank; it is asserted against it and recorded in the profiling counters

Return value

void. Nothing distinguishes a successful release from a refused one at the call site, and the distinction is visible only in the log and in deallocCount under PROFILE_ENABLED.

Examples

No engine source calls this member by name either: it is the deallocate half of the pair the constructor registered, reached through MemoryManager::Deallocate by whatever stands in an AllocatorScope over the instance.

The testlet releases every block with a size of zero. Each release is answered by the address lookup, which finds the owning bank regardless, and the profiling assert on the size never sees a value to complain about — which is exactly why this page states the size argument as a hint rather than as a key.
