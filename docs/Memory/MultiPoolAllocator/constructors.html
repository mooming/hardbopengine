MultiPoolAllocator

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Build the ladder from a cached configuration, from a hand-written one, or from nothing at all - and record who owns the banks.

Signature

explicit MultiPoolAllocator(const char* name, size_t allocationUnit = DefaultBankUnit,
								size_t minBlockSize = DefaultMinBlock)

MultiPoolAllocator(const char* name, TInitializerList initialConfigurations,
					   size_t allocationUnit = DefaultBankUnit, size_t minBlockSize = DefaultMinBlock)

Function description

Both forms end at the same two statements: record whichever allocator is current at this instant as parentID, then register this object with the manager. Everything between them decides only how many banks exist at the moment the object becomes usable. 

	parentID = hbe::MemoryManager::GetCurrentAllocatorID();
…
	id = mmgr.RegisterAllocator(this, name, false, capacity, allocFunc, deallocFunc);

From Engine/Memory/MultiPoolAllocator.cpp, both MultiPoolAllocator::MultiPoolAllocator() overloads

The AllocatorScope a caller happens to be standing in when it constructs an allocator therefore decides where every bank's backing buffer is later borrowed from, and which allocator the destructor opens as its scope. That is recorded once, at construction, and never revised.

FormBanks at the end of constructionConfiguration cache
name, optional bank size and minimum block size None when the cache has no entry for the name — the first request for each size class then builds its own bank Read. GenerateBanksByCache is called, and its return value is discarded
name plus an std::initializer_list of PoolConfig One bank per entry, in ascending block size; the list is sorted before any bank is built Never consulted — a hand-configured ladder is never replaced by a cached one
A registration that fails is not reported to the caller. MemoryManager::RegisterAllocator returns InvalidAllocatorID when the shared proxy pool is empty, and neither constructor tests the id it stores (Engine/Memory/MultiPoolAllocator.cpp). The pool holds MaxNumAllocators minus one usable slots — 255 — and every bank is a registration of its own on top of the multi-pool's own (Engine/Memory/AllocatorID.h, PoolAllocator::PoolAllocator()). An allocator built after the 255th slot still allocates correctly through its own Allocate, because the banks it owns work; what breaks is everything that reaches it by id, which is to say its reports and any scope opened over it. See what registration records.
A minBlockSize of zero is not diagnosed, and it is a divisor. The constructor stores the argument in minBlock without a check, and CalculateBlockSize computes (requested + minBlock - 1) / minBlock (Engine/Memory/MultiPoolAllocator.cpp). Nothing in this class rejects zero, so the first request large enough to need a new bank divides by zero instead. The unit tests in Engine/Memory/MultiPoolAllocator.cpp never pass zero, so no test catches it.
The name is the allocator's identity, in two places that both outlive this object. It is the log category of every line the instance writes, and name.GetID() is the key GenerateBanksByCache looks the bank ladder up with and ReportConfiguration reports it under (Engine/Memory/MultiPoolAllocator.cpp). Two instances that share a name share a ladder and merge into one cache entry, because MultiPoolConfigCache::Normalize folds same-name entries by taking the maximum block count per size. See what an allocator name is worth for what the manager itself does with the name string.
allocationUnit reserves nothing at construction. It becomes bankSize, and bankSize is read only by CalculateNumberOfBlocks when a bank is generated later (Engine/Memory/MultiPoolAllocator.cpp). The bytes this constructor actually takes are exactly blockSize × numberOfBlocks over the configurations it was given — or none, for the name-only form — and a bank generated later may be considerably larger than allocationUnit rather than smaller.

Parameters

ParameterTypeRequirement
name const char* Copied into a StaticString member, so the buffer need not outlive the call. It is the log category and the configuration-cache key at once; a null pointer is turned into "None" by the manager, not rejected
initialConfigurations TInitializerList (std::initializer_list<PoolConfig>) Second form only. At most 128 entries — Assert(initialConfigurations.size() <= InlineBufferSize) with InlineBufferSize 128 — and nothing validates a block size or block count, so a zero-count entry reaches PoolAllocator, whose own early return leaves its free-list head uninitialised (Engine/Memory/PoolAllocator.cpp)
allocationUnit size_t Defaults to DefaultBankUnit, one mebibyte. The backing size a generated bank asks for, not a total budget and not a reservation now
minBlockSize size_t Defaults to DefaultMinBlock, 16, which is Config::DefaultAlign. Every generated block size is a power-of-two multiple of it, and every request below it is rounded up to it. Must not be zero — see the hazard above

Return value

Construction, so there is no value and no status. Both forms allocate during construction — a bank's buffer is a request to the parent allocator, and the initializer-list form sorts and reserves first — so the ambient scope at the call site is charged for the object itself. A profiling build records the sum of the initial banks' capacities as the registered capacity (Engine/Memory/MultiPoolAllocator.cpp); a build without profiling records the number and never reads it back.

Examples

From Engine/Test/TestCollection.cpp, TestCollection::RunTestAt()

		MultiPoolAllocator alloc(testName);
		AllocatorScope scope(alloc);

Every unit-testlet body runs inside its own multi-pool built by the name-only form, and the pool is what the testlet's allocations are charged to; the same function calls PrintUsage on it afterwards, from inside that scope.

From Engine/Core/TaskStream.cpp, the TaskStream::TaskStream() overloads

	, allocator("None")

A TaskStream owns one instance as a member and enters it with AllocatorScope on every pass, so the stream's pool is built before the engine has finished initialising — a bank is only generated once that pass allocates something (Engine/Core/TaskStream.cpp, TaskStream::RunLoop()).

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocatorTest::Prepare() — test-only code

		MultiPoolAllocator allocator(
				"TestMultiPoolAlloc",
				{{64, 1024}, {128, 1024}, {256, 1024}, {512, 1024}, {1024, 1024}, {2048, 1024}, {4096, 1024}});

The pre-configured form: seven size classes, one thousand and twenty-four blocks each, in a literal that is already in ascending order — the sort in the constructor is what makes the order a property of the type rather than of the literal.
