PrintUsage

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h Write the totals and one line per bank to the log - profiling builds only, and the owning thread only.

Signature

void PrintUsage() const

Function description

Writes the allocator's usage to the log under its own name: the manager's totals for this id, then one line per bank, then the block-size histogram a cached configuration would be built from. The entire body sits inside #if PROFILE_ENABLED, and Engine/Config/BuildConfig.h defines that macro to 0; neither the CMake files nor build.sh override it, so in every configuration this tree builds the function returns without reading anything. That fact comes from the sources, not from a compiled probe.

LineWhere the figure comes from
Usage = usage / maxUsage, Capacity = capacity, Alloc: …, Dealloc: …, Fallback: …One AllocStats snapshot copied out of the manager by MemoryManager::GetAllocatorStat(GetID())
[blockSize] Memory = usage / capacity, Max Usage = …, one per bankRead from each PoolAllocator directly: GetUsage(), GetCapacity(), GetUsedBlocksMax() * GetBlockSize()
Opt.{ {blockSize, peakBlocks}, … }Per-block-size sum of the banks' peak block counts, accumulated in a std::map keyed on block size — the same aggregation ReportConfiguration publishes

The redirect that decides who pays for the last of those lines opens late:

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::PrintUsage()

Only the StringBuilder is redirected, and that is the one container that would otherwise charge this pool. StringBuilder is built on a std::basic_string over an engine allocator, so its buffer is an engine allocation — and the real caller stands inside the pool it is reporting when it calls: TestCollection::RunTestAt opens AllocatorScope scope(alloc) and calls alloc.PrintUsage() before that scope closes (Engine/Test/TestCollection.cpp). Without the inner scope, the report's own text would be allocated from the bank the report is measuring, and could generate a new bank between printing a capacity and printing the histogram. The std::map above the scope needs no redirect for a different reason: a standard allocator reaches the heap through the global allocation entry points this engine replaces, so its nodes are counted as global heap and never charge this allocator's usage figures (global allocation accounting).
The twin redirects from its first statement and this one does not. ThreadSafeMultiPoolAllocator::PrintUsage opens AllocatorScope(SystemAllocatorID) before it touches a container; this member opens it around the StringBuilder only (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp against Engine/Memory/MultiPoolAllocator.cpp). Nothing states whether the difference is intended, so this page describes the code as it reads and the divergence is named as an open question on the class page. For this class the difference is not a deadlock risk: there is no lock held here, which is the whole reason the class exists.
It reads every bank without a lock, so it belongs to the owning thread. The per-bank loop walks banks while reading four counters each. Called concurrently with an allocation that generates a bank, it is reading a vector another thread may be reallocating. Nothing here can detect that, and the shared variant exists precisely because this call is not safe against a concurrent Allocate.
Cost. One statistics copy, one log call per bank plus one per distinct block size, and a std::map holding one entry per distinct block size. It never writes to this allocator's own state, and the counters it reads are maxUsage and GetUsedBlocksMax() — high-water marks that no reset clears, so the "Max Usage" figure is the peak of the instance's whole life.

Parameters

None.

Return value

void. Everything it learns goes to the log, under the allocator's own name as the log category, at Info level. Nothing it prints can be read back programmatically; the machine-readable output of the same numbers is ReportConfiguration.

Examples
