GetID

member of hbe::MultiPoolAllocator Engine/Memory/MultiPoolAllocator.h The manager's handle for this allocator, and the only name anyone outside the object can allocate against.

Signature

[[nodiscard]] auto GetID() const

Function description

Returns the allocator id the manager assigned at registration. The body is one line and lives in the header: 

		return id;

From Engine/Memory/MultiPoolAllocator.h, MultiPoolAllocator::GetID()

id is written twice in the object's life: initialised to InvalidAllocatorID in the member initialiser list, then assigned from MemoryManager::RegisterAllocator as the last statement of either constructor (Engine/Memory/MultiPoolAllocator.cpp). Between those two points — inside construction — the value is already readable, which matters because the banks built in between record the ambient allocator as their parent, never this id.

The id can be the invalid one, and this class does not say so. Registration fails by returning InvalidAllocatorID when the manager's proxy pool is empty, and neither constructor examines the value it stores (Engine/Memory/MemoryManager.cpp, the hazard on the constructor page). A caller cannot tell a successful registration from a failed one by asking this member, because both answers are indistinguishable from an allocator that was never registered — and one of them still allocates correctly. What stops working is everything keyed on the id: PrintUsage, ReportConfiguration, and any AllocatorScope opened over the instance, which lands on the dummy proxy instead.
One id for the whole ladder. Every bank registers itself and owns its own id — PoolAllocator::PoolAllocator() calls RegisterAllocator per bank (Engine/Memory/PoolAllocator.cpp) — and no public member of this class exposes them. The id this member returns is the multi-pool's own, the one that routes to Allocate. A caller that wants a specific bank has no way to ask for one.
The id dies with the object. The destructor calls DeregisterAllocator(GetID()), after which the slot is pushed back to the pool and may be handed to a different allocator (Engine/Memory/MemoryManager.cpp). Retaining this value past the allocator's lifetime does not read a stale allocator — it reads whatever took the slot.

Parameters

None.

Return value

TypeWhat you get
TAllocatorID (deduced by auto) The registration id, or InvalidAllocatorID before registration completes and forever after a registration that failed. Valid only while the allocator object is alive

Examples

From Engine/Log/Logger.cpp, Logger::StartTask()

		auto& allocatorProxy = mmgr.GetAllocatorProxy(allocator.GetID());
		allocatorProxy.threadId = threadID;

The logger's own MultiPoolAllocator member is stamped with the IO thread's id when the drain task starts, and put back on the shutdown path — under MEMORY_VERIFICATION_ENABLED only. It is the engine's one mechanism for moving an un-synchronised allocator between threads, and it is an assertion about the caller, not a lock: the id it names is the value returned here.
