Function description

Three constructors, all defined inline in the class body of Engine/Memory/Shareable.h, and only the first of them allocates. The variadic constructor is the class's only way to create a value: its single initializer is body(Body::Create(std::forward<Types>(args)...)), and Body::Create() calls MemoryManager::GetInstance().New<Body>(args...) — which constructs Body with count(0) and data built from the same arguments — and then returns newBody->Reference(). Two consequences a caller should hold at once:

FactWhy it matters
The count reaches 1 before the handle exists.A finished handle always owns a Body that already counts it, so GetReferenceCount on a freshly built handle is 1, never 0.
There is no non-allocating construction, not even a default one.The class declares no default constructor; the variadic constructor with an empty pack is the default constructor, and it allocates and default-constructs TType anyway. hbe::String's default constructor relies on this: its body is buffer->push_back('\0');, which dereferences the buffer it never explicitly created (Engine/String/String.h, String::String()).

The memory comes from whatever allocator scope the constructing thread has open, because MemoryManager::New<Type>() allocates through AllocateByType and the scoped id is static thread_local (Engine/Memory/MemoryManager.h). The matching release happens in the destructor, under whatever scope that thread has open then — see the gap on the class page.

The copy constructor takes a mutable reference, so a handle you cannot modify is a handle you cannot copy. The parameter is Shareable& rhs. Its body is the conventional one — if (rhs) body = rhs.body->Reference(); else body = nullptr; — and the else branch is reachable: copying a handle that was moved from or released produces an empty handle rather than a failure. The cost of the missing const is visible one level up: hbe::String's copy constructor is String(String& rhs), non-const for no reason of its own, because its member initialiser buffer(rhs.buffer) cannot bind a const handle. The unconstrained variadic constructor is an unrelated candidate in that situation and is not a rescue; the open question about it is named in Coverage on the class page.
The move constructor steals the pointer and is not declared noexcept. Its body is two assignments — body = rhs.body; rhs.body = nullptr; — and no self-check, which the assignment operator needs and a construction does not. After it, the source is an empty handle: false, count 0, and safe to destroy or to copy from (the copy constructor's else branch). It is not marked noexcept, and this page deliberately stops there: a container that chooses between copying and moving elements by that property is making a standard library's decision, and no page here claims what a given library does with a move that is not declared no-throw.
Move-assigning a handle does not compile. The declared operator= is the class's copy-assignment operator and takes Shareable&, which suppresses the implicit copy-assignment and, with the user-declared destructor, the implicit move assignment as well — so a = std::move(b) has no viable operator. Move construction is available, and that is what hbe::String's move constructor uses: buffer(std::move(rhs.buffer)) (Engine/String/String.h, String::String(String&&)).
