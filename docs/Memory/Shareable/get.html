Get

member of hbe::Shareable Engine/Memory/Shareable.h The shared object by reference, const or mutable, with no test for an empty handle and no protection for a shared one.

Signature

[[nodiscard]] TType& Get()

[[nodiscard]] const TType& Get() const

Function description

Two overloads defined inline in the class body of Engine/Memory/Shareable.h, each one line: return body->GetBody();, and Body::GetBody() is itself return data;. So Get() is a named spelling of the object the handle shares, returned by reference, with a const overload that follows the handle's own constness.

Neither overload tests the handle, and the non-const one is how a shared object gets mutated by two owners. Both dereference body unconditionally, so on an empty handle — one moved from or released — the call is undefined before the object is even reached. The boolean test is the caller's job, and the tree's user does it: Engine/String/String.cpp writes buffer ? buffer.Get().data() : "" rather than assuming. The non-const overload then hands out a mutable reference to an object other handles may share, and the class does nothing about that: no copy on write, no debug assertion on a non-unique count. The whole policy belongs to the caller, and hbe::String implements it by asking GetReferenceCount first.
The reference is stable for as long as the object lives. The Body is one heap allocation and never relocates, so a TType& from this function does not move when handles are copied or destroyed. What invalidates it is the object's own destruction — the last destructor or Release — so keeping this reference past the last handle is the hazard, not keeping it past a copy.

Examples

	auto& buf = buffer.Get();
	const auto index = buf.size();
	buf.resize(index + 2); // room for the letter + trailing null terminator

From Engine/String/String.cpp, String::AppendSelf(const TChar letter)

The reason this accessor exists beside operator* and operator->: take the reference once and reuse it. Every call on the handle — this one, buffer->, (*buffer) — re-reads the body pointer to reach data, so a loop that writes three elements through buffer-> reaches the same object three times by way of the handle, and one local reference reaches it three times directly. Whether a mutation here is legal is decided one level up, by the count, not here.
