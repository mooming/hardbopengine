operator=

member of hbe::Shareable Engine/Memory/Shareable.h Releases first, then shares - with no return value, no self-assignment test, and no move-assignment form at all.

Signature

Shareable& operator=(Shareable& rhs)

Function description

Defined inline in the class body of Engine/Memory/Shareable.h. The body releases what this handle holds and then takes a reference on the source: 

Release();

if (rhs)
{
	body = rhs.body->Reference();
}

From the copy-assignment operator of hbe::Shareable in Engine/Memory/Shareable.h; this block is an excerpt of an operator= rather than a quotation of one named symbol.

Order matters and is the safe half of the design: Release runs first, so the old object's count drops (and the old object may die) before the new reference is taken, and the assignment is correct when the two handles share one object. The parameter is a mutable reference, as in the copy constructor, so a handle you cannot modify cannot be assigned from either.

It returns a reference and returns nothing. The declaration is Shareable& and the body has no return statement: control reaches the end of a function that returns a reference. Chained assignment (a = b = c) and any read of the expression's value therefore use a value the code never produced. What a given compiler yields there is not a contract, and it is not a question these pages answer — the defect belongs to the source, and the safe rule for a caller is to treat this operator as returning nothing. The tree's only user never assigns through it: hbe::String::operator= reaches its copy by building a temporary and calling Swap (Engine/String/String.cpp, String::operator=), so no in-tree path observes the missing return.
Self-assignment empties the handle. There is no this == &rhs test, and one is not merely missing cosmetics here: Release() clears body — and because rhs is this object, the cleared pointer is the one the following if (rhs) reads. It is false, so nothing is adopted and the handle ends up naming nothing. If this handle held the last reference, the object is destroyed on the way; if other handles shared it, they keep it alive and this handle simply stops naming it. Either way x = x turns an owning handle into an empty one, which the boolean test will report honestly afterwards and Get will not. No testlet covers it, and the class has no test file of its own.
Because this is the copy-assignment operator, there is no move assignment. A user-declared copy-assignment operator suppresses the implicit one, and the user-declared destructor suppresses the implicit move assignment, so a = std::move(b) finds no viable operator — while a = b from a mutable lvalue compiles. The workaround the engine uses for the same reason is construction: String(String&&) move-constructs its handle (Engine/String/String.h).

Examples
