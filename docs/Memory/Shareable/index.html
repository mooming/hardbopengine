Shareable

Engine/Memory/Shareable.h template <typename TType, typename RefCount = uint8_t> A reference-counted handle to one object the MemoryManager allocated: a counter and a value in one Body, and a copy-on-write contract its one user has to enforce itself.

Class description

template <typename TType, typename RefCount = uint8_t> class Shareable at Engine/Memory/Shareable.h is a reference-counted handle to one object that the MemoryManager allocated. The handle is a single Body*; Body is a private nested type declared inside Shareable that holds a RefCount count and a TType data next to each other, so control block and object are one allocation. Both declarations are in the properties table below.

Control block and object are therefore the same allocation, which is the cheap half of the design: one MemoryManager::New<Body>() call rather than two, and no separate block to chase when the count is read. The other half of that choice is fixed by the same line: there is no weak count, no stored deleter, no stored allocator, and the count's width is a template argument that defaults to uint8_t.

The tree's only user is hbe::String, whose entire storage is one handle — Shareable<Vector<TChar>> buffer; in Engine/String/String.h, where Vector is hbe::HVector — and Applications/ contains no use of the class. It is a copy-on-write handle in that user, which is the contract the rest of this page is written against: String::operator=(const String&) in Engine/String/String.cpp asks buffer.GetReferenceCount() > 1 and takes one of two branches — Swap(String(rhs.ToCharArray())), which builds a whole new String and exchanges the handles, or, when the count says this handle is alone, resize to rhs's length and memcpy its characters into this buffer.

That GetReferenceCount() > 1 is the question "is anyone else looking?", and the two branches are the only safe answers: build a new buffer if someone is, mutate in place if the count says you are alone. Every rule below follows from the same dependency — the count is the only thing standing between operator-> and a mutation two owners both thought they were entitled to.

Nothing is atomic, so a shared object may not be shared across threads. count is a plain RefCount, and Engine/Memory/Shareable.h names no mutex, no atomic and no fence: Reference() is ++count and Dereference() is --count. Copying a handle, letting one go out of scope, and Release all mutate the same non-atomic counter, so two handles naming one object on two threads are in a data race: a lost increment leaves the object freed while a handle still names it, and a lost decrement leaves it allocated with nobody able to free it. Two handles naming one object across threads are safe only under locking the caller supplies, and nothing in the engine supplies it today. What no page here claims — because the code does not say — is that any of this was ever intended to be thread-safe.
The object is allocated and freed under whoever is current at that moment, not under one owner. Body::Create() calls MemoryManager::New<Body>() and Dereference() calls MemoryManager::Delete<Body>(), and both of those go through the manager's current scoped allocator — which in Engine/Memory/MemoryManager.h is a static thread_local id. A handle created inside an AllocatorScope on one thread and released in another scope on another thread therefore frees memory through an allocator that never allocated it. This is the cross-allocator free that PoolAllocator's pages describe and solved by recording parentID at construction; Shareable records nothing, and no page here claims the manager tolerates it.
The default count is one byte wide, and the 256th owner is the failure. RefCount defaults to uint8_t, and every in-tree use takes the default. Reference() is a bare ++count, so a 256th copy of one object wraps the count to 0; Dereference() is guarded by if (count > 0), so from that moment every release is a no-op and the object can never be freed. A container of handles that expects more than 255 simultaneous owners of one value must be instantiated with a wider RefCount; no code in the tree tests the boundary.
Only a mutable handle can be copied or assigned. The copy constructor and the copy-assignment operator both take Shareable& — not a reference to const — so a handle you cannot modify is a handle you cannot copy. hbe::String demonstrates the cost at the level above: its copy constructor is String(String& rhs), non-const for no reason of its own, because the member initialiser buffer(rhs.buffer) cannot bind a const handle to that constructor. Assignment is narrower still: because this operator= is the class's copy-assignment operator and takes a non-const reference, there is no implicitly declared move assignment either, so a = std::move(b) does not compile. Move construction is available and is what String(String&&) uses.
There is no "empty" constructor, and default construction still allocates. The class declares no default constructor; what default-constructs a Shareable is the variadic template <typename... Types> Shareable(Types&&... args) with an empty pack, and its initializer is Body::Create(...) — an allocation and a construction of TType before the handle can be used at all. So Shareable<T> handle; is never null and never free, and the only ways to hold no object are to be moved from (constructors) or to call Release. That is why the null tests in Engine/String/String.cpp guard against a moved-from String, not an uninitialised one.

Template parameters

ParameterWhat it constrainsWhat getting it wrong costs
typename TType The owned type. It is constructed in place inside Body from whatever arguments the handle receives, so it must accept them; the handle exposes it only as TType&, const TType&, TType* and const TType*. Nothing constrains the variadic constructor's pack, so a bad argument list fails inside Body::Create() and Body's constructor rather than at the call site.
typename RefCount = uint8_t The counter's type: its width sets the maximum number of simultaneous owners, and its signedness sets what a decrement below zero means. The guard in Dereference() is count > 0, which is only meaningful for an unsigned type. Too narrow wraps silently at 256 with the default, and a wrapped count makes the object permanently uncreatable-again: see the note above. A signed RefCount would make the count > 0 test a signedness comparison instead of a liveness test.

Non-member helper functions

None. There is no operator==, no std::hash specialisation, no free MakeShared factory: handles are created by constructing them and compared — if at all — by the address of the object the caller already holds. That absence is why hbe::String carries its own hash cache rather than hashing its buffer, and it is recorded in Coverage rather than presented as a style choice.

Thread-safety of a shared object, in either direction. The pages state the fact (no atomic, no lock, one plain counter) and stop there. Whether the engine intends handles to cross threads at all is not answered by Engine/Memory/Shareable.h or by its one user, and no test exercises it. A confident sentence either way would be a guess.

operator='s missing return value: what a caller receives. The declaration returns Shareable& and the body ends without a return statement, so the value is indeterminate; what a given compiler produces there is not a contract this page can state, and no in-tree caller assigns through this operator at all (hbe::String::operator= reaches its copy through Swap instead).
Whether the variadic constructor makes a handle copy-constructible from a const handle. Not settled here. The copy constructor cannot bind a const reference, and the unconstrained variadic constructor is a candidate that would fail deeper in the instantiation rather than at the call site; which of the two a compiler reports is not a fact about this class. What is settled is that no well-formed copy from a const handle exists — Engine/String/String.h's copy constructor takes String& for that reason.
The members of the nested Body: Create, GetBody, Reference, GetRefCount, Dereference and its constructor. Private to Shareable and unreachable from a caller, so they are described here and on the pages that use them (constructors, destructor, GetReferenceCount) rather than as one page per name; a nested class belongs to its owner's page. Their behaviour is quoted where a caller depends on it — the counter's width, the first reference taken by Create(), and the count > 0 guard that decides what the last release does.
Body::SizeOfType. Documented as unread: a search of Engine/ finds no use. Whether it is a leftover or a placeholder for a sized delete is not stated anywhere in the source, so no page invents an answer.
Copy-on-write as a policy. The class provides a count and nothing else: it never copies on write, never defers, never forks. The policy lives in Engine/String/String.cpp, and the String pages own it. This page quotes the assignment operator because it is the only in-tree reading of GetReferenceCount as a decision.
