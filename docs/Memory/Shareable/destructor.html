Destructor

member of hbe::Shareable Engine/Memory/Shareable.h Drops this handle's reference; if the count reaches zero the object is destroyed and its memory returned by the allocator current then.

Signature

~Shareable()

Function description

Defined inline in the class body of Engine/Memory/Shareable.h. The body is one guarded release: 

if (body != nullptr)
{
	body->Dereference();
	body = nullptr;
}

From Engine/Memory/Shareable.h, hbe::Shareable::~Shareable

An empty handle — one that was moved from or released — costs one pointer test and nothing else, so the destructor is safe to run twice. Who decrements: this handle, and only this handle's reference. The decrement itself lives in Body::Dereference(), which is if (count > 0) { --count; ... }.

What the last release does, in four steps. When the decrement takes the count to zero, Dereference() calls MemoryManager::GetInstance().Delete<Body>(this). In Engine/Memory/MemoryManager.h that template runs ptr->~Type() and then DeallocateTypes<Type>(ptr, 1), so: Body's destructor destroys data (running TType's destructor), the sizeof(Body) block is returned to the manager's current scoped allocator, and every handle that shared the object is now dangling — because nothing clears them. There is no resurrection: the same value can be created again by a new handle, and it will be a different object.
The deallocation is charged to whoever is current when the last handle dies. DeallocateTypes uses GetScopedAllocatorID(), and the scoped id is static thread_local in Engine/Memory/MemoryManager.h. So the allocator that frees a shared object is whichever scope the last-owner's thread happened to have open — not the scope that allocated it, and nothing records the pairing. A handle created inside one AllocatorScope and dropped inside another frees memory through an allocator that never allocated it; whether that is detected anywhere is a question for the MemoryManager pages, not an answer this one can give. A TType destructor that allocates runs under the same current scope, one step earlier.
The guard is the leak, and the design has no cycle breaker. if (count > 0) means a count that reached 0 by any route other than a real last owner — the wrap described on the class page, at 256 handles with the default uint8_t — makes every later release, including this destructor's, a silent no-op, and the object is never freed. For the same reason there is no cycle collection: Body has one count and no weak count, so if a TType ever holds handles that lead back to itself, nothing will reach zero and the ring leaks. The tree's one user holds Vector<TChar>, which cannot form such a ring.

Parameters

None.

Return value

Nothing. Afterwards this handle names nothing; other handles naming the same Body are unaffected in count, and the one that brings the count to zero is the one that destroys the object.

Examples

	void Swap(String&& target) noexcept
	{

		hashCode = target.hashCode;

From Engine/String/String.h, String::Swap

The one place String reshuffles buffers without touching a count: after Swap exchanges the two pointers, the temporaries being swapped destroy themselves and each one drops the reference it now holds. Assignment reaches this destructor through exactly that shape — String's copy path builds a temporary and swaps with it, so the buffer the old value owned is released by the temporary's destructor rather than by operator=.
