Module Index / Memory / Shareable / operator->

operator->

member of hbe::Shareable Engine/Memory/Shareable.h The member-access route to the shared object - the door through which a shared buffer gets mutated without asking the count.

Signature

[[nodiscard]] TType* operator->()

[[nodiscard]] const TType* operator->() const

Function description

Two overloads defined inline in the class body of Engine/Memory/Shareable.h, each returning &body->GetBody(); — the address of the data member of the shared Body, so that handle->member reaches the object. The const overload yields a pointer to const TType, which is how a handle you cannot modify hands out read-only access.

This is the copy-on-write breach, and the class will not prevent it. The non-const overload hands out a mutable TType* to an object that other handles may share, with no reference-count test on the way. hbe::String shows both sides of that in one function: its copy-assignment path first asks GetReferenceCount, and only in the branch where the count is 1 does it write — buffer->resize(length) — while reads of another handle go through the const overload (rhs.buffer->size()). Any other caller that writes through this operator without asking the count first mutates a value its copies are still reading. Nothing in Engine/Memory/Shareable.h asserts, copies or refuses.
No null test, and the pointer is a member of the shared block. Both overloads dereference body unconditionally, so on an empty handle — moved from or released — the call is undefined before it returns anything; guard with the boolean test as Engine/String/String.cpp does. The returned pointer points inside the Body, which never relocates, so it stays put for the object's lifetime and becomes dangling exactly when the last handle is destroyed (destructor) — not when another handle is copied.
