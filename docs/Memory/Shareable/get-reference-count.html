GetReferenceCount

member of hbe::Shareable Engine/Memory/Shareable.h How many handles share this object - the number a copy-on-write mutation decides on, and the first thing to break at 256 owners.

Signature

[[nodiscard]] RefCount GetReferenceCount() const

Function description

Defined inline in the class body of Engine/Memory/Shareable.h. The body is return body != nullptr ? body->GetRefCount() : 0; — the count the shared Body carries, or 0 for a handle that names nothing. The count is the number of live references, not the number of handles that ever existed: Body::Create() takes the first before any handle exists (constructors), every copy takes one more, and every destruction or Release drops one.

AnswerWhat the handle may safely doIn-tree use
1Mutate the object: no other handle names it.The else branch of String::operator=, which resizes and memcpys into the buffer in place.
greater than 1Not mutate it: somebody else is reading the same object.The guard of the same function — if (buffer.GetReferenceCount() > 1) — which takes the copy-on-write branch instead.
0Nothing: the handle is empty, and this answer means "no object", not "one free slot".Reached by a moved-from or released handle; see the gap below for the other way to get it.
With the default uint8_t counter, 256 owners of one object make it report 0. Reference() is a bare ++count, so the 256th reference wraps an 8-bit count to 0. From then on the destructor cannot free the object (Dereference() is guarded by count > 0) and this function reports 0 for an object with 256 live owners. Read together with the table above, that is the dangerous pair: a copy-on-write caller testing > 1 gets "you are alone", and mutates in place a buffer that everyone else is still reading. Instantiate a wider RefCount if a value can have that many simultaneous owners; the tree's one user does not test the boundary.
The answer is a snapshot of a plain, non-atomic byte. count is not an atomic and nothing locks it (see the class page), so the value is true at the instant of reading and not afterwards. The check-then-mutate pattern above is sound because a single thread that holds the only handle cannot have its count changed by anyone else; in a program where two threads touch handles naming one object, this function is the racing read, not the protection.

Parameters

None.

Return value

TypeWhat you get
RefCountThe shared object's owner count, or 0 when this handle names nothing. The type is the template argument, uint8_t by default — so the return type itself is a warning about the width of the answer.

The whole copy-on-write decision in one comparison: share, therefore rebuild; alone, therefore overwrite. It is also the reason this function is [[nodiscard]] in a class where very little is — the answer is the only input to that branch.
