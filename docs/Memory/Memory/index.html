Memory

Engine/Memory/Memory.h namespace hbe The free-function layer over the allocator system: New and Delete in two forms each - one driving an allocator object the caller holds, one delegating to the MemoryManager and the calling thread's allocator scope - plus two std::function allocation shapes

Class description

Engine/Memory/Memory.h is not a class: it is the engine's free-function layer over the allocator system, and this page is the folder the coverage ledger demands for it. The file declares two aliases and four function templates, in two matched pairs. The allocator pair — New(TAllocator&, ...) and Delete(TAllocator&, TType*) — works on any allocator object the caller holds: anything with a value_type and allocate/deallocate in STL shape, including SystemAllocator (docs/Memory/SystemAllocator/). The pair without an allocator — New(TTypes&&...) and Delete(TType*) — is a one-line delegation to MemoryManager::New and MemoryManager::Delete (Engine/Memory/Memory.h), which means it allocates through the calling thread's current allocator scope (docs/Memory/AllocatorScope/), exactly as AllocateByType does.

The two pairs differ in more than the argument list. The allocator pair checks, at compile time, that the allocator's value_type and the type being constructed have the same sizeof — sizes, not types — and then asks the allocator for exactly one such element, placement-constructs, and hands back the live pointer; the release calls the destructor and hands the pointer back with the element count 1. The manager pair carries no such assert, because the manager sizes by sizeof(TType) itself — and inherits the routing rule of the id-free paths: the Delete(ptr) call is routed by whichever allocator is current when it runs, not by whichever one answered the New. That is the same fact that forced the allocator-teardown fixes this module records on the scope destructor page (docs/Memory/AllocatorScope/destructor.html), and inside a ScopedAllocator (docs/Memory/ScopedAllocator/) it is the reason construct and destroy are written in the same nesting level.

All four functions are declared noexcept and construct objects inside themselves. A constructor that throws cannot propagate through them: the exception reaches the function's own noexcept specification and the process terminates. The types these helpers are for are types whose construction does not throw — which is a caller-side condition, since nothing in the file tests it.
The allocator-taking Delete and the manager-taking Delete both call the destructor through the pointer with no null test. Delete(allocator, ptr) is ptr->~TType(); allocator.deallocate(ptr, 1); as written (Engine/Memory/Memory.h): a null pointer is a crash, not a no-op. The manager form is the same call on its Delete(Type*), which likewise starts at ptr->~Type() (its page).

Non-member helper functions

None beyond the four functions above — the point of this file is that its whole surface is non-member. There are no types to extend, no state in the file, and the state those four functions touch (the thread's scoped allocator id) belongs to MemoryManager.
