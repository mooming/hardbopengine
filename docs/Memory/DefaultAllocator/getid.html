GetID

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h The one member: a borrowed registration id, naming whoever was current on this thread when the object was constructed.

Signature

[[nodiscard]] auto GetID() const

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::GetID() const. auto deduces TAllocatorID (int, from Engine/Memory/AllocatorID.h) and the value is the one member the class has. This is the whole state of an allocator instance: no pointer, no capacity, no counter — a number naming somebody else's registration. 

[[nodiscard]] auto GetID() const
{
	return allocatorID;
}

[[nodiscard]] auto GetSourceAllocatorID() const
{
	return allocatorID;
}

From Engine/Memory/DefaultAllocator.h, DefaultAllocator::GetID() const and DefaultAllocator::GetSourceAllocatorID() const

The value names whichever allocator was current on the constructing thread — see the constructor — and it never changes afterwards. The other allocator classes in this module answer the same question about a registration they own: PoolAllocator::GetID returns the id its constructor registered and its destructor deregisters. Here the id is borrowed: this object neither registered it, nor can it tell whether the registration is still alive.

What the number is worth after the allocator it names dies. MemoryManager::DeregisterAllocator clears the proxy's function pointers and returns the slot to proxyPool, so the integer this function returns keeps pointing at a slot rather than at the allocator that occupied it — and MemoryManager::RegisterAllocator pops from that same pool, which means a later registration can occupy the number. Nothing here detects that; operator== will happily call two allocators equal because they hold the same stale number.

Parameters

None.

Return value

TypeWhat you get
auto → TAllocatorIDThe recorded registration id, by value — identical to GetSourceAllocatorID. It is MemoryManager::SystemAllocatorID (0) whenever the object was constructed with no AllocatorScope open, which is what sends allocate down its malloc fast path.

Examples

Illustrative — no engine call site asks a DefaultAllocator for its id; the containers that hold one use it as an opaque member and the class's own allocate reads the member directly rather than this function.

PoolAllocator alloc("MyPool", 64, 128);
{
	AllocatorScope scope(alloc);

	std::vector<int, DefaultAllocator<int>> v;
	// v.get_allocator().GetID() == alloc.GetID(): the scope that was open when v was built.
}

The reason the accessor exists at all is the template constructor in Engine/Memory/AllocatorScope.h, which accepts any object exposing GetID() — the shape that lets one line, AllocatorScope scope(allocator);, work for a pool, an arena, or an adapter holding a borrowed id.
