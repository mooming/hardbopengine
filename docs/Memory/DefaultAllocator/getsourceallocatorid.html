GetSourceAllocatorID

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h The same id as GetID, under the name the converting constructor reads when a container rebinds an allocator to another type.

Signature

[[nodiscard]] auto GetSourceAllocatorID() const

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::GetSourceAllocatorID() const. It returns the same member as GetID, and the reason it exists is the one place in the tree that calls it: this class's own converting constructor. 

template <class TOther>
explicit DefaultAllocator(const DefaultAllocator<TOther>& rhs) noexcept
	: allocatorID(rhs.GetSourceAllocatorID())
{
}

From Engine/Memory/DefaultAllocator.h, DefaultAllocator::DefaultAllocator(const DefaultAllocator<TOther>&)

That constructor is what every type-changing copy of an allocator goes through, and the standard library performs such copies constantly: a node-based container holds an allocator for its node type, not for the value type the user wrote, and it obtains one by building DefaultAllocator<Node> from the DefaultAllocator<T> the user supplied. Because the constructor reads the source's id instead of asking the MemoryManager what is current now, the rebound allocator serves the same arena as its parent, and every node of a container and the container's own element storage agree on one allocator. Had it captured the ambient id instead, a container moved between two scopes would have had its elements and its nodes allocated from two different allocators — and operator== would then report two allocators inside one container as unequal.

The name reads "the id of the allocator I was made from", which is precisely the value the constructor stores. For a default-constructed instance the two accessors agree by definition, so GetSourceAllocatorID() on a fresh allocator is simply GetID().

Two names, one member, and no code that can tell them apart. Both are [[nodiscard]] auto returning allocatorID; nothing in the repository reads GetSourceAllocatorID() except the converting constructor named above, and nothing reads it through an interface that would notice if the two ever diverged. Any future behaviour difference between them — an id that records where an allocator came from rather than where it allocates — would be invisible to allocate, which uses the member directly, and to operator==, which compares the member too.

Parameters

None.

Return value

TypeWhat you get
auto → TAllocatorIDThe recorded id — always the same value GetID returns, and always the id this object was either default-constructed with or copied from another allocator's.

Examples

std::vector<int, DefaultAllocator<uint8_t>> bytes;
DefaultAllocator<int> ints(bytes.get_allocator());

Illustrative — the spelling is what the engine's own containers rely on; the repository never writes the conversion by hand.

Engine/Container/HashMap.h and Engine/Container/Map.h default their allocator parameter to DefaultAllocator<uint8_t> and Engine/Container/LinkedList.h to DefaultAllocator<LinkedListNode<TType>>, so the element type of the allocator is a container's choice rather than the user's; whenever a library type rebinds one allocator to another element type, this is the accessor the new allocator's id came through. The constructor is explicit, so the hand-written form above must name the type — an implicit conversion between two DefaultAllocator instantiations does not exist.
