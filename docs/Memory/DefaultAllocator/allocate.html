allocate

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h n elements of T: straight to malloc when the recorded id is the system allocator, otherwise through a per-call AllocatorScope into the named registration.

Signature

[[nodiscard]] T* allocate(std::size_t n) noexcept

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::allocate(std::size_t n) noexcept: the allocator entry point the standard library and the engine's own containers call, for n elements of T. It has two paths, and which one runs is decided by the four bytes the object holds. 

if (allocatorID == MemoryManager::SystemAllocatorID)
{
	return static_cast<T*>(malloc(n * sizeof(T)));
}

AllocatorScope scope(allocatorID);
auto& mmgr = MemoryManager::GetInstance();
auto ptr = mmgr.AllocateByType<T>(n);

return ptr;

From Engine/Memory/DefaultAllocator.h, DefaultAllocator::allocate(std::size_t n)

The first path is the one most engine allocations take, and the reason is arithmetic rather than intent: MemoryManager::SystemAllocatorID is 0, MemoryManager::scopedAllocatorID is initialised to 0 in Engine/Memory/MemoryManager.cpp, and a default-constructed allocator records whatever is current — so every allocator built with no AllocatorScope open matches the comparison and goes straight to malloc. That is a deliberate fast path: no scope, no manager instance, no proxy dispatch. It is also an accounting hole — the replacement operator new in Engine/Memory/GlobalAllocation.cpp is AllocateAccounted(...), so heap traffic that goes through new is counted and this path, calling malloc directly, is not counted by anything.

The second path opens a scope on the recorded id and asks the manager to allocate by type, and the scope is what makes the recorded id mean anything: MemoryManager::AllocateByType<T> reads the scoped id (GetScopedAllocatorID()), so installing the recorded value for the duration of the call is how an allocator captured long ago is still the one that answers. It costs an AllocatorScope per allocation — a manager lookup, a read of the previous id and two writes of the thread-local, in both directions — which is exactly the indirection the fast path exists to avoid. The scope requires a live manager: AllocatorScope's constructor and MemoryManager::GetInstance() both go through FatalAssert(mmgrInstance != nullptr), which is live in every configuration.

At exhaustion it returns whatever it gets: noexcept means no std::bad_alloc. Neither path tests the result. On the fast path a failing malloc returns null and this function returns null. On the slow path the answer is the named allocator's own policy — a pool falls back to its parent, a multi-pool generates a bank — and if that still fails, MemoryManager::Allocate ends with Assert(ptr != nullptr, "Allocation Failed"): an abort in Debug and Dev, and in Release a null pointer returned here and handed to the caller. The allocator contract expects either memory or a throw, so the container that receives null proceeds to write through it. A caller that must survive exhaustion cannot learn that from this return value; the only signal the engine offers is the assert, and only outside Release.
A stale id is dispatched, not diagnosed. AllocatorScope's constructor routes through MemoryManager::SetScopedAllocatorID, which replaces an out-of-range id that is not InvalidAllocatorID with 0 after an error log — and leaves InvalidAllocatorID (-1) installed, which then trips Assert(id != InvalidAllocatorID) inside MemoryManager::Allocate. Any in-range id, live or dead, indexes allocators[id] directly and calls allocProxy.allocate(allocProxy.allocator, nBytes) behind Assert(allocProxy.allocate != nullptr). So an allocator that recorded a registration which has since been deregistered either aborts, or calls through a null function pointer, or — once MemoryManager::RegisterAllocator has reused the slot — quietly allocates from a different allocator than the one that was captured. This is the hazard the header's own warning is about, and the constructor page states the rule that avoids it.
Alignment is whatever the far end happens to provide. allocate never reads alignof(T), takes no alignment argument and offers no aligned form, so the alignment of the block is a property of the path rather than of the request: malloc's fundamental alignment on the fast path, and on the slow path whatever the named allocator guarantees — the engine allocators round by Config::DefaultAlign (16). A type whose alignment requirement exceeds that is served at the alignment that was going to be handed out anyway, and the caller gets no diagnostic. Per-allocator alignment belongs to the pages in the allocator catalogue.

The size handed downstream is n * sizeof(T), computed here and again by MemoryManager::AllocateByType<T>'s caller-visible arithmetic — the same expression, so the release in deallocate recomputes it and agrees. There is no overflow check on that product, and a zero request is not special-cased: on the slow path MemoryManager::Allocate returns nullptr for 0 bytes, while the fast path asks malloc for 0 and returns whatever the platform returns. Two further costs are worth knowing for a hot container: the per-allocation scope on the slow path, and the fact that nothing is synchronised here — the manager reads allocators[id] without a lock (its statsLock guards statistics only), so thread-safety is the named allocator's problem, exactly as it is for PoolAllocator.

Parameters

ParameterTypeRequirement
nstd::size_tElement count, not bytes: the product n * sizeof(T) is what is requested downstream. No overflow check, no zero check, and no alignment input.

Return value

TypeWhat you get
T*Uninitialised storage for n elements. Memory from the system allocator when the recorded id is MemoryManager::SystemAllocatorID, memory from the named registration otherwise, and null when the far end failed — with no exception and no log in Release.

Both assertions are about this function: constructing v must not touch the pool, because the vector holds no elements yet, and the first reserve must land inside the pool's buffer. The second is true only because the allocator was constructed while the scope was open, took the pool's id, and so reached the pool rather than malloc. Engine containers use the same function without the standard library in between: Engine/Container/HashMap.h and Engine/Container/Map.h hold a DefaultAllocator<uint8_t> member and call allocator.allocate(allocSize) for their entry storage, and Engine/Container/LinkedList.h reaches it once per node through hbe::New in Engine/Memory/Memory.h.
