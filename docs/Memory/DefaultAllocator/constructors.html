DefaultAllocator

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h Records a registration id once: the thread's current allocator, or another instantiation's. Every later call is a dispatch on that snapshot.

Signature

DefaultAllocator()
		: allocatorID(MemoryManager::GetCurrentAllocatorID())

template <class TOther>
	explicit DefaultAllocator(const DefaultAllocator<TOther>& rhs) noexcept
		: allocatorID(rhs.GetSourceAllocatorID())

Function description

Both are defined inline in Engine/Memory/DefaultAllocator.h. They have one job, and it is the whole contract of the class: choose a registration id once, at construction, and never look at the allocator scope again. The default form records whatever is current on this thread; the template form copies the id out of an allocator of another element type. There is no constructor that takes a TAllocatorID, no constructor that takes an allocator object, and no way to point one of these at a pool except by opening an AllocatorScope first or by copying one from something already built.

A DefaultAllocator is a photograph of the scope that was open when it was built. MemoryManager::GetCurrentAllocatorID() is a read of the thread-local scopedAllocatorID and needs no manager instance, so construction is legal before an Engine exists — and what it captures there is 0, because that is the value MemoryManager::scopedAllocatorID is initialised to in Engine/Memory/MemoryManager.cpp. Since MemoryManager::SystemAllocatorID is also 0, an allocator built outside every scope is the allocator whose allocate goes straight to malloc. Inside a scope it captures that scope's id and keeps it for the object's whole life: two identical containers built in two different scopes are not the same allocator, and everything that follows — which pool serves them, whether they can swap (operator!=) — follows from where each one was constructed.
Copying and moving the allocator is free; the registration behind it is the thing with a lifetime. The class declares no copy constructor, no move constructor, no assignment operators and no destructor, so all four special members are implicit and the object is a plain int: a probe of the declaration shape with c++ -std=c++2b -Wall -Wextra -fsyntax-only reports is_trivially_copyable_v true and sizeof(A) == sizeof(int). Nothing about a copy is dangerous in itself — unlike InlineMonotonicAllocator, where a copy duplicates a whole arena and keeps one registration. The danger is the referent: MemoryManager::DeregisterAllocator clears a proxy's function pointers and returns its slot to proxyPool, and MemoryManager::RegisterAllocator hands those slots out again, so a container that outlives the allocator it recorded holds an id that either names nothing usable or, worse, names something else entirely. That is the hazard the header's own warning states — this adapter is the one allocator in the module whose value can outlive what it refers to, and it is most likely to happen with the short-lived allocators, a stack allocator opened for a frame or a pool opened for one load phase, whose registrations come and go. The rule that keeps it safe is not to release through stale ids but to keep the container inside the scope that supplied the id.

The template form exists for the type-changing copies the standard library performs when it rebinds an allocator: a node-based container builds DefaultAllocator<Node> from the user's DefaultAllocator<T>, and reading GetSourceAllocatorID rather than the ambient scope is what keeps every node of a container in the same arena as its elements. It is explicit, and the probe confirms the consequence — is_convertible_v<DefaultAllocator<int>, DefaultAllocator<double>> is false — so the library's explicit construction works while an implicit conversion between two instantiations does not exist; hand-written code must name the target type.

No AllocatorScope is open here, so every one of those hundred vectors captures 0 and every growth step takes the malloc path — a hundred vectors and roughly a thousand reallocations that never touch the MemoryManager at all. The testlet in the same file that does open a scope, "Basic Usage", is the counter-example quoted on allocate: one reserve inside a pool's scope and the pool's usage figure moves. Between those two testlets sits the entire behaviour of this class, and it is decided in the constructor.
