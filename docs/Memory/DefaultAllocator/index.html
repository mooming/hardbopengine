DefaultAllocator

Engine/Memory/DefaultAllocator.h namespace hbe template <typename T> final STL allocator adapter holding one registration id: malloc when that id is the system allocator, a scoped MemoryManager dispatch otherwise, and the default allocator of every engine container.

Class description

template <typename T> class DefaultAllocator final at Engine/Memory/DefaultAllocator.h is the adapter between the C++ allocator interface and this engine's registration-based memory system. It holds one TAllocatorID and nothing else. It is the default of every container in the tree — the HSTL and Container aliases all name it as their allocator parameter — and it is named "default" in the literal sense: an engine container written without an allocator argument is using this class, and the allocator it will actually allocate from is decided by whatever AllocatorScope happens to be open where the container is constructed.

It reaches the engine in three ways and is registered nowhere. The standard library calls it through std::allocator_traits whenever one of the aliases above grows. The engine's own containers hold it as a member and call it directly — Engine/Container/HashMap.h and Engine/Container/Map.h keep a TAllocator allocator; and call allocator.allocate(allocSize) for their entry arrays. And hbe::New<TType>(allocator, args...) in Engine/Memory/Memory.h calls allocator.allocate(1) per object, with a static_assert(sizeof(typename TAllocator::value_type) == sizeof(TType)) beside it, which is one reason the class publishes value_type at all. What all three reach is the same pair of paths: a direct malloc when the recorded id is MemoryManager::SystemAllocatorID, and otherwise a per-call AllocatorScope plus MemoryManager::AllocateByType<T>, described on allocate and deallocate.

It is the one allocator in the module whose value can outlive what it refers to. Construction photographs the thread's current scope; the id is then inert. Meanwhile MemoryManager::DeregisterAllocator clears a proxy's function pointers and returns its slot to proxyPool, and MemoryManager::RegisterAllocator deals those slots back out — so an id is re-used, and a container that outlives the allocator it recorded will allocate and free through a dead slot, a stranger's arena, or an Assert. The header states the same warning in its own words: this adapter is the one to be careful with when the current allocator is a short-lived one, the stack-allocator-shaped registrations that open and close around a phase. The discipline is the one the engine's own call sites follow: build the container inside the scope, and let it die inside it too.
Copying a container is safe, cheap, and changes nothing about where its memory lives. No special member is declared, so copy and move are implicit: a probe of the declaration shape with c++ -std=c++2b -Wall -Wextra -fsyntax-only reports all four true, is_trivially_copyable_v true, and sizeof(A) == sizeof(int). The same probe records what the standard library synthesises from the absence of the rest of the interface: is_always_equal, propagate_on_container_copy_assignment, propagate_on_container_move_assignment and propagate_on_container_swap all false, because the class is not an empty type. So containers copy the allocator by value, but they will not adopt one silently, they compare before stealing a buffer (operator==), and a rebound allocator inherits its source's id rather than the ambient scope (GetSourceAllocatorID) — which is what keeps a node-based container's nodes in the same arena as its elements.

Three further consequences are worth holding before reading the method pages. Exhaustion is not this class's decision: allocate is noexcept, throws nothing and tests nothing, so a failing request comes back as null (fast path) or as whatever MemoryManager::Allocate's Assert(ptr != nullptr, "Allocation Failed") allows — an abort in Debug and Dev, null in Release. Alignment is likewise not offered: no argument, no aligned form, no read of alignof(T). Nothing here is synchronised, and the manager's dispatch reads allocators[id] without a lock (its statsLock guards statistics only), so thread-safety is the named allocator's property; the per-call scope mutates a thread-local, so it is per-thread by construction. And the fast path is an accounting hole worth stating plainly: the replacement operator new in Engine/Memory/GlobalAllocation.cpp records what it sees, and a path that calls malloc directly is visible to nothing.

Template parameters

ParameterKindWhat it constrains
TtypenameThe element type the allocator is instantiated for — the type the standard library rebinds it to, never a type the allocator inspects beyond sizeof(T). It sizes every request (n * sizeof(T), recomputed identically in allocate and deallocate), it is what value_type reports to std::allocator_traits and to hbe::New's static assert, and it must be a complete type wherever either function is instantiated.

T appears nowhere in the id logic, and that is the point of the design: two instantiations holding the same id are the same allocator, which is what makes operator== meaningful across a rebind and what makes the converting constructor the mechanism that carries an id across a type change. The parameter is not a capacity, a policy or an allocator — the catalogue records one non-type parameter for InlineMonotonicAllocator and InlinePoolAllocator, and this class has neither: everything about where it allocates comes from the ambient scope at construction time, at run time.

Coverage

Not documented hereWhy
What the allocator behind a given id does at exhaustion, at what alignment, and under what locking This class decides none of those; it forwards. Every statement above is about the two paths through the adapter, and the per-allocator guarantees belong to the pages of the named allocators in the catalogue — of which PoolAllocator, documented here, is the only one this author read directly. Several of those entries are being written in this same wave, so the gaps are sequenced, not unknown.
Whether any engine container actually outlives the registration its id names The mechanism is documented (deregistration clears the proxy, the proxy pool re-uses slots) and the hazard is stated, but no call site in the repository provably survives a deregistration: the testlets in Engine/Memory/DefaultAllocator.cpp build and destroy their vectors inside the scope, and the engine containers hold the allocator as a member that dies with them. Whether such a container exists somewhere in engine code is a question about those containers, not about this class, and this wave has not read them all.
Whether stale ids are meant to be detectable at all Nothing in MemoryManager ages or generations a registration — the checks that exist are MEMORY_VERIFICATION_ENABLED's thread-id check and PROFILE_ENABLED's leak report, both compiled out in Engine/Config/BuildConfig.h. Whether a generation counter or an epoch is intended is a MemoryManager design question, answered nowhere in the repository, so it is not asserted on any page here.
The per-call AllocatorScope and whether it can re-enter the allocator it names The scope stays open across the whole dispatch, so anything the named allocator allocates from the ambient scope is charged to the allocator being asked. PoolAllocator's and MonotonicAllocator's constructors do take their buffer from the ambient scope (Engine/Memory/PoolAllocator.cpp, Engine/Memory/MonotonicAllocator.cpp), which is a construction-time concern only, and MultiPoolAllocator::GenerateBank in Engine/Memory/MultiPoolAllocator.cpp opens its own scope on its recorded parent, which is what shields bank generation from this path. Whether every allocator's dispatch path is so shielded is not established here.
Platform behaviour of the malloc fast path The page claims only that the path calls malloc and free and records nothing. What those return for a zero-byte request, what alignment they guarantee, and how they behave under concurrency are platform answers, not engine ones, and are deliberately not asserted.
Why GetFallbackCount exists Nothing reads it, no other allocator in the module declares a counterpart, and the engine's real counter is AllocStats::fallbackCount behind PROFILE_ENABLED. The value is documented exactly — a constant 0 — and the intent behind the accessor is not established anywhere in the repository.
Who, if anyone, reads the nested rebind struct std::allocator_traits synthesises A<U> and does not consult it (proved by probe), and a repository search finds no use of rebind<...>::other. It is documented as present; a claim that nothing anywhere reads it would extend to third-party templates instantiated with this allocator, and this wave cannot see them.
BaseAllocatorTest Test-only: declared in Engine/Memory/DefaultAllocator.h inside #ifdef __TEST__, defined in Engine/Memory/DefaultAllocator.cpp with the three testlets Basic Usage, Multiple Allocations and Nested Allocations. They are quoted as examples on the method pages, because they are the only call sites that distinguish the two paths; the class itself owns no page of its own.
