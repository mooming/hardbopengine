operator==

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h Two allocators are equal when they hold the same registration id, which is what lets the standard library move or swap their containers.

Signature

template <class TOther>
	bool operator==(const DefaultAllocator<TOther>& rhs) const noexcept

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::operator==(const DefaultAllocator<TOther>& rhs) const noexcept. One comparison of one member: two allocators are equal when they name the same registration id. The TOther parameter is what makes the relation cross-type, which is not a convenience here but the reason the function exists — the allocator requirements ask whether two allocators of different element types can be used interchangeably, and a node-based container asks that question about DefaultAllocator<Node> against DefaultAllocator<T> constantly. Comparing two instantiations of the same type works too, with TOther deduced to T.

Because the class declares no is_always_equal member, std::allocator_traits synthesises one as std::is_empty<A> — and this class is not empty, it holds a TAllocatorID — so the answer is false and the containers actually ask the question rather than assuming equality. Verified by compiling the declaration shape with c++ -std=c++2b -Wall -Wextra -fsyntax-only and asserting the synthesised traits: is_always_equal::value, propagate_on_container_copy_assignment::value, propagate_on_container_move_assignment::value and propagate_on_container_swap::value are all false. The consequences all land on this operator: a std::vector may steal another vector's buffer on move-assignment only when the two allocators compare equal, and with propagate_on_container_swap false a swap of unequal allocators is not available at all. Two containers built in two different AllocatorScopes therefore record two ids, compare unequal, and fall back to element-wise moves instead of a pointer handover — a silent performance difference, and the only visible effect this operator has inside the engine's own containers.

Equal does not guarantee interchangeable memory once an id has been reused. The relation compares numbers, and MemoryManager::RegisterAllocator hands out numbers from proxyPool — the same pool MemoryManager::DeregisterAllocator returns them to. An allocator that recorded id 7 of a pool that has since been destroyed compares equal to an allocator that recorded id 7 of whatever was registered next, and their memory is emphatically not interchangeable: releasing one's block through the other reaches a stranger's allocator. The guarantee the allocator concept asks for — equal allocators may free each other's blocks — is true here for as long as both ids name live registrations, and this operator has no way to check that they do.
Its partner is a second definition, not a compiler-generated one. C++20 would derive operator!= from operator==; this header declares its own, so the two are independent lines that a future edit must keep in agreement. Neither is [[nodiscard]], so a comparison whose result is dropped is not diagnosed, and both are const and noexcept.

Return value

TypeWhat you get
boolTrue exactly when both hold the same TAllocatorID. It says nothing about whether that registration is still alive, and nothing about which allocator a given pointer came from.

Examples

Illustrative — the comparison is issued by the standard library on the engine's behalf; no engine source compares two of these allocators by hand.

std::vector<int, DefaultAllocator<int>> a;
std::vector<int, DefaultAllocator<int>> b;

a = std::move(b);	// allocator_traits::is_always_equal is false, so the move
					// assignment compares a.get_allocator() == b.get_allocator()
					// before it can take b's buffer.

Both vectors here are constructed with no AllocatorScope open, so both record MemoryManager::SystemAllocatorID, compare equal, and the move still steals the buffer. Move one of them into a scope opened on a pool and the comparison stops being a formality — see the constructor for what each one captures and when.
