operator!=

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h The hand-written negation of the id comparison: it tells the caller the two registrations differ, and stops there.

Signature

template <class TOther>
	bool operator!=(const DefaultAllocator<TOther>& rhs) const noexcept

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::operator!=(const DefaultAllocator<TOther>& rhs) const noexcept: the negation of the same one-int comparison, spelled out by hand rather than derived by the compiler from operator==. C++20 asks an allocator for == alone, so this declaration is the older half of the requirement kept for consumers that still spell the question with !=; it is cross-type for the same reason its partner is, and it is const and noexcept and not [[nodiscard]].

What inequality is worth: the two allocators name different registration slots, so a block from one is not a block the other knows how to release. The standard library uses that to protect itself — with propagate_on_container_swap synthesised as false, as the probe on operator== records, a swap of two containers whose allocators compare unequal is not available, and a move assignment cannot take the source's buffer.

Inequality is a warning, not a guard. Nothing in this class refuses a cross-allocator release: deallocate routes a pointer by the receiving allocator's recorded id and never asks where the block came from — there is no IsMine-style range test here, because there is no buffer to range-test. Hand a block allocated through one allocator to a second one whose != says true and the call still runs: the pointer goes to the second allocator's registration, and what it does with a block it never handed out is that allocator's own policy. The comparison is information for the caller and for the containers that choose to ask it.

Return value

Examples

Illustrative — the standard library issues this comparison; no engine source does.

std::vector<int, DefaultAllocator<int>> a;
std::vector<int, DefaultAllocator<int>> b;

a.swap(b);	// legal and cheap only while the two allocators compare equal

To make the two unequal, build one of them inside an AllocatorScope over some other allocator: the captured ids then differ, the containers can no longer exchange buffers, and the only remaining way to move their contents is element by element. That is the whole cost of the inequality — a silent allocation-policy decision, not an error.
