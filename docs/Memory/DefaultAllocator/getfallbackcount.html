GetFallbackCount

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h A static constexpr literal 0: this adapter owns no storage so it performs no fallback, and the engine's real fallback counter is elsewhere.

Signature

[[nodiscard]] static constexpr size_t GetFallbackCount()

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::GetFallbackCount(). Its body is return 0; — a literal. Nothing writes it, nothing stores it, and because it is static and constexpr it does not even look at an object: it answers about the class template, not about the allocator instance or the id it carries, and being constexpr it can be read in a constant expression.

What the answer means follows from what a fallback is in this engine. A fallback happens when an allocator that owns storage cannot serve a request and asks its parent: MemoryManager::FallbackAllocate(id, parentId, requested) in Engine/Memory/MemoryManager.cpp does that, and the count of such events lives in AllocStats::fallbackCount, incremented by MemoryManager::ReportFallback — the whole body of which sits behind #if PROFILE_ENABLED, which Engine/Config/BuildConfig.h sets to 0. DefaultAllocator owns no storage, has no capacity to exhaust and no parent of its own: it names an allocator and stands in front of it. So 0 is a truthful statement about this adapter and nothing else — the allocator whose id it holds may be falling back on every call, and the number returned here will not change.

The zero is not a measurement, and it is not the engine's fallback counter. A caller who reads this as "no fallback has happened" reads the wrong thing twice over: the figure is constant, and the real counter is per registration in AllocStats::fallbackCount, reachable through MemoryManager::GetAllocatorStat(id) in a PROFILE_ENABLED build. No code in the repository calls this function at all — Engine/Memory/DefaultAllocator.h is both its declaration and its only appearance — and no other allocator in the catalogue declares a counterpart, so there is no family-wide interface it can be said to be completing. See Coverage.

Parameters

None. Being static, it is called as DefaultAllocator<T>::GetFallbackCount(); calling it through an instance is permitted and reads nothing from it.

Return value

TypeWhat you get
size_tAlways 0, for every instantiation of the class template and every state of the allocator. Not a count of anything that happened.

Examples

Illustrative — no call site for this exists anywhere in the repository.

static_assert(DefaultAllocator<int>::GetFallbackCount() == 0);

That is the only thing the function can be used for: a compile-time constant. To ask the runtime question — how often has the allocator behind this id actually handed a request to its parent — there is no path through this class; it goes through MemoryManager's statistics, and in this tree the statistics are compiled out.
