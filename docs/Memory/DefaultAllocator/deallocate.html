deallocate

member of hbe::DefaultAllocator Engine/Memory/DefaultAllocator.h free on the system path, or a scoped release into the named registration: legal and real, and what it reclaims is that allocator's answer.

Signature

void deallocate(T* ptr, std::size_t n) noexcept

Function description

Defined inline in Engine/Memory/DefaultAllocator.h as DefaultAllocator::deallocate(T* ptr, std::size_t n) noexcept. The mirror of allocate, down the same two paths, and — unlike the monotonic arenas of this module — an individual release here is a real release. What it actually reclaims is decided by the allocator the recorded id names, not by anything in this function. 

Assert(ptr != nullptr);

if (allocatorID == MemoryManager::SystemAllocatorID)
{
	free(ptr);

	return;
}

AllocatorScope scope(allocatorID);
auto& mmgr = MemoryManager::GetInstance();
mmgr.DeallocateTypes(ptr, n);

From Engine/Memory/DefaultAllocator.h, DefaultAllocator::deallocate(T* ptr, std::size_t n)

The assert is the only provenance check anywhere in this class, and it checks only that a pointer was passed: a null release aborts in Debug and Dev, and in Release Assert is an empty inline function in Engine/Core/Debug.h and the null simply reaches free. Nothing asks where ptr came from. There is no IsMine-style range test, because the class owns no buffer to test a pointer against, so the routing is by the receiving allocator's id alone: hand a block to a different DefaultAllocator and the release is dispatched to that one's registration, whatever it thinks of a pointer it never handed out. A pool forwards it to its parent, the system path calls free on an address malloc did not return, and a double release is equally undetectable in both.

The size travels as a count again: MemoryManager::DeallocateTypes<T> deduces T from the pointer's static type and recomputes n * sizeof(T), which is why the n must be the same element count that allocate was given and not a byte count. Report the wrong count and nothing here complains — the checks that could notice are MemoryManager's and SystemAllocator's, and both live behind MEMORY_VERIFICATION_ENABLED and PROFILE_ENABLED, which Engine/Config/BuildConfig.h sets to 0. The slow path costs the same per-call AllocatorScope as the allocation did, and requires a live manager for the same reason: MemoryManager::GetInstance() is FatalAssert-guarded in every configuration.

What a release reclaims is the named allocator's answer, not this one's. This class is a proxy, so the semantics belong to whatever the id points at: a pool puts the block back on its free list and the bytes are genuinely reusable, a multi-pool returns the block to the bank that owns it, and a monotonic or stack allocator — the case the header warns about — takes the release and returns nothing. Nothing in this function reports which of those happened, and the fast path is the clearest case of the rule: free hands the block back to the system heap and the engine records nothing, because the replacement operator delete in Engine/Memory/GlobalAllocation.cpp is the accounting point and this call bypasses it exactly as allocate does.

The hazard that dominates this function is lifetime rather than arithmetic. A release is dispatched to a registration slot, so a container that outlives the allocator its id names will release through a dead proxy — MemoryManager::Deallocate asserts allocProxy.deallocate != nullptr, which is an abort in Debug and Dev and a call through a null function pointer in Release — or through whatever allocator has since been registered under that number. Keeping the container inside the scope that supplied the id is the whole remedy, and the constructor page names the containers for which that is easy and the ones for which it is not.

Parameters

ParameterTypeRequirement
ptrT*A block this allocator family returned, from the same registration. Null is asserted against; provenance is not checked at all.
nstd::size_tThe element count originally passed to allocate. Multiplied by sizeof(T) downstream, so a count-and-bytes mix-up silently misreports the size to the allocator that owns the block.

Return value

None, and nothing is returned that would tell the caller whether the block was reclaimed, ignored or forwarded. For an id naming a monotonic arena the honest answer to "did that free my memory" is not available from here.

The testlet is a proof of the note above: the vector was built while the inner pool's scope was open, so its buffer belongs to that pool, and shrink_to_fit drives one call here whose release the pool honours — a pool has a free list, so its usage returns to zero. Substitute a bump allocator behind the same id and the same call would leave the usage figure where it was, with this function returning the same nothing.
