~AllocatorScope

member of hbe::AllocatorScope Engine/Memory/AllocatorScope.h Writes the saved id back, once, unconditionally - the restore that defines what a scope protects and what it cannot

Signature

~AllocatorScope() noexcept

Function description

Defined at Engine/Memory/AllocatorScope.cpp: fetch MemoryManager::GetInstance(), then mmgr.SetScopedAllocatorID(previous). That is the entire restore — the value this thread held when the scope was constructed is written back, once, on every exit path (the GetInstance() FatalAssert being the single way out that is not a restore). Because each object stores what it found rather than what it replaced, nested scopes unwind correctly in any stack order: each destructor hands back the exact value its constructor read.

Two properties of this one line decide what a scope is and is not. First, it is unconditional: the destructor does not check whether the id it is restoring is still meaningful, only that it is a stored number — an allocator that was deregistered while current is restored to being current, pointing at a slot the next registration may already own. Second, it runs on whichever thread destroys the object: the saved value came from the constructing thread's thread_local slot, and the setter writes the destroying thread's. Construct and destroy on one thread; see the hazard below.

What this destructor cannot protect you from is the release of memory that was allocated before the scope opened. The classic shape in this module: an allocator object allocates its backing buffer from its parent, is destroyed while its own scope is open, and its destructor releases through the id-free MemoryManager::Deallocate(void*, size_t) — which reads this thread's current scope, not the buffer's history. The release then enters the dying allocator's own Deallocate, which ignores individual releases by design, so nothing asserts and the buffer leaks. That was MonotonicAllocator's bug until the 2026-10-06 fix (reproduced by the testlet Destroy In Own Scope, recorded in JOURNAL.md): the destructor now names its parent explicitly, the line quoted below. 
	mmgr.Deallocate(parentID, bufferPtr, capacity);

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::~MonotonicAllocator()

The repaired release line — and the general rule it encodes: a scope protects where calls made inside it are routed and restores the outer value on exit; it protects neither an object's own teardown nor a pointer's history from whichever scope happens to be current at the moment of release.

Parameters

None.

Return value

None. After it returns, the calling thread allocates by id exactly as it did before the scope was constructed.

Examples

	auto& mmgr = MemoryManager::GetInstance();
	mmgr.SetScopedAllocatorID(previous);
