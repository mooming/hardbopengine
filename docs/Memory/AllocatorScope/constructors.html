AllocatorScope

member of hbe::AllocatorScope Engine/Memory/AllocatorScope.h Save this thread's allocator id, install the given one - by id, by asking an allocator object for its id, or by installing InvalidAllocatorID as a deliberate refusal to allocate

Signature

AllocatorScope(const AllocatorScope&) = delete

AllocatorScope(AllocatorScope&&) = delete

AllocatorScope() noexcept

AllocatorScope(TAllocatorID id) noexcept

template <typename T>
	AllocatorScope(const T& allocator) noexcept
		: AllocatorScope(allocator.GetID())

Function description

The two live non-template constructors are defined at Engine/Memory/AllocatorScope.cpp; the template constructor is defined in the class body of Engine/Memory/AllocatorScope.h as a delegating call, AllocatorScope(allocator.GetID()). The installing steps all happen in the TAllocatorID form: fetch MemoryManager::GetInstance() — a FatalAssert if no manager exists, live in every build configuration — save this thread's current id into previous, record the requested id in current, and write it through MemoryManager::SetScopedAllocatorID, the manager's private setter that names this class its friend. The default constructor delegates with InvalidAllocatorID.

The setter applies one correction before storing: an id that is neither InvalidAllocatorID nor within range is logged as an error and replaced by 0, the system allocator (MemoryManager::SetScopedAllocatorID). So an out-of-range id opens a scope that silently redirects to slot 0 after logging, while InvalidAllocatorID is stored as given — under it, MemoryManager::Allocate(size_t) takes its Assert(id != InvalidAllocatorID) with the message "Memory allocation is not permitted." and only afterwards, in a build where that assert has no teeth, falls back to slot 0 with an error line.

Copying and moving are deleted, and the declarations sit in the private section. A scope object holds exactly one restore obligation for exactly one saved value, discharged once by its destructor. A copy would put two live objects in possession of the same obligation — the second destructor would write previous back over whatever the first one had restored — and a move would let the same happen across two lifetimes in the wrong order. The header forbids all four operations (the class table lists them); being private as well as deleted, the compiler reports them by access where it can. A scope is created where it is used and destroyed where the redirection must end; nothing else is meaningful.

Parameters

ParameterTypeRequirement
idTAllocatorIDA registered allocator's id, or InvalidAllocatorID to open a scope under which allocation is refused. An out-of-range non-invalid id is coerced to slot 0 by the setter, after an error log.
allocatorconst T&Any object with a GetID() — every allocator in this module has one; the object must outlive the scope, which the scope does not help enforce.

Return value

None; constructors. On return the calling thread's scoped allocator id is the one requested, and the value found there is stored for the destructor.

Examples

	auto& mmgr = MemoryManager::GetInstance();
	previous = mmgr.GetScopedAllocatorID();
	current = id;

	mmgr.SetScopedAllocatorID(current);
