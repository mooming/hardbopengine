AllocatorScope

Engine/Memory/AllocatorScope.h final namespace hbe RAII redirection of one thread's default allocations: saves the scoped allocator id, installs another, restores the saved value on destruction - and protects the routing of calls, never the history of pointers

Class description

class AllocatorScope final at Engine/Memory/AllocatorScope.h is the engine's way to say "allocate from this allocator while I am current." On construction it reads the thread's current allocator id from MemoryManager, stores it in previous, and installs the id it was given; on destruction it writes previous back (Engine/Memory/AllocatorScope.cpp). The state it steers is MemoryManager::scopedAllocatorID, a thread_local value that the id-free entry points MemoryManager::Allocate(size_t) and MemoryManager::Deallocate(void*, size_t), and the free New/Delete helpers, read on every call. It changes nothing about allocators themselves — it registers nothing, owns nothing, and keeps nothing alive; it changes where one thread's subsequent default traffic goes.

Three ways to open one, all on the constructors page: by id, AllocatorScope scope(someId); by allocator object, the template constructor that forwards allocator.GetID(), which is the shape the pool users write; or default-constructed, which installs InvalidAllocatorID — a scope under which an actual allocation asserts (see below), not a scope that means "no opinion." Nesting works because each object stores the value it found, not the value it replaced: scopes opened inside one another restore in reverse order, which is what ordinary stack lifetimes already give. The copy and move operations are deleted and private — an object holds the single restore obligation for one saved value, and a second live object carrying the same saved value would write it back twice (constructors).

A scope redirects the calls made inside it; it does not attach itself to memory. An allocation made while a scope is open does not "belong" to that scope: release is routed by whichever scope is current at the moment of the release call, because the id-free deallocate reads the same thread-local value. The module has already paid for this fact twice. A monotonic allocator destroyed while its own AllocatorScope was open used to release its backing buffer through the ambient scope instead of the parent recorded at construction — the release entered the dying allocator's own inert Deallocate, nothing asserted, and the buffer never returned to its parent; the repair of 2026-10-06 (recorded in JOURNAL.md, reproduced by the testlet Destroy In Own Scope) names the parent explicitly, and the fixed release line is quoted on the destructor page. PoolAllocator's destructor carries the same rule, recorded in its own page's gap note. The general statement, which is the reason both allocators state it: an AllocatorScope protects the routing of calls made inside it and the restoration of the outer value on exit — it does not protect an object's own teardown from the scope that happens to be open around it, does not keep the allocator it names alive (destroying a scoped-over allocator leaves the id pointing at a cleared or reused slot), and does not cross threads (a new thread begins at id 0, and destroying a scope on a thread other than the one that constructed it writes one thread's saved value into another thread's state).
A scope is not safe before the engine exists or after it dies. Every constructor and the destructor reach the manager through MemoryManager::GetInstance(), whose FatalAssert is live in all three build configurations (Engine/Memory/AllocatorScope.cpp, GetInstance). Static-init-time or post-shutdown construction aborts the process rather than falling through to the system allocator.

Template parameters

The class is not a template, but its third constructor is: one type parameter, the allocator object's class, with one requirement — it must offer a GetID() returning a TAllocatorID. Every allocator in the module does; the constructor body is that single call.
