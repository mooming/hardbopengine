Deallocate

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h Null is ignored, a pointer from elsewhere goes to the parent, and a block released twice is not detected.

Signature

void Deallocate(Pointer ptr, size_t size)

Function description

Defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::Deallocate(Pointer ptr, size_t size). Three exits before any block is touched: a null pointer is ignored, a pointer outside the pool's buffer goes to the parent, and a free list that no longer makes sense is reported and left alone. Otherwise the block goes back on the free list.

A null pointer is a silent no-op, and size is not examined on that path. There is no Assert(size == 0) here, unlike MultiPoolAllocator::Deallocate(), which asserts it. Releasing null costs nothing and tells you nothing, whatever byte count came with it.
A pointer this pool never gave out is forwarded to the parent rather than rejected. IsMine is a range test on the buffer (IsMine), and a pointer outside it is handed to mmgr.Deallocate(parentID, ptr, size) — where size is the byte count the caller just passed. This is the other half of the oversized-request contract, and it is what makes a request the pool could not serve round-trip correctly through the pool it was asked of. It is also the reason a wild, stale or already-foreign pointer is not caught here: it is passed up to the parent, which has no way to know it is not its own. A pool is not a checker for a pointer you are not sure about.
Nothing detects a block released twice. There is no "is this block already free" test, so a second release links the block again and counts it again. The second release of the same block links it to itself, which leaves the pool answering two consecutive Allocate calls with one address, and the free count is inflated by one for the rest of the pool's life. The only witness is the closing Assert(numberOfFreeBlocks <= numberOfBlocks) printed above — real in Debug and Dev, an empty inline function in a Release build (Engine/Core/Debug.h) — and it fires only once the inflated count passes the block count. The two branches printed above make the missing test visible: each asks something about the free list — the index of its head in the if, its emptiness in the else — and neither asks whether the block being released already sits on it. No testlet performs a double release, so the whole of this claim is read from the code rather than demonstrated against the engine: the testlets of PoolAllocatorTest::Prepare (Engine/Memory/PoolAllocator.cpp) release each block they allocate exactly once, and Reallocation After An Exhausted Free List confirms that no address it receives is one still held, so the path that would catch a block released twice is never walked.
The one corruption check reports and returns. If the free-list head names a block index past the end of the pool, the release is abandoned with a logged error and the block is lost — not returned, not asserted. The message reads " is not alloacted by this.", misspelling included, which matters when the only thing you have to search a log with is the word it used (Engine/Memory/PoolAllocator.cpp, PoolAllocator::Deallocate()). Note what it does not test: the index of the head, not the index of the block being released, so a damaged list is detected one release later than it happened.
size decides nothing inside the pool, and everything on the way out. For a block the pool owns, the byte count is used only by the PROFILE_ENABLED assertion Assert(size <= blockSize) and by the profile report — neither of which runs in a build this tree compiles. For a foreign pointer, that same number is what the parent is asked to release. So the pairing rule stands even though the pool itself cannot check it: pass the size you allocated with, because the pool may be a pass-through to something that takes the number seriously.
A free-list link is a block index or the sentinel numberOfBlocks, and releasing into a completely full pool writes the sentinel. The constructor ends the list with the link value numberOfBlocks, and AllocateBlock reads a link below numberOfBlocks as "another block follows" and anything else as the end of the list — so numberOfBlocks is the terminating sentinel, and nothing other than a block index or that sentinel is a legal link. The else branch printed above, taken when the pool had no free block for the released one to link to, writes numberOfBlocks, and WriteNextIndex accepts it: its bound is Assert(index <= numberOfBlocks, ...), the same bound ReadNextIndex already applied when reading a link back (Engine/Memory/PoolAllocator.cpp). Before that branch was corrected it wrote numberOfBlocks - 1 instead — an ordinary block index naming the pool's last block — which put a block some caller was still holding back on the free list and handed it to a second caller two allocations later. The guard is the testlet Reallocation After An Exhausted Free List in PoolAllocatorTest::Prepare: it exhausts a pool, returns half the blocks, allocates again, and fails naming the colliding address if any address it receives is still held. Restore the previous branch and that testlet fails, reporting a collision against the last block, and the collection reports FAIL with exit code 1. A checked build aborts before it can show you that collision, and which configuration you are debugging in decides whether the failure is visible at all. Debug and Dev abort at Assert(numberOfFreeBlocks > 0) in AllocateBlock, which sits above that function's return ptr;, so the pool crashes rather than passing the colliding address back to anyone. Release was the only configuration in which a caller silently received the same address twice: Assert is an empty inline function there (Engine/Core/Debug.h, live unless RELEASE_BUILD), and MemoryManager::LogError says nothing because MemoryManager::Log() wraps its entire body in #if MEMORY_LOGGING_ENABLED, which Engine/Config/BuildConfig.h defines as 0. How the free list is laid out — where in a block that link lives, and what a block costs because of it — is mechanism, and is still owed to a Memory design document under docs/; see the class Coverage section.

Parameters

ParameterTypeRequirement
ptrPointerA block this pool handed out, a pointer the pool forwarded to its parent, or nullptr. Anything else is treated as the parent's.
sizesize_tThe byte count the allocation was made with. Unused by the pool's own path outside the profile build; forwarded verbatim when the pointer is foreign.

Return value

Nothing. Every failure mode this function has — foreign pointer, damaged free list, block counted twice — is reported by a log line or by an assertion, never by a return value, because there is none.
