ReadNextIndex

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h Private: reads the block ordinal stored in a block's first word, bounded only by an assertion.

Signature

Function description

Defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::ReadNextIndex(Pointer ptr) const. Private. It reads one size_t from the address of a block and treats it as a block ordinal. 

auto index = GetAs<TSize>(ptr);
Assert(index <= numberOfBlocks, "PoolAllocator: free-list link ", index, " is out of bounds for ", numberOfBlocks,
		   " blocks.");

return index;

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::ReadNextIndex(Pointer ptr) const

The one bound check is an assertion, and only in Debug and Dev. index <= numberOfBlocks accepts the value that means "no more blocks", so a legal terminator passes and an index past it stops the build that has assertions. In a Release build, where Assert is an empty inline function (Engine/Core/Debug.h), the value is returned whatever it is and AllocateBlock decides what to do with it: anything at or above the block count ends the walk.
The read is alignment-checked before it happens, by the helper it goes through. GetAs<TSize> asserts that the address is a multiple of sizeof(TSize) (Engine/Core/CommonUtil.h) — which holds because the block stride is a multiple of Config::DefaultAlign (GetBlockSize) and every block starts on that stride. A pool whose stride had not been aligned would trip that assertion here rather than read misaligned; that is the same fact as the constructor's block-size floor, seen from the other end.
What the value means is the pool's internal layout, and this page deliberately stops at the boundary. A block carries this ordinal when it is free and does not carry it when it is handed out (WriteNextIndex has one caller). Why the pool stores its bookkeeping inside the blocks it manages instead of beside them, what that costs a caller in block size, and how the list is threaded — the design document the class Coverage section names as owed. A caller only needs the consequences: the floor on block size, and the fact that a held block's bytes are untouched.
