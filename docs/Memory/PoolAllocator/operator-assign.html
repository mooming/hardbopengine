operator=

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h noexcept Ends this pool and rebuilds it in place from rhs, so the old buffer is freed and the old id deregistered first.

Signature

PoolAllocator& operator=(PoolAllocator&& rhs) noexcept

Function description

Defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::operator=(PoolAllocator&& rhs). It is not an assignment that copies fields: it ends this pool and rebuilds it in place. 

this->~PoolAllocator();
new (this) PoolAllocator(std::move(rhs));

return *this;

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::operator=(PoolAllocator&& rhs)

Two consequences follow from that shape and nothing else in the class announces them. The destination's buffer is released to its own recorded parent and its registration deregistered, exactly as the destructor would, before a byte of rhs is read. And the pool that ends up in this carries rhs's parentID, so the buffer now held here owes its return to the allocator that was current where rhs was built — not where this assignment happens (the recorded-parent rule).

Assigning over a pool that is still lending blocks releases that buffer anyway. Nothing between the caller and this->~PoolAllocator() compares the free count with numberOfBlocks. Any live object in the destination's buffer is left pointing at memory returned to that pool's parent. This is the same exposure the destructor carries, and it arrives through ordinary container work: std::sort move-assigns, and a bank of a multi-pool is a pool with blocks handed out.
Self-move-assignment ends the pool instead of doing nothing. There is no this != &rhs guard. The destructor runs on the live object first — releasing its buffer and deregistering its id — so the move constructor that follows is stealing from an object it has just emptied: it copies InvalidAllocatorID, trips its own Assert(id != InvalidAllocatorID), zeroes the fields again and then asks MemoryManager::GetAllocatorProxy() for InvalidAllocatorID, which logs an error and hands back a throwaway record (Engine/Memory/MemoryManager.cpp). Debug and Dev stop at the assertion; a Release build, where Assert is an empty inline function (Engine/Core/Debug.h), leaves a pool that owns nothing and can never allocate again.
The move that follows a sort is the case a measurement exists for. std::sort over a vector of pools moves pools repeatedly, and the question worth asking is whether a destructive assignment like this one can release a bank's live buffer mid-shuffle. JOURNAL.md records the 2026-10-05 answer as measured, not assumed: libc++'s shift move-assigns only into the slot the previous move has just vacated, and the run recorded zero releases for an out-of-order insert — "Safe by luck, not by contract". The same entry, finding 5, records that the manager's proxy for the id keeps naming the moved-from object (constructors), so a pool that has been moved should not be allocated through by id.
Copy assignment does not exist. Declaring the move operations deletes the copy constructor and copy assignment implicitly — verified against a class carrying the same declarations with std::is_copy_assignable_v false. A pool cannot be duplicated, which is the correct answer for a type that owns one buffer and one registration id: a second copy would free the same buffer and deregister the same id twice.
