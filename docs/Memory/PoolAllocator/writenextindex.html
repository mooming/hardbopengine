WriteNextIndex

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h Private: writes that ordinal as a block is released, which is why a block you hold is never written.

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::WriteNextIndex(Pointer ptr, TSize index)

The one consequence a caller can rely on: the pool writes into a block only when it takes the block back. Its sole caller is Deallocate. Nothing in Allocate or AllocateBlock writes to a block, so a block you hold is untouched — the whole stride is yours, the first sizeof(size_t) bytes included, and no bookkeeping of the pool's is hidden in it while you have it. The moment you release it, that word is the pool's.
Both halves now accept the same set of values: a block index, or the terminator. This helper asserts index <= numberOfBlocks, the bound ReadNextIndex has always applied, and AllocateBlock reads a link below numberOfBlocks as "another block follows". A link is therefore a block index or numberOfBlocks, and nothing else.
The two bounds used to disagree, and that disagreement is the reason this page matters. This helper asserted index < numberOfBlocks, which forbade the terminator the constructor itself lays down, so Deallocate conformed to the wrong bound and wrote numberOfBlocks - 1 — an ordinary block index naming the pool's last block — when it had no free block to link to. The guard is the testlet Reallocation After An Exhausted Free List in PoolAllocatorTest::Prepare, which fails with that branch restored.
Assertions aside, SetAs<TSize> itself asserts the destination is a multiple of sizeof(TSize) (Engine/Core/CommonUtil.h), the same stride argument as on the read half.

Parameters

ParameterTypeRequirement
ptrPointerAddress of the block being released. The write lands in its first sizeof(TSize) bytes, over whatever the holder left there.
indexTSizeA block ordinal below numberOfBlocks. Asserted in Debug and Dev, written unchecked in Release.

Return value

Nothing. The effect is one value written into a block, and no report of whether it was a sane one — that is the assertion's job, and only in a build that has assertions.
