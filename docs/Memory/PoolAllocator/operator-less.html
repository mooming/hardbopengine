From Engine/Memory/PoolAllocator.cpp, PoolAllocator::operator<(const PoolAllocator& rhs) const

Block size ascending; within one block size, the pool with more free blocks first. Read against Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::GetBankIndex(size_t), the intent of the second key is visible: that scan walks the banks in order and takes the first one whose block size covers the request and whose GetAvailableBlocks is non-zero, so whichever pool sorts earliest is the one that gets the allocation. Ordering the emptier pool first spreads requests across banks of the same size instead of filling one.

Nothing else about a pool is compared. The id, the name, the buffer address, the total block count and the recorded parent are all invisible to this ordering. Two pools of the same block size with the same number of free blocks compare equivalent, so their relative order after a sort is whatever the algorithm leaves behind — an index into the bank vector is not a stable identity across a sort.
The ordering is a function of live state, so a sorted vector stops being sorted the moment anyone allocates. The second key reads numberOfFreeBlocks, which Allocate and Deallocate change. Nothing in the tree re-sorts after an allocation: MultiPoolAllocator::GenerateBank() sorts once, immediately after appending a bank, and the bank order thereafter drifts with usage. Treat the order as a hint the size scan tolerates, not as an invariant anything can rely on.
Sorting pools executes the destructive move assignment. Every shuffle this operator drives calls operator=, which runs the destructor of the pool being overwritten and rebuilds it in place. JOURNAL.md (2026-10-05, finding 5) measured that libc++'s insertion sort move-assigns only into a slot its own previous move has vacated — so no live bank buffer was released — and recorded that as "Safe by luck, not by contract". A sort of pools is therefore a place to change carefully, not freely.

Parameters

ParameterTypeRequirement
rhsconst PoolAllocator&Any pool, including an inert one: a moved-from pool reports a block size of 0 and zero free blocks, so it compares less than every live pool of a non-zero block size.

Return value

TypeWhat you get
boolWhether this pool should be served before rhs: smaller block size, or the same block size with more blocks still free. A valid strict weak ordering — lexicographic on block size and then on descending free count — so it is safe to hand to std::sort.

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::GenerateBank()

The bank vector of a multi-pool is kept ordered by this operator each time a bank is generated, and Engine/Memory/ThreadSafeMultiPoolAllocator.cpp runs the same pair in its own bank generation. No engine code compares two pools by hand. Whether ordering banks is safe to compute on banks shared between threads is a question about that class and its lock, not about this comparison: this operator reads two plain members, takes no lock and is documented as such.
