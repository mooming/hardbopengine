PoolAllocator

Engine/Memory/PoolAllocator.h final Fixed-size blocks for objects of one type: one pre-allocated buffer, one free list, and a parent allocator that receives everything the pool cannot serve.

Class description

class PoolAllocator final at Engine/Memory/PoolAllocator.h is a fixed-size block allocator for objects of a single type. It pre-allocates a pool of memory blocks and manages a free list, which makes it the efficient choice for many allocations of objects that all have the same size. Construction is one allocation of blockSize * numberOfBlocks bytes from the allocator that is current at that moment, the linking of those blocks into a free list, and a registration of the object with the MemoryManager under an id of its own.

The registration is what lets a pool serve code that never sees it. The shape the repository actually uses is LinkedListTest::Prepare() in Engine/Container/LinkedList.cpp: one pool named "LinkedListTest::Allocator" built with a block size of sizeof(LinkedList<int>::Node) — the node type is what the caller measures, since the pool knows nothing about it — and a block count of the list's element count plus ten blocks of headroom, then an AllocatorScope opened over the pool object itself (AllocatorScope allocScope(alloc);, the template constructor that forwards to GetID — the linear allocators' users open their scopes on the id instead). Every node the list then builds arrives from the pool through the default allocator.

A pool returns everything to the allocator recorded at construction, not to whichever one is current later. The id the constructor found current is stored as parentID, and it is that recorded id — never the ambient scope — that the destructor releases the buffer through, that Allocate sends oversized requests to, and that Deallocate sends foreign pointers to. Pools are destroyed by other allocators' teardown: a bank of a multi-pool is destroyed when the vector holding it is emptied, under whatever scope that happens to run in. Before the fix of 2026-10-05 the destructor released through the current scope, and the failure was visible as PoolAllocator.cpp's own testlet reporting that the buffer "is allocated by another allocator". The consequence for a caller: destroy a pool wherever it suits you, and do not open an AllocatorScope to protect the destruction.
Two behaviours the names do not announce. Allocate with a request larger than the pool's block size does not fail: it asks the parent through MemoryManager::FallbackAllocate(GetID(), parentID, size), and the pointer you get back belongs to the parent, not to the pool. Deallocate with a pointer outside the pool's buffer does not fail either: it forwards to the same parent. The two are one contract seen from both ends — an oversized block never touches the free list, and handing it back to the same pool object is the correct way to release it.
The block size you pass is not the block size the pool uses. The constructor stores OS::GetAligned(std::max(inBlockSize, sizeof(TSize)), Config::DefaultAlign) — a floor of sizeof(size_t) and a round up to Config::DefaultAlign (16 bytes). The floor is a precondition the constructor asserts rather than a value it can serve, and the rounding is why a request of 24 bytes becomes a 32-byte block; GetBlockSize is the truth, the constructor argument is a request. A caller who sizes a pool from the request rather than the answer over-counts capacity: the buffer holds GetCapacity() bytes, which is more than requested, but only numberOfBlocks blocks of it.
Nothing in this class is synchronised. Engine/Memory/PoolAllocator.cpp takes no lock and reads or writes no atomic: the counters, the free-list head and the profile peak are plain members. One pool is one thread's at a time, including the two multi-pool allocators that hold pools as banks — those own their own synchronisation and hand out a bank without publishing it. The engine's shareable shape is ThreadSafeMultiPoolAllocator; a bare pool is not it, and it is not reentrant either, because Deallocate and Allocate can both reach the logger.

The class is move-only. Declaring the move constructor and move-assignment operator deletes the copy constructor and copy assignment implicitly, which is the correct answer for a type that owns a buffer and holds a registration id: two live copies of a pool would deregister the same id and free the same buffer twice. Verified by compiling a class carrying the same five declarations with c++ -std=c++2b -fsyntax-only and std::is_copy_constructible_v and std::is_copy_assignable_v both false, both move operations true.

Template parameters

None. PoolAllocator is final and not a template: everything variable about a pool — name, block size, block count — is a constructor argument, and the element type is carried by the caller's arithmetic rather than by the pool.

Non-member helper functions

None. A pool is reached through its own object or through the MemoryManager registration the constructor created; the free functions in Engine/Memory/Memory.h work on any allocator and belong to the module page.

The mechanism behind the free list's terminating link, and the block released twice The contract itself is documented and test-guarded, not an open question: the link value numberOfBlocks is the terminating sentinel, AllocateBlock reads a link below it as "another block follows", Deallocate's empty-list branch writes that sentinel, WriteNextIndex accepts the same bound ReadNextIndex applies, and the testlet Reallocation After An Exhausted Free List in PoolAllocatorTest::Prepare guards it — restoring the numberOfBlocks - 1 that branch used to write makes the testlet fail. What this page still owes is the mechanism behind the link, which belongs to a Memory design document under docs/ that this wave has not written (the first row above), and the double-release case, which no testlet covers and which Deallocate names as a gap.

The unchecked side belongs with review finding 6 (2026-10-05), which is open robustness work rather than documented behaviour.
