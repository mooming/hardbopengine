GetUsedBlocksMax

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h nodiscard PROFILE_ENABLED only Peak blocks checked out at once — the figure a multi-pool caches into the next boot, in a configuration that does not compile.

Signature

#if PROFILE_ENABLED
	[[nodiscard]] auto GetUsedBlocksMax() const

Function description

Declared in the class body of Engine/Memory/PoolAllocator.h inside #if PROFILE_ENABLED, returning maxUsedBlocks: the largest number of blocks the pool has had checked out at one instant since it was constructed. The peak is raised in AllocateBlock and never lowered, never reset, and not raised by a release. 

#if PROFILE_ENABLED
	maxUsedBlocks = std::max(maxUsedBlocks, numberOfBlocks - numberOfFreeBlocks);
#endif // PROFILE_ENABLED

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::AllocateBlock()

This is a figure of a build that does not compile. JOURNAL.md records on 2026-10-05 that setting PROFILE_ENABLED to 1 breaks this tree in three unrelated places — including that hbe::source_location, the type of the sibling member srcLocation, is only ever forward declared while Engine/OSAL/SourceLocation.h defines SourceLocation. Everything said here is read from source that has never executed, and every claim about what the peak is used for inherits that caveat. See Coverage.
Blocks the parent served are not in the peak. Only AllocateBlock raises it, and an oversized request never reaches that function (Allocate sends it to the parent). A pool whose peak reads low may still be the route by which large allocations happened; the manager's fallback counter is the only witness of those, and it too is PROFILE_ENABLED-only.
The number decides how the next boot is sized. MultiPoolAllocator::ReportConfiguration() keys each bank by its block size and takes this peak as the bank's block count, writes the pairs to the multi-pool configuration cache, and asserts the reported total equals the summed peaks — the assertion added when JOURNAL.md finding F1 showed every bank's count being doubled by an accumulate that reserve had made silent. A wrong peak is therefore not a wrong report; it is the next run's pool sizing.

Parameters

None.

Return value

TypeWhat you get
size_tPeak blocks checked out at once, over the pool's whole life. Multiply by GetBlockSize for peak bytes, which is how the usage report prints it. Zero means never tracked, which under PROFILE_ENABLED would mean the pool never handed anything out.
