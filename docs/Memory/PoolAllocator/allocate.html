Allocate

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h One block off the free list, the parent's answer to an oversized request, or null when the pool is empty.

Signature

Pointer Allocate(size_t size)

Function description

Defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::Allocate(size_t size). One comparison decides everything: a request that fits the pool's block size pops a block off the free list, and a request that does not is answered by the pool's parent. 

if (unlikely(size > blockSize))
{
	auto& mmgr = MemoryManager::GetInstance();

	return mmgr.FallbackAllocate(GetID(), parentID, size);
}

auto ptr = AllocateBlock();

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::Allocate(size_t size)

A request bigger than a block does not fail — the parent answers it. FallbackAllocate is a thin call at the pool's parent id, and the parent allocates the bytes (Engine/Memory/MemoryManager.cpp, MemoryManager::FallbackAllocate()). The pointer that comes back is the parent's, not the pool's: IsMine answers false for it, and the pool's counters never moved, so GetUsage and GetAvailableBlocks say nothing about it. Handing that pointer back to the same pool's Deallocate is nonetheless correct — it recognises the pointer as foreign and forwards it to that same parent.
An exhausted pool returns null. It does not grow, retry, or stop the program. AllocateBlock reports the shortage through the manager and hands back nullptr, and Allocate passes that through. Two consequences a caller has to live with: the pool never enlarges itself, so a pool sized too small stays too small for its whole life; and the complaint is a log line, which MemoryManager::Log() drops entirely unless MEMORY_LOGGING_ENABLED is on (Engine/Memory/MemoryManager.cpp). The null itself is the only reliable signal. The engine's own caller does not look at it: MultiPoolAllocator::Allocate() checks the bank's free-block count first and then returns bank.Allocate(size) as its own result (Engine/Memory/MultiPoolAllocator.cpp), so a bank that emptied between those two steps propagates a null upward. The fatal assert on an out-of-memory path belongs one level up, to a multi-pool that generated a bank and still found no index (Engine/Memory/ThreadSafeMultiPoolAllocator.cpp, ThreadSafeMultiPoolAllocator::NewBankAllocate()); that is review finding 6 in JOURNAL.md (2026-10-05), open robustness work rather than intended design, and this class has no part in it.
Asking for zero bytes costs a whole block. Only size > blockSize is special, so a zero-sized request takes an ordinary block off the free list and reports it as used. Nothing here normalises a zero the way the allocation entry points do, and nothing distinguishes it afterwards: the block is indistinguishable from any other until it is released.
While you hold a block, all of it is yours. The pool writes into a block only as part of releasing it (WriteNextIndex has one caller), so nothing of yours is disturbed while the block is checked out, and the usable size is the full block size — not the size you asked for, and not smaller because the pool stores bookkeeping inside the block. What it stores there, and why that forces the constructor's block-size floor, is the layout the class Coverage section leaves to a design document.
Alignment is inherited, never requested. A block sits at buffer + index * blockSize, and blockSize is a multiple of Config::DefaultAlign (16 bytes), so every block is as aligned as the buffer the parent handed over — which the pool's own testlet asserts rather than assumes (Allocation With A Clamped Block Size, Engine/Memory/PoolAllocator.cpp). There is no alignment parameter, no aligned entry point, and no fallback for a type whose alignof exceeds 16: such a type is silently under-aligned. That is review finding 9 in JOURNAL.md (2026-10-05) — a gap in the interface that is still open, not a design decision to rely on.
Allocation is not synchronised, and it can reach the logger. No lock is taken here, and the empty case logs through the manager. Two threads allocating from one pool corrupt its free list; one thread allocating while another logs from inside a lock that this call would have to take is the shape of the deadlock recorded in JOURNAL.md (2026-10-05) for the class that banks pools. A pool is a single-threaded object.

Parameters

ParameterTypeRequirement
sizesize_tBytes wanted. At most GetBlockSize() keeps the request inside the pool; more is served by the parent; zero is served by the pool and costs a whole block.

Return value

TypeWhat you get
Pointer A block of GetBlockSize() bytes drawn from the pool's buffer — release it with Deallocate. Or, for an oversized request, whatever the parent returned, which is not the pool's memory. Or nullptr: the pool was empty, or the parent could not serve the oversized request either.

Examples

}

pool.Deallocate(ptr, allocSize);

The allocation and its matching release, and the check that matters afterwards: the size you get back is the block size, not the 50 bytes you asked for.
