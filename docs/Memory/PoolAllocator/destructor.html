~PoolAllocator

member of hbe::PoolAllocator Engine/Memory/PoolAllocator.h Returns the buffer to the allocator recorded at construction and releases the registration, under whatever scope the destruction happens in.

Signature

~PoolAllocator()

Function description

Defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::~PoolAllocator(). Two branches: an object with no registration — a moved-from pool, or one whose construction stopped at the zero-capacity early return (constructors) — gives up immediately; anything else returns its buffer and releases its registration.

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::~PoolAllocator()

The buffer goes back to the allocator recorded at construction, whatever scope the destruction happens in. mmgr.Deallocate(parentID, buffer, totalSize) names the recorded id explicitly rather than calling the no-id overload that follows the current scope. That is the fix recorded in JOURNAL.md on 2026-10-05 as F2, and it is a contract about where a pool may die: pools are destroyed by other allocators' teardown — a bank of a multi-pool goes when the vector holding it is cleared, in the middle of that multi-pool's own destruction — so a destructor that asked the ambient allocator to release memory it never borrowed hands a foreign pointer to a stranger. Before the fix, the guard testlet Pool Buffer Returns To Its Recorded Parent in Engine/Memory/PoolAllocator.cpp fails exactly that way, logging that the buffer is allocated by another allocator and trapping. The consequence for a caller: no AllocatorScope is needed to destroy a pool safely, and opening one changes nothing about where the buffer goes.
A recorded id is a number, not a lease on the parent. parentID is validated only as a range (IsValid), and an out-of-range id is replaced by id 0 with a logged error while Assert(id != InvalidAllocatorID) is the only complaint about the invalid one (Engine/Memory/MemoryManager.cpp, MemoryManager::Deallocate()). A registration id is freed for reuse by MemoryManager::DeregisterAllocator() the moment its owner deregisters. So the ordering requirement is on the caller: a pool must be destroyed while its parent's registration is still alive, or its buffer is handed to whatever allocator happens to hold that id by then.
Nothing checks that the blocks came back. The destructor compares nothing against numberOfBlocks; it releases the buffer while blocks are still handed out. Anything still pointing into the pool is then reading memory that has gone back to the parent, and the pool says nothing about it. Returning every block — or being certain nobody holds one — is caller work (Deallocate, GetUsage), and the only witness the tree has is the profile build's leak warning inside MemoryManager::DeregisterAllocator(), a configuration this tree does not compile.
The two size arguments are recomputed, not remembered. totalSize is blockSize * numberOfBlocks again at destruction. Nothing in the class changes either member after construction — the counters that move are the free count and, under PROFILE_ENABLED, the peak — so the product is the same number the constructor allocated. A pool whose members were moved out of never reaches this line at all.
The destructor ends the object for the manager too. buffer and id are reset last, so an object that has been destroyed reads as inert to the accessors — which is not the same as being alive: nothing here prevents the object's own storage from being reused, and the class has no virtual destructor because it is final and never a base. Destruction is implicitly noexcept (verified by compiling a class of the same shape and asserting noexcept(p.~P())), so a throw beneath it ends the process rather than propagating.

Parameters

None.

Return value

Nothing. There is no failure to report: a pool with no registration releases nothing, and a pool with one cannot fail to release.

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::~MultiPoolAllocator()

The one place the engine destroys pools in quantity: banks.clear() runs this destructor over every bank, and the multi-pool has already opened AllocatorScope scope(parentID); as its first statement. That scope is why the fix of this destructor and the fix of the multi-pool destructors had to be tested separately — with the scope in place the multi-pool masks a reverted ~PoolAllocator, so the guard testlet drives a bare pool instead (JOURNAL.md, 2026-10-05).
