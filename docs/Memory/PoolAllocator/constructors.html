Function description

Both non-moving forms are defined in Engine/Memory/PoolAllocator.cpp as PoolAllocator::PoolAllocator(); the only difference between them is the location argument that PROFILE_ENABLED adds. In order, construction interns the name, records the allocator that is current at that moment as parentID, takes one allocation of blockSize * numberOfBlocks bytes from that same current allocator, links the blocks, and registers the object with the MemoryManager under a new id. The pool is a live allocator from the moment the constructor returns; there is no separate initialisation step. 

parentID = hbe::MemoryManager::GetCurrentAllocatorID();
…
const TSize totalSize = blockSize * numberOfBlocks;
if (totalSize <= 0)
{
	return;
}

auto& mmgr = MemoryManager::GetInstance();
buffer = static_cast<Byte*>(mmgr.Allocate(totalSize));
availables = &buffer[0];

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::PoolAllocator()

A block cannot be narrower than sizeof(size_t), and the constructor stops there rather than quietly widening it. Assert(inBlockSize >= sizeof(TSize)); is the first statement of the constructor body, and the release path and allocation path both treat a block as holding that value. A Debug or Dev build therefore ends on an undersized request; a Release build, where Assert is an empty inline function (Engine/Core/Debug.h, RELEASE_BUILD), carries on, because the member initialiser has already floored the stride with std::max(inBlockSize, sizeof(TSize)) and aligned it to Config::DefaultAlign. Either way the caller-visible floor is the same: GetBlockSize never answers less than 16 bytes, so sizing a pool from the number you passed rather than the number you get back under-counts the bytes. Why a free block must be able to hold that value is the pool's internal layout — the reason behind this precondition lives in the free-list mechanism, which the class Coverage section names as owed to a design document; what belongs to a caller is only the floor and the assert.
An empty pool is a different object than an allocator. When blockSize * numberOfBlocks comes out zero — in practice inNumberOfBlocks == 0, since the floored block size cannot be zero — the constructor returns before the allocation, before the free list and before the registration. The result is an object whose id is InvalidAllocatorID, whose buffer is nullptr, and whose availables holds whatever happened to be in memory: the header gives that member no initialiser and this path never reaches the line that writes it. Destroying such an object is safe and every figure it reports is zero, but Allocate is not — AllocateBlock reads that unset head first. A pool of zero blocks is not a pool that is merely full, and the multi-pool that used to build one from a cached {64, 0} pair is recorded as robustness finding 8 in JOURNAL.md (2026-10-05).
The name is interned before the buffer is allocated. name(inName) runs StaticStringTable::Register, which takes the table lock and can grow the table — an allocation of its own from the allocator that is current, which at that instant is still the parent rather than the pool. It is also why inName is a precondition: a null pointer is handed straight to std::string_view inside StaticStringTable::Register, and RegisterAllocator's later substitution of "None" never gets the chance, because it receives a second copy of the same pointer.

The move constructor steals all of it: the id, the parent id, the name, the stride, both counts, the buffer and the free-list head, plus the profile peak when that build runs. It asserts the source held a real registration (Assert(id != InvalidAllocatorID)), then leaves the source inert — invalid ids, null pointers, zero counts, empty name — which is what makes a moved-from pool safe to destroy and useless for everything else. Then it repairs the manager's record for the id it just took: 

auto& allocProxy = mmgr.GetAllocatorProxy(GetID());
…
allocProxy.allocate = allocFunc;
allocProxy.deallocate = deallocFunc;

From Engine/Memory/PoolAllocator.cpp, PoolAllocator::PoolAllocator(PoolAllocator&& rhs)

A move refreshes the manager's function pointers for the id but not the object pointer they are called with. AllocatorProxy::allocator is written once, by RegisterAllocator inside the original constructor, and the move never touches it — while dispatch is allocProxy.allocate(allocProxy.allocator, nBytes) (Engine/Memory/MemoryManager.cpp, MemoryManager::Allocate()). Allocation routed through the pool's id therefore keeps reaching the object that was moved from. Every bank in a multi-pool is a pool that has been moved at least once, and the vector growth that generates a bank moves them again; JOURNAL.md records the measurement of the std::sort case on 2026-10-05 as finding 5 — "Safe by luck, not by contract", latent because nothing in the tree allocates through a bank's own id yet. Do not start.

Return value

Nothing — a constructor. Success is implicit: a constructed pool owns a buffer, holds a registration id, and is ready to be entered as an AllocatorScope. There is no null, no error code, and no query that distinguishes a registered pool from the zero-block object, other than GetID answering InvalidAllocatorID.

The indirect form, and the one that exercises the move constructor: emplace_back constructs a bank in place and std::sort then move-assigns banks into order (operator=, operator<). A multi-pool's own buffer is the parent here, because the call sits inside AllocatorScope allocScope(parentID);.
