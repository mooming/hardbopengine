InlineMonotonicAllocator

Engine/Memory/InlineMonotonicAllocator.h namespace hbe template <size_t Capacity> final Bump allocation inside a member array of Capacity bytes: the arena is the object, an overflow forwards to the parent, and a copy (which is also what a move becomes) duplicates the whole arena under one registration id.

Class description

template <size_t Capacity> class InlineMonotonicAllocator final at Engine/Memory/InlineMonotonicAllocator.h is a bump allocator whose arena is a member array. The storage is declared inside the object — HE_ALIGN uint8_t buffer[Capacity];, where HE_ALIGN is alignas(hbe::Config::DefaultAlign) from Engine/OSAL/OSMemory.h — so there is no backing allocation from any other allocator, the object's size is the arena, and where the object lives is where the memory lives. Confirmed against a struct carrying the same four members with c++ -std=c++2b -fsyntax-only: sizeof(InlineMonotonicAllocator<2048>) is 2064, alignof is 16, and buffer sits at offset 16 — the three preceding members (id, parentID, cursor) occupy exactly the alignment padding, which is what makes the constructor's alignment assert hold.

The constructor does three things: it records the allocator that is current on this thread as parentID (MemoryManager::GetCurrentAllocatorID()), registers this with the MemoryManager as an inline allocator of capacity Capacity, and stores the returned id in id. Registration is what lets code that never sees the object allocate from it: an AllocatorScope opened on GetID routes every later default-allocator allocation through Allocate. That is exactly how the only call sites in the repository use it — the Vector Allocation testlet of InlineMonotonicAllocatorTest::Prepare() in Engine/Memory/InlineMonotonicAllocator.cpp aliases using Allocator = InlineMonotonicAllocator<2048>;, constructs the object from a name alone (Allocator alloc("InlineMonotonicAllocator"); — the arena is the template argument, never a constructor argument), opens an AllocatorScope on alloc.GetID() inside a nested block, and lets an HVector<int> fill it; the vector is destroyed inside that block, which is where the ignored Deallocate happens.

Monotonic means the cursor only moves forward. Allocate rounds the request up to Config::DefaultAlign (16) and hands back buffer + cursor; Deallocate of a pointer inside the arena does nothing but log and report. Individual frees are therefore free but worthless — the memory comes back only when the whole object is destroyed, which is the entire bargain of a bump allocator and the reason a scope is normally opened around a bounded phase rather than a long-lived container.

An object holding one must not be copied, and moving it is a copy. The class declares only a constructor and a destructor, so the compiler still gives it a copy constructor and copy assignment (implicitly defined — the standard marks the implicit copy deprecated because a destructor is user-declared) and gives it no move constructor and no move assignment. An rvalue therefore binds to the copy constructor. Verified twice with c++ -std=c++2b -Wall -Wextra: std::is_copy_constructible_v, std::is_copy_assignable_v, std::is_move_constructible_v and std::is_move_assignable_v are all true for the same declaration shape, and a type with that same shape plus one member whose copy is observable leaves both objects holding their data after auto b = std::move(a); — the copy constructor ran. Replacing that observable member with one that cannot be copied makes the compiler say so directly: call to implicitly-deleted copy constructor on the line that wrote auto b = std::move(a);.
A copy does not duplicate the registration — and it invalidates every pointer already handed out. Copying copies id, so both objects claim the same registration; the registration table keeps the this pointer the constructor passed to RegisterAllocator, so routed allocations (MemoryManager::Allocate(id, n), anything inside an AllocatorScope) keep mutating the original's cursor while copy.Allocate() mutates the copy's. Each object owns its own array and its own cursor, so every pointer the original handed out still points into the original's arena — a copied allocator does not own the memory its GetUsage figure claims it owns. Then both destructors call DeregisterAllocator(GetID()) on the same id, and MemoryManager::DeregisterAllocator ends with proxyPool.Push(allocator): the same proxy slot returns to the free pool twice and can be handed to two later registrations as two different allocators. Nothing here is detectable at runtime in this tree's configuration.
Sizing Capacity wrong fails softly in one direction and expensively in the other. Too small never fails: Allocate logs a warning through MemoryManager::LogWarning and forwards the request to parentID, so the allocator quietly becomes a forwarding layer — one warning log and one parent round trip per overflowed request, with no error anywhere. Too large costs the bytes: Capacity is added to the size of whatever holds the object (a stack frame, one member of an owning object, a static), every copy duplicates all of it, and because Capacity is a template parameter each size is a separate type — it cannot be chosen per instance at runtime, and a class that exposes it in its own template list propagates the decision to its users.
Nothing here is synchronised, and nothing here is measured in the configurations this tree builds. cursor, id and parentID are plain members and the class takes no lock. The MemoryManager registration it relies on does record the owning thread id, but only under MEMORY_VERIFICATION_ENABLED, which Engine/Config/BuildConfig.h sets to 0, so in this tree neither the allocator nor the registration notices a second thread. One instance belongs to one thread, and the leak warning that deregistration would log (stats.usage > 0 in MemoryManager::DeregisterAllocator) is PROFILE_ENABLED code that also does not exist here — an over-full or leaking arena is silent.

Two of its statistics calls sit behind #ifdef __MEMOR_STATISTICS__, and that macro is defined nowhere in the repository (no header, no CMakeLists.txt definition — the Debug and Dev flag sets add only TEST_ENABLED besides their own DEBUG_BUILD / DEV_BUILD marker). In this tree the destructor's arena release report and Allocate's allocation report are dead code in all three configurations, while Deallocate's report is PROFILE_ENABLED code and equally absent. See Coverage.

Template parameters

ParameterKindWhat it constrains
Capacitysize_t non-typeBytes of inline arena. It is the array bound of buffer, the capacity handed to RegisterAllocator, the ceiling GetAvailable counts down from and the end of the range IsMine tests. It must be at least 1: the constructor writes buffer[0] = 0; before anything else, unconditionally.

There is one parameter and it is not a type the allocator serves — the class allocates raw bytes and takes no element type, so the caller does the element arithmetic (n * sizeof(T)) exactly as the callers of InlinePoolAllocator in the allocator catalogue do. Because the bound is a compile-time constant, InlineMonotonicAllocator<1024> and InlineMonotonicAllocator<2048> are unrelated types: no resize, no runtime sizing, and a template that takes the capacity propagates it to everyone who includes it.

Whether InlineMonotonicAllocator<0> is rejected at compile time A claim about what compiles needs a compiler and this wave does not build. What is established by reading is enough to size safely: the constructor writes buffer[0] = 0; with no guard, so Capacity 0 would write past the array whatever the compiler decides about a zero-size member. Recorded here rather than guessed at on the constructor page.
Every path behind #ifdef __MEMOR_STATISTICS__ and #if PROFILE_ENABLED __MEMOR_STATISTICS__ is defined nowhere in the repository, and Engine/Config/BuildConfig.h sets PROFILE_ENABLED to 0, so the destructor's ReportDeallocation of the whole arena, Allocate's ReportAllocation and Deallocate's ReportDeallocation are described from source and have never run in Debug, Dev or Release. The isInline and capacity arguments of the registration are only read by the inlineUsage accounting that is itself PROFILE_ENABLED code.
What a copy does to the accounting inside MemoryManager The class-level consequence is documented (one id, two objects, a proxy slot pushed twice). The manager's own bookkeeping — inlineUsage, usage, the AtomicStackView that owns proxy slots — is owned by the Memory module page, which this wave has not finished either.
Serving a type whose alignment exceeds Config::DefaultAlign (16) No such interface exists: the class takes no alignment argument and rounds requests, not addresses. Every pointer it hands out from the arena is 16-aligned because every cursor step is a multiple of 16, and an over-aligned type would be served at the same 16-byte alignment — a known gap in the interface, the same one recorded for PoolAllocator, not intended design.
What happens to a release of an address that belongs to neither this arena nor its parent IsMine can answer only "inside my array" or "not inside it", so an address in the untaken tail is treated as owned and silently ignored, and every other address is forwarded to parentID untouched. What the parent then does with a pointer it never returned is the parent's contract: with MemoryManager::SystemAllocatorID as parent the release ends in free through SystemAllocator::DeallocateBytes in Engine/Memory/SystemAllocator.h, on an address malloc never handed back. No testlet covers it, and this class cannot answer it — recorded on Deallocate as the consequence, not resolved.
Thread-safety of a shared instance Stated as a fact that nothing in the class or in this configuration's registration path is synchronised or checked. Whether any design intends one arena to be shared across threads is not answered anywhere in the repository, so it is not asserted here. The mechanism that would answer it — MEMORY_VERIFICATION_ENABLED's registering-thread check in MemoryManager::DeregisterAllocator — is switched off in Engine/Config/BuildConfig.h.
Whether the parent is a stack or scope-limited allocator The class stores the parent's id and nothing else, so it cannot know. That question belongs to the allocator catalogue and to DefaultAllocator, whose own contract is the engine's case of a recorded allocator id outliving a short-lived allocator. Same shape of hazard, different class — this one records the parent in a constructor that also owns the arena, so it is the narrower case.
InlineMonotonicAllocatorTest Test-only: declared in Engine/Memory/InlineMonotonicAllocator.h inside #ifdef TEST_ENABLED, with the four testlets Vector Allocation, Allocation (2), Deallocation and Deallocation (2) defined in Engine/Memory/InlineMonotonicAllocator.cpp. All four assert the same thing — that GetUsage is non-zero after a scope that allocated and destroyed — which is the test suite stating that a monotonic arena does not reclaim. It owns no page of its own.
