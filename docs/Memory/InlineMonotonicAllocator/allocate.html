Allocate

member of hbe::InlineMonotonicAllocator Engine/Memory/InlineMonotonicAllocator.h Bumps the cursor inside the member array, or warns and forwards to the recorded parent when the request does not fit.

Signature

[[nodiscard]] TPointer Allocate(size_t requested)

Function description

Defined inline in Engine/Memory/InlineMonotonicAllocator.h as InlineMonotonicAllocator::Allocate(size_t requested). This is the bump: one comparison, one pointer, one addition — and the comparison is the whole policy, because a request the arena cannot hold is not a failure but a forwarding. 

auto size = OS::GetAligned(requested, Config::DefaultAlign);

const auto freeSize = GetAvailable();
if (unlikely(size > freeSize))
{
	auto& mmgr = MemoryManager::GetInstance();
	mmgr.LogWarning([size, freeSize](auto& ls)
	{ ls << "The requested size " << size << " is exceeding its limit, " << freeSize << '.'; });

	auto ptr = mmgr.Allocate(parentID, requested);

	return ptr;
}

auto ptr = reinterpret_cast<void*>(buffer + cursor);
cursor += size;

Three consequences follow from those lines, and every caller depends on all three. The cursor advances by the aligned size, so a 1-byte request spends 16 of the 16-byte Config::DefaultAlign granularity and every address handed out of the arena is 16-aligned for that reason. The availability test is GetAvailable — the same figure the caller can read — so the arena never over-subscribes itself: a request that fits is served from buffer, and one that does not never touches the cursor. And the overflow path asks the recorded parentID for the unaligned requested bytes, which is the allocator that was current when this object was constructed, not whatever scope is open now.

Exhaustion is a warning, never a failure — and it is invisible in this tree. An overflow calls MemoryManager::LogWarning and then MemoryManager::Allocate(parentID, requested). With MEMORY_LOGGING_ENABLED at 0, as Engine/Config/BuildConfig.h sets it, MemoryManager::Log is an empty function: the closure is still built at the call site and the call is still made, but the message never runs. So an arena sized too small becomes a forwarding layer that spends one manager dispatch per request and reports nothing — there is no error code, no null return and no counter that distinguishes a served request from an overflowed one.
An overflowed block belongs to the parent, is not counted here, and is not released by this object. The pointer returned on the overflow path came from another allocator, so IsMine reports false for it and Deallocate forwards it back to parentID — the pairing is correct, and it stays correct only while the same object and the same recorded parent are used. What is lost is the accounting: GetUsage counts cursor alone, so the usage figure understates the memory this object is responsible for, and the destructor releases none of those blocks. A long-lived arena with a small capacity is a permanent client of its parent.

Null is not possible from the arena path — the address is buffer + cursor. It is possible from the parent path, and this function does not test it: MemoryManager::Allocate ends with Assert(ptr != nullptr, "Allocation Failed"), which aborts in Debug and Dev and does nothing in Release, where the null arrives back here and is returned to the caller.

A request of 0 is worth naming, because it behaves differently from the manager's: OS::GetAligned(0, 16) is 0, so the guard passes, the cursor does not move, and the call returns buffer + cursor — a non-null address that a second zero-sized request will receive again. MemoryManager::Allocate returns nullptr for 0 bytes; this arena does not, and nothing here is required to hand out distinct addresses.

Nothing is synchronised. cursor is a plain size_t incremented without a lock or an atomic, so two threads bumping one arena hand out the same block. The function is not reentrant either: the overflow path reaches the manager, and the #if MEMORY_LOGGING_ENABLED report reaches the logger. Both switches that would notice (MEMORY_VERIFICATION_ENABLED and MEMORY_LOGGING_ENABLED) are 0 in this tree. The #ifdef __MEMOR_STATISTICS__ report of every successful allocation to MemoryManager::ReportAllocation is dead code here — that macro is defined nowhere in the repository — so in no configuration does the manager learn what this arena handed out.

Parameters

ParameterTypeRequirement
requestedsize_tBytes wanted. Rounded up to a multiple of Config::DefaultAlign (16) before it is compared against GetAvailable, and that rounded figure — not this argument — is what the arena spends. 0 is accepted and returns the current cursor address without moving it.

Return value

TypeWhat you get
TPointer (void*)16-aligned memory. Either an address inside buffer that belongs to this object and is reclaimed by nothing until the object is destroyed, or — when the arena could not hold the request — a block owned by parentID. Never null from the arena; null only if the parent's own allocator answered null.

No code in the repository calls this function directly. The only path in is through the registration the constructor made: AllocatorScope installs the id, MemoryManager::AllocateByType<T> reads the scoped id, and MemoryManager::Allocate calls the allocFunc lambda the constructor registered, which casts its first argument back to InlineMonotonicAllocator* and calls this. So the growth of an HVector is what reaches it here, and one push_back on an empty vector is one 4-byte request rounded to 16.
