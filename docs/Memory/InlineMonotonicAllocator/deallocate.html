Deallocate

member of hbe::InlineMonotonicAllocator Engine/Memory/InlineMonotonicAllocator.h An owned pointer is ignored on purpose; a pointer outside the arena is forwarded to the recorded parent unchanged.

Signature

void Deallocate(TPointer ptr, TSize requested) noexcept

Function description

Defined inline in Engine/Memory/InlineMonotonicAllocator.h as InlineMonotonicAllocator::Deallocate(TPointer ptr, TSize requested). It is legal to call, and for a block this arena handed out it does nothing. That is the design, not an omission: a monotonic arena reclaims in one direction only, and the release call exists so that a caller holding one pointer does not have to know which of the two possible sources it came from.

From Engine/Memory/InlineMonotonicAllocator.h, InlineMonotonicAllocator::Deallocate(TPointer ptr, TSize requested)

The address range decides everything, so the two branches are one contract seen from both ends. A pointer outside [buffer, buffer + Capacity) is by construction a block Allocate obtained from parentID when the arena overflowed, and forwarding it to the same recorded id is the correct release: the block returns to the allocator that owns it. A pointer inside the range is an arena block, and the function's remaining work is a log line and a profiling report — the cursor does not move backwards, the block is not recorded as free anywhere, and no later Allocate can ever hand it out again. A second release of the same owned pointer is therefore harmless and undetected, because the first one had no effect either.

The only reset this class has is its own destruction, and it takes every pointer with it. Engine/Memory/InlineMonotonicAllocator.h declares no reset, no rewind and no checkpoint: the ways the bytes come back are the destructor (which returns the registration but not the storage, since the storage is the object) and the destruction of whatever owns the object. So "release everything the arena holds" is "let the object die", and every pointer into the arena dies with it — the storage is the caller's, so those addresses keep reading stale bytes rather than faulting. The safe pattern is the one the testlets use: open an AllocatorScope over a bounded phase, destroy everything allocated in it before the arena dies, and never let a pointer outlive the block that declares it.
A null pointer is not special-cased before the range test. IsMine compares ptr against buffer, and the language leaves the result of comparing pointers to unrelated objects unspecified — in practice the null address is below the object, so a null release takes the forwarding branch and reaches MemoryManager::Deallocate(parentID, nullptr, requested). That function returns early on a null pointer but first asserts Assert(nBytes == 0), so releasing null with a non-zero size aborts in Debug and Dev. Compare PoolAllocator::Deallocate, which tests ptr == nullptr itself before anything else.

The requested argument is only ever information: it is the size passed on when the pointer is foreign, and the size named in the log line and in the PROFILE_ENABLED report, whose fourth argument is a literal 0 — the bytes actually reclaimed. Both of those reports are absent in this tree (MEMORY_LOGGING_ENABLED and PROFILE_ENABLED are 0 in Engine/Config/BuildConfig.h), so an ignored release here is silent and uncounted. The function is noexcept while calling the manager and, in a logging configuration, the logger: a throw from either ends the process.

Parameters

ParameterTypeRequirement
ptrTPointer (void*)A block from Allocate on this same object. The address range alone decides the branch, so a pointer from a copy of this object looks foreign and is forwarded to parentID.
requestedTSize (size_t)The size originally asked for. Used for the forwarded call and for the two reports; for an owned block it changes nothing. Passing the rounded size or the original request both work, because nothing compares it.

Return value

None. There is no return value that says "this block was yours and I kept it", so a caller cannot learn whether the arena or the parent served the pointer it is releasing.

From Engine/Memory/InlineMonotonicAllocator.cpp, InlineMonotonicAllocatorTest::Prepare(), testlet "Deallocation"

The String is destroyed inside the inner block while the scope is still open on the arena, so its release arrives here and is ignored — which is the fact the testlet asserts, in four testlets, by requiring GetUsage to be non-zero afterwards. Note the ordering difference from the "Vector Allocation" testlet, where the scope closes first: the scope's lifetime decides which allocator is current when a container dies, and therefore which object this function is even reached on.
