GetUsage

member of hbe::InlineMonotonicAllocator Engine/Memory/InlineMonotonicAllocator.h The cursor: rounded arena bytes bumped so far, and the one counter the class keeps.

Signature

[[nodiscard]] size_t GetUsage() const

Function description

Defined inline in Engine/Memory/InlineMonotonicAllocator.h as InlineMonotonicAllocator::GetUsage(). It returns the cursor, and the cursor is the class's only counter: bytes bumped so far, in the rounded sizes the arena spent. 

Assert(cursor < Capacity);

return cursor;

From Engine/Memory/InlineMonotonicAllocator.h, InlineMonotonicAllocator::GetUsage() const

A completely full arena aborts when you ask it how full it is. The assertion is cursor < Capacity, which is false in the state cursor == Capacity — and that state is ordinary, not corrupt: a Capacity that is a multiple of Config::DefaultAlign (16) can be filled exactly, and Allocate is happy to do it, because its own guard is GetAvailable's Capacity >= cursor, which tolerates zero remaining. So the two accessors disagree about one legal value: a full arena answers GetAvailable with 0 and answers this function with an abort in Debug and Dev. In Release Assert is an empty inline function in Engine/Core/Debug.h and the call simply returns Capacity. Prefer GetAvailable as the "how much is left" question.

The figure counts the arena and nothing else, which makes it a floor rather than a total. Bytes handed out by Allocate's overflow path belong to parentID, never move the cursor, and are not released by the destructor, yet this function is the only usage figure the class has. It also counts rounded bytes: a caller who asked for 1 byte fourteen times reads 224 here, not 14, which is the honest number for "bytes of the array consumed" and the wrong number for "bytes my objects need".

Nothing outside the object learns this number in the configurations the repository builds. The reporting calls that would push it into MemoryManager's inlineUsage record sit behind #ifdef __MEMOR_STATISTICS__ — a macro defined nowhere in the tree — and the record itself is PROFILE_ENABLED code, which Engine/Config/BuildConfig.h sets to 0. Like every other member here it reads a plain size_t with no lock, so concurrently with a bump it is a snapshot.

None.

Return value

TypeWhat you get
size_tcursor: bytes of the member array already bumped, at 16-byte granularity. Excludes anything the parent served. Aborts in Debug and Dev when it equals Capacity; never larger.

Examples

AddTest("Vector Allocation", [this](auto& ls)
{
	Allocator alloc("InlineMonotonicAllocator");
	{
		AllocatorScope scope(alloc.GetID());

		HVector<int> a;
		a.push_back(0);
	}

	if (alloc.GetUsage() == 0)
	{
		ls << "Monotonic Allocator doesn't provide deallocation."
		   << " Usage should not be zero, but " << alloc.GetUsage() << lferr;
	}
});

From Engine/Memory/InlineMonotonicAllocator.cpp, InlineMonotonicAllocatorTest::Prepare(), testlet "Vector Allocation"

This is the only call site in the repository, and all four testlets are the same assertion with different numbers of containers: everything allocated inside the scope has been destroyed, and the usage figure must still be non-zero. Read as documentation, the suite is the engine stating that Deallocate reclaims nothing — the test passes precisely because the counter never goes down.
