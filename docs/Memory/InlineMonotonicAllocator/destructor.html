~InlineMonotonicAllocator

member of hbe::InlineMonotonicAllocator Engine/Memory/InlineMonotonicAllocator.h Deregisters the id and returns the proxy slot; the arena needs no release, because the arena is the object.

Signature

~InlineMonotonicAllocator()

Function description

Defined inline in Engine/Memory/InlineMonotonicAllocator.h as InlineMonotonicAllocator::~InlineMonotonicAllocator(). It asks for the manager and deregisters the id; the arena needs no release, because the arena is the object — a member array whose storage belongs to whoever owns the object.

		mmgr.ReportDeallocation(id, buffer, cursor, cursor);

From Engine/Memory/InlineMonotonicAllocator.h, InlineMonotonicAllocator::~InlineMonotonicAllocator()

MemoryManager::DeregisterAllocator in Engine/Memory/MemoryManager.cpp clears the registration's allocate and deallocate function pointers and ends with proxyPool.Push(allocator), which returns the AllocatorProxy slot to the free pool. That is the whole effect: the cursor is not reset, the buffer is not touched, and the bytes the arena handed out stay exactly where they were.

A pointer into the arena outlives the object as readable memory, and stops being releasable. Nothing is unmapped here — the buffer's storage is the caller's (a stack frame, a member of a heap object, a static), so a pointer still held after this destructor returns keeps reading plausible bytes and no read of one will fault. What changed is the routing: an Deallocate through a second arena object tests IsMine against its own buffer, so the dead arena's pointer looks foreign and is forwarded to that object's parentID. When the recorded parent is MemoryManager::SystemAllocatorID — the ordinary case, since MemoryManager::scopedAllocatorID starts at 0 in Engine/Memory/MemoryManager.cpp — the release ends in free through SystemAllocator::DeallocateBytes in Engine/Memory/SystemAllocator.h, on an address malloc never returned.
The id becomes available to a later allocator, and any saved copy of it follows silently. Because the slot goes back to proxyPool, the next MemoryManager::RegisterAllocator can hand the same integer to a different object. A stored TAllocatorID — which is exactly what DefaultAllocator holds — or an AllocatorScope opened on the old value then reaches the new allocator, and MemoryManager::Allocate cannot tell the difference: it indexes allocators[id] and calls whatever function pointers the slot now carries. Between deregistration and reuse those pointers are null, and MemoryManager::Allocate guards them with Assert(allocProxy.allocate != nullptr) — an abort in Debug and Dev, and in Release a call through a null function pointer.
The leak report exists in the configuration that would skip the pool return. Under PROFILE_ENABLED, DeregisterAllocator logs a memory-leak warning and returns when stats.usage > 0, before proxyPool.Push — a leaking registration never gives its slot back. This class cannot reach that branch in practice: the only accounting it performs is the ReportAllocation inside Allocate, and that sits behind #ifdef __MEMOR_STATISTICS__, a macro defined nowhere in the repository. With PROFILE_ENABLED off, as Engine/Config/BuildConfig.h sets it, the warning is absent and the slot always returns.

Two orderings are worth knowing. A request the arena could not hold was forwarded to parentID by Allocate, and this destructor does not release it: those blocks stay live in the parent until the parent dies, so an arena that overflowed has handed out memory this object never accounted for. And the destructor begins with MemoryManager::GetInstance(), which is FatalAssert(mmgrInstance != nullptr) — live in every configuration — while MemoryManager::~MemoryManager sets mmgrInstance = nullptr. An arena with static storage destroyed after the manager aborts the process during shutdown rather than exiting.

From Engine/Memory/InlineMonotonicAllocator.cpp, InlineMonotonicAllocatorTest::Prepare(), testlet "Vector Allocation"

The arena is declared outside the scope, so it is still alive while the testlet reads GetUsage and only deregisters when the testlet's body ends. That ordering is what the testlet is asserting: the HVector was destroyed inside the scope, its block came back as a Deallocate call that did nothing, and the usage figure still says the bytes are gone — because the only thing that reclaims them is this destructor, and by then nobody is reading the counter.
