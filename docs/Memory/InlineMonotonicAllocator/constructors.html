InlineMonotonicAllocator

member of hbe::InlineMonotonicAllocator Engine/Memory/InlineMonotonicAllocator.h Aligns, touches the arena, records the parent allocator, and registers this address with the MemoryManager.

Function description

Defined inline in Engine/Memory/InlineMonotonicAllocator.h as InlineMonotonicAllocator::InlineMonotonicAllocator(const char* name). It is the only constructor, and it is explicit: there is no conversion from a name to an allocator.

What it does, in the order the source writes it:

Assert(OS::CheckAligned(buffer));
buffer[0] = 0;

parentID = hbe::MemoryManager::GetCurrentAllocatorID();
auto& mmgr = MemoryManager::GetInstance();
id = mmgr.RegisterAllocator(this, name, true, Capacity, allocFunc, deallocFunc);

From Engine/Memory/InlineMonotonicAllocator.h, InlineMonotonicAllocator::InlineMonotonicAllocator(const char* name)

  1. It asserts the arena is aligned to Config::DefaultAlign. The assert exists because the alignment is a layout property the caller can break: HE_ALIGN makes the whole object 16-aligned, and the three members ahead of buffer fill exactly 16 bytes, so a placement construction into an under-aligned address is the one way to arrive here misaligned. In Debug and Dev that aborts; in Release Assert is an empty inline function (Engine/Core/Debug.h) and the misalignment is simply kept.

  2. It writes buffer[0] = 0; — unconditionally, before any size test. That single statement is why Capacity must be at least 1, and it is also what first touches the arena: for a stack-resident object this is where the pages are committed.

  3. It records parentID as the allocator current on this thread (MemoryManager::GetCurrentAllocatorID(), which reads the thread-local scopedAllocatorID and needs no MemoryManager instance). Everything Allocate cannot hold and Deallocate does not own goes to this recorded id, never to whatever scope happens to be open later.

  4. It registers the object: RegisterAllocator(this, name, true, Capacity, allocFunc, deallocFunc), where allocFunc and deallocFunc are non-capturing lambdas converted to the plain function-pointer types AllocatorProxy holds, and the first argument those functions receive is the stored this. The registration therefore names this object's address, not its id: a copy of a constructed allocator is unreachable through the manager, and routed allocations keep mutating the original.

A live MemoryManager is a hard precondition. MemoryManager::GetInstance() is FatalAssert(mmgrInstance != nullptr) followed by a dereference, and FatalAssert is live in every configuration, not only in Debug and Dev. An arena constructed before the manager exists — a namespace-scope object, or any static initialised before Engine builds the manager — aborts the process in this line rather than failing quietly.
A failed registration is not detected. RegisterAllocator returns InvalidAllocatorID after a FatalError log when the proxy pool is empty (the table holds MaxNumAllocators = 256 slots). The constructor stores that value in id without testing it, so the object still works as a bump allocator through its members while every routed path (GetID into an AllocatorScope, or MemoryManager::Allocate(id, n)) reaches the manager's invalid-id branch. The same shape of unchecked failure is recorded for PoolAllocator.
The name is decoration in this tree. RegisterAllocator substitutes "None" for a null name and stores the string in AllocStats only under PROFILE_ENABLED, which Engine/Config/BuildConfig.h sets to 0. Pass a real name anyway: it is what the registration and deregistration log lines print, and those lines exist only when MEMORY_LOGGING_ENABLED is raised from its 0 here.

From Engine/Memory/InlineMonotonicAllocator.cpp, InlineMonotonicAllocatorTest::Prepare()

The capacity is a compile-time constant of the call site, and the object is constructed as a local so the arena lives and dies with the block. Those two facts are the whole safe usage: nothing in the repository stores an arena in a heap object or passes one across a function by value, which is also why the copy behaviour described on the class page has never executed here.
