ReportDeallocation

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The mirror, and the only place a size mismatch between the two halves is caught — then subtracted anyway.

Signature

void ReportDeallocation(TId id, void* ptr, size_t requested, size_t allocated)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::ReportDeallocation(), the mirror of ReportAllocation: allocators call it after releasing a block, and it is the only place in the module where a mismatch between the two halves of a transaction is caught. The whole body is inside #if PROFILE_ENABLED, so a build of this repository links an empty function.

Where the mirror is not exact, it matters:

AspectReportAllocationReportDeallocation
Invalid idError log, debugBreak() outside Release, dropError log, drop — no break
LockingOne nested scope inside a lambda; the diagnostics and log run after it closesOne std::lock_guard for the entire body — the SystemStatistics call and the log line are emitted with statsLock held
Threshold checkusage over capacity → fatal log and returnusage under the amount being released → error log, and then the subtraction runs anyway
A size mismatch wraps the per-allocator figure while the engine total is protected. The body tests stats.usage < allocated, logs "Incorrect Memory usage" and breaks outside Release — and then executes stats.usage -= allocated; regardless, on an unsigned type. The identical test against the engine-wide record does return before subtracting. So one bad pair corrupts that allocator's usage into a huge value, which then trips the capacity check on the next ReportAllocation for the same id. The rule a caller must take from this: allocated has to be exactly the value passed for the same block, which is why the multi-pool passes bank.GetBlockSize() on both sides rather than the caller's size.
It logs while holding the statistics lock. Unlike its sibling, this method's Log call and its statistics.ReportSysMemDealloc(allocated) call both sit inside the lock scope opened at the top of the body. Logging inside a held lock is the exact deadlock shape recorded in JOURNAL.md for ThreadSafeMultiPoolAllocator — the logger allocates its buffer from an allocator, and that allocation can ask for a lock this thread already owns. It is invisible in this tree, where the guard removes the body and IsLogEnabled is hard-coded false, and it is the reason the registration path deliberately closes its scope before logging.
deallocCount moves before the record is checked. ++stats.deallocCount; runs immediately after the per-allocator subtraction, so an allocator's release count includes releases that were later judged invalid at the record level and dropped. The two counts printed together in the Info line are therefore not guaranteed to be a matched pair after a mismatch has been reported.

Parameters

ParameterTypeRequirement
idTIdThe releasing allocator's registration id; invalid → Error log and the report is dropped.
ptrvoid*The block being released, for the log line only — never tracked, never validated.
requestedsize_tThe caller's original request; appears in the messages, and is not used to update totalRequested (that field belongs to the allocation half alone).
allocatedsize_tMust equal the value reported at allocation. This is the number subtracted, so a mismatch is a corrupted statistic rather than a lost block.

Return value

void. A detected mismatch is reported and broken on, never propagated to the caller — the release the allocator already performed is not undone.

Examples

bank.Deallocate(ptr, size);

#if PROFILE_ENABLED
	{
		auto& mmgr = MemoryManager::GetInstance();
		mmgr.ReportDeallocation(GetID(), ptr, size, bank.GetBlockSize());
	}
#endif // PROFILE_ENABLED

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::Deallocate()

The correct pairing: size is the caller's request and travels in requested, while the bank's fixed block size is what both halves report as allocated. The instructive variant is MonotonicAllocator::Deallocate(), which reports mmgr.ReportDeallocation(id, ptr, requested, 0); — a monotonic release returns no capacity, so allocated is zero and the usage figure deliberately keeps climbing until MonotonicAllocator::~MonotonicAllocator() releases the whole cursor in one report (mmgr.ReportDeallocation(id, bufferPtr, 0, cursor);). Any pairing that mixes the two conventions corrupts the statistics as described above.
