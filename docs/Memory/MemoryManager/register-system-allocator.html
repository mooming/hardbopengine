RegisterSystemAllocator

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Fills slot 0 by hand, seeds the capacity total and points this thread at it — constructor only, and once.

Signature

void RegisterSystemAllocator()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::RegisterSystemAllocator(), declared private with one caller: the constructor. It is the only writer of slot 0, and it does not go through RegisterAllocator — the slot is filled in place, which is why slot 0 never appears in proxyPool and why no registration can ever receive SystemAllocatorID. 

using TSysAlloc = SystemAllocator<uint8_t>;
static TSysAlloc systemAllocator;

auto allocFunc = [](void*, size_t nBytes) -> void* { return systemAllocator.allocate(nBytes); };
auto deallocFunc = [](void*, void* ptr, size_t nBytes)
{ systemAllocator.deallocate(static_cast<uint8_t*>(ptr), nBytes); };

auto& allocator = allocators[SystemAllocatorID];
allocator.allocate = allocFunc;
allocator.deallocate = deallocFunc;

Assert(usage.totalCapacity == 0);
Assert(usage.maxCapacity == 0);
usage.totalCapacity = Config::MemCapacity;
usage.maxCapacity = Config::MemCapacity;
Assert(systemAllocator.GetID() == SystemAllocatorID);
SetScopedAllocatorID(SystemAllocatorID);

From Engine/Memory/MemoryManager.cpp, MemoryManager::RegisterSystemAllocator()

Both function pointers are captureless lambdas that convert to the proxy's calling convention while closing over the function-local static SystemAllocator<uint8_t>; their first parameter — the userData the manager would pass — is ignored, which is what makes SysAllocate's habit of passing &allocators[0] as userData harmless. The object itself owns no state: SystemAllocator (Engine/Memory/SystemAllocator.h) has no data members and both its special members are defaulted, so its lifetime as a function-local static is inert. The asserted identity is a tautology — SystemAllocator::GetID() is a constexpr that returns MemoryManager::SystemAllocatorID — so it documents intent rather than testing anything.

In a profiled build the system capacity is counted twice. The unconditional usage.totalCapacity = Config::MemCapacity; above is then added to again inside the PROFILE_ENABLED block (rec.totalCapacity += Config::MemCapacity;), so GetUsage reports 10 GiB of capacity against a 5 GiB Config::MemCapacity, and ReportAllocation's engine-wide overflow check is measuring usage against double the real ceiling. Unremarkable in this tree, where the guard removes the second addition — and the reason the two figures quoted on GetUsage are stated per configuration rather than as one number.
It also sets the constructing thread's scope. The final statement is SetScopedAllocatorID(SystemAllocatorID), which is why an allocation with no scope open anywhere answers from the system allocator rather than failing. It applies to this thread only: any other thread starts at the thread_local initialiser's 0 and coincidentally agrees (GetCurrentAllocatorID).
Slot 0 keeps a proxy id of InvalidAllocatorID. The constructor's seeding loop writes proxy.id for slots 1…255 only, and this method never touches the field, so GetAllocatorProxy(0) hands back a proxy whose own id reads -1 while every other slot reports its index. Nothing in the tree reads it; see the constructor for the shape of the loop that leaves it that way.

Parameters

None. Everything it uses is a constant: Config::MemCapacity (5 GiB) and the type SystemAllocator<uint8_t>.

Return value

void. It cannot fail — there is no slot to run out of — and it reports nothing.
