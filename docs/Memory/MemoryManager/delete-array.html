DeleteArray

member of hbe::MemoryManager Engine/Memory/MemoryManager.h n destructors, then one release — and only the caller knows whether n was right.

Signature

template <typename Type>
	void DeleteArray(Type* ptr, size_t n)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: n explicit destructor calls in ascending order, then one DeallocateTypes with the same count. 

for (size_t i = 0; i < n; ++i)
{
	ptr[i].~Type();
}

DeallocateTypes<Type>(ptr, n);

From Engine/Memory/MemoryManager.h, MemoryManager::DeleteArray()

The element count is an argument because the block cannot carry one: NewArray takes a single allocation with no array-new cookie, so nothing in memory records how many objects were built in it. The release is one call for the whole block, not one per element — the reason the array pair is cheap and the reason a wrong n is silent.

A wrong count fails in three different silent ways. Too small and the remaining objects are never destructed while their storage is returned — their resources leak and any destructor with side effects simply does not happen. Too large and destructors run past the end of the block on memory the allocator may have handed to someone else. Either way the byte count passed down is also wrong, which is the mismatch that corrupts a pool's free list (Deallocate) and, under PROFILE_ENABLED, wraps the usage statistic (ReportDeallocation).
Zero elements does not mean "release nothing" — it means "release this block with size zero". With n == 0 the loop is skipped and DeallocateTypes is still called with the real pointer and a byte count of 0. Deallocate only ignores a null pointer, so a non-null block is dispatched with a size the allocator never handed out. Compare Delete, where a null pointer is a crash and a zero count is not expressible.
Destruction order is ascending, matching NewArray's construction order. A standard container destroys in the reverse of construction; this pair destroys in the same order it built. For element types whose destructors touch neighbours, that is a real difference, and it is a property of these two templates rather than of arrays.
The count's type is not the type it came from. NewArray takes Index size; this takes size_t n. The conversion is silent in both directions, which is how a signed count that was negative on the way in becomes an enormous unsigned one on the way out. Callers that store the count in a Buffer-style byte size recover it by dividing: size / sizeof(T) in BufferUtil::GetMemoryBuffer(), asserted before use.

Parameters

ParameterTypeRequirement
Typetemplate parameterThe element type the array was created with. It selects the destructor and the byte count, exactly as in Delete.
ptrType*A block from NewArray. Null with a non-zero n is a null dereference on the first iteration.
nsize_tExactly the count the array was created with — the same value, not a recomputed one, and not the byte size.

Return value

void. No report, no cleared pointer, and no way to discover after the fact that the count was wrong.

Examples

auto releaser = [&mmgr](TSize size, TBufferData data)
{
	const TSize numElements = size / sizeof(T);
	Assert((numElements * sizeof(T)) == size);

	auto ptr = reinterpret_cast<T*>(data);
	mmgr.DeleteArray<T>(ptr, numElements);
};

From Engine/Resource/BufferUtil.h, BufferUtil::GetMemoryBuffer()

The count that NewArray consumed is reconstructed here from the block's byte size and asserted before it is used — the honest acknowledgement that a pointer cannot carry its own length. The same pairing appears in Engine/Resource/Buffer.cpp and Engine/Resource/BufferInputStream.cpp, where the count is a test constant on both sides.
