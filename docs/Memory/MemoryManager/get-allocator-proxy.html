GetAllocatorProxy

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The registration slot itself, mutable — and an invalid id answers with a live-looking dummy instead of failing.

Signature

AllocatorProxy& GetAllocatorProxy(TId id)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::GetAllocatorProxy(). Given a valid id it returns allocators[id] — the registration slot itself, by mutable reference, so the caller can rewrite the two function pointers, the allocator userData pointer and (under PROFILE_ENABLED) the whole AllocStats record. Given an id that fails IsValid it logs an Error and returns a stand-in instead: 

if (unlikely(!IsValid(id)))
{
	Log(ELogLevel::Error, [funcName = __func__, id](auto& ls)
	{ ls << "[" << funcName << "] Invalid allocator id(" << id << ") is provided."; });

	static AllocatorProxy dummy;
	new (&dummy) AllocatorProxy();

	return dummy;
}

From Engine/Memory/MemoryManager.cpp, MemoryManager::GetAllocatorProxy()

An invalid id answers with a usable-looking dummy, and that is the whole error policy. The intent is that a bad id cannot index allocators out of bounds. The consequence a caller must carry is that the returned reference is a real AllocatorProxy that never fails: a default-constructed proxy has null allocator, allocate and deallocate, so writes to it succeed, reads from it look legitimate, and the mistake surfaces as a log line rather than at the call that made it. Two properties of the dummy are decided nowhere: the static object is shared by every thread that asks with a bad id, and it is placement-reconstructed on each call — while another thread may still hold a reference to it. Choosing between "fail loudly" and "route the dummy to slot 0 so the work at least happens" is a policy decision, recorded as a named omission in Coverage.
Allocation does not come through here, whatever the older design note said. Allocate reads allocators[id] directly after its own range check, so the dispatch path never sees this function and the dummy never intercepts a bad allocation — an invalid id on that path is redirected to slot 0 instead. What this getter owns is inspection and mutation of a registration, and that is what its three call sites in the module use it for.
Mutable access to a slot is exactly as safe as the caller's discipline. PoolAllocator's move constructor is the instructive case (Engine/Memory/PoolAllocator.cpp, PoolAllocator::PoolAllocator(PoolAllocator&&)): it fetches the proxy for the id it just inherited and refreshes allocate and deallocate to lambdas that cast their argument to PoolAllocator* — but it never touches allocProxy.allocator, and dispatch is allocProxy.allocate(allocProxy.allocator, nBytes). The slot therefore keeps handing a moved-from pool to the new pool's own functions. Nothing in the manager can prevent that; this getter is a pointer into the table, not an abstraction over it.

Parameters

ParameterTypeRequirement
idTId (TAllocatorID)The id returned by RegisterAllocator. Never out of bounds — an out-of-range value is answered with the dummy, so this call cannot be used to detect a bad id by exception; compare the returned id field if the distinction matters.

Return value

TypeWhat you get
AllocatorProxy&The live slot for a valid id — mutable, and invalidated only when the slot is deregistered and re-registered (DeregisterAllocator). The function-local dummy for anything else. Never null; there is no way to distinguish the two by reference alone.

Examples

#if PROFILE_ENABLED
	const auto incCapacity = blockSize * numberOfBlocks;
	auto& mmgr = MemoryManager::GetInstance();
	auto& allocProxy = mmgr.GetAllocatorProxy(GetID());
	allocProxy.stats.capacity += incCapacity;
#endif // PROFILE_ENABLED

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::GenerateBank()

The representative use: a multi-pool growing a bank has to tell the manager that its capacity moved, and this getter is the only public door to the AllocStats record that holds it. The write is made without AcquireStatsLock, which is the asymmetry that page documents. The other two sites are PoolAllocator's move constructor (rewiring function pointers) and MultiPoolAllocator::~MultiPoolAllocator(), which re-stamps each bank's proxy thread id under MEMORY_VERIFICATION_ENABLED.
