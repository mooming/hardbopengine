DeallocateTypes

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Turns an element count back into the byte count and releases it — running no destructor on the way.

Signature

template <typename T>
	void DeallocateTypes(T* ptr, size_t n)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h, and the exact counterpart of AllocateByType: it recomputes n * sizeof(T), re-reads this thread's scoped id, and hands both to Deallocate. 

const auto nBytes = n * sizeof(T);
Deallocate(GetScopedAllocatorID(), static_cast<void*>(ptr), nBytes);

From Engine/Memory/MemoryManager.h, MemoryManager::DeallocateTypes()

It does not destruct anything. The name says types, but what the template argument does is turn an element count back into the byte count the block was taken with, so the release arrives with the size the allocator expects. Destructors are the job of Delete and DeleteArray, which call this after running them.

Both halves re-read the scope independently, so a moved scope misroutes the block. AllocateByType and DeallocateTypes each call GetScopedAllocatorID at the moment they run. Storage taken inside one AllocatorScope and released outside it is dispatched to whatever allocator is current at release — which is not an error the manager can detect (Deallocate has no record of who gave out what), and not one the allocator is likely to survive quietly. The correct shape, used by the engine's STL adapter, is to open the scope around each call so the pair cannot diverge: 

AllocatorScope scope(allocatorID);
auto& mmgr = MemoryManager::GetInstance();
mmgr.DeallocateTypes(ptr, n);

From Engine/Memory/DefaultAllocator.h, DefaultAllocator<T>::deallocate()

The count must be the count it was allocated with. A pool uses the size to identify the block being returned (PoolAllocator::Deallocate), and a mismatch corrupts its free list rather than failing. Nothing here stores an element count with the block — a pointer cannot carry one — so n is pure caller obligation, and that is why the array form takes its count as an argument at all (DeleteArray).

Parameters

ParameterTypeRequirement
Ttemplate parameterElement type; only sizeof(T) is used. It must be the type the block was taken with, or the byte count will not match.
ptrT*A block from AllocateByType. A null pointer is ignored by Deallocate, with an assertion that the size was zero too.
nsize_tElement count — the same value passed to the allocation, and subject to the same unchecked n * sizeof(T).

Return value

void. The pointer is not cleared; the caller's copy stays dangling, as it does on every release path in this class.

From Engine/Memory/DefaultAllocator.h, DefaultAllocator<T>::deallocate()

The one production call site, and the shape worth copying: the id is remembered by the adapter (as a snapshot of the ambient allocator at construction) and re-installed as a scope for both the allocation and the release, so a container that outlives the scope it was built in still returns its memory to the right place. Inside the class, Delete and DeleteArray are the only other callers.
