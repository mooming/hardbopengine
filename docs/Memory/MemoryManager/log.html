Log

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Every memory diagnostic funnels through one filtered forward to Engine::Log — and it can be a complete no-op.

Signature

void Log(ELogLevel level, TLogFunc func) const

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::Log(). The body is a filter and one forwarding call: 

#if MEMORY_LOGGING_ENABLED
	if (!IsLogEnabled(level))
	{
		return;
	}

	auto& engine = Engine::Get();
	engine.Log(level, func);
#endif // MEMORY_LOGGING_ENABLED

From Engine/Memory/MemoryManager.cpp, MemoryManager::Log()

A line is therefore a callable, not a formatted string: TLogFunc is std::function<void(std::ostream& out)>, so the caller writes a lambda and the text is only built if the level survives IsLogEnabled. From there the line goes to Engine::Log — the Engine module's own routing and level filtering apply again, so a line can pass this gate and still be dropped by the logger.

The whole method is compiled out here, and the lambda is still built. MEMORY_LOGGING_ENABLED is 0 in Engine/Config/BuildConfig.h, so IsLogEnabled is unreachable and the body is empty: every diagnostic in this module is silently discarded in every build of this repository. Note what that does not remove — the conversion from a lambda to TLogFunc happens at the call site, before the call, so captures are copied and a std::function is constructed and destroyed even where the body cannot run. Lambdas that capture a handful of pointers stay inside the small-object buffer; a capture list heavy enough to exceed it allocates, through the very allocator the line was going to describe.
It needs a constructed Engine, which the manager sometimes does not have. Engine::Get() asserts the engine instance exists (Engine/Engine/Engine.cpp). The manager's own constructor runs before Engine::logger is constructed (MemoryManager), and the cache load it performs logs at Significant and Error — with logging enabled those lines are the ones most at risk, and with it disabled they are simply never written.
A fatal level is not an exemption. Every call in the class goes through this same gate, including the ones that report conditions a caller cannot recover from: SysAllocate without an allocate function, an allocation over capacity, an allocation arriving for a deregistered slot. Those paths pair the log with debugBreak() outside Release, but the report itself is subject to the same MEMORY_LOGGING_ENABLED and threshold tests as a verbose trace line — which is why several pages in this folder describe a failure as "logged and continued" rather than "reported".

Parameters

ParameterTypeRequirement
levelELogLevelChosen by the caller; compared by ordinal against the "Log.Memory" threshold. There is no bypass for high levels.
funcTLogFuncA std::function taking the log stream, passed by value — so the conversion cost is paid at the call site whether or not the line is emitted. It is invoked at most once, and only under MEMORY_LOGGING_ENABLED.

Return value

void. The caller cannot learn whether the line was emitted; IsLogEnabled is the only way to ask beforehand.

The dominant pattern in the module, and an instructive one: the call site wraps itself in the same macro the body uses, so a line that cannot be printed is not even compiled. The two convenience wrappers LogWarning and LogError fix the level and take the callable by const& instead, and are the form most allocators use.
