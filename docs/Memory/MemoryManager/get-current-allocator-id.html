GetCurrentAllocatorID

member of hbe::MemoryManager Engine/Memory/MemoryManager.h This thread's current allocator id: what every allocator records as its parent.

Signature

static TId GetCurrentAllocatorID()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::GetCurrentAllocatorID(): it returns the thread-local scopedAllocatorID and nothing else. It is the public half of the same field the private GetScopedAllocatorID reads — the two bodies are identical, and the difference is only who may call them.

Its dominant use is not allocation at all but adoption: an allocator constructed inside someone else's scope records this value as the parent it forwards to and returns buffers to. Six constructors do exactly that (Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::MonotonicAllocator(); Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::MultiPoolAllocator(); Engine/Memory/StackAllocator.cpp; Engine/Memory/PoolAllocator.cpp; Engine/Memory/InlineMonotonicAllocator.h; Engine/Memory/InlinePoolAllocator.h), and Engine/Container/LinkedList.cpp shows the pairing it depends on — build the pool, open the scope, and the pool's own parent is whatever was current one level out. 

parentID = hbe::MemoryManager::GetCurrentAllocatorID();
bufferPtr = mmgr.Allocate(capacity);

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::MonotonicAllocator()

It answers for this thread only, and a new thread starts at 0. scopedAllocatorID is static thread_local and initialised to SystemAllocatorID in Engine/Memory/MemoryManager.cpp. A worker thread that the task system starts therefore reports 0 even while the thread that queued the work sits inside an AllocatorScope, so anything it allocates lands on the system allocator and never on the pool the caller believed it was using. Nothing in Engine/ propagates a scope across a thread boundary, and a registration takes the parent with it, which is how PoolAllocator guarantees its buffer returns to the right place regardless of where the destructor runs.
It is a snapshot, not a handle. Two calls can disagree, and the engine relies on that being understood: Engine/Core/TaskRegistry.cpp caches the value once at construction as bankAllocatorID and then allocates its record banks against that stored id (TaskRegistry::AllocateBank()) rather than re-reading the ambient scope on every growth. The typed entry points do the opposite — AllocateByType and DeallocateTypes each re-read the scope — so an allocation and its release must sit in the same scope or the block goes to a stranger.

Parameters

None.

Return value

TypeWhat you get
TId (TAllocatorID, an int)This thread's current allocator id: 0 before any scope opens, the id the innermost open AllocatorScope installed, or whatever a caller wrote into the public field directly. It can legitimately be InvalidAllocatorID: SetScopedAllocatorID exempts exactly that value from its range check, and AllocatorScope's default constructor installs it (Engine/Memory/AllocatorScope.cpp, AllocatorScope::AllocatorScope()) — no call site in this tree opens a scope that way, but an unsized Allocate inside one asserts in Debug and Dev and is redirected to slot 0 in Release.

Examples

AllocatorScope scope(allocator);

auto& mmgr = MemoryManager::GetInstance();
auto ptr = mmgr.Allocate(100);

if (mmgr.GetCurrentAllocatorID() != allocator.GetID())
{
	ls << "Current allocator ID is not the given allocator id(" << allocator.GetID() << ')' << lferr;
}

mmgr.Deallocate(ptr, 100);

From Engine/Memory/AllocatorScope.cpp, AllocatorScopeTest::Prepare()

The unit test for the scope mechanism, which is also the clearest statement of what this getter is for: after AllocatorScope scope(allocator) the current id is the allocator's own registration id, and an unnamed Allocate therefore comes from it. The second production use is Engine/Memory/DefaultAllocator.h, DefaultAllocator<T>::DefaultAllocator(), which stores this id as the source a container's memory came from.
