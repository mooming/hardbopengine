IsValid

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The private range test every public entry runs first — and the nine different things a negative answer causes.

Signature

#endif

	[[nodiscard]] static bool IsValid(TAllocatorID id)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h as return id >= 0 && id < MaxNumAllocators;, and marked private — although AllocatorScope is a friend and every public entry point in the class calls it, so nothing outside needs to. MaxNumAllocators is 256 and TAllocatorID is int (Engine/Memory/AllocatorID.h), so the test is exactly "is this an index into allocators".

It is a second copy of a predicate that already exists at namespace scope. Engine/Memory/AllocatorID.h declares a free hbe::IsValid(TAllocatorID) noexcept with an identical body. The two agree today because both read the same MaxNumAllocators constant, and they are still two places a future change has to be made — the bound is shared, the test is not. The module page lists the free one among the module functions; this member is what the manager's own code uses.

What the method does not decide is the interesting half. Every caller runs the same test and then does something different with a negative answer, so an out-of-range id produces nine different outcomes depending on which entry point was reached:

CallerAnswer to false
Allocate, DeallocateError log, then id = 0; — the request goes to the system allocator and still succeeds
GetAllocatorNameReturns "Null", no log
GetAllocatorProxyError log, returns a function-local dummy proxy
DeregisterAllocator (both overloads)Error log, the slot is left untouched
GetAllocatorStatError log, returns a zeroed AllocStats
ReportAllocation, ReportDeallocation, ReportFallbackError log and, for two of the three, debugBreak() outside Release; the report is dropped
SetScopedAllocatorIDError log and id = 0; — with one documented exemption, InvalidAllocatorID itself is allowed through
Being in range is not the same as being registered. Every slot index from 0 to 255 passes this test, including the ones sitting unused in proxyPool with null function pointers, and including a slot whose registration was refused and left nulled. That is why Allocate follows the range check with Assert(allocProxy.allocate != nullptr, …) rather than trusting it — and why, in Release, where Assert compiles away, a valid-but-unregistered id becomes a call through a null function pointer.

The shape every internal use takes: the check is wrapped in unlikely() (Engine/OSAL/Intrinsic.h), so the valid path stays the fall-through, and the branch itself is a policy decision made by the caller rather than by this method. The only caller that does not bail out on a negative answer is Allocate, which substitutes 0 and proceeds — the difference between a guard and a guard that quietly changes the request.
