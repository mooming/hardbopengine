RegisterAllocator

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Pops a free slot, writes the dispatch pointers and returns its permanent id — 255 available, then InvalidAllocatorID.

Signature

TId RegisterAllocator(void* allocator, const char* name, bool isInline, size_t capacity, TAllocBytes allocFunc,
						  TDeallocBytes deallocFunc)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::RegisterAllocator(). A registration is nothing but a slot in allocators, and this method fills one: it pops a free slot from proxyPool, writes the three things needed to route an allocation, and returns the slot's permanent id.

ArgumentWhere it lands
allocatorallocProxy.allocator — an untyped userData pointer, passed back as the first argument of every dispatch: allocProxy.allocate(allocProxy.allocator, nBytes)
allocFunc, deallocFuncallocProxy.allocate / allocProxy.deallocate — function pointers, so a capturing lambda will not compile; every call site passes a captureless one
name, isInline, capacityOnly under PROFILE_ENABLED: AllocStats::OnRegister plus one capacity total. Without profiling the recording lambda does not even capture them, and name survives only in the Info log line.

A null name becomes "None" rather than an error, so registration never fails on the name alone. Under PROFILE_ENABLED the name is interned by AllocStats::OnRegister (name = StaticString(inName);), which means the string need only be readable during the call; without profiling it is not retained at all. The capacity is recorded, never enforced here — enforcement is ReportAllocation comparing usage against it.

No parent allocator is recorded, and that omission is the design. The registration has no parent parameter. The hierarchy the module relies on — a pool returning its buffer to whoever owned it — lives in the allocator object itself, which captures GetCurrentAllocatorID in its own constructor and later calls Allocate(parentID, …) or FallbackAllocate(own id, parent id, …). The manager only ever learns the child.
255 registrations, then InvalidAllocatorID — and the caller is expected to stop. MaxNumAllocators is 256 and slot 0 is never in proxyPool, so the 256th registration is the one that fails: the null pop logs at FatalError and returns InvalidAllocatorID. Nothing in the manager prevents the caller from ignoring that. Production call sites do not — InlinePoolAllocator follows the call with FatalAssert(id != InvalidAllocatorID); and FatalAssert(id != 0); (Engine/Memory/InlinePoolAllocator.h, InlinePoolAllocator::RegisterAllocator()) — but an allocator that does not check goes on to allocate through an invalid id, which Allocate silently redirects to the system allocator. Unbounded bank growth in a multi-pool is the known route to this ceiling; see MultiPoolAllocator.
The id is an array index, so it is reused. Each proxy's id field is written once, by the constructor's seeding loop, and never cleared; popping the same slot again after a deregistration hands the same number to the next allocator. Nothing version-tags a registration, so an id is only meaningful while its registrant is alive — the property PoolAllocator::GetID() is documented around, and the reason a stored id must not outlive the object that obtained it.
What the call is safe to make concurrently. proxyPool is an AtomicStackView, so two threads cannot be handed the same slot, and the statistics half of the update takes the same lock the rest of the class uses in a nested scope that closes before the Info line is emitted. That ordering is deliberate: logging inside a held lock is the deadlock shape recorded in JOURNAL.md for ThreadSafeMultiPoolAllocator. What the method does not serialise is the caller's own setup around the call — two allocators racing to register is fine, two threads mutating one slot through GetAllocatorProxy is not.

Parameters

ParameterTypeRequirement
allocatorvoid*The allocator object, passed back untouched on every dispatch. It must outlive the registration: the manager holds no reference count and will keep calling through these pointers until DeregisterAllocator says otherwise.
nameconst char*May be null, which becomes "None". Retained only under PROFILE_ENABLED, and then interned.
isInlinebooltrue when the allocator's storage lives inside the allocator object itself, which decides whether its capacity and usage land in GetInlineUsage or GetUsage.
capacitysize_tThe total bytes this allocator intends to serve. Added to the corresponding usage record's totalCapacity; an over-estimate makes the overflow diagnostic in ReportAllocation useless, an under-estimate makes it fire on correct code.
allocFuncTAllocBytesvoid* (*)(void* userData, size_t allocSize). Its first argument is the allocator pointer above, so the usual body is a cast and a member call.
deallocFuncTDeallocBytesvoid (*)(void* userData, void* pointer, size_t allocSize). The size must be the one the block was allocated with — see Deallocate.

Return value

TypeWhat you get
TId (TAllocatorID)The slot number, in 1 … MaxNumAllocators-1 — never 0, which is SystemAllocatorID and is written only by RegisterSystemAllocator — or InvalidAllocatorID when no free slot remains. The id names the array element forever, so the same number will be given to the next registrant after a deregistration.

Examples

const auto capacity = ActualBlockSize * ActualNumBlocks * sizeof(T);
id = mmgr.RegisterAllocator(this, "InlinePoolAllocator", true, capacity, allocFunc, deallocFunc);

FatalAssert(id != InvalidAllocatorID);
FatalAssert(id != 0);

From Engine/Memory/InlinePoolAllocator.h, InlinePoolAllocator::RegisterAllocator()

The defensive form, and the only call site that treats the return value as a fact rather than a formality: an inline pool is isInline == true, so its capacity is accounted in the inline total, and its two assertions encode what the registration protocol guarantees. The plain form is id = mmgr.RegisterAllocator(this, name, false, capacity, allocFunc, deallocFunc); in MonotonicAllocator::MonotonicAllocator(), MultiPoolAllocator's constructors, StackAllocator::StackAllocator() and PoolAllocator::PoolAllocator() — all of which assume a slot is available.
