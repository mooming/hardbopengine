ReportFallback

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The only place fallback traffic is counted — it counts the request the child refused, not what the parent spent.

Signature

void ReportFallback(TId id, void* ptr, size_t requested)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::ReportFallback(), declared private and called from exactly one place: FallbackAllocate, under PROFILE_ENABLED. It is where fallback traffic is counted, and nowhere else counts it. 

std::lock_guard lockScope(statsLock);

auto& allocator = allocators[id];
auto& stats = allocator.stats;

++stats.fallbackCount;
stats.totalFallback += requested;
stats.maxFallback = std::max(requested, stats.maxFallback);

From Engine/Memory/MemoryManager.cpp, MemoryManager::ReportFallback()

The counters belong to id, the allocator that declined, even though the bytes came from the parent (FallbackAllocate). That is what makes AllocStats::fallbackCount a useful diagnostic: a non-zero value on an allocator means "requests arrived that this allocator could not serve", which is the signal for a block size or bank geometry that needs adjusting, and GetAllocatorStat is how a caller reads it.

It counts the request, not the answer. totalFallback and maxFallback move by requested, which is what the original caller asked the declining allocator for. The parent may have spent more than that — a multi-pool rounds up to its bank's block size, the system allocator rounds to whatever malloc chose — and the excess is recorded nowhere in this record. So totalFallback is not "bytes obtained by fallback"; it is "bytes that fell back", and dividing it by fallbackCount gives an average request, not an average cost.
A failed fallback is counted the same as a successful one. The body never inspects ptr except to print it in the Verbose line, so a fallback where the parent also failed still increments the count. The pointer is diagnostic only — nothing here records which block was involved, so a fallback cannot later be traced from these numbers.
Invisible in every build of this repository, by two routes. The whole body is inside #if PROFILE_ENABLED, which Engine/Config/BuildConfig.h sets to 0, so the counters never move; and its log line is at Verbose, the one level the default "Log.Memory" threshold suppresses even when logging is compiled in. The multi-pool testlet that asserts stat.fallbackCount != 2 is itself guarded by the same macro, which is why it does not currently prove anything about this method.

Parameters

Return value

void. Nothing about a fallback is reported back to FallbackAllocate, which has already returned by the time this runs.

}

From Engine/Memory/MemoryManager.cpp, MemoryManager::FallbackAllocate()

The only call site, and the reason the method is private: fallback accounting is not something an allocator may report by hand, so the numbers can only come from a request that genuinely went to a parent. Code that wants to fall back calls FallbackAllocate and is counted automatically.
