LoadMultiPoolConfigs

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Reads the cache file in the constructor; a missing, unreadable or incompatible file is a log line and an empty table.

Signature

void LoadMultiPoolConfigs()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::LoadMultiPoolConfigs(), declared private, called once from the constructor. It fills multiPoolConfigCache — the table LookUpMultiPoolConfig searches — from one file, and every failure mode it has is a log line plus an empty cache.

ConditionWhat happensLevel
!OS::Exist(path)Return, cache empty — the normal first runSignificant
BufferUtil::GetReadOnlyFileBuffer(path) yields no dataReturn, cache emptyError
multiPoolConfigCache.Deserialize(buffer) returns falseReturn, cache emptyError
Deserialize succeeded and logging is on and not ReleaseWalk every (blockSize, numberOfBlocks) pair and print itVerbose

The third row is the interesting one, because MultiPoolConfigCache::Deserialize (Engine/Memory/MultiPoolConfigCache.cpp) rejects a file whose stored class name or version does not match its own — the version is 0 — so a cache written by a different build of the engine is not misread, it is refused, and every multi-pool then boots from its compiled-in default geometry.

The loader never sorts, and the search that reads this table requires order. Deserialize appends entries in file order; the ordering guarantee belongs to the writer, whose Serialize calls Normalize() before emitting. So a file edited or concatenated by hand can hold an entry that the binary search will never find, with no diagnostic anywhere. The one ordering check in the loader is over each item's block-size runs, is #if !RELEASE_BUILD, and logs a fatal error rather than refusing the file.
It runs while the engine's logger does not exist yet. The constructor calls this before Engine::logger is constructed (the constructor), and its lines go through Log into Engine::Log. In this tree MEMORY_LOGGING_ENABLED is 0 so the point is moot; where it is on, "the cache file was missing" and "the cache file was corrupt" are precisely the two facts most likely to be lost, which is the argument for making them visible another way.
Relative path, read once, never re-read. The file name is ".multiPoolConfig.dat" with no directory, so the working directory at process start decides which file is read — two applications launched from different directories have different caches. The cache is loaded once, in the constructor, and never reloaded: an allocator created later sees the same table regardless of what happens to the file afterwards.

Parameters

None.

Return value

void. Whether the cache is populated is observable only by calling LookUpMultiPoolConfig and comparing the returned name against the one asked for.

The consumer of whatever ends up in the cache is MultiPoolAllocator::GenerateBanksByCache(), which rebuilds a multi-pool's banks from last run's peak geometry and answers false when the name does not come back — at which point the pool uses its own defaults. Nothing in the engine treats a failed load as an error worth stopping for.
