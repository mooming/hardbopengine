New

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Allocate one element from the scoped allocator, then placement-construct — with no null check in between.

Signature

template <typename Type, typename... Types>
	Type* New(Types&&... args)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: one element of storage from AllocateByType, then a placement construction in it, then the same pointer returned. 

auto ptr = AllocateByType<Type>(1);
auto tptr = new (ptr) Type(std::forward<Types>(args)...);

return tptr;

From Engine/Memory/MemoryManager.h, MemoryManager::New()

Which allocator serves it is decided at run time by this thread's scope (GetScopedAllocatorID), so the object lives and dies inside whoever's AllocatorScope was open at the call — a fact the caller has to respect at destruction time (Delete). The free function hbe::New<TType>(args...) in Engine/Memory/Memory.h is a thin wrapper onto this method and is how most engine code reaches it; the module page lists those wrappers under module functions.

The allocation result is not tested before the constructor runs. There is no null check between the two statements. A zero-size request is impossible here, since the count is the constant 1 and sizeof(Type) is at least one, so the only null that can arrive is an allocator that failed — caught by Assert(ptr != nullptr, "Allocation Failed") inside Allocate in Debug and Dev, and in Release reaching this body as a placement construction at address zero. The engine does not throw on exhaustion at the global level (Engine/Memory/GlobalAllocation.cpp reports and aborts instead of producing std::bad_alloc), and nothing here catches an exception from a constructor either — a throwing constructor leaves the block allocated with no pointer in reach to release it.
Arguments are forwarded, not copied twice. Types&&... is a pack of forwarding references, so an lvalue argument binds to an lvalue constructor and an rvalue moves. What constrains the call is Type's own constructors: there is no static assert, no perfect-forwarding guard and no check that the argument list is even valid before the allocation is taken.
Nothing here knows the object needs Delete. The type is allocated from a scoped allocator, so ordinary delete would hand a pool-owned pointer to operator delete, and a plain destructor call would leak the storage. The matching release is Delete(ptr) — same type, same count of one, same scope — and the pairing is enforced by nothing but discipline. Engine/Memory/Shareable.h shows the convention: create through mmgr.New<Body>(...), destroy through mmgr.Delete<Body>(this).

Examples

auto& mmgr = MemoryManager::GetInstance();
auto newBody = mmgr.New<Body>(std::forward<Types>(args)...);

From Engine/Memory/Shareable.h, Shareable<TType, RefCount>::Body::Create()

The dominant shape, and the pairing that matters: the same class's release path calls mmgr.Delete<Body>(this);, so construction and destruction both go through the manager and both see the same allocator. The second route in is Engine/Memory/Memory.h, where the free New/Delete pair fetches GetInstance and forwards, which is what most call sites use.
