GetMultiPoolConfigCacheFilePath

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The one cache-file name the multi-pool geometry is loaded from and saved to, as a StaticStringID.

Signature

static StaticStringID GetMultiPoolConfigCacheFilePath()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::GetMultiPoolConfigCacheFilePath(). The body builds one function-local static const StaticString path(MULTIPOOL_ALLOC_LOG); and returns path.GetID(), so the string is hashed once per process and every later call is a StaticStringID copy.

MULTIPOOL_ALLOC_LOG is defined in Engine/Config/BuildConfig.h as ".multiPoolConfig.dat" — a bare file name with no directory component, so which file this names depends on the process's working directory at the moment the engine reads or writes it. It is one name for one file shared by both halves of the cache: LoadMultiPoolConfigs reads it in the constructor and SaveMultiPoolConfigs overwrites it at shutdown, which is the whole mechanism by which one run's measured pool geometry becomes the next run's starting geometry.

The return value is an id, not a path. A caller that wants to open the file has to turn the id back into text first — StaticString path(pathStrID); in SaveMultiPoolConfigs is the shape — and that conversion only round-trips for a string that was registered as a StaticString, which the function-local static in this very body is what guarantees.

Parameters

None.

Return value

TypeWhat you get
StaticStringIDThe hash id of ".multiPoolConfig.dat". Never fails and never returns an empty id: the input is a literal.

Examples

StaticString path(GetMultiPoolConfigCacheFilePath());
if (!OS::Exist(path))
{
	Log(ELogLevel::Significant, [path](auto& ls) { ls << "Load MultiPoolConfig: Failed to find " << path; });

	return;
}

From Engine/Memory/MemoryManager.cpp, MemoryManager::LoadMultiPoolConfigs()

Both call sites in the tree are inside this class — LoadMultiPoolConfigs and SaveMultiPoolConfigs — and no allocator or application asks the manager where its configuration came from. That is deliberate: an allocator that wanted the file would still have to go through the manager to get its contents, because the loaded table is a private member (LookUpMultiPoolConfig is the only window onto it).
