FallbackAllocate

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Allocate from the parent, book the event to the child — one hop, no chain, and the block belongs to the parent.

Signature

void* FallbackAllocate(TId id, TId parentId, size_t requested)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::FallbackAllocate(). The body is three lines and they are the whole contract: allocate from parentId, then, under PROFILE_ENABLED, report the event against id with ReportFallback, and return the pointer. 

auto ptr = Allocate(parentId, requestedSize);

#if PROFILE_ENABLED
	ReportFallback(id, ptr, requestedSize);
#endif // PROFILE_ENABLED

	return ptr;

From Engine/Memory/MemoryManager.cpp, MemoryManager::FallbackAllocate()

This is the mechanism by which an allocator degrades instead of failing: a request it cannot serve is sent to the allocator that owns it, while the event is booked to the allocator that gave up, so the fallback counters belong to the child. The memory itself is the parent's from that moment on.

Exactly one hop, and no chain. There is no walk up a parent list and no retry: if parentId cannot serve the request either, whatever that allocator's own failure behaviour is becomes this call's answer. Since the call goes through Allocate, that includes its Assert(ptr != nullptr, "Allocation Failed") — a trap in Debug and Dev, a returned null in Release. Note that id is never validated on this path unless PROFILE_ENABLED is on; only parentId is range-checked, by Allocate.
A fallback block is the parent's block, forever. Nothing marks the pointer. Releasing it through the child means the child must recognise it as foreign and forward the release, which is exactly what the call sites do: PoolAllocator::Deallocate() tests IsMine(ptr) and, when it is not, calls mmgr.Deallocate(parentID, ptr, size); (Engine/Memory/PoolAllocator.cpp). An allocator that adds a fallback path without a matching foreign-pointer release hands the block to the parent and then corrupts its own free list with it.
In practice this is an "too big for me" path, not an "I am empty" path. PoolAllocator::Allocate() calls it on size > blockSize — a request the pool could never satisfy — and StackAllocator::Allocate() and InlineMonotonicAllocator::Allocate() use it for the same purpose on exhaustion of a different kind. A pool that simply runs out of blocks is not automatically redirected; see PoolAllocator::Allocate for what happens in that case.

Parameters

ParameterTypeRequirement
idTIdThe requesting allocator's own id — used for attribution only, and only under PROFILE_ENABLED.
parentIdTIdThe allocator that will actually serve the request. An out-of-range value is logged and redirected to slot 0 by Allocate.
requestedsize_tByte count. 0 returns nullptr before anything happens, and is still counted as a fallback when profiling is on.

Return value

TypeWhat you get
void*Storage owned by parentId's allocator, or nullptr for a zero-size request or a failed parent allocation. The bytes the parent actually consumed may exceed requested — the fallback counters record the request, not the answer (ReportFallback).

The clearest use: a block-size pool cannot serve anything larger than its block, so oversized requests go to the parent and the pool's own statistics still show that it declined them. StackAllocator::Allocate() and InlinePoolAllocator::Allocate() follow the same shape for requests they cannot fit.
