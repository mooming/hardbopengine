RecordGlobalAllocation

member of hbe::MemoryManager Engine/Memory/MemoryManager.h What the replaced operator new reports: cumulative bytes and requests, safe in the earliest static initialiser.

Signature

static void RecordGlobalAllocation(size_t nBytes) noexcept

Function description

Defined in Engine/Memory/GlobalAllocation.cpp as MemoryManager::RecordGlobalAllocation(), and the body is two relaxed fetch_add: nBytes into globalAllocationBytes and 1 into globalAllocationCount. Both counters are namespace-scope std::atomic objects value-initialised to zero in that translation unit, so they are constant-initialised before any dynamic initialiser runs and the earliest static initialiser in the process is already accounted for.

Its caller is not engine code but the replaced allocation functions in the same file: every operator new overload funnels through RecordAllocation(), which calls this and then decides whether the caller's return address falls inside the macOS shared cache (GetOSAllocationCount). RecordAllocation is handed the caller's requested size, not the size passed to malloc: the zero-size normalisation (const size_t requestSize = size == 0 ? 1 : size;) is applied to the allocation only, so a zero-byte request increments the count and adds nothing to the byte total.

Why these counters exist alongside the allocator statistics at all. A std::vector, a std::string and every other standard container reach the heap through operator new, which no AllocatorScope can intercept — so without this entry point that traffic is invisible to ReportAllocation and to every allocator's own figures. The two measures are not interchangeable: this one counts bytes requested by the caller, ReportAllocation counts capacity obtained from an allocator, and SystemAllocator's own traffic is deliberately counted only on that second path (GetGlobalAllocationBytes states the consequence).
Never logs, never allocates, never fails. An accounting path that allocated would re-enter the allocator it is measuring, and one that logged would allocate a log line. The body touches nothing but the two atomics, which is what makes it callable from operator new itself; it is noexcept for the same reason.

Parameters

ParameterTypeRequirement
nBytessize_tThe size the caller asked operator new for. Zero is legal and adds nothing to the byte total while still counting as a request.

Return value

void. Nothing reports failure, and nothing can: the counters are cumulative and never decrement.

Examples

const auto totalBefore = MemoryManager::GetGlobalAllocationCount();

std::vector<size_t> values;

for (size_t i = 0; i < 64; ++i)
{
	values.push_back(i);
}

const auto totalAfter = MemoryManager::GetGlobalAllocationCount();

if (totalAfter <= totalBefore)
{
	ls << "std::vector growth through operator new was not counted globally" << lferr;
}

The test that proves the wiring, and the only place in the tree a caller reads the figure it writes. Nothing in Engine/ calls RecordGlobalAllocation directly; the replacement operators are the sole production caller, which is exactly the point — engine code allocates, and the accounting happens underneath it.
