ReportMultiPoolConfiguration

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Append one pool's geometry to this run's log — PROFILE_ENABLED only, and the name's odd spelling is the header's.

Signature

void ReportMultiPoolConfiguration(StaticStringID uniqueName, TPoolConfigs&& poolConfigs)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::ReportMultiPoolConfiguration(), declared inside #if PROFILE_ENABLED and therefore absent from every configuration this repository builds.

The body is a single statement:

auto& data = multiPoolConfigLog.GetData();
data.emplace_back(uniqueName, std::move(poolConfigs));

From Engine/Memory/MemoryManager.cpp, MemoryManager::ReportMultiPoolConfiguration()

That is all it does: append one MultiPoolAllocatorConfig — a name plus a TPoolConfigs (std::vector<PoolConfig>, the (blockSize, numberOfBlocks) pairs) — to this run's log, the table SaveMultiPoolConfigs writes out at shutdown. It validates nothing, never searches for an existing entry with the same name, and does not touch the cache that the loader filled and that LookUpMultiPoolConfig reads. Reports for the current run and configuration for the next boot are deliberately separate tables, and only a save operation moves one into the file.

Repeated reports for one name are merged — later, somewhere else. Every call appends unconditionally, so a pool that reports twice leaves two entries. The reconciliation happens in MultiPoolConfigCache::Normalize() (Engine/Memory/MultiPoolConfigCache.cpp), which Serialize calls before writing: entries are sorted by uniqueName, runs with the same name are merged by PoolConfigUtil::MergeMax taking the larger block count per size, and entries whose configuration is empty are dropped. A caller may therefore report as often as it likes — but the merge is a max, so reporting a shrunken geometry does not shrink the saved one.
The argument is moved from, and the ordering decides whether it survives to the file. std::move(poolConfigs) leaves the caller's vector in a moved-from state, so a caller that reuses it must rebuild it. And because the only writer of the file runs from PreEngineShutdown, a report made later than that — which is what a report from a destructor is, and both call sites are MultiPoolAllocator::ReportConfiguration() and ThreadSafeMultiPoolAllocator::ReportConfiguration(), reached from their destructors — appends to a table that is about to be destroyed with the manager. In this tree the whole path is compiled out, so the cache file is never rewritten by a run at all.

Parameters

ParameterTypeRequirement
uniqueNameStaticStringIDThe multi-pool's interned name — the same id LookUpMultiPoolConfig will one day search for. Nothing checks that a pool reports under the name it was loaded under.
poolConfigsTPoolConfigs&&The (blockSize, numberOfBlocks) pairs to record, taken by move. An empty vector is legal here and is discarded only later, by Normalize().

Return value

void. Nothing is reported back: not whether a name was already present, and not whether a later save will run before the manager dies.

Examples

	Assert(reportedBlocks == peakBlocks, "ReportConfiguration: the reported block count ", reportedBlocks,
		   " does not match the summed bank peak ", peakBlocks);

	auto& mmgr = MemoryManager::GetInstance();
	auto uniqueName = GetName();
	mmgr.ReportMultiPoolConfiguration(uniqueName.GetID(), std::move(configs));

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::ReportConfiguration()

The only producer, and it is guarded by an assertion first: a multi-pool sums its banks' peak block usage and refuses to report a total that does not match, because a wrong number here becomes next run's starting geometry. GetName() is interned on the way in, so the name reported is the same id the pool would be looked up by — with the caveat on PreEngineShutdown about which pools get to report before the file is written.
