GetAllocatorStat

member of hbe::MemoryManager Engine/Memory/MemoryManager.h A copy of one allocator's statistics under PROFILE_ENABLED — the only stats accessor that takes a snapshot.

Signature

#if PROFILE_ENABLED
	AllocStats GetAllocatorStat(TAllocatorID id)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::GetAllocatorStat(), declared inside #if PROFILE_ENABLED — so in a build of this repository, where that macro is 0, the method does not exist and neither does the AllocStats member it copies. Everything on this page is read from the source of a configuration the tree does not currently compile.

It is the one accessor in the class that hands back a value rather than a reference into the manager, and that is the point: the copy is made while statsLock is held, so the twelve fields that come back (name, isInline, capacity, usage, maxUsage, totalRequested, maxRequested, totalFallback, maxFallback, allocCount, deallocCount, fallbackCount — see Engine/Memory/AllocStats.h) belong to one instant. Contrast GetUsage and GetInlineUsage, which hand out live references and take nothing.

An invalid id answers with a default record, not a failure. The body logs Error and returns a copy of a function-local static const AllocStats stats; — the all-zero record AllocStats::AllocStats() builds, whose name is the empty string. A caller cannot tell that from an allocator that legitimately has done nothing except by comparing names, and every real registration has a non-empty one.
The lock is held for the copy only. The scope covers the read of allocators[id].stats and nothing else, so a caller that then prints the twelve fields is not holding anything — which is what makes this safe to call from a reporting path, and also why a caller must not expect the numbers still to be true a statement later. It is a snapshot of the manager's view, and that view is only as good as the allocators' own ReportAllocation/ ReportDeallocation discipline.
Callers must be inside the same guard as the declaration. Every call site in the module wraps itself in #if PROFILE_ENABLED for exactly this reason: MultiPoolAllocator::PrintUsage(), InlinePoolAllocator's testlet and the multi-pool testlets in Engine/Memory/MultiPoolAllocator.cpp all keep their GetAllocatorStat calls out of the non-profiled branch. Code that wants one figure in both configurations has to fall back to what the allocator itself tracks — which is why the testlets print "MultiPoolAllocator has been created" in the #else branch instead of a capacity.

Parameters

ParameterTypeRequirement
idTAllocatorIDThe registration whose statistics are wanted. Out-of-range → an Error log and a zeroed copy (IsValid decides).

Return value

TypeWhat you get
AllocStatsA consistent copy, taken under statsLock. It is a snapshot: no later allocation is reflected in it, and nothing about the allocator's live state can be inferred from it after the call returns.

Examples

auto& mmgr = MemoryManager::GetInstance();
auto stats = mmgr.GetAllocatorStat(GetID());

log.Out([&stats](auto& ls) { ls << "Usage = " << stats.usage << " / " << stats.maxUsage; });

log.Out([&stats](auto& ls) { ls << "Capacity = " << stats.capacity; });

log.Out([&stats](auto& ls)
{
	ls << "Alloc: " << stats.allocCount << ", Dealloc: " << stats.deallocCount
	   << ", Fallback: " << stats.fallbackCount;
});

From Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::PrintUsage()

The dominant use: take one snapshot, then print from it, so a multi-line report is internally consistent even though allocations are happening elsewhere. The fallbackCount in the last line is filled by ReportFallback, which is what makes a non-zero value meaningful at all — see FallbackAllocate for who triggers it.
