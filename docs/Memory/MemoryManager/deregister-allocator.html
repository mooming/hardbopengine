DeregisterAllocator

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Clears the slot and returns it to the pool — what happens to a live block, and what a refusal costs, differ by build flag.

Signature

void DeregisterAllocator(TId id)

void DeregisterAllocator(TId id, const hbe::source_location& srcLocation)

Function description

Both are defined in Engine/Memory/MemoryManager.cpp as overloads of MemoryManager::DeregisterAllocator(); the second is inside #if PROFILE_ENABLED and therefore does not exist in a build of this repository. Deregistration is the inverse of RegisterAllocator: it clears the slot's two function pointers and returns the slot to proxyPool, making its id available to the next registration.

The one-argument body runs these steps in this order, and the order is the contract:

#StepCompiled in
1IsValid fails → Error log, return. The slot is untouched.always
2Info log — the allocator's name under PROFILE_ENABLED, otherwise ID(n)always
3allocator.allocate = nullptr; allocator.deallocate = nullptr;always
4Thread-id mismatch → Error log, debugBreak() outside Release, return without returning the slotMEMORY_VERIFICATION_ENABLED
5stats.usage > 0 → leak Warning, debugBreak() outside Release, return without returning the slotPROFILE_ENABLED
6Under statsLock: subtract usage from the record, subtract capacity from maxCapacity, stats.Reset()PROFILE_ENABLED
7proxyPool.Push(allocator) — the id becomes reusablealways
A live block is checked only where the numbers exist, and this tree has no numbers. The leak detection at step 5 compares stats.usage, which is only ever non-zero because allocators called ReportAllocation and ReportDeallocation — both of whose bodies are PROFILE_ENABLED. Engine/Config/BuildConfig.h sets that to 0, along with MEMORY_VERIFICATION_ENABLED, so in every build of this repository steps 4, 5 and 6 do not exist: an allocator is deregistered with bytes still handed out, the slot returns to the pool, and nothing anywhere detects it. The block itself is untouched — deregistration never walks live allocations, because the manager keeps no record of what it gave out — and releasing it later dispatches to whoever holds the slot.
Identity is a slot index and slots are reused, so a stale id names someone else's allocator. allocators[i].id is written once, in the constructor's seeding loop, and is never cleared; step 7 puts the number back into circulation. An id held past the lifetime of its registrant is therefore not dangling in the usual sense — it is valid, in range, and points at the next allocator that got the slot. The manager's only defence is the Assert(allocProxy.allocate != nullptr) inside Allocate, which catches a slot that was deregistered but not yet re-taken, and which compiles away in Release. What a caller holding a live block must do is not answered by any source, comment or test: named as an omission in Coverage, and there is no testlet for the case.
A refused deregistration costs a registration slot for the life of the process. Step 3 has already nulled the function pointers by the time the checks at steps 4 and 5 run, and both of them return without reaching step 7. So a leak at PROFILE_ENABLED leaves a slot that is neither usable (no allocate function) nor available (never pushed back), and the manager is one of its 255 registrations poorer. It also leaves the caller believing it deregistered something: the method returns void, so refusal is visible only in the log. DeregisterSystemAllocator inherits the same shape at shutdown, where ~MemoryManager clears the global handle regardless.
The second overload's extra argument is never read. Its body validates the id, takes statsLock, calls stats.Report(), releases the lock and then delegates to the one-argument form — so everything the srcLocation parameter could have contributed is discarded, and the only observable difference is that AllocStats::Report() pushes one record to SystemStatistics before teardown. Note also that the type itself, hbe::source_location, is forward-declared in Engine/Memory/MemoryManager.h as struct source_location; and has no definition anywhere under Engine/; every use of it in the module — PoolAllocator's srcLocation member, StackAllocator::TSrcLoc, the call in StackAllocator::~StackAllocator() — is likewise behind PROFILE_ENABLED, which no configuration here enables.
One of the two leak checks can never run. The PROFILE_ENABLED block contains two identical if (unlikely(stats.usage > 0)) tests; the second prints a shorter message and returns, and is unreachable because the first one returns first. It is a leftover of an earlier shape of this function rather than a second condition, and it is the reason a reader who checks only for "a leak warning" may look at the wrong log line.

Parameters

ParameterTypeRequirement
idTId (TAllocatorID)The id from RegisterAllocator. An out-of-range value is logged and ignored; slot 0 is a legal argument, which is how DeregisterSystemAllocator works.
srcLocationconst hbe::source_location&Second overload only, and unused by the body — see the note above. Call sites obtain it from their own member (StackAllocator::~StackAllocator()), which is captured at construction, not at destruction.

Return value

void. There is no way for a caller to learn that the deregistration was refused, which is the design's most consequential omission on this page.

Examples

#if PROFILE_ENABLED
	mmgr.DeregisterAllocator(GetID(), srcLocation);
#else // PROFILE_ENABLED
	mmgr.DeregisterAllocator(GetID());
#endif // PROFILE_ENABLED

From Engine/Memory/StackAllocator.cpp, StackAllocator::~StackAllocator()

Every allocator in the module calls one overload or the other from its destructor; the branch above is the only place the pair is chosen. The two that matter for ordering are MultiPoolAllocator::~MultiPoolAllocator(), which calls it after banks.clear() has released the banks, and PoolAllocator::~PoolAllocator(), which releases its buffer first for the same reason — because after step 3, a release routed through this id has nowhere to go.
