MemoryManager

Engine/Memory/MemoryManager.h final singleton The allocator registry every other allocator hangs off: 256 proxy slots, the thread-local current allocator, the typed New and Delete pair, and the two halves of the engine's allocation accounting.

Class description

class MemoryManager final at Engine/Memory/MemoryManager.h is the registry and dispatch table every allocator in the engine hangs off. It owns a fixed array of MaxNumAllocators (256) AllocatorProxy slots, and a registration is nothing but a slot: the allocator object as void*, its two function pointers, and — under PROFILE_ENABLED — an AllocStats record. Allocation is one indirect call through that slot (MemoryManager::Allocate() does allocProxy.allocate(allocProxy.allocator, nBytes)), so the manager knows nothing about any allocator's strategy. An allocator is PoolAllocator, MultiPoolAllocator, StackAllocator, SystemAllocator or anything else that can be reduced to the two calling conventions TAllocBytes and TDeallocBytes.

There is exactly one instance, and it is a member of Engine (Engine/Engine/Engine.h, Engine::memoryManager), constructed as memoryManager(*this) before Engine::logger and Engine::statistics. The constructor publishes itself into the file-scope mmgrInstance and calls engine.SetMemoryManagerReady(), so GetInstance() is a valid global handle from that moment — which is what lets an allocator constructed by a static initialiser register before Engine::Initialize() has run. The destructor clears mmgrInstance, and GetInstance() after that point is a FatalAssert and std::abort(), not a null return.

The second axis is which allocator a call goes to. Every allocation that does not name an id uses this thread's scopedAllocatorID, and AllocatorScope — a friend class, because the two accessors it needs (GetScopedAllocatorID and SetScopedAllocatorID) are private — is the RAII way to nest a scope. That is the whole mechanism by which a PoolAllocator serves code that never mentions it: LinkedListTest::Prepare() in Engine/Container/LinkedList.cpp builds one pool and then opens AllocatorScope allocScope(alloc); over the pool object itself — the template constructor that forwards to that allocator's GetID() — and from that statement on, every allocation made inside the block reaches the pool without naming it. See the PoolAllocator page for the recording rules, and AllocatorScope for the three constructors.

The third axis is accounting, and it is split in two because the two halves measure different things. ReportAllocation and ReportDeallocation are called by allocators to publish bytes they have handed out — capacity, per allocator and per engine, all under PROFILE_ENABLED. RecordGlobalAllocation and RecordGlobalFree are called by the replacement global operator new and operator delete in Engine/Memory/GlobalAllocation.cpp, which catch what no allocator scope can intercept: a std::vector or std::string that reaches the heap directly. Those eight counters are the only part of this class that is unconditionally live, and the test suite reads them as deltas around a testlet (Engine/Test/TestCollection.cpp, TestCollection::RunTestAt()).

Most of this class is compiled out in the configurations this repository builds. Engine/Config/BuildConfig.h sets PROFILE_ENABLED, MEMORY_LOGGING_ENABLED, MEMORY_VERIFICATION_ENABLED and FORCE_USE_SYSTEM_MALLOC all to 0, with no per-configuration override. So the statistics members (AllocStats inside every proxy, the two UsageRecords, allocCount, deallocCount), every diagnostic log line, the thread-ownership check, the leak warning at deregistration, GetAllocatorStat, the two-argument DeregisterAllocator overload and the body of SaveMultiPoolConfigs do not exist in a build of this tree. Two consequences that a caller cannot see from the header: Log and IsLogEnabled return false and do nothing, so GetAllocatorName answers "Unknown" for every id; and an allocation that leaks through a deregistered allocator is reported by nothing at all (DeregisterAllocator).
A live block does not pin the id it came from. DeregisterAllocator clears the slot's two function pointers and pushes the slot back on proxyPool; nothing consults the callers that still hold bytes from it. So Allocate on a deregistered id either hits an Assert on the null function pointer (Debug and Dev) or calls whatever the next RegisterAllocator put in that slot with a pointer belonging to a dead allocator (Release). See DeregisterAllocator for what is and is not detected, and the Coverage row below for what no source answers.
Identity is a slot number, and slots are reused. allocators[i].id is written once, in the constructor's loop over i = 1 … MaxNumAllocators-1, and is never cleared, so an id a caller once received names the same array element forever and is handed back out by the next registration after a deregistration. SystemAllocatorID (0) is deliberately not in proxyPool: the constructor pushes slots 1 and up, so RegisterAllocator can never return 0, and RegisterSystemAllocator is the only writer of slot 0. Every allocator that registers asserts the consequence (Engine/Memory/InlinePoolAllocator.h, InlinePoolAllocator::RegisterAllocator() asserts id != InvalidAllocatorID and id != 0).
The scoped allocator is per thread and is not inherited. scopedAllocatorID is static thread_local, initialised to 0. A thread that the task system starts therefore opens at SystemAllocatorID even when the thread that spawned it sits inside an AllocatorScope: work handed to a worker silently leaves the scope. Nothing in Engine/ propagates a scope across a thread boundary, and the field is public, so any code can write it without saving the previous value (SetScopedAllocatorID is the path that validates and logs).
What the manager locks, and what it does not. statsLock is taken only on the PROFILE_ENABLED statistics paths — registration, deregistration, reporting, GetAllocatorStat — and AcquireStatsLock exists to let an allocator add its own figures the same way. The dispatch path takes no lock at all: Allocate reads a slot and calls through it, which is safe because the slot table is fixed and a proxy's function pointers are only rewritten between a registration and a deregistration. Registration itself is lock-free rather than mutex-guarded — the free-slot list is an AtomicStackView — but the std::mutex in the same path is taken inside it, so registration and logging are one nesting order and JOURNAL.md records a deadlock in exactly that shape for the class that banks pools (ThreadSafeMultiPoolAllocator).

Template parameters

None. MemoryManager is final and not a template. It carries one alias template (TVector) and eight member function templates (AllocateByType, DeallocateTypes, New, NewArray, Delete, DeleteArray), and in every one of them the type parameter chooses a size and a constructor — never an allocator. Which allocator is used is a runtime decision made by the scoped id (GetScopedAllocatorID), so a template argument cannot pin one.

Non-member helper functions

None. The module's free functions live in Engine/Memory/Memory.h and are indexed by the module page: the four overloads of New and Delete, of which the two that name no allocator are thin calls into MemoryManager::New and MemoryManager::Delete. The id vocabulary — TAllocatorID, MaxNumAllocators, InvalidAllocatorID, the free IsValid — is declared in Engine/Memory/AllocatorID.h, and the private IsValid member is a second copy of it, so a change to the range must be made twice.

Coverage

Not documented hereWhy
Whether reusing a deregistered id while a block from it is still live is intended. Named omission. The code answers the mechanical half — the slot is pushed back on proxyPool and the next RegisterAllocator hands out the same number — but no source, comment or test states what a caller holding a live block must do, and there is no testlet for the case. What the pages assert is only what the code does: see DeregisterAllocator. The policy belongs to whoever owns the module, not to this reference.
Whether GetAllocatorProxy's dummy proxy is meant to be usable, and what it should do with a call. Named omission, and it was already recorded in the manager's design document before these pages existed; that document now defers the three behaviours it owned to GetAllocatorName, RegisterAllocator and GetAllocatorProxy, and leaves this one open. The dummy is a function-local static shared by every thread and re-constructed on each call, and a default proxy routes nowhere; choosing between "fail loudly" and "route the dummy to slot 0" is a decision, not a finding.
Thread-safety of the statistics as a whole. Named omission. Every write path inside MemoryManager that touches an AllocStats holds statsLock, but the engine's allocators write the proxy they were handed without it (Engine/Memory/MultiPoolAllocator.cpp, MultiPoolAllocator::GenerateBank() adds to allocProxy.stats.capacity after GetAllocatorProxy and before any AcquireStatsLock). Whether the lock is a requirement on callers or only a convenience is not stated anywhere, and this tree's PROFILE_ENABLED is 0, so nothing here has ever run. The two-allocator lock order is documented for the one class that has a locking protocol, in the thread-safe multi-pool locking design.
What a registration after shutdown is meant to do. Named omission. Slot 0 is the one proxy whose id field is never written — the constructor seeds slots 1…255 only, and RegisterSystemAllocator fills slot 0's function pointers without naming it — while DeregisterSystemAllocator pushes that id-less slot back onto proxyPool. A RegisterAllocator reached after that pops slot 0, reads id as InvalidAllocatorID, and either trips the assert on the way out or returns -1 in Release having written the registration there. No source, comment or test says what should happen to a late registrant, and the same silence covers whether allocators[0].id is deliberately left -1. What the pages assert is the mechanism: see DeregisterSystemAllocator and the constructor.
How long a registered allocator's interned name stays valid. Named omission. GetAllocatorName returns a pointer into the StaticString intern table (Engine/String/StaticString.h) rather than into the registration slot, so the pointer does not die with the slot — but whether an interned entry is ever released is a question for the String module, and this wave has not written its pages. The same module owns StaticStringID ordering, which is what LookUpMultiPoolConfig's binary search and MultiPoolConfigCache::Normalize both compare by.
Every path behind #if PROFILE_ENABLED, #if MEMORY_LOGGING_ENABLED, #if MEMORY_VERIFICATION_ENABLED and #if FORCE_USE_SYSTEM_MALLOC All four are 0 in Engine/Config/BuildConfig.h with no per-configuration override, so those paths have never compiled in this tree; the same limitation is recorded for PoolAllocator. Every sentence about them on these pages is read from the source and labelled as such, and GetAllocatorStat, ReportAllocation, ReportDeallocation, Log and SaveMultiPoolConfigs name their own compiled-out halves.
What the replaced global operator new and operator delete do — the malloc backing store, the posix_memalign path, the new_handler loop, the abort instead of std::bad_alloc, and the OS-image caller bucket That is Engine/Memory/GlobalAllocation.cpp, a translation unit with no header of its own, so it is not an entry a module page can link. Its eight counters are methods of this class and own pages here (RecordGlobalAllocation and the seven getters); the replacement operators themselves belong to a Memory design document under docs/ that this wave has not written.
The multi-pool cache file's on-disk format, its versioning and the normalisation that keeps its entries sorted Belongs to MultiPoolConfigCache, MultiPoolAllocatorConfig and PoolConfig — none of which owns a page yet, so LookUpMultiPoolConfig documents only what a caller of this class can depend on: the ordering the binary search assumes and the shape of a miss.
Engine::Log, Engine::GetStatistics() and SystemStatistics's ReportSysMemAlloc / ReportSysMemDealloc / Report(const AllocStats&) Contracts of the Engine and Core modules. These pages say when the manager calls them and what the call means for a memory figure; the log formatting, the level filters those calls then pass through, and what a SystemStatistics report becomes are documented there. One fact here is unavoidable: the manager's constructor logs while Engine::logger has not been constructed yet, because memoryManager precedes logger in Engine's member order.
What each registered allocator does with the registration it is given — parent-id recording, bank ownership, the inline-versus-external capacity question Owned by each allocator's own pages: PoolAllocator, MultiPoolAllocator, ThreadSafeMultiPoolAllocator. The remaining allocators (SystemAllocator, DefaultAllocator, MonotonicAllocator, StackAllocator, InlinePoolAllocator, InlineMonotonicAllocator) do not own pages yet, so their call sites are cited by file and symbol instead of linked.
