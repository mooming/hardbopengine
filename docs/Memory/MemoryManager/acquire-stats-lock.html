AcquireStatsLock

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Hand the caller a locked guard on the statistics mutex — which the manager's own callers do not always take.

Signature

std::lock_guard<std::mutex> AcquireStatsLock()

Function description

Defined in the class body of Engine/Memory/MemoryManager.h — the header carries the whole definition, so the call inlines into every includer and there is no .cpp half to read. Its body is return std::lock_guard(statsLock);: it locks the manager's private std::mutex and hands the caller the RAII guard that unlocks it.

Its reason for existing is that GetAllocatorProxy hands out the registration slot itself, mutable, and under PROFILE_ENABLED that slot contains an AllocStats the manager is concurrently updating from ReportAllocation and ReportDeallocation. An allocator that wants to add its own figures to that record is expected to take this guard while it does, so its write is serialised against the manager's.

What the manager itself guards with statsLockCompiled in
The AllocStats::OnRegister bookkeeping and the capacity totals in RegisterAllocatorPROFILE_ENABLED
The usage/capacity subtraction and stats.Reset() in DeregisterAllocatorPROFILE_ENABLED
The whole statistics update in ReportAllocation and ReportDeallocation, and the counters in ReportFallbackPROFILE_ENABLED

The dispatch path: Allocate, Deallocate, SysAllocatenever — no lock is taken on allocation
A discarded call is a lock you held for one statement. The guard is a return value, so mmgr.AcquireStatsLock(); locks and unlocks without protecting anything. The name invites exactly that mistake; the correct form binds the temporary, as in auto lock = mmgr.AcquireStatsLock();, and the guard's scope must cover the write it exists to protect.
Nothing in this repository calls it, and at least one writer ignores it. There is no call site under Engine/ or Applications/ — the only in-module writer that touches a proxy's statistics from outside the manager does so without the guard: allocProxy.stats.capacity += incCapacity; in MultiPoolAllocator::GenerateBank() (Engine/Memory/MultiPoolAllocator.cpp). Combined with the read in GetAllocatorName, which also runs unlocked, the honest statement is that statsLock serialises the manager's own statistics writes and nothing else. Whether callers are required to take it is a named omission, recorded in Coverage, and in this tree the guarded members do not exist at all because PROFILE_ENABLED is 0.
Do not hold it across a log call. The manager's own diagnostics are emitted outside its lock scopes, with one exception: the two-argument DeregisterAllocator calls stats.Report() while holding the guard. That shape — log while holding a lock, where the logger allocates from an allocator that will ask for that lock — is the deadlock JOURNAL.md records for ThreadSafeMultiPoolAllocator, and the protocol that avoids it is written down in the thread-safe multi-pool locking design.

Parameters

None.

Return value

TypeWhat you get
std::lock_guard<std::mutex>An already-locked guard on statsLock, deduced by class template argument deduction. Move-only and non-copyable, so binding it to a named variable is the only way to keep the lock. The method is non-const, so it cannot be called through a const MemoryManager&.

Examples

Illustrative — no call site for this exists in the repository; the manager uses the same mutex internally with a local std::lock_guard instead.

auto& proxy = mmgr.GetAllocatorProxy(GetID());
{
	auto lock = mmgr.AcquireStatsLock();
	proxy.stats.capacity += incCapacity;
}

This is the pairing the method was written for: a proxy reference obtained from GetAllocatorProxy, then a write performed under the guard the manager uses for the same fields. The real code in MultiPoolAllocator::GenerateBank() does the first half and skips the second.
