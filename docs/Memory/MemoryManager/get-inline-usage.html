GetInlineUsage

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The engine-wide total for inline allocators, by reference — and a permanently zero record in a build of this tree.

Signature

[[nodiscard]] auto& GetInlineUsage() const

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: return inlineUsage;. The record it hands back is the engine-wide total for allocators registered with isInline == true — those whose storage lives inside the allocator object rather than in a buffer they allocated elsewhere — which is why their capacity is not mixed into the other total. Registration chooses the bucket (RegisterAllocator); this getter only reads it.

The declared return type is auto& in a const member function, so deduction makes it const UsageRecord&: the caller sees the six counters described on the class page (allocCount, deallocCount, totalUsage, maxUsage, totalCapacity, maxCapacity) and cannot write them.

In a build of this repository the record is permanently zero. Every writer of this record — the capacity bookkeeping in RegisterAllocator, the subtraction in DeregisterAllocator, the increments in ReportAllocation and ReportDeallocation — is inside #if PROFILE_ENABLED, and Engine/Config/BuildConfig.h sets that to 0. The member itself is not guarded, so the getter compiles and answers an all-zero record — which is not the same fact as "no inline allocator allocated anything", and a caller that prints it as usage will be reporting a constant. GetUsage differs only because RegisterSystemAllocator seeds its totalCapacity and maxCapacity outside the guard.
A reference, not a snapshot. The return binds the member directly, so a reference held across further allocations observes it changing — and under PROFILE_ENABLED those changes happen while the writer holds statsLock, which a reader of this getter does not take. Copy the record if the six numbers have to agree with each other; hold the reference only if reading a tear is acceptable. Whether the lock is meant to be a requirement on readers is named in Coverage.
Nothing in the repository calls it. GetInlineUsage and GetUsage have no call site under Engine/ or Applications/: the engine's memory summary is assembled from per-allocator GetAllocatorStat copies and from SystemStatistics, not from these two totals. They are the only public window onto the engine-wide UsageRecords, and they are unexercised.

Parameters

None.

Return value

TypeWhat you get
const UsageRecord&The live inline-allocator total by reference — all six fields zero in a build of this tree, and, elsewhere, figures that move under you.

Examples

Illustrative — no call site for this exists in the repository; the allocators report into these totals but nothing reads them back.

const auto& inlineTotal = mmgr.GetInlineUsage();
const auto& otherTotal = mmgr.GetUsage();

ls << "usage = " << inlineTotal.totalUsage + otherTotal.totalUsage
   << " / " << inlineTotal.totalCapacity + otherTotal.totalCapacity;

The intended shape: the two records are complementary halves of one engine total, selected at registration by isInline, so a summary that wants "everything" has to add them. Copying them out as above is also the way to read six numbers that belong to the same instant.
