LookUpMultiPoolConfig

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Binary search over the loaded cache — a miss returns a shared default whose name is not the one you asked for.

Signature

const MultiPoolAllocatorConfig& LookUpMultiPoolConfig(StaticStringID uniqueName) const

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::LookUpMultiPoolConfig(): a binary search over multiPoolConfigCache — the table LoadMultiPoolConfigs read from the cache file at construction — keyed by a multi-pool's interned name. A hit also emits a Warning line listing every (blockSize, numberOfBlocks) pair it found; a miss returns a static default.

From Engine/Memory/MemoryManager.cpp, MemoryManager::LookUpMultiPoolConfig()

The ordering the search requires is a property of the file, not of this call. MultiPoolConfigCache::Deserialize copies entries out of the buffer in the order it finds them and never sorts; the sorted invariant comes from MultiPoolConfigCache::Serialize, which calls Normalize() — std::sort on MultiPoolAllocatorConfig::operator<, which compares uniqueName alone. So the binary search is only as correct as the last write, and a cache file that was hand-edited, concatenated or written by an older layout can produce a miss for an entry that is plainly present. Nothing here validates the order — the ordering check that exists in the loader is over each item's block-size runs, and only outside Release.

An empty cache and a miss answer identically. Both return the same function-local static const MultiPoolAllocatorConfig null;: default-constructed, so uniqueName is a default StaticStringID and configs is empty. The reference is always valid, so a caller cannot detect the difference from the reference alone — the contract in use is to compare the returned name against the one asked for: 

auto& cacheItem = mmgr.LookUpMultiPoolConfig(nameID);
if (cacheItem.uniqueName != nameID)
{
	return false;
}

which is the only reliable test, and is how both call sites (MultiPoolAllocator::GenerateBanksByCache() and ThreadSafeMultiPoolAllocator::GenerateBanksByCache()) decide whether to boot from cached geometry or from their own default configuration.

The on-hit log line is at Warning. Finding an entry is the expected outcome, yet the line is emitted at warning level, so with MEMORY_LOGGING_ENABLED on, every successful cache hit is reported as if it were notable. It is a diagnostic of convenience rather than a signal, and it is filtered by IsLogEnabled like any other — silent, in this tree.

bool MultiPoolAllocator::GenerateBanksByCache(MemoryManager& mmgr)
{
	auto nameID = name.GetID();
	auto& cacheItem = mmgr.LookUpMultiPoolConfig(nameID);
	if (cacheItem.uniqueName != nameID)
	{
		return false;
	}

	auto& configs = cacheItem.configs;
	for (auto& config : configs)
	{
		InlineStringBuilder<1024> str;
		str << name << '_' << config.blockSize << '_' << config.numberOfBlocks;

		banks.emplace_back(str.c_str(), config.blockSize, config.numberOfBlocks);
	}

	return true;
}
