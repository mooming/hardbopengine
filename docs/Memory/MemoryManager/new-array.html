NewArray

member of hbe::MemoryManager Engine/Memory/MemoryManager.h One block, then size constructions from the same argument list — and only the caller knows how many there were.

Signature

template <typename Type, typename... Types>
	Type* NewArray(Index size, Types&&... args)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: one block big enough for size elements, then size constructions in ascending address order, then the block pointer. 

auto ptr = AllocateByType<Type>(size);

for (Index i = 0; i < size; ++i)
{
	new (&ptr[i]) Type(std::forward<Types>(args)...);
}

return ptr;

From Engine/Memory/MemoryManager.h, MemoryManager::NewArray()

The allocation is one block, not one per element — which is the point of the array form, and the reason its release must name the count. Every element is constructed from the same argument list, so what is built is size copies of one value, not a sequence: BufferUtil uses exactly that: mmgr.NewArray<T>(numElements, defaultValue) inside BufferUtil::GetMemoryBuffer(), whose release side recovers the count as size / sizeof(T) — the only reason the count can be reconstructed later at all.

The count is an Index, and it is the caller's to remember. Index is TIndex (Engine/Core/Types.h), and it is converted to size_t by AllocateByType, so a negative value becomes an enormous request whose n * sizeof(T) product wraps like any other. Nothing stores the count with the block: DeleteArray takes its own size_t n, and getting either number wrong skips destructors, runs extra ones, or releases the wrong byte count — see Deallocate for what a size mismatch does.
A constructor that throws mid-loop leaves earlier elements constructed and the block unreclaimable. There is no try, no rollback and no partially-built path: the loop simply stops, the earlier objects are never destructed and the storage is never released, because the caller never receives the pointer. This engine does not run on exceptions at the allocation boundary (Engine/Memory/GlobalAllocation.cpp reports and aborts rather than producing std::bad_alloc), which makes the case theoretical — but the code itself offers no protection, and a constructor that throws is a leak by construction.
Construction order is ascending, and destruction order is not the reverse. Elements are built at ptr[0] … ptr[size-1], and DeleteArray destroys them in the same ascending order. For types whose destructors depend on a neighbour's state, that is not the order a standard container would give you — the pairing is a fact about this pair of templates, not about arrays.

Return value

TypeWhat you get
Type*The first of size constructed elements in one contiguous block from the scoped allocator, or nullptr for a zero count. There is no array-new cookie, so the block is exactly size * sizeof(Type) bytes and knows nothing about itself.

Examples

auto ptr = mmgr.NewArray<T>(numElements, defaultValue);

From Engine/Resource/BufferUtil.h, BufferUtil::GetMemoryBuffer()

One call per buffer, every element seeded with the same value, and the count carried by the caller — the surrounding Buffer tracks it and hands it back to mmgr.DeleteArray<T>(ptr, numElements); on the way out. A testlet of the same shape appears in Engine/Resource/Buffer.cpp as mmgr.NewArray<int>(TestSize, -1).
