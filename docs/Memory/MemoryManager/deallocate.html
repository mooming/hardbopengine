Deallocate

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The size must be the one the block arrived with, and nothing here can tell you it was not.

Signature

void Deallocate(TId id, void* ptr, size_t nBytes)

void Deallocate(void* ptr, size_t nBytes)

Function description

Both are defined in Engine/Memory/MemoryManager.cpp as overloads of MemoryManager::Deallocate(), and the unsized form is again one line through the thread's scoped id (GetScopedAllocatorID). The shape mirrors Allocate with two differences that matter: the null test comes first and takes the size with it, and there is no result to check.

The size must be the size the block arrived with. The manager does nothing with nBytes but pass it on, and the allocators do a great deal with it: a pool releases a block back into its free list using the size to identify the block (PoolAllocator::Deallocate), a multi-pool resolves the bank the same way, and ReportDeallocation subtracts exactly that number from the usage it was given. A release with a different size than its allocation therefore corrupts an allocator's bookkeeping rather than failing — and ReportDeallocation, which is the one thing that would notice, is compiled out of this tree.
Nothing detects a double release. The manager keeps no record of live blocks — the reports it receives are counters, not a table — so a second release of the same pointer is indistinguishable from a first. The only defences are inside the allocators: PoolAllocator::Deallocate() checks IsMine(ptr) and, for a block whose index falls outside its own range, logs "is not alloacted by this." and drops it. Releasing a block through the wrong id is answered the same way at best and by free-list corruption at worst.
The unsized overload is scope-sensitive in both directions. An allocation and its release each re-read the ambient id, so a block allocated inside an AllocatorScope and released after that scope closes is dispatched to a different allocator. The module's own destructors are the example of the fix: MultiPoolAllocator::~MultiPoolAllocator() opens AllocatorScope scope(parentID); as its first statement before clearing its banks, and PoolAllocator::~PoolAllocator() avoids the problem by naming the id explicitly — mmgr.Deallocate(parentID, buffer, totalSize);.

Parameters

ParameterTypeRequirement
idTIdThe allocator that served the block. Out-of-range is logged and redirected to slot 0, exactly as on the allocation side.
ptrvoid*A live block from that allocator. Null is ignored, with an assertion that the size was zero as well.
nBytessize_tMust equal the count the block was allocated with — including any rounding the caller applied, which is why AllocateByType and DeallocateTypes are a pair.

Return value

void. The caller is never told whether the release reached the allocator it was aimed at; the pointer is not cleared and not marked, because nothing here knows about it.

Examples

const size_t totalSize = blockSize * numberOfBlocks;
Assert(buffer != nullptr);

auto& mmgr = MemoryManager::GetInstance();

The disciplined form: the id is named, the size is recomputed from the same factors used at allocation, and the release happens before deregistration — after step 5 of that method, this id has no deallocate function left. The scope-relative form is the unit test in Engine/Memory/AllocatorScope.cpp, where a block requested from an open scope is released from inside it.
