GetAllocatorName

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Three different answers, only one of them a name — and in this tree every valid id answers "Unknown".

Signature

const char* GetAllocatorName(TAllocatorID id) const

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::GetAllocatorName(). It answers in three different ways and only one of them is a name, so the first thing a caller must know is which question the answer is responding to.

ConditionAnswerWhat it actually means
id fails IsValid (the unlikely fast-out)"Null"The id was never registrable: InvalidAllocatorID, a negative value, or >= MaxNumAllocators.
PROFILE_ENABLED onallocators[id].stats.nameThe name that RegisterAllocator was given, interned by AllocStats::OnRegister; "None" if a null name was passed.
PROFILE_ENABLED off"Unknown"Names are not stored at all in this configuration — the AllocStats member that holds them is compiled out of AllocatorProxy.

"Null" and "Unknown" are two different facts and must not be collapsed into one "no name" case by a caller: the first says the id is out of range, the second says the id may be perfectly good and this build simply does not record what it is called. Engine/Config/BuildConfig.h sets PROFILE_ENABLED to 0 with no per-configuration override, so every build of this repository answers "Unknown" for every valid id — including the log lines in Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::Deallocate() and Engine/Memory/InlineMonotonicAllocator.h, InlineMonotonicAllocator::Allocate() that call this specifically to label themselves.

The pointer comes from the intern table, not from the proxy. AllocStats::OnRegister stores the name as StaticString(name), and Engine/String/StaticString.h documents that type as an interned string holding only a StaticStringID; the implicit operator const char*() is what lets the body return stats.name directly. So the returned text is not storage owned by the registration slot, and it does not die the moment the slot is recycled. Whether an interned entry is ever released is a question for the String module, recorded as an omission here rather than answered.
This read is not covered by statsLock. The body indexes allocators[id].stats.name with no lock held, while the paths that write a name — RegisterAllocator and the stats.Reset() inside DeregisterAllocator — take the lock. The page states both facts and draws no conclusion; the class-wide question of what the lock is required to protect is named in Coverage, and the same asymmetry is catalogued for the writer side on AcquireStatsLock.

Parameters

ParameterTypeRequirement
idTAllocatorIDAny value at all — this getter never rejects one, it changes its answer instead. Pass the id from RegisterAllocator or from an allocator's GetID().

Return value

TypeWhat you get
const char*Either "Null", "Unknown" or the registered name, per the table above. Never null, so a caller can print it unconditionally — but printing it in a build of this tree tells the reader nothing about which allocator produced a log line.

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::Deallocate()

The shape every call site uses: label a diagnostic with the allocator that was actually asked — here a buffer that does not belong to this pool, whose release is about to be dropped. Note what this makes dependent on a build flag: the message's identity, not its correctness. The whole call site sits behind MEMORY_LOGGING_ENABLED, and even where that is on, IsLogEnabled decides whether the lambda runs.
