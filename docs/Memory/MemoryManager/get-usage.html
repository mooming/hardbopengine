GetUsage

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The non-inline engine total — zero usage counters over a capacity the constructor seeds outside every build flag.

Signature

[[nodiscard]] auto& GetUsage() const

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: return usage;. This is the UsageRecord for every allocator that is not inline — which in practice means all of them that allocate their own backing buffer, plus SystemAllocator, which registers with isInline == false from RegisterSystemAllocator. The inline counterpart is GetInlineUsage; the two are complementary halves of one total, and neither is a sum of the other.

The declared auto& in a const member deduces to const UsageRecord&, so the six fields listed on the class page are readable and not writable, and the reference is to the live member rather than a copy.

The one figure this record holds in every configuration is a capacity. RegisterSystemAllocator sets usage.totalCapacity = Config::MemCapacity; and usage.maxCapacity = Config::MemCapacity; outside any PROFILE_ENABLED guard, asserting first that both were zero. Config::MemCapacity is 5 GiB (Engine/Config/EngineConfig.h). So a build of this repository — where every writer of allocCount, deallocCount, totalUsage and maxUsage is compiled out — answers {0, 0, 0, 0, 5 GiB, 5 GiB}: a real declared capacity over an all-zero usage history, which reads as "nothing has been allocated" only because the accounting is not in the binary.
The capacity is a declaration, not a limit. Nothing on the allocation path compares against it. What it does is give ReportAllocation a ceiling to test the running total against: exceed it and the manager logs at FatalError and breaks outside Release, then continues with the over-shot figure recorded. A caller who treats this record's totalCapacity as an enforceable budget will be disappointed in exactly the way the MaxBaseMemory constant already is — that one is read by nothing at all.
No call site exists, and the reference is unsynchronised. Nothing under Engine/ or Applications/ reads either usage getter; the engine's memory reporting goes through per-allocator GetAllocatorStat copies instead. And where the writers do exist, they hold statsLock while a reader of this getter takes nothing — so copy the record out before treating its fields as one consistent moment. The wider question of what the mutex is required to cover is recorded in Coverage.

Examples

Illustrative — no call site for this exists in the repository.

const auto& rec = mmgr.GetUsage();

if (rec.totalUsage * 2 > rec.totalCapacity)
{
	ls << "Non-inline allocators are past half of their declared capacity";
}

The comparison this record exists to support. Note the two caveats above while reading it: in a build of this repository the left side is always zero, and even elsewhere the capacity is a ceiling that produces a diagnostic rather than a refusal.
