ReportAllocation

member of hbe::MemoryManager Engine/Memory/MemoryManager.h An allocator publishing what it handed out — allocated moves the counters, requested only feeds the request stats.

Signature

void ReportAllocation(TId id, void* ptr, size_t requested, size_t allocated)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::ReportAllocation(), and called by allocators, never by code that wants memory: after a pool, a stack or the system allocator has produced a pointer it tells the manager about the event here. The whole body sits inside #if PROFILE_ENABLED, so in a build of this repository the method exists, links, and does nothing — every statistic this page describes is read from the source, not observed.

The two size arguments are not the same number and the counters treat them differently:

Field movedMoved byNotes
stats.usage, maxUsage, allocCountallocatedCapacity the allocator actually consumed, per allocator; maxUsage is the running high-water mark.
stats.totalRequested, maxRequestedrequestedWhat the caller asked for; the pair is what an average-request/peak-request comparison needs.
the corresponding UsageRecord's allocCount, totalUsage, maxUsageallocatedEngine-wide total, chosen by stats.isInline — inline versus everything else.
allocCount (the manager's own member)oneNot reachable through any getter; it only appears in this method's log line (allocCount).

All of that happens inside a lambda that holds statsLock and copies the resulting AllocStats and UsageRecord out by value. The two diagnostics that follow are evaluated against those copies, after the lock is released — so a concurrent allocation can move the live figures before the check runs, and the numbers a caller sees in the message are the snapshot's, not the current ones.

Over capacity is a fatal log plus a break, and the over-flowed value stays. stats.usage > stats.capacity logs at FatalError and, outside Release, calls debugBreak() — then returns. Nothing rolls the increment back, so the record keeps the value that triggered the warning, and the engine carries on running. The engine-wide comparison (rec.totalUsage > rec.totalCapacity) is a second, separate fatal log and does not return early, so an allocator that is individually over its capacity can also be reported as breaking the total. Both halves are compiled together — the Log call is unconditional within the block, only the debugBreak() is guarded by #if !RELEASE_BUILD — which is the pattern described in the manager's design document.
Slot 0 feeds the engine's system-memory figure from here and nowhere else. The last statement is if (id == SystemAllocatorID) { engine.GetStatistics().ReportSysMemAlloc(allocated); } — the pairing that makes SystemStatistics's system heap number meaningful. Two consequences: a build with PROFILE_ENABLED off has no system-memory figure at all, since SystemAllocator::AllocateBytes() only calls this method inside that same guard; and the path calls Engine::Get(), which asserts the engine instance exists (Engine/Engine/Engine.cpp), so a system allocation reported before Engine is constructed is a failure on the engine's readiness, not on this class's. What a SystemStatistics report becomes is documented in the Core module.
The ptr argument is diagnostic only. It is never stored, never compared against a table of live blocks and never used to decide anything — the manager keeps no per-pointer record, which is exactly why a deregistration cannot detect the bytes that are still out (DeregisterAllocator). Its value is that the fatal and info lines can be matched to a debugger address.

Parameters

ParameterTypeRequirement
idTIdThe reporting allocator's own registration id. Invalid → Error log, debugBreak() outside Release, and the report is dropped.
ptrvoid*The pointer that was handed out, for the log line.
requestedsize_tBytes the caller asked for; feeds totalRequested/maxRequested only.
allocatedsize_tCapacity this allocator considers itself to have spent. Every usage figure moves by this, so it must be the same number ReportDeallocation will pass for the same block.

Return value

void. Reports are never refused except on an invalid id, and there is no way to tell a dropped report from a recorded one.

Examples

auto ptr = reinterpret_cast<void*>(buffer + cursor);
cursor += size;

#if PROFILE_ENABLED
	{
		auto& mmgr = MemoryManager::GetInstance();
		mmgr.ReportAllocation(id, ptr, requested, size);
	}
#endif // PROFILE_ENABLED

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::Allocate()

The pattern across the module: the allocator reports the space it consumed (size, its own aligned reservation) rather than the caller's requested. The other reporters are InlinePoolAllocator::Allocate(), which passes its constant BlockSizeInBytes, MultiPoolAllocator::Allocate(), which passes bank.GetBlockSize(), InlineMonotonicAllocator::Allocate(), and SystemAllocator::AllocateBytes() — the last of which passes OS::GetAllocSize(ptr), the real block size malloc chose, so its usage figures are capacity rather than requests by construction.
