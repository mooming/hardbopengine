SaveMultiPoolConfigs

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The write half of the cache, entirely inside PROFILE_ENABLED — it saves this run's reports, not the loaded table.

Signature

void SaveMultiPoolConfigs()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::SaveMultiPoolConfigs(), declared private, and the entire body — from the first declaration to the last log line — sits inside #if PROFILE_ENABLED. In every configuration this repository builds, where that macro is 0, the method is an empty function with no effect.

What it does where profiling is on:

const size_t size = GetOutputSize();
auto pathStrID = GetMultiPoolConfigCacheFilePath();
StaticString path(pathStrID);

…

auto buffer = BufferUtil::GetWriteOnlyFileBuffer(path, size);
auto result = multiPoolConfigLog.Serialize(buffer);

if (result != size)
{
	Log(ELogLevel::Error, [path](auto& ls) { ls << '[' << func << "] Failed to deserialize the file " << path; });

	return;
}

The source of what gets written is a different table from the one that is read. This serialises multiPoolConfigLog — this run's reports, appended by ReportMultiPoolConfiguration — not multiPoolConfigCache, the table loaded at start-up. Entries are only appended, never merged with what was loaded, so a pool that reports nothing in a run contributes nothing to the file even if last year's cache contained it. Combined with the single call site in PreEngineShutdown, that is the whole reason most pools' geometry never reaches the file: a multi-pool reports from its own destructor, which runs after this method.
Two quirks a reader should not spend an hour on. The failure message for a serialisation that wrote the wrong number of bytes reads "Failed to deserialize the file" — the wrong verb, copied from the loader, and a real dead end if trusted. And the size is computed by serialising twice: once into a dummy buffer to measure, once into the real one to write, so the payload is generated twice per shutdown.
Successive runs are not cumulative in the file, but they are in the log. Because multiPoolConfigLog is a member of the manager, it dies with the manager; the file is overwritten wholesale. A run that produces no reports therefore empties the cache file for the next run rather than preserving the previous one — the file is a snapshot of one run's reports, not an accumulation across runs.

Parameters

None.

Return value

void. A failed write leaves the previous file in place, or partially written — the method checks the byte count, not the file's integrity afterwards.
