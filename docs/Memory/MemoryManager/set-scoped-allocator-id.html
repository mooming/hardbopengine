SetScopedAllocatorID

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The only validating write of the thread's scoped id — and an out-of-range id is quietly replaced with 0.

Signature

void SetScopedAllocatorID(TId id)

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::SetScopedAllocatorID(), declared private and reachable from outside the class only by the AllocatorScope friend. It is the only writer of scopedAllocatorID that checks anything — the field is public, so anything can assign it without asking.

From Engine/Memory/MemoryManager.cpp, MemoryManager::SetScopedAllocatorID()

Two things follow from the first line. An out-of-range id is silently replaced with 0 rather than rejected, so the scope opens and the caller's allocations go to the system allocator — the only trace is an Error line that this tree cannot print. And InvalidAllocatorID is deliberately exempt, which is what lets AllocatorScope::AllocatorScope() install -1 as a legal scope: an Allocate inside such a scope then trips Assert(id != InvalidAllocatorID, "Memory allocation is not permitted.") in Debug and Dev and is redirected to slot 0 in Release.

Its entire mechanism is one save-and-restore pair. AllocatorScope's constructor reads GetScopedAllocatorID, calls this with the new id, and its destructor calls this again with the saved one. Nesting works because each object restores what it personally observed, so the stack discipline is in the scopes, not in the manager. The other caller in the tree is RegisterSystemAllocator, which points the constructing thread at slot 0.
The optional trace cannot fire, and would print the wrong thing if it did. Before writing the field the method consults dVarScopedAllocLogging — a TDebugVariable<bool> at file scope in this same translation unit, and Engine/Core/Debug.h defines that alias as const T. The flag is therefore false and immutable, so the block is unreachable by construction. Were it reachable, its message reads "Previous ID = " << id << ", New ID = " << id — the same value twice, because the previous id was never read. Both are inert today; they are recorded here so no one reads a missing trace line as evidence that no scope changed.
No lock, and none is needed. The field is static thread_local, so a write is private to the calling thread by language rule. What is not protected is the value itself against a caller that writes the public member directly, or that opens a scope on one thread and expects it on another (GetCurrentAllocatorID).

Parameters

idTId (TAllocatorID)The allocator every unnamed allocation on this thread should now go to. 0 … 255 or InvalidAllocatorID are installed as given; anything else becomes 0.

Return value

void. A substituted id is not reported to the caller, so a scope opened with a bad id looks exactly like a scope opened with a good one.
