DeregisterSystemAllocator

member of hbe::MemoryManager Engine/Memory/MemoryManager.h An ordinary DeregisterAllocator on id 0, called by the destructor — which means it can refuse, and does.

Signature

void DeregisterSystemAllocator()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::DeregisterSystemAllocator(), declared private, and its entire body is DeregisterAllocator(SystemAllocatorID);. It is the teardown half of RegisterSystemAllocator, called once from ~MemoryManager — but it is not a special teardown: it is the ordinary deregistration applied to id 0, and it inherits every quirk of that method, including the ability to refuse.

It can refuse, and the destructor does not look. Under PROFILE_ENABLED the shared path returns early on a thread-id mismatch or on stats.usage > 0 — after already nulling the slot's two function pointers and without returning the slot to the pool (DeregisterAllocator). The destructor then clears the global handle anyway, so a system allocator still holding bytes produces one warning line and nothing else: no retry, no summary, no way for the process to know its teardown was incomplete.
It puts slot 0 back into the free-slot pool, and slot 0 has no usable id. The last statement of the shared path is proxyPool.Push(allocator) for whatever slot it was given, so a deregistration of id 0 pushes slot 0 — and slot 0 is the one proxy whose id field was never written, because the constructor's seeding loop starts at i = 1 (the constructor, RegisterSystemAllocator). A subsequent RegisterAllocator would pop that slot, read id as InvalidAllocatorID, trip Assert(id != InvalidAllocatorID) in Debug and Dev, and in Release return -1 to its caller having written the registration into slot 0. During static destruction, when a late allocator may still try to register, that is the shape of the failure — nothing in the tree exercises it, and no source states an intended behaviour. Recorded as a named omission in Coverage.
What stops working the moment it returns. Slot 0's function pointers are null, so SysAllocate logs FatalError and returns null, SysDeallocate logs and drops the release, and any Allocate that arrives for an out-of-range id — every one of which is redirected to 0 — lands on the same null pointer, where the guard is an Assert that Release removes. Anything that frees after Engine's members are gone is in this window, which is why late destructors that release memory through GetInstance are the module's most fragile code.

Parameters

None. The id is the constant SystemAllocatorID, not an argument.

Return value

void. Success, refusal and the loss of a registration slot are all indistinguishable to the destructor that calls it.

Examples

MemoryManager::~MemoryManager()
{
	if (mmgrInstance == nullptr)
	{
		return;
	}

	DeregisterSystemAllocator();
	mmgrInstance = nullptr;
}

From Engine/Memory/MemoryManager.cpp, MemoryManager::~MemoryManager()

The single call site. It runs while every other Engine member has already been destroyed — the manager is declared first in Engine/Engine/Engine.h and so dies last — which is exactly the ordering that makes this call safe, and the ordering that leaves any allocator which failed to deregister itself pointing into a manager that is on its way out.
