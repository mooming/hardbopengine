Allocate

member of hbe::MemoryManager Engine/Memory/MemoryManager.h One indirect call through the slot — zero is null, an invalid id quietly becomes slot 0, and the scope decides the rest.

Signature

void* Allocate(TId id, size_t nBytes)

void* Allocate(size_t nBytes)

Function description

Both are defined in Engine/Memory/MemoryManager.cpp as overloads of MemoryManager::Allocate(). The unsized form is one line — return Allocate(GetScopedAllocatorID(), nBytes); — so everything below applies to both, with the thread's scoped id supplied by GetScopedAllocatorID. Dispatch is a single indirect call through the registration slot: the manager knows nothing about the strategy on the other end.

#Step in Allocate(TId, size_t)Compiled in
1nBytes == 0 → return nullptr. Happens before any validation.always

Which allocator answers is a thread property, not a template property. The unsized overload is the reason a PoolAllocator can serve code that never mentions it: AllocatorScope installs the pool's id in this thread's scopedAllocatorID and every unnamed call lands there. It is also why the typed templates — AllocateByType, New, NewArray — cannot pin an allocator: their template arguments choose a size and a constructor only. A new thread starts at 0 and does not inherit the scope of the thread that queued its work (GetCurrentAllocatorID).
Zero bytes is nullptr, and so is a failure — and an invalid id never fails. Step 1 means a legitimate request for nothing and an allocator that could not oblige are reported identically, so a caller that wants to distinguish them must not request zero. Step 4 goes the other way: a bad id is not an error the caller can see, it is a quiet redirection to slot 0, which is where a mis-scoped allocation goes to hide — the memory arrives, from somewhere, and the only trace is an Error line that this tree cannot print. In Release, steps 2, 5 and 7 are compiled away entirely (Engine/Core/Debug.h), so a deregistered id becomes a call through a null function pointer.
No lock, no accounting of its own, no alignment parameter. The slot table is fixed and a proxy's function pointers are only rewritten between a registration and a deregistration, so the dispatch path is lock-free by design — statistics are reported by the allocators afterwards (ReportAllocation), not here, and the global counters belong to the replaced operator new instead. There is no alignment argument anywhere in the path, so the alignment of a block is whatever the chosen allocator gives: JOURNAL.md records that for the pool family, where only blockSize is aligned to Config::DefaultAlign, a type with a larger alignof is silently under-aligned.

Return value
