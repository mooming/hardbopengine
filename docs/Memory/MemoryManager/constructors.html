MemoryManager

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Publishes the singleton, seeds 255 free slots, installs slot 0 and loads the pool geometry — one call per process, asserted.

Signature

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::MemoryManager(Engine&), with the initialiser list allocCount(0), deallocCount(0) and a body that does four things in this order: publish the instance, seed the free-slot pool, install the system allocator, load the previous run's pool geometry.

There is exactly one, and the constructor is what makes it findable. mmgrInstance is a file-scope pointer in the translation unit, and publishing it before anything else happens is what lets GetInstance answer from the first statement of the constructor onwards. The copy constructor is = delete and copy assignment too — two objects would publish the same handle and each try to deregister slot 0 — so the only route to an instance is Engine's own member (Engine/Engine/Engine.h, Engine::memoryManager). The single call site is Engine::Engine()'s initialiser list, where memoryManager(*this) sits ahead of statistics and logger.
Slot 0 is installed by a different path, and its proxy never learns its own number. The seeding loop starts at i = 1: slot 0 is never pushed onto proxyPool — which is what stops RegisterAllocator from ever handing out SystemAllocatorID — but its id field is also never written, so allocators[0].id stays InvalidAllocatorID, the default from AllocatorProxy::AllocatorProxy(). Nothing in the tree reads that field for slot 0 (RegisterSystemAllocator asserts against the class constant instead), so it is a latent inconsistency rather than a live bug — but a caller who walks GetAllocatorProxy(0) and trusts proxy.id is reading -1.
The constructor logs before there is a logger. LoadMultiPoolConfigs is called from here and its diagnostics go through Log into Engine::Log, while Engine::logger has not been constructed yet — memoryManager precedes logger in Engine's member order, and Engine::isLoggerReady is still false. In this tree the point is academic, because MEMORY_LOGGING_ENABLED is 0 and Log compiles to nothing; where memory logging is switched on, the cache-load lines are the ones most likely to be lost.
What the constructor leaves set. RegisterSystemAllocator has filled slot 0, seeded GetUsage's totalCapacity and maxCapacity with Config::MemCapacity (5 GiB, Engine/Config/EngineConfig.h) and pointed this thread's scopedAllocatorID at slot 0, and LoadMultiPoolConfigs has either filled the config cache or left it empty. engine.SetMemoryManagerReady() is the last statement, so readiness is published only once all of that is true.

Parameters

ParameterTypeRequirement
engineEngine&The owning Engine, used only for SetMemoryManagerReady(). It must outlive the manager, which the member declaration order guarantees at the one call site; later calls reach the engine through Engine::Get() instead, not through a stored reference — the class keeps no Engine* member at all.

Return value

None — this is a constructor. Failure is not reportable: a second construction trips an Assert in Debug and Dev and silently replaces the published handle in Release, where Assert compiles away (Engine/Core/Debug.h).
