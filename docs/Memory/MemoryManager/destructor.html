~MemoryManager

member of hbe::MemoryManager Engine/Memory/MemoryManager.h Deregisters slot 0 and clears the global handle; every allocator must already be gone, and nothing here can tell you if one is not.

Signature

~MemoryManager()

Function description

Defined in Engine/Memory/MemoryManager.cpp as MemoryManager::~MemoryManager(). The whole body is a re-entry guard, one deregistration and one clear: 

if (mmgrInstance == nullptr)
{
	return;
}

DeregisterSystemAllocator();
mmgrInstance = nullptr;

From Engine/Memory/MemoryManager.cpp, MemoryManager::~MemoryManager()

The guard makes destruction idempotent — a manager whose handle was already cleared tears nothing down again — and it is also the reason a manager that was never published (a construction that failed before the assignment) can be destroyed quietly. After this returns, GetInstance is a FatalAssert and std::abort(), not a null reference: the pointer it reads is exactly the one cleared here.

Every allocator must already be gone, and nothing here can tell you if one is not. The destructor deregisters slot 0 and nothing else. An allocator still holding a registration keeps its id, and its proxy slot still names its two function pointers, but the object that owns the slot is dying — so a later Allocate through that id either trips the Assert(allocProxy.allocate != nullptr) in Allocate (Debug and Dev) or, in Release, where Assert compiles to nothing (Engine/Core/Debug.h), calls through whatever the slot holds. There is no registry walk, no leak summary and no assert that the free-slot pool is full again.
A refused deregistration still ends the process-wide handle. DeregisterSystemAllocator is an ordinary DeregisterAllocator on id 0, and under PROFILE_ENABLED that call can return early — on a thread-id mismatch or on stats.usage > 0 — having already nulled the slot's two function pointers. The destructor does not look at the result: mmgrInstance = nullptr; runs either way, so a leaked system allocation is neither retried nor reported beyond that one warning line.
Destruction order is what makes this safe at all. As an Engine member declared ahead of statistics, logger, taskSystem, resourceManager and application (Engine/Engine/Engine.h), the manager is destroyed after all of them, which is the property every subsystem relies on when it frees its memory in its own destructor. Code that reaches the manager by GetInstance rather than by an Engine& shares that lifetime exactly: Engine/Log/LogLine.cpp, LogLine::~LogLine() is one such release, and it is an abort rather than a crash if it ever runs after the engine's members are gone.

Parameters

None.

Return value

None — this is a destructor. It reports nothing: no status, no leak count, no failure path.
