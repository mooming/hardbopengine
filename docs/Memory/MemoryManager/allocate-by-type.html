AllocateByType

member of hbe::MemoryManager Engine/Memory/MemoryManager.h n elements, not n bytes, from this thread's scoped allocator — and the multiply is unchecked.

Signature

#endif

	template <typename T>
	T* AllocateByType(size_t n)

Function description

Defined in the class body of Engine/Memory/MemoryManager.h, so the body inlines into every includer. Its whole content is a unit conversion plus a dispatch: 

const auto nBytes = n * sizeof(T);
auto ptr = Allocate(GetScopedAllocatorID(), nBytes);

return static_cast<T*>(ptr);

From Engine/Memory/MemoryManager.h, MemoryManager::AllocateByType()

n is an element count, not a byte count — that is the only thing the template parameter buys, since T is used nowhere else in the body. The allocator is still chosen at run time by this thread's scoped id; no template argument can pin one. The returned pointer is raw storage cast to T*: nothing is constructed, which is why New and NewArray are built on top of this rather than being alternatives to it.

The multiply is unchecked, and zero is indistinguishable from failure. n * sizeof(T) wraps silently for a large n, and the wrapped product is what Allocate is asked for — a small number that will succeed and hand back too few elements, with no diagnostic anywhere. A zero n takes the other path: Allocate answers nullptr before doing anything else, so a caller cannot tell "you asked for nothing" from "the allocator refused", and this template performs no check of its own before returning the cast pointer.
The pair to release with is DeallocateTypes, with the same count. Both halves recompute n * sizeof(T) and re-read the scoped id independently, so a release must match the count and sit in the same scope. Delete and DeleteArray do exactly that, which is why they exist; calling Deallocate by hand with a byte count instead is the mistake this pairing prevents.
Alignment and lifetime come from the allocator, not from the type. There is no alignment parameter in the path, so alignof(T) beyond what the current allocator happens to give is not served (Allocate records what that means for the pool family). And because the block came from a scope, the object's lifetime is bounded by that allocator's, not by the pointer's.

The one production call site outside the class itself: the STL-compatible adapter that feeds container memory through the scoped allocator, pairing it with DeallocateTypes in its deallocate(). Inside the class, New is AllocateByType<Type>(1) followed by a placement constructor, and NewArray is the same call with an element count.
