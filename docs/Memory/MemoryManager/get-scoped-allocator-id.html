GetScopedAllocatorID

member of hbe::MemoryManager Engine/Memory/MemoryManager.h The private twin of GetCurrentAllocatorID — the id the dispatch path and AllocatorScope actually use.

Signature

[[nodiscard]] static TId GetScopedAllocatorID()

Function description

Defined in the class body of Engine/Memory/MemoryManager.h: return scopedAllocatorID;, reading the static thread_local id this thread's unnamed allocations go to. The body is byte-for-byte what GetCurrentAllocatorID does — the difference between the two is who may call them, and that difference is what the allocator scope mechanism is built on.

Who uses itallocators adopting a parent id in their constructorsthis class's own dispatch and the AllocatorScope friend

The private one is what the machinery reads: the unsized Allocate and Deallocate overloads each call it, as do AllocateByType and DeallocateTypes and therefore New, NewArray, Delete and DeleteArray. AllocatorScope reaches it as a declared friend class — the reason the friendship exists at all, together with SetScopedAllocatorID.

Why two getters for one field. Keeping the dispatch path on the private one means the pair can diverge — a future validity check, a debug counter or a trace would land on the internal reader without changing what an allocator sees when it adopts a parent. Today they are identical, and the pairing is the cheapest way to say "this value has two roles": one as public information, one as the routing decision. Both read the field directly and validate nothing.
Per thread, and never inherited. The field is static thread_local and initialised to 0 in Engine/Memory/MemoryManager.cpp, so a worker thread started by the task system reads SystemAllocatorID even while the thread that queued its work sits inside an AllocatorScope. Nothing in Engine/ propagates a scope across a thread boundary; the module's answer is to record a parent id instead (GetCurrentAllocatorID) and name it explicitly at release time. A value read here is a snapshot: the two halves of a typed allocate/release pair each re-read it, so a scope that moves in between sends the block to a stranger.

Parameters

None.

Return value

TypeWhat you get
TId (TAllocatorID)This thread's current id, unvalidated — 0 before any scope opens, the id the innermost open AllocatorScope installed, or whatever a caller wrote straight into the public field. See GetCurrentAllocatorID for the case where it is legitimately InvalidAllocatorID.

Examples

AllocatorScope::AllocatorScope(TAllocatorID id) noexcept
{
	auto& mmgr = MemoryManager::GetInstance();
	previous = mmgr.GetScopedAllocatorID();
	current = id;

	mmgr.SetScopedAllocatorID(current);
}

The friend that exists for this getter and its setter: read the current id, install a new one, restore the saved value in the destructor. No code outside this class and AllocatorScope can call it — the allocators that need the same value all use the public twin.
