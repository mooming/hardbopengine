StackAllocator

member of hbe::StackAllocator Engine/Memory/StackAllocator.h 2 overloads Rounds the capacity up, takes the buffer from the allocator that is current, and registers this object with the manager.

Signature

Function description

Defined in Engine/Memory/StackAllocator.cpp as StackAllocator::StackAllocator(). Construction is four steps: round the capacity up, record the current allocator as the parent, take the buffer, register the object. Each is a request to the MemoryManager, and the first two decide where the bytes come from and where everything this stack cannot serve will later go. 

{
	constexpr auto AlignUnit = Config::DefaultAlign;
	const auto multiplier = (capacity + AlignUnit - 1) / AlignUnit;
	capacity = multiplier * AlignUnit;
}

auto& mmgr = MemoryManager::GetInstance();
parentID = hbe::MemoryManager::GetCurrentAllocatorID();
bufferPtr = mmgr.Allocate(capacity);

From Engine/Memory/StackAllocator.cpp, StackAllocator::StackAllocator()

id = mmgr.RegisterAllocator(this, name, false, capacity, allocFunc, deallocFunc);

From Engine/Memory/StackAllocator.cpp, StackAllocator::StackAllocator()

Which allocator owns the buffer is decided by the scope that is open right here. parentID is read from MemoryManager::GetCurrentAllocatorID(), which returns the thread-local scopedAllocatorID, and the buffer is then taken through mmgr.Allocate(capacity) — the overload that allocates against that same thread-local id. Open an AllocatorScope over another allocator and construct inside it, and that allocator supplies the backing bytes; construct with no scope open and scopedAllocatorID is 0, the system allocator, which is the state of a thread that has never opened one. The pairing is worth holding because the destructor releases the buffer through the scope that is open then, not through this recorded parentID: the PoolAllocator destructor in Engine/Memory/PoolAllocator.cpp releases through its recorded parent, this one does not.
The name is the manager's, not the object's. The constructor stores no copy of name — the class has no name member and no GetName() — and passes it only to MemoryManager::RegisterAllocator(), where a null pointer becomes "None" (Engine/Memory/MemoryManager.cpp). Under PROFILE_ENABLED the registration copies it into the allocator's statistics record; in the configuration this tree compiles the registration keeps the allocate and deallocate function pointers and nothing else. Log lines that name the allocator — the leak warning in MemoryManager::DeregisterAllocator(), for instance — are profile-build lines.
The capacity you pass is not the capacity you get. The rounding above rewrites capacity in place, so a request of 1000 bytes becomes a 1008-byte buffer and a request of 1048576 stays 1048576, and it is the rounded figure that GetAvailable reports and that the registration records. The same rounding is applied to every request by Allocate, which is why a request of 1 byte costs 16 and why Deallocate can be given any byte count that rounds to the same number.
Two things the constructor does not check. MemoryManager::GetInstance() guards the singleton with FatalAssert, which aborts in every configuration (Engine/Core/Debug.h), so constructing before the engine's memory manager exists is fatal rather than undefined. A registration failure is the softer case: when the manager's proxy pool is empty — the id space is MaxNumAllocators, 256 entries — RegisterAllocator logs a fatal-priority line and returns InvalidAllocatorID, and the constructor stores that id and keeps the buffer it already took. GetID then reports -1, Allocate still serves from the buffer, and the destructor logs an error from DeregisterAllocator. That state has no testlet — see Coverage.

The two signatures are one constructor behind #if PROFILE_ENABLED. Engine/Config/BuildConfig.h defines that macro as 0, so the branch that is taken here is the two-argument form and the location parameter, the TSrcLoc alias and the srcLocation member do not exist; JOURNAL.md (2026-10-05) records that turning the macro on breaks the build for reasons unrelated to this class, so the profile branch has never been compiled.

Parameters

ParameterTypeRequirement
nameconst char*A label for the registration. Not stored by the object and not copied in the configuration this tree compiles; nullptr is accepted and becomes "None".
capacitySizeTypeBytes of backing store wanted. Rounded up to a multiple of Config::DefaultAlign (16) before the request is made. A capacity of 0 asks the manager for 0 bytes, and it returns nullptr for that — a state no testlet covers.
locationconst TSrcLoc&Construction site handed to the two-argument MemoryManager::DeregisterAllocator. Exists only under PROFILE_ENABLED; defaults to TSrcLoc::current().

Return value

Constructors produce an object rather than a value. What a successful one guarantees: capacity bytes of buffer owned by this object, cursor at 0, GetAvailable equal to the rounded capacity, and an id that an AllocatorScope can be opened with. Nothing guarantees the buffer is non-null.

The second form is the nesting the class is built for: ScopedAllocator<TAlloc> (Engine/Memory/ScopedAllocator.h) constructs the allocator and opens its scope together, so a nested stack's parent is the stack one level out, and the scope is restored before the allocator is destroyed — which is the order that hands the buffer back to the right allocator.
