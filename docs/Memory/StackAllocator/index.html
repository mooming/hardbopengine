StackAllocator

Engine/Memory/StackAllocator.h final namespace hbe Bump allocation from one fixed buffer: release is last-in-first-out, a block that does not fit goes to the parent, and everything left dies with the object.

Class description

class StackAllocator final at Engine/Memory/StackAllocator.h hands out bytes from one fixed buffer by moving a cursor. The constructor rounds the requested capacity up to a multiple of Config::DefaultAlign (16 bytes), records the allocator that is current at that moment as parentID, takes the buffer from the MemoryManager, and registers the object under an id of its own — the same three steps PoolAllocator performs, with a free list replaced by a cursor. Every byte it serves comes from inside that one buffer, except the ones described under exhaustion below.

Release is last-in-first-out. Deallocate rewinds the cursor, and it rewinds it only for the block that currently sits on top of the stack, given a byte count that rounds up to the same size the block was charged. The shape the repository actually uses is the Vector Allocation testlet of StackAllocatorTest::Prepare() in Engine/Memory/StackAllocator.cpp: a StackAllocator named "Test::StackAllocator" holding a 1 MiB buffer, an AllocatorScope opened over stack.GetID() inside a nested block, and an HVector<int> declared after that scope — so the vector is destroyed while the scope is still current and its buffer release reaches this allocator rather than the default one. Nothing in the engine calls Allocate on a stack directly.

A pointer into the buffer dies with the object, not with the block that was released. The destructor returns the whole buffer to the manager in one call; there is no per-block bookkeeping left to release, and no block survives that call. There is also no reset: the header declares no Reset, Rewind, or ReleaseAll, so destroying the object is the only way to drop many allocations at once, and it drops every pointer the allocator ever handed out from the buffer — including the ones still held. The one release that keeps the rest alive is a Deallocate of the current top block: the bytes below it keep their addresses, the released block's address is reusable by the next Allocate, and nothing clears or poisons the released memory first.
A release that is not the top of the stack is a reported failure, and in a Release build it leaks silently. Deallocate compares buffer + cursor against ptr + alignedSize. On a mismatch it logs an error naming the pointer it was given and the address it expected, calls Assert(false), and returns without touching the cursor. In Debug and Dev that assert aborts the process (Engine/Core/Debug.h); in Release Assert is an empty inline function, so the only trace is the log line, and MemoryManager::LogError prints nothing unless MEMORY_LOGGING_ENABLED is on — Engine/Config/BuildConfig.h defines it as 0. A wrong-order release in a shipped build therefore strands those bytes until the allocator is destroyed, with no diagnostic anyone sees.
Exhaustion is not a failure, and the block that survives it belongs to the parent. When the aligned request exceeds GetAvailable(), Allocate asks the parent instead of returning null: return mmgr.FallbackAllocate(GetID(), parentID, requested);. That block is outside this buffer, so a later Deallocate of it is forwarded to parentID rather than rewinding the cursor — asking the same stack object is the correct way to release it. Two consequences a caller has to hold: the comparison is made against the rounded size, so a request that would fit in the last few bytes goes to the parent anyway; and the fallback block is not freed by this object's destructor, so it must be released explicitly or it leaks past the stack.
Alignment is fixed at the engine default and cannot be asked for. Every request is rounded up to Config::DefaultAlign (16) by the inline arithmetic in StackAllocator::Allocate() — (size + AlignUnit - 1) / AlignUnit, then multiplied back — and the same rounding is applied to the byte count in Deallocate, which is why the two must be paired by size. Neither this class nor its parent path takes an alignment argument, so a request for an over-aligned type gets 16-byte spacing at best, and even that is inherited: a block's address is buffer + cursor, and the buffer is whatever the parent's answer happened to be aligned to. See the Coverage section for what the code does not settle.

The class declares no copy constructor, no move constructor and no assignment operator, and it owns two resources: one buffer and one registration id whose proxy record stores this (MemoryManager::RegisterAllocator() in Engine/Memory/MemoryManager.cpp). Two live objects over one buffer would each return that buffer to the manager and each deregister the same id, so one object per buffer is the only supported use. Whether the implicit operations compile at all is a build question this page does not answer — the migration step that owns these pages runs no compiler; see Coverage.

Template parameters

None. StackAllocator is final and not a template: capacity and name are constructor arguments, and the allocator serves raw bytes, so no element type reaches the class.

Coverage

Not documented hereWhy
Thread-safety, and whether one stack may be shared or moved between threads The code does not answer it. Engine/Memory/StackAllocator.cpp takes no lock and reads and writes no atomic: cursor, capacity and the registration id are plain members, so two threads allocating at once race on the cursor. Against that: the MemoryManager it calls into holds its own statsLock and a thread_local scoped-allocator id, and the engine's shareable shape is the multi-pool allocator the allocator catalogue names. No testlet runs either allocator from two threads, and no assertion binds an allocator to the thread that constructed it (MEMORY_VERIFICATION_ENABLED is 0), so whether sharing is "merely" racy or already checked somewhere is not established here. The manager's own rules are owned by the Memory module page.
Whether an implicit copy or move of StackAllocator compiles A build claim, and this migration step runs no compiler. What is stated instead is the consequence: the destructor frees the buffer and deregisters the id, so a second live object over the same buffer is a double free of both. The class declares nothing about the matter, which is itself the finding — PoolAllocator declares its move operations explicitly, this class does not.
The alignment a returned pointer actually carries Only that block starts are 16 bytes apart, because every charge is rounded to Config::DefaultAlign. Whether buffer itself is 16-byte aligned depends on the allocator that served the constructor's request — in this configuration that is SystemAllocator's malloc path (Engine/Memory/SystemAllocator.h), which the code does not check or force. No test asserts an address modulus, so anything beyond "16 bytes apart inside one buffer" is unnamed.
Every path behind #if PROFILE_ENABLED: TSrcLoc, srcLocation, the location constructor parameter, the ReportAllocation and ReportDeallocation calls, and the two-argument DeregisterAllocator Engine/Config/BuildConfig.h defines PROFILE_ENABLED as 0, and JOURNAL.md (2026-10-05) records that flipping it breaks the build before any Memory file is reached. Those paths are described from the source and have never executed, so their accounting claims — for instance that Allocate reports the rounded size as both requested and allocated — are read, not observed.
Behaviour of a zero-capacity allocator, and of a failed construction Read from the code, never exercised: no testlet constructs either of these allocators with a capacity of 0, and none makes MemoryManager::Allocate fail. What the code says is that a capacity of 0 rounds to 0, that the manager returns nullptr for a 0-byte request, and that a registration failure yields InvalidAllocatorID while the object still holds a buffer — but the resulting state is untested, so it is named rather than documented as a contract.
What a mismatched or wrong-order release leaves behind in a Release build Deallocate documents what the code does — log, assert, return with the cursor unmoved — but no testlet performs a mismatched release, so the size of the resulting leak and the exact conditions under which any diagnostic survives to a shipped build are not demonstrated.
