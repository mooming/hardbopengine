GetUsage

member of hbe::StackAllocator Engine/Memory/StackAllocator.h nodiscard Bytes charged against the buffer at their rounded size -- and a fully exhausted buffer trips this function's own assertion.

Signature

[[nodiscard]] size_t GetUsage() const

Function description

Defined in Engine/Memory/StackAllocator.cpp as StackAllocator::GetUsage() const. Two lines: an assertion about the cursor, then the cursor itself. 

Assert(cursor < capacity);

return cursor;

From Engine/Memory/StackAllocator.cpp, StackAllocator::GetUsage() const

The number is bytes charged against the buffer, so it counts the rounding as well as the request: five allocations of 20 bytes report 160, not 100, because each was charged 32. That is what makes it a faithful picture of the buffer's state and an unfaithful picture of what the caller asked for.

The assertion is strict, so a fully-exhausted buffer trips it. The condition is cursor < capacity, not <=. A stack that has handed out its last byte has cursor == capacity, and asking it how much it is using then fires Assert — which aborts in Debug and Dev (hbe::Assert, Engine/Core/Debug.h) and does nothing in Release, where the function returns capacity as if nothing had happened. The same strict form fires for a zero-capacity allocator, where 0 < 0 is false from the moment it is constructed. Derived from the source; no testlet fills a buffer or constructs a zero-capacity stack, so this is stated as a hazard and named in Coverage, not as observed behaviour.
It counts buffer bytes only, so it under-reports what a caller is actually holding. Blocks that arrived through Allocate's overflow path belong to parentID and never touched cursor. A stack can report usage 0 while its caller holds live memory. The one thing this figure does tell you, and the thing the class's own testlets check, is whether the rewind happened: the testlets in Engine/Memory/StackAllocator.cpp assert GetUsage() == 0 after a scope closes, which is precisely the check a monotonic allocator would fail — its test requires the opposite.
Nothing here is the manager's accounting. Under PROFILE_ENABLED the manager keeps its own per-registration figures, fed by ReportAllocation and ReportDeallocation; this function reads cursor and is independent of them. That macro is 0 in Engine/Config/BuildConfig.h, so in this tree GetUsage() is the only usage number that exists at all.

Parameters

None.

Return value

TypeWhat you get
size_tcursor: bytes charged against the backing buffer at their rounded size. Excludes every block the parent supplied. Meaningless on a destroyed object — the destructor ends this allocator's life, and reading a dead member is not a query. The attribute is [[nodiscard]].

Examples

StackAllocator stack("Test::StackAllocator::Deallocation", 1024 * 1024);
AllocatorScope scope(stack.GetID());
{
	String a = "0";

	if (stack.GetUsage() <= 0)
	{
		ls << "Allocation Failed. Usage should not be zero, but " << stack.GetUsage() << lferr;
	}
}

if (stack.GetUsage() != 0)
{
	ls << "Deallocation Failed. Usage should be zero, but " << stack.GetUsage() << lferr;
}

From Engine/Memory/StackAllocator.cpp, StackAllocatorTest::Prepare(), Deallocation testlet

Both readings are needed to say anything: non-zero inside the scope proves the container allocated through the stack, and zero after it proves the release rewound the cursor. Note the comparison style — the test compares a size_t against <= 0, which for an unsigned type tests only the "is zero" half.
