DeallocateBytes

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Cache, free list, or parent: the release path, and the one place the pool decides what its own memory is.

Signature

void DeallocateBytes(void* ptr, size_t nBytes) noexcept

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and the counterpart of AllocateBytes. It is reached from deallocate (which passes n * sizeof(T), a byte count that agrees with AllocateBytes) and from the deallocation lambda the pool registers with the manager in RegisterAllocator, so every release the engine makes through an AllocatorScope on this pool arrives here. Three branches, in this order:

OrderGuardResult
1!IsValidPointer(ptr) MemoryManager::Deallocate(parentID, ptr, nBytes) and return — a pointer outside the array belongs to the allocator that was current when the pool was constructed, and it is that allocator's to be told about. This guard runs in every configuration.
2immediateBlock == nullptr && nBytes <= BlockSizeInBytes Store ptr in the one-slot cache and return. The free list is not touched; under PROFILE_ENABLED the release is reported with BlockSizeInBytes as the allocated figure.
3otherwise WritePointerToNext(ptr, availableBlock), then availableBlock = ptr: the block becomes the head of the free list, reported the same way.
Ownership is settled before anything else, in every configuration. The order above is the fix, not the original shape. Branch 1 used to be compiled only under PROFILE_ENABLED, so in a shipping build branch 2 came first and looked only at the size: a block the pool had borrowed from its parent satisfied the size test, was parked in immediateBlock, and went back out to a caller as if it were array storage. Nothing told the parent its block had returned, and the pool handed out the same address a second time on the next release. That is the failure the testlet "Foreign Block Returns To Its Own Parent" in Engine/Memory/InlinePoolAllocator.cpp measures — it fails against the old order and passes against this one, in all four configurations. A null pointer still satisfies the size test of branch 2, but branch 1 now turns it away: IsValidPointer is a range test, and null is below the array.
A block released twice is not detected, and it will be handed out twice. Nothing compares ptr against the list it is about to join: branch 3 writes the current head into the block and makes the block the head. Release the same address twice at different times and the address appears twice in the list, so two later allocations receive the same pointer. Engine/Memory/InlinePoolAllocator.cpp has no double-release testlet, and IsValidPointer cannot help — it answers "is this inside the array", never "is this already free". The same absence covers AllocateBytes's cache: a block taken from immediateBlock and released again while a copy of it is still held elsewhere follows the same path.
The size argument routes nothing; the range decides, and the range has one soft edge. nBytes now only gates entry to branch 2 and appears in the two reporting calls; the choice between "back to the free list" and "back to the parent" is IsValidPointer alone. It compares block[0] <= ptr && ptr <= block[LastBlockIndex] — an address inside the final block reads as outside it, because the upper bound is that block's start rather than the array's end. A block released from the last slot of the array therefore travels to parentID instead of joining the free list: the memory is not lost, and the pool simply never reuses it. That bound is recorded here rather than quietly corrected because changing it changes which allocator a release is billed to.

Parameters

ParameterTypeMeaning
ptrvoid*Storage to release. Not dereferenced unless it is being pushed onto the free list, where its first sizeof(void*) bytes become the next-pointer.
nBytessize_tByte count, and deallocate now really passes one: n * sizeof(T). It gates branch 2 and is the figure reported and forwarded to the manager. It is never compared against the size the block was taken out with — routing is the range test's job, so a wrong count misreports but cannot corrupt the free list.

Return value

None. Every branch is terminal, and the function reports nothing about which branch ran.

Examples

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::DeallocateBytes()

The vector-growth testlets in Engine/Memory/InlinePoolAllocator.cpp are built to land on exactly this branch: each iteration ends with clear() and shrink_to_fit(), which releases the buffer, and the next iteration's first reserve() asks for the same block again. One-slot caching is enough for that rhythm, which is the allocation pattern the class was shaped for.
