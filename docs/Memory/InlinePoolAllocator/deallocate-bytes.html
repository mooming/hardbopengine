DeallocateBytes

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Cache, free list, or parent: the release path, and the one place the pool decides what its own memory is.

Signature

void DeallocateBytes(void* ptr, size_t nBytes) noexcept

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and the counterpart of AllocateBytes. It is reached from deallocate (with an element count, not a byte count — see that page) and from the deallocation lambda the pool registers with the manager in RegisterAllocator, so every release the engine makes through an AllocatorScope on this pool arrives here. Three branches, in this order:

OrderGuardResult
1immediateBlock == nullptr && nBytes <= BlockSizeInBytes Store ptr in the one-slot cache and return. The pointer is not validated, the free list is not touched, and nothing is reported to the manager.
2!IsValidPointer(ptr) MemoryManager::Deallocate(parentID, ptr, nBytes) — a pointer the pool does not own is returned to the allocator that was current when the pool was constructed.
3otherwise WritePointerToNext(ptr, availableBlock), then availableBlock = ptr: the block becomes the head of the free list. Under PROFILE_ENABLED the release is reported with BlockSizeInBytes as the allocated figure.
Branch 1 parks a pointer before asking where it came from. The cache test comes first and looks only at the size, so a block that AllocateBytes obtained from the parent can be parked in immediateBlock and then handed out again as if it were array storage. For as long as it sits in the slot, and again for as long as it is in the caller's hands afterwards, the manager has not been told about it: branch 2 is the only release path that reaches MemoryManager::Deallocate, and branch 1 returns before it. The pool's own accounting is unaffected (it keeps no accounting — see the gap there), but the parent's live-byte figure keeps counting a block the pool believes it recycled. The same is true of a null pointer with the cache empty: null satisfies the size test, so it is parked — and since the guard is immediateBlock == nullptr, storing null leaves the slot empty, which makes that call a silent no-op.
A block released twice is not detected, and it will be handed out twice. Nothing compares ptr against the list it is about to join: branch 3 writes the current head into the block and makes the block the head. Release the same address twice at different times and the address appears twice in the list, so two later allocations receive the same pointer. Engine/Memory/InlinePoolAllocator.cpp has no double-release testlet, and IsValidPointer cannot help — it answers "is this inside the array", never "is this already free". The same absence covers AllocateBytes's cache: a block taken from immediateBlock and released again while a copy of it is still held elsewhere follows the same path.
The size argument is not trusted for routing, only for thresholds. nBytes decides entry to branch 1 and appears in the two reporting calls; the decision between "back to the free list" and "back to the parent" is made by IsValidPointer alone. That is what keeps deallocate's element-count mistake from corrupting the list, and it is also why a block that came from the parent but happens to fall inside the array's byte range would be pushed onto the free list instead of being released. The range is contiguous and belongs to this object, so the case is unlikely in practice; the page records it because the routing test is a range comparison and not an ownership record.

Parameters

ParameterTypeMeaning
ptrvoid*Storage to release. Not dereferenced unless it is being pushed onto the free list, where its first sizeof(void*) bytes become the next-pointer.
nBytessize_tByte count in name; from deallocate it is an element count. Tested against BlockSizeInBytes and passed on to the manager's release.

Return value

None. Every branch is terminal, and the function reports nothing about which branch ran.

Examples

if (immediateBlock == nullptr && nBytes <= BlockSizeInBytes)
{
	immediateBlock = ptr;

	return;
}

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::DeallocateBytes()

The vector-growth testlets in Engine/Memory/InlinePoolAllocator.cpp are built to land on exactly this branch: each iteration ends with clear() and shrink_to_fit(), which releases the buffer, and the next iteration's first reserve() asks for the same block again. One-slot caching is enough for that rhythm, which is the allocation pattern the class was shaped for.
