InlinePoolAllocator

Engine/Memory/InlinePoolAllocator.h template <class T, size_t BlockSize, size_t NumBlocks> A block allocator whose storage is a member array: two blocks of a compile-time size, a free list, the parent allocator behind it, and a copy constructor that asserts.

Class description

template <class T, size_t BlockSize, size_t NumBlocks> class InlinePoolAllocator at Engine/Memory/InlinePoolAllocator.h is a block allocator whose storage is inside the allocator object. The bytes are a member array, not a pointer to a separate allocation: alignas(AlignUnit) uint8_t block[ActualNumBlocks][BlockSizeInBytes]. An allocator of InlinePoolAllocator<char, 128, 2> therefore measures about 256 bytes plus its bookkeeping, and every object that owns one pays that in full. This is what separates it from PoolAllocator, which asks a parent allocator for one buffer and keeps only a pointer to it: a PoolAllocator is cheap to place and expensive to size at runtime, an InlinePoolAllocator is free to place (no parent allocation at construction time) and expensive at compile time, because the size is three template arguments and it cannot change.

The repository's users are the two inline containers in Engine/HSTL/, and both pass NumBlocks = 2. Engine/HSTL/HString.h spells HInlineString as std::basic_string<char, std::char_traits<char>, hbe::InlinePoolAllocator<char, PoolSize, 2>> behind template <size_t PoolSize = 128>, so a use site may re-pick the pool size, while HInlinePathString is the same alias with the pool size fixed at hbe::Config::MaxPathLength.

Engine/HSTL/HVector.h is the same shape: HInlineVector<T, PoolSize = 16> is std::vector<T, InlinePoolAllocator<T, PoolSize, 2>>. Two blocks is the whole point of the pairing — the container gets one request served from its own object and one spare block for the growth step that follows it, and the object carrying the container carries its memory with it.

An object holding one of these pools cannot be copied or moved the way its other members can. The class declares a copy constructor and a virtual destructor and declares no move operation, so C++ gives it no move constructor: an attempt to move a pool selects the copy constructor, and that constructor's body is Assert(false). It delegates to the default constructor, so what it produces is a fresh, empty pool of the same shape — a new registration id, a full free list, none of the source's contents and none of its allocated blocks. In a Dev or Debug build the assertion fires first; otherwise the copy succeeds quietly and the destination starts with nothing. For a HInlineVector the consequence is concrete: moving the vector transfers its element buffer to the destination while the destination's allocator is this newly built empty pool, so a later release of that buffer is not recognised by IsValidPointer (which tests the destination's own array) and travels to MemoryManager::Deallocate under the destination's parentID instead of returning to the source pool. That last step depends on the standard library's move constructor move-constructing the allocator, which the engine does not control; what the engine guarantees is only the empty-pool behaviour above.
BlockSize counts objects, not bytes. The header's own comment block calls it "the desired size of the object allocated in bytes", and the code multiplies it by sizeof(T): BlockSizeInBytes = sizeof(T) * ActualBlockSize. The users agree with the code — HInlineVector<T, 16> means sixteen elements, and a caller who read the comment and passed 16 bytes of a 4-byte type would get four elements' worth of block and send every later request to the parent. The two figures a caller must actually compare against are GetBlockSize (elements) and the byte threshold they multiply out to.

Serving order is fixed and never fails: AllocateBytes takes the one-slot immediateBlock cache if it holds a block, then pops the free list, and if neither can serve the request it calls MemoryManager::FallbackAllocate(GetID(), parentID, nBytes), which allocates from parentID — the allocator that was current when this pool was constructed. A pool therefore never returns nullptr and never reports exhaustion: an over-large request is simply served by the parent, silently. Released blocks go back to the free list, unless the pointer did not come from this pool, in which case DeallocateBytes forwards it to the same recorded parent. The recorded parent is the whole reason the two paths agree: as with PoolAllocator, a pool hands everything it cannot serve to the allocator recorded at construction, not to whatever scope happens to be open at the time.

Construction does three things beyond linking the free list: it records MemoryManager::GetCurrentAllocatorID() as parentID, it registers the pool with the manager under the name "InlinePoolAllocator" and a capacity of ActualBlockSize * ActualNumBlocks * sizeof(T), and it asserts the array is aligned. Deregistration happens in the destructor. The registration is a real per-object cost — see the row on RegisterAllocator.

The conversion operator cannot be used, and its body would not compile if it were. The class declares template <typename TOther> explicit operator InlinePoolAllocator<TOther, ActualBlockSize, ActualNumBlocks>() noexcept. Its body returns TCastedAlloc(parentID) when parentID is valid and TCastedAlloc(GetID()) otherwise, but the class has no constructor taking a TAllocatorID — only the default and the copy constructor — so the expression TCastedAlloc(parentID) is ill-formed. Nothing in Engine/ or Applications/ converts a pool to another element type (a search of both trees for the conversion finds only the declaration), and a template member function is instantiated only when used, so the defect has never been compiled. A container that needs the pool over another element type uses rebind, which hands it InlinePoolAllocator<TOther, BlockSize, NumBlocks> — the arguments as written, not the clamped ActualBlockSize and ActualNumBlocks this conversion would have carried. This entry is documented here rather than on a page of its own for a tooling reason named in Coverage.
Nothing here is synchronised, and one pool is one thread's at a time. The class reads and writes no atomic and takes no lock: availableBlock, immediateBlock and id are plain members mutated by both allocation and release. Two threads allocating through one pool — including two threads inside one HInlineVector — race on the free list. The engine's shareable shape is ThreadSafeMultiPoolAllocator; an inline pool embedded in a container that two threads touch is not it.

Template parameters

ParameterWhat it constrainsWhat getting it wrong costs
class T The element type. sizeof(T) scales every block, allocate casts its result to T*, and AlignUnit is at least sizeof(T). Nothing checks that a request's element count belongs to T; the type is only a unit of arithmetic and a cast target.
size_t BlockSize How many objects of type T one block holds. Raised to sizeof(void*) as a byte count by ActualBlockSize, because a free block must be wide enough to carry the next-pointer of the free list. Too small is silent: a request larger than BlockSizeInBytes bypasses the pool entirely and is served by the parent allocator, so the inline storage is never used and nothing reports the miss except the profile's fallback counter. Too large is not silent: ActualNumBlocks * sizeof(T) * BlockSize bytes are added to the size of every object that owns the pool, and the constructor walks all of them to link the free list.
size_t NumBlocks How many such blocks the array holds — the pool's depth. ActualNumBlocks clamps it to a minimum of 1, so NumBlocks = 0 yields one block rather than none. Same trade in the other direction: more blocks means more simultaneous small allocations before the parent is needed, and more bytes in every owning object. Both HInlineString and HInlineVector chose 2.

Non-member helper functions

None. A pool is reached through its own object or through the MemoryManager registration RegisterAllocator created. The two names the standard library requires — allocate and deallocate — are members for that reason and for no other.

Coverage

Not documented hereWhy
The conversion operator has a note above but no page of its own, and what it would promise is undocumented. Two reasons, both stated so the gap can be closed deliberately. First, the code cannot answer it: the body's TCastedAlloc(parentID) needs a constructor the class does not declare, so there is no observable behaviour to describe — see the note in the class description. Second, docs_pass.py signatures cannot build a Signature block for it: that script names a declaration by the identifier immediately before its opening parenthesis, and a conversion operator's "identifier" is a type carrying template arguments, so the declaration is collected under no name at all and the page would be reported NOT IN HEADER forever. docs_methods.py asks for no page either (its run over Memory filtered to this class lists 17 names and the conversion is not one of them). A future author who fixes the constructor, or teaches the script to name a conversion operator, owes that page.
The behaviour of the #if MEMORY_VERIFICATION_ENABLED zero-fill in the constructor. Named here as a gap, not guessed at: that branch calls std::memset(buffer, 0, length) and the class declares no member named buffer (the array is block), so the branch cannot compile as written. It is inert in this tree — Engine/Config/BuildConfig.h defines MEMORY_VERIFICATION_ENABLED to 0 — and the mismatch is open code work, not documented behaviour. The zero-fill is the constructor page's to describe once the name is fixed.
Whether a given HInlineString or HInlineVector call reaches allocate at all. std::basic_string keeps short strings in its own buffer and std::vector decides growth factors itself; both are standard-library decisions this engine does not make. The page documents what the pool promises a container that does call it, and names the SSO threshold and the growth schedule as outside its scope.
What copying a pool does to a standard container's invariants. The allocator-side half is documented (copy construction and the class description above). The container-side half — which buffer ends up where after a std::vector move, and whether a given library re-allocates on the way — depends on the standard library's implementation and is not claimed anywhere in these pages.
Every path behind #if PROFILE_ENABLED. The profiling configuration of this tree does not compile, recorded in JOURNAL.md on 2026-10-05. The ReportAllocation and ReportDeallocation calls inside AllocateBytes and DeallocateBytes, and the capacity the registration passes along, are described from the source and have never run.
MemoryManager contracts this class leans on: RegisterAllocator, DeregisterAllocator, GetCurrentAllocatorID, FallbackAllocate, the nesting of AllocatorScope. Owned by the MemoryManager pages and the module page. These pages state what a pool does with them, not what they promise.
Whether std::max is available to an includer of this header alone. The header includes <cstddef> and <cstring> and no <algorithm>, so ActualBlockSize, ActualNumBlocks and AlignUnit rely on a transitive include. Recorded as an include-hygiene gap; the three-configuration build is the proof that it currently works, and this wave does not change headers.
InlinePoolAllocatorTest. Test-only: declared in Engine/Memory/InlinePoolAllocator.h inside #ifdef __UNIT_TEST__ and defined in Engine/Memory/InlinePoolAllocator.cpp as eight performance-and-stress testlets plus three vector-growth testlets. It reports timings and warns when the rate exceeds one; it asserts almost nothing, so none of its numbers is a contract, and it owns no page of its own.
