Function description

Both are defined inline in the class body of Engine/Memory/InlinePoolAllocator.h. The default constructor initialises id and parentID to InvalidAllocatorID, points availableBlock at &block[0][0], leaves immediateBlock null, and then, in the body: asserts the first block is aligned with Assert(OS::CheckAligned(block[0])), records the allocator that is current at that moment as parentID from MemoryManager::GetCurrentAllocatorID(), links every block of the array into the free list with WritePointerToNext and terminates the list with a null next-pointer, and finishes with RegisterAllocator. Construction is therefore O(ActualNumBlocks) writes and one manager call, and it requires a live MemoryManager — a pool that exists during static initialisation would be constructing against one that does not.

The copy constructor is a failure path, not a copy. InlinePoolAllocator(const InlinePoolAllocator& rhs) : InlinePoolAllocator() { Assert(false); } — it delegates to the default constructor and then asserts. So the object it builds is a brand-new empty pool (its own registration id, its own full free list, its own parentID taken from whatever scope is open at the copy), and it copies nothing: not the free list, not the blocks already handed out, not the caller's idea of what the pool holds. The assertion fires in a build where Assert is live (Engine/Core/Debug.h defines the reporting form and an inert form; which one is in force is a configuration decision), and where it is inert the copy completes silently. Nothing in the engine tests either outcome — the testlets in Engine/Memory/InlinePoolAllocator.cpp never copy a pool.
There is no move constructor, so "moving" a pool is copying one. The class declares a copy constructor and a virtual destructor and declares no move operation, and a class that declares either of those gets no implicit move constructor. std::is_move_constructible_v is still true for the type — an rvalue binds to the copy constructor — which is exactly the trap: the standard library's move paths accept the allocator happily and land on Assert(false). For an HInlineVector or HInlineString this is the reason a container that owns an inline pool should be built in place and left where it was built rather than stored in a std::vector that reshuffles it. The chain of consequences for a moved container is on the class page.

No assignment operator is declared, so the class carries the implicitly defined copy-assignment operator: it copies every member including the array, and it therefore overwrites the destination's id with the source's while the destination's own registration is still live in the manager. The two objects then hold the same registration id and both hand it to DeregisterAllocator when they die. This page does not document assignment as supported: nothing in Engine/ assigns a pool, no testlet exercises it, and the destructor has no guard against a stolen id beyond the InvalidAllocatorID test.

The Zero-sized Allocation & Deallocation testlet is the tree's only construction of a pool written as a statement of intent rather than as a timing harness: the eight Perf. & Stress testlets each construct one pool with NumBlocks = 32 and measure it against std::allocator. Both HInlineString and HInlineVector construct their pool as part of the container, which is the case with no testlet of its own.
