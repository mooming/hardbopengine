allocate

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h The standard-library allocation entry point: elements become bytes, the pool answers or the parent does, and it never reports exhaustion.

Signature

[[nodiscard]] T* allocate(std::size_t n) noexcept

Function description

Defined inline in the class body of Engine/Memory/InlinePoolAllocator.h. It converts the element count to bytes (n * sizeof(T)), calls AllocateBytes, and casts the result to T*. The name is not a style choice — the header marks it // This function name is enforced by STL, and it exists so that std::vector and std::basic_string can call an engine allocator, which is how HInlineVector and HInlineString are built. It allocates raw storage and constructs nothing: the container runs the constructors itself.

What it never does is fail. AllocateBytes answers a request too large for a block, or made after the free list ran dry, by asking the parent allocator recorded at construction, so a non-null pointer comes back and the caller cannot tell inline storage from parent storage. The noexcept is a promise the pool keeps only through the parent's own behaviour.

allocate(0) hands out a real block. A zero-byte request satisfies the size test in AllocateBytes (0 is never larger than a block), so it takes the immediateBlock cache if one is parked there, otherwise it pops the free list — and a whole block of BlockSizeInBytes bytes leaves the pool for a request of nothing. The Zero-sized Allocation & Deallocation testlet in Engine/Memory/InlinePoolAllocator.cpp exercises exactly this pair and asserts nothing about it, so the block loss is unmeasured as well as silent.
Pair it with deallocate, and read that page first. The two halves of this pair do not use the same unit: allocate converts n to bytes, while deallocate passes n on as a count. The mismatch is harmless for the common allocate-then-deallocate-same-count sequence inside a container because the pointer's identity — IsValidPointer — decides where a block goes, not the size; but it is why a size-based reasoning about this allocator does not survive contact with the code.

Parameters

ParameterTypeMeaning
nstd::size_tNumber of objects of type T. Multiplied by sizeof(T) before the pool sees it, with no overflow check; a request whose byte count exceeds BlockSizeInBytes is served by the parent rather than by the array.

Return value

TypeWhat you get
T*Uninitialised storage for n objects, either from inside this object's block array or from the parent allocator. The page does not document a null return, because none of the engine-side paths produce one; whether the parent can return null is the MemoryManager's contract.

Examples

void* ptrArray[std::decay<decltype(allocator)>::type::ActualNumBlocks];
...
for (int i = 0; i < maxAllocSize; ++i)
{
	for (auto& ptr : ptrArray)
	{
		ptr = allocator.allocate(i);
	}

	for (auto ptr : ptrArray)
	{
		allocator.deallocate(static_cast<int*>(ptr), i);
	}
}

From Engine/Memory/InlinePoolAllocator.cpp, hbe::InlinePoolAllocatorTest::Prepare()

The stress testlet allocates ActualNumBlocks blocks in a row at each size — every block the pool owns, held at once — and then releases them all, so each iteration walks the free list from full to empty and back. What it never does is exceed the pool: the largest request in a testlet is (maxAllocSize - 1) * sizeof(int) bytes and maxAllocSize equals the BlockSize template argument, so the byte count always stays under BlockSizeInBytes and the parent path described above is precisely what these timings never measure.
