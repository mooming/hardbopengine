IsValidPointer

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h A byte-range test over the object's own array - the only thing that separates pool memory from parent memory.

Signature

[[nodiscard]] bool IsValidPointer(void* ptr) const

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and the class's only test of memory ownership: it answers "is this address somewhere inside my array", and that answer is what DeallocateBytes routes on. Two comparisons over a compile-time constant bound: 

constexpr size_t LastBlockIndex = ActualNumBlocks - 1;

return block[0] <= ptr && ptr <= block[LastBlockIndex];

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::IsValidPointer()

block[0] and block[LastBlockIndex] are the addresses of the first byte of the first and last block, so the test is a byte-range comparison against the object's own array — not a lookup in a table of handed-out blocks, and not a query to the MemoryManager.

AddressAnswerConsequence in DeallocateBytes
The start of any blocktrueThe block is pushed onto the free list — the normal return of a pool block.
An interior address of any block except the lasttrueAlso pushed onto the free list, so a pointer that is not a block start becomes a free-list entry whose next-pointer is read from that offset. The class itself never produces such a pointer, so this is a caller-created case.
An interior address of the last blockfalseForwarded to MemoryManager::Deallocate(parentID, ...): memory that is unquestionably part of this object is released to the parent allocator. The bound is the last block's first byte, not the end of the array.
Outside the array — including nullptrfalseForwarded to the parent. This is the path a block that AllocateBytes obtained from the parent normally takes back.
"Inside the array" is not "one of my free blocks", and the upper bound is the last block's first byte. The test cannot distinguish a live block from a released one, so it never detects a double release (see the gap there). And because the comparison ends at block[ActualNumBlocks - 1], the accepted span stops BlockSizeInBytes - 1 bytes short of the end of the array. Every block the pool itself hands out is a block start, so both flaws stay out of sight in ordinary use — which is why no testlet in Engine/Memory/InlinePoolAllocator.cpp tests either bound.
Why the class needs a range test at all. Because a pool answers requests it cannot serve: AllocateBytes sends an over-large request to the parent, and the answer to that request is memory the pool must not put on its free list. The range test is how the release path tells the two apart, at the cost of assuming that the only memory in that byte range is the pool's own. PoolAllocator solves the same problem with IsMine, a range test over its separately allocated buffer; the difference between the two is only which allocation the range covers.

Parameters

ParameterTypeMeaning
ptrvoid*The address to test. Never dereferenced; only its value is compared.

Return value

TypeWhat you get
booltrue when ptr lies between the first byte of block[0] and the first byte of the last block, inclusive. It says nothing about whether that block is currently allocated, in use, or aligned.

Examples

The only caller is DeallocateBytes, which uses the answer as a two-way branch: 

if (!IsValidPointer(ptr))
{
	auto& mmgr = MemoryManager::GetInstance();
	mmgr.Deallocate(parentID, ptr, nBytes);

	return;
}
