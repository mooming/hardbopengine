RegisterAllocator

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Publish the pool to the MemoryManager through two callbacks, or die trying: registration slots are a fixed 256.

Signature

void RegisterAllocator() noexcept

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and called from exactly one place: the end of the default constructor, which the copy constructor reaches by delegation. It builds two stateless lambdas, computes the pool's capacity, and registers this object with the MemoryManager under the literal name "InlinePoolAllocator" and the inline flag set: 

const auto capacity = ActualBlockSize * ActualNumBlocks * sizeof(T);
id = mmgr.RegisterAllocator(this, "InlinePoolAllocator", true, capacity, allocFunc, deallocFunc);

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::RegisterAllocator()

That call is what makes the pool reachable from code that has never seen its type. The lambdas capture nothing and take the void* the manager stored, cast it back to InlinePoolAllocator*, and call AllocateBytes or DeallocateBytes — so an allocation made inside an AllocatorScope opened on this pool arrives at the same two functions a container calls. The capacity figure is the byte size of the member array and is recorded, not enforced: nothing in this class refuses an allocation for exceeding it, and the value is used only by the PROFILE_ENABLED statistics, where the inline flag routes it to the inline usage record (Engine/Memory/MemoryManager.cpp, MemoryManager::RegisterAllocator()).

Registration consumes one of a fixed 256 slots, and running out is fatal. MemoryManager::RegisterAllocator() pops a proxy record from the manager's free pool; when none is left it logs a fatal error and returns InvalidAllocatorID (Engine/Memory/MemoryManager.cpp). The pool then hits FatalAssert(id != InvalidAllocatorID). The pool of records is the fixed array AllocatorProxy allocators[MaxNumAllocators] in Engine/Memory/MemoryManager.h, and MaxNumAllocators is 256 (Engine/Memory/AllocatorID.h). This matters because the inline pools are not process-level singletons: every HInlineString and HInlineVector that is constructed registers one, and every one that is destroyed gives it back. A program holding hundreds of live inline containers at once is competing for the same 256 records as every explicit allocator in the engine.
FatalAssert(id != 0) is the system allocator's number. MemoryManager reserves id 0 as SystemAllocatorID (Engine/Memory/MemoryManager.h), so a pool that came back with 0 would be indistinguishable from the system allocator to anything routing by id. The second assertion is the guard against that, and both assertions are the only validation this function performs on the manager's answer.
A successful registration logs. MemoryManager::RegisterAllocator() writes an Info line naming the allocator and its new id, so constructing an inline pool is a logging call as well as an allocation from the proxy pool. It is also the reason the pool's own GetName text is worth matching the literal passed here: the log line and the profile entry both come from the literal.

Parameters

None. Everything it reports — name, inline flag, capacity — is derived from the type.

Return value

None. The side effect is id: the pool is registered for as long as that holds a real value, which DeregisterAllocator ends.

Examples

auto allocFunc = [](void* allocatorPtr, size_t nBytes) -> void*
{
	auto allocator = static_cast<InlinePoolAllocator*>(allocatorPtr);

	return static_cast<void*>(allocator->AllocateBytes(nBytes));
};

The callback carries no capture, so the manager holds a bare function pointer plus the this it was handed. The obligation that follows is the lifetime rule: the pool must outlive every scope, thread and container that can reach its id.
