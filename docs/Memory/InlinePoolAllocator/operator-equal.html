operator==

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Always false, even for an object compared with itself - the allocator-completeness operator, not an identity test.

Signature

bool operator==(const InlinePoolAllocator&) const

Function description

Defined inline in the class body of Engine/Memory/InlinePoolAllocator.h. The body is return false;. The parameter is unnamed and nothing is compared: not the registration id, not parentID, not the free-list pointers, not the array. An object compared with itself answers false.

The answer is a constant, so no caller may treat it as identity — and containers treat it as inequality. Every other member of this class is instance state, and two pools of the same instantiation are separate objects with separate registrations and separate arrays, so "never equal" is at least a true statement about the world. The consequence worth knowing is that the standard library asks this question: a container move-assigning or swapping from another container of the same type may consult allocator equality before adopting the other container's buffer, and an allocator that always answers unequal forces the element-by-element route into freshly allocated storage. That route is a standard library's decision, not the engine's, and no page here claims which libraries take it — what is documented is the input they get: always false.
The inverse is operator!=, and the pair is consistent. Both are members, so each only accepts a pool of the identical instantiation: same T, same BlockSize, same NumBlocks. Comparing two different instantiations is a compile error rather than a false.

Examples

Nothing in Engine/ or Applications/ compares two pools, and no testlet in Engine/Memory/InlinePoolAllocator.cpp does either. The only comparisons that reach it are the ones a standard container makes internally, which is the reason the operator exists at all.
