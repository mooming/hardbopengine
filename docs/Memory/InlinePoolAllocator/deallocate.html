deallocate

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h The standard-library release entry point - and it forwards the element count where allocate forwarded a byte count.

Signature

void deallocate(T* ptr, std::size_t n) noexcept

Function description

Defined inline in the class body of Engine/Memory/InlinePoolAllocator.h; the body is one call, return DeallocateBytes(ptr, n);. Like allocate, the name is the standard library's requirement and not the engine's choice — the header marks it // This function name is enforced by STL — so that std::vector and std::basic_string can hand a block back, which is what the inline containers in Engine/HSTL/ rely on. It destroys nothing: the container has already run the destructors.

It forwards the element count where allocate forwarded a byte count. allocate computes n * sizeof(T) before calling the helper; this function passes n through unchanged. Inside DeallocateBytes that argument is used as the byte size for three decisions — the threshold that lets a block into the immediateBlock cache, the threshold that lets a block back into the free list, and the size reported to the profiler under PROFILE_ENABLED. For T = char (every HInlineString) the two units coincide and the asymmetry is invisible; for HInlineVector<int> a release of n elements is tested against the block size as if it were n bytes, so the release path admits requests four times larger than the allocation path would have served from the pool. The reported figure is under-stated by the same factor. What actually routes a block is the pointer's identity, not this size, so the asymmetry is a reporting and threshold defect rather than a corruption — and no testlet asserts on it.
Where the block goes is decided by IsValidPointer, not by the caller's intent. A pointer inside this object's block array returns to the free list; anything else is forwarded to MemoryManager::Deallocate(parentID, ...). Releasing a block to a pool other than the one it came from is therefore not an error the pool detects — it is a forwarding decision, and a moved container is the realistic way to make it (see the class page).

Parameters

ParameterTypeMeaning
ptrT*Storage from allocate. A null pointer is not tested for: it takes whichever branch its size and the state of immediateBlock select — see the gap below.
nstd::size_tNumber of objects, passed to the helper unchanged, where the helper treats it as bytes.

Return value

None. The function cannot report failure, and it has no failure to report: both branches end in a pointer write or a manager call.

Examples

auto ptr = allocator.allocate(0);
allocator.deallocate(ptr, 0);

From Engine/Memory/InlinePoolAllocator.cpp, InlinePoolAllocatorTest::Prepare()

The Zero-sized Allocation & Deallocation testlet is the pair in its plainest form: allocate(0) pops a whole block off the free list, and this call parks that block in immediateBlock rather than putting it back, so the pool dies holding one block that never returned. A second zero-size release while the cache is occupied is the case that surprises: the cache test fails, so DeallocateBytes proceeds to IsValidPointer, which a null pointer fails, and the null is forwarded to MemoryManager::Deallocate. No testlet covers that, and the manager's answer to a null release is not documented here.
