Destructor

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Deregisters the pool and nothing else: outstanding blocks, the parent's fallback memory and the array itself are left to others.

Signature

virtual ~InlinePoolAllocator()

Function description

Defined inline in the class body of Engine/Memory/InlinePoolAllocator.h; the body is one call, DeregisterAllocator. It returns this pool's registration slot to the MemoryManager and leaves id as InvalidAllocatorID, which makes a second pass a no-op. It does not walk the blocks, does not release anything to the parent, and does not test whether blocks are still outstanding.

Everything the pool handed out dies with it, silently. The pool's storage is the member array block (see Class properties), so when this object finishes, the bytes it lent are gone. A pointer obtained from allocate and still live when the pool is destroyed does not become invalid in any detectable way: the free list is simply no longer there, and neither is the memory. For the users in Engine/HSTL/ this is the lifetime rule that matters. A HInlineString owns its pool as its allocator, so a c_str() pointer into pool memory cannot outlive the string — and, given that the copy constructor asserts, it cannot outlive a copy attempt either. What the pool does not answer is what happens to a fallback allocation that is still outstanding at destruction: AllocateBytes obtained it from the parent allocator under parentID, the destructor never mentions it, so the release has to come from someone else holding the pointer. The code does not say who.
Virtual, and nothing derives from it. The declaration is virtual ~InlinePoolAllocator(), so every instance carries a vtable pointer and the class is polymorphic. A search of Engine/ finds no class inheriting from InlinePoolAllocator, and the pool's own registration calls it through plain function pointers cast back from void*, not through a base class — so the virtual destructor buys a vtable and nothing else. It also means the implicit copy-assignment operator and the absence of a move operation (see constructors) are permanent: adding a move constructor later is a source-compatible change to the type's shape, not to its layout.

Parameters

None.

Return value

Nothing. After it runs, the object's remaining members (including the pool array) are destroyed by the language, not by this function.

From Engine/Memory/InlinePoolAllocator.cpp, InlinePoolAllocatorTest::Prepare()

Every stress testlet is shaped like this: the pool is a local, so destruction is the ordinary end of a scope, and the testlet has already released what it allocated before the pool dies. That is the pattern this page recommends, not a pattern the destructor enforces — no testlet destroys a pool with allocations outstanding, so that path is unexercised.
