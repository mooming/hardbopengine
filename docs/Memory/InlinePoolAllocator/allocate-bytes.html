AllocateBytes

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Release cache, then free list, then the parent allocator: the only path in the class that can produce a pointer.

Signature

void* AllocateBytes(size_t nBytes) noexcept

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and the only place in the class that produces a pointer. allocate reaches it through the standard-library spelling; the pool's own registration hands the manager a lambda that calls this same function, so a request arriving through AllocatorScope and a request arriving from a container take the same three steps in the same order:

OrderSourceConditionWhat the caller cannot tell afterwards
1immediateBlock — the one-slot release cachenBytes <= BlockSizeInBytes and the slot is occupiedWhether the parked block came from this array or from the parent (DeallocateBytes parks without asking).
2availableBlock — the free listnBytes <= BlockSizeInBytes and the list is not emptyNothing: the pop reads the next-pointer out of the block's own bytes before handing the block over, so the caller may overwrite those bytes immediately.
3The parent allocatorEither the request is larger than one block, or the free list is empty That the storage is not inside this object, and therefore that its size is not BlockSizeInBytes.
auto& mmgr = MemoryManager::GetInstance();
auto ptr = mmgr.FallbackAllocate(GetID(), parentID, nBytes);

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::AllocateBytes()

The third step is the whole of the pool's relationship with the rest of the memory system, and it behaves exactly as PoolAllocator's does: MemoryManager::FallbackAllocate() in Engine/Memory/MemoryManager.cpp forwards to Allocate(parentID, requestedSize), so the bytes come from the allocator that was current when this pool was constructed — not from whatever scope is open now — and only the fallback count is charged to this pool's id, under PROFILE_ENABLED.

The pool keeps no count of what it has handed out, so it can neither report nor warn. There is no counter of live blocks: availableBlock is the only state, and when it reaches nullptr the allocation simply continues into the parent. Contrast PoolAllocator, which answers GetAvailableBlocks, GetUsage and GetCapacity. A caller of this class cannot ask how full the pool is, cannot detect that the inline storage is being wasted, and cannot size a pool from evidence — GetBlockSize and GetNumBlocks report the template arguments, not the traffic. The only observable signal is the profile's fallback count, and that configuration does not compile in this tree.
The size test is against BlockSizeInBytes, which is elements times sizeof(T). One comparison decides whether the array can serve the request at all: nBytes <= BlockSizeInBytes. A request one byte too large is not truncated, split or refused — it is served by the parent, and every later release of it is forwarded back to the parent by DeallocateBytes. Nothing in either direction reports the miss.

Parameters

ParameterTypeMeaning
nBytessize_tByte count. Compared against BlockSizeInBytes; a value of 0 is "small enough" and so consumes a whole block — the case allocate(0) reaches by arithmetic.

Return value

TypeWhat you get
void*Storage of at least nBytes, either inside this object's block array or from the parent allocator, and never a null produced by this function itself. The alignment is that of the array (AlignUnit = at least Config::DefaultAlign, 16 bytes) for array storage; for parent storage it is whatever the parent guarantees.

Examples

auto allocFunc = [](void* allocatorPtr, size_t nBytes) -> void*
{
	auto allocator = static_cast<InlinePoolAllocator*>(allocatorPtr);

	return static_cast<void*>(allocator->AllocateBytes(nBytes));
};

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::RegisterAllocator()

This is why the function is private yet reaches the whole engine: the registration casts the owning object back from the void* the manager stored and calls it. Any allocation made inside an AllocatorScope opened on this pool arrives here, including from code that has never seen the type — which also means the pool must outlive that scope.
