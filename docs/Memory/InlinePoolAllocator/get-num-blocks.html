GetNumBlocks

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Blocks in the member array after the minimum-one clamp - the pool's depth, and the owning object's size.

Signature

[[nodiscard]] static auto GetNumBlocks()

Function description

Defined inline in the class body of Engine/Memory/InlinePoolAllocator.h; the body returns ActualNumBlocks, which is std::max(NumBlocks, static_cast<size_t>(1)). It is the pool's depth: how many blocks of BlockSizeInBytes bytes the member array holds, and therefore how many simultaneous small allocations the pool can serve before the parent allocator has to. Static, compile-time, and silent about how many of them are in use.

A pool of zero blocks is a pool of one, and this is the accessor that proves it. The clamp exists so the array is never empty, which also keeps the constructor's WritePointerToNext(block[ActualNumBlocks - 1], nullptr) inside the array bounds. Reading the answer back is cheaper than re-deriving it: use this, or the constant, rather than the template argument.
The cost it reports is paid by whatever owns the pool. The array is a member, so an object owning InlinePoolAllocator<T, BlockSize, NumBlocks> grows by GetNumBlocks() * sizeof(T) * GetBlockSize() bytes, and the constructor writes a free-list link into every one of those blocks at construction time. Both HInlineString and HInlineVector set it to 2 — one block for the container's first request and one for the block it holds while it grows into a larger one.

The stress harness sizes its holding array by the same constant this accessor returns, so the testlet's worst case is "every block in the pool, held at once" for whatever NumBlocks it was instantiated with — 32 for the eight timing testlets, 2 for anything built through the HSTL aliases.
