DeregisterAllocator

member of hbe::InlinePoolAllocator Engine/Memory/InlinePoolAllocator.h Return the registration slot to the MemoryManager and clear the id, with no question asked about outstanding blocks.

Signature

void DeregisterAllocator() noexcept

Function description

Private, defined inline in the class body of Engine/Memory/InlinePoolAllocator.h, and called from exactly one place: the destructor. Three steps — bail out if there is no registration, hand the id to the manager, clear the id: 

if (id == InvalidAllocatorID)
{
	return;
}

From Engine/Memory/InlinePoolAllocator.h, hbe::InlinePoolAllocator::DeregisterAllocator()

Clearing id is what makes the call idempotent, which matters because the destructor of a class is not the only thing that can run twice in a badly built program: the implicit copy-assignment operator copies id from a live pool to another object (constructors records the consequence), and a second deregistration of a stolen id would otherwise reach the manager a second time.

Nothing checks whether the pool still owes anyone. This function does not consult the free list, does not walk the blocks, and does not ask the parent about fallback allocations. After it runs, the manager's proxy record for the id is released, so any allocation or release routed by that id — through an AllocatorScope still open, or through a pointer someone kept — is addressed to a record that may already have been handed to the next allocator that registers (see GetID). What the engine does to catch that is outside this page: the manager-side check under MEMORY_VERIFICATION_ENABLED is a configuration this tree does not compile, and the pool-side answer is that there is none.
The pool calls the one-argument form. MemoryManager.h also declares DeregisterAllocator(TId id, const hbe::source_location& srcLocation) under PROFILE_ENABLED, which records where an allocator died. This class never passes a location, so an inline pool's deregistration carries no site information even in a profiling build — unlike PoolAllocator, which stores a source_location from its own construction.

Parameters

None. It operates on id and on nothing else.

Return value

None. Afterwards id is InvalidAllocatorID whether or not a manager call happened.

The initialiser that starts the whole cycle: id begins invalid, RegisterAllocator gives it a real value at the end of that same constructor, and this function takes it back. Between those two points is the only window in which the pool can be addressed by the manager.
