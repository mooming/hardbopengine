MultiPoolAllocatorConfig

member of hbe::MultiPoolAllocatorConfig Engine/Memory/MultiPoolAllocatorConfig.h the empty record a failed lookup returns, and the record every report appends

Signature

MultiPoolAllocatorConfig() noexcept = default

MultiPoolAllocatorConfig(StaticStringID id, TPoolConfigs&& configs) noexcept

Function description

Two ways to make a record of type MultiPoolAllocatorConfig at Engine/Memory/MultiPoolAllocatorConfig.h. The defaulted default constructor is declared, not written: it value-initialises uniqueName and leaves configs as an empty vector, which is exactly the record MemoryManager::LookUpMultiPoolConfig returns as its "no such allocator" answer — a function-local static that every failed lookup shares and reads.

The two-argument form is defined out of line in Engine/Memory/MultiPoolAllocatorConfig.cpp and does what its initializer list says: uniqueName(id), configs(std::move(inConfigs)). The parameter is a name and an rvalue reference to the pool list, so the caller's vector is emptied by the move and no copy of the configurations is made. Both parameters are taken by value-of-reference and neither is inspected — a null name id and an empty list produce a record just the same.

Both are reached through emplace_back, so the record is built inside the MultiPoolConfigCache's vector rather than into a temporary that is then copied:

  • data.emplace_back(uniqueName, std::move(poolConfigs)) in MemoryManager::ReportMultiPoolConfigutation — the record for what this run peaked at
  • data.emplace_back(key.GetID(), std::move(configs)) in MultiPoolConfigCache::Deserialize — one per record read back from the cache file, where the name arrives as a StaticString and is interned to an id on the way in

The type has no copy or move constructor of its own, so it has the ones it gets. Neither is declared, deleted or defaulted in the header, so the compiler supplies members-copies of both fields: the id copies, and the pool list copies element-wise. That matters at load time because data is a std::vector and every growth reallocates and copies its elements — records move around the cache while it is being filled, which is why a reference into it is not a promise (see the class page's note on ownership).

Parameters

ParameterTypeRequirement
idStaticStringIDThe allocator's interned name. Not checked for emptiness or uniqueness — two allocators that intern to one id share one record's identity
configsTPoolConfigs&&The pool sizes, moved in and left empty in the caller. May be empty, may be unsorted: neither is inspected here

The default constructor takes nothing.

Return value

Constructors return nothing and cannot fail. Neither form reports an empty name, an empty configuration list, or an out-of-order one; a record is valid-looking the moment it exists, and only the cache's normalisation step ever decides what to do with a useless one.

Examples

Both constructors are invoked through the vector that will own the record:

data.emplace_back(key.GetID(), std::move(configs));

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Deserialize(const Buffer&)

The name is read out of the file as text and interned by GetID() at this point — so the id in a loaded record is this run's id for that spelling of the name, not a number that travelled through the file. That is what allows LookUpMultiPoolConfig to match a freshly constructed allocator's GetName().GetID() against a record written by an earlier process.
