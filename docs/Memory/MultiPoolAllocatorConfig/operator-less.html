operator<

member of hbe::MultiPoolAllocatorConfig Engine/Memory/MultiPoolAllocatorConfig.h ordering by allocator name - the invariant the binary-search lookup is built on

Signature

bool operator<(const MultiPoolAllocatorConfig& rhs) const noexcept

Function description

Declared in Engine/Memory/MultiPoolAllocatorConfig.h, defined in Engine/Memory/MultiPoolAllocatorConfig.cpp, and its body is one comparison: the record is smaller when its uniqueName is smaller. The pool list configs plays no part in it, so two records naming the same allocator are equivalent under this comparator however differently they are provisioned.

That is a deliberate mirror of how the records are used. The cache holds one vector of records and finds things in it by name, so the vector is kept sorted by name:

  • MultiPoolConfigCache::Normalize() calls std::sort(data.begin(), data.end()) before it groups duplicates, and calls it again after, so the vector is name-ordered on the way out of a run — see MultiPoolConfigCache::Normalize
  • the file inherits that order, and Deserialize restores records in the order they were written
  • MemoryManager::LookUpMultiPoolConfig is a plain binary search over that vector — midpoint, compare uniqueName, halve. It is only correct because this comparator is what ordered the vector

The search has no fallback for a list that is not ordered. Nothing between Deserialize and the lookup re-sorts the records: the check that runs on load, outside RELEASE_BUILD, validates the block-size order inside each record's configuration list, not the name order of the vector holding the records. A file whose records were written out of name order therefore loads without complaint and makes the binary search fail — and a failed lookup is indistinguishable from "this allocator has never been seen", so the allocator silently provisions itself by demand instead of by cache.

Name equivalence is used to group, not to merge. MultiPoolConfigCache::Normalize() counts distinct names by comparing each record's uniqueName against the previous one, which relies on this comparator having put every equal name next to every other. Two records for one allocator — two reports in one run, or a report that disagrees with the file — are then collapsed by PoolConfigUtil::MergeMax, keeping the larger block count for every size.

Examples

The comparator is the whole of the body:

return uniqueName < rhs.uniqueName;

From Engine/Memory/MultiPoolAllocatorConfig.cpp, MultiPoolAllocatorConfig::operator<

It is used at exactly the two moments a name-ordered vector needs: before the cache is written, by Serialize through Normalize, and once more inside that same normalisation after the groups have been collapsed. No sort elsewhere in the module uses it — bank lists inside one allocator are ordered by PoolConfig's comparator instead.
