MultiPoolAllocatorConfig

Engine/Memory/MultiPoolAllocatorConfig.h final namespace hbe one allocator name and the pool sizes recorded for it - the record the multi-pool configuration cache stores, writes and looks up

Class description

class MultiPoolAllocatorConfig final at Engine/Memory/MultiPoolAllocatorConfig.h: one allocator's name and the list of pool sizes it should be provisioned with. Where PoolConfig answers "how big, how many", this answers "which multi-pool allocator". It is the record MultiPoolConfigCache stores, writes and reads, and the thing MemoryManager looks up by name at start-up.

A record is created in exactly two places. On the way out of a run, MemoryManager::ReportMultiPoolConfiguration appends one built from an allocator's name and the block sizes it actually peaked at. On the way in, MultiPoolConfigCache::Deserialize appends one per record the cache file held. Nothing else in the engine constructs one, and nothing modifies one afterwards: both fields are public, but the only mutating code path is the vector they live in.

PieceWhat it isWhere the contract lives
uniqueName The interning id of the allocator's name — the key the whole cache is ordered and searched by operator<, LookUpMultiPoolConfig
configs Its pool sizes, ascending by block size once the cache has normalised them Normalize, GenerateBanksByCache
The empty record The defaulted default constructor — a default StaticStringID and an empty list constructors, LookUpMultiPoolConfig

Its ordering is by name; the record inside it is ordered by size. PoolConfig compares block size, this compares a name. operator< compares uniqueName and nothing else, and that is what makes MemoryManager::LookUpMultiPoolConfig a binary search: MultiPoolConfigCache::Normalize() sorts the vector with this comparator before the cache is written, so the file arrives name-ordered and the search over it works. Inside one record, the configs list is ordered by the other comparator. The two orderings are independent, and the nested list is the one a reader most often assumes was sorted by size.

A record is a value the cache owns, and a lookup hands out a reference into the cache's vector. The records live in MultiPoolConfigCache::data, which lives inside MemoryManager — one for the loaded cache and, under PROFILE_ENABLED, a second for what this run reports — so a reference to a record is valid for as long as that vector is not reallocated. LookUpMultiPoolConfig returns such a reference, and hands back a function-local static empty record when the name is absent — the caller distinguishes "not found" by comparing uniqueName, which is exactly what GenerateBanksByCache does before it builds any bank. Nothing here refills a record the caller forgot to check.

Template parameters

None on the class: MultiPoolAllocatorConfig is final and not a template. Its public TVector alias is a member alias template, which is a different thing — it exists to spell the list type inside the class without naming std::vector at each use.
