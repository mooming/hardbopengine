~MonotonicAllocator

member of hbe::MonotonicAllocator Engine/Memory/MonotonicAllocator.h The only release this class performs: the whole buffer goes back through whichever allocator is current, then the registration.

Signature

~MonotonicAllocator()

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::~MonotonicAllocator(). This is the only release the class performs. Three statements, in this order: a profile report, the whole buffer back to the manager, the registration released. 

auto& mmgr = MemoryManager::GetInstance();

#if PROFILE_ENABLED
mmgr.ReportDeallocation(id, bufferPtr, 0, cursor);
#endif // PROFILE_ENABLED

mmgr.Deallocate(bufferPtr, capacity);
mmgr.DeregisterAllocator(GetID());

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::~MonotonicAllocator()

Everything this object ever handed out from its buffer dies on this line — pointers still held included. Deallocate(bufferPtr, capacity) releases the backing allocation itself. There is no per-block record to unwind and no partial release: every address this allocator returned from the buffer becomes invalid the instant the call is made, whether or not the caller ever attempted to release it, and there was never a way to release it individually anyway (Deallocate ignores those calls). The one thing that survives in the other direction is a block that came from the overflow path — those belong to parentID, this destructor does not touch them, and they stay allocated until someone releases them, through this object or through the parent directly.

Who is asked for the bytes back is whichever allocator is current at the moment of destruction, and for this class getting that wrong loses the buffer without a sound. Deallocate(bufferPtr, capacity) is the manager's two-argument overload, and it is a one-line redirect: 

void MemoryManager::Deallocate(void* ptr, size_t nBytes)
{
	Deallocate(GetScopedAllocatorID(), ptr, nBytes);
}

From Engine/Memory/MemoryManager.cpp, MemoryManager::Deallocate(void* ptr, size_t nBytes)

So the buffer release is dispatched through the thread's current scope, not through the parentID the constructor recorded. PoolAllocator's destructor releases through its recorded parent instead; this one does not, which is the asymmetry a caller has to know about when moving an allocator object between scopes. For a monotonic allocator the worst case is worse than the stack's: destroy the object while an AllocatorScope over its own id is still open, and the redirect routes the buffer release straight back into this object's Deallocate — which recognises the address as its own and ignores it. The buffer is never returned to anyone, and nothing asserts, logs or reports: IsMine says true, the call is "ignored" by design, and the leak is total. Derived from the two functions quoted above; no testlet constructs that ordering, so it is named as a hazard and recorded in Coverage.

Declaration order is therefore part of the contract, and the engine's own wrappers get it right. ScopedAllocator<TAlloc> (Engine/Memory/ScopedAllocator.h) declares allocator before scope, so the scope is destroyed first and the buffer returns to the allocator that supplied it. The testlets in Engine/Memory/MonotonicAllocator.cpp declare the allocator outside the scope for the same effect.

The profile report treats the whole buffer as one deallocation of what is still charged. ReportDeallocation(id, bufferPtr, 0, cursor) names the buffer's base and the current cursor, with a requested size of 0 — an accounting entry, not a release. It sits under PROFILE_ENABLED, which Engine/Config/BuildConfig.h defines as 0, and JOURNAL.md (2026-10-05) records that enabling it breaks the build before any Memory file is reached, so this line has never run.
The id is recycled whether or not anything is still outstanding. MemoryManager::DeregisterAllocator(TId id) clears the proxy's function pointers and ends proxyPool.Push(allocator);. The early return that would withhold the id from reuse — a "Memory leak is detected!" warning when the registration's usage is non-zero — sits inside #if PROFILE_ENABLED, so in this configuration the slot is handed to the next allocator unconditionally. Keep a GetID() value only as long as this object is alive.

Parameters

None.

Return value

Nothing. The destructor cannot report a failure, and the failures it can encounter — a buffer released into a scope that will not take it, a registration id that was never valid — are handled (or not) by the manager, not surfaced to the caller. A release that does not happen leaves the bytes owned by the process with no handle to them.

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocatorTest::Prepare(), Deallocation testlet

The test asserts that the destructor's work has not happened yet: after the string is destroyed the allocator must still report non-zero usage, because only this destructor can lower it — and when it does, the object is gone and so is the figure. That is the whole difference between this class and the stack, whose version of the same test demands the opposite.
