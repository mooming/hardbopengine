Deallocate

member of hbe::MonotonicAllocator Engine/Memory/MonotonicAllocator.h noexcept Ignored for this allocator's own bytes; a foreign pointer is forwarded to the parent, where it really is released.

Signature

void Deallocate(const TPointer ptr, TSize size) noexcept

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::Deallocate(Pointer ptr, TSize requested) noexcept — the source names the pointer parameter's type Pointer and drops the top-level const the header writes; neither changes the signature's type. This is the function that decides what this class is: for a pointer the buffer contains, it does nothing at all.

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::Deallocate(Pointer ptr, TSize requested) noexcept

An individual deallocation is legal, and for this allocator's own bytes it is inert. The function is not deleted, not asserting and not empty, so a caller gets no signal of any kind: no return value, no error log, no assertion, and cursor is untouched. GetUsage() is unchanged afterwards, and the bytes cannot be handed to anybody again. The header states it plainly — "Individual deallocations are ignored" — and the class's own testlets in Engine/Memory/MonotonicAllocator.cpp turn that into an assertion, requiring usage to remain non-zero after the scope that allocated has closed, with the message "Monotonic Allocator doesn't provide deallocation.".
In this configuration even the log line does not exist, so the silence is total. The Verbose message that says the call "shall be ignored" sits inside #if MEMORY_LOGGING_ENABLED, and Engine/Config/BuildConfig.h defines that as 0; MemoryManager::Log keeps its entire body inside the same guard and IsLogEnabled returns false unconditionally underneath it. The PROFILE_ENABLED report is likewise compiled out, and when it is present it records ReportDeallocation(id, ptr, requested, 0) — the requested size passed through with a released amount of zero, which is the accounting code saying "nothing was freed". So a caller cannot distinguish "this block is still mine" from "my release was heard" by observation; only this page says so.
A pointer the buffer does not contain is genuinely released — including one that should never have arrived here. The first branch forwards anything IsMine rejects to mmgr.Deallocate(parentID, ptr, requested), and that is a real release from the parent. It is the correct route for a block that came from the parent through Allocate's overflow path. It is also, by construction, the only release this object ever carries out — and it is unconditional: a pointer that belongs to neither this buffer nor the parent (a stack address, a block owned by a sibling allocator, a pointer already given back) is forwarded anyway, and the manager's release path checks id validity and a non-null function pointer and nothing else (MemoryManager::Deallocate(TId id, void* ptr, size_t nBytes)), so the result is a release into the wrong allocator. The stack's release path has the same shape and the same blind forward, but it asserts first for pointers that are inside the buffer; here there is no assert anywhere.
This inertness is what makes the destructor's dispatch dangerous. ~MonotonicAllocator returns the buffer with mmgr.Deallocate(bufferPtr, capacity), which the manager redirects to whichever scope is current. If that scope is this allocator itself, the buffer release arrives here, IsMine recognises the address as belonging to the buffer, and the release is ignored — the buffer is never given back to the allocator that lent it, and no diagnostic exists to say so. See Coverage.
A null pointer is dispatched, not discarded. IsMine answers false for nullptr against a live buffer, so a null release reaches MemoryManager::Deallocate(TId id, void* ptr, size_t nBytes), whose first act is if (unlikely(ptr == nullptr)) { Assert(nBytes == 0); return; }. Releasing null with a non-zero byte count therefore asserts in Debug and Dev and is a clean no-op with 0. Contrast PoolAllocator::Deallocate, which discards null silently before dispatching.
What this makes the class good for, in one sentence. An allocator whose entire body of allocations is released at one point — a frame, an import, a parse, a scope whose every object is known to die before the allocator does. Anything that frees individual objects early, or whose containers outlive the scope that filled them, has to use the stack (last-in-first-out release, honestly reported) or a pool (any-order release into a free list) instead.

Parameters

ParameterTypeRequirement
ptrconst TPointerAny address. The only distinction the function makes is whether it falls inside this buffer; nothing checks that it was ever returned by Allocate.
sizeTSizeThe block's byte count. Unused for a buffer block; passed through unchanged to parentID for anything outside it, which is why a caller must keep the number it gave the overflow path.

Return value

Nothing. The function is noexcept and reports nothing back: the difference between a release that freed memory and one that was ignored is not observable through this interface. GetUsage() is the only way to check from outside, and it will tell you the release did not happen for every block that came from the buffer.

Examples

auto deallocFunc = [](void* allocatorPtr, void* ptr, size_t size)
{
	auto allocator = static_cast<MonotonicAllocator*>(allocatorPtr);
	allocator->Deallocate(ptr, size);
};

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::MonotonicAllocator(const char* name, TSize inCapacity)

No engine or application source calls Deallocate on a monotonic allocator by name; this lambda, handed to MemoryManager::RegisterAllocator, is the call site — which means every destructor of every container built under an AllocatorScope over GetID() arrives here and is dropped. The testlets make that explicit rather than leaving it as a surprise.
