GetID

member of hbe::MonotonicAllocator Engine/Memory/MonotonicAllocator.h nodiscard The registration id the manager keys this allocator by, and the handle an AllocatorScope is opened with.

Signature

[[nodiscard]] auto GetID() const

Function description

Declared and defined in the class body of Engine/Memory/MonotonicAllocator.h: it returns id, so the deduced return type is TAllocatorID (int, Engine/Memory/AllocatorID.h) by value. Because the body lives in the header it inlines into every includer; the rest of the class is in Engine/Memory/MonotonicAllocator.cpp. The value is whatever MemoryManager::RegisterAllocator() returned to the constructor — a slot index in the manager's allocator table, in the range 0 to MaxNumAllocators - 1 (256).

This is the handle a caller needs to make the allocator the current one. Every use the repository makes of it opens an AllocatorScope over the value: AllocatorScope scope(alloc.GetID());, after which containers built in that scope allocate and "release" through this object without naming it. The class uses it on itself too — the destructor hands it to ReportDeallocation (under PROFILE_ENABLED) and to MemoryManager::DeregisterAllocator.
The number is recycled the moment the object dies, so an id you keep has a shelf life. MemoryManager::DeregisterAllocator(TId id) (Engine/Memory/MemoryManager.cpp) clears the proxy's function pointers and ends proxyPool.Push(allocator);, which makes the same index available to the next allocator registered. A value held past this object's destruction addresses whoever received that slot next, and the manager's only guard on the allocation and release paths is the range check IsValid(id). The early return that would withhold an id whose registration still shows usage sits inside #if PROFILE_ENABLED, which is 0 here, so recycling is unconditional in this configuration.
An id from a dead allocator is worse here than elsewhere: the new owner may ignore the release. Because Deallocate routes on IsMine() against the current holder's buffer, a release carrying a stale id is dispatched into whatever object occupies the slot now. If that is another monotonic allocator, the call is likely to be ignored and the memory leaked rather than freed; if it is not, the bytes go to an allocator that never saw them. Nothing in the manager can detect either case.
InvalidAllocatorID is a state that can persist, and it does not mean the object owns nothing. The constructor initialises id to InvalidAllocatorID (-1) before the registration call, and a registration that finds the manager's proxy pool empty logs a FatalError and returns InvalidAllocatorID (MaxNumAllocators is 256) — a check this constructor does not make, so the object keeps a buffer it is not registered to serve. Then the destructor still returns the buffer and asks the manager to deregister an id it will reject with an Error log. No testlet drives that state; see Coverage.

Parameters

None.

Return value

TypeWhat you get
auto, deduced as TAllocatorID (int)The registration id, or InvalidAllocatorID (-1) when registration failed. Valid values satisfy 0 <= id < MaxNumAllocators per hbe::IsValid. The attribute is [[nodiscard]].

Examples

MonotonicAllocator alloc("Test::MonotonicAllocator", 1024 * 1024);
{
	AllocatorScope scope(alloc.GetID());

	HVector<int> a;
	a.push_back(0);
}

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocatorTest::Prepare()

The whole of the engine's usage in one line: the id turns an ordinary allocator object into the thread's current one for the lifetime of a scope. Note the declaration order the destructor depends on — the allocator is constructed outside the scope, so the scope closes first and the buffer is returned while the allocator that lent it is current again. ScopedAllocator<TAlloc> (Engine/Memory/ScopedAllocator.h) encodes the same ordering structurally by declaring allocator before scope.
