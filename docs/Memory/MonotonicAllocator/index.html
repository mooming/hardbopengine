MonotonicAllocator

Engine/Memory/MonotonicAllocator.h final namespace hbe Bump allocation from one fixed buffer: individual releases are ignored, a block that does not fit goes to the parent, and everything left dies with the object.

Class description

class MonotonicAllocator final at Engine/Memory/MonotonicAllocator.h hands out bytes from one fixed buffer by moving a cursor forward and never backward. The constructor rounds the requested capacity up to a multiple of Config::DefaultAlign (16 bytes), records the allocator that is current at that moment as parentID, takes the buffer from the MemoryManager, and registers the object under an id of its own — the same three steps StackAllocator performs, with one difference that decides everything else about this class: the cursor has no way back.

The header states the contract in one sentence — "Memory is released all at once on destruction. Individual deallocations are ignored." — and the source honours it literally. Deallocate accepts a pointer that came from this buffer, logs a Verbose line saying the call "shall be ignored", and returns without touching cursor. The shape the repository actually uses is the Vector Allocation testlet of MonotonicAllocatorTest::Prepare() in Engine/Memory/MonotonicAllocator.cpp: a MonotonicAllocator named "Test::MonotonicAllocator" holding a 1 MiB buffer, an AllocatorScope opened over alloc.GetID(), and an HVector<int> built inside that scope and destroyed inside it too — nothing in the engine calls Allocate on a monotonic allocator directly.

That test asserts the consequence rather than the mechanism. After the scope closes and the string and vectors are destroyed, it demands alloc.GetUsage() != 0 and reads the failure message "Monotonic Allocator doesn't provide deallocation.". A caller who expects a container's destructor to give memory back to this allocator is writing the wrong program; the bytes are gone until the object itself dies.

Every pointer this allocator handed out dies at the destructor, and nothing short of the destructor frees anything. There is no reset: the header declares no Reset, Rewind, ReleaseAll or per-block release that does anything, so the object's destruction is the only moment bytes return. ~MonotonicAllocator calls mmgr.Deallocate(bufferPtr, capacity), which releases the whole backing allocation in one step — so a pointer into the buffer is invalid after that call whether or not the block behind it was ever "released", and the addresses of sibling blocks do not survive either. The one thing that does outlive this object is a block that arrived through the overflow path, because that block belongs to parentID and the destructor does not touch it. See the Deallocate page for what a release attempt actually costs, which is nothing.
A release attempt is legal, silent and inert for this allocator's own bytes. Deallocate is not deleted, not asserting and not empty: it dispatches on IsMine(). A pointer inside the buffer produces a Verbose log and, under PROFILE_ENABLED, a ReportDeallocation whose released amount is 0 — and no other effect. Because MEMORY_LOGGING_ENABLED is 0 in Engine/Config/BuildConfig.h, in this configuration a release of one of this allocator's own blocks does literally nothing observable: GetUsage() is unchanged, and the only hint the code ever gave is a line no build prints. A caller cannot distinguish "this block is still mine" from "my release was heard" without reading this page.
Exhaustion is not a failure, and the block that survives it belongs to the parent. When the aligned request exceeds GetAvailable(), Allocate asks the parent instead of returning null — auto ptr = mmgr.Allocate(parentID, requested);, preceded by a LogWarning that this configuration cannot print. Two consequences a caller has to hold: the pointer is outside this buffer, so IsMine() says no and a later Deallocate of it is forwarded to parentID and genuinely released — unlike a release of a real block — and the block is not freed by this object's destructor, so it must be released explicitly or it leaks past the allocator. Note also that this path calls MemoryManager::Allocate directly, where the stack's overflow path calls MemoryManager::FallbackAllocate: under PROFILE_ENABLED the monotonic overflow is recorded as a plain allocation of the parent and never counted as a fallback.
Alignment is fixed at the engine default and cannot be asked for. Every request is rounded up to Config::DefaultAlign (16) by the inline arithmetic in MonotonicAllocator::Allocate() — (size + AlignUnit - 1) / AlignUnit, then multiplied back. Neither this class nor its parent path takes an alignment argument, so a request for an over-aligned type gets 16-byte spacing at best, and even that is inherited: a block's address is buffer + cursor, and the buffer is whatever the parent's answer happened to be aligned to. See the Coverage section for what the code does not settle.

The class declares no copy constructor, no move constructor and no assignment operator, and it owns two resources: one buffer and one registration id whose proxy record stores this (MemoryManager::RegisterAllocator() in Engine/Memory/MemoryManager.cpp). Two live objects over one buffer would each return that buffer to the manager and each deregister the same id, so one object per buffer is the only supported use. Whether the implicit operations compile at all is a build question this page does not answer — the migration step that owns these pages runs no compiler; see Coverage.

Template parameters

None. MonotonicAllocator is final and not a template: capacity and name are constructor arguments, and the allocator serves raw bytes, so no element type reaches the class.

Non-member helper functions

None. A monotonic allocator is reached through its own object or through the MemoryManager registration its constructor created. The free functions in Engine/Memory/Memory.h (New, Delete) and the AllocatorScope and ScopedAllocator wrappers work on any allocator and belong to the module page. The similarly named InlineMonotonicAllocator is a separate class and is not this one's base or alias.

Coverage

Not documented hereWhy
Thread-safety, and whether one allocator may be shared or moved between threads The code does not answer it. Engine/Memory/MonotonicAllocator.cpp takes no lock and reads and writes no atomic: cursor, capacity and the registration id are plain members, so two threads allocating at once race on the cursor. Against that: the MemoryManager it calls into holds its own statsLock and a thread_local scoped-allocator id, and the engine's shareable shape is the multi-pool allocator the allocator catalogue names. No testlet runs either allocator from two threads, and no assertion binds an allocator to the thread that constructed it (MEMORY_VERIFICATION_ENABLED is 0), so whether sharing is "merely" racy or already checked somewhere is not established here. The manager's own rules are owned by the Memory module page.
Whether an implicit copy or move of MonotonicAllocator compiles A build claim, and this migration step runs no compiler. What is stated instead is the consequence: the destructor frees the buffer and deregisters the id, so a second live object over the same buffer is a double free of both. The class declares nothing about the matter, which is itself the finding — PoolAllocator declares its move operations explicitly, this class does not.
The alignment a returned pointer actually carries Only that block starts are 16 bytes apart, because every charge is rounded to Config::DefaultAlign. Whether buffer itself is 16-byte aligned depends on the allocator that served the constructor's request — in this configuration that is SystemAllocator's malloc path (Engine/Memory/SystemAllocator.h), which the code does not check or force. No test asserts an address modulus, so anything beyond "16 bytes apart inside one buffer" is unnamed.
Every path behind #if PROFILE_ENABLED: the ReportAllocation and ReportDeallocation calls in Allocate, Deallocate and ~MonotonicAllocator, and the stats bookkeeping they drive Engine/Config/BuildConfig.h defines PROFILE_ENABLED as 0, and JOURNAL.md (2026-10-05) records that flipping it breaks the build before any Memory file is reached. Those paths are described from the source and have never executed, so their accounting claims — for instance that Deallocate reports a released amount of 0 while passing the requested size through, or that the destructor reports the whole buffer as a single deallocation of cursor bytes — are read, not observed.
Behaviour of a zero-capacity allocator, and of a failed construction Read from the code, never exercised: no testlet constructs either of these allocators with a capacity of 0, and none makes MemoryManager::Allocate fail. What the code says is that a capacity of 0 rounds to 0, that the manager returns nullptr for a 0-byte request, and that a registration failure yields InvalidAllocatorID while the object still holds a buffer — but the resulting state is untested, so it is named rather than documented as a contract.
What an ignored release costs a long-lived allocator in practice The mechanism is documented on Deallocate — the cursor never moves — but no testlet allocates, releases and re-allocates against a monotonic allocator, so the practical growth of GetUsage() under a workload that "frees" repeatedly is not measured here, only implied by the code.
The stale-pointer and double-release shapes that a block without a header cannot detect Named for completeness: neither class keeps a block header, a footer or a generation counter, so no code in this class can tell a live block from a stale handle to a reused offset. The stack's release path can be talked into rewinding a block that is not the current top, which is the case where that becomes a live-pointer problem; here the same ambiguity is harmless by construction, because no release moves anything. The stack page owns that analysis; this page names it and does not extend it.
