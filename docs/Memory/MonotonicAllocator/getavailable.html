GetAvailable

member of hbe::MonotonicAllocator Engine/Memory/MonotonicAllocator.h nodiscard capacity - cursor: bytes left in the buffer, and on this class a number that can only ever fall.

Signature

[[nodiscard]] size_t GetAvailable() const

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::GetAvailable() const. Two lines: an assertion that the cursor never ran past the buffer, then the subtraction. 

Assert(capacity >= cursor);

return capacity - cursor;

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::GetAvailable() const

Both operands are buffer properties: capacity is the constructor argument already rounded up to a multiple of Config::DefaultAlign, and cursor is the bytes charged against it by Allocate. The same pair of lines is what Allocate consults before deciding whether to serve a request or hand it to the parent.

For this class the figure only ever falls, which is the second sense of "monotonic". No operation lowers cursor — Deallocate ignores every release of a buffer block — so whatever this returns now is the largest value it will ever return again. A stack reports space coming back (the same formula, different life); here the number is a countdown from the constructor's capacity to zero, and the only way to reset it is to destroy and reconstruct the object.
Zero available does not mean allocation fails, so this is not a capacity-to-allocate figure. Allocate answers a request this number cannot cover by calling mmgr.Allocate(parentID, requested). An allocator reporting 0 available will still hand out memory — from the parent, outside this buffer, and invisible to both this function and GetUsage(). Use this number to reason about where the next block will come from, not about whether one will.
The last partial alignment unit of a buffer is not reachable through this number. The comparison in Allocate is size > freeSize where size is the rounded request and freeSize is exactly what this function returns. With 10 bytes available, a request of 10 rounds to 16, and 16 is greater than 10, so the request goes to the parent. A partly-consumed buffer therefore keeps reporting a small non-zero availability that no caller can ever use up.
The assertion is the only place a cursor overrun would be caught. Assert(capacity >= cursor) is why a corrupted cursor is visible at all in a checked build; in Release, hbe::Assert (Engine/Core/Debug.h) is an empty inline function and the subtraction wraps to a huge value that Allocate would read as "plenty of space left", turning every later request into an in-buffer hand-out past the end of the allocation.

That is the function's only consumer, and it is internal: Allocate calls this to decide which allocator will serve the request. No engine or application source asks a monotonic allocator how much room it has left — the class is used through an AllocatorScope only, and its testlets in Engine/Memory/MonotonicAllocator.cpp check GetUsage() rather than this.
