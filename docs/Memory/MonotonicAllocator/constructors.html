MonotonicAllocator

member of hbe::MonotonicAllocator Engine/Memory/MonotonicAllocator.h Rounds the capacity up, takes the buffer from the allocator that is current, and registers this object with the manager.

Signature

MonotonicAllocator(const char* name, TSize capacity)

Function description

Defined in Engine/Memory/MonotonicAllocator.cpp as MonotonicAllocator::MonotonicAllocator(const char* name, TSize inCapacity). One constructor, one overload — the stack's profile-carrying third parameter has no counterpart here. Four steps, in this order: round the capacity, take the buffer from the allocator that is current, describe the two dispatch lambdas, register. 

: id(InvalidAllocatorID)
	, cursor(0)
	, capacity(inCapacity)
	, buffer(nullptr)
{
	{
		constexpr auto AlignUnit = Config::DefaultAlign;
		const auto multiplier = (capacity + AlignUnit - 1) / AlignUnit;
		capacity = multiplier * AlignUnit;
	}

	auto& mmgr = MemoryManager::GetInstance();
	parentID = hbe::MemoryManager::GetCurrentAllocatorID();
	bufferPtr = mmgr.Allocate(capacity);

	// … the allocFunc and deallocFunc registration lambdas …
	id = mmgr.RegisterAllocator(this, name, false, capacity, allocFunc, deallocFunc);

StepWhat it fixes for the object's whole life
Round capacityUp to a multiple of Config::DefaultAlign (16), so capacity is never smaller than what was asked and is always a whole number of alignment units.
Record parentIDMemoryManager::GetCurrentAllocatorID() returns the thread's current scoped id — the scope that was open when this constructor ran, or SystemAllocatorID (0) if none was. Written in the body; this member is not named in the initializer list.
Take the buffermmgr.Allocate(capacity) is the two-argument call through GetScopedAllocatorID(), so the bytes come from the same allocator parentID names, and from this thread's scope.
RegisterRegisterAllocator(this, name, false, capacity, allocFunc, deallocFunc) stores this in an AllocatorProxy record. The false is isInline.
The object owns the buffer for its entire life, and nothing can hand it back early. There is no GetBuffer() accessor and no release path a caller can drive: only ~MonotonicAllocator returns the bytes, in one call, whether or not the caller is still using blocks inside them. Callers own the blocks within the buffer; the object owns the buffer itself. That is the sentence a caller of this class has to plan around, because for a monotonic allocator "I am done with this string" buys back nothing — see Deallocate.
The name is a registration label, not a member. It is passed to RegisterAllocator, which stores it in the profile statistics and substitutes "None" for a null pointer (Engine/Memory/MemoryManager.cpp); neither this class nor its proxy record keeps it in a configuration where PROFILE_ENABLED is 0. The class has no GetName, and Deallocate's Verbose line reaches the name through mmgr.GetAllocatorName(id) instead of a member.
Two failure shapes are readable from this body, and neither is exercised by a test. Constructing before the manager exists is fatal and immediate: MemoryManager::GetInstance() is FatalAssert(mmgrInstance != nullptr); return *mmgrInstance;, and FatalAssert aborts in every configuration because it sits outside the #if !RELEASE_BUILD block in Engine/Core/Debug.h. A registration that finds the manager's proxy pool empty logs a FatalError and returns InvalidAllocatorID (MaxNumAllocators is 256, Engine/Memory/AllocatorID.h) — and this constructor does not check for it, so the object keeps a buffer it cannot serve allocations for. Both are described from the source and untested; see Coverage.
Capacity is rounded before it is spent, so a request below the alignment unit still costs a full one. A capacity of 1 becomes 16; a capacity of 17 becomes 32. A capacity of 0 stays 0, and the manager's MemoryManager::Allocate(TId id, size_t nBytes) returns nullptr for a zero-byte request — so a zero-capacity allocator is an object with a null buffer, a valid id, and an GetUsage() assertion that fails the first time it is called. Named rather than documented as a contract: no testlet constructs either allocator with a capacity of 0.

Parameters

ParameterTypeRequirement
nameconst char*Label for the manager's registration log and profile statistics. nullptr is accepted and becomes "None". Not copied by this object.
capacityTSizeBytes of backing storage to reserve, rounded up to a multiple of Config::DefaultAlign before the request is made. Read as an unsigned value: a negative intent becomes a very large request.

Return value

Nothing — construction either produces a usable allocator or aborts the process. The one non-fatal failure, a full proxy pool, produces an object holding a buffer and carrying InvalidAllocatorID; nothing in this body reports it to the caller.

From Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocatorTest::Prepare(), Vector Allocation testlet

The declaration order is part of the use: the allocator is constructed outside the scope, so its parentID is whatever was current before the scope opened (in the test, the system allocator), and the scope's own destruction restores that state before the allocator is destroyed. ScopedAllocator<TAlloc> (Engine/Memory/ScopedAllocator.h) encodes the same ordering structurally — it declares allocator before scope, so the scope always dies first. It is also the only way to nest this class over itself: the nested-scope testlet in Engine/Memory/StackAllocator.cpp uses ScopedAllocator<StackAllocator>, and the same shape applies here, with each level's buffer coming from the level outside it.
