Module Index / Memory / AllocatorID

AllocatorID

Engine/Memory/AllocatorID.h namespace hbe utility header the identity type every allocator in the engine is named by, its two bounds, and the single range check that guards it

Class description

A header, not a class: Engine/Memory/AllocatorID.h declares the identity type that every other signature in the Memory module is written against — using TAllocatorID = int; in namespace hbe, the two constants that bound it, and the one free function that tests it. Everything else in the module takes or returns this type: GetID on every allocator, MemoryManager's RegisterAllocator and DeregisterAllocator, and the allocation and deallocation entry points that route a request to an allocator by number.

An id names a slot, not an allocator object. MemoryManager owns AllocatorProxy allocators[MaxNumAllocators] and hands out the slot's fixed index (Engine/Memory/MemoryManager.h); the proxy at that index is the registration, and AllocatorProxy holds the allocator pointer plus the allocate and deallocate function pointers that a request is dispatched through. Id 0 is reserved: MemoryManager::SystemAllocatorID is registered before the free pool is built, so the pool a normal allocator draws from holds indices 1 to MaxNumAllocators - 1.

PieceWhat it isWhere the contract lives

The dispatch Index → proxy → function pointer. An out-of-range id is answered with a throwaway proxy, not a failure GetAllocatorProxy

The lifetime of an id is exactly the lifetime of the registration that issued it. It is not a handle, not a lease, and carries no generation: AllocatorProxy stores an id but nothing that says which registration is currently sitting in that slot. Contrast TaskID, which pairs an index with a generation precisely so a stale identity resolves to nothing. Once DeregisterAllocator returns the proxy to the free pool, the next RegisterAllocator call may hand the same integer to an unrelated allocator, and IsValid still reports the old value as valid because the only thing it can check is the range. Nothing in the engine can tell the two registrations apart.

A block that outlives its registration is routed by the id it carries, not by the allocator that gave it memory. That is the hazard this module has already had to fix once: the monotonic allocators recorded their owner in parentID at construction but released their backing buffer through the ambient MemoryManager::Deallocate, which resolves the currently open scope. Destroying such an allocator while its own scope was open sent the release into that allocator's own Deallocate — which ignores individual releases — so the buffer never came back; the destructor now names the parent explicitly (mmgr.Deallocate(parentID, bufferPtr, capacity) in Engine/Memory/MonotonicAllocator.cpp, MonotonicAllocator::~MonotonicAllocator()). The rule for a caller is the same rule: memory is released through the id of the allocator that owns it, never through whatever scope happens to be open.
What a stale id costs depends on the build. Under PROFILE_ENABLED, DeregisterAllocator inspects the proxy's usage, logs Memory leak is detected! with the byte counts, calls debugBreak() outside RELEASE_BUILD, and returns early — so the slot is never recycled and a stale id keeps naming the dead registration whose function pointers are already null. With profiling off there is no usage accounting at all, so the proxy goes straight back to the pool and the same stale id reaches whatever allocator takes that slot next, whose deallocate receives a pointer it never handed out. ReportDeallocation then subtracts that byte count from the new owner's usage, which is how an accounting error and a wrong-allocator free arrive together.

Template parameters

None. Engine/Memory/AllocatorID.h declares no template — the id is a plain alias, not a type wrapper, so it converts implicitly with int everywhere.

Class methods

One function. It is a free function in namespace hbe, declared inline in the header, so it is reachable unqualified from anywhere the alias is.

Non-member helper functions

None besides IsValid. MemoryManager also declares a private static member of the same name and the same expression (MemoryManager::IsValid); the two are independent definitions of one rule, and the member does not call this one.

Thread-safety of registration and deregistration — whether two threads may register at once The free pool is an AtomicStackView, and the statistics under PROFILE_ENABLED are written under statsLock, but the plain writes to allocator, allocate and deallocate in MemoryManager::RegisterAllocator are unsynchronised. No page in the module states a rule, so none is asserted here

There is no compile-time or running count that warns before the exhaustion happens
