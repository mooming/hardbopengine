AllocatorProxy

Engine/Memory/AllocatorProxy.h final namespace hbe The record the MemoryManager dispatches every engine allocation through: one allocator handle, the two operations forwarded as plain function pointers, plus the identity, free-list link and profiling state that ride along

Class description

class AllocatorProxy final at Engine/Memory/AllocatorProxy.h is the record the MemoryManager dispatches every engine allocation through. It adapts an allocator object of any design to one fixed C calling convention: an opaque void* allocator handle plus two free-function pointers, allocate(handle, nBytes) and deallocate(handle, ptr, nBytes). A request reaches the registered allocator as the plain call allocProxy.allocate(allocProxy.allocator, nBytes) from MemoryManager::Allocate() (Engine/Memory/MemoryManager.cpp) — no virtual dispatch, no template, nothing between the manager and the function the allocator registered. The two forwarded operations are exactly these and nothing else: the proxy forwards allocation and release; size queries, ownership tests and statistics never travel through it, they live on the allocator object itself or on AllocStats.

The proxy belongs to the manager, not to the allocator it describes. Every proxy is one element of the fixed array AllocatorProxy allocators[MaxNumAllocators] owned by MemoryManager (Engine/Memory/MemoryManager.h), and it outlives every registration: RegisterAllocator pops a free record and fills it, DeregisterAllocator nulls both operation pointers and pushes the same record back onto the manager's free list, where the next registration reuses it. A pointer or reference to a proxy is therefore an address into the manager's array — never a lease on the allocator behind it, and its contents can describe a different allocator by the next line.

An out-of-range id is silently re-routed on the allocation path, but only after the assert path has been taken. MemoryManager::Allocate(TId, size_t) asserts id != InvalidAllocatorID, logs an error naming the id for any other invalid value, and then uses slot 0 — the system allocator (Engine/Memory/MemoryManager.cpp). So a stale id does not fail a shipped build; it moves the traffic to the system heap and leaves an error line as the only trace. The pointer you get back is then owned by slot 0, and releasing it through a different id is exactly the mismatch this module's allocators guard with IsMine.

Template parameters

None. AllocatorProxy is final and not a template — type erasure is done with the two function pointers and the void* handle, so one record shape serves every allocator in the engine.
