Module Index / Memory

Memory

namespace hbe Engine/Memory 23 headers, 16 sources — allocators, the manager that registers them, and the typed helpers over both

Module description

The engine does not call malloc directly. An allocator is an object with a strategy — bump a pointer, carve fixed blocks, recycle from a free list, keep one pool per block size — and the MemoryManager registers those objects under an id so any subsystem can allocate against the right strategy without owning one. Every container and HSTL alias in the engine routes through this module, which is what makes memory accounting mean anything.

Which strategy to use, and why, is the subject of docs/AllocatorGuide.md and docs/MemoryManagement_Guide.md. This page is what you call.

MemoryManager (Engine/Memory/MemoryManager.h)

Class description

Registers allocator objects under ids and routes allocation to them. One instance belongs to the Engine, and it must be the first thing alive — every other subsystem allocates through it, and the memory level cannot be switched off.

Template parameters

None — MemoryManager is not a template.

Class properties

The registered allocator table and the current-allocator stack; header-private.

Class methods

    void SysDeallocate(void* ptr, size_t nBytes);

MethodContract a caller depends on
RegisterAllocatorThe allocator object is passed as void* and must outlive the registration; isInline says whether storage lives inside the object, which is what decides who frees what
Allocate, DeallocateBoth take the id, and the size must match between them — a pool returns a block to the size class it came from, so a mismatched size is a corrupted free list, not a leak
SysAllocate, SysDeallocateThe system allocator, for the cases where a custom pool is wrong: oversized or long-lived blocks
FallbackAllocateTry one allocator, then a parent — the shape behind an allocator that degrades instead of failing
New, Delete, NewArray, DeleteArrayTyped wrappers: construct after allocating, destroy before releasing. DeleteArray takes the element count, because the engine cannot recover it from a pointer

Every allocator here implements the same pair — allocate bytes, deallocate bytes — under the TAllocBytes and TDeallocBytes shapes the manager calls through. AllocatorScope (Engine/Memory/AllocatorScope.h)

Class description

RAII: saves the current allocator on construction, installs another, restores on destruction. This is how a subsystem says "everything allocated in this block of code belongs to this pool" without threading an allocator through every call.

Template parameters

None — AllocatorScope is not a template; one constructor is, taking anything that answers GetID().

Class properties

The saved allocator id and the scope's depth; header-private.

Class methods

class AllocatorScope final
{
public:
    AllocatorScope(const AllocatorScope&) = delete;
    AllocatorScope(AllocatorScope&&) = delete;

    AllocatorScope() noexcept;                          // current allocator, saved and restored
    AllocatorScope(TAllocatorID id) noexcept;
    template<typename T>
    AllocatorScope(const T& allocator) noexcept : AllocatorScope(allocator.GetID()) {}
    ~AllocatorScope() noexcept;
};

Copying and moving are both deleted on purpose: a scope that could be copied to another stack frame would restore the allocator in the wrong order, which is the failure this type makes uncompilable instead of rare-and-fatal. The default constructor is not "do nothing" — it saves and restores too, which is what you want when a callee changes the current allocator internally.

Non-member helper functions

None.

AllocatorProxy (Engine/Memory/AllocatorProxy.h)

Class description

The record the manager keeps for a registered allocator: its id, the object, and the two plain function pointers it calls. Any allocator can be registered by filling one in, which is why the manager holds void* rather than a virtual base.

Template parameters

None — AllocatorProxy is not a template.

Global allocation accounting (Engine/Memory/GlobalAllocation.cpp)

The engine owns the process's allocation entry points, and the accounting that comes with them. It exists because AllocatorScope cannot reach them: a std::vector or std::string reaches the heap through operator new, which no scope redirects, so without this file an allocation made in the middle of anything - a task, a test, a subsystem boot - happens off every report the engine owns. That is not a hypothetical: measured over the unit test suite, 320 of 372 testlets reach the global heap from their own bodies, and the engine's own per-testlet allocator reports usage for none of them.

Static members of MemoryManager

Called by the allocation entry points, not by engine code directly; never logs and never allocates, because an accounting path that allocated would re-enter the allocator it measures.

static uint64_t GetGlobalAllocationCount() noexcept Requests made since process start. Same cumulative rule.
static size_t GetGlobalFreeBytes() noexcept Bytes released since process start, where a release through the unsized operator delete reports the block size the system heap chose rather than the size originally asked for.
static uint64_t GetGlobalFreeCount() noexcept Releases that reached the entry points since process start.

Contract

PropertyGuarantee
Availability Valid from the first instruction. The counters are constant initialised, so there is no ready flag to get wrong and no window in which an allocation goes unrecorded. This is why the record is not paired: an allocation made before anything existed and released afterwards cannot drive a negative figure, which is exactly what a paired record would suffer.
Thread safety Relaxed atomics. The totals are correct in the aggregate; there is no ordering between the byte counter and the request counter, so never treat a bytes/count pair as one instantaneous sample.
Recursion Impossible by construction on the accounting path. The failure path is the exception, and it is guarded by giving any installed new_handler its turn before reporting.
Exhaustion Logs the size and alignment, then aborts. A deliberate deviation from the standard's std::bad_alloc: the engine is exception-free, so nothing could catch it, and throwing would lose the message with it.
Alignment The over-aligned forms go through posix_memalign with the requested alignment rounded up into the size, which is what that API requires.

Decisions, with what decided them

DecisionReason, measured where measurement was possible
The backing store stays malloc SystemAllocator is the natural owner of the system heap and routing these entry points through it is the right destination. Not yet: its investigation configuration allocates page granular with underrun placement, which would silently turn each small standard-library allocation into a page and change what every configuration measures. Keeping malloc also keeps releases unambiguous - a pointer produced before this file existed is still freeable by the same call that was freeing it then.
Not merged with SystemAllocator's usage record Two independent reasons. MultiPoolAllocator takes its bank backing through AllocatorScope(MemoryManager::SystemAllocatorID), so a merged figure would attribute a bank to whichever testlet or task happened to trigger it. And the two count different quantities: this one counts bytes requested, that one counts capacity obtained and pairs allocations with releases.
The entry points are operator new, not malloc Measured on macOS/arm64 with Apple clang before choosing. A __DATA,__interpose entry replacing malloc in the executable caught nothing - not even a malloc(64) issued directly by the test's own translation unit - because callers inside the dyld shared cache are pre-bound and interposition cannot rebind them. Defining operator new in the binary caught every allocation of std::string, std::vector and a bare operator new in the same program: 3 requests, 18,496 bytes. Allocations made inside system images still bypass this, which is a boundary of the technique rather than a defect in it.
Cost is accepted in all three configurations A/B with counters live against counters zeroed, three samples each, median: Debug +0.23s (+1.3%), Release indistinguishable - the instrumented build measured 0.53s faster, which says only that the difference is noise.

Reading it

// Every figure is a delta: none of these totals is ever reduced by a release.
const auto requestsBefore    = MemoryManager::GetGlobalAllocationCount();
const auto bytesBefore       = MemoryManager::GetGlobalAllocationBytes();
const auto freedBytesBefore  = MemoryManager::GetGlobalFreeBytes();

DoWork();

const auto requests = MemoryManager::GetGlobalAllocationCount() - requestsBefore;
const auto bytes    = MemoryManager::GetGlobalAllocationBytes() - bytesBefore;
const auto freed    = MemoryManager::GetGlobalFreeBytes() - freedBytesBefore;

/* Retained is what a ceiling wants: a loop may request hundreds of megabytes and
 *  hold almost none of it, a leak holds every byte without asking for more. The
 *  clamp is not decoration - a block can be larger than the size that was asked
 *  for, so freed can slightly outrun bytes. */
const auto retained = bytes > freed ? bytes - freed : 0;

The unit test suite is the current consumer and shows the shape: it measures the delta around each testlet body, refuses a testlet holding more than its ceiling - see the Test module's ceiling page - and prints the totals for the run.
