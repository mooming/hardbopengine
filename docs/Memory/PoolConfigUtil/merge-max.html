MergeMax

member of hbe::PoolConfigUtil Engine/Memory/PoolConfigUtil.h free function in hbe::PoolConfigUtil reconcile two configuration lists by keeping the larger count for every block size - and empty the source

Signature

void MergeMax(TPoolConfigs& dst, TPoolConfigs& src);

Function description

Defined in Engine/Memory/PoolConfigUtil.cpp. It reconciles two configuration lists into the first one: after it, dst holds every block size either list mentioned, with the count for a size shared by both taken as the larger of the two, and src is empty.

The order of operations is the contract:

  1. Normalize is applied to dst first, always.
  2. If src is empty the function returns there, leaving dst normalised and src untouched.
  3. Otherwise src is normalised too, so both sides are ascending and free of duplicate sizes.
  4. A merge walk runs over dst by index. Every src entry smaller than the current destination size is appended to dst; on equal size the destination keeps std::max(dstNumBlocks, srcNumBlocks) and the source index advances.
  5. Whatever src entries remain are appended, src.clear() empties the source, and std::sort(dst.begin(), dst.end()) puts the whole result back in ascending order.

The max is the name of the function and the point of it. Within one list Normalize sums the counts of equal sizes, because two pools of the same stride really do hold that many blocks between them. Across two lists it takes the larger, because two lists describing the same allocator are two observations of the same thing — a peak seen before and a peak seen now — and the larger is the one that is safe to provision.

src is destroyed by the call. The last steps are src.clear() and the sort of dst, so a caller that kept the source list for anything else — a second merge, a report, a fallback — finds it empty. The one caller relies on exactly that: MultiPoolConfigCache::Normalize() merges each duplicate entry's configurations into an accumulator and never reads them again. Note the asymmetry too: the early return for an empty src is the only path that leaves both arguments in a state the caller might still recognise.

The walk does not see what it appends. The destination length is read once at the top of the merge loop, while new entries are added with push_back during it, so appended source entries are never revisited as destinations. That is what allows a source size to land between two destination sizes without being merged into anything, and it is why the closing std::sort is not redundant: the appends happen at the end of the vector, out of order with respect to the rest of it. It also means the growth is reallocation of the caller's vector while the loop indexes it by position — indexes stay valid, but any reference or iterator a caller held into dst does not.

Parameters

ParameterTypeRequirement
dstTPoolConfigs&The list that survives. Normalised on entry regardless of what happens next, then grown and re-sorted; may be empty, in which case it receives the source
srcTPoolConfigs&The list that is consumed. Normalised unless it is already empty, and cleared before the function returns

Return value

None. The outcome is the state of the two lists when the call returns: the merged and sorted result in dst, an empty src.

Examples

The single caller merges each cached entry's configurations into the accumulator it is building:

PoolConfigUtil::MergeMax(tempConfigs, item.configs);

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Normalize()

The cache can hold several records with the same uniqueName — one per ReportMultiPoolConfigutation call, and an allocator may report more than once in a run. This call is where those records collapse into one provisioning plan per allocator, keeping the highest count seen for every block size rather than adding the reports together. See MultiPoolConfigCache::Normalize.
