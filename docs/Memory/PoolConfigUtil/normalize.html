Normalize

member of hbe::PoolConfigUtil Engine/Memory/PoolConfigUtil.h free function in hbe::PoolConfigUtil sort a configuration list, then fold it down to one entry per block size, summing the counts of every run

Signature

void Normalize(TPoolConfigs& configs);

Function description

Defined in Engine/Memory/PoolConfigUtil.cpp. It takes a list of pool configurations in any order and leaves behind the same list sorted ascending by block size and folded down to at most one entry per size. Three steps, in this order:

  1. std::sort(configs.begin(), configs.end()) — the ordering PoolConfig::operator< decides, which reads blockSize only.
  2. A first pass counts distinct block sizes with a local lambda, skipping every entry whose count is zero, so the result can be reserved exactly.
  3. A second pass walks the sorted list and emits one entry per run of equal sizes, with the run's counts summed.

The walk is run-detection, not a hash: it advances to a new size whenever config.blockSize != blockSize, which is only correct because step 1 put equal sizes next to each other. Before the second pass the caller's vector is swapped into a temporary and configs.reserve(numUniqueBlocks) is called, so the output is written into freshly reserved storage sized to the distinct count — the caller's previous capacity is not kept, and any pointer or reference into the old buffer is invalid once this returns.

The fold is closed by Assert(configs.size() == numUniqueBlocks): the number of entries emitted must equal the number of sizes counted in step 2. That assertion is the only cross-check between the two passes.

Two kinds of entry are dropped silently, and the assertion cannot see it. The emit guard is if (blockSize > 0 && numBlocks > 0), so a run whose block size is zero or whose summed count is zero never reaches the output; the counting pass makes the same exclusion — it skips zero-count entries, and its running comparison is seeded with blockSize = 0, which means a leading zero-size entry is never recognised as a new run either. Both passes agree, so the sizes still match and the assertion passes. A configuration that asked for nothing is quietly removed rather than reported, and a list of nothing-but-zeros comes back empty.

Counts are summed here and maxed later. Normalisation is the additive step: two entries of the same size become one whose count is their total. The next function in this namespace, MergeMax, deliberately does not add — across two lists it keeps the larger count for each size.

Parameters

ParameterTypeRequirement
configsTPoolConfigs&A list of pool configurations, modified in place. May be empty, may be unsorted, may hold duplicate sizes; the caller keeps the sorted, folded result and loses its original capacity

Return value

None. The function reports nothing: it cannot fail, it cannot refuse an entry, and it gives no signal when it drops one. The observable outcome is entirely in the list the caller passed in.

Examples

The one caller in the tree applies it to each bank configuration before a merge:

PoolConfigUtil::Normalize(item.configs);

From Engine/Memory/MultiPoolConfigCache.cpp, MultiPoolConfigCache::Normalize()

That call sits inside the loop over every cached allocator entry, run before the entries are grouped by name and reconciled with MergeMax. The same function is what guarantees the cache file is written in size order, because it is called from MultiPoolConfigCache::Serialize by way of that Normalize — and Deserialize trusts that order rather than restoring it.
