PoolConfigUtil

Engine/Memory/PoolConfigUtil.h namespace hbe::PoolConfigUtil utility header the two algorithms a list of pool configurations has to pass through before the cache trusts it

Class description

A namespace, not a class: hbe::PoolConfigUtil at Engine/Memory/PoolConfigUtil.h holds the two algorithms a list of PoolConfig entries needs before it can be trusted — Normalize, which sorts a list and folds it down to one entry per block size, and MergeMax, which reconciles two such lists by taking the larger count for every size. Both are declared here and defined in Engine/Memory/PoolConfigUtil.cpp, so unlike most of this module's small helpers they are real out-of-line calls.

The namespace also owns the list type itself: using TPoolConfigs = std::vector<PoolConfig>; is the container every configuration path passes around. MultiPoolAllocatorConfig spells the same list MultiPoolAllocatorConfig::TPoolConfigs over its own TVector, and MultiPoolConfigCache::Deserialize() builds one as MemoryManager::TVector<PoolConfig> — three names for one shape, and only this one carries the algorithms.

PieceWhat it isWhere the contract lives
The list type std::vector<PoolConfig>, sorted ascending by block size whenever these functions have finished with it TPoolConfigs
Compaction Sort, then one entry per distinct block size with the run's counts summed Normalize
Reconciliation Merge two normalised lists, keeping the larger count per size and consuming the source MergeMax

Both functions have exactly one caller in the engine. MultiPoolConfigCache::Normalize() in Engine/Memory/MultiPoolConfigCache.cpp is the only code that calls either one: it normalises each bank configuration and then merges duplicates before the cache is written. A configuration list assembled anywhere else — a caller building its own TPoolConfigs, or the list GenerateBanksByCache replays — reaches the allocators unnormalised unless something in that path happens to sort it first.

Template parameters

None. The namespace declares one alias and two free functions; nothing in it is templated. The element type is fixed to PoolConfig, so a list of anything else is a different type and a different problem.

Class methods

NameSignatureWhat a caller depends on
Normalize void Normalize(TPoolConfigs& configs) The list ends sorted ascending by block size with at most one entry per size; counts of equal sizes are summed and zero totals are dropped.
MergeMax void MergeMax(TPoolConfigs& dst, TPoolConfigs& src) Both lists are normalised first, equal sizes keep the larger count rather than the sum, and src is emptied when the merge finishes.

Non-member helper functions

Both declared functions are free functions of hbe::PoolConfigUtil; there is no helper beside them. Engine/Memory/PoolConfigUtil.h includes <vector> and PoolConfig.h, and the implementation additionally pulls in <algorithm> for std::sort and std::max and Engine/Core/Debug.h for the assertion that closes Normalize.

Coverage

Not documented hereWhy
Whether these two functions are thread-safe, or may be called on one list from two threads Neither takes a lock and neither documents a rule, and the single caller runs on the shutdown path where no concurrent registration is expected. Nothing in Engine/ states the assumption, so it is not asserted here
What a caller should do with a list that Normalize shortened The functions report nothing: entries vanish silently when their block size or their summed count is zero, and the only witness is the assertion comparing the result size to the distinct-size count. There is no return value, no log line and no error code in either function
Why MergeMax takes the maximum of two counts rather than their sum The code is unambiguous — dst[dstIndex].numberOfBlocks = std::max(dstNumBlocks, srcNumBlocks) — but the reason is a design choice about what a reported peak means, and no comment, test or document in the tree states it
