Engine

Engine/Engine/Engine.h namespace hbe final non-copyable the object that owns every subsystem by value, publishes itself as the one instance, and has to be told to shut down before it dies

Class description

Engine is the aggregate. Five subsystems live inside it as plain members — MemoryManager, SystemStatistics, Logger, TaskSystem and ResourceManager — together with one std::unique_ptr to the OS application, one std::ofstream for the engine's own log lines, and two mutexes. Declaring one is how an application starts the engine: every entry point in the repository declares it as an automatic object in main (Applications/WindowExample/Main.cpp, Applications/VulkanExample/Main.cpp, Applications/EngineTest/TestMain.cpp). Nothing returns a pointer to it, and nothing has to.

Declaring it also publishes it. The first member is preEngineInit, a private nested struct whose constructor stores the address into the file-static engineInstance (Engine/Engine/Engine.cpp). Because a member declared first is constructed first, Engine::Get already resolves while the remaining members are being built — which is what lets MemoryManager's constructor raise SetMemoryManagerReady and Logger's raise SetLoggerReady before Initialize has been mentioned by anyone.

The lifecycle the header offers is four steps and no more: construct, Initialize(argc, argv, levels), then drive frames — either by polling the OS layer yourself, which is what the two windowed applications do, or with Run — and finally ShutDown before the object goes out of scope. There is no per-frame entry point in the public surface: no tick, no update, no frame function, and no wait-for-end. The engine owns no loop of its own to hand a frame to; Run is a task-system pump that returns when the task system is switched off, and the application's window loop is the frame loop.

Member declaration order is the shutdown order, and it is the only ordering the engine has. C++ destroys members in reverse declaration order, so an Engine dies application, resource manager, task system, logger, statistics, memory manager, log stream. That happens to be the right order — the task system joins its threads before the logger is destroyed, and the memory manager goes last — but nothing enforces it. Reordering two lines in the header reorders teardown, and no test in the repository covers the difference.
Letting an Engine die without calling ShutDown does not clean up; on the main thread thread it stops there forever. The destructor's whole body is CloseLog(). Everything else is a member destructor, and ~TaskSystem() calls JoinAndClear(), which on the thread that constructed the task system loops while (isRunning || pending main-thread tasks). isRunning is set true by BuildStreams() during Initialize and set false by exactly one function, TaskSystem::RequestShutDown() — called from one place, Engine::ShutDown(). Skip the call and that loop has no exit. See Core: TaskSystem for the join itself.

Template parameters

None — Engine is not a template, and it takes no allocator or platform policy parameter either.

The two remaining members are private and are named here because they are the reason the two lifecycle calls do what they do: void PostInitialize() is called at the end of Initialize, whatever levels ran, and void PreShutdown() is called part-way through ShutDown. Neither is callable by a caller, and neither has a subsystem to notify any more — MemoryManager::PostEngineInit() has an empty body and MemoryManager::PreEngineShutdown() only writes the pool configuration cache when PROFILE_ENABLED is set. Coverage carries the detail.

Non-member helper functions

None. Engine.h declares one thing at namespace scope besides the class — the forward declaration template <size_t, class> class InlineStringBuilder;, which keeps the header from pulling the builder's definition in — and defines nothing. The Engine::Get instance pointer is a file-static in Engine.cpp, not a global, so no other translation unit can read or redirect it. The two functions that make EInitLevel usable, operator| and HasFlag, belong to that entry: EInitLevel: non-member helpers.

Coverage

GapDetail
The instance pointer is never cleared PreEngineInit has no destructor, so nothing sets engineInstance back to null. During member destruction — which is when a log line, a task, or an allocator profile gets printed — Get still answers, and it answers with an object that is partly gone. After destruction it returns a dangling reference, and the null check inside Get cannot see the difference
PostInitialize and PreShutdown Private, and named rather than documented as API. What they do today is one log line each around a hook that has nothing behind it: MemoryManager::PostEngineInit() is an empty function; MemoryManager::PreEngineShutdown() saves the pool configuration only under PROFILE_ENABLED, and PreShutdown reports the memory configuration only under the same macro. Describing them as "where subsystems get started" would describe a call graph that does not exist
What each level initialises Deliberately not summarised on this page — Initialize owns that table, and the level set itself is documented on the EInitLevel page
Thread-safety of the lifecycle calls Engine.h attaches one comment to this class's lifecycle: Run "should call on main thread". Nothing is stated for Initialize or ShutDown, and neither is guarded by a mutex or a once flag. What the code supports is on each of those pages; what it does not guarantee is recorded there rather than inferred here
Calling Initialize twice No guard and no documented precondition. The TaskSystem branch rebuilds the stream table in place (streams.Swap(Array<TaskStream>(numHardwareThreads))) and TaskStream declares ~TaskStream() = default; over a std::thread member, so the consequences belong to Core: TaskStream rather than being asserted from here. Treat the call as once per object
Contracts that live in other modules Which pool each allocation comes from (Memory); what the drain task does and how it stops (Log); when a worker stream picks a task up (Core); what OS::Application::Initialize opens (OSAL). None of it restated
The logging design Log documents this class's half — the two config parameters, the mutex, the file. The line format, the drain task and the level vocabulary are in the Log module page and docs/LoggerGuide.md
Test-only use Engine/Test/UnitTestCollection.cpp calls ShutDown from inside the suite's own task, which is the mechanism that lets Run return in Applications/EngineTest/TestMain.cpp. Quoted as a call site on those two pages, not documented as a second lifecycle
Related defect, outside this page README.md's "Basic Engine Initialization" example ends with engine.WaitForEnd();. Engine.h declares no such member, and nothing under Engine/ or Applications/ names it, so that snippet cannot compile. The lifecycle the header does offer is on Run and ShutDown
