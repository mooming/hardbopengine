ShutDown

member of hbe::Engine Engine/Engine/Engine.h header comment: "Shut down engine. It'll shut down its task system." print the closing report and ask the task system to stop — which is the whole of what the class calls teardown

Signature

void ShutDown();

Function description

The body does four things, in this order:

  1. Prints the closing report, whatever was started. Through ConfigSystem::Get() it prints the interned-string table, then every registered configuration parameter, then statistics.Print() and statistics.PrintAllocatorProfiles(). None of this is gated on a level or on a ready flag: a run that started nothing still prints the tables, and the numbers it prints are whatever the counters reached. String and Config own what those reports contain.
  2. Calls the private PreShutdown(). That reports the logger's memory configuration and calls memoryManager.PreEngineShutdown() — and both of those bodies only do anything when PROFILE_ENABLED is set, so in a plain build the hook contributes two log lines.
  3. Logs Shutting down... under the Engine category, at Info level.
  4. Requests the task system stop, if one was ever started: if (isTaskSystemReady) { taskSystem.RequestShutDown(); }. Reading the ready flag rather than the level argument is the deliberate choice the header documents — a level you never passed cannot be torn down, so EInitLevel::TaskSystem absent means this step is skipped and nothing reaches into a task system with no streams. RequestShutDown() clears one atomic flag; that is the mechanism that lets Run return.
It stops nothing it does not name, and it names one thing. The drain task the Logger level started keeps running — Logger::StopTask is called from exactly one place in the engine, the signal handler, and not from here. No thread is joined (that is Run or ~TaskSystem), the OS application is not destroyed, the resource manager is not touched, neither log file is closed, and no ready flag is cleared. After this call the engine is alive and its accessors work; the only observable change is that the task system's running flag is now false.
Twice is not an error and not a no-op. There is no once-flag and no assertion, so a second call repeats step 1: the string table, the parameter list, the statistics and the allocator profiles print again, into the console and the log. The fourth step is safe to repeat — writing false to that atomic is idempotent — and step 2 is a hook that re-runs whatever PROFILE_ENABLED made it do. So the correct statement about this call is: re-running it is harmless to state and noisy in output.

From another thread the source supports the part that matters most and guarantees nothing about the rest. The shutdown request is an atomic store, so a worker thread can use this call to end Run — which is precisely how Engine/Test/UnitTestCollection.cpp finishes the suite, calling Engine::Get().ShutDown() as the last statement of the suite's own task. What is not synchronised is the report: the string-table print, the parameter print and the statistics print hold no lock, so two threads shutting down at once interleave their reports. The header attaches its thread comment to Run, not to this function, and no code enforces anything for this one.

Where it belongs in an application is last, after the caller's own subsystems are done — the engine owns no renderer and no window, so it cannot be first (Renderer, OSAL: Window). Both windowed examples follow that order.

Parameters

None.

Return value

void, with nothing to check afterwards. In particular it does not report whether a task system was asked to stop; the flag it consulted for that decision is readable directly through IsTaskSystemReady.

Examples

Ordering in a real application: renderer first, then the window, then the engine.

        renderer.Shutdown();
        window->Close();
        hengine.ShutDown();

        return 0;
}

From Applications/VulkanExample/Main.cpp.

The same call issued from the work itself, which is what makes it a shutdown request rather than a teardown:

        testEnv.Start();

        Engine::Get().ShutDown();

        return 1;
};

From Engine/Test/UnitTestCollection.cpp — the last statement of the test suite's task, run on a worker stream.

Omitting the call is not the same as deferring it. Both applications also contain failure paths that return before reaching their ShutDown() line — a window that could not be created, a renderer that could not initialise — and by then the task system is running. On those paths nothing clears the running flag, and the destructor's join waits for a flag that only this call clears. See the destructor for what happens in that window.
