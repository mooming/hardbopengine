Log

member of hbe::Engine Engine/Engine/Engine.h body guarded by ENGINE_LOG_ENABLED the engine module's own log line: two thresholds, one mutex, one file that is not hardbop.log

Signature

void Log(ELogLevel level, const TLogFunc& func);

Function description

Everything in the definition sits inside #if ENGINE_LOG_ENABLED, a macro BuildConfig defines to 1. Flip it and the function is an empty body: the parameters are still evaluated, the closure is still constructed by the caller, and no line is written anywhere. It is a different program, not a quieter one, and no runtime knob reaches it.

The path of one call, in order:

  1. Two configuration parameters are read — Log.Engine, the floor for writing to the file, and Log.Engine.Print, the floor for also echoing to standard output. Both are function-local static TAtomicConfigParam<uint8_t>, so they are registered on the first call and stay registered for the process, and both appear in the parameter dump ShutDown prints. Their defaults come from Config::EngineLogLevel and Config::EngineLogLevelPrint, which the config header pins with a static_assert so the console floor can never sit below the file floor.
  2. The severity test: if (levelAsValue < CPEngineLogLevel.Get()) return;. ELogLevel runs from Verbose at zero up to FatalError, so a lower configured value means more lines kept. The return happens before func is called, which is the entire reason the argument is a callable rather than a string.
  3. The stamp: elapsed time against statistics.GetStartTime() is decomposed into hours, minutes % 60, seconds % 60 and milliseconds % 1000, and IncEngineLogCount() is bumped. Because the start time is captured by the constructor, the prefix measures engine lifetime, not process lifetime.
  4. Under std::lock_guard lock(logLock): if the level also clears the print threshold, the stamp and the text are built into a std::stringstream and handed to ConsoleOutLn; then the stamp is written to logFile, func(logFile) writes the text, and an endl closes the line. The lock covers both sinks, so one call's console line and file line cannot be separated by another thread's pair.
The callable runs once per sink — up to twice per call. When a line clears both thresholds the body executes func(ss) for the console and func(logFile) for the file, on two different streams. A functor that builds text is fine; a functor with an observable side effect — a counter, a state change, anything that is not a pure function of the stream — runs twice and reports it twice. Write these closures as pure producers, which is what every caller in the tree does.
Two files, and this is the quieter one. Lines here go to logFile, the std::ofstream opened as "helowlevel.log" in the working directory, with the stamp written directly by this function. The category-attributed lines the rest of the engine writes go through Logger into ./hardbop.log, asynchronously, with the drain task (Log: Logger). Grepping one file will not show the other's content, and FlushLog is the only call that lands both.
An unopenable log file is an assert in Debug and silence in Release. The write is preceded by Assert(logFile.is_open()), and Assert is the configuration-limited form (Core: Debug): it aborts under __DEBUG__ and compiles away otherwise. In a Release build a stream whose open failed — a read-only working directory is enough — accepts the writes into its fail state and every engine line disappears without a message. There is no retry and no fallback sink.

Parameters

ParameterTypeRequirement
level ELogLevel Severity, compared as its numeric value against the two configuration parameters. Anything below Log.Engine is dropped untouched; anything at or above Log.Engine.Print additionally reaches standard output
func const TLogFunc& — std::function<void(std::ostream&)> Writes the line's text into whatever stream it is handed, without adding a trailing newline (this function appends one). Must be re-runnable: see the two-sink note above. It is invoked while logLock is held, so a functor that blocks blocks other threads' log calls too

Return value

void. Nothing distinguishes the four outcomes: filtered by level, written to the file only, written to file and console, or swallowed by a stream in a failed state.

Examples

The one call site that reaches this with an explicit level is the memory manager's own logging front door, which does its own filter first and then forwards: 

void MemoryManager::Log(ELogLevel level, TLogFunc func) const
{
#if MEMORY_LOGGING_ENABLED
        if (!IsLogEnabled(level))
        {
                return;
        }

        auto& engine = Engine::Get();
        engine.Log(level, func);
#endif // MEMORY_LOGGING_ENABLED
}

From Engine/Memory/MemoryManager.cpp.

From the outside, the form in use is LogError, which fixes the level and leaves the closure to the caller — quoted there. Both are the engine's own channel; for a line attributed to a subsystem, the log module's Logger::Get(category, level) is the path, as GetClassName shows.
