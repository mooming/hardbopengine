~Engine

member of hbe::Engine Engine/Engine/Engine.h one statement — CloseLog() — after which C++ destroys the subsystems in reverse declaration order

Signature

~Engine();

Function description

The destructor's own work is a single call: CloseLog(), which flushes the engine's log stream and leaves it open (that page covers why the name overstates it). Everything else about teardown is the language destroying members, and the engine relies on that entirely: there is no teardown list, no ordered shutdown of subsystems, and no check that ShutDown ever happened.

DestroyedMemberWhat actually runs
1st application The std::unique_ptr releases the OS::Application, unless Run already reset it. Whatever the OS layer closes at that point is its own contract (OSAL: Application)
2nd resourceManager Its defaulted destructor destroys the loaded items, and each item's Buffer runs its releaser — the one part of the resource module that genuinely works (Resource: Coverage)
3rd taskSystem JoinAndClear(): on the engine loop thread it waits for the running flag to clear and the main-thread queue to empty, then joins every worker stream and clears the array. See the hazard below
4th logger Clears the Logger singleton pointer, processes whatever is still buffered, then flushes and closes ./hardbop.log. Because it is destroyed after the task system, the drain task's thread is already joined by now — the ordering is right, and accidental
5th statistics Nothing to release. Any report it wants to make had to happen in ShutDown, which is the only caller of its print functions
6th memoryManager Deregisters the system allocator and clears its instance pointer — but only if it is still the instance. Allocations that outlive this point are the leak nobody reports
7th logFile, the mutexes, the flags, preEngineInit The stream closes for real here, in std::ofstream's own destructor. preEngineInit has no destructor at all, so the instance pointer is left pointing at this dying object
If ShutDown was never called, this destructor does not reach its seventh member. ~TaskSystem() calls JoinAndClear(), which on the engine loop thread — the thread that constructed the engine, which is the thread a local Engine is destroyed on — loops while (isRunning || mainThreadTaskQueue.HasPendingTasks()). Nothing clears isRunning except TaskSystem::RequestShutDown(), and in the engine that is called from exactly one place: ShutDown. So the sequence "construct, Initialize with the TaskSystem level, leave scope" stops here rather than completing, and it stops without a message. This is reachable through the repository's own error paths: Applications/WindowExample/Main.cpp returns early when window creation fails, and Applications/VulkanExample/Main.cpp returns early when the renderer fails to initialise, both after the task system was started and both before their ShutDown() line.
The instance pointer is live for all seven steps, which is what makes them able to report at all. Engine::Get() answers throughout, so a destructor that logs, prints allocator profiles or touches the config system still reaches the engine. Nothing sets the pointer to null afterwards, so the same call made by anything that outlives the Engine — a static object destroyed later in the same translation unit's teardown, a detached thread — gets a reference to memory that is no longer an Engine, and the non-null check inside Get passes.

Parameters

None.

Return value

A destructor returns nothing and reports nothing. It does not say whether the subsystems it destroyed were shut down in an orderly way, and there is no flag that would tell it: the ready flags are never cleared, so afterwards all five still read as they did while the object was alive.

Examples

No source calls this destructor. Every entry point relies on scope, which is the intended use — and it is why the ordering of the last two lines of main matters more than the closing brace: 

        window->Close();
        hengine.ShutDown();

        return 0;
}

From Applications/WindowExample/Main.cpp — ~Engine runs at the closing brace, after the request to stop the task system has already been made.

Read that pairing as the contract: ShutDown clears the flag, and the destructor's join then finds nothing to wait for and the seven destructions proceed. Add a return between them, as the failure paths above do, and the join has no exit.
