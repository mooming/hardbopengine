Run

member of hbe::Engine Engine/Engine/Engine.h header comment: "Should call on main thread." pump main-thread tasks until something switches the task system off, then join the workers and destroy the OS application

Signature

void Run();

Function description

Five statements, in this order, and none of them is a frame. FatalAssert(isTaskSystemReady, "Engine::Run needs EInitLevel::TaskSystem") first, so a call after an Initialize that skipped that level aborts in every build configuration. Then the pump: 

while (taskSystem.GetMainThreadTaskQueue().HasPendingTasks() || taskSystem.IsRunning())
{
        taskSystem.ProcessMainThreadTasks();
        std::this_thread::yield();
}

That is the whole loop. It runs tasks queued for the main thread and yields the processor otherwise — no clock tick, no renderer advance, no window polling, no sleep. It ends when the task system reports itself not running with an empty main-thread queue, which in practice means when somebody calls ShutDown or TaskSystem::RequestShutDown() from elsewhere. Run is therefore a wait, not a driver: it keeps the process alive and the main-thread lane moving while other threads do the work, and it cannot end itself.

What follows is teardown, and it is the reason the header says main thread. taskSystem.JoinAndClear() waits the queue out again with a one-millisecond sleep, joins each worker stream thread and clears the stream array. Then ProcessMainThreadTasks() once more, to run anything a joining thread posted on the way out. Finally, under the source's own comment // It may terminate the application immediately., the line application.reset();.

Run destroys the OS application on return. After it, GetApplication() is null and every window handle obtained earlier refers to an application object that no longer exists — while the Engine itself is still alive, its logs still open, and its other accessors still valid. Anything that outlives this call must not hold an OS::Application*. This is also why the two windowed applications never call it: they close the window first and let the destructor tear the rest down (the destructor for what that does and does not do).

The main-thread requirement has a mechanical reason rather than being a convention. TaskSystem recorded the thread that constructed it — the thread that ran the engine constructor — as the engine loop thread, and JoinAndClear only runs its wait-and-pump loop when it is called from that thread. Called from anywhere else it skips straight to joining the worker threads, so tasks on the main-thread lane are never processed by this call, and a task that only ever completes on the main thread leaves the join waiting for it.

A second call is quiet, not fatal. The streams are joined and the array cleared by the first return, so a second entry finds the running flag false, drains whatever is still queued for the main thread, joins nothing and returns; application.reset() on an already-null pointer does nothing. There is no guard and no state saying "already run" — a caller that wants a second pump gets a short one, not an error.

Parameters

None.

Return value

void, and no reason: Run cannot distinguish "the task system finished its work" from "somebody asked it to stop", because both are the same flag. Callers that care ask separately — Applications/EngineTest/TestMain.cpp reads the failure count out of TestEnv after Run returns, and exits non-zero from that rather than from anything Run reported (Test: TestEnv).

Examples

The one call site in the repository, where the exit condition is supplied by the work itself:

hbe::Engine hengine;
hengine.Initialize(argc, argv);
hbe::Test::RunTests();
hengine.Run();

// The suite runs as a task that shuts the engine down when it finishes, so the tallies
// are only complete once Run() returns.
const hbe::TestEnv& testEnv = hbe::TestEnv::GetEnv();
const unsigned int failures = testEnv.GetFailureCount();

From Applications/EngineTest/TestMain.cpp; the shutdown that ends the pump is issued by the suite's own task in Engine/Test/UnitTestCollection.cpp.

For contrast, the loop that the two windowed applications use instead — this is the frame loop, and Run is absent from it:

for (int i = 0; i < 10; ++i)
{
        app->PollEvents();
        window->PollEvents();

        std::this_thread::sleep_for(std::chrono::seconds(1));

        if (window->IsClosed())
        {
                break;
        }
}

window->Close();
hengine.ShutDown();

From Applications/WindowExample/Main.cpp.

Reading the two together is the point. Initialize plus a loop of your own is a complete application; Run is an optional way of waiting, and it needs someone else to call ShutDown for it to come back. Nothing in the header or in the source makes a member that waits for the end of the process — the name WaitForEnd that README.md's example calls does not exist in Engine.h, and ShutDown plus Run is what the class actually offers in its place.
