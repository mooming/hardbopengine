GetResourceManager

member of hbe::Engine Engine/Engine/Engine.h the accessor for the one subsystem the engine owns but never starts, never advances and never asks about

Signature

auto& GetResourceManager()
{
        return resourceManager;
}

Function description

A field read defined inline; auto& deduces to ResourceManager&. The member is constructed by the engine constructor as an empty manager and destroyed second, which releases whatever it holds. Between those two moments no engine code touches it: Initialize has no branch for it — EInitLevel declares no resource flag at all — ShutDown does not mention it, no frame hook calls it, and SetResourceManagerReady has no caller, so this reference is the only way the manager gets used by anyone.

What the manager itself can do is a separate matter, and smaller than its declaration suggests: PostUpdate(Engine&) is public, defined with an empty body and called by nobody, while its two loading entry points are declarations with no definition anywhere in the repository, so a call to either compiles and fails at link time. That is the resource module's subject and it is documented there — Resource: Coverage. What matters from this side is that the engine adds nothing to it.

There is no level to request, so there is no state to check either. Because nothing raises the flag, IsResourceManagerReady() answers false for the entire process, whether or not the manager holds anything. A caller that gates loading on that flag therefore never loads; a caller that ignores it and calls PostUpdate gets an empty function running. The honest position today is that resource loading in this engine happens through the buffer factories, not through this manager.

Parameters

None.

Return value

TypeWhat you get
ResourceManager& The member, mutable, never null, valid for the engine's lifetime. It is not constructed with the engine — ResourceManager() takes no arguments — so the only tie between the two is that they are constructed and destroyed together. Not [[nodiscard]]

Examples

Illustrative — no call site for this exists in the repository. Grepping Engine/ and Applications/ finds no caller of GetResourceManager at all: the manager is constructed, exposed and destroyed without being used.

hbe::Engine hengine;
hengine.Initialize(argc, argv);

// The one member of the manager that names the engine takes it as an argument,
// which is why reaching it through the engine is the natural shape.
auto& resources = hengine.GetResourceManager();
resources.PostUpdate(hengine);          // public, empty body, no caller in the tree

This snippet is complete because it is the only complete thing there is to do. The two members that would carry real work, RequestLoad and Load, are declared and never defined, so no snippet calling them can be offered here — such a program does not link. What actually produces bytes in this build is the buffer factory family in the resource module (Resource: module functions), which MemoryManager already uses for its own configuration cache.
