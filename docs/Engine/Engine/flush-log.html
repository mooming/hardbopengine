FlushLog

member of hbe::Engine Engine/Engine/Engine.h the one call that reaches both logging channels — the asynchronous Logger and the engine's own file

Signature

void FlushLog();

Function description

The definition is three statements:

void Engine::FlushLog()
{
        logger.Flush();

        if (!logFile.is_open())
        {
                return;
        }

        logFile.flush();
}

The order matters, and it is the order of the two channels' risk. Logger::Flush() is the asynchronous half: if the calling thread is the thread the drain task was given when the Logger level ran, it processes the buffer directly; otherwise it waits for the drain task to acknowledge, with a deadline, and drains inline if no task is running (Log: Logger explains the three cases). Only after that does this touch logFile, the Log destination.

No engine code calls this except one: FlushLogs() in Engine/Core/Debug.cpp, the free function that Assert and FatalAssert invoke immediately before they abort (Core: Debug). That is the reason this function exists — a crash report is worthless if the lines that explain it are still sitting in a buffer owned by a thread that is about to be stopped.

ShutDown does not call it. The closing report writes through Logger::Get(...).Out(...), which queues asynchronously, and then asks the task system to stop. Whether those last lines reach hardbop.log depends on the drain task running before ~Logger takes over, or on the signal handler's explicit stop-and-flush path. If a shutdown report is missing its tail, this is the gap, and FlushLog is the call that closes it.
On a foreign thread this blocks, and its deadline is silent. The wait belongs to Logger::Flush, not to this function; when the deadline passes without the drain task acknowledging, the call returns anyway and reports nothing. So "the logs were flushed" is not a fact this call establishes — at best it is a request with a bounded wait and an unreported timeout. Calling it from the drain task's own thread is the case that never waits, because the buffer is processed inline.

Parameters

None.

Return value

void. Nothing distinguishes "both channels drained" from "the file was not open" or "the wait expired". CloseLog is the narrower call when only the file matters.

Examples

The engine's only caller, and the reason it is there:

void FlushLogs()
{
        auto& engine = Engine::Get();
        engine.FlushLog();
}

From Engine/Core/Debug.cpp — called by Assert and FatalAssert before std::abort().

From application code the use is the same one an assertion makes: you are about to leave in a hurry, and the buffered lines have to be on disk first. Applications/VulkanExample/Main.cpp makes the same argument with the logger directly when renderer initialisation fails — Logger::Get().Flush();, with the comment "The logger is asynchronous: flush so its diagnostics survive this exit."
