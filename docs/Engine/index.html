Engine

namespace hbe Engine/Engine 2 headers, 1 source the singleton that owns every subsystem by value, and the level set that says which of them to start

Module description

Two declarations and one source file, and one of the two declarations is the one an application constructs. Engine holds the MemoryManager, SystemStatistics, Logger, TaskSystem and ResourceManager by value as members, so their construction order is its member declaration order and their destruction needs no bookkeeping — and, just as much, so their destruction order is that order reversed and the teardown sequence is a matter of where lines sit in a header. It registers itself as the process's one instance from its constructor's first member, which is why Engine::Get answers from inside the constructors of the subsystems it holds.

EInitLevel is the second header's contribution: which subsystems Initialize starts, so a headless tool can convert a file without ever touching a window server. Three bits, one dependency the function closes for you, and two static_asserts that keep None empty and All complete. Note what the level set cannot reach: the memory manager, the statistics object and the logger object are built by the constructor, and no level can omit them.

The lifecycle this module offers is four steps, and none of them is a frame. Construct, Initialize(argc, argv, levels), then drive the work — a loop of your own over the OS layer, as both windowed applications do, or Run, which pumps main-thread tasks and returns once the task system is switched off — and finally ShutDown before the object goes out of scope. There is no per-frame entry point in the class and no wait-for-end: see Coverage for the README example that claims one.

Module variables

None at namespace scope in a header. The subsystems are members of the instance rather than globals, and the instance pointer Engine::Get reads is a static Engine* file-scope variable in Engine.cpp — set by the constructor's first member, and cleared by nothing, so it is neither a reachable global nor a safe one to read after the object dies. The only other statics in the module are function-local: the class name inside GetClassName, and the two log-level configuration parameters read by Log.

Module functions

Two, both in EngineInitLevel.h, both constexpr and noexcept, and both needed because a scoped enumeration combines and tests nothing on its own. They are the whole callable surface of EInitLevel and are documented on that entry's pages; the singleton itself is reached through Engine::Get and the accessors beside it, not through a free function.

Coverage

GapDetail
Related defect, outside this page The "Basic Engine Initialization" example in README.md ends with engine.WaitForEnd();. Engine.h declares no such member, and nothing under Engine/ or Applications/ names it, so the snippet does not compile as written. It also omits ShutDown, which is not optional: without it the task system's running flag is never cleared and ~Engine stops in the task system's join. The lifecycle the header does offer is on Run and ShutDown.
What each readiness flag means Each of the five setters and getters has its own page, because the five are not five of anything: three are raised by subsystem constructors during the engine's own construction, one is raised by a level and gates a fatal assert, and one is never raised at all. The flag for the logger reports the object rather than the drain task, and the log header says so — see IsLoggerReady.
Thread-safety of the lifecycle calls The header comments one call, Run, with "Should call on main thread", and the reason is mechanical rather than stylistic. Nothing at all is stated or enforced for Initialize or ShutDown; neither holds a lock or a once flag, and neither can be called twice safely. Each page states what the code supports and where it is silent.
The instance pointer is never cleared PreEngineInit has no destructor and ~Engine does not unregister, so Get answers throughout member destruction — which is what lets teardown report at all — and keeps answering after the object is gone, where its non-null test cannot detect the problem.
The renderer Engine exposes no renderer accessor and no level starts one, so Renderer is reached directly through its own factory today; Applications/VulkanExample/Main.cpp constructs a concrete renderer and shuts it down before calling ShutDown. Whether the engine should own it is a design question with a real answer in docs/RendererDesign.html.
The resource manager is owned but never driven There is no level for it, SetResourceManagerReady has no caller, and nothing pumps it, so IsResourceManagerReady() is false for the whole process. The reasons and the consequences are in Resource: Coverage.
Contracts that belong to other modules What the drain task does and how it stops (Log); which pool each allocation draws from (Memory); when a stream runs a task and what JoinAndClear waits for (Core); what OS::Application::Initialize opens and what PollEvents drains (OSAL). The line format and level vocabulary of the logging path live in docs/LoggerGuide.md. None of it restated here.
Test-only lifecycle Engine/Test/UnitTestCollection.cpp calls ShutDown from inside the suite's own task, which is how Run ends in Applications/EngineTest/TestMain.cpp. Quoted as a call site on those pages rather than documented as a second lifecycle, and the runner itself is Test's subject.
