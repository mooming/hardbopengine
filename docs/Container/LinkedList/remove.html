Remove

member of hbe::LinkedList Engine/Container/LinkedList.h noexcept unlink and free the node that holds this element — found by address, never by value

Signature

Iterator Remove(TType& element) noexcept;

Function description

The parameter is a non-const lvalue reference to the element, and that is the contract rather than a style choice: Remove recovers the node by address with GetNodeOf(element), which is a reinterpret_cast from the element's address to the node's address. A temporary, or a foreign object that merely compares equal, cannot bind to the parameter — so the requirement that the element belongs to this list is enforced by the type before the precondition is ever tested.

The node is then unlinked and destroyed: Unlink takes the neighbour pointers, calls Delete<Node>(allocator, node) — which destroys the element and returns one node to the list's own allocator — and stitches the neighbours together. The head or tail pointer is updated first if the node was either end. The return value is an iterator to the node that followed the one removed, captured before the unlink, which is why removal inside a loop can be written correctly.

The precondition is an Assert, not a check, and Assert is compiled out of Release. Both Remove and GetNodeOf run Assert(ContainsElement(element)), where ContainsElement is the address scan against every node the list owns (Core: Debug documents the family: Assert is live in Debug and Dev, silent in Release). Feed it an element from a different list and Release builds skip the test entirely, then reinterpret that object's address as a node header and free memory through the wrong allocator. The type stops temporaries; only the assert stops a wrong-but-owned-looking reference.
The element must be the first member of its node, which is a layout assumption about TType. GetNodeOf assumes the element sits at offset zero of LinkedListNode<TType>, and it is — the struct declares value first. Pointer interconversion between a node and its first member is only guaranteed for standard-layout types, so a TType with a non-static data member in a base class or mixed access control makes that cast undefined before anything else runs. A plain data type is what this container expects; it will not tell you otherwise at compile time.

Parameters

ParameterTypeRequirement
element TType& A modifiable lvalue owned by this list: obtained from an iterator's operator*, from Find, or from the return of Add / AddFirst / AddLast / AddNext / AddPrevious. Not const, because a const element would not prove ownership — and note the consequence: an element reached through a const LinkedList cannot be removed without casting the const away, and there is no const-correct removal path here. Value equality is not sufficient: use FindAndRemove for that

Return value

TypeWhat you get
Iterator The next node, or end() — which is Iterator(nullptr) — if the removed element was the tail. The element inside the removed node has been destroyed, so the reference you passed in is dead on return, as is any other reference to it. Not [[nodiscard]], and ignoring it is what turns a removal loop into a walk through a freed pointer: operator++ on a list iterator follows node->next of whatever node it holds

Examples

Illustrative — no call site for this exists in the repository. Container/LinkedList.h is included by Engine/Test/UnitTestCollection.cpp and by nothing else in Engine/ or Applications/; the LinkedListTest fixture in Engine/Container/LinkedList.cpp exercises construction, iteration and allocator scoping but never calls Remove through a public path a caller could copy.

hbe::LinkedList<Component> components;

auto& added = components.AddLast(makeComponent);   // the list owns the node; this is its element

for (auto it = components.begin(); it != components.end(); )
{
        auto next = components.Remove(*it);      // returns the following node: loop-safe

        if (needsDestroying)
        {
                continue;                        // `it` is dead — advance only through `next`
        }

        ++it;
}

The pattern to keep is the one the return value exists for: take the next node from Remove rather than advancing an iterator that has just lost its node. And when what you have is a value rather than a reference into the list, FindAndRemove(value) does the search and the removal together and answers bool.
