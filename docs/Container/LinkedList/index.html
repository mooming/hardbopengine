LinkedList

Engine/Container/LinkedList.h namespace hbe template <typename TType, class TAllocator = DefaultAllocator<LinkedListNode<TType>>> final a doubly-linked list of nodes, each one allocated on its own through the container's allocator

Class description

LinkedList holds two pointers — head and tail — and nothing else. Every element lives in a LinkedListNode allocated one at a time through New<Node>(allocator, value) and released through Delete<Node>(allocator, node), so insertion and removal are pointer surgery with no element movement at all, and every element address is stable for the life of its node. There is no index, no random access and no size: position costs a walk.

Identity is the organising idea. Contains is overloaded — by value (operator== against each element) and by address (Contains(&element)) — and Remove, Find and GetNodeOf work on the address side of that pair, because the node is recovered from the element's own address. The module page described this class's removal as taking const TType&; the header takes TType&, and the difference is the mechanism that makes value-equality removal impossible by accident.

The list keeps no element count, so there is no Size() and length is never free. The members are head, tail and allocator — no counter is maintained anywhere, and IsEmpty() is the only constant-time query about how much is in it. Anything that needs a length pays an O(n) walk: Count(value) is the one accessor that reports a number, and it counts matches of a value, not entries. That absence is also why the leak described on move assignment is undetectable from the outside.
Guards here are Assert, not FatalAssert — the opposite of the contiguous containers. IsEmpty() asserts the head/tail consistency rule (head != nullptr || head == tail), and Remove and GetNodeOf assert element ownership the same way. Assert is live in Debug and Dev and compiled out of Release, where Array::operator[]'s FatalAssert still fires — so a Release build runs this class's precondition violations through without a word. See Core: Debug.

Template parameters

ParameterKindWhat it must satisfy
TType typename Copy-constructible or move-constructible according to the Add overload used — the node's own constructors take const TType& and TType&& and nothing else, so there is no emplace path here. Standard-layout in practice, because the node is recovered from the element's address by reinterpret_cast and that interconversion is only guaranteed for standard-layout types. operator== is needed only by the value-based Contains, Find, Count and FindAndRemove; the address-based operations require no comparison at all
TAllocator class, defaults to DefaultAllocator<LinkedListNode<TType>> A node allocator, not an element allocator — the node carries the two links as well as the value, so a pool sized for the element alone is the wrong pool. The free helpers in Memory/Memory.h that do the work impose three requirements: it must expose value_type (a static_assert on sizeof(value_type) == sizeof(Node) is in the body of both New and Delete), and it must accept a count of one — allocate(1) and deallocate(ptr, 1), one allocation per node. Never exchanged by a move, so the destination of a move frees nodes it did not allocate

Non-member helper functions

No free functions. The header does declare one name at namespace scope, and this class is its only user: 

template<typename TType>
struct LinkedListNode final
{
        using This = LinkedListNode;

        TType value;                    // first member — the address GetNodeOf casts from
        LinkedListNode* previous;
        LinkedListNode* next;

        explicit LinkedListNode(const TType& value) noexcept;
        explicit LinkedListNode(TType&& value) noexcept;

        bool IsHead() const noexcept;   // previous == nullptr
        bool IsTail() const noexcept;   // next == nullptr
};

It is public, its links are public, and it carries operator* in both const flavours plus operator!= against another node — enough to be iterated over directly. Because the allocator's value_type must be the node and not the element, this type is part of what a caller writes when naming a pool: DefaultAllocator<LinkedListNode<TType>>. It is documented here rather than as a separate entry of the module page, and the module page's Coverage records that choice — as does HashMap's page for its state enum.

No thread safety anywhere in the class Links are plain pointers with no atomic operation, so concurrent Add and Remove corrupt the chain. Nothing here documents an intended single-thread rule either — it is an absence, not a guarantee
