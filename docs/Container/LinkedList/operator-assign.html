operator=

member of hbe::LinkedList Engine/Container/LinkedList.h 2 overloads, one deleted two pointer assignments that neither free what was there nor protect against self-assignment

Signature

LinkedList& operator=(LinkedList&& rhs) noexcept;
LinkedList& operator=(const LinkedList&) = delete;

Function description

The body saves rhs.head and rhs.tail, nulls both in rhs, and writes the saved values into this->head and this->tail. Five assignments, no loop, no allocation, no deallocation. The copy overload is deleted, in line with the rest of the module.

The destination's nodes are not destroyed and not freed — they are leaked. No Clear runs first, so every node the destination already owned becomes unreachable at the moment its head is overwritten: the destructor of the destination will only walk the new chain, and nothing else holds the old one. A node is a real allocation through the list's allocator (New<Node>(allocator, value)), so this is a leak proportional to the destination's length, and an Assert-free one — nothing anywhere in this class notices. Assigning into a list that has never been cleared is the only safe use of this operator; otherwise call Clear() yourself immediately before it.
Self-move-assignment empties the list and leaks all of it. There is no this != &rhs guard — unlike Vector, which has one for exactly this reason — so list = std::move(list); sets head = nullptr; tail = nullptr; after having "saved" its own pointers into itself. The result is an empty list, an entire chain of nodes nobody can reach, and no diagnostic. Any generic code that moves a container into itself — a shuffle, a rotate, a "move if you must" branch that does not test first — reaches this in one line.
The allocator is left behind, as it is in every move here. The constructor form LinkedList(LinkedList&& rhs) also takes only head and tail, so the destination default-constructs its TAllocator and later frees nodes that a different allocator instance allocated — a different pool when the allocator is one, which is exactly how the fixture configures it with PoolAllocator and AllocatorScope. See Memory: allocators.

Parameters

ParameterTypeRequirement
rhs LinkedList&& The list to take the chain from. After the call it is empty — IsEmpty() is true — and it holds its own TAllocator. A const list cannot be moved from, and cannot be copied either, so a const list is read-only and lifetime-bound with no way to hand its contents over
(deleted overload) const LinkedList& Copy assignment removed, matching the deleted copy constructor. There is no clone path on this class at all

Return value

TypeWhat you get
LinkedList& Reference to *this, now owning the source's chain. Nothing is reported about the nodes it dropped — there is no counter, no warning, and no way to detect afterwards that a leak happened, because the list keeps no count of its own length

Examples

Illustrative — no call site for this exists in the repository; see the note on Remove.

hbe::LinkedList<Component> destination;
Fill(destination);                       // 400 nodes, each one an allocation

destination.Clear();                       // required: release what you already own first
destination = std::move(source);            // now safe: destination had nothing left to lose

hbe::LinkedList<Component> other;
Fill(other);
destination = std::move(other);              // leaks 400 nodes — the old chain is unreachable

self = std::move(self);                     // empties `self` and leaks every node in it

Read the last two lines as the two things to avoid rather than as usage. The constructor form is the safer transfer: LinkedList<Component> taken(std::move(other)); has no destination contents to clobber, and the list you mean to replace should be destroyed and rebuilt rather than assigned over.
