Remove

member of hbe::HashMap Engine/Container/HashMap.h destroys one entry and leaves a tombstone where it was — the count drops, the capacity does not

Signature

bool Remove(const TKey& key);

Function description

Probes for the key. If no occupied slot compares equal, returns false and changes nothing. Otherwise it destroys the Pair in place with entries[idx].~Pair(), writes EHashEntryState::Tombstone into that slot's state byte, decrements count, increments tombstoneCount, and returns true.

The tombstone is not tidiness, it is correctness. With linear probing, a key inserted after a collision sits past the slot it hashed to; blanking that slot to Empty would end the probe chain that later keys depend on and make them unfindable. Marking it Tombstone keeps the chain walkable while excluding the slot from lookups — FindSlot skips tombstones and stops only at Empty.

Nothing else happens. The buffer stays allocated, the capacity is unchanged, and the destroyed object's memory is not reused until a later Insert lands on that exact slot — which is the only thing that decrements tombstoneCount short of a rehash or a Clear.

Deleting and re-adding in a loop grows this map forever. The load-factor test is count + tombstoneCount >= cap * MaxLoadFactor, so tombstones are charged exactly like live entries. A map that inserts n keys, removes them all, and inserts n more has spent its tombstones and will rehash into a larger table even though Size() never exceeded n. Capacity never shrinks — Reserve refuses anything at or below the current capacity — so that growth is permanent for the life of the map. A churn workload is a case for calling Clear between passes, which zeroes both counters while keeping the table, rather than removing entries one by one.
Iterators: one dies loudly, the rest survive. An iterator that pointed at the removed slot fails its IsValidSlot check in operator* and hits a FatalAssert when dereferenced — a stop, not a read of garbage — and comparing it still works, so it != map.end() tells you nothing about whether it is safe to dereference. Every other iterator is untouched: nothing is rehashed and open addressing moves no slots, so the remaining elements stay at the same index. That is a stronger guarantee than Vector can give, and it costs the tombstone accounting above.

Parameters

ParameterTypeRequirement
key const TKey& Hashable and comparable under this map's THash and TKeyEqual, and still hashing to the same value it hashed to when inserted. There is no removal by iterator and no removal by predicate: to drop entries selectively you collect the keys first, because erasing while iterating would leave the iterator over the dead slot

Return value

TypeWhat you get
bool true if an entry was destroyed, false if the key was not present — which is also the answer when the map is empty, so a removal that never finds anything is indistinguishable from a bug in the key unless you check. Not [[nodiscard]]. Size is decremented only on true

Examples

Illustrative — no call site for this exists in the repository; see the note on Insert.

if (textures.Remove(path))
{
        // the entry is gone: Contains(path) is now false, Find(path) == end()
}

const auto doomed = 4;
for (auto it = textures.begin(); it != textures.end(); )
{
        auto next = it;
        ++next;                              // advance before the slot dies …

        if (it->value.refCount == doomed)
        {
                textures.Remove(it->key);         // … `it` is dead from here on
        }

        it = next;                            // fine: every other slot kept its index
}

The copy-then-advance is not defensive style, it is the shape the contract forces: after Remove the slot behind it is a tombstone, and dereferencing it asserts.
