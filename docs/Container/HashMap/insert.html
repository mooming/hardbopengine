Insert

member of hbe::HashMap Engine/Container/HashMap.h 3 overloads add a key that is not there yet — a key that is there is left exactly as it was, and told so

Signature

bool Insert(const TKey& key, const TValue& value);
bool Insert(const TKey& key, TValue&& value);
bool Insert(TKey&& key, TValue&& value);

Function description

All three follow the same two steps. A probe (hash(key) & (cap - 1), then linear probing over (idx + probe) & (cap - 1)) looks for the key; if an occupied slot compares equal under keyEqual, the insert is abandoned and the answer is false. Otherwise InsertInternal runs, and the value is stored into the slot it found.

There is no insert-or-overload here. A key already in the map keeps its value; the argument you passed is neither copied, moved nor assigned. That makes the returned bool load-bearing rather than courtesy: it is the only signal that your value was discarded. For the "set it either way" behaviour the map offers operator[], which default-constructs a value for a new key and hands back a reference you then assign — two steps instead of one, and the only way to overwrite.

What the slot receives is Pair{key, TValue{}} — the key copied or moved as the overload chose, and the value default-constructed — after which the caller assigns the argument into entries[slot].value. Two consequences follow that the signature does not show: TValue must be default-constructible, and it must be assignable, because the value never reaches the slot through a constructor argument. A value type with a deleted default constructor or a deleted assignment operator cannot be held by this map.

An insert that crosses the load factor rehashes, and a rehash invalidates every iterator, pointer and reference in the map. The trigger is count + tombstoneCount >= cap * MaxLoadFactor (0.7), or an empty table, checked before the probe — so the growth is not predictable from Size() alone, because deleted keys still count. Values survive the rehash by moving into new slots at new indices, and the old buffer is returned to the allocator. If a reference into the map has to survive, reserve the table first with Reserve so that no insert can trigger one; an insert that does not rehash moves nothing, because open addressing leaves every other slot where it was.
The growth path does not test the allocation. Rehash carves the new buffer straight out of allocator.allocate(...)'s return value and starts writing state bytes into it, so a failed allocation is a write through a null pointer rather than a refused insert — there is no false on that path, and the bool you get back describes the key, never the memory. See Memory: allocators for what a failure means for the pool you chose.

Parameters

ParameterTypeRequirement
key const TKey& (first two overloads) Copy-constructible TKey. Must satisfy the pair the defaults assume: std::hash<TKey> produces a value and std::equal_to<TKey> compares one, or you supplied your own THash and TKeyEqual. A key whose hash changes while it is in the map becomes unreachable
key TKey&& (third overload) Move-constructible TKey. Note that both arguments must be rvalues to reach this overload — Insert(std::move(k), v) with an lvalue value selects the second one instead, which copies nothing and moves nothing
value const TValue& / TValue&& Default-constructible, and assignable from the argument passed. Only assigned when the key was actually inserted; a duplicate key discards it. It is not touched when the map rehashes to make room, because the rehash happens before the assignment

Return value

TypeWhat you get
bool true when a new slot was taken, false when the key was already present. Not [[nodiscard]], so map.Insert(k, v); compiles and silently throws away the answer — which is fine for a set-like use and is exactly how the "last writer wins" bug gets written. The function cannot report an allocation failure; that case never returns at all

Examples

Illustrative — no call site for this exists in the repository. Container/HashMap.h is included by Engine/Test/UnitTestCollection.cpp and by nothing else in Engine/ or Applications/; the module's own HashMapTest fixture in Engine/Container/HashMap.cpp is the only code that exercises it.

hbe::HashMap<StaticStringID, TextureHandle> textures;
textures.Reserve(256);                             // 256 slots: 179 entries fit before any growth

if (!textures.Insert(path, handle))
{
        // path was already there — `handle` was discarded, the old one stands.
        // To overwrite instead: textures[path] = handle;
}

hbe::HashMap<int, MeshHandle> meshes;
meshes.Insert(id, BuildMesh(desc));               // const key, rvalue value: second overload
auto slot = meshes.Find(id);                     // valid only until an insert rehashes
if (slot != meshes.end())
{
        slot->value.lodBias = 0.5f;                  // Pair& through the iterator: key and value
}

The Reserve at the top is not a micro-optimisation here: it is what makes the iterator below meaningful, because without it the insert that crosses 70 per cent of the table moves slot out from under the caller.
