Reserve

member of hbe::HashMap Engine/Container/HashMap.h not noexcept force the table to a size before inserting — which also wipes every tombstone and moves every entry

Signature

void Reserve(TIndex newCapacity);

Function description

Returns immediately when newCapacity <= cap. Otherwise it takes newCap = max(MinCapacity, cap) and doubles it until it reaches newCapacity, then rehashes into a table of that size: one allocation of sizeof(Pair) * newCap + sizeof(EHashEntryState) * newCap bytes, all state bytes written as Empty, every occupied pair moved into the new table by move, the old pairs destroyed, and the old byte buffer returned to the allocator.

The capacity you get is never the capacity you asked for. Every slot index in this map is computed as hash & (cap - 1), so cap must be a power of two — which is what the doubling loop is for. The result is the smallest power of two that is at least max(MinCapacity, cap) and at least newCapacity. MinCapacity is 4, so a fresh map cannot be given a three-slot table, and asking for 1000 on an empty map gets you 1024.

Because the rehash writes a brand-new state array, it is also the only routine that forgets tombstones: the new tombstoneCount starts at zero, and the dead slots of the old table are simply not carried over. Remove explains why that matters for a churn workload — and the asymmetry to notice is that a reserve large enough to trigger a rehash clears the tombstone debt, while a reserve that is refused (newCapacity <= cap) leaves it in place.

It cannot shrink, so it cannot release memory. The early return covers every request at or below the current capacity, and there is no other path out of the allocation: a map's buffer is returned only by its destructor. Combined with tombstones counting toward the load factor, the practical consequence is that a map which once held a large working set holds that table for life. A map that has finished with a workload is a map to destroy and rebuild, not a map to empty.
All iterators, pointers and references die, and a failed allocation is not reported. Both keys and values are moved into the new buffer, so every address inside the map changes — and unlike Vector::Reserve, which at least asserts when the allocator returns null, Rehash tests nothing: the state bytes are written through the returned pointer before anything looks at it. This member is not marked noexcept either, which does not help: a throw from a key or value move constructor inside a noexcept rehash terminates anyway.

Parameters

ParameterTypeRequirement
newCapacity TIndex (int) Entries you intend to hold — a slot count, not a byte count, even though this map's default allocator is DefaultAllocator<uint8_t> and the allocation it performs is in bytes: the conversion from slots to bytes happens inside Rehash, never at the call. The number is a floor, not a target; it is rounded up to a power of two, and a request of MinCapacity or less on an empty map still builds a four-slot table

Return value

void. Read Capacity afterwards for the table you actually got, and remember that Size() stays exactly as it was — this is a rehash of the contents, not a change to them. A rehash is also what an Insert can trigger by itself, so reserving enough up front is the only way to keep the insert path free of reallocation.

Examples

Illustrative — no call site for this exists in the repository; see the note on Insert.

hbe::HashMap<StaticStringID, TextureHandle> textures;
textures.Reserve(1000);
textures.Capacity();                        // 1024 — the next power of two, and not the number asked for
textures.Reserve(8);                         // refused: 8 is below the capacity, nothing happens

for (const auto& entry : manifest)
{
        textures.Insert(entry.id, entry.handle);   // 1000 inserts here would still rehash — see below
}

The last comment is the reason for the whole call, and the arithmetic has to include the load factor rather than the capacity: MaxLoadFactor is 0.7, so a 1024-slot table grows as soon as 717 slots are used, counting tombstones. Reserving for 1000 entries means reserving for 1000 / 0.7 slots — Reserve(1500) takes the capacity to 2048 and the inserts stop reallocating. A reserve that only covers the entry count is a reserve that pays for one more rehash later.
