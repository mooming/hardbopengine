PushRange

member of hbe::BoundedPriorityQueue Engine/Container/BoundedPriorityQueue.h 2 template overloads noexcept push one item after another — a loop written once, with every property of Push intact

Signature

template <typename Iterator>
void PushRange(Iterator begin, Iterator end) noexcept;

template <typename TContainer>
void PushRange(const TContainer& container) noexcept;

Function description

The container overload is one line — PushRange(container.begin(), container.end()); — and the iterator overload is one loop: for (auto it = begin; it != end; ++it) Push(*it);. There is no batch allocation, no size hint, no pre-growth of buckets: each element goes through the ordinary Push, which means each one is routed by its own priority field, each one may create its bucket, and the sequence may land in a hundred different buckets in an order that has nothing to do with the input order. What the caller saves is the spelling, not the work.

Because the routing is per item, the queue does not preserve the range's order at the far end: two items from the same range with the same priority do keep their relative order (the bucket is a back-appending deque), but two items with different priorities are separated into different levels and the more urgent one is drained first regardless of where it sat in the input.

Pushing a range of the queue's own elements is a deadlock of aliases, not of locks. Neither overload copies the source first. Feeding a queue from a live view of itself — from a bucket reference you are holding, or from any container that a Remove in the same expression may still be rebuilding — means iterating storage while the push moves elements into it, and a bucket that grows relocates the very elements being walked. The real call site below is careful in exactly this way: it first completes a Remove sweep, then re-adds from a separate holding container, then clears that container.
Requirements are on the iterator pair, not on a container concept. The pair form needs ++it, it != end and a *it that binds to Push — so an input iterator over a temporary is fine, and the element type, not the iterator category, is what decides whether the copy or the move Push is selected. Since *it on a const container yields a const reference, the container overload always takes the copy path: a range push moves nothing, it copies everything. Elements too expensive to copy have to be pushed one at a time with std::move.

Parameters

ParameterTypeRequirement
begin, end Iterator (deduced) A half-open range, incrementable and comparable with !=, whose *it is convertible to T. Both are deduced independently, so a mismatched pair — the common (begin, begin) typo — compiles and pushes nothing
container const TContainer& (deduced) Anything with const begin() and end() returning a comparable pair: an Vector, a HVector, a Map, a plain array-based type. A LinkedList qualifies too — its iterator's operator++ returns void, which is still a valid increment expression in a for statement. What does not qualify is a range whose *it is not readable, since Push needs a value: an output iterator fails to compile

Return value

void, with no count of what went in. If the range is empty the call does nothing at all — no bucket is created, no allocation happens. Size() afterwards reflects however many items arrived, and nothing here distinguishes "the range was empty" from "the range had fifty items in forty levels".

Examples

Real call site — Engine/Core/TaskStream.cpp, the per-iteration sweep of the worker loop, quoted with its surrounding lock scope and its comment.

HVector<RangedTask> readdingPriority;            // line 197: a holding container, not the queue

for (; likely(taskSys.IsRunning()); ++loopCount)
{
        {
                std::unique_lock lock(queueLock);

                // A task that finished elsewhere is released from its lane and put back on that same lane, so the
                // sweep and the re-add are per lane and no task changes lane on the way.
                priorityQueue.Remove([](const RangedTask& task) { return task.HasFinished(); });   // 210
                priorityQueue.PushRange(readdingPriority);                                        // 211
                readdingPriority.clear();                                                // 212

                // …
        }
}

Read the three lines as one transaction: drop the items that no longer belong, re-add the ones whose priority changed, then release the holding container. The order is load-bearing — Remove rotates every bucket it touches before PushRange starts appending to it, and the source is a separate container rather than a view into the queue.
