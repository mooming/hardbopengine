Remove

member of hbe::BoundedPriorityQueue Engine/Container/BoundedPriorityQueue.h noexcept drop every item a predicate claims — by rotating every bucket, whatever the answer is

Signature

using TPredicate = bool (*)(const T&);

std::size_t Remove(TPredicate predicate) noexcept;

Function description

A null predicate returns 0 at once. Otherwise every priority from 0 to MaxPriority - 1 is visited; an unengaged bucket is skipped, and an engaged one is rotate-filtered. The bucket's length is captured first, then that many times: take the front item out by move, drop it if the predicate claims it, otherwise append it to the back. After a full rotation the survivors are in the same arrival order they started in, the claimed ones are gone, and the bucket is released if it drained. Finally totalSize is reduced by the count and highestBucket is walked down to the next level that still holds anything.

TPredicate is a function pointer, so a capturing lambda does not compile. bool (*)(const T&) accepts a function, a captureless lambda and a static member function — nothing else. [&](const T& item) { return item.id == wanted; } is a hard error at the call, and the diagnostic points at the call site rather than at this typedef. The workarounds are a captureless lambda plus a lookup the lambda itself performs, or a free function taking the state through a global — neither is recorded in the header, so this constraint tends to be discovered by the compiler.
The argument your predicate receives is not in the queue any more. Each item is moved out of the bucket and the slot is destroyed (PopFront) before the predicate is consulted, so the reference is to a local in this function's frame. Two consequences: writing through it changes nothing the queue can see, and comparing its address against a pointer you took earlier from Top() or a previous traversal will not match — Remove cannot be used to locate an element by identity.
The cost is everything in the queue, not everything that matched. Every element of every engaged bucket is moved out and, if it survives, moved back in. So a queue of ten thousand items with one finished task at the bottom still pays ten thousand move-and-destroy pairs, and every element address in the queue is invalidated even when Remove returns 0. Any pointer, reference or iterator obtained before the call is dead after it. The engine's own comment about this price is at Engine/Core/TaskStream.cpp:222: the surrounding sweep "is the same O(n)-per-loop price BoundedPriorityQueue::Remove already pays."

Parameters

ParameterTypeRequirement
predicate TPredicate — bool (*)(const T&) nullptr is legal and means "remove nothing". Must not throw in practice — the function is noexcept. Must not call back into the queue: it runs while the rotation holds a bucket mid-flight, so a nested Push, Pop or Remove from inside it corrupts the rotation. Must be captureless

Return value

TypeWhat you get
std::size_t How many items were dropped — 0 when nothing matched or the predicate was null. Not [[nodiscard]]; the engine's real caller discards it. Size() afterwards is the previous value minus this one, and buckets that drained have already released their buffers

Examples

Real call site — Engine/Core/TaskStream.cpp:210, inside the worker loop's lock scope. The lambda is captureless precisely because TPredicate demands it, and it reads the state out of the item.

// Engine/Core/TaskStream.cpp
priorityQueue.Remove([](const RangedTask& task) { return task.HasFinished(); });

// This is also where the header's type requirement on T comes from: HasFinished() is not called
// by BoundedPriorityQueue, it is called by the predicates its callers write.

The same sweep appears in the task system's documentation as the maintenance pass of the stream. What it buys is that a finished task is never handed out again; what it costs is a full rotation of every populated level, every iteration of the loop, which is why the surrounding code runs it once per wake rather than per task.
