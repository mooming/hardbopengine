PushBack

member of hbe::Deque Engine/Container/Deque.h 2 overloads noexcept construct at the tail cursor, advance it with the wrap mask, count one more

Signature

void PushBack(const TElement& value) noexcept;
void PushBack(TElement&& value) noexcept;

Function description

If the deque is full — count == Capacity(), where Capacity() is mask + 1 — the private Grow runs first and calls Reserve with max(DefaultCapacity, Capacity() * 2), which moves every live element into a bigger buffer and unwraps them in the process. Then the element is constructed at data[tail], tail advances through WrapIndex(tail + 1), and count is incremented. Constant time in the ordinary case.

Both ends cost the same here: unlike Vector::PushBack, appending at the front is not a shift of everything, and unlike Array nothing is full-size-allocated. That symmetry is the reason this container is the one the task system queues with.

There are two overloads, one taking the value by const reference and one by rvalue reference, chosen by the argument exactly as you would expect. Both return void, so reach the appended element through Back() or operator[] with Size() - 1.

A push that triggers a growth moves every element and unwraps the ring. All pointers, references and iterators into the deque are invalidated — the same rule the other containers carry, with the extra twist that after a growth the elements sit at different slot numbers than they did before (a growth rewrites them contiguously from index 0). And the allocation result is not tested: Reserve writes through it, so a failed growth is a crash rather than a refusal.
Nothing in a deque serialises access. The two overloads mutate tail and count with no atomic operation and no lock, so a queue shared between threads has to be guarded by its owner. Every call site in the engine does exactly that, and the example below shows the guard as part of the pattern rather than as decoration.

Parameters

ParameterTypeRequirement
value const TElement& Copy-constructible TElement; the copy is made into the ring's buffer
value TElement&& Move-constructible TElement. If the argument refers into this same deque and the push grows, the source is destroyed by the growth before the move reads it — the same aliasing trap as EmplaceBack

Return value

void on both overloads, with no signal that a growth happened. A caller that cares compares Capacity() before and after; a caller that cares about element addresses should have reserved first.

Examples

The engine's real use, from the task stream's FIFO admission path:

bool TaskStream::EnqueueFifo(const RangedTask& task) noexcept
{
        // ... capacity and admission checks ...

        std::scoped_lock<std::mutex> lock(queueLock);
        fifoQueue.PushBack(task);               // Deque<RangedTask>, copied in under the lock
        cv.notify_one();
        return true;
}

Condensed from Engine/Core/TaskStream.cpp. fifoQueue is declared as Deque<RangedTask> fifoQueue; in Engine/Core/TaskStream.h, next to BoundedPriorityQueue<RangedTask> priorityQueue;, and the mutex guards both.

The copy is the const overload at work: task is a const reference the caller keeps, so the deque builds its own element. A producer that can give up its task would pass std::move(task) and take the rvalue overload instead.
