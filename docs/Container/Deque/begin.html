begin

member of hbe::Deque Engine/Container/Deque.h 2 overloads address of the oldest element — correct on its own, and only paired with end until the ring wraps

Signature

Iterator begin() noexcept;              // TElement*
ConstIterator begin() const noexcept;   // const TElement*

Function description

Returns &data[head] — the slot holding the oldest live element. It is the address of a real element whenever the deque is non-empty, and it is the right answer by itself: *begin() is Front(), and the slot is the one PopFront will destroy.

Nothing wraps inside this function, and that is not an oversight on its own — a pointer to one element needs no modulus. The problem is only what it means as the start of a range, because end() is computed as &data[head + count] with the same absence of a modulus.

begin() to end() is not a valid range once the ring has wrapped, and range-for uses it. Every other member of this class resolves slot numbers through the private WrapIndex(index) { return index & mask; } — operator[], Front, Back, DestroyAll, Reserve's copy loop — but the range pair does not. As soon as head + count exceeds the capacity, end() points past the end of the allocation and the range is longer than the element count. Two calls demonstrate it on a fresh deque, whose capacity is 4: PushFront(1) then PushBack(2) leaves the elements in slots 3 and 0 with head = 3, tail = 1 and count = 2, so begin() is &data[3] and end() is &data[5]. The walk yields the element in slot 3, then reads slot 4 — outside a buffer whose indices run 0 to 3 — and never reaches the element that wrapped around to slot 0. Reading a wrapped deque with a range-for therefore touches memory the deque never allocated, and writing through it corrupts whatever is next to it.

The consequence in practice: iterate a deque with an index — for (auto i = 0; i < d.Size(); ++i) Use(d[i]); — which routes every access through WrapIndex and is correct in every state. Engine/Core/TaskStream.cpp does exactly this, and never uses a range-for over fifoQueue. The wrap state cannot be tested from outside either: head and mask are private, and Size() plus Capacity() are not enough to tell whether head + count has run off the end.

Parameters

None.

Return value

TypeWhat you get
TElement* / const TElement* The oldest element's address — data + head, and nullptr on a default-constructed or cleared deque that never allocated, where head is 0 and the expression forms the address of a null base. Valid until a growth, a Reserve that moves the buffer, a Clear or destruction. A non-growing push at either end leaves it pointing at the same slot, which may no longer hold the element it used to

Examples

The correct shape, and the one the engine uses — index arithmetic through operator[]:

// Where the whole queue has to be inspected, this is the form that stays correct across a wrap:
for (hbe::Deque<RangedTask>::TIndex i = 0; i < fifoQueue.Size(); ++i)
{
        Inspect(fifoQueue[i]);              // WrapIndex inside, every time
}

Index-walk form; the surrounding drain loop is Engine/Core/TaskStream.cpp's fifoQueue.Front() / fifoQueue.PopFront() pair. Nothing in Engine/ range-iterates a deque.

What the pair is safe for:

Illustrative — no call site for this exists in the repository.

if (queue.Size() > 0)
{
        TakeFirst(queue.begin(), queue.Size());   // a single pointer, not a range: fine
}

for (auto& item : queue)   // do not: begin/end do not wrap — see the hazard above
{
        Use(item);
}
