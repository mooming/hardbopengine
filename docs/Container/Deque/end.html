end

member of hbe::Deque Engine/Container/Deque.h 2 overloads noexcept head + count, unmasked — the half of the range that breaks first

Signature

Iterator end() noexcept;              // TElement*
ConstIterator end() const noexcept;   // const TElement*

Function description

Returns &data[head + count]. In a ring buffer whose slot numbers are produced by index & mask everywhere else in the class, this expression is deliberately unmasked, and the consequence is that it names a slot number that may not exist.

When the live elements sit contiguously — head + count <= Capacity(), which is the state after construction, after a Reserve, or after any run of pushes that never wrapped — this is the ordinary one-past-the-end pointer, begin() to end() walks exactly the elements, and range-for is as correct here as it is on Vector.

Once the ring wraps, this pointer is past the allocation and the range is longer than the container. PushFront moves head backwards through the mask (WrapIndex(head - 1)), so on a four-slot deque PushFront(1) followed by PushBack(2) leaves head at 3 with count 2 and this function returns &data[5] — two slots beyond a buffer whose one-past-the-end is &data[4]. A loop written against the pair then reads slot 4, which belongs to the allocator, and a loop that writes writes there. Compare Array::end, whose data + length is always exactly one past a buffer of that many elements.

It is worth being precise about what is and is not wrong here, because the failure looks like a simple off-by-one and invites a simple wrong fix. end() is not "one short": wrapping it to WrapIndex(head + count) would make it equal to an interior slot, and a pointer loop for (; it != d.end(); ++it) would then run off the other end instead. The range protocol and a circular buffer do not meet at the pointer level, so the correct answer is not to use the range on this container: use Size() with operator[], or drain with Front() and PopFront() the way Engine/Core/TaskStream.cpp does.

Parameters

None.

Return value

TypeWhat you get
TElement* / const TElement* A pointer one slot past the newest element in linear index space, never dereferenced by the range protocol itself. On a deque that never allocated, data is null and the value is null, equal to begin() — an honest empty range. On one that has wrapped, the value is not a valid address at all, which is the case the box above is about

Examples

The two states, side by side:

Illustrative — no call site for this exists in the repository.

hbe::Deque<int> a;                  // capacity 4, head 0
a.PushBack(1); a.PushBack(2);         // head 0, count 2 → begin=&data[0], end=&data[2]
for (auto v : a) { Use(v); }        // fine: 1 then 2

hbe::Deque<int> b;
b.PushFront(1); b.PushBack(2);      // elements land in slots 3 and 0; head 3, count 2
                                       // → begin=&data[3], end=&data[5]
for (auto v : b) { Use(v); }        // wrong: reads data[3] then data[4], never sees data[0]

for (auto i = 0; i < b.Size(); ++i)
{
        Use(b[i]);                   // right in both states: 1 then 2
}

Note what the last loop also fixes: the range version of the second case walks two slots but the second one is not the second element, so the bug shows up as a wrong value before it shows up as a bad address — and Size() still says two, which is why the count mismatch alone will not catch it either.
