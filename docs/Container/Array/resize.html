Resize

member of hbe::Array Engine/Container/Array.h noexcept change the element count to exactly the number you asked for — no growth policy, no spare capacity

Signature

void Resize(TIndex newSize) noexcept;

Function description

Allocates a buffer of exactly newSize elements through this array's own allocator, moves every existing element into it, default-constructs the elements past the old count, then destroys the old elements and returns the old buffer.

The exactness is the point. There is no capacity figure growing geometrically behind your back, so a count chosen to fit a memory layout stays that number and can be reasoned about afterwards. Shrinking is symmetric: elements from newSize up are destroyed and their memory is handed back rather than held for reuse.

Parameters

ParameterTypeRequirement
newSize TIndex (int) The exact element count wanted, zero or greater. See the hazard below about negative values. Asking for the size the array already has returns immediately, allocating nothing.

Return value

void. There is no status to check: the function reports a failed allocation by asserting and leaving the array exactly as it was. The early return sits outside the assertion, so a configuration where Assert is silent — Release, per Core: Debug — still keeps the old size and the old buffer; it just stops saying anything. A caller that has to know whether the resize happened compares against Size afterwards.

A negative newSize is not diagnosed, and it leaves the array in a state no other operation expects. The allocation-failure branch is guarded by newSize > 0, so a negative count walks past it: every element is destroyed, the old buffer is returned, and the negative number is stored as the length. Size then reports negative, IsValidIndex rejects every index including 0, and the destructor skips the buffer because the pointer is now null — corrupt, but not a crash, which is what makes it slow to find. Validate the count before calling this with a number that came from a file, a network packet or a subtraction.
Two things every caller inherits from moving all the elements. An element that is expensive to move costs that cost on every resize, and a pointer or reference into the array is invalidated by it — including to elements whose value survived, because they now live at different addresses. If something else holds an address into the buffer, do not resize the array; see ToRawArray for the same invalidation from the other side.

Examples

Growing keeps what was there and default-constructs the tail:

hbe::Array<int> sizes;
sizes.Resize(4);            // 4 elements, an allocation of exactly 4
sizes[0] = 128;

sizes.Resize(2);            // 128 is moved into a new 2-element buffer;
                            // elements 2 and 3 are destroyed and the old buffer is freed
sizes.Resize(4);            // back to 4: 128 and 0 survive, slots 2 and 3 are default-constructed

Resizing to zero is a normal request, not a failure — it empties the array and releases the buffer:

sizes.Resize(0);
if (sizes.Size() == 0)
{
        // and sizes.ToRawArray() is now nullptr
}

Where the memory comes from is decided by the constructor, not by the resize — a resize reuses the allocator the array already holds:

// The allocator argument is what pins an array to a pool; Resize keeps using it.
hbe::Array<MeshVertex, FrameAllocator> batch(frameAllocator, 1024);
batch.Resize(2048);   // allocated from frameAllocator, not from the scope open right now

The third example's FrameAllocator and frameAllocator stand for whichever allocator you use — see the constructors for which forms take one, and Memory: allocators for what they draw from.
