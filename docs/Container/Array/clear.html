Clear

member of hbe::Array Engine/Container/Array.h noexcept empty the array and hand the buffer back — the whole body is Swap(Array())

Signature

void Clear() noexcept;

Function description

One statement: construct a temporary empty Array and swap with it. The temporary arrives as (length = 0, data = nullptr), the two arrays exchange those two fields, and the temporary — now holding the only pointer to the buffer — is destroyed at the end of the full-expression, destroying every element and releasing the memory.

The result is a genuinely empty array: Size is 0 and ToRawArray is nullptr. Nothing is kept for reuse. That is the deliberate difference from the other containers in this module, which destroy their elements and keep their buffer: Vector::Clear, Deque::Clear and HashMap::Clear all leave Capacity() unchanged, while Array::Clear drops the allocation entirely, because for this container the allocation and the element count are the same number. Refilling an array after a clear therefore costs a fresh allocation plus a full construction pass; if the intent is "empty it but keep the room", the container that wants that job is Vector, or an explicit resize back up to the size you still want.

The buffer is freed by the temporary's allocator, not by this array's. Array() default-constructs its own TAllocator, and the temporary — not this — runs the destructor that calls deallocate. A DefaultAllocator records the allocator id current at construction, so the memory is released through the scope open where you called Clear, not the scope that allocated it. A stateful adapter such as NamedPoolAllocator<T>, which is constructed from a specific pool, makes this a free into the wrong pool or into nothing. This is the same property that makes move assignment and Swap allocator-blind; Clear is simply the case that happens on every call, and the one a caller cannot see coming.
Everything pointing into the array dies here. Every pointer, reference and iterator obtained from the array — from begin, operator[] or ToRawArray — refers to memory that is freed before Clear returns. The elements are destroyed in ascending order, by the temporary, using the same explicit ~Element() walk described on the destructor page.

Parameters

None.

Return value

void. There is no status and nothing can fail: Clear asserts nothing, allocates nothing, and is noexcept. It is safe on an array that is already empty — the swap exchanges two null-state pairs and the temporary frees nothing.

Examples

The one call site in the engine, during shutdown:

void TaskSystem::JoinAndClear() noexcept
{
        for (auto& stream : streams)
        {
                // ... request shutdown of each stream, then join its worker thread ...
                thread.join();
        }

        streams.Clear();          // Array<TaskStream>: every TaskStream destroyed, buffer released
}

From Engine/Core/TaskSystem.cpp, in TaskSystem::JoinAndClear. Note the range-for immediately before it: the buffer that loop walked is the buffer this call frees.

The refill cost, which is the reason to think twice before putting this in a loop:

Illustrative — no call site for this exists in the repository.

for (const auto frame : frames)
{
        batch.Clear();                       // allocation released
        batch.Resize(frame.count);           // allocation taken again, every element reconstructed
        Fill(batch, frame);
}
