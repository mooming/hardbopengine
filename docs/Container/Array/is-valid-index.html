IsValidIndex

member of hbe::Array Engine/Container/Array.h const noexcept the bounds test the accessors assert — exposed, so a caller can check before it indexes

Signature

[[nodiscard]] bool IsValidIndex(TIndex index) const noexcept;

Function description

Returns index >= 0 && index < length: two comparisons and no memory access. It is the exact predicate operator[] and Emplace assert, so calling it is not a duplicate safety net — it is running the same test the accessor will run, and getting a bool instead of a fatal assert.

The index >= 0 half is why TIndex is int. Against an unsigned index that test is trivially true and a negative value would be admitted as an enormous positive one; here a negative index is rejected on its own terms. It also means IsValidIndex answers false for every index, 0 included, when the array has been resized to a negative count — the one case where "no valid index" is the correct answer for the wrong reason.

The engine-wide hbe::TIndex is a different type. Core/Types.h defines hbe::TIndex as size_t, and hbe::TIndex and the member alias are both reachable by the spelling TIndex depending on scope. Passing a size_t index narrows silently into the int parameter; a value above INT_MAX becomes negative and is then rejected, so the failure mode is a rejected index rather than a wrong element. Write the member alias explicitly at the call site.

Parameters

ParameterTypeRequirement
index TIndex (int) Any value at all — that is the point of the function. No precondition, nothing to get wrong by passing

Return value

TypeWhat you get
bool true when operator[] would accept this index without asserting. Always false for an empty array, since length is 0 and no index is below it. [[nodiscard]], so a bare array.IsValidIndex(i); that meant to be a test is a compile error

Examples

The task system uses it as a precondition on a public lookup whose index arrives from outside — the real guard, and the pattern for anything indexing an Array with a number it did not create: 

[[nodiscard]] bool HasStream(TIndex index) const noexcept
{
        return streams.IsValidIndex(index);
}

bool TaskSystem::Enqueue(const TIndex streamIndex, const RangedTask& task) noexcept
{
        if (!streams.IsValidIndex(streamIndex))
        {
                Assert(false, "Invalid stream index %d", streamIndex);

                return false;
        }

        auto& stream = streams[streamIndex];
        return stream.EnqueueFifo(task);
}

From Engine/Core/TaskSystem.h, where HasStream is nothing but this call, and Engine/Core/TaskSystem.cpp, in TaskSystem::Enqueue. GetStreamName in the same file does the same test and returns a static "Unknown" string instead of indexing.

Checking and then indexing is only safe if nothing changes the array in between. A successful IsValidIndex followed by a shrink or a clear and then an operator[] reaches the assert anyway. The engine's own header says this in as many words on TaskSystem::HasStream: the test "is not a lifetime guarantee across the call: a concurrent JoinAndClear can retire the stream between the test and the use." In a multi-threaded reader it is a diagnostic, not a lock.
