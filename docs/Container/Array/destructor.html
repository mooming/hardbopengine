~Array

member of hbe::Array Engine/Container/Array.h destroys every element explicitly, then frees through the allocator the array already holds

Signature

~Array();

Function description

Three steps, in this order: return immediately if data is null; call item.~Element() on each element by walking the range begin() to end(); then hand the buffer back with allocator.deallocate(data, length). Elements are destroyed before the memory goes, which is the only order that is safe, and the count passed to deallocate is the same element count that was passed to allocate — the allocator is asked for the same thing twice.

Destruction is explicit rather than a std::destroy-style loop because the buffer holds constructed objects the array itself placed there; the array never assigns through the elements on this path, so an element with a deleted assignment operator still lives in an Array that is only ever constructed, moved and destroyed.

The destructor is the reason the allocator is a member at all. Allocation and deallocation cannot end up split across two pools, because both use the one copy stored in allocator — chosen by whichever constructor built the array.

The array's own lifetime must end inside the memory scope its allocator refers to. A DefaultAllocator records the allocator id that was current when the array was constructed, and the destructor replays it; an adapter that holds a reference to a pool inherits that pool's lifetime rule instead of a softer one. So an Array built from a frame allocator that outlives the frame — a member of a longer-lived object, or a static — frees into memory that has already gone. This is the ordering rule for any container placed in an arena: the container is destroyed first, or it must not be in the arena.
Elements are destroyed in ascending index order — the same direction they were constructed in. The loop is for (auto& item : *this), so element 0 dies first. That is not the reverse-of-construction order a stack-like destruction would give, and it matters only for elements whose destructor touches a sibling element through a stored reference or pointer: such an element can be destroyed before the thing it refers to. An element that stores an index instead of an address is unaffected, and GetIndex works during destruction only in the trivial case.

Parameters

None.

Return value

A destructor has no return value and cannot fail in a way you can observe: it is implicitly noexcept, so an element destructor that throws propagates out of a noexcept function and terminates the process. The null-buffer early return also means an array whose buffer was never obtained — the state a failed sized construction leaves behind — releases nothing and reports nothing.

Examples

A destructor is only ever observed by leaving scope, which is exactly what the module's fixture does — every test constructs a local Array and lets it go at the closing brace: 

AddTest("Default Constructor", [this](auto& ls)
{
        const Array<int> array;        // no buffer, so the early return fires
        if (array.Size() != 0)
        {
                ls << "Null Array Size is not zero." << lferr;
        }
});                                        // array is destroyed here, releasing nothing

Where the ordering rule bites, in the shape that breaks:

Illustrative — no call site for this exists in the repository.

// Wrong: the array outlives the allocator scope its buffer came from.
Array<MeshVertex, FrameAllocator> vertices(frameAllocator, 1024);
// ... returned or stored somewhere that lives past this frame ...

// Right: declared inside the scope, destroyed before it closes.
{
        Array<MeshVertex, FrameAllocator> scratch(frameAllocator, 1024);
        FillScratch(scratch);
}
