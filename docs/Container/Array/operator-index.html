operator[]

member of hbe::Array Engine/Container/Array.h 2 overloads noexcept direct element access, guarded by an assertion rather than by a fallback value

Signatures

One page for the name, because both overloads state one contract and differ only in const-ness:

/// mutable view of the element at `index`
Element& operator[](TIndex index) noexcept;

/// read-only view of the element at `index`
const Element& operator[](TIndex index) const noexcept;

Function description

Returns a reference to the element at index, straight from the buffer: data[index], with no bounds-clamping and no copy. Overload resolution picks the pair — an const Array gets the read-only one.

Both overloads assert IsValidIndex(index) with FatalAssert before touching memory. The absence of a return value for the bad case is the design: an out-of-range index is a bug to be caught where it happened, not a condition to be handled downstream.

Parameters

ParameterTypeRequirement
index TIndex (int) 0 to Size() - 1 inclusive. Negative is out of range, not wrapped. When the index is computed from external input, test it with IsValidIndex first

Return value

TypeWhat you get
Element& / const Element& The element itself, so array[i] = value; writes in place and &array[i] is a pointer into the array's buffer. That pointer is good until something resizes, clears or destroys the array — not until the element's value changes

Examples

for (hbe::Array<int>::TIndex i = 0; i < sizes.Size(); ++i)
{
        sizes[i] = i * i;            // writes in place; TIndex keeps the comparison signed
}

Reading through a const reference, which selects the second overload:

const hbe::Array<MeshVertex>& verts = mesh.GetVertices();
const auto& first = verts[0];      // const MeshVertex&
A loop counter of the wrong integer type is how this assert gets hit. TIndex is int; a size_t counter compared against Size() mixes signed and unsigned, and a counter driven below zero reaches operator[] with a negative index. Compare signed against signed, as the first example does.
FatalAssert is active in every configuration, Release included. The bounds check is not compiled out of a shipped build, so an out-of-range index stops the process where it happened rather than reading garbage — see Core: Debug for the assert family. Contrast Resize, whose failed-allocation report uses Assert, which is limited to Debug and Dev builds.
