ToRawArray

member of hbe::Array Engine/Container/Array.h 2 overloads const noexcept the buffer itself, for the interfaces that take a pointer and a count

Signature

[[nodiscard]] Element* ToRawArray() noexcept;
[[nodiscard]] const Element* const ToRawArray() const noexcept;

Function description

Returns data — the field, unchanged, with no address-of arithmetic. It is the accessor that names the intent: an Array's elements are one contiguous buffer of exactly Size of them, so a pointer plus that count is everything a C API, a graphics API or a serialiser needs, with no copy through an intermediate.

The two overloads differ in the const-ness of what you can do through the pointer, not in the value returned. The pointer type is exactly what begin() yields for a non-empty array; ToRawArray is the safer spelling on an empty one, because returning a stored null pointer does not form an address from a null base the way &data[0] does.

Both are [[nodiscard]] and noexcept. The trailing const on the second return type qualifies the returned pointer rather than what it points at, which for a prvalue amounts to very little: it blocks binding the result to a non-const reference (auto& p = array.ToRawArray(); is ill-formed, const auto& is fine) and shows up in decltype(auto) deduction. Reading it as "the pointer cannot be reseated" is accurate and is the only place it can be observed.

The pointer is valid only as long as the buffer is, and four things end that. Resize frees the buffer it was allocated from after moving the elements out of it, Clear frees it outright, the destructor frees it, and a Swap or a move assignment leaves it owned by a different array — the bytes stay valid, but they are another array's elements now. Any of those leaves the pointer you are holding pointing into freed memory with nothing to detect it: this is a raw pointer, and there is no debug layer between it and the allocator.
An empty array gives you nullptr, and a zero-length pass is a different contract per callee. A default-constructed, cleared or zero-resized array has never allocated, so the pointer is null rather than a valid-but-unusable address. Pair ToRawArray() with Size() and test the count before handing the pair to anything; do not assume a null pointer with a zero count is accepted, and do not "fix" the null by allocating a dummy element — the null is the array's stated state.

Parameters

None.

Return value

TypeWhat you get
Element* / const Element* const The first element's address, or nullptr if the array holds nothing. The memory belongs to the array: do not free it, and do not keep it past the next resize, clear, swap or destruction

Examples

Illustrative — no call site for this exists in the repository. Grepping Engine/ and Applications/ for ToRawArray finds the declaration in Engine/Container/Array.h and nothing else: the engine's own code indexes Array through operator[] or walks it with range-for instead, as ResultContainer::Append and TaskSystem::JoinAndClear do.

const auto count = vertices.Size();

if (count > 0)
{
        // The pointer and the count come from the same object, in the same scope.
        renderer.Upload(vertices.ToRawArray(), count);
}

// Writing straight into the buffer is allowed — it is the array's own storage.
auto* slot = reinterpret_cast<float*>(payload.ToRawArray());
slot[0] = timeSeconds;                  // a view over the elements, not a copy of them

The second statement is what the accessor makes possible — one buffer, seen as Element by the container and as bytes by the caller — and equally what makes it dangerous: nothing in the type system stops that write from running past Size() elements, because the array cannot see a pointer it did not hand out through operator[].
