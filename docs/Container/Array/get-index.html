GetIndex

member of hbe::Array Engine/Container/Array.h const noexcept which slot is this element in — answered by address arithmetic, not by a search

Signature

TIndex GetIndex(const Element& element) const noexcept;

Function description

The body is three lines: return -1 if data is null; compute static_cast<TIndex>(&element - &data[0]); return that difference if IsValidIndex accepts it, and -1 otherwise. No element is read, no comparison is made, and Element needs no operator== for this to compile. The cost is one subtraction divided by sizeof(Element) — the same arithmetic the compiler already performs inside operator[], run in reverse.

It answers "where is this object", not "where is a value equal to this one". That is the useful half of the contract: an element obtained from operator[], begin() or an Emplace result is recognised by identity even when the element compares equal to several others, or does not support comparison at all. Vector in this same module offers the other question — its FindIndex walks the buffer comparing with operator== — and the two are not interchangeable.

What it does to a foreign object is the part to understand. The subtraction is performed on two pointers before anything is known about them, and subtracting pointers into unrelated allocations is not something the standard defines; in practice the result is the byte distance divided by sizeof(Element). The range check that follows turns most foreign objects into -1 — one at a lower address always gives a negative difference — but an object in another allocation above this buffer can produce a difference that lands inside [0, Size()), and the function then returns it as a confident, wrong index. There is no way to tell that case from a correct answer. Treat a non-negative result as meaningful only for a reference you took out of this array, and remember that an resize or a swap leaves the address you are holding in a buffer that no longer belongs to the array.
Two small consequences of how it is written. The null-buffer test is marked unlikely, so the compiled path assumes a live buffer — an empty array still answers -1, just along the cold branch. And the function is not [[nodiscard]], so array.GetIndex(item); as a statement compiles and does nothing; every other query on this class carries the attribute.

Parameters

ParameterTypeRequirement
element const Element& Ideally an lvalue the array owns — something you read back out of it. Taken by const reference so the address survives: passing a temporary that merely looks like an element is exactly the foreign-object case above, and it is not prevented by the type. A const reference to a non-const array's element is fine; the function reads nothing

Return value

TypeWhat you get
TIndex (int) The slot the element occupies, usable straight as an operator[] index, or -1 for "not answered": an empty array, an object below this buffer, or an object far enough above it to fall outside [0, Size()). -1 is a sentinel, not an index — test it before indexing

Examples

Illustrative — no call site for this exists in the repository. Grepping Engine/ and Applications/ for GetIndex( finds only the declaration in Engine/Container/Array.h; the engine keeps its own index alongside the element instead, as TaskSystem::GetStreamName and ResultContainer's slot count do.

auto& hit = slots[probeIndex];                // a reference taken out of the array
const auto slot = slots.GetIndex(hit);        // probeIndex, recovered from the address alone

if (slot == -1)
{
        // The reference is not an element of this array — most often because the array was
        // resized or swapped since it was taken. Do not index with it.
        return;
}

RemoveSlot(slot);

The realistic use is therefore a round trip: take a reference out, hand it around, and recover its slot when it comes back. The reference has to have arrived untouched, because the recovery is arithmetic on its address and nothing else — a copy of an element, however faithful, is a different object and gets a different answer.
