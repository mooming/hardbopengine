Swap

member of hbe::Array Engine/Container/Array.h noexcept exchange length and data and nothing else — every move, assignment and clear in this container is built on it

Signature

void Swap(Array&& rhs) noexcept;

Function description

Two fields change hands: length and data. No element is constructed, destroyed, moved or copied, which is what makes the operation O(1), allocation-free and noexcept. The third member, allocator, is deliberately not touched — see the hazard below.

It is the primitive the rest of the class is written in. The move constructor is Array() { Swap(rhs); }, move assignment is Swap(rhs); return *this;, and Clear is Swap(Array()). Reading this function is therefore the shortest route to the semantics of all three.

The parameter is an rvalue reference, so the other side must be a temporary or explicitly moved. That is stricter than it needs to be and it is worth knowing before you write the call: a.Swap(b); with two named arrays does not compile, a.Swap(std::move(b)); does. Compare Vector::Swap(Vector&) and Deque::Swap(Deque&) elsewhere in this module, which take an lvalue reference — the spelling that works for one of these containers is not the spelling that works for the other.

Only two of the three members move, so each array ends up freeing memory it did not allocate. The allocator member stays where it was while the buffer it is paired with does not, so after a swap between two arrays built in different memory scopes each will hand its adopted buffer to the wrong allocator at destruction. DefaultAllocator captures the allocator id that was current when it was constructed, so the mismatch is real even with no custom allocator in sight; with a pool adapter such as NamedPoolAllocator<T> it is a cross-pool free. Safe in the common case — both arrays use DefaultAllocator and were built while the same scope was open, which is the situation in every call site the engine has — and silently unsafe in the others. The allocator contract in Memory is the place that rule belongs; this is where it bites.
Iterators survive a swap in the arithmetic sense and die in the ownership sense. A pointer obtained before the swap still points at the same bytes and still compares equal to itself, but those bytes are now elements of the other array, sized by the other array's length. A range you were iterating does not become invalid — it becomes somebody else's range. Use ToRawArray and Size freshly after any swap rather than carrying a range across one.

Parameters

ParameterTypeRequirement
rhs Array&& A temporary, or a named array with std::move applied. Same Element and same TAllocator type, since the two are different types otherwise. An array swapped against a default-constructed temporary — the Clear pattern — receives a null buffer and a zero length, which is what makes that idiom work

Return value

void. There is nothing to report and no way to fail: the body is four assignments. Swapping an array with itself is not a special case that needs guarding — the assignments write each field with its own value, and the array is unchanged.

Examples

The engine's real use — give an array a new buffer and let the temporary take the old one away:

// streams is Array<TaskStream>, a member of TaskSystem, default-constructed so far.
streams.Swap(Array<TaskStream>(numHardwareThreads));

// streams now owns numHardwareThreads default-constructed TaskStreams.
// The temporary holds the buffer streams used to have (none, here) and releases it at the
// semicolon, through its own freshly constructed allocator.

From Engine/Core/TaskSystem.cpp, in the task system's stream construction. The sized temporary is the two-argument-less size constructor, so the allocation happens on the temporary's allocator, not on one captured earlier.

The two-array form, which needs the explicit move:

Illustrative — no call site for this exists in the repository.

a.Swap(std::move(b));        // a holds b's old buffer; b holds a's; neither element moved
a.Swap(b);                  // does not compile: Swap takes Array&&
