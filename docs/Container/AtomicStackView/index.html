AtomicStackView

Engine/Container/AtomicStackView.h namespace hbe template <CNext T> final one atomic pointer, a compare-and-swap loop, and nodes the caller owns — the thread-safe one of this module

Class description

This is a lock-free stack in the textbook shape: a single std::atomic<T*> top;, a push that installs a node at the head, and a pop that detaches it, both driven by compare_exchange_weak. The linkage lives inside the elements — the type parameter has to carry a next member, expressed as the CNext concept — so the container itself allocates nothing and stores nothing but one pointer.

"View" is the word that carries the ownership rule. The stack points at objects somebody else created and keeps alive; Push writes into one of them, Pop hands a pointer back to it, and the stack never constructs, destroys, frees or counts anything. The engine's one user shows the arrangement that makes this sound: Engine/Memory/MemoryManager.h:173 declares AtomicStackView<AllocatorProxy> proxyPool; directly beside AllocatorProxy allocators[MaxNumAllocators];, and the two are push and pop in a fixed pool of never-freed nodes.

The stack owns nothing, so it releases nothing — not even on destruction. The destructor is = default, and it will happily destroy a stack that still has a chain hanging off it: the nodes survive, the links into them are simply lost. A pool that is torn down while proxies are still checked out leaks them without a word, and nothing in the interface even lets you find out whether anything is left, because there is no count and no head accessor. The owner has to drain it, and no engine code does that today — MemoryManager lives for the process.
It is neither copyable nor movable, and the header never says so. No copy or move operation is declared, and the implicit ones are removed by the compiler because std::atomic is not copyable or movable — a deleted-ness you discover at the call site rather than from the interface. That is the right outcome for a shared head pointer (copying one would be aliasing the same chain from two owners), but every other class in this module states its deletions explicitly, so this one's immobility is an inference rather than a declaration.
A platform gate is enforced at compile time. The class body opens with static_assert(std::atomic<T*>::is_always_lock_free, …), so a type whose pointer is not lock-free on the target is rejected where the class is instantiated rather than silently taking a locked implementation. The rest of the memory model is fixed rather than configurable: release on success, relaxed on the initial load and on failure — see Pop for what that buys and for the two exposure points the algorithm leaves open.

Template parameters

ParameterKindWhat it must satisfy
T constrained by CNext A type with a member named next — the concept checks only that the name exists. The real requirement is stronger and is enforced later, inside Push: next has to be assignable from a T*, so in practice T* or something convertible from it. AllocatorProxy qualifies with AllocatorProxy* next; (Engine/Memory/AllocatorProxy.h:21). A type whose next is, say, an int satisfies the constraint and then fails to compile in the body of Push — a confusing diagnostic location that is a property of the concept as written, not of your type. The object must also outlive every concurrent compare-and-swap that could touch it, which for a recycled pool means: never free a node another thread may still be reading

Class properties

NameDeclarationWhat it means
top std::atomic<T*> top; private The entire container: the address of the most recently pushed node, or null. Push and Pop are the only ways to change it, and there is no accessor for reading it — even a non-destructive peek at the head is not offered
Iterator using Iterator = T*; member type Declared, and never usable: the class has no begin() or end(), so nothing can produce or consume one. It exists for symmetry with the other containers' aliases and is dead code as far as this header is concerned
ConstIterator using ConstIterator = const T*; member type Same situation. A walk over a live stack is not merely un-aliased, it is fundamentally unsafe — the chain changes under you — so no such operation is provided

Class methods

MethodSignatureWhat a caller depends on
constructor AtomicStackView() noexcept Sets top to nullptr. Allocates nothing, and is the only constructor — there is no range-constructing or pre-sizing form
destructor ~AtomicStackView() = default Destroys the pointer only. Nodes still linked on the stack are neither unlinked nor freed nor noticed — see the gap above
copy and moveall implicitly removed not declared The atomic member makes every copy and move form unavailable. Nothing can be declared to fix it either: two owners of one head pointer is the bug the deletion prevents
Push void Push(T& newItem) noexcept Installs an object the caller owns at the head; cannot fail, cannot report; overwrites newItem.next, so the object may be in exactly one such stack at a time
Pop T* Pop() noexcept Detaches the head and clears its link field, or returns nullptr when the stack is empty or lost the race. No assert, and no [[nodiscard]] either — discarding the pointer is a silent leak
IsEmpty [[nodiscard]] bool IsEmpty() const noexcept One relaxed load compared against null. It is a snapshot, not a guarantee: by the time you act on IsEmpty() == false another thread may have drained the stack, which is why the engine's real caller tests the result of Pop() rather than the result of IsEmpty() before using a proxy

Non-member helper functions

One name at namespace scope, and it is a constraint rather than a function: 

template<typename T>
concept CNext = requires(T t) { t.next; };

It is exported from Container/AtomicStackView.h into hbe and used by exactly one class today, but it is visible to every translation unit that includes the header, so any later intrusive atomic container in the engine can reuse it — which makes its weakness a shared property: it tests for a member name only. It is documented here rather than as a separate entry of the module page, and the module page's Coverage records that choice; the same treatment is applied to LinkedListNode and EHashEntryState.
