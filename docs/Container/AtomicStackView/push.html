Push

member of hbe::AtomicStackView Engine/Container/AtomicStackView.h noexcept compare-and-swap an object you already own onto the head of an intrusive lock-free list

Signature

void Push(T& newItem) noexcept;

Function description

Three lines. The object's own next field is loaded with the current head (top.load(std::memory_order_relaxed)), then a compare-and-swap-weak loop tries to install &newItem as the new head, expecting the old head it just read. On failure the CAS has written the head it actually saw back into newItem.next — which is why the loop needs no re-load, and why compare_exchange_weak is acceptable despite its spurious failures: each retry simply re-reads the head into the same field. Success publishes with std::memory_order_release, so a thread that later loads the head with acquire sees the link field this thread wrote.

Nothing is allocated. The stack is a single std::atomic<T*> and the link is a field of the element itself — that is what the "View" in the class name means, and it is the reason the parameter is a non-const T&: the call has to write into your object.

Push overwrites newItem.next, so an object belongs to at most one such stack and must not be pushed twice. After the call, that member is the stack's bookkeeping, not yours. Two consequences with no diagnostic anywhere: pushing an object that is already in this stack makes it point at itself or forms a cycle and corrupts the list for every thread using it, and keeping the same object linked in a second AtomicStackView (or in a hand-rolled intrusive list using the same field) means the two structures overwrite each other. Nothing checks for either. The engine's only user keeps the discipline by state: an AllocatorProxy is either in the free pool or handed out to a registered allocator, never both — Engine/Memory/MemoryManager.cpp:50 and :255 are the two transitions.
The stack does not own what you push, and it never frees it. There is no destructor logic, no allocator, no count: dropping the last reference to the stack leaves whatever is still linked on it exactly where it was. Objects have to outlive every pop that will ever return them, which in practice means static or pool-resident nodes — see Pop for who does eventually release them.

Parameters

ParameterTypeRequirement
newItem T& A modifiable lvalue of a type satisfying CNext — it must have a member next assignable from T*, as AllocatorProxy does with AllocatorProxy* next; at Engine/Memory/AllocatorProxy.h:21. A temporary or a const object cannot bind, which is deliberate: the call mutates the argument. The object must be alive until it is popped and, under contention, must not be destroyed while any thread's CAS may still be reading its link

Return value

void. Pushing cannot fail — there is no capacity and no allocation — and cannot report anything: the loop retries until the install succeeds. IsEmpty() is false once the call returns, and a concurrent Pop may already have taken the object again by then.

Examples

Real call site — Engine/Memory/MemoryManager, which keeps its allocator proxies in one of these and hands them out to threads without a lock.

// Engine/Memory/MemoryManager.h:172-173 — the nodes are a fixed array the manager owns
AllocatorProxy allocators[MaxNumAllocators];
AtomicStackView<AllocatorProxy> proxyPool;

// Engine/Memory/MemoryManager.cpp:46-50 — every proxy but the system allocator starts in the pool
for (int i = 1; i < MaxNumAllocators; ++i)
{
        auto& proxy = allocators[i];
        proxy.id = i;
        proxyPool.Push(proxy);
}

// Engine/Memory/MemoryManager.cpp:255 — released back when the allocator is unregistered
proxyPool.Push(allocator);

Note what the array buys: the pushed objects are never freed, so the pointers the stack hands out stay valid for the whole process, and a proxy is only ever pushed by whoever currently owns it. That arrangement — static nodes, single-owner state machine — is what makes this class safe in the engine, and it is not something the class enforces for you.
