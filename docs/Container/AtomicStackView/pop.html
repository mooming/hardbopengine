Pop

member of hbe::AtomicStackView Engine/Container/AtomicStackView.h noexcept detach the head by compare-and-swap and hand back the pointer — or nullptr, and not only when empty

Signature

T* Pop() noexcept;

Function description

The head is loaded relaxed and guarded by unlikely(node == nullptr) — the branch hint from OSAL/Intrinsic.h — returning nullptr at once if the stack is empty. Otherwise a compare-and-swap-weak loop tries to replace the head with node->next, publishing with std::memory_order_release and retrying relaxed on failure, and the loop re-tests node for null on every iteration because a failed CAS loads whatever head it found into node. On success the link field is cleared (node->next = nullptr;) and the object is returned.

A null return does not mean the stack was empty — it can mean another thread won the race. If several threads pop at once, the losers keep re-reading the head until they either succeed or find a stack drained to nothing, and that second path returns nullptr even though the stack was non-empty on entry. So the return value is the whole contract: there is no assert (compare Queue::Pop and RingQueue::Pop, which stop the process), no exception, and no way to distinguish "empty" from "somebody else got there first" — which is exactly why a caller loops on it instead of treating a null as a bug.
You own the returned object, and nothing will ever give it back. The stack stores pointers to objects the caller created (Push explains the ownership rule); Pop only detaches. So the value must be recycled with another Push, or released by whatever owns its storage — and if it is neither, it is simply lost: this class has no destructor logic, and its own destruction does not walk the remaining chain.
The link field is a plain pointer, and this design has the two standard exposure points of a compare-and-swap stack. Both are properties of the algorithm as written, not of a particular platform, and neither is defended anywhere in the header:
  • The ABA window. top is a single-word pointer CAS with no tag, counter or version. A thread that reads head = A, loses the race, and later finds top == A again will succeed its CAS on the strength of the address alone — so freeing a node, reusing its memory as a new node, and re-pushing it can make a stale CAS succeed. That is possible here precisely because node addresses are recycled by design.
  • A race on next. node->next is read as the desired value of the CAS while a different thread that has just detached that same node writes node->next = nullptr. Both are plain, non-atomic accesses to the same scalar, so formally this is a data race; in substance the stale value cannot break anything, because the decision is made by the compare against top and a wrong next only produces a failed CAS and a retry.
What keeps the engine's own use out of both traps is the shape of the data, not the code: the nodes are a fixed array of static-lifetime objects (AllocatorProxy allocators[MaxNumAllocators]; at Engine/Memory/MemoryManager.h:172) that are never freed, and each one is either in the pool or checked out, so a node's identity never changes while the stack refers to it. Any other use of this class inherits the same requirements.

Parameters

None.

Return value

TypeWhat you get
T* The detached object, with its next field already cleared so it can be inspected or re-pushed safely, or nullptr if the stack was empty or was drained by another thread first. Not [[nodiscard]] — calling Pop() and discarding the pointer loses the object with no warning. The type parameter is not const: a stack of const-usable objects still hands out a mutable pointer

Examples

Real call site — Engine/Memory/MemoryManager.cpp:140, where a null pop is treated as pool exhaustion and reported rather than assumed impossible.

auto allocatorProxyPtr = proxyPool.Pop();
if (unlikely(allocatorProxyPtr == nullptr))
{
        Log(ELogLevel::FatalError, [funcName = __func__, name](auto& ls)
        { ls << "[" << funcName << "][" << name << "] failed to register an allocator."; });

        return InvalidAllocatorID;
}

auto& allocatorProxy = *allocatorProxyPtr;
auto id = allocatorProxy.id;

That is the whole usage pattern: test the pointer, use the object, and return it with Push when the consumer is finished — the release path at Engine/Memory/MemoryManager.cpp:255. The pool is bounded by the size of the static array, so exhaustion is a real condition with a real diagnostic, not a theoretical one.
