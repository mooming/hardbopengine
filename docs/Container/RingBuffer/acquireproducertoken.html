AcquireProducerToken

member of hbe::RingBuffer Engine/Container/RingBuffer.h give a producer thread its slot in the declaration array, cached in thread-local storage

Signature

[[nodiscard]] size_t AcquireProducerToken() noexcept

Function description

Gives the calling thread its producer slot: the index of the entry in producerSlots that this thread alone writes. The index is cached in a static thread_local, so the search costs one thread-local read on every push after the first and the mutex is touched once per thread per queue. The cache is validated before it is trusted: it names the queue instance the token was earned from, and a token earned in one queue is refused by another. Each slot is padded to LineSpacing, so declaring a block never contends with another producer's declaration. Caching a per-thread identity is the engine's own idiom for the same problem, used by MemoryManager (Engine/Memory/MemoryManager.h) for its scoped allocator.

Validation is against the instance — its address plus an identity taken from a process-wide counter — and not against a thread id, for two reasons the same bug taught. A thread id cached from a queue that has since been destroyed cannot be checked without dereferencing that queue, which is exactly the memory the cache must never touch; and a thread id can come back after its thread has ended, because ids may be recycled, so a slot that seemed to belong to a dead producer can be handed to a new one while the queue still counts it as taken. Before the cache was validated, a thread that pushed into one queue was treated as tracked in every queue of the same type, so in a process holding several such queues two producers could be given the same slot — and since the slot is what declares a block alive, both of them then wrote the address of the block each was working on, which is the one piece of state RetireBlock trusts. A queue in a long benchmark run was seen to stop accepting work entirely; A Producer Thread Is Tracked In Every Queue It Pushes in Engine/Container/RingBuffer.cpp is the control that fails without this check and passes with it.

The slot declares which block the thread is working on. Push writes the address there, re-reads tail to confirm nobody moved it, and only then dereferences the block; it clears the slot once the block's ring has taken the element. RetireBlock will not free a block that any slot declares, and it will not retire one until tail has been moved off it, which together is what makes the reclamation sound: declaring after reading is only safe because the read is then repeated and the block's retirement is gated on the same pointer.

A slot is never released. A thread that finishes while holding one keeps it, so the number of distinct threads that ever push into this queue must not exceed inMaxProducers over the life of the queue, not merely at one instant. Since the token is per queue, a thread that pushes into several queues holds one slot in each of them. That is a real limit and it is stated here rather than hidden: on the engine it is comfortably satisfied, because producer threads are pool threads bounded by TaskSystem's hardware thread count.

Parameters

NameWhat the caller must supply
noneThis method takes no argument.

Return value

The thread's producer slot index, or InvalidProducerToken when every slot is claimed. Reaching that value asserts, in every build that has assertions, because it is a construction-size error rather than a runtime condition; in a release build the assertion is compiled out and the caller turns the value into EPushResult::TooManyProducers rather than letting the thread run untracked.

Examples

Illustrative — no call site for this exists in the repository.

const size_t token = AcquireProducerToken();
if (unlikely(token == InvalidProducerToken))
{
        return EPushResult::TooManyProducers;
}

producerSlots[token].block.store(block, std::memory_order_seq_cst);
