AtomicQueueViewMultiProviderSingleConsumer

Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.h namespace hbe template <CNext T> final Many producers pushing, one consumer popping: a Treiber stack outside, a consumer-private reversal that turns last-in first-out back into first-in first-out

Class description

Two pointers, no allocator, and one thread that is allowed to take things out. newest is an atomic Treiber stack that any number of producer threads push onto; oldest is a plain T* naming the list the consumer has already taken and not yet handed out. When Pop finds that private list exhausted it claims the entire producer stack with a single exchange and reverses the chain locally — the last-in first-out order of a stack read backwards is first-in first-out. The shape is the two-stack queue of Michael and Scott, restricted to a single consumer so that the consumer's half of the algorithm is protected by thread affinity instead of by a lock, which is what lets the reversal run on ordinary pointer writes with no atomics in it at all.

"View" carries the same ownership rule it carries in AtomicStackView: the nodes belong to the caller. The container allocates nothing, constructs nothing, destroys nothing and counts nothing — it stores a pointer into an object somebody else created, and Pop hands that pointer back. That is also why this class can be lock-free at all on this engine: the alternative, a queue that allocates its own nodes, would reach for ThreadSafeMultiPoolAllocator, whose free list is a mutex, and the lock would sit in the exact path the class exists to keep lock-free.

One property makes handing a node back to its owner sound, and the container has it. A producer writes exactly one link field — the one inside the node it is pushing — and it writes it before its compare-and-swap publishes that node. It never writes into a node that is already in the chain. So by the time Pop returns a pointer, no thread inside the container will read or write that object again: the caller may destroy it, recycle it, or push it back in. This is the property a two-phase publish (reserve a slot with an exchange, then link by writing the previous head's link field) does not have, and it is the reason that shape was not taken. Evidence, not assertion: AtomicQueueViewMultiProviderSingleConsumer's A Popped Node Belongs to Its Owner and to No One Else testlet holds 4,800 handed-back nodes against two hammering producers, and the same shape under ThreadSanitizer reports no race.
Pop and IsEmpty belong to one thread. oldest is a plain T*, not an atomic: it needs no atomic because exactly one consumer is permitted, and that permission is a contract rather than something the type enforces. Calling either from a second thread is a data race on an unguarded pointer, not a benign read — the guardrail in docs/TaskSystemRedesign.md §9 that makes a single producer or consumer provable rather than inferred is what a caller of this class owes. Push has no such restriction: any number of threads may push, and pushing is the only operation that touches an atomic.
What the reversal costs, and when. A Pop that finds its private list empty reclaims the whole producer stack, so one call can walk every node another thread had pushed since the last refill. The work is one read and two writes per node and each node is reversed exactly once in its lifetime, so the cost is amortised to one pass per node — but it lands on a single call, which makes that call's latency proportional to the burst it drained. A consumer that pops a steady one-at-a-time trickle refills one node at a time and never sees the spike. The design document records the invariants the argument rests on.
What this class deliberately does not have. No second consumer (that is a different algorithm, with a reclamation scheme attached), no element count, no front or back peek — peeking the producer stack would require claiming it, and a peek that consumes is not a peek. No blocking wait either: Pop returns null rather than parking, although std::atomic::wait is available on this toolchain, because a queue that can park its consumer cannot be drained from a shutdown path that outlives its producers. No cache-line padding either; see Coverage for why that is an open measurement rather than a decision.

Class properties

Type + NameDefault ValueDescription
std::atomic<T*> newest; private none in the header The producer stack: the most recently pushed node, whose next chain runs back through earlier pushes. Initialised to nullptr by the constructor; the only field with a memory order in it
T* oldest; private none in the header The consumer's own list, already reclaimed and reversed, in the order it will be handed out. Read and written by the one consumer thread and by nobody else, which is why it is not atomic

Both fields are one machine word, so an instance is 16 bytes on this platform (measured: sizeof 16, alignof 8) and a queue can live inside another object without a heap allocation of its own.

Non-member helper functions

One alias at namespace scope, and one constraint it depends on that this header borrows rather than owns: 

template<typename T>
concept CNext = requires(T t) { t.next; };   // declared in Container/AtomicStackView.h

template <CNext T>
using AtomicQueueViewMPSC = class AtomicQueueViewMultiProviderSingleConsumer<T>;

AtomicQueueViewMPSC is the readable spelling of the same type: the full name states the topology — multi-provider, single-consumer — that the class cannot enforce in its own signature, and the alias exists so a call site can be shorter without being vaguer. Both names name one type, not two, and either may be used anywhere the other is. CNext is defined in Container/AtomicStackView.h and reused here rather than restated, so the constraint has one home; it is documented there, and the same treatment is recorded for LinkedListNode on the module page's Coverage.

One naming fact a reader inherits with the alias: in this engine provider is already the task-supplying actor of the task system (Engine/Core/TaskProvider.h), while the concurrency literature calls a thread that enqueues a producer — which is what MPSC abbreviates. The full name uses provider; the algorithm means a thread that pushes.

Coverage

GapDetail
No throughput figure, and padding is an open question rather than a decision Nothing here is benchmarked. The producer stack and the consumer's list sit in the same 16 bytes, and all producers hammer newest while the consumer reads oldest on every pop, which is the classic shape for false sharing. Padding them apart is plausible and unmeasured, so it was not done — a TaskRegistry-style reservedToCacheLine gap added without a number would be decoration. The measurement that would decide it is a push-rate comparison with and without the gap
No engine call site yet The class ships with tests and no user. Every claim about what it is for comes from the guardrail in docs/TaskSystemRedesign.md §9, which prefers a lock-free single-consumer enqueue over a mutex and forbids a multi-consumer lock-free one without profiling; adopting it for a task stream is a separate change with its own review
The rejected alternative is recorded, not measured Why a two-phase publish (exchange to reserve, then write the previous head's link) was passed over — it needs a sentinel node the queue owns, and it leaves the newest node unreachable until a later node arrives behind it — is argued in .Plans/PLAN_lock_free_queue.md §3 from the algorithm's own steps. No implementation of that shape exists in this tree to benchmark against
