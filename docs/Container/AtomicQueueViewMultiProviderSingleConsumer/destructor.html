Destructor

member of hbe::AtomicQueueViewMultiProviderSingleConsumer Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.h defaulted, releases nothing, and cannot tell you the queue died still holding nodes

Signature

~AtomicQueueViewMultiProviderSingleConsumer() = default

Function description

Defaulted, and it does exactly what defaulted means here: the two words of state go away and nothing else happens. The destructor has no way to free what the queue holds even if it wanted to, because the nodes were never the queue's to free — Push took references to objects the caller created, and there is no allocator, no destructor call, no count, and no traversal.

That leaves a queue that can die holding nodes, which is a state worth naming rather than pretending is impossible: at the moment of destruction the consumer's private list may still be linked, and the producer stack may still hold everything a producer pushed that the consumer never came back for. Nothing is freed and nothing is lost — the caller still owns every one of those objects, and can pick them up by reading the fields it already has. The testlet Destroying a Queue That Still Holds Nodes Releases Nothing pushes three nodes, pops one, destroys the queue with two still inside, and then re-pushes all three into a fresh queue and reads their values back.

Nothing tells you the queue was non-empty. There is no count, no IsEmpty assertion in the destructor, and no log line, so a queue destroyed with work still queued fails silently — the nodes simply stop being reachable through any handle, and if the only owner of those objects was "whatever is in the queue", they leak. Every other container in this module destroys its elements and releases its storage, so the habit of assuming a destructor cleans up is exactly the habit this class punishes. The same property is recorded for AtomicStackView, and the reason is the same in both: a view that owns nothing can release nothing.
The queue must outlive every push that may still be in flight. Push writes into newest, so destroying the queue while a producer thread is between its load and its successful compare-and-swap is a use-after-free of the queue object itself — the plainest kind of bug, and no cheaper to fix than to avoid. The order a caller owes: stop or join the producers, drain on the consumer, then destroy. Destruction is a consumer-thread act, since it reads and invalidates the private list that only that thread may touch.

Parameters

None.

Return value

None; a destructor cannot report, and this one has nothing it could report about.

Examples

Real code — Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.cpp. A file-scope helper exists precisely so that "destroy it while it still holds two nodes" is a named act in the test rather than a bare brace pair.

void PushThreeThenDestroyWithoutDraining(std::array<QueueNode, 3>& nodes)
{
        AtomicQueueViewMPSC<QueueNode> queue;

        for (auto& node : nodes)
        {
                queue.Push(node);
        }

        queue.Pop();
}

The queue goes out of scope with two nodes still in it — one in the private list, one still in the producer stack — which is the state the testlet needs. What the caller keeps is the array, and the testlet's assertion is that all three nodes come back out of a second queue with their values intact.
