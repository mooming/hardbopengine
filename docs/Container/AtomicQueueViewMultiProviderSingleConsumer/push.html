Push

member of hbe::AtomicQueueViewMultiProviderSingleConsumer Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.h install a node you already own on top of the producer stack, from any thread, with no lock and no allocation

Signature

void Push(T& newItem) noexcept

Function description

Two statements, and the same two statements AtomicStackView::Push runs: the node's own next is loaded with whatever the producer stack's head currently is (newest.load, relaxed), then a compare_exchange_weak loop tries to install &newItem as the new head with release ordering. A failed compare-and-swap writes the head it actually saw back into newItem.next, which is why the loop needs no re-load and why the weak form is the right choice despite its spurious failures — a retry just re-reads the head into the field it is about to link from.

The published result is a stack, not a queue: newest runs newest-first, and first-in first-out order is restored later by ReverseNewest, which is legitimate only because exactly one thread performs that reversal. Nothing else about the push knows or cares who else is pushing.

One node, one link field, written once, before the compare-and-swap that publishes it. That is the whole reason a node may be recycled after it comes back out of Pop: a producer never touches a node that is already in the chain, so no push can reach into an object the consumer has handed away.

Push overwrites newItem.next, so a node may be linked in one structure at a time. After the call that field is the queue's bookkeeping rather than yours. Pushing a node that is already in this queue makes it link to itself or closes a cycle, and the consumer then walks a loop forever; keeping the same field used by a second intrusive container means the two overwrite each other. Nothing detects either. The discipline is the caller's: a node is either in the queue or in a hand, never both — which is the same single-owner state machine that keeps MemoryManager's proxy pool consistent.
Pushing cannot fail, cannot block, and cannot be refused. There is no capacity to fill and nothing to allocate, so the loop terminates as soon as one attempt wins the compare-and-swap. It is lock-free rather than wait-free: a thread may retry while others succeed. The node must already be alive and must stay alive until it has been popped — destroying a node while a concurrent push is still retrying against it destroys the object the compare-and-swap is writing.

Parameters

ParameterTypeRequirement
newItem T& A modifiable lvalue whose type satisfies CNext, with next assignable from T*. A temporary or a const object cannot bind, which is deliberate: the call writes into the argument. The object must outlive its own pop, and under contention must not be destroyed while any thread may still be retrying a push on it

Return value

void. There is no result to report: the call returns only once the node is installed, and by then a concurrent Pop may already have taken it away again. newItem.next is not a usable value after the call.

From Engine/Container/AtomicQueueViewMultiProviderSingleConsumer.cpp, the "Four Producers and One Consumer Lose Nothing" testlet

Each producer owns a disjoint slice of a fixed array, so no node is ever pushed twice and nothing is allocated while the threads run — the arrangement the class needs from its caller. The result the testlet asserts is 4,000 nodes delivered, none duplicated, and each producer's own thousand arriving in the order it pushed them.
