Insert

member of hbe::Map Engine/Container/Map.h 3 overloads put one entry in sorted position — which means moving every entry above it down one slot

Signature

bool Insert(const TKey& key, const TValue& value);
bool Insert(const TKey& key, TValue&& value);
bool Insert(TKey&& key, TValue&& value);

Function description

A binary search (FindIndex) decides whether the key is already there; if it is, the insert is dropped and the answer is false. Otherwise InsertSorted finds the insertion point with LowerBound, grows the buffer if it is full, shifts every entry from that point to the end up by one slot, and constructs Pair{key, TValue{}} in the hole. The caller then assigns value into entries[idx].value.

That last pair of steps is why TValue must be default-constructible and assignable: the value you pass is never a constructor argument. The same shape appears in HashMap::Insert, so it is a module convention rather than an accident of this class — and the consequence is the same: a value type that can be constructed but not assigned cannot live here.

Cost. The search is O(log n), but the shift is O(n) move-construct-and-destroy pairs, and a full buffer adds a reallocation that moves all of them again. Inserting into a Map in sorted order is cheap (the insertion point is the end, so nothing shifts); inserting into the front of a populated map moves the whole array. For a workload whose keys arrive in order — a build table, a resource manifest read from disk — this container is the right choice, and its ordered iteration and cache-linear lookups come free. For random insertion into a large map, it is the wrong one.

Every insert moves elements, so every iterator, pointer and reference into the map is invalidated by an insert that is not appended at the end. Even when no reallocation happens, the shift re-homes the entries above the insertion point by move-constructing each into the next slot and destroying the source, so a reference you held to an unrelated entry now points at a slot holding a different pair. Growth invalidates everything as well, and a growth here is not reported: Grow uses allocator.allocate(sizeof(Pair) * newCap) without testing the result before writing through it.
Order is whatever TCompare says it is, and the default is std::less<TKey>. The comparison is used asymmetrically — compare(stored, sought) and compare(sought, stored) — which is how equality is derived from ordering: neither one less than the other. A comparator that is not a strict weak ordering does not produce a compile error; it produces a sorted array that binary search cannot trust, and the symptom is an Insert that returns true for a key that is already in the map.

Parameters

ParameterTypeRequirement
key const TKey& (first two) / TKey&& (third) Copy- or move-constructible as the overload requires, and comparable under this map's TCompare. Duplicate keys are rejected rather than replaced, so the bool is the only report of the collision
value const TValue& / TValue&& Default-constructible, and assignable from the argument. Assigned only when the key was new — and note the order of events: the shift of other entries has already happened before the value arrives, so a value type whose assignment throws leaves the map one entry longer with a default-constructed hole in it

Return value

TypeWhat you get
bool true when a new entry was created (and the argument value then assigned), false when the key was present and the argument value discarded. Not [[nodiscard]]. There is no path that reports an allocation failure, so a true here does not prove the memory was validly obtained

Examples

Illustrative — no call site for this exists in the repository. Container/Map.h is included by Engine/Test/UnitTestCollection.cpp and by nothing else in Engine/ or Applications/; the MapTest fixture in Engine/Container/Map.cpp is the only code that exercises it.

hbe::Map<int, MeshHandle> byId;

byId.Insert(10, a);                        // first entry: no shift at all
byId.Insert(20, b);                        // appended after 10: still nothing to shift
if (!byId.Insert(10, c))
{
        // key present — `c` discarded, a still stands
        // overwrite instead: byId[10] = c;
}

byId.Insert(5, d);                         // both existing pairs move up one slot

for (const auto& entry : byId)
{
        // visited in TCompare order: 5, 10, 20 — ordered iteration is the reason for this type
}

The loop is the payoff, and it is what HashMap cannot offer: its iteration order is slot order and changes on every rehash.
