Remove

member of hbe::Map Engine/Container/Map.h destroy one entry and close the gap — every entry above the hole moves down a slot

Signature

bool Remove(const TKey& key);

Function description

Binary-search for the key; return false if it is absent. Otherwise destroy the pair in place with entries[idx].~Pair(), then walk the remaining entries down one slot each — new (&entries[i - 1]) Pair(std::move(entries[i])); entries[i].~Pair(); — decrement count, and return true.

There is no tombstone here and no gap left behind: this is a sorted array, so closing the hole is the only way to keep the ordering meaningful. The cost is the mirror image of Insert's — O(n) moves below the removed entry, free if the entry was the last one. The capacity is not reduced, and nothing in this class releases memory short of the destructor, so removal never gives room back.

Every iterator, pointer and reference at or above the removed slot is now wrong, and this container will not catch you using it. The entries that moved down changed address; the slot they left holds a destroyed object. Map's Iterator::operator* is a bare return *ptr; with no state check — unlike HashMap's iterator, which asserts that the slot is still Occupied — so reading through a stale one here is a silent read of destroyed memory, not a stop. And the forward-iteration trap is specific: after removing the entry the iterator sits on, the entry that was next has moved back into the slot the iterator already passed, so a plain ++ skips it.
There is no removal by iterator and none by predicate. The only key this function accepts is a key; selective removal means collecting keys first. Clear is the bulk path, and unlike removal one by one it costs O(n) once rather than O(n) per entry — a map being emptied in pieces is quadratic movement for no reason.

Parameters

ParameterTypeRequirement
key const TKey& Comparable under this map's TCompare, and ordering-stable since position, not hash, is what locates it: a key whose comparison result changes after insertion is unreachable, and an unreachable key can be neither read nor removed — its memory is only reclaimed by Clear or the destructor

Return value

TypeWhat you get
bool true when an entry was destroyed, false when no key compared equal. Not [[nodiscard]]. Size() drops by one on the true path; Capacity() never changes

Examples

Illustrative — no call site for this exists in the repository; see the note on Insert.

if (byId.Remove(staleId))
{
        // every entry above the one removed now lives one slot earlier
}

// Selective removal done the only safe way: decide first, erase after.
hbe::Vector<int> doomed;                       // see ../Vector/index.html for this container

for (const auto& entry : byId)
{
        if (entry.value.IsStale())
        {
                doomed.PushBack(entry.key);
        }
}

for (const auto key : doomed)
{
        byId.Remove(key);
}

// Or, when the whole map is going anyway — one pass instead of n of them:
byId.Clear();                              // destroys every pair, keeps the buffer and capacity

Two notes on that shape. The keys are gathered while iterating and erased afterwards, because erasing mid-walk invalidates the iterator the loop is standing on; and each erase inside the second loop is another O(n) shift, which is acceptable for a handful of doomed keys and is the wrong tool for a map being halved.
