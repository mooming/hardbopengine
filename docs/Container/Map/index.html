Map

Engine/Container/Map.h namespace hbe template <typename TKey, typename TValue, class TCompare = std::less<TKey>, class TAllocator = DefaultAllocator<uint8_t>> final a sorted array of key-value pairs searched by binary search — not a tree, and that choice is the whole design

Class description

Map keeps one buffer of Pair objects in key order. Lookup is a binary search (FindIndex) comparing in both directions — compare(stored, sought), then compare(sought, stored), with equality being "neither is less". Insertion finds its slot with LowerBound and shifts the tail up; removal shifts the tail back down. Ordered iteration is a plain pointer walk, lookups are cache-linear, and there are no nodes and no per-entry allocation anywhere.

What that buys and costs is the same fact seen twice: O(log n) lookups with no pointer chasing, and O(n) element movement on an insert or remove that is not at the end. Keys arriving in order make this the best container in the module; keys arriving in the middle make it the worst.

Growth is invisible: a full buffer doubles through the private Grow, from DefaultCapacity = 4 upward, exactly — no power-of-two rounding, because indexing here is a comparison search rather than a mask. There is no Capacity() and no Reserve(), so the buffer a map ends up with is a result of how its keys arrived and cannot be stated in advance. That absence is the sharpest difference from HashMap, and it means the growth cannot be prevented from the outside either.

Neither move operation carries the comparator. The move constructor and move assignment exchange entries, count and cap and nothing else: compare and allocator are default-constructed in the destination. A map that was sorted by one ordering is therefore reinterpreted by a default-constructed TCompare — identical behaviour for std::less, and a silently broken search for any comparator that was seeded, reversed, or configured: the binary search then runs over an array that is not ordered under it, and reports "not found" for keys that are present. Memory is the smaller problem, though it has the same shape: the destination frees the adopted buffer with the allocator it constructed, not the one that allocated it. Nothing copied here can be fixed by std::move being spelled correctly — see Memory: allocators.
ConstIterator is using ConstIterator = Iterator; — an alias, not a distinct type, unlike HashMap's. The practical effect: a ConstIterator obtained from a const Map is an ordinary iterator holding a mutable Pair*, and copying it into a non-const local gives access to Pair& through the non-const operator*. Const-ness of the container does not survive a copy of its iterator. Read that as: this class does not enforce read-only iteration, so do not rely on the alias name for it.

Template parameters

ParameterKindWhat it must satisfy
TKey typename Copy-constructible for two of the insert overloads, move-constructible for the third, and comparable under TCompare. It is stored inline in the pair array, so a key whose ordering changes while it is in the map cannot be found, removed or overwritten — and nothing in the type system stops that
TValue typename Default-constructible and assignable: a new slot is built as Pair{key, TValue{}} and the caller's value is assigned in afterwards. Also move-constructible, because growth and both shift operations move pairs from slot to slot
TCompare class, defaults to std::less<TKey> A strict weak ordering, callable both ways as compare(a, b) and compare(b, a), returning something testable. Equality is derived from it, so an ordering that is inconsistent — reflexive, non-transitive, or comparing by a field that changes — produces a table binary search cannot trust rather than a compile error. Held by value, and never moved or swapped: see the hazard above
TAllocator class, defaults to DefaultAllocator<uint8_t> allocate(count) / deallocate(pointer, count), with count in bytes — this container computes sizeof(Pair) * capacity itself and reinterpret_casts the result to Pair*, so the only alignment guarantee is the one a byte allocation carries. Never exchanged by a move

Members this class does not have, listed because the shape of HashMap invites the assumption. The old module page described Map as "the same interface pattern as HashMap"; the method set is narrower than that, which is why it is spelled out here rather than left to inference.
