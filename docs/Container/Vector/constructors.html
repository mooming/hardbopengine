constructors

member of hbe::Vector Engine/Container/Vector.h 4 overloads + 1 deleted start empty or state a capacity — growth from here on is the container's decision, not yours

Signature

Vector(const Vector&) = delete;

Vector() noexcept;                                     // allocates nothing
explicit Vector(TIndex initialCapacity);              // capacity exactly this, never rounded up
Vector(std::initializer_list<TElement> list);         // reserves list.size(), then PushBack
Vector(Vector&& rhs) noexcept;                         // steals three fields, zeroes rhs

Function description

Unlike Array, which sizes itself to a number of elements, these constructors set a capacity. A default-constructed Vector allocates nothing at all — count, capacity and data are zero, null — and the first PushBack is what takes the first buffer, of DefaultCapacity = 4 elements. The explicit Vector(TIndex) form calls Reserve with your number, and because Reserve only refuses when the request is at or below the current capacity, the capacity you get is the number you passed: not rounded to a power of two, not clamped to a minimum.

The std::initializer_list form reserves list.size() and then copy-constructs each value through PushBack, so TElement must be copy-constructible for it, and no growth path runs — capacity already equals the element count when the loop starts. Zero-size lists allocate nothing.

Copy construction and copy assignment are both deleted, matching the rest of the module: nothing duplicates a buffer without being told to. The copy deleted here is the one you meet first in a compile error from a std::vector-shaped habit, and there is no substitute member — to copy a Vector you build one and fill it.

The move constructor steals the buffer and leaves the allocator behind. Its member list is count, capacity, data; allocator is default-constructed, and a DefaultAllocator records the allocator id current at that moment. So after auto v2 = std::move(v1);, the buffer allocated under v1's scope is freed under v2's, and v1 keeps its own allocator with nothing left to free. The same applies to move assignment, which additionally guards this != &rhs because it destroys and frees the destination first. Moving a vector whose memory is pinned to a named pool is where this stops being theoretical; see Memory: allocators and Swap, which has the same property.

Parameters

ParameterTypeRequirement
initialCapacity TIndex (int) Elements of room wanted, taken exactly. Zero or negative allocates nothing and leaves the vector to grow on first push — the guard is newCapacity <= capacity, so a negative request is silently a no-op rather than an error
list std::initializer_list<TElement> Initial values in order. Needs TElement copy-constructible; it does not need default construction, assignment or comparison
rhs Vector&& The vector to take storage from. After the call it is empty with zero capacity — unlike Array, whose move is a swap and leaves the source holding the destination's former contents. It keeps its own TAllocator object
(deleted overload) const Vector& Copy construction and copy assignment are both removed; a third type in this module, std::vector, is what a caller who genuinely wants a copy reaches for — see HSTL

Return value

A constructor has no return value. What you can observe afterwards is Size() — 0, or the list's length — and Capacity(), which is 0 for the default form, the number you passed for the sized form, and the list length for the list form. A failed allocation inside Reserve is not reported: see that page.

Examples

Illustrative — no call site for this exists in the repository. Vector.h is included by Engine/Test/UnitTestCollection.cpp and by nothing else in Engine/ or Applications/: the Vector members in Engine/Math/Transform.h and Engine/String/String.h are std::vector. Neither header includes Container/Vector.h, both include HSTL/HVector.h — which includes <vector> — and the methods called on those members are push_back, erase and cbegin, none of which hbe::Vector declares. Worth knowing before copying an example from either file.

hbe::Vector<Light> lights;                    // nothing allocated yet; Size() == 0, Capacity() == 0
lights.PushBack(a);                          // first buffer: exactly 4 elements (DefaultCapacity)

hbe::Vector<Light> batch(64);               // Capacity() == 64, Size() == 0, one allocation
batch.PushBack(a);                           // no allocation: the reserved room is used

hbe::Vector<Light> defaults({a, b, c});     // Capacity() == 3, Size() == 3, one allocation

The last two forms are the point of this container's construction: capacity stated up front, so the pushes that follow do not reallocate and no element address changes underneath a caller who is already holding one.
