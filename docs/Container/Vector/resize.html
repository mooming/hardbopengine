Resize

member of hbe::Vector Engine/Container/Vector.h noexcept change the element count; the buffer follows only when the new count needs more room than it has

Signature

void Resize(TIndex newSize) noexcept;

Function description

Two branches and one assignment. Shrinking (newSize < count) destroys the elements from newSize up and leaves the buffer alone. Growing (newSize > count) calls Reserve with the new count — which does nothing if the existing capacity already covers it — and then default-constructs each new slot. Finally count = newSize;.

This is a different contract from Array::Resize, and the difference is the reason two containers both called "dynamic array" exist. Array allocates exactly the element count and so reallocates on every size change, reporting a failed allocation and keeping its old state; Vector reallocates only when capacity runs out, keeps its capacity when you shrink, and says nothing at all when an allocation fails. Where a size is decided once and must not move, the Array contract is the one that fits; where a count oscillates, this one avoids the repeated allocation.

Growing within the existing capacity is the case worth remembering: Reserve returns early, no allocation happens, no element moves, and every pointer and reference into the vector stays valid while new elements appear. The same call with a count above capacity moves every element and invalidates all of them. The two behave identically through the return value, which is void.

Shrinking does not release memory. Elements above newSize are destroyed, but capacity and data are untouched, so the buffer — possibly far larger than the new count — stays allocated until the vector is destroyed. There is no shrink-to-fit here: the way to hand the memory back is v.Swap(empty); as shown on Swap.
A negative newSize is not diagnosed, and here the damage starts immediately. The shrink branch is taken (newSize < count), and its loop begins at the negative index: data[i].~TElement() is called outside the buffer before count is even considered. That is undefined behaviour on the call itself, not a recoverable state. Even where the loop happens to run zero times, count becomes negative, so Size() reports negative, IsEmpty() reports false and IsValidIndex rejects everything. Validate a count that came from a file, a packet or a subtraction before passing it here.

Parameters

ParameterTypeRequirement
newSize TIndex (int) Element count wanted, zero or greater. Growing above the current capacity requires TElement to be default-constructible — and, for the elements that move, move-constructible; a count within capacity requires only default construction. A count equal to Size() changes nothing in either buffer or element

Return value

void, and unlike Array::Resize there is no failure-with-old-state case to detect: a failed allocation inside the growth is unchecked, so this either appears to work or corrupts. Size() after the call tells you the count it recorded, and Capacity() tells you whether a reallocation happened.

Examples

Illustrative — no call site for this exists in the repository; see the note on the constructors.

hbe::Vector<Light> lights(8);       // Capacity() == 8, Size() == 0
lights.Resize(3);                         // 3 default-constructed elements, still Capacity() == 8

auto& first = lights[0];
lights.Resize(8);                         // within capacity: no allocation, `first` is still valid
lights.Resize(9);                         // above capacity: Reserve(9), so Capacity() becomes exactly 9

lights.Resize(2);                         // elements 2..8 destroyed; Capacity() is still 9
lights.Size();                            // 2 — the memory for the other seven is still allocated

The asymmetry in the middle four lines is the whole page: growth that fits the capacity is free and changes no address, growth that does not is a move of every element. The last two lines are the other half — a shrinking resize costs the destructors and nothing else.
