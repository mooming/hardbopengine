Reserve

member of hbe::Vector Engine/Container/Vector.h noexcept buy room up front so nothing reallocates later — and the one way this container can take memory

Signature

void Reserve(TIndex newCapacity) noexcept;

Function description

Returns immediately when newCapacity <= capacity. Otherwise it allocates a buffer of exactly newCapacity elements, move-constructs each live element into the same slot number of the new buffer and destroys the source right after its move, returns the old buffer to the allocator, then adopts the new pointer and capacity.

The capacity you ask for is the capacity you get. There is no rounding to a power of two as in Deque::Reserve and no minimum as in HashMap's — Capacity() reports the number you passed. That makes this the function to call when a caller has already worked out the room it needs, which is also what stops the next PushBack from deciding anything: a vector at capacity grows by max(DefaultCapacity, capacity * 2), so stating a ceiling here is the difference between one allocation you chose and several that chose themselves.

It only ever grows. A request at or below the current capacity is a no-op, and there is no counterpart that releases unused capacity — Resize to a smaller count destroys elements but keeps the buffer, so the memory comes back only when the vector is destroyed or swapped against an empty one.

A failed allocation is not checked, and the failure is a crash rather than a no-op. The returned pointer is used unconditionally: the very next statement is new (&newData[i]) TElement(...), and for an empty vector — where the copy loop is skipped — data becomes the null pointer while capacity becomes the requested size, so Capacity() reports room that does not exist and the next push writes to address zero. Contrast Array::Resize, which tests the pointer, asserts and keeps its old state. Nothing in this function can tell you it failed, so a caller that cannot afford this either reserves early enough that the allocator has not fragmented, or uses Array and checks Size after every resize.
Every iterator, pointer and reference into the vector is invalidated by a real reserve. The elements keep their values — they are moved, not copied — but they live at new addresses, and the buffer they were in is returned to the allocator before the function returns. This includes pointers to elements you did not touch, which is the part that surprises: Array::Resize carries the same rule, and the reason both state it is that neither can help it. An element whose address escapes the container does not belong in a container that reallocates.
noexcept plus a move that can throw is a terminate, not an exception. The element loop is new (&newData[i]) TElement(std::move(data[i])) inside a function that promises not to throw. An element type with a throwing move constructor cannot be held by this container safely; the type trait std::is_nothrow_move_constructible is the one to consult before you find out at runtime.

Parameters

ParameterTypeRequirement
newCapacity TIndex (int) Element slots wanted, counted in elements rather than bytes — allocate is called with this number directly against the allocator's own value type. Anything at or below the current Capacity(), including a negative number, is accepted and ignored. There is no upper bound and no check that the allocation succeeded

Return value

void, with nothing to inspect in the failure case: the only honest post-condition is Capacity(), and after a failed allocation it reports a capacity that the buffer does not have. If the call did nothing — the request was at or below the current capacity — no reallocation happened and every address in the vector is still good; comparing against Capacity() before and after tells you which case you are in.

Examples

Illustrative — no call site for this exists in the repository; see the note on the constructors for why the engine's Vector-shaped members are not this class.

hbe::Vector<Light> lights;
lights.Reserve(256);                     // one allocation, Capacity() == 256
lights.PushBack(a);                       // no reallocation: the reserved room is used

auto* first = &lights[0];                // a pointer into the buffer, taken while Size() == 1
lights.PushBack(b);                       // fine: capacity is not reached, nothing moved

lights.Reserve(512);                     // first is now dangling; Capacity() == 512
lights.Reserve(64);                      // no-op: smaller than the capacity, buffer untouched

The pair at the end is the two behaviours worth remembering: a larger request moves everything, a smaller one is ignored. Neither can be observed from the return value, because there is none.
