Module Index / Log

Log

namespace hbe Engine/Log 5 headers, 3 sources asynchronous logging on the task system's IO stream: producers format and enqueue, one drain thread writes the file and the console

Module description

A log statement formats on the thread that wrote it and returns; a drain task on the IO task stream renders the queued lines and writes them twice — to the log file and to the engine console. Lines carry a category and a level, which is how one subsystem is silenced without editing its call sites. The behaviour — double buffering, category rules, output destinations — is docs/LoggerGuide.md; this site is the surface you call, one page per class and per method name.

There are two ways to emit a line and one way to receive them. SimpleLogger (bound category and level, obtained from Logger::Get(category, level)) is what call sites use; Logger::AddLog is what it forwards to. Everything lands in a LogLine in a queue, and ProcessBuffer turns a batch of them into text. LogUtil supplies the elapsed-time clock and the two formatters; PrintArgs is the fallback print that bypasses this entire system.

Only the helpers are engine-free. LogUtil touches no Engine, so a process that never built one can still format timestamps and level names. The sink is the opposite: AddLog calls Engine::Get() and GetTaskSystem() for the thread name, the console destination PrintStdIO calls Engine::Get() again, and LogLine's long-message path needs the memory manager. The one kind of logging that works with no engine is the emergency print — taken whenever Logger::instance is null, which is before construction and after destruction — and it goes to standard output or standard error, never to the log file.
Do not confuse this with Engine::Log. The engine has a second, older pipeline of its own — Log / LogError, gated by ENGINE_LOG_ENABLED, writing a separate file under its own mutex. It takes an ELogLevel argument and is otherwise unrelated to this module; see Engine.

Module variables

None exposed. Sizing comes from Config and behaviour switches from BuildConfig.h; what matters is which of them any code actually reads, because a constant nobody consults is a wish rather than a setting.

Config::LogLineLength (1024) LogLine.h, LogLine.cpp, Logger.cpp Inline body capacity, the short/long threshold (size >= 1023) and, doubled, the size of the render buffer a line is formatted into — hence the ~2000-character ceiling on a written line

LOG_ENABLED One place: the top of AddLog Set to 0 and the sink returns before anything else runs. It does not silence the emergency print, which is compiled outside this gate, nor PrintArgs
LOG_FORCE_PRINT_IMMEDIATELY Logger.cpp: the ImmediateLog helper and one branch of AddLog Every line is printed at its call site and nothing is queued, so the file, the drain task and the console destination go unused — the option that keeps output in hand when a crash is about to discard the queue
LOG_BREAK_IF_WARNING, LOG_BREAK_IF_ERROR Logger.cpp: two branches of AddLog, and the #if that decides whether ImmediateLog is compiled at all Print the line immediately, debugBreak(), and return — so at 1 the log file stops containing warnings (respectively errors), because those lines never enter the queue. Note the guard: it is the macro alone, not __DEBUG__. BuildConfig.h annotates both "(debug only)", but setting either to 1 makes a Release build trap; nothing restricts it to a debug configuration
PROFILE_ENABLED Logger.h and Logger.cpp around ReportMemoryConfiguration; LogLine.cpp around the two log-count statistics Whether the memory report is part of the type at all, and whether line counts are recorded. See Config: BuildConfig for the wider reach of this switch

Two thresholds are runtime rather than compile-time and are worth knowing about because they are the ones that silently eat output: the Log.Level parameter, created on the first AddLog call and defaulting to Info, and any per-category filter installed with SetFilter — for example Log.TaskSystem, which the task system sets to Warning and compares with >, dropping its own Info lines. Both are configuration parameters.

Module functions

This module's free functions are LogUtil (four, in hbe::LogUtil, one definition shared by the whole program) and PrintArgs (two templates, in an unnamed namespace at global scope, one copy per translation unit that includes the header). Two namespace-scope aliases are declared beside the class in Logger.h: hbe::TLog for Logger::SimpleLogger and hbe::LogStream for the 131072-byte stream a callback writes into — listed with Logger's non-member declarations.

Coverage

GapDetail
Two constants that are read by nothing Config::LogMemoryBlockSize and Config::LogNumMemoryBlocks exist in the header and influence no code. They are documented above rather than dropped, since a reader who finds them will otherwise assume the logger's pools are sized by them — as this page previously did
Helpers the deleted guide invented LogUtil::GetLogLevelName and LogUtil::GetCurrentTimeString do not exist and never did; the real names are GetLogLevelString and GetTimeStampString. There is no wall-clock string anywhere in the module — the log clock is steady_clock and every timestamp is elapsed time
Async machinery Double buffering, the drain task's scheduling on the IO stream, and how the stream parks between drains are design and belong to docs/LoggerGuide.md and Core: TaskStream. The pages here state what a caller can observe; ProcessBuffer is the boundary
File-local helpers, deliberately undocumented as API Logger.cpp's unnamed namespace holds ImmediateLog, EmergencyLog, DrainGuard, MaxFlushWaitMs (1000) and FlushPollPeriodMs (10). They cannot be called from outside that translation unit, but they decide behaviour a caller depends on, so they are described on the pages that depend on them — Flush, IsDrainTaskRunning
Examples Per-method examples are on the method pages, quoted from real call sites with the file named. The one that most often decides whether a first-time caller gets what they expect is SimpleLogger::Out: the callback runs on the producing thread, before the call returns, which is what makes [&] captures sound and what charges the formatting to your frame
Test-only logging Engine/Test/TestCollection.cpp logs through TLog and through Logger::Get(name, level); the test framework's own reporting is Test's subject
