OutFatalError

member of hbe::Logger::SimpleLogger Engine/Log/Logger.h 2 overloads const noexcept one line to the log, then a trap — this call does not return to a running program

Signature

void OutFatalError(const TLogFunction& logFunc) const noexcept
{
        Out(ELogLevel::FatalError, logFunc);
}

void OutFatalError(const char* text) const noexcept
{
        OutFatalError([text](auto& ls) { ls << text; });
}

Function description

The call itself is the ordinary one: Out(ELogLevel::FatalError, …). Everything that makes it fatal is in AddLog, which enqueues the line and then does this: 

if (unlikely(level >= ELogLevel::FatalError))
{
        Flush();
        debugBreak();
        Assert(false);

        return;
}

So the sequence is: enqueue, drain the queue on this thread (with the one-second bound that Flush carries), trap, and — after a trap that does not terminate — assert. The IO stream is never woken, because the flushing has already been done here.

debugBreak() is not a debug-build facility: it is __builtin_trap() on Clang and GCC and __debugbreak() on MSVC (OSAL: Intrinsic), compiled into every configuration including Release. Treat this function as "write this line, then end the process" — which is what the engine's allocator and configuration callers intend, even where their code reads otherwise.

Every call site in the engine is followed by a return that will not run. The convention is log.OutFatalError(…); return; — ConfigSystem::Register does exactly that for a duplicated key, and MultiPoolAllocator for a pointer it does not own. The return is unreachable once the sink reaches its trap, so any cleanup written after the call is dead code. If the process must survive the condition, this is the wrong call: use OutError and handle the failure.
Suppress the line and you suppress the crash. The threshold and filter checks in the sink happen before the fatal branch. A Log.Level parameter set to MAX, or a category filter that returns false for FatalError, makes the whole call a no-op: no enqueue, no flush, no trap, and execution continues through the return the caller thought it would never reach. The opposite hazard is the one that bites harder — if the drain thread is wedged, the bounded flush gives up after a second and the line is still in memory when the trap fires, so the message you wrote for the post-mortem is in standard error only (the give-up report), not in the file.
Before a logger exists, this function is merely a print. With Logger::instance null the call falls to the emergency path, which writes to standard error and returns normally — no flush, no trap. Same for a process that never builds an Engine. A fatal report emitted during early startup therefore reports and continues, which is the one case where the return after it does execute.

Parameters

ParameterTypeRequirement
logFunc const TLogFunction& Runs on this thread before anything else happens, provided the threshold and filter let the line through. It is the last formatted output this thread produces, so anything it needs has to be captured now
text const char* NUL-terminated literal, captured as a pointer. Keep it short: it shares the line's 1023-character inline budget, and a body beyond roughly 2000 characters is cut before it is written (the render limit)

Return value

void, and there is no path that returns normally while the logger is live and the line survives its filters: the trap sits between the flush and the function's end. Write it as the last statement of a failure branch, not as a message followed by recovery.

Examples

A configuration key registered twice — reported, then the process ends:

From Engine/Config/ConfigSystem.cpp

if (unlikely(byteParams.find(name) != byteParams.end()))
{
        auto log = Logger::Get(GetName());
        log.OutFatalError([name](auto& ls)
        { ls << "The key " << name << " is duplicated. It's not allowed strictly."; });

        return;   // unreachable: the sink traps before AddLog returns
}

The same shape in the allocator, where the message walks its own banks to explain the mismatch:

From Engine/Memory/MultiPoolAllocator.cpp

auto index = GetBankIndex(ptr);
if (index >= banks.size())
{
        auto log = Logger::Get(name);
        log.OutFatalError([ptr, this](auto& ls)
        {
                ls << ptr << " is not allocated by this allocator.";
                ...
        });
}

The callback there enumerates the pool's banks while formatting — legitimate, since it runs before the trap, and a reminder that whatever evidence you want in the record has to be assembled inside this callback. Nothing after the call runs, and the flush that precedes the trap is the last thing the logger does for you.
