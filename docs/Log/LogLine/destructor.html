~LogLine

member of hbe::LogLine Engine/Log/LogLine.h noexcept frees the heap body if there is one; for an inline line it does literally nothing

Signature

~LogLine() noexcept;

Function description

if (likely(!isLong)) return;

Assert(longText != nullptr);
auto& mmgr = MemoryManager::GetInstance();
mmgr.SysDeallocate(longText, longTextSize);

Two paths, selected by isLong. An inline line returns immediately — no free, no bookkeeping, no visit to the memory manager. That asymmetry is what makes the move constructor safe to write and cheap for the common case, and it is why a batch of ordinary lines costs one call each to destroy and nothing else.

A long line hands longText back to MemoryManager::SysDeallocate together with longTextSize — the same size + 1 the constructor asked for, so a deallocation can never disagree with its allocation. Note which allocator that is: the system allocator, not the logger's pools, so a long line's memory does not follow the pool the queue lives in.

Producer and reclaimer are usually different threads, by design. The allocation happens on whatever thread logged; the free happens when ProcessBuffer calls swapBuffer.clear(), which is the log thread. Every long line in the engine is therefore a cross-thread free. That is legal for the system allocator, but it does mean the logger's own pool statistics see neither side of the transaction.
There is one state this destructor cannot survive: isLong true with a pointer that was never assigned. The guard is an Assert — Debug and Dev only — and then it frees the value regardless. A line left in that state by the null-text branch of the producing constructor is thus freed as though it were valid, which is a deallocation of an indeterminate address. No logger code produces that state today; it is a hazard for anyone constructing a line directly.
The manager has to be alive. MemoryManager::GetInstance() is called unconditionally on the long path, so a long line destroyed after the memory manager — a static holding one, or a queue emptied during teardown in the wrong order — reaches for a manager that is gone. In an ordinary run this cannot happen: the last drain is inside ~Logger, and Engine declares its members so that the memory manager outlives the logger.

Parameters

None.

Return value

void, from a noexcept destructor: SysDeallocate is expected not to throw, and if it did the process would terminate rather than unwind through a container holding lines. There is no report of a mismatch between a size and an allocation, because nothing here checks one beyond the null test.

Examples

Destruction is never explicit. Lines die when the queue they live in gives up its storage — the drain clearing its batch:

The first clear() destroys every line in the batch, which frees each long body while the second keeps the rendered text alive until both destinations have consumed it. Ordering matters here: had the lines gone after the write instead, the rendered strings would already have copied the text — they do, which is why this is a copy rather than a view — so the order is safe either way, but only because the render step makes a copy into HString.
