FlushBuffer

member of hbe::Logger private const noexcept the one funnel: hand a batch of finished lines to every installed destination, in order

Signature

// private:
void FlushBuffer(const TTextBuffer& buffer) const noexcept;

Function description

for (auto& func : flushFuncs)
{
        Assert(func != nullptr);
        func(buffer);
}

Each element of flushFuncs receives the whole batch, in registration order, which is the order the constructor installed them: WriteLog (the file) first, then PrintStdIO (the console). This is the function that answers "where do log lines go" — there is no public way to install a third, so a custom destination means either a fork of this class or reading the file it writes.

It is const in the sense that it never changes the logger's own bookkeeping; the destinations obviously mutate, an std::ofstream and a console each. The batch is passed by reference and unchanged, so a destination may keep a copy of a line but must not modify the one it was handed.

Three callers, and they are the three ways text can leave this module. ProcessBuffer with a whole drained batch; AddLog's inline path with a single-element thread-local buffer for an error produced on the log thread; and, transitively, the two shutdown calls to ProcessBuffer in StopTask and the destructor. Everything that reaches the file passes through this loop; the emergency and LOG_FORCE_PRINT_IMMEDIATELY paths do not — they write to the C++ standard streams and never appear in the log file.
A destination that throws terminates the process. flushFuncs holds std::function, which carries no noexcept, while FlushBuffer itself is noexcept. An exception escaping either output function therefore propagates out of a function promised not to throw — std::terminate, with the batch half-written: file written, console not, and the caller in ProcessBuffer never reaching its needFlush clear. Likewise a null entry is diagnosed by Assert, which is Debug and Dev only (see Core: Debug) and then calls it anyway.

Parameters

ParameterTypeRequirement
buffer const TTextBuffer& (HVector<HString>) The finished lines, already prefixed, in output order; an empty buffer is legal and calls each destination once with nothing to write. It must stay alive for the whole call — each function receives the same reference in turn, so a temporary is fine but destroying it between two destinations is not

Return value

void. No destination reports anything back: a failed file write (WriteLog checks nothing) and a console that discarded the line (PrintStdIO checks nothing) are both successes here. This is the layer where a caller's assumption "it is on disk" is either honoured or silently dropped, and it cannot tell you which.

Examples

The inline single-line write — an error produced by the log thread, which cannot safely queue itself, so it builds a one-element batch on the spot and writes through this function:

From Engine/Log/Logger.cpp

if (unlikely(level >= ELogLevel::Error && std::this_thread::get_id() == threadID))
{
        AllocatorScope memAllocScope(MemoryManager::SystemAllocatorID);

        thread_local TTextBuffer tmpTextBuffer;
        tmpTextBuffer.reserve(1);
        ...
        tmpTextBuffer.emplace_back(text.c_str());

        FlushBuffer(tmpTextBuffer);
        tmpTextBuffer.clear();

        if (unlikely(level >= ELogLevel::FatalError))
        {
                debugBreak();
        }

        return;
}

Note the allocator scope this caller opens: the batch's HString is built from the system allocator rather than the logger's pool, because a thread that is already inside the drain must not take from the pool the drain is writing. The buffer is thread-local and cleared rather than destroyed, so the reserve happens once per thread.
