IsDrainTaskRunning

member of hbe::Logger Engine/Log/Logger.h const noexcept [[nodiscard]] whether a drain task exists — defined in the header, one acquire load and nothing else

Signature

[[nodiscard]] bool IsDrainTaskRunning() const noexcept
{
        return isRunning.load(std::memory_order_acquire);
}

Function description

The only logger method with a body in the header. It loads isRunning, which StartTask sets and StopTask clears, and returns. No lock, no task-system call, no memory allocation.

Its reason for existing is a specific decision at shutdown: StopTask waits for the drain task to acknowledge, so calling it when none is running blocks forever. The header says this in as many words — the answer "lives here rather than in a flag elsewhere" because a caller weighing StopTask against a plain Flush has to ask it first.

The header adds a thread-safety claim, and the code supports it: a single acquire load with no other side effect is readable from any thread, and the header goes as far as naming a signal handler. The engine's is a real caller of exactly that kind.

Three similar questions, three different answers. This one is not "is the queue empty", which is needFlush and is private. It is not "is a drain in progress right now" either — that is isDraining, the buffer claim, also private. And it is not "does the logger exist": Engine::IsLoggerReady is set by the constructor and stays true whether or not a drain task was ever started. The one question this answers is whether StartTask has run and StopTask has not.
true does not prove the drain is capable of running. isRunning is a flag, not a poll of the task registry. In the failure branch of StartTask — where the registry could not track the task — the flag was already set and is never cleared, so this reports true while nothing will ever drain, and a caller that trusts it picks StopTask over Flush and waits on a task nobody owns. Symmetrically, a drain task that exists but is starved still answers true; that is the case Flush survives by timing out.

Parameters

None.

Return value

TypeWhat you get
bool true between StartTask and StopTask, false before and after. [[nodiscard]]: the value is a decision input, so reading and discarding it is always a bug. Treat it as "has logging been started", never as "will my line be written"

Examples

The one call site, deciding how to get a crash report out:

From Engine/Engine/Engine.cpp

void SignalHandler(int sigNum)
{
        auto& engine = Engine::Get();
        if (engine.GetLogger().IsDrainTaskRunning())
        {
                engine.GetLogger().StopTask(engine.GetTaskSystem());
        }
        else
        {
                engine.GetLogger().Flush();
        }
        ...
}

The pairing is the pattern: stop the drain when there is one to stop — which is also the path that flushes and closes the file — and flush directly when there is not, because WaitForFlush only drains inline once it has established that no drain task can run.
