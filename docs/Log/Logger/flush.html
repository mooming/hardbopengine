Flush

member of hbe::Logger Engine/Log/Logger.h noexcept the only public way to ask for text on disk — and it is bounded, not guaranteed

Signature

void Flush() noexcept;

Function description

Two lines of dispatch, and the whole contract is in the question they ask:

if (std::this_thread::get_id() == threadID)
{
        ProcessBuffer();
        return;
}

WaitForFlush();

On the log thread, Flush is the drain: it writes everything queued, right now, and returns. Anywhere else it delegates to WaitForFlush, which polls needFlush every 10 ms against a 1000 ms deadline — and which, when no drain task can run (never started, or already stopped), drains inline itself instead of waiting, because then the caller is the only thread that could ever write the queue.

So Flush never merely "requests" a flush: it either performs one or blocks until one has happened. What it does not do is wait forever. If a second passes with the queue still unwritten, it writes a report straight to standard error through the file-local emergency path and returns without draining — deliberately, because draining while a live drain task is running would race on that task's buffers. The design intent, stated in the header, is that a blocked or starved IO thread must not swallow the report that made you flush in the first place.

Returning does not prove your line was written. Three separate ways to leave Flush with text still in memory: the one-second timeout just described; another thread's drain winning the isDraining claim, since a caller that cannot claim it returns having done nothing; and the header's own caveat that the handshake "guarantees an empty queue at some instant, not the caller's own prefix" — a producer that enqueues just after the queue empties can satisfy the wait that you are sitting in. Use Flush where losing a line is survivable (a crash path, a threshold) and never as a checkpoint that says "the file now contains my line".
The cost of this call depends entirely on which thread you are on. On the log thread it is one drain pass — the file write plus the console write for each queued line. On any other thread it is, in the good case, one sleep cycle of 10 ms while the drain catches up, and in the bad case a full second plus an stderr report. Two places inside AddLog call it on an arbitrary producer thread: a FatalError, and a queue that reached Config::LogForceFlushThreshold. A subsystem that logs faster than the drain can write therefore pays a flush every 8192 lines, on the producing thread.
The report on giving up goes somewhere else. It is written to standard error, not to the log file, and it names its own category (Logger) and level (Error). That is the only evidence the drain was alive but unresponsive, and it is not in the file a post-mortem reader opens — capture standard error in any run where a hang matters.

Parameters

None.

Return value

void. No status, no timeout indication, no count of lines written. The only way to detect the give-up case from code is to look at what it produced: an Error line on standard error mentioning the timeout, and a queue that is still non-empty afterwards — and the queue itself is private, so nothing here can tell you that.

Examples

Choosing between stopping the drain and flushing it, from the engine's signal handler:

From Engine/Engine/Engine.cpp

void SignalHandler(int sigNum)
{
        auto& engine = Engine::Get();
        if (engine.GetLogger().IsDrainTaskRunning())
        {
                engine.GetLogger().StopTask(engine.GetTaskSystem());
        }
        else
        {
                engine.GetLogger().Flush();
        }
        ...
}

And the in-module uses, which show how the call is normally reached without being written by hand:

From Engine/Log/Logger.cpp

if (unlikely(level >= ELogLevel::FatalError))
{
        Flush();
        debugBreak();
        Assert(false);

        return;
}
...
if (bufferSize >= Config::LogForceFlushThreshold)
{
        Flush();
}

For a synchronous write you can actually rely on, there are two levers outside this function: log at Warning or above, which makes the drain flush the file stream after the batch (ProcessBuffer), or build with LOG_FORCE_PRINT_IMMEDIATELY set, which removes the queue from the picture entirely and prints each line at its call site — at the cost of the ordering guarantees, since every thread then writes on its own.
