Logger

Engine/Log/Logger.h namespace hbe final 16 methods one queued sink per process: producers format and hand over, one drain thread writes the file and the console

Class description

Logger is the queue between a log statement and its destinations. A producer formats its text into an inline buffer on its own thread, and AddLog appends a LogLine to inputBuffer under inputLock — then returns. A drain task on the IO task stream runs ProcessBuffer, which swaps the queue into swapBuffer, renders each line, and hands the batch to two output functions: the log file and the engine console.

There is exactly one live instance, and the type makes that structural rather than a convention: it is final, its copy and move constructor and assignment are = delete, and its constructor publishes this into the static instance while its destructor clears it. The constructor takes an Engine& because it needs the memory manager to be ready and calls Engine::SetLoggerReady() when it is done — this module has no instance registry of its own; Engine holds a Logger as a member.

The queue is double-buffered, not lock-free. The lock is held only for the emplace and for the swap, so a log statement's cost on a frame-critical thread is the formatting (which happens on the caller, in the caller's callback) plus one short mutex hold.

Two log lines are not one string. A line is category, level, thread name, an instant and text; the prefix is assembled at drain time in ProcessBuffer, not at the call site. That is why a line's timestamp is when it was produced even though the file is written later, and why changing the line format is one function rather than a hunt through call sites.
The log file is truncated when the logger is constructed. The constructor calls outFileStream.open(logPath.c_str()) with the default open mode, which for std::ofstream truncates: relaunching a process discards the previous run's log. There is no append mode, no rotation and no size limit anywhere in this module, so a long-running build grows one file until the disk refuses.

Template parameters

None — Logger is not a template. Its configurable behaviour is the SimpleLogger it hands out and the filter you install with SetFilter, neither of which is parameterised on the logger type.

Thread safety of the entry points

CallFrom a worker threadWhat is held while it runs
SimpleLogger::Out…, AddLog Yes — this is the intended use filterLock for the lookup, released before formatting; then inputLock for the emplace. Formatting and both level checks happen outside every lock
SetFilter Yes filterLock for the map write. Your predicate then runs later, on whatever thread logs, still holding that lock — see the deadlock note below
Flush Yes, but it blocks Either the drain claim (isDraining) if it drains itself, or nothing at all while it polls needFlush every 10 ms for up to a second
Get, GetName, IsDrainTaskRunning Yes Nothing: a pointer read, an interned static, an acquire load. The header states the last is safe from a signal handler, and the engine's signal handler is a real caller
StartTask, StopTask No — one thread, during initialisation and shutdown They write threadID, which is not an atomic, while every producing thread reads it in AddLog and Flush; StopTask also blocks until the drain task acknowledges
ProcessBuffer Only one at a time, by design The isDraining claim for the whole pass, inputLock only for the swap
Whether the log thread is you is decided by a non-atomic field. threadID is an ordinary std::thread::id, written by StartTask and reset by StopTask, and read by AddLog and Flush on other threads. In practice StartTask runs once before any worker exists, so the write is harmless; the exposure is StopTask, which clears it while producers may still be comparing against it. Every other flag in this class is an std::atomic — isRunning, hasInput, needFlush, isDraining — which is what makes this one look unintended rather than designed.
Order is per batch, and the bypasses are visible in the output. Queued lines are written in the order the enqueue lock was won, and a batch is rendered in that order to both destinations. But four paths skip the queue: an Error or worse produced on the log thread itself, a FatalError (which flushes then breaks), the emergency path used when no logger exists, and the LOG_BREAK_IF_WARNING, LOG_BREAK_IF_ERROR and LOG_FORCE_PRINT_IMMEDIATELY builds. Those are interleaved with queued output by whichever thread got there first, so two lines that look adjacent in the file may have crossed paths through different mechanisms.
A category filter that logs is a deadlock, and nothing detects it. AddLog calls your predicate while holding filterLock, and std::mutex is not recursive. A filter that calls SetFilter deadlocks the producing thread outright; a filter that logs at a level the filter itself would reject escapes only because the rejection happens before the lookup. Decide filters from level alone, without I/O, as the real example does.

GapDetail
Four helpers that decide behaviour but are not API Logger.cpp's anonymous namespace holds ImmediateLog (compiled only when one of the three immediate macros is set), EmergencyLog (the no-logger path), DrainGuard (the isDraining claim) and the constants MaxFlushWaitMs = 1000 / FlushPollPeriodMs = 10. They are described on the pages that depend on them and are not callable from outside the translation unit
Memory verification bookkeeping StartTask and StopTask retag the logger pool's owning thread under MEMORY_VERIFICATION_ENABLED, which is a build configuration switch, not this module's surface. See Memory: AllocatorProxy
How the drain task is scheduled StartTask creates a task and enqueues a subtask on the IO stream; what happens after that — the stream's wake-up, the task's re-enqueue policy, its affinity — is Core: TaskSystem
Who constructs and starts the logger Engine holds a Logger member built with ("./", "hardbop.log"), calls StartTask under EInitLevel::Logger. Its signal handler is the only caller of StopTask in the repository; a clean shutdown never stops the drain task, so the last batch is written by the destructor. That wiring belongs to Engine
The other logging pipeline Engine::Log / Engine::LogError write a separate file through their own mutex and are gated by ENGINE_LOG_ENABLED, not by this class. They take an ELogLevel argument, which is the only thing they share with this module. See Engine
