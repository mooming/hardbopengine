PrintStdIO

member of hbe::Logger private static noexcept destination two: the console, one line at a time, through the engine — which makes the engine a dependency of draining

Signature

// private:
static void PrintStdIO(const TTextBuffer& buffer) noexcept;

Function description

auto& engine = Engine::Get();

for (auto& logText : buffer)
{
        engine.ConsoleOutLn(logText.c_str());
}

The second function installed into flushFuncs, so the console sees a batch after the file does. It is static — the only one of the two destinations that does not need the object — because it touches no logger state: it goes straight to the process's engine and hands over one line at a time.

Engine::ConsoleOutLn is std::lock_guard on the engine's console mutex followed by std::cout << str << std::endl (Engine). Per-line locking, per-line newline: the drain does not hold the console for the whole batch, and the text arrives exactly as ProcessBuffer rendered it.

Draining requires a live Engine, and this is the call that makes it so. Engine::Get() asserts the instance pointer is non-null — Debug and Dev only — and dereferences it in every configuration. The engine is already needed one layer up, since AddLog itself calls Engine::Get() and GetTaskSystem() for the thread name, and LogLine's long-message constructor needs the memory manager. The practical consequence: a Logger constructed in a process with no engine does not merely lose its console output — the drain reaches this line and dereferences null. Anything that wants logging without an engine has to use LogUtil and write the text itself.
Batch atomicity is per line, so console order can differ from file order. The lock covers one line, which means another thread writing to std::cout directly — the no-logger emergency path, or the LOG_BREAK_IF_* / LOG_FORCE_PRINT_IMMEDIATELY immediate path — can land between two lines of the same batch. The file, written first and by one claimed thread, keeps the batch contiguous. Diffing a console transcript against the log file therefore proves nothing about ordering inside a batch.

Parameters

ParameterTypeRequirement
buffer const TTextBuffer& (HVector<HString>) Finished lines in output order; empty is legal and writes nothing. Only c_str() is passed on, so the string's allocator is irrelevant to this call — but a NUL inside a line ends it here, where WriteLog would have written up to the embedded NUL's length

Return value

void. Whether the console accepted the text is not reported back by Engine::ConsoleOutLn either, so this destination, like the file one, is fire-and-forget: neither a redirect nor a closed standard output changes what the logger does next.

Examples

Installed as an output function in the constructor; never called by name:

From Engine/Log/Logger.cpp

flushFuncs.reserve(2);
flushFuncs.emplace_back([this](const TTextBuffer& buffer) { WriteLog(buffer); });
flushFuncs.emplace_back([](const TTextBuffer& buffer) { PrintStdIO(buffer); });

The consequence of that pairing is the output you actually see: every line appears in the file and on the console, in the same rendering, with the file write first. A build whose console is quiet while the file fills is not filtering — the engine's console path is where to look. A build whose file is empty while the console is busy is the opposite case, and WriteLog explains why nobody notices.
