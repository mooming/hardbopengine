AddLog

member of hbe::Logger Engine/Log/Logger.h noexcept the whole life of a log statement: five ways to be dropped, three to bypass the queue, one to be queued

Signature

void AddLog(StaticString category, ELogLevel level, const TLogFunction& logFunc) noexcept;

Function description

In execution order — and every branch below is a decision a caller can observe in the output:

StepWhat happensIf it stops here
1 Assert(this == instance) — the logger you are calling must be the published one Debug and Dev only; a non-instance logger proceeds silently in Release
2 #if !LOG_ENABLED return; — a compile-time switch, read nowhere else in the repository Nothing is logged at all, except lines from the no-logger emergency path, which is not gated by it
3 AllocatorScope scope(InvalidAllocatorID) — the default-allocator scope is closed for the rest of the call —
4 A null logFunc logs "Null log function!" at Warning under the logger's own category and returns Your line is gone; the replacement is, which is how a bad std::function becomes visible
5 The first call creates a TAtomicConfigParam<uint8_t> named Log.Level defaulting to Info; the line is dropped if level < its value Filtered before your callback runs — the reason callback-shaped logging is affordable
6 The category's filter, if any, is consulted under filterLock Same — see SetFilter for what a filter may and may not do
7 Engine::Get(), GetTaskSystem() and TaskSystem::GetCurrentStreamName() supply the engine, the task system and the thread name No engine instance means no logging: the assert fires in Debug and Dev, and the pointer is dereferenced anyway in Release
8 TLogStream ls; logFunc(ls); — your callback renders into a 131072-byte inline builder, on this thread —
9 With LOG_BREAK_IF_WARNING set: at Warning or above, print immediately, debugBreak(), return The line never enters the queue and never reaches the file
10 With LOG_BREAK_IF_ERROR set: the same from Error up Same
11 With LOG_FORCE_PRINT_IMMEDIATELY set: print immediately, return Every line takes this path; the queue, the drain task and the file are unused
12 If level >= Error and this is the log thread: format into a thread-local buffer, allocated from the system allocator, and write it through FlushBuffer directly The line skips the queue, so it appears ahead of lines queued before it; FatalError additionally calls debugBreak()
13 Otherwise: enqueue a LogLine under inputLock with inputAlloc open as allocator scope, then set hasInput and needFlush —
14 If level >= FatalError: Flush, debugBreak(), Assert(false), return The IO stream is never woken — the flush already happened on this thread
15 If the IO stream exists, wake it —
16 If the queue length reached Config::LogForceFlushThreshold (8192), flush inline A producer that outpaces the drain blocks here
Step 8 puts a 128 KiB automatic object on the calling thread's stack. TLogStream is InlineStringBuilder<Config::LogOutputBuffer> and that builder holds its buffer inline (String: InlineStringBuilder), so every accepted log statement costs the caller a stack frame large enough to hold a whole rendered line — and same object appears again in the no-logger emergency path, and step 12 uses one 128 bytes larger. On a thread created with a platform-default main stack this is invisible; on a worker created with a small stack it is an overflow from a single log call. If you spawn threads outside the task streams, check their stack size before logging from them.
Breaking on a warning is enabled by the macro, not by the build — and it also removes the line from the log. BuildConfig.h annotates LOG_BREAK_IF_WARNING and LOG_BREAK_IF_ERROR as "(debug only)", but the only guard around those blocks is the macro itself (steps 9 and 10): set either to 1 in a Release build and the Release build breaks. Both branches return after debugBreak(), so a warning-or-worse line is printed to standard output by the file-local ImmediateLog and is not queued — with either macro on, the log file stops containing the very lines you were debugging. See Config: BuildConfig.
The thread name in the prefix is whatever the task system recorded for this thread. Step 7 reads TaskSystem::GetCurrentStreamName(), a thread_local value that a stream sets when it runs a task. A thread that never joined a stream — the main thread before the streams start, or a thread you created — yields an empty name, and the line renders as [0:0:0:12][][Renderer][Info] …. It is also the name at the moment of production, which is the right one: the drain thread never appears in the prefix of a queued line.
Two different quantities are compared in steps 12 and 16. The force-flush threshold is a count of lines in the queue — inputBuffer.size() — not a byte total, so 8192 short lines and 8192 long ones trigger it equally. Step 12's test is a thread-identity comparison against threadID, which is why a logger whose drain task was never started still takes the inline path for errors but only for errors.

Parameters

ParameterTypeRequirement
category StaticString The filter key and prefix. Interned, so a const char* argument is looked up in the string table on the first call
level ELogLevel Compared against Log.Level, then against the category filter, then against the Error / FatalError special cases. It selects behaviour, not only text
logFunc const TLogFunction& Called at most once, on this thread, before the enqueue — never later, so anything it captures must outlive the call itself, not the eventual write. Must not be null (step 4) and must not assume it is running on the drain thread. If it allocates through the default allocator it does so with the scope closed to InvalidAllocatorID; what that costs is Memory's contract

Return value

void, and there is no way to learn which of the sixteen steps your line stopped at. A dropped line is indistinguishable from a line that is still queued: both leave the function successfully and both leave the file unchanged. If a call site must know, compare Flush before and after, or filter the category yourself rather than guessing afterwards.

Examples

Direct calls in the engine come from inside the logger itself — a call site has no reason to name a level it can bind once:

From Engine/Log/Logger.cpp

void Logger::StartTask(TaskSystem& taskSys)
{
        AddLog(GetName(), ELogLevel::Info, [](auto& logStream) { logStream << "Logger started."; });
        ...
}

The ordinary call site reaches this function through a bound SimpleLogger — and note that the callback may be a plain literal, which the const char* overloads wrap for you:

From Engine/Renderer/Vulkan/VulkanCapabilities.cpp

static const auto log = Logger::Get("VulkanCapabilities", ELogLevel::Error);
...
log.OutError("Error: cannot query capabilities from a null physical device; leaving capabilities unqueried");

and, when the text has to be assembled from values, the callback form:

From Engine/Core/TaskStream.cpp

const auto log = Logger::Get(name);
...
log.OutWarning([dt = deltaTime](auto& ls) { ls << "Slow DeltaTime = " << dt; });

The capture discipline matters more here than it looks: dt = deltaTime copies, and the engine's other style — [&] — is safe only because step 8 runs the callback before AddLog returns. A std::function stored and handed to a later drain pass would be the bug; this module never does that.
