WaitForFlush

member of hbe::Logger private Engine/Log/Logger.h noexcept the bounded, polled wait behind Flush — 10 ms sleeps against a 1000 ms deadline

Signature

void WaitForFlush() noexcept

Function description

Private: no caller outside Logger reaches it, and Flush is the only thing that calls it. It is a loop over one flag — needFlush, set by every enqueue and cleared by the drain — with a deadline measured from entry.

Each iteration, in order:

  1. Read isRunning with acquire ordering: "is there a drain task at all".
  2. If there is none, call ProcessBuffer — the caller becomes the writer, because nobody else can be.
  3. If the deadline has passed, write a report through the file-local emergency path and return without draining. Two reports exist, and they say different things: one for a drain task that is alive but has not written the queue, one for no drain task at all. Both state that the entries stay buffered.
  4. Otherwise sleep 10 ms and test the flag again.

Both constants are file-local (MaxFlushWaitMs = 1000, FlushPollPeriodMs = 10) and neither is a configuration parameter — you cannot lengthen the wait, and you cannot make it configurable without editing the source. The choice is deliberate: an unbounded wait would let a wedged IO thread swallow whatever report made the caller flush.

The timeout is a report, not a retry, and the give-up path never touches the buffers. After one second the function returns with the queue exactly as it found it. Two consequences a caller can observe: the lines are still in memory, to be written by some later drain or by the destructor — so they are lost only if the process dies first; and the caller has no in-band way to know this happened, because the report goes to standard error under the logger's own category. A run with a stalled drain therefore looks like a run with a slow drain until you read standard error.
With a flag stuck true and no task behind it, every flush costs the full second. The inline drain in step 2 happens only when isRunning is false. In the failure branch of StartTask the flag was set before the task was created and is never cleared, so this loop takes the waiting path, times out, and reports — every time, on every thread, at every Config::LogForceFlushThreshold. See that page's hazard for the message that promises something else.
10 ms is a floor on this call, and the wait is polled rather than signalled. Nothing here blocks on a condition variable, so a waiting thread wakes on its own timer: the drain can finish a microsecond after you sleep and you still pay the remainder. It also means the only thing this costs while waiting is a sleep — no lock is held, and the drain is never slowed by a waiter. Note too that the inline ProcessBuffer in step 2 can be refused by the isDraining claim, in which case the loop simply keeps waiting for whoever holds it.

Parameters

None — it waits for whatever the queue holds at the moment each iteration reads the flag.

Return value

void. Success and timeout are indistinguishable to the caller; only the emergency report on standard error, under the category Logger at Error, records which happened. Since this method is private, the caller in question is Flush, which likewise reports nothing — so no public surface of this module can tell you whether your flush worked.

Examples

Its only call site is the non-log-thread branch of Flush, in the same translation unit:

From Engine/Log/Logger.cpp

void Logger::Flush() noexcept
{
        if (std::this_thread::get_id() == threadID)
        {
                ProcessBuffer();
                return;
        }

        WaitForFlush();
}

void Logger::WaitForFlush() noexcept
{
        const auto deadline = std::chrono::steady_clock::now() + std::chrono::milliseconds(MaxFlushWaitMs);

        while (needFlush.load(std::memory_order_relaxed))
        {
                const bool hasDrainTask = isRunning.load(std::memory_order_acquire);

                if (!hasDrainTask)
                {
                        ProcessBuffer();
                }

                if (std::chrono::steady_clock::now() >= deadline)
                {
                        ...   // EmergencyLog(… "Flush gave up after " << MaxFlushWaitMs << "ms" …); then return
                }

                if (needFlush.load(std::memory_order_relaxed))
                {
                        std::this_thread::sleep_for(std::chrono::milliseconds(FlushPollPeriodMs));
                }
        }
}

Note the relaxed loads on needFlush against the acquire load of isRunning: the flag being polled is a signal that something changed, while the data it is a signal about — the queue contents — is synchronised by inputLock inside the drain, not by this loop.
