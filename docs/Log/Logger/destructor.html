~Logger

member of hbe::Logger Engine/Log/Logger.h noexcept closes the file after one last drain — and retires the singleton before doing it

Signature

~Logger() noexcept

Function description

Four statements, in this order:

instance = nullptr;

ProcessBuffer();

outFileStream.flush();
outFileStream.close();

Clearing instance first means the queue stops accepting from that instant: every SimpleLogger::Out now finds a null instance and diverts to the emergency path, which writes to standard output or standard error and never to the file. The drain that follows is a direct ProcessBuffer call on the destroying thread — it does not go through Flush, so it neither waits nor cares whether a drain task still exists, and it writes whatever is queued at this moment to both destinations. Then the stream is flushed and closed.

That is the whole shutdown guarantee in a clean run. StopTask has exactly one caller in the repository — Engine's signal handler — so an ordinarily terminating process reaches the file for the last time right here.

Lines produced after this point cannot reach the log file, and nothing tells you. The emergency path is silent about being an emergency: it writes to standard output, bypasses the level parameter and every category filter, and returns. A subsystem that logs from a static destructor, or from a thread still running after the engine is gone, produces text that looks like log output on the console and is absent from the file — the exact symptom that reads as "logging is broken". Order your shutdown so that logging ends before the logger does.
The final drain still writes to the console, which means it still needs the engine. ProcessBuffer hands the batch to both output functions, and the second is PrintStdIO → Engine::Get().ConsoleOutLn(…). Engine::Get() asserts that an instance exists and dereferences the pointer regardless. For a Logger that is an Engine member this happens to work: the PreEngineInit object that publishes the engine pointer is its first member and so is destroyed last, leaving the pointer live while the logger's destructor runs. A logger constructed anywhere else — or destroyed after its engine — has no such protection at this line.
The destructor does not stop the drain task. It clears no isRunning and releases no taskID, so a task that is still live when the object dies belongs to whoever called StartTask. That is why StopTask exists as a separate call and why the header insists IsDrainTaskRunning is not the same question as "does the logger exist".

Parameters

None.

Return value

void, from a noexcept destructor: an exception escaping any of this — from the output functions, from a stream — terminates rather than unwinding. There is also no report of whether the last batch made it: if the stream was already in a failed state (see the constructor's note), the final drain writes into a dead stream and the last lines of the run are lost quietly.

Examples

There is no call site for a logger destructor: the object is an Engine member, so it is destroyed with the engine and never explicitly. The nearest real shutdown sequence — the signal handler, which stops the drain task while it still can, and only then relies on the flush — is the correct way to think about this destructor's limits:

From Engine/Engine/Engine.cpp

void SignalHandler(int sigNum)
{
        auto& engine = Engine::Get();
        if (engine.GetLogger().IsDrainTaskRunning())
        {
                engine.GetLogger().StopTask(engine.GetTaskSystem());
        }
        else
        {
                engine.GetLogger().Flush();
        }
        ...
        engine.CloseLog();

        exit(128 + sigNum);
}

Note what that handler does not rely on: it exits through exit, so the engine's members — including this logger — are never destroyed, and the lines it wants preserved are written by StopTask or Flush rather than by the destructor. Treat this destructor as the clean-exit path only.
