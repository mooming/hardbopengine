SetLoggerStream

member of hbe::Logger Engine/Log/Logger.h public install the IO stream this logger's driver thread should drive, or withdraw it — the handover that makes stream destruction safe while another thread is running it

Signature

void SetLoggerStream(TaskStream* stream) noexcept

Function description

Installs the IO stream this logger's driver thread should drive, or withdraws it. The body is two policy checks, a lock acquisition and an assignment. The lock is the entire design, and the checks exist so that the acquisition is never attempted by a caller that cannot be satisfied — both messages are elided here, see the Notes below for what they report:

Assert(Engine::Get().GetTaskSystem().IsEngineLoopThread(),
	   "Setup and configuration belong to the engine loop thread, and this call is not on it …");

Assert(TaskSystem::GetCurrentStreamIndex() == TaskSystem::NonStreamIndex,
	   "Configuration may not run inside a task pass …");

std::lock_guard lock(driverLock);

loggerStream = stream;

Logger's IO stream is a service stream — the logger is one of its customers, as asynchronous file access will be — and it is a ride-on-thread stream, so its driver must be named rather than assumed. The task system installs it once its streams exist and withdraws it before it destroys them. That ordering is not politeness: driverThread outlives the task system by design, so a pointer left installed would be read on a pass whose stream had already been freed.

Passing the lock is what makes withdrawal mean something. DriverLoop holds driverLock across stream->Update(), so nullptr cannot land while a pass is in flight: the call blocks until that pass has returned. This is the only mechanism that lets the task system free its streams while another thread is running them.

Withdrawing also withdraws the drain task that lived on the stream, and the flag goes with it:

if (stream == nullptr)
{
    isRunning.store(false, std::memory_order_release);
}

Nothing can run that task any more, so leaving isRunning set would have every later Flush wait its full 1000 ms on an executor that no longer exists, then report the loss and assert. From here on the driver loop writes the queue directly — the same work with one fewer hop.

Parameters

ParameterTypeMeaning
stream TaskStream* The service stream to drive, or nullptr to withdraw it. Not owned: never freed here. The previous value, if any, is replaced without warning — there is one slot, not a stack of customers

Return value

None. The call cannot fail; the only thing it can do is wait for an in-flight pass.

Notes

  • Who calls it. The task system, from the engine loop thread — never the driver thread, and never from inside a task pass. TaskSystem installs &GetIOTaskStream() once its streams exist, and passes nullptr while shutting streams down. See TaskSystem.
  • Policy: setup and configuration belong to the engine loop thread, and this function checks it. The first statement is Assert(Engine::Get().GetTaskSystem().IsEngineLoopThread(), …), answered against engineLoopThreadID — the thread captured in the task system's initializer list, on its own page IsEngineLoopThread. The two legitimate callers already satisfy it, because each holds the line at its own end of the bargain: both live in TaskSystem, BuildStreams opens with Assert(IsEngineLoopThread()), and JoinAndClear withdraws only inside if (isEngineLoopThread && hasStreams) — that function is prepared to be called by a thread which does not own the run, and leaves the stream installed rather than dismantling another thread's structures. This method has no such foreign-thread path, so it is free to assert instead of negotiating.
  • What the second check adds. That the call is not happening inside a task pass — which being on the right thread does not exclude. The engine loop thread is entitled to configure, but not while it is draining the base stream on a task's behalf: DriverLoop holds driverLock across Update(), a pass on the IO stream runs the work that stream's tasks hand onward, and a task waiting on the base thread would have that thread parked here. So the second Assert requires TaskSystem::GetCurrentStreamIndex() == NonStreamIndex. Both checks sit before the lock_guard: placed after it, the thread is already blocked in the acquisition the checks exist to prevent and nothing would ever be reported. They are Asserts, so Debug and Dev report a violation while Release keeps the hang.
  • Why neither check is TaskSystem::IsBaseThread(). Measured, that predicate aborts the engine at startup. It tests the thread-local StreamIndex, which is NonStreamIndex on every thread outside a pass and is restored to it when a pass ends, so it means this thread is draining the base stream right now — and both legal callers run outside any pass, on the thread about to build or tear down the streams. Comparing thread ids against threadID is no better: that names the thread the logger writes from, which is the IO stream's, not the engine loop's. The pair that works is documented on IsEngineLoopThread.
  • Not on a logging path. It is not called by AddLog or any logging path.
  • Ordering. Withdrawal must precede stream destruction, and installing must follow stream construction. Both are the task system's obligation, and nothing in the signature enforces either.
