WriteLog

member of hbe::Logger private noexcept destination one: the log file, one line per element, flushed at the end of the batch

Signature

void WriteLog(const TTextBuffer& buffer) noexcept

Function description

auto& ofs = outFileStream;

for (auto& logText : buffer)
{
        ofs << logText << std::endl;
}

ofs.flush();

The first of the two functions installed into flushFuncs by the constructor, so the file is written before the console sees a batch. It adds exactly one thing to each line: a newline, via std::endl. The text itself is whatever ProcessBuffer rendered — timestamp, thread, category, level, message — with no trailing newline of its own.

The stream is flushed once per batch, not per line. A second flush may follow the batch inside ProcessBuffer if any line reached Warning, which is redundant work in the usual case and the reason severity affects how fast text reaches disk.

Stream failure is never examined, so an unwritable log file is indistinguishable from an idle logger. Nothing in this function, in FlushBuffer or in the constructor checks outFileStream's state: a path that could not be opened, a full disk, or a file that stopped accepting writes all leave the stream in a failed state while every call returns normally. Lines are discarded one batch at a time, and the console destination — which is installed after this one and is unaffected — keeps printing, which is how a "logging works" console coexists with an empty log file.
One writer at a time, and the guarantee comes from elsewhere. This function has no lock of its own. What serialises file writes is the isDraining claim taken by ProcessBuffer, plus the fact that AddLog's inline error path only runs on the log thread. Two drains cannot therefore be in this loop together. Output that does bypass the serialisation — the emergency path and the LOG_BREAK_IF_* / LOG_FORCE_PRINT_IMMEDIATELY builds — writes to the C++ standard streams rather than to this file, so interleaving is a console phenomenon here, not a file one.

Parameters

ParameterTypeRequirement
buffer const TTextBuffer& (HVector<HString>) Finished lines in output order; an empty buffer writes nothing and still flushes the stream. Each element is written with operator<< for std::basic_string over the engine's allocator, so it goes through c_str-equivalent data — embedded NULs would truncate a line here, though no Log code produces them

Return value

void, and not a count of bytes or lines. Because failures are unexamined, no caller of this function — including Flush two layers up — can distinguish "written to disk" from "discarded by a dead stream".

Examples

No call site names this function; the constructor installs it as one of the two output functions, and FlushBuffer invokes it:

From Engine/Log/Logger.cpp

flushFuncs.reserve(2);
flushFuncs.emplace_back([this](const TTextBuffer& buffer) { WriteLog(buffer); });
flushFuncs.emplace_back([](const TTextBuffer& buffer) { PrintStdIO(buffer); });

Reading the resulting file: every line is exactly what the drain built, so a line you cannot find is a line that was filtered, dropped or truncated upstream — AddLog for the first two, ProcessBuffer for the third — and not a line this function lost. One exception: the logger's own shutdown line is written with an explicit end-line marker (hendl appended in StopTask) on top of the newline added here, so a stopped logger leaves a blank line after Logger shall be terminated. — the only such gap in the file.
