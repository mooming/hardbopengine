Logger constructors

member of hbe::Logger Engine/Log/Logger.h 1 constructing form 4 deleted opens the file, builds the pools, and claims the process-wide instance pointer

Signature

Logger(const Logger&) = delete

Logger(Logger&&) = delete

Logger(Engine& engine, const char* path, const char* filename) noexcept

Function description

Construction is the whole setup, and it happens in one order that matters. The pools come first as members ("LoggerMemoryPool", then "LoggerInputPool"), then the body publishes instance = this and touches LogUtil::GetStartTime() purely to create the log clock's epoch. From that point on every allocation the constructor makes is inside AllocatorScope scope(allocator), with a nested scope for inputAlloc around the two queue reserves — so the logger's own storage is its own, never whatever scope happened to be open.

Then the file name is assembled: path is copied into logPath, every \ is replaced with /, the length of filename is measured (capped at Config::MaxPathLength, which is 512), a separator is added if the path did not already end in one, the file name is appended, and the buffer is shrunk to fit. Only then does outFileStream.open(logPath.c_str()) run.

Finally the two output functions are registered, in this order: a lambda calling WriteLog, then one calling PrintStdIO. That is the order a batch reaches the file and the console. The last statement is engine.SetLoggerReady(), which is the flag Engine reports as "logging available".

The queue is reserved for 16 lines on each side and the text buffer, filter map and destination list for 16, 16 and 2. Nothing else is pre-allocated: the queue grows on demand, from the logger's pools on the drain side and the thread-safe pool on the enqueue side.

An empty path reads one element before the buffer. The body takes auto endChar = logPath[logPath.size() - 1]; to decide whether a separator is needed, with no test for an empty string. On an empty path that index is size() - 1 on an unsigned count — a huge offset out of the allocation — and std::basic_string::operator[] has no bounds check to catch it, in any configuration. Pass at least one character; "./", as the engine does, is the smallest sensible value.
Nothing here prevents a second logger, and the singleton is not protected from one. The four deleted special members stop a copy or a move; they do not stop a second call to this constructor, which overwrites instance with the new object while the first object keeps its own open file and its own pools. Whichever is destroyed first clears instance unconditionally, and from that moment every SimpleLogger::Out in the process silently falls through to the emergency path. A process with one Engine cannot reach this; one that constructs two, or that constructs a logger outside an engine, can.
The file is truncated, not appended to, and the open is not checked. std::ofstream::open with its default mode truncates, so a relaunch replaces the previous run's log rather than continuing it. Neither the truncate nor a failed open is reported: outFileStream simply enters a failed state, and every later WriteLog writes into a dead stream and is discarded without a word. If a log file is missing, suspect this line before suspecting the logging calls.
The one precondition check is an Assert. The body opens with Assert(engine.IsMemoryManagerReady()); — the family documented in Core: Debug, which means it is live in Debug and Dev and compiled out in Release. The pools it protects are registered with the memory manager as they are constructed, so the ordering requirement is real whether or not the build reports a violation.

Parameters

ParameterTypeRequirement
engine Engine& Must have a ready memory manager; its only use is SetLoggerReady() and the assertion. It must outlive the logger — Engine satisfies this by holding the Logger as a member
path const char* At least one character, for the reason above. Directory part of the log file; backslashes are rewritten as forward slashes, and a trailing separator is accepted and not doubled
filename const char* File name only. Its length is measured with StringUtil::StrLen(filename, Config::MaxPathLength), so a longer string is under-reserved rather than truncated, and then appended in full. A relative name is resolved against the process working directory

Return value

A constructed Logger — and, as a side effect, the process's logging instance. There is no success value: a log file that could not be opened still yields a fully working logger whose lines go to the console only. Because the type is final and uncopyable, the object you construct is the only handle to it; everybody else reaches it through Get.

Examples

The only construction in the engine — an Engine member, initialised in the constructor's member list:

From Engine/Engine/Engine.cpp

Engine::Engine()
        : preEngineInit(this)
        , isMemoryManagerReady(false)
        , ...
        , logFile("helowlevel.log")
        , memoryManager(*this)
        , statistics(*this)
        , logger(*this, "./", "hardbop.log")   // the log file lands next to the working directory
{
        time::ResetEngineEpoch();
        LogUtil::ResetStartTime();
        ...
}

Two ordering facts are visible in that snippet and both are load-bearing. The logger is constructed after memoryManager and statistics, which is what makes the IsMemoryManagerReady assertion satisfiable — members initialise in declaration order, not in the order you write them. And LogUtil::ResetStartTime() runs in the constructor body, that is, after this constructor has already logged nothing but has created the epoch, so the epoch is then moved to the end of engine construction.
