StopTask

member of hbe::Logger Engine/Log/Logger.h public retire the drain task cooperatively, write the last batch, close the file

Signature

void StopTask(TaskSystem& taskSys);

Function description

The drain task ends itself; StopTask only asks it to and then waits (see StartTask's return-value trick). Clearing isRunning is the request — a runnable in flight sees it on its next iteration and reports its range complete instead of draining once more.

Then:

  1. The task is found by taskID. If it is missing or reports HasDone(), the id is released and the function returns immediately — no final line, no final drain, no close.
  2. Otherwise drainTask->Wait() blocks until the drain acknowledges, and the id is released.
  3. threadID is reset to a default-constructed id, so no thread is the log thread any more.
  4. One last line is logged — "Logger shall be terminated." with an explicit end-line marker (hendl), unlike every other line in the engine, which leaves the newline to the writer.
  5. ProcessBuffer is called directly, writing that line and whatever the drain left behind to both destinations, and the file stream is flushed and closed.

After this call the logger is still a live object and still accepts AddLog: the queue simply has no drainer, so lines accumulate in memory until the destructor writes them. The exception is a line at FatalError, which calls Flush itself and, with no drain task, will drain inline.

Called with no drain task running, it blocks forever. The header says so in terms: IsDrainTaskRunning exists precisely because StopTask "called without a task … waits for something that was never started". The registry lookup and the HasDone() test catch a task that never existed or already finished, but a logger whose task the registry could not track (the failure branch in StartTask) still has isRunning set, and that combination is exactly what the check in the engine's signal handler guards against before it chooses between this call and Flush. Ask the question, then call.
The early-return branch skips the last two steps above. When the task is absent or already done, the function releases the id and leaves — the final log line is never enqueued, no final drain runs, and outFileStream is not flushed or closed here. Whatever was queued stays queued until the destructor, and the file is closed by the stream's own destructor with no explicit flush first. So calling StopTask twice, or calling it after the drain has already retired, is not a no-op: it silently loses the shutdown flush that a caller reasonably believes it performed.
Two lines are written by this function and by nobody else. Its own final line and anything still in the queue at that moment. If you want your own last message in the file, log it before calling StopTask — after it, you are writing into a queue with no drainer, and the level parameter and category filters are still consulted, so a suppressed line never appears at all.

Parameters

ParameterTypeRequirement
taskSys TaskSystem& The same system passed to StartTask, still able to resolve FindTask, Wait and ReleaseTask for that id. It is also used by the final AddLog, which reads the IO stream's existence through it before deciding to wake it

Return value

void. Nothing distinguishes "drain task waited for and released" from "id released, no drain performed" — the difference is visible only in whether the log file got its final bytes. Treat a successful return as "I asked the drain to stop", and rely on the destructor or an explicit Flush if the write itself must be certain.

Examples

The only caller in the repository — and it asks first whether a drain task exists:

From Engine/Engine/Engine.cpp

void SignalHandler(int sigNum)
{
        auto& engine = Engine::Get();
        if (engine.GetLogger().IsDrainTaskRunning())
        {
                engine.GetLogger().StopTask(engine.GetTaskSystem());
        }
        else
        {
                engine.GetLogger().Flush();
        }
        ...
}

The shape to copy is the branch, not just the call: a logger that was constructed but never started has to be flushed directly, because StopTask on it would wait for a task that does not exist. Note also that this handler is running inside a signal — Wait(), a mutex and a file write are all doing work that a signal context does not normally permit; the engine accepts that because losing the crash report is the alternative.
