ReportMemoryConfiguration

member of hbe::Logger Engine/Log/Logger.h only exists when PROFILE_ENABLED is 1 hand the logger's own pool to the memory manager's pool-configuration report

Signature

Both the declaration and the definition sit inside the same guard, in the header and in the source:

#if PROFILE_ENABLED
void ReportMemoryConfiguration();
#endif // PROFILE_ENABLED

Function description

One statement: allocator.ReportConfiguration(); — that is, the logger's "LoggerMemoryPool" and nothing else. The pool walks its banks, collects each block size against the high-water mark of blocks used, and registers the result with MemoryManager under the interned pool name; what it costs and where the summary is printed is Memory's business. Note the asymmetry this method encodes: the *input* pool "LoggerInputPool" is a ThreadSafeMultiPoolAllocator with its own ReportConfiguration, and the logger never calls it, so this report never covers the pool that producers allocate from.

It is a profiling instrument, not part of logging: no log line is produced, the queue is untouched, and no output destination is involved.

In a default build this member does not exist, so a call is a compile error, not a link error. BuildConfig.h sets PROFILE_ENABLED to 0, the declaration inside Logger.h is inside the guard, and the MultiPoolAllocator::ReportConfiguration it calls is also guarded. That is the good failure mode — a mistyped call in a normal build is diagnosed immediately — but it also means code that wants to call it must carry the same #if. The one engine call site does exactly that: Engine::PreShutdown() wraps it in #if PROFILE_ENABLED, so in a default build that line is not compiled either and the member has no live caller.
Nothing here is thread-safe by construction, and the engine's own call site shows the exposure. The method has no lock, and the bank walk it triggers reads pool state that ProcessBuffer writes whenever the drain runs. Engine::PreShutdown() calls it between two of its own log statements, with the drain task still live — the read is concurrent with the pool's writer. StopTask first is the point at which the pool is quiescent, and nothing does that here.

Parameters

None.

Return value

void, non-const, and not noexcept — the only logger method with neither qualifier. It reports by side effect into the memory manager, so a caller gets no data back and no indication that profiling was compiled out (which, in a build where PROFILE_ENABLED is 0, is not a thing that can happen: the call would not compile).

Examples

The engine's shutdown hook, which is the only call site in the repository and carries the matching guard:

From Engine/Engine/Engine.cpp

void Engine::PreShutdown()
{
        auto log = Logger::Get(ToCompactMethodName(__PRETTY_FUNCTION__));

        log.Out("Engine PreShutdown [Start]");

#if PROFILE_ENABLED
        logger.ReportMemoryConfiguration();
#endif // PROFILE_ENABLED

        memoryManager.PreEngineShutdown();

        log.Out("Engine PreShutdown [Done]");
}

Two things are visible in the placement. The report is emitted while the drain task is still running — the log lines either side of it go through the same pools it is about to read — and it happens before memoryManager.PreEngineShutdown(), so the figures describe the pool as it stood at the start of shutdown rather than as it stands when the logger is finally destroyed. For the pool's numbers without a guard at all, MultiPoolAllocator::PrintUsage is the ungated sibling, and Core: SystemStatistics prints allocator profiles as log lines — see the drain for how such a line reaches the file.
