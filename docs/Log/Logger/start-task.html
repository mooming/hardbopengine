StartTask

member of hbe::Logger Engine/Log/Logger.h public attach the drain task to the IO stream — the call that turns a buffering queue into a writing one

Signature

void StartTask(TaskSystem& taskSys);

Function description

Before it does anything with the task system, it logs one line: "Logger started." at Info under the category GetName() — enqueued, like everything else, so it reaches the file whenever the drain first runs.

The rest, in order:

  1. A runnable is defined that reads isRunning with a relaxed load, returns 1 if it is clear, and otherwise calls ProcessBuffer and returns 0.
  2. isRunning is stored true with release ordering — before the task is created.
  3. taskID = taskSys.CreateTask("Logger", runnable, this) registers the drain and keeps its identity.
  4. The task is looked up. If the registry cannot produce it, an Error line is logged and the function returns without enqueuing anything.
  5. Otherwise a ranged task over indices 0 to 1 is generated from it and enqueued on the IO task stream (TaskSystem::GetIOTaskStreamIndex()).
  6. threadID is captured from that stream — the value that later decides whether Flush drains inline and whether an error line is written directly.

The runnable's return value is the mechanism worth understanding. A TRunnable returns the number of indices it has finished, and returning less than the range means "call me again". The range here is a single index, so 0 means the drain is rescheduled and 1 means the task is complete — a self-terminating loop: the drain runs again and again while isRunning holds, and the moment StopTask clears it the runnable reports the index as done and the task retires itself without anyone cancelling.

Draining has no back-off of its own. Each pass that finds hasInput clear returns after one atomic load, but the runnable still reports the range unfinished, so the stream is entitled to call it again immediately. The only thing in this module that yields is WaitForFlush's sleep, on the waiting thread. What an idle drain actually costs — whether the stream parks between invocations — is TaskStream behaviour, and it is the question to ask before assuming an idle logger is free.
If the registry cannot track the task, the logger degrades into something that does not match its own error message. The Error line promises "log lines are flushed inline by whoever produces them", but isRunning was already stored true in step 2 and nothing clears it on this path. Consequences: WaitForFlush only drains inline when no drain task can run, so from here on every Flush polls for the full 1000 ms, then reports to standard error that the queue is still buffered; the queued lines are written only by the direct ProcessBuffer calls in StopTask and the destructor. A producer that hits the force-flush threshold therefore stalls a full second per threshold. This branch is reachable only when the task registry declines to track the task — but nothing here tests that it happened.
Call it exactly once, after the task system is initialised. The function overwrites taskID without releasing the previous one, so a second call leaks the first task identity and leaves two drains competing for the isDraining claim — the loser of that claim returning having done nothing. Engine calls it once, from Initialize, under EInitLevel::Logger, which also implies EInitLevel::TaskSystem — that implication is what makes the argument valid.

Parameters

ParameterTypeRequirement
taskSys TaskSystem& Already initialised, with an IO stream available and a working task registry: it is used for GetIOTaskStreamIndex, CreateTask, FindTask, Enqueue, GetIOTaskStream and, through the stream's thread, GetThreadID. It must outlive the logger's logging, since StopTask needs it again

Return value

void, and there is no status to inspect: the registry-tracking failure is reported only as a log line in the category you may already have filtered. If you must know whether the drain is live afterwards, ask IsDrainTaskRunning — and be aware that in the failure case above it answers true, because it reports the flag rather than the task.

Examples

The engine's wiring — start the task system, then attach the logger to it:

From Engine/Engine/Engine.cpp

void Engine::Initialize(int argc, const char* argv[], EInitLevel levels)
{
        if (HasFlag(levels, EInitLevel::Logger))
        {
                levels = levels | EInitLevel::TaskSystem;
        }

        if (HasFlag(levels, EInitLevel::TaskSystem))
        {
                taskSystem.Initialize();
                isTaskSystemReady = true;
        }

        if (HasFlag(levels, EInitLevel::Logger))
        {
                logger.StartTask(taskSystem);
                isLoggerReady = true;
        }
        ...
}

Everything logged between construction and this call is buffered rather than written — that is normal and not a lost line, because the file is written by the drain this function installs. What the call does change is Flush: before it, a flush drains inline on the caller; after it, a flush from any other thread waits for the drain instead.
