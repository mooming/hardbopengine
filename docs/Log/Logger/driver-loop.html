DriverLoop

member of hbe::Logger Engine/Log/Logger.h private the driver thread's body — one pass of the IO stream, or a direct write when there is no stream yet

Signature

void DriverLoop() noexcept

Function description

The body of driverThread. It runs one pass of the IO stream on the logger's own thread, or writes the log queue directly when no stream has been handed over yet — the same work with one fewer hop, which is what lets logging work before the task system exists and after it is gone.

threadID = std::this_thread::get_id();
TaskSystem::SetThreadName("LogDriver");

auto log = Get(GetName());
log.Out("Log driver thread is running.");

while (driverRunning.load(std::memory_order_acquire))
{
    TaskStream* stream = nullptr;
    {
        std::lock_guard lock(driverLock);
        stream = loggerStream;

        if (stream != nullptr)
        {
            (void) stream->Update();
        }
    }

    if (stream != nullptr)
    {
        stream->WaitForWork(std::chrono::milliseconds(20));
    }
    else
    {
        ProcessBuffer();
        std::this_thread::sleep_for(std::chrono::milliseconds(1));
    }
}
{
    std::lock_guard lock(driverLock);
    if (loggerStream != nullptr)
    {
        while (loggerStream->Update())
        {
        }
    }
}

ProcessBuffer();

That first log line is deliberate and exists for a reason worth stating: a thread which never logs is a thread whose name is never observable, because every log line is attributed to the thread that wrote it. One line from this thread is what makes "LogDriver" visible in a log rather than assumed from the call that set it.

Two ways to wait

With a stream installed the thread waits on the stream itself, not on a timer:

  • stream->WaitForWork(20ms) — the wake-up is what makes the thread cheap when nothing is happening and immediate when something is. A log line already wakes that stream, so one wake-up serves both customers of one thread.
  • The 20 ms timeout is a safety net, not the mechanism. The wake-up notification is issued without the queue lock held, so a lost notification costs at most one interval rather than a stall that never ends.
  • With no stream there is nothing to wait on, so the other arm of the same test calls ProcessBuffer and sleeps 1 ms.

The pass's answer is discarded with (void). Update reports false both when the stream was asked to close and when it found nothing to take, and for a driven stream the idle answer is the ordinary one — TaskStream::RunLoop answers the same false with a wait, and this loop does the same one line later with WaitForWork(20ms). Reading the idle answer as a failure would stop a quiet engine, because a fatal line is Flush, debugBreak and Assert(false) — the only failure this thread can survive is one where the stream is gone, and that is the arm above.

The last pass

After the loop the thread takes driverLock in a scope of its own, calls loggerStream->Update() until it reports no more work, releases the lock, and finishes with ProcessBuffer — outside it, so the last write to the file does not hold the lock that SetLoggerTaskStream_MainThread needs to withdraw the stream. This lives here rather than in StopDriverThread so that the final write is performed by the thread that owns the file — see that page for why the ordering matters.

Parameters

None. Everything it needs is member state: driverRunning for the loop condition, loggerStream and driverLock for the pass.

Return value

None. Returning ends the driver thread; StopDriverThread joins it.

Notes

  • Private, and reachable only as a thread body. The constructor starts it with driverThread = std::thread([this] { DriverLoop(); }). Nothing calls it directly, which is why it has no overload and no return value.
  • Lock discipline. driverLock is held across Update(), never around the pointer read alone. That is what makes SetLoggerTaskStream_MainThread with nullptr a synchronisation point rather than a flag write. The cost of holding it that wide is that Update runs tasks, so a task pass executes inside this mutex, and anything a task reaches that takes driverLock would be waiting on a pass that is itself — std::mutex is not recursive. That is the reason SetLoggerTaskStream_MainThread asserts instead of waiting, and the reason no logging path takes this lock at all.
  • Starts with the logger, not with the first subsystem that wants to write a line, so a line emitted during early construction has somewhere to go. Logging never depends on the subsystem it is reporting on.
